# §4.2 Параметры DAG

В [§4.1](chapter-04-01.md) мы ввели DAG и контекстный менеджер `with DAG(...)`. В конструктор `DAG()` передаются параметры, которые задают идентификатор пайплайна, расписание, начальную дату и другие свойства. В этом разделе разобраны основные параметры DAG: **dag_id**, **schedule_interval** (cron или timedelta), **start_date**, **tags**, а также кратко **catchup** и **backfill**. Детали расписания и логической даты запуска — в [главе 5](chapter-05-02.md).

---

## 4.2.1. dag_id

**dag_id** — обязательный строковый параметр, уникальный идентификатор DAG в рамках установки Airflow. По нему пайплайн отображается в UI и хранится в метаданных; его же используют в CLI и API. Рекомендуется задавать осмысленное имя: латиница, цифры, подчёркивания (например, `sales_daily_load`, `staging_returns`). Дубликаты `dag_id` в разных файлах приводят к тому, что «побеждает» один из DAG (обычно загруженный позже). См. [§3.4](chapter-03-04.md).

---

## 4.2.2. schedule_interval (расписание)

**schedule_interval** задаёт, как часто планировщик создаёт новые запуски DAG. Передаётся в конструктор `DAG()`.

Типичные значения:

- **Строка в формате cron** — например, `"0 2 * * *"` (каждый день в 02:00), `"0 0 * * 1"` (каждый понедельник в полночь). Синтаксис cron из пяти полей: минута, час, день месяца, месяц, день недели.
- **Объект `timedelta`** (из `datetime`) — например, `timedelta(hours=6)` (каждые 6 часов), `timedelta(days=1)` (раз в день). Удобно для интервалов, заданных в часах или днях.
- **`None`** — DAG не запускается по расписанию; только ручной запуск (Trigger DAG) или внешний триггер.

В Airflow 2.2+ расписание можно задавать также через объект **Schedule** (например, `CronTrigger` или `TimedeltaTrigger`); для начала достаточно строки cron или `timedelta`. Подробнее синтаксис cron и примеры — в [§5.2](chapter-05-02.md).

Пример:

```python
from datetime import timedelta
from airflow import DAG

with DAG(
    dag_id="daily_sales",
    schedule_interval="0 2 * * *",  # ежедневно в 02:00
    # или: schedule_interval=timedelta(days=1),
) as dag:
    ...
```

## 4.2.3. start_date

**start_date** — дата (и при необходимости время), с которой планировщик начинает генерировать запуски для этого DAG. Обычно задаётся как `datetime` в прошлом (например, фиксированная дата «с какого дня считаем пайплайн»). От `start_date` и `schedule_interval` Airflow строит ряд логических дат запуска (logical date / execution date); каждая такая дата соответствует одному DAG Run. Важно: **start_date** — это не «момент первого запуска в реальном времени», а начало ряда периодов для пайплайна. Детали — в [§5.3](chapter-05-03.md).

Пример:

```python
from datetime import datetime
from airflow import DAG

with DAG(
    dag_id="daily_sales",
    schedule_interval="0 2 * * *",
    start_date=datetime(2025, 1, 1),
) as dag:
    ...
```

---

## 4.2.4. tags

**tags** — список строк (тегов) для фильтрации и группировки DAG в UI. Удобно помечать пайплайны по команде, источнику данных или окружению: например, `tags=["sales", "daily", "prod"]`. В веб-интерфейсе можно отфильтровать список DAG по тегу. Не обязательный параметр.

---

## 4.2.5. catchup (кратко)

**catchup** — булев параметр. Если `catchup=True` (по умолчанию в ряде версий) и DAG включён с задержкой, планировщик может создать запуски за все пропущенные периоды между `start_date` и «сейчас» (догон, catchup). Если `catchup=False`, новые запуски создаются только начиная с текущего момента по расписанию, без автоматического догона за прошлое. Подробнее — в [§5.4](chapter-05-04.md).

Для многих пайплайнов данных удобно задавать `catchup=False`, чтобы не порождать массу старых запусков при первом включении DAG. Запуск за прошлые периоды при необходимости делают вручную через backfill.

---

## 4.2.6. backfill (кратко)

**Backfill** — ручной запуск DAG за выбранные прошлые даты (диапазон логических дат). Выполняется из UI (Trigger DAG с параметрами) или из CLI: `airflow dags backfill -s <start_date> -e <end_date> <dag_id>`. Используется, когда нужно «догнать» данные за период, когда DAG не работал или был отключён. См. [§5.4](chapter-05-04.md) и [Глоссарий](glossary.md).

---

## 4.2.7. Другие полезные параметры

В конструктор `DAG()` можно передать и другие аргументы, например:

- **default_args** — словарь аргументов по умолчанию для всех задач этого DAG (retries, retry_delay, owner, email и т.д.); см. [§4.3](chapter-04-03.md) и [§7.1](chapter-07-01.md).
- **max_active_runs** — максимальное число одновременных DAG Run для этого DAG; помогает ограничить нагрузку.
- **concurrency** — лимит одновременных экземпляров задач внутри одного DAG (в зависимости от версии и настроек).

Их можно задать по мере необходимости; для первого DAG достаточно `dag_id`, `schedule_interval` и `start_date`.

---

## Ключевое

- **dag_id** — обязательный уникальный идентификатор DAG.
- **schedule_interval** — расписание: строка cron (например, `"0 2 * * *"`), `timedelta` или `None` (только ручной запуск).
- **start_date** — дата начала ряда логических дат запуска; детали взаимодействия с расписанием — в [§5.3](chapter-05-03.md).
- **tags** — список тегов для фильтрации в UI.
- **catchup** — при `True` планировщик может создавать запуски за пропущенные периоды; при `False` — только «вперёд» от текущего момента. **Backfill** — ручной запуск за выбранные прошлые даты.

В [§4.3](chapter-04-03.md) разберём задачу (Task): экземпляр оператора, привязка к DAG и уникальный task_id.
