# §6.5 Проверка в UI

В [§6.4](chapter-06-04.md) мы связали шаги extract >> transform >> load и настроили retries и алерты. Осталось **проверить** пайплайн в веб-интерфейсе: убедиться, что прогон завершается успешно, при сбое посмотреть логи и при необходимости выполнить повтор задачи. В этом разделе — что смотреть в UI после запуска дага загрузки и как действовать при ошибке. В конце главы 6 — выводы и задание. Подробнее об интерфейсе Airflow — в [§4.5](chapter-04-05.md); далее в [главе 7](chapter-07-01.md) — операторы, сенсоры и хуки.

---

## 6.5.1. Успешный прогон

После Trigger DAG или по расписанию откройте DAG в UI и перейдите к **Graph View** или **Tree View**. Для выбранного DAG Run проверьте:

- Все задачи (extract, transform, load) в статусе **success** (зелёные). Порядок выполнения должен соответствовать графу: сначала extract, затем transform, затем load.
- В **Tree View** по строке run видно, что каждая ячейка задачи окрашена как успешная; время выполнения отображается при наведении или в деталях задачи.
- В целевой БД или файловой системе данные за логическую дату run появились (проверка по месту назначения — вне UI).

Успешный прогон подтверждает, что цепочка зависимостей работает, скрипты и подключения настроены верно, и идемпотентность при перезапуске за ту же дату не ломает результат.

---

## 6.5.2. Просмотр логов задачи

Если нужно проверить, что именно выполнилось (какая дата подставлена, какой путь к файлу, сколько строк обработано), откройте **логи** задачи:

1. В Graph View или Tree View кликните по задаче (extract, transform или load).
2. В меню выберите **Log**.
3. В логах будет вывод команды (BashOperator) или функции (PythonOperator): print, логирование, трассировка при исключении. При нескольких попытках (retry) в логах видны все попытки.

По логам можно убедиться, что в скрипт передаётся правильная дата (`{{ ds }}`), путь к файлу корректен и загрузка в БД прошла без ошибок. Это основной способ диагностики при сбоях.

---

## 6.5.3. Повтор при ошибке

Когда задача перешла в статус **failed** (после исчерпания retries или без retry):

- **Логи** — первое действие: открыть Log и по выводу понять причину (файл не найден, ошибка подключения к БД, исключение в коде). Исправьте код или данные и затем перезапустите.
- **Clear** — сбросить состояние задачи (и при необходимости следующих по графу) для этого run. Планировщик заново поставит задачу в очередь, и она выполнится с текущим кодом. Подходит, когда ошибка была временной или уже исправлена в коде. После Clear убедитесь, что задачи идемпотентны, чтобы повтор не продублировал данные.
- **Retry** — в части версий UI есть действие «Retry» для упавшей задачи: повторная попытка без сброса всего run. Эффект аналогичен очередному retry в рамках настроенных retries.
- **Trigger DAG** за ту же логическую дату (если DAG позволяет или через backfill) — создаётся новый run за эту дату; используйте при идемпотентной загрузке, когда нужно «перезалить» день после исправления.

Рекомендация: после исправления кода сохраните файл DAG, дождитесь обновления в Airflow ([§3.4](chapter-03-04.md)), затем сделайте Clear упавшей задачи или Trigger DAG (backfill) за нужную дату и снова проверьте логи.

## 6.5.4. Чек-лист проверки дага загрузки

- [ ] DAG появляется в списке, парсится без ошибок (нет метки parse error).
- [ ] Trigger DAG (или run по расписанию) создаёт run; в Graph/Tree все задачи переходят в success по порядку extract → transform → load.
- [ ] Логи каждой задачи содержат ожидаемый вывод (дата, пути, количество строк при необходимости).
- [ ] Данные за логическую дату run присутствуют в целевом слое (Raw/Staging).
- [ ] При имитации сбоя (например, неверный путь) задача уходит в retry, затем в failed; логи показывают причину; после исправления Clear или повторный запуск приводит к успеху.

## Ключевое по главе 6 и задание

**Выводы главы 6:**

1. **Постановка:** источник (файл/БД), назначение (Raw/Staging), идемпотентность (перезапись среза или upsert).
2. **Таски:** extract (BashOperator/PythonOperator, при необходимости Hook), transform и load (PythonOperator с Pandas/SQL или BashOperator + скрипт), загрузка в БД с учётом идемпотентности.
3. **Связывание:** extract >> transform >> load; retries и retry_delay в default_args; on_failure_callback для алертов.
4. **Проверка в UI:** успешный прогон по статусам в Graph/Tree, логи задач для диагностики, Clear или повторный запуск при ошибке.

**Задание:**

- **Реализовать даг загрузки по сценарию.** По выданному или выбранному сценарию (источник, целевая таблица/файл, расписание) реализуйте полный DAG: постановка (§6.1), таски извлечения (§6.2), преобразования и загрузки (§6.3), связи и retry (§6.4). Проверьте прогон в UI (§6.5), убедитесь, что логи корректны и данные попадают в назначение. При необходимости добавьте сенсор ожидания файла ([§7.2](chapter-07-02.md)) или настройте Connections ([§7.5](chapter-07-05.md)).

В [главе 7](chapter-07-01.md) — операторы (BashOperator, PythonOperator, шаблоны), сенсоры, хуки, XCom и Variables/Connections.
