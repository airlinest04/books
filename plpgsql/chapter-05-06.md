# §5.6 SECURITY DEFINER и INVOKER

В [§5.5](chapter-05-05.md) мы разобрали вызов функции из SQL. В этом разделе рассмотрим, **от чьего имени** и **с какими правами** выполняется функция: **SECURITY INVOKER** (по умолчанию) — с правами вызывающего; **SECURITY DEFINER** — с правами владельца функции. Разберём, когда нужен SECURITY DEFINER, и кратко — меры безопасности (search_path, ограничение прав на выполнение). С этим завершается глава 5; далее — гл. 6 (процедуры). См. [Глоссарий](glossary.md).

---

## 5.6.1. SECURITY INVOKER (по умолчанию)

При **SECURITY INVOKER** (по умолчанию) функция выполняется с правами **роли, которая её вызвала**. Доступ к таблицам, представлениям и другим объектам проверяется для этой роли: если вызывающий не имеет SELECT на таблицу, обращение к ней внутри функции приведёт к ошибке доступа. См. [Глоссарий](glossary.md).

Такой режим привычен: пользователь через функцию не получает прав выше своих; любая операция в функции допустима только если она разрешена его роли напрямую. Для большинства функций INVOKER достаточен.

Указать явно: **SECURITY INVOKER** в CREATE FUNCTION (или **EXTERNAL** SECURITY INVOKER для совместимости со стандартом).

---

## 5.6.2. SECURITY DEFINER — выполнение с правами владельца

При **SECURITY DEFINER** функция выполняется с правами **владельца функции** (роли, создавшей или последней изменившей функцию). Вызывающий может не иметь прав на таблицы, к которым обращается функция, — проверка прав выполняется для владельца. Это позволяет дать ограниченный доступ: пользователь вызывает только функцию, а функция внутри выполняет операции от имени владельца (например, запись в служебную таблицу, к которой у пользователя нет прямого доступа). См. [Глоссарий](glossary.md).

Типичные случаи использования SECURITY DEFINER:

- **Единая точка доступа к данным:** пользователи не имеют прав на таблицу, но могут вызывать функцию, которая проверяет параметры и выполняет только разрешённые действия.
- **Аудит и логирование:** функция пишет в таблицу логов от имени владельца, вызывающий не имеет прав на запись в эту таблицу.
- **Обход ограничений в контролируемом виде:** выполнение операций (например, смена пароля, изменение статуса), которые должны быть доступны только через проверенный код функции.

---

## 5.6.3. Риски SECURITY DEFINER и search_path

Функция SECURITY DEFINER выполняется с правами владельца; если в коде используются **неквалифицированные имена** объектов (таблица без схемы), поиск идёт по **search_path** сессии. Злоумышленник с правом создавать объекты в одной из схем в search_path может создать таблицу или функцию с тем же именем — и функция выполнит обращение к подменённому объекту. См. [Глоссарий](glossary.md).

Рекомендация (по документации PostgreSQL): для SECURITY DEFINER задавать **жёсткий search_path** при создании функции, например **SET search_path = доверенная_схема, pg_temp** (pg_temp в конце, чтобы временные объекты не подменяли постоянные). Тогда поиск по неполному имени не выйдет за пределы указанных схем. Пример:

```sql
CREATE FUNCTION check_password(uname text, pass text) RETURNS boolean
AS $$ ... $$
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = admin, pg_temp;
```

В теле по возможности использовать **квалифицированные имена** (схема.таблица).

---

## 5.6.4. Ограничение прав на выполнение функции

По умолчанию право **EXECUTE** на новую функцию выдаётся **PUBLIC**. Для SECURITY DEFINER часто нужно **ограничить** круг вызывающих: создать функцию, **REVOKE EXECUTE** у PUBLIC, **GRANT EXECUTE** только нужным ролям. Чтобы не было «окна», когда функция доступна всем, создание и выдача прав лучше выполнять в одной транзакции. См. [Глоссарий](glossary.md).

Пример (по документации PostgreSQL):

```sql
BEGIN;
CREATE FUNCTION check_password(uname text, pass text) RETURNS boolean
AS $$ ... $$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = admin, pg_temp;
REVOKE ALL ON FUNCTION check_password(text, text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION check_password(text, text) TO app_role;
COMMIT;
```

---

## Ключевое

- **SECURITY INVOKER** (по умолчанию) — функция выполняется с правами **вызывающего**; доступ к объектам проверяется для его роли.
- **SECURITY DEFINER** — функция выполняется с правами **владельца**; используется для контролируемого доступа к объектам, на которые у вызывающего нет прав.
- Для SECURITY DEFINER задавайте **SET search_path** в CREATE FUNCTION (доверенные схемы, pg_temp в конце) и по возможности используйте квалифицированные имена объектов.
- Ограничивайте **EXECUTE**: REVOKE у PUBLIC, GRANT только нужным ролям; создание и выдача прав — в одной транзакции.
