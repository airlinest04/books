# Глоссарий

Термины книги «Neoflex Datagram» в порядке появления. Сокращения и английские эквиваленты приведены где уместно.

---

**Neoflex Datagram** — российская ETL-платформа для Big Data: визуальное проектирование пайплайнов интеграции и преобразования данных с генерацией кода на Scala или Python и исполнением на Apache Spark. См. [§1.1](chapter-01-01.md).

**ETL** (Extract, Transform, Load) — извлечение, преобразование и загрузка данных; модель пайплайна данных: чтение из источников, трансформации, запись в целевые хранилища или витрины. См. [§1.1](chapter-01-01.md).

**Big Data** (большие данные) — сценарии обработки данных, требующие распределённой обработки (кластер), больших объёмов и разнородных источников/назначений (HDFS, Hive, Kafka, DWH). В контексте книги — область применения Datagram. См. [§1.1](chapter-01-01.md).

**Apache Spark** — открытый движок распределённой обработки данных (batch и streaming); среда исполнения сгенерированного Datagram кода. См. [§1.1](chapter-01-01.md).

**Apache Airflow** — платформа оркестрации заданий (workflow); один из вариантов оркестратора для запуска этапов пайплайнов Datagram. См. [§1.1](chapter-01-01.md).

**Apache Oozie** — оркестратор заданий в экосистеме Hadoop; альтернатива Airflow для запуска этапов пайплайнов Datagram. См. [§1.1](chapter-01-01.md).

**low-code** — подход к разработке с минимизацией ручного кода за счёт визуального проектирования и готовых компонентов; в Datagram — сборка потока в дизайнере с генерацией кода. См. [§1.1](chapter-01-01.md).

**Neoflex Reporting** — экосистема решений Neoflex для корпоративной отчётности и аналитики; Datagram входит в неё как компонент загрузки и преобразования данных. См. [§1.1](chapter-01-01.md).

**Neoflex Reporting Big Data Edition** — направление линейки Neoflex Reporting для проектов на больших данных; включает Datagram для ETL и построения хранилищ и витрин. См. [§1.1](chapter-01-01.md).

**Дизайнер трансформаций** — компонент Datagram для визуальной разработки потока данных (источники, преобразования, приёмники) и генерации кода трансформаций. См. [§1.1](chapter-01-01.md).

**Дизайнер Workflow** — компонент Datagram для визуальной разработки потока управления (последовательные и параллельные этапы, условия) и генерации описаний для Airflow или Oozie. См. [§1.1](chapter-01-01.md).

**Model Driven Architecture (MDA)** — архитектура, управляемая моделью: разработка ведётся от визуальной или декларативной модели процесса, исполняемый код получается автоматической генерацией. В Datagram: модель в дизайнерах трансформаций и Workflow → генерация Scala (Python) и описаний для оркестратора. См. [§1.2](chapter-01-02.md).

**Реестр российского ПО** — единый реестр программ для ЭВМ и БД, ведение которого регулируется российским законодательством; включение продукта важно для заказчиков с требованиями по использованию российского ПО. См. [§1.3](chapter-01-03.md), [§9.4](chapter-09-04.md).

**Импортозамещение** — переход с зарубежных платформ и решений на российские или на открытый стек с российской поддержкой; в контексте ETL — замена инструментов вроде InfoSphere, ODI на решения типа Datagram. См. [§1.3](chapter-01-03.md), [§9.4](chapter-09-04.md).

**Lineage** (линия происхождения, прослеживаемость данных) — отслеживание происхождения поля или набора данных по цепочке преобразований: откуда пришло поле и какие операции к нему применены; в Datagram поддерживается в дизайнере трансформаций. См. [§2.1](chapter-02-01.md), [§5.2](chapter-05-02.md).

**Маппинг** (mapping) — соответствие между полями входа и выхода в потоке данных: какие поля передаются, переименовываются или вычисляются; в дизайнере задаётся связями и настройками трансформаций. См. [§2.1](chapter-02-01.md), [§4.3](chapter-04-03.md).

**Batch** (пакетная обработка) — режим обработки данных целиком или крупными порциями за один запуск задания; типичные источники — файлы, Hive, JDBC. См. [§2.4](chapter-02-04.md).

**Streaming** (потоковая обработка) — режим непрерывной обработки данных по мере поступления; типичный источник — Apache Kafka; в Spark — Structured Streaming. См. [§2.4](chapter-02-04.md).

**Apache Kafka** — распределённая платформа обмена сообщениями; в Datagram используется как источник потоковых данных для режима streaming. См. [§2.4](chapter-02-04.md), [§3.3](chapter-03-03.md).

**Источник** (source) — элемент потока, откуда читаются данные; в дизайнере задаётся тип (файл, Hive, Kafka, JDBC и др.) и параметры (путь, схема, подключение). См. [§3.1](chapter-03-01.md).

**Приёмник** (target, sink) — место назначения записи данных в потоке: файл (HDFS, локально), Hive-таблица, топик Kafka, таблица по JDBC. В дизайнере задаётся как элемент потока с настройками пути, формата и режима записи. См. [§3.1](chapter-03-01.md).

**HDFS** (Hadoop Distributed File System) — распределённая файловая система экосистемы Hadoop; типичное хранилище файлов (Parquet, ORC, CSV) для batch-источников в Datagram. См. [§3.1](chapter-03-01.md), [§3.2](chapter-03-02.md).

**Apache Hive** — система метаданных и запросов поверх данных в HDFS (и др.); таблицы Hive используются в Datagram как источники и приёмники в batch-режиме. См. [§3.1](chapter-03-01.md), [§3.4](chapter-03-04.md).

**JDBC** (Java Database Connectivity) — стандартный API доступа к реляционным БД из Java/Scala; в Datagram через JDBC подключаются источники и приёмники к Oracle, PostgreSQL и другим СУБД. См. [§3.1](chapter-03-01.md), [§3.4](chapter-03-04.md).

**Parquet** — колоночный формат хранения данных в экосистеме Apache; схема хранится в файле; в Datagram используется как источник и приёмник файлов в HDFS. См. [§3.2](chapter-03-02.md).

**ORC** (Optimized Row Columnar) — колоночный формат, связанный с Hive; в Datagram — источник и приёмник в HDFS наравне с Parquet. См. [§3.2](chapter-03-02.md).

**Топик** (Kafka topic) — именованный поток сообщений в Kafka; потребитель подписывается на топик(и) и читает сообщения с заданной позиции (offset). В Datagram топик задаётся в настройках источника Kafka. См. [§3.3](chapter-03-03.md).

**Checkpoint** (потоковая обработка) — каталог, в котором Spark Structured Streaming сохраняет прогресс чтения (offset по партициям Kafka); при перезапуске приложение продолжает с последней позиции. См. [§3.3](chapter-03-03.md).

**JSON** (JavaScript Object Notation) — текстовый формат представления объектов и массивов; в Datagram используется как источник (файлы, Kafka value) с парсингом и заданием схемы. См. [§3.5](chapter-03-05.md).

**Avro** — бинарный формат с явной схемой; в Datagram — источник из файлов или Kafka (при поддержке Schema Registry). См. [§3.5](chapter-03-05.md).

**Spark SQL** — модуль Apache Spark для работы с данными через SQL и API DataFrame; в Datagram используется как тип трансформации в потоке (запрос над входным набором, вложенные структуры). См. [§4.1](chapter-04-01.md).

**Drools** (JBoss Drools) — движок правил для декларативного описания бизнес-логики (условие → действие); в Datagram применяется как трансформация в потоке для правил классификации, кодов, валидации. См. [§4.4](chapter-04-04.md).

**Бизнес-правила** — логика предметной области (классификация, коды, маршрутизация, валидация), применяемая к данным в потоке; в Datagram может реализовываться выражениями, Spark SQL или правилами Drools. См. [§4.4](chapter-04-04.md).

**Spark MLlib** (ML) — библиотека машинного обучения в Apache Spark; алгоритмы классификации, регрессии, кластеризации на DataFrame; в Datagram — трансформация применения обученной модели к данным в потоке. См. [§4.5](chapter-04-05.md).

**Предиктивная аналитика** — использование моделей машинного обучения для предсказания (класс, число, кластер) по признакам; в ETL-потоке — обогащение данных полем предсказания (скоринг, категоризация, прогноз). См. [§4.5](chapter-04-05.md).

**Link** (связь) — в дизайнере Workflow: связь между двумя этапами, задающая порядок выполнения и при настройке — передачу контекста или параметров от одного этапа к другому. Граф связей образует DAG для оркестратора. См. [§6.4](chapter-06-04.md).

**XCom** (Airflow) — механизм Airflow для передачи данных между задачами одного DAG run; задачи могут записывать и читать значения по ключу; для больших объёмов передают путь или идентификатор. См. [§6.4](chapter-06-04.md).

**Дата среза** (business date) — дата, за которую выполняется загрузка или расчёт; задаётся при запуске Workflow и передаётся в этапы для формирования путей (партиции), фильтров и подстановки в приёмники. См. [§6.4](chapter-06-04.md), [§7.3](chapter-07-03.md).

**JAR** (Java Archive) — архив с скомпилированными классами (и ресурсами) приложения на JVM; основной артефакт сборки проекта Datagram на Scala для запуска на Spark через `spark-submit`. См. [§7.1](chapter-07-01.md).

**Артефакт сборки** — результат сборки проекта: JAR приложения, конфигурационные файлы, сгенерированные описания для оркестратора (DAG, Oozie workflow); разворачиваются в среду и используются при запуске на кластере. См. [§7.1](chapter-07-01.md).

**spark-submit** — утилита Apache Spark для отправки приложения на кластер: указываются JAR, главный класс, адрес менеджера кластера (YARN, Kubernetes, standalone) и опции конфигурации; оркестратор (Airflow, Oozie) запускает задание через вызов этой команды. См. [§7.2](chapter-07-02.md).

**Окружение** (environment, среда) — выделенная среда выполнения (dev, test, prod) с собственными кластерами, путями и подключениями; параметры и конфигурация подставляются в зависимости от окружения. См. [§7.3](chapter-07-03.md).

**Spark UI** — веб-интерфейс приложения Apache Spark для мониторинга выполнения: задания, стадии, задачи, исполнители, логи; доступен во время работы приложения и через Spark History Server после завершения. См. [§7.4](chapter-07-04.md).

**DWH** (Data Warehouse, хранилище данных) — целевое хранилище для аналитики и отчётности; в контексте главы 8 — загрузка в Hive-таблицы (слой Staging). См. [§8.1](chapter-08-01.md).

**Raw** (слой) — слой сырых данных «как есть» после извлечения из источника (например, файлы Parquet/ORC в HDFS); без бизнес-преобразований. См. [§6.1](chapter-06-01.md), [§8.1](chapter-08-01.md).

**Staging** (слой) — слой после очистки, маппинга и при необходимости обогащения; данные готовы для загрузки в витрины и Core. См. [§6.1](chapter-06-01.md), [§8.1](chapter-08-01.md).

**Миграция** (ETL) — перенос пайплайнов интеграции и преобразования данных с одной платформы (например, IBM InfoSphere DataStage, Oracle ODI) на другую (в т.ч. Neoflex Datagram) с сохранением или адаптацией бизнес-логики и результатов. См. [§9.1](chapter-09-01.md).

**Lift-and-shift** — стратегия миграции «как есть»: воспроизведение существующей логики пайплайна на новой платформе с минимальными изменениями; противопоставляется реинжинирингу (перенос с оптимизацией и доработкой). См. [§9.3](chapter-09-03.md).
