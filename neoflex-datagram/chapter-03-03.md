# §3.3 Apache Kafka и потоковые источники

В [§3.2](chapter-03-02.md) мы разобрали файловые источники (CSV, HDFS, Parquet, ORC). В этом разделе рассматривается **Apache Kafka** как источник потоковых данных в Neoflex Datagram: подключение к кластеру Kafka, настройка топиков, потоковый режим чтения через Spark Structured Streaming и при необходимости формат сообщений (JSON, Avro). Kafka — типичный источник для сценариев streaming ([§2.4](chapter-02-04.md)); настройка источника Kafka в дизайнере приводит к генерации кода с чтением потока из топиков. ## 3.3.1. Kafka: топики и потребители

**Apache Kafka** — распределённая платформа обмена сообщениями. Данные организованы в **топики (topics)**; каждое сообщение попадает в один из топиков и хранится с присвоенным **offset** (позиция в партиции топика). **Производитель (producer)** публикует сообщения в топик; **потребитель (consumer)** читает сообщения, начиная с заданной позиции (или с начала, или с конца). Топик может быть разбит на **партиции** для параллельного чтения и записи; несколько потребителей в одной **группе (consumer group)** распределяют партиции между собой.

В контексте Datagram источник типа Kafka — это **потребитель**: приложение читает сообщения из одного или нескольких топиков. Для потокового режима используется **Spark Structured Streaming**: драйвер периодически запрашивает новые сообщения из Kafka (микро-батчами), преобразует их в DataFrame и передаёт в цепочку трансформаций. Позиция чтения (offset) сохраняется в **checkpoint**, чтобы при перезапуске приложения продолжить с последней обработанной позиции и не терять сообщения (или не дублировать при настройке exactly-once). Актуальные возможности Spark по интеграции с Kafka (версия коннектора, семантика доставки) уточняйте в документации Spark и Neoflex.

## 3.3.2. Подключение к Kafka в дизайнере

В дизайнере трансформаций при добавлении **источника Kafka** задаются параметры подключения и потребления:

- **Адреса брокеров (bootstrap servers)** — список хостов и портов Kafka-кластера, например `broker1:9092,broker2:9092`. По этим адресам клиент подключается к кластеру и получает метаданные о топиках и партициях.
- **Топик(и)** — имя топика или список топиков, из которых читать. Можно указать один топик или подписку по шаблону (topic pattern), если платформа это поддерживает.
- **Группа потребителя (consumer group)** — идентификатор группы; Kafka использует его для координации партиций между потребителями и для хранения offset (при хранении offset в Kafka). Уникальное имя группы для приложения позволяет не смешивать позицию с другими заданиями.
- **Дополнительные опции** — начало чтения (earliest, latest), настройки таймаутов, SSL/SASL при защищённом доступе. При необходимости задаётся путь к checkpoint для сохранения offset (для Structured Streaming).

Эти параметры попадают в сгенерированный код в виде опций `spark.readStream.format("kafka").option("kafka.bootstrap.servers", ...).option("subscribe", ...)` (или эквивалента). Точный набор опций и названия полей в дизайнере см. в документации Neoflex. При развёртывании задания кластер Spark должен иметь сетевой доступ к брокерам Kafka и при использовании Kerberos/SSL — корректную конфигурацию безопасности.

## 3.3.3. Потоковый режим и исполнение

В **потоковом режиме** задание с источником Kafka не завершается после одного прохода: оно запускается один раз и работает непрерывно, периодически запрашивая новые сообщения из топика, применяя к ним трансформации и записывая результат в приёмник (файл, Hive, другой топик или консоль для отладки). Режим приёмника должен поддерживать потоковую запись (append, например в партиционированные таблицы Hive или в файлы с checkpoint). Оркестратор (Airflow, Oozie) в этом случае не перезапускает задание по расписанию для «следующей порции» — задание одно и длительное; оркестратор может использоваться для первичного запуска и мониторинга (перезапуск при падении по политике).

**Checkpoint** — каталог, в котором Structured Streaming сохраняет прогресс обработки (offset по партициям Kafka и метаданные). При перезапуске приложение читает checkpoint и продолжает с последней сохранённой позиции. Checkpoint должен быть в надёжном хранилище (HDFS или совместимом), доступном драйверу Spark. Без checkpoint при перезапуске чтение начнётся заново (с earliest или latest по настройке), что может привести к дублированию или потере данных. Настройка пути к checkpoint и политики восстановления задаётся в дизайнере или в конфигурации запуска; детали — в документации платформы и Spark Structured Streaming.

## 3.3.4. Формат сообщений и схема

Сообщения в топике Kafka — байтовые последовательности; смысл задаётся **форматом** и **схемой**. Типичные варианты:

- **JSON** — текст в формате JSON; в Spark поток из Kafka даёт столбцы `key`, `value`, `topic`, `partition`, `offset` и др.; поле `value` содержит сырое сообщение. Для разбора JSON применяют трансформацию (например, `from_json` в Spark SQL) с указанием схемы ожидаемых полей. В дизайнере может быть доступен элемент «парсинг JSON» или настройка схемы для поля value; сгенерированный код тогда включает разбор и извлечение полей.
- **Avro** — бинарный формат с описанием схемы (в сообщении или в Schema Registry). Коннектор Spark-Kafka при поддержке Schema Registry может автоматически подставлять схему; иначе схема задаётся вручную. Avro удобен для эволюции схемы и компактной передачи.

Выбор формата зависит от того, как производители пишут в топик. После извлечения полей из `value` дальнейшая обработка идёт как с обычным DataFrame (фильтр, join, агрегация, запись в приёмник). Подробнее работа со сложноструктурированными форматами (JSON, Avro) в потоке — в [§3.5](chapter-03-05.md).

## 3.3.5. Kafka как приёмник (запись в топик)

При поддержке платформой **Kafka может выступать приёмником**: результат трансформаций записывается в топик. Типичный сценарий — обогащённый или агрегированный поток событий передаётся дальше по конвейеру (другое приложение или витрина в реальном времени). В дизайнере добавляется приёмник типа Kafka; задаются топик назначения, адреса брокеров и при необходимости формат сериализации (JSON, Avro). Сгенерированный код использует `df.writeStream.format("kafka").option(...).start()`. Актуальную поддержку записи в Kafka и опции уточняйте в документации Neoflex.

## Ключевое

- **Kafka как источник:** в дизайнере задаются брокеры, топик(и), группа потребителя; генерируется код с чтением потока через Spark Structured Streaming.
- **Топики и offset:** сообщения читаются из топиков; позиция (offset) сохраняется в checkpoint для продолжения после перезапуска и семантики exactly-once при корректной настройке.
- **Потоковый режим:** задание работает непрерывно, обрабатывает сообщения микро-батчами; приёмник должен поддерживать потоковую запись (append). Checkpoint — в надёжном хранилище (HDFS).
- **Формат сообщений:** JSON или Avro; разбор value и схема задаются в дизайнере или в трансформации (from_json, Avro schema). См. [§3.5](chapter-03-05.md).
- **Kafka как приёмник:** при поддержке — запись результата потока в топик; настройка топика и брокеров в свойствах приёмника.
