## 2.3.1. От визуальной модели к коду

Модель потока данных, созданная в дизайнере трансформаций, хранится в виде **метаданных** проекта: описание элементов (источники, трансформации, приёмники), их параметры (пути, схемы, условия, выражения) и связи между ними. **Генератор кода** (часть платформы Datagram) обходит эту модель и производит исходный код на **Scala** (в открытых материалах также упоминается генерация на Python — актуальность уточняйте у поставщика), который реализует ту же логику средствами API Apache Spark.

Процесс генерации можно представить так:

1. **Обход графа потока** — от источников к приёмникам в порядке зависимостей (топологическая сортировка): сначала элементы без входящих связей (источники), затем трансформации по мере готовности входов, затем приёмники.
2. **Для каждого элемента** генератор выбирает шаблон кода: для источника Parquet — вызов `spark.read.format("parquet").load(path)` с заданной схемой; для фильтра — `.filter(условие)`; для join — `.join(...)` с указанными ключами и типом соединения; для приёмника Hive — запись DataFrame в Hive-таблицу. Параметры элемента (имена полей, пути, выражения) подставляются в шаблон.
3. **Сборка цепочки** — результат каждого шага (DataFrame или DataSet) передаётся как вход следующему; переменные или цепочка вызовов формируют линейный или разветвлённый код, соответствующий графу модели.
4. **Вывод артефактов** — исходные файлы Scala (или Python) записываются в каталог проекта; при сборке (compile/build) они компилируются в исполняемый артефакт (JAR для Scala), который затем разворачивается и запускается на кластере Spark.

Соответствие «элемент модели → фрагмент кода» было приведено в [§1.2](chapter-01-02.md) (таблица в 1.2.4). Повторная генерация выполняется при изменении модели (добавление/удаление элементов, смена параметров); при этом ранее сгенерированные файлы перезаписываются, поэтому ручные правки в них могут быть потеряны — порядок сопровождения см. в [§1.2](chapter-01-02.md) и в документации платформы.

## 2.3.2. Роль Apache Spark как движка исполнения

**Apache Spark** — распределённый движок обработки данных. Сгенерированный код Datagram не выполняется «как скрипт» на одной машине; он передаётся **драйверу Spark** (driver), который строит граф вычислений (DAG стадий и задач) и распределяет выполнение по **исполнителям** (executors) на узлах кластера. Таким образом, Spark обеспечивает:

- **Распределённое выполнение** — данные разбиваются на партиции, задачи выполняются параллельно на нескольких узлах; объёмы, не помещающиеся в память одной машины, обрабатываются кластером.
- **Единый API** — чтение (DataFrame Reader), трансформации (фильтр, join, агрегация, Spark SQL), запись (DataFrame Writer); генератор Datagram использует именно этот API, так что сгенерированный код типичен для приложений на Spark.
- **Интеграцию с источниками и приёмниками** — HDFS, Hive, Kafka, JDBC, файловые форматы (Parquet, ORC, CSV) доступны через коннекторы Spark; дизайнер Datagram опирается на те же возможности при настройке источников и приёмников.

Роль Spark в контексте Datagram: **исполняемая среда** для кода, полученного из визуальной модели. Разработчик не вызывает Spark API напрямую в повседневной работе — он редактирует модель в дизайнере; но при отладке, оптимизации или ручной доработке знание Spark (DataFrame, партиционирование, конфигурация заданий) необходимо. Книга серии «Spark (PySpark)» ([../spark-pyspark/](../spark-pyspark/)) даёт основы; детали трансформаций в Datagram (Spark SQL, Join, Aggregation и т.д.) — в главах 4 и 5.

## 2.3.3. Кластер и среда исполнения

Исполнение сгенерированного кода происходит на **кластере Spark**. Кластер состоит из:

- **Driver (драйвер)** — процесс, в котором запускается приложение (в т.ч. сгенерированный код); он строит DAG заданий, запрашивает ресурсы у менеджера кластера и координирует выполнение задач. Обычно один driver на одно приложение (одно задание пайплайна).
- **Executor (исполнитель)** — процесс на узле кластера, выполняющий задачи (tasks), назначенные драйвером; хранит данные в памяти или на диске, выполняет трансформации над партициями. Несколько executors на разных узлах работают параллельно.
- **Cluster Manager (менеджер кластера)** — выделяет ресурсы для приложения: **Apache YARN**, **standalone** (встроенный менеджер Spark) или **Kubernetes**. Выбор зависит от инфраструктуры заказчика (Hadoop-кластер на YARN, отдельный Spark-кластер, контейнеры K8s). Datagram генерирует код приложения; развёртывание и запуск на выбранном менеджере выполняются средствами оркестратора (Airflow, Oozie) и скриптов/конфигурации окружения (подробнее — в [§7.2](chapter-07-02.md)).

Конфигурация Spark (память драйвера и исполнителей, число ядер, настройки для конкретных источников и форматов) задаётся при запуске задания или в конфигурационных файлах; от неё зависят производительность и стабильность пайплайна. Окружение может быть поставляемым Neoflex или собственным кластером заказчика при совместимости версий Spark. Требования к версиям Spark и к окружению уточняйте в документации поставщика.

## 2.3.4. Сборка проекта и артефакт для запуска

После генерации кода проект необходимо **собрать** (compile, package): исходники Scala компилируются, зависимости (библиотеки Spark и коннекторов) подключаются, формируется артефакт для развёртывания — обычно **JAR** (Java Archive) для приложения на Scala. Сборка выполняется средствами сборки (Maven, Gradle, SBT — по тому, что использует платформа Datagram) в среде разработки или в CI/CD. Итоговый JAR (или набор JAR и конфигураций) разворачивается в среду, откуда оркестратор будет запускать задание (например, узел с установленным Spark client или контейнер с Spark), и передаётся в команду запуска Spark (`spark-submit` или аналог). Подробнее сборка, зависимости и развёртывание — в [§7.1](chapter-07-01.md) и [§7.2](chapter-07-02.md).

Цепочка в целом: **модель (дизайнер трансформаций) → генерация → исходники Scala → сборка → JAR → запуск на кластере Spark по вызову из Airflow/Oozie**. Workflow из дизайнера Workflow описывает, когда и в каком порядке вызывать эти задания; сами задания — скомпилированные потоки трансформаций.

## Ключевое

- **Генерация кода:** модель потока данных (метаданные проекта) обходится генератором; для каждого элемента (источник, трансформация, приёмник) подставляется шаблон кода на Scala (или Python); вывод — исходные файлы, затем сборка в артефакт (JAR).
- **Роль Spark:** сгенерированный код выполняется в среде Apache Spark; Spark — движок распределённого выполнения (DataFrame API, чтение/запись, трансформации). Разработчик работает с моделью; Spark обеспечивает масштабирование на кластер.
- **Кластер:** driver строит DAG и координирует выполнение; executors на узлах выполняют задачи; cluster manager (YARN, standalone, Kubernetes) выделяет ресурсы. Исполнение пайплайнов Datagram — всегда на кластере (или локальном режиме Spark для тестов), не внутри среды дизайнера.
- **Артефакт:** после сборки — JAR (или эквивалент); развёртывается и запускается через `spark-submit` или аналог по вызову оркестратора. Детали — в главе 7.

В [§2.4](chapter-02-04.md) мы разберём режимы batch и streaming: пакетная и потоковая обработка данных, использование Kafka и выбор режима для сценария.
