# §5.3 Проверки при загрузке

В [§5.2](chapter-05-02.md) мы разобрали проверки при преобразовании: валидация по правилам, отбрасывание и карантин. На этапе **загрузки** ([§2.4](chapter-02-04.md)) данные записываются в целевые таблицы; целевая СУБД применяет свои ограничения — уникальность ключей, внешние ключи, проверочные ограничения (CHECK), типы данных. Нарушение этих ограничений приводит к ошибке записи; от выбора политики (откат транзакции, пропуск проблемной записи, карантин загрузки) зависят полнота и согласованность данных в цели. В этом разделе мы систематизируем проверки при загрузке: целостность по ключам и ссылкам, ограничения целевой таблицы и откат транзакции при нарушении. Метрики загруженных и отклонённых записей — в [§5.4](chapter-05-04.md). См. [Глоссарий](glossary.md).

---

## 5.3.1. Роль проверок при загрузке

Проверки при загрузке — это, с одной стороны, **ограничения целевой таблицы и БД** (уникальность, внешние ключи, CHECK, NOT NULL, типы), которые СУБД проверяет при INSERT/UPDATE/MERGE; с другой — **политика обработки** ошибок, возникающих при нарушении этих ограничений: откатить транзакцию, пропустить запись с логированием, сохранить в карантин загрузки. Цель — не допустить в целевое хранилище данные, нарушающие целостность, и при этом явно обработать сбои: залогировать, посчитать отклонённые, при необходимости сохранить их для разбора. См. [Глоссарий](glossary.md).

Идеально, чтобы все записи, не проходящие ограничения целевой таблицы, были отсеяны на этапе преобразования (валидация и карантин там). На практике часть нарушений может проявиться только при загрузке (например, гонка при параллельной загрузке, изменение ограничений в цели, ошибка в маппинге). Поэтому политика при ошибке загрузки обязательна.

---

## 5.3.2. Целостность: ключи и ссылки

Целевая таблица может иметь ограничения **уникальности** (первичный ключ, уникальный индекс) и **внешние ключи** (ссылки на другие таблицы). Загрузка должна их соблюдать.

**Уникальность (PRIMARY KEY, UNIQUE):** вставляемая или обновляемая запись не должна создавать дубликат по ключу. При INSERT дубликат приведёт к ошибке уникальности; при MERGE/upsert дубликаты в одном батче должны быть устранены до загрузки (дедупликация при преобразовании), иначе результат недетерминирован. Проверка при загрузке: СУБД отклонит вставку при нарушении; задача ETL — не поставлять дубликаты по ключу в одном батче и обеспечивать идемпотентность при повторной доставке (upsert по ключу). См. [§2.4.4](chapter-02-04.md).

**Внешние ключи (FOREIGN KEY):** значение в столбце-ссылке должно существовать в целевой таблице, на которую ссылается ограничение. Например, фактовая таблица имеет поле `customer_id` с FK на таблицу `customers`. Вставка факта с `customer_id`, которого нет в `customers`, приведёт к ошибке FK. Проверки при загрузке: СУБД отклонит запись при нарушении FK (если ограничение включено). Чтобы минимизировать такие ошибки, при преобразовании выполняют проверку ссылочной целостности ([§5.2.3](chapter-05-02.md)) и загружают измерения до фактов ([§2.4.7](chapter-02-04.md)). При возникновении ошибки FK политика та же: откат, пропуск с логированием или карантин загрузки.

**Ссылочная целостность** гарантирует, что в целевой БД нет «сирот» — записей, ссылающихся на несуществующие строки. Ограничения FK в целевой таблице — последняя линия защиты; проверки при преобразовании снижают количество сбоев на этапе загрузки.

## 5.3.3. Ограничения целевой таблицы

Помимо уникальности и внешних ключей, целевая таблица может иметь:

- **NOT NULL:** столбец не допускает NULL. Вставка NULL приведёт к ошибке. Проверка должна выполняться при преобразовании (обязательность полей); при загрузке СУБД отклонит запись при нарушении.
- **CHECK:** условие на значение (например, `amount >= 0`, `status IN ('A','B','C')`). Нарушение ведёт к ошибке при INSERT/UPDATE. Правила, эквивалентные CHECK, желательно применять при преобразовании (валидация), чтобы не полагаться только на отказ при загрузке.
- **Типы данных:** несоответствие типа (переполнение, неверный формат даты) приведёт к ошибке. Приведение типов при преобразовании и валидация форматов снижают такие ошибки; при загрузке СУБД отклонит запись при несовместимом типе.

Все эти ограничения работают как **проверки при загрузке**: СУБД не примет запись, нарушающую ограничение. Задача ETL — поставлять данные, уже прошедшие эквивалентные проверки на этапе преобразования, и иметь явную политику при любой ошибке загрузки (откат, пропуск, карантин).

## 5.3.4. Откат транзакции при нарушении

При ошибке записи (нарушение уникальности, FK, CHECK, типа) возможны варианты обработки.

**Транзакция целиком (rollback):** вся загрузка батча или всего прогона выполняется в одной транзакции. При любой ошибке транзакция откатывается — в целевой таблице не остаётся ни одной записи из этого батча. Плюсы: целевая таблица либо получает полный согласованный батч, либо не меняется. Минусы: одна «плохая» запись откатывает весь батч; при большом батче это может быть нежелательно. Уместно при небольших батчах и жёстких требованиях «всё или ничего».

**Пропуск с логированием:** при ошибке для одной записи (или для одного подбатча) запись не вставляется, ошибка логируется (код, сообщение, ключ записи или данные), загрузка продолжается для остальных. Итог: часть записей загружена, часть — нет. Требуются счётчики загруженных и отклонённых и при необходимости карантин загрузки для отклонённых записей. Риск: частичная загрузка; для согласованности среза нужна явная политика (например, не обновлять водяной знак при наличии отклонённых и перезапустить после исправления).

**Остановка при первой ошибке:** загрузка прерывается при первой же ошибке; уже записанные в этой транзакции данные откатываются (если батч в одной транзакции), либо остаются (если коммит после каждой записи/подбатча). В последнем случае для возврата к согласованному состоянию может потребоваться процедура отката (удаление по run_id, откат партиции) или идемпотентный полный перезапуск.

**Карантин загрузки:** записи, вызвавшие ошибку, сохраняются в отдельную таблицу (reject table загрузки) с текстом ошибки и при необходимости с исходными данными. Аналогично карантину при валидации ([§5.2.4](chapter-05-02.md)); позволяет анализировать причины и повторно загружать после исправления. Остальные записи батча при этом могут быть загружены (при политике «пропуск с логированием») или транзакция откатывается (при политике «всё или ничего» для батча).

Рекомендация: логировать все ошибки загрузки, вести счётчики загруженных и отклонённых; при критичных ошибках (недоступность цели, массовое нарушение ограничений) — алерт и остановка без обновления водяного знака ([§2.4.6](chapter-02-04.md)).

## 5.3.5. Сверка объёма после загрузки

После успешной загрузки полезно проверить **полноту загрузки**: количество записанных записей совпадает с количеством переданных на загрузку (за вычетом записей, сознательно отклонённых по политике). Расхождение указывает на тихий сбой (часть записей не вставлена без явной ошибки — редко, но возможно при некоторых драйверах и настройках) или на ошибку в счётчиках. Сверка: число строк, вставленных в целевую таблицу за прогон (по метке run_id или по временному диапазону), сравнить с числом записей, переданных из преобразования. При расхождении — алерт и разбор.

---

## 5.3.6. Типичные ошибки

- **Не задать политику при ошибке загрузки:** при ошибке ограничения неопределённое поведение (исключение без обработки, частичный коммит) приводит к непредсказуемому состоянию цели. Политика (откат, пропуск, карантин) должна быть задана явно и реализована в коде загрузки.
- **Загружать факты до измерений:** при включённых FK загрузка фактов со ссылками на ещё не загруженные измерения приведёт к массовым ошибкам FK. Соблюдать порядок загрузки ([§4.3.2](chapter-04-03.md)).
- **Не логировать отклонённые при загрузке:** при политике «пропуск с логированием» отсутствие лога не даёт понять, какие записи не загрузились и почему. Обязательно логировать ключ (или строку), код ошибки и сообщение СУБД; предпочтительно — карантин загрузки.
- **Игнорировать сверку объёма:** без проверки «сколько передали — сколько записали» тихие потери при загрузке могут остаться незамеченными. Минимум — счётчики и сравнение после загрузки.

---

## Ключевое

- При загрузке **ограничения целевой таблицы** (уникальность, FK, CHECK, NOT NULL, типы) проверяются СУБД; нарушение ведёт к ошибке записи. Задача ETL — поставлять данные, прошедшие эквивалентную валидацию при преобразовании, и иметь явную **политику при ошибке**: откат транзакции, пропуск с логированием, карантин загрузки.
- **Целостность:** уникальность ключа и ссылочная целостность (FK) обеспечиваются порядком загрузки (измерения до фактов) и проверками при преобразовании; при ошибке загрузки — обработка по политике.
- После загрузки целесообразна **сверка объёма**: количество записанных записей совпадает с переданным на загрузку; при расхождении — алерт и разбор.
- Логирование ошибок загрузки и счётчики загруженных/отклонённых обязательны для наблюдаемости и метрик качества ([§5.4](chapter-05-04.md)).

В [§5.4](chapter-05-04.md) мы разберём метрики качества в пайплайне: счётчики обработанных и отклонённых записей, сравнение с предыдущим прогоном и отчётность по качеству.
