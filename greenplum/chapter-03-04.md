# §3.4 Первый запуск и проверка

В [§3.3](chapter-03-03.md) мы выполнили gpinitsystem и настроили MASTER_DATA_DIRECTORY. После успешной инициализации кластер **уже запущен** (gpinitsystem сам стартует все инстансы). В этом разделе — как **запускать кластер после остановки или перезагрузки** (gpstart), как подключиться к нему через **psql**, как проверить топологию по представлению **gp_segment_configuration** и как выполнить простой тестовый запрос. Детали управления кластером (gpstop, опции перезапуска) — в [§4.1](chapter-04-01.md). См. [Глоссарий](glossary.md).

---

## 3.4.1. Состояние кластера сразу после gpinitsystem

По завершении gpinitsystem все процессы Greenplum (Master и сегменты) **уже работают**. Дополнительно запускать ничего не нужно: можно сразу подключаться к Master через psql и выполнять запросы. Если вы только что закончили [§3.3](chapter-03-03.md), переходите к подразделу 3.4.3 (подключение через psql) и 3.4.4 (проверка gp_segment_configuration).

Если кластер был **остановлен** (gpstop или перезагрузка серверов), для следующего включения используется утилита **gpstart**. См. следующий подраздел.

---

## 3.4.2. Запуск кластера: gpstart

Утилита **gpstart** запускает все инстансы Greenplum (Master и сегменты) на всех узлах кластера. Выполняется **на хосте Master** под пользователем **gpadmin**; перед запуском должны быть заданы **GPHOME** и **MASTER_DATA_DIRECTORY** (через source greenplum_path.sh и export MASTER_DATA_DIRECTORY или через ~/.bashrc). См. [§4.1](chapter-04-01.md) для полного набора опций. По документации Tanzu Greenplum.

Базовая команда:

```bash
gpstart
```

Утилита по MASTER_DATA_DIRECTORY находит конфигурацию кластера, по SSH подключается к хостам сегментов и запускает на них постмастеры и сегменты, затем запускает Master. По умолчанию gpstart запрашивает подтверждение при обнаружении сегментов в состоянии «down». Для неинтерактивного запуска используйте опцию **-a** (auto‑accept):

```bash
gpstart -a
```

Вывод gpstart показывает прогресс запуска каждого сегмента и в конце — успешный старт или список ошибок. Логи пишутся в **~/gpAdminLogs**. При ошибках проверьте доступность хостов (ping, SSH), права на каталоги данных и логи в gpAdminLogs и в каталогах данных сегментов (pg_log). См. [§4.4](chapter-04-04.md).

## 3.4.3. Подключение через psql

Кластер принимает подключения на **порту Master** (тот, что задан в конфиге gpinitsystem, по умолчанию 5432). Подключение выполняется так же, как к обычному PostgreSQL: клиент подключается только к Master. См. [§2.1](chapter-02-01.md), [§2.4](chapter-02-04.md).

С хоста Master под пользователем gpadmin (после `source greenplum_path.sh` и с заданным MASTER_DATA_DIRECTORY):

```bash
psql -d postgres
```

Будет использоваться база по умолчанию **postgres**, пользователь — текущий ОС‑пользователь (gpadmin), хост — localhost, порт — из переменной **PGPORT** (если задана) или 5432. Явное указание хоста и порта:

```bash
psql -h localhost -p 5432 -d postgres -U gpadmin
```

После подключения появится приглашение `postgres=#` (или имя другой базы). Дальше можно выполнять SQL и проверять топологию. Среда: Greenplum, клиент psql из поставки Greenplum.

---

## 3.4.4. Проверка топологии: gp_segment_configuration

Системное представление **gp_segment_configuration** содержит конфигурацию всех сегментов кластера: content id, роль (primary/mirror), хост, порт, статус (up/down) и т.д. Проверка этого представления подтверждает, что все сегменты видны Master и находятся в состоянии **up**. См. [§2.2](chapter-02-02.md).

В сессии psql выполните:

```sql
SELECT content, role, preferred_role, status, hostname, port
FROM gp_segment_configuration
ORDER BY content, role;
```

Ожидаемый результат: строки для каждого content id (0, 1, 2, …) с role = 'p' (primary) и при включённом mirror — 'm' (mirror); status = 'u' (up); hostname и port заполнены. Строка с content = -1 соответствует Master (coordinator). Если у какого‑то сегмента status = 'd' (down), кластер будет работать с ограничениями или откажет при обращении к данным этого сегмента; причину смотрите в логах и при необходимости используйте gprecoverseg ([§4.2](chapter-04-02.md)).

Краткая проверка только количества и статусов:

```sql
SELECT status, COUNT(*) FROM gp_segment_configuration GROUP BY status;
```

Все сегменты должны быть в статусе **u**. См. документацию по системным каталогам Greenplum.

## 3.4.5. Простой тестовый запрос

Чтобы убедиться, что запрос выполняется с участием сегментов (распределённое выполнение), удобно запросить **идентификатор сегмента** для каждой строки. В Greenplum для этого служит функция **gp_segment_id**: она возвращает номер сегмента, на котором обрабатывается текущая строка. См. [§1.3](chapter-01-03.md).

Пример:

```sql
SELECT gp_segment_id, COUNT(*) 
FROM (SELECT 1 AS x FROM generate_series(1, 100)) t 
GROUP BY gp_segment_id 
ORDER BY gp_segment_id;
```

Подзапрос генерирует 100 строк; они распределяются по сегментам; группировка по gp_segment_id показывает, сколько строк обработал каждый сегмент. Вы должны увидеть несколько строк (по одной на каждый primary‑сегмент), с разными gp_segment_id и ненулевыми COUNT. Значение -1 соответствует Master (строка, обработанная на координаторе); остальные — сегменты. Так мы проверяем, что данные и запрос реально распределяются по кластеру.

Дополнительно можно создать тестовую таблицу, вставить в неё несколько строк и выполнить SELECT; при правильном распределении строки окажутся на разных сегментах (проверка через gp_segment_id при выборке из таблицы). См. гл. 6 про распределение таблиц.

## 3.4.6. Версия Greenplum и базы

Проверить версию СУБД и бэкенда:

```sql
SELECT version();
```

В выводе будет указана версия Greenplum и базовая версия PostgreSQL. Убедитесь, что подключаетесь именно к нужному кластеру (хост, порт, MASTER_DATA_DIRECTORY на сервере).

## 3.4.7. Типичные ошибки

- **Запускать gpstart без MASTER_DATA_DIRECTORY:** утилита не найдёт конфигурацию кластера; задайте переменную в сессии или в ~/.bashrc и повторите.
- **Подключаться к порту сегмента:** клиенты подключаются только к **Master** (порт 5432 или заданный в конфиге); к портам сегментов напрямую не подключаются.
- **Игнорировать status = 'd' в gp_segment_configuration:** при «down» сегменте часть данных недоступна; нужно выяснить причину и при необходимости выполнить восстановление (gprecoverseg).

---

## Ключевое

- После **gpinitsystem** кластер уже **запущен**; при последующих остановках или перезагрузках кластер поднимают командой **gpstart** (на Master под gpadmin, с заданными GPHOME и MASTER_DATA_DIRECTORY).
- Подключение к кластеру — через **psql** (или другой клиент PostgreSQL) к **хосту и порту Master** (по умолчанию 5432); подключаться к сегментам напрямую не нужно.
- Топологию проверяют по представлению **gp_segment_configuration**: content, role, status, hostname, port; все сегменты должны быть в статусе **up**.
- Простой тест распределённого выполнения — запрос с **gp_segment_id** и GROUP BY (например, по generate_series); в результате видно участие нескольких сегментов.

В [§4.1](chapter-04-01.md) мы разберём управление кластером: **gpstart** и **gpstop** (опции graceful и immediate, перезагрузка конфигурации).
