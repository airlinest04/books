# §7.2 Особенности диалекта

В [§7.1](chapter-07-01.md) мы разобрали совместимость SQL с PostgreSQL. В Greenplum добавлены **расширения для MPP**: системные представления и таблицы с префиксом **gp_*** для наблюдения за кластером и отладки распределённого выполнения, а также функции, полезные при работе с распределёнными данными. В этом разделе — обзор **gp_*** представлений (топология, статистика, перекос, очереди), псевдостолбец **gp_segment_id** и примеры типичных запросов. Полный список — в разделе System Catalogs и gp_toolkit документации Greenplum. По [Tanzu Greenplum 7 — System Views](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/ref_guide-system_catalogs-catalog_ref-views.html), [gp_segment_configuration](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/ref_guide-system_catalogs-gp_segment_configuration.html).

---

## 7.2.1. Зачем нужны представления gp_*

В PostgreSQL системная информация о процессах, таблицах и транзакциях сосредоточена в **pg_stat_***, **pg_catalog** и т.п. В Greenplum данные **распределены по сегментам**: чтобы видеть состояние всего кластера, нужны представления, которые **агрегируют** данные с каждого сегмента или показывают **топологию** (какой сегмент где работает). Для этого служат объекты с префиксом **gp_**: таблицы конфигурации сегментов, представления статистики по кластеру в целом и схема **gp_toolkit** с утилитами для мониторинга и диагностики. См. [§1.3](chapter-01-03.md).

---

## 7.2.2. Топология и конфигурация сегментов

**gp_segment_configuration** — системная **таблица** (не представление), в которой хранится конфигурация всех сегментов и координатора: dbid, content (content id), role (p — primary, m — mirror), preferred_role, mode (s — synchronized, n — not in sync), status (u — up, d — down), hostname, address, port, datadir. По ней проверяют, что все сегменты в статусе **up** и при необходимости выявляют упавшие (status = 'd'). См. [§3.4](chapter-03-04.md), [§4.2](chapter-04-02.md), [§4.4](chapter-04-04.md).

Пример:

```sql
SELECT content, role, preferred_role, status, hostname, port
FROM gp_segment_configuration
ORDER BY content, role;
```

**gp_pgdatabase** — представление со статусом сегментов (dbid, isprimary, content, valid, definedprimary), используется утилитами отказоустойчивости и при диагностике.

---

## 7.2.3. Статистика по кластеру: gp_stat_*

В PostgreSQL **pg_stat_activity** показывает активность на одном инстансе; **pg_stat_all_tables**, **pg_stat_user_tables** и т.д. — статистику по таблицам на одном узле. В Greenplum им соответствуют **gp_stat_activity**, **gp_stat_all_tables**, **gp_stat_user_tables** и др.: они **собирают** данные с координатора и всех первичных сегментов. В результате каждая строка может соответствовать одному сегменту; во многих представлениях есть столбец **gp_segment_id** (идентификатор сегмента, для координатора часто -1). Это позволяет видеть активные запросы и использование таблиц по всему кластеру. См. документацию Greenplum по мониторингу.

Пример: активные запросы по сегментам:

```sql
SELECT gp_segment_id, pid, usename, application_name, state, query
FROM gp_stat_activity
WHERE state != 'idle';
```

## 7.2.4. gp_segment_id при работе с данными

**gp_segment_id** — псевдостолбец (и функция), возвращающий **номер сегмента**, на котором обрабатывается текущая строка в контексте запроса. В SELECT по пользовательской таблице он показывает, на каком сегменте лежит строка; в групповых запросах по нему можно проверить распределение строк по сегментам и выявить перекос. См. [§3.4](chapter-03-04.md), [§6.1](chapter-06-01.md).

Пример: число строк на каждом сегменте по таблице `facts`:

```sql
SELECT gp_segment_id, COUNT(*) AS cnt
FROM facts
GROUP BY gp_segment_id
ORDER BY 1;
```

На реплицированных таблицах (DISTRIBUTED REPLICATED) обращение к **gp_segment_id** в запросе в Greenplum **запрещено**. См. [§6.2](chapter-06-02.md).

## 7.2.5. gp_toolkit: перекос и очереди

Схема **gp_toolkit** содержит представления и функции для диагностики и мониторинга. В книге уже использовались:

- **gp_toolkit.gp_skew_idle_fractions** — доля «простаивающих» сегментов при скане таблицы (индикатор перекоса по данным или по обработке); столбец siffraction. Значение выше ~0.1 (10%) — повод проверить распределение таблицы. См. [§6.1](chapter-06-01.md).
- **gp_toolkit.gp_skew_coefficients** — коэффициент вариации по данным на сегментах (skccoeff); чем выше, тем сильнее перекос.

При использовании **очередей ресурсов** (resource queues) полезно **gp_toolkit.gp_resqueue_status** (или **gp_resqueue_status**): количество ожидающих и активных запросов по очередям, лимиты и использование. При управлении ресурсами через **resource groups** — представления **gp_resgroup_status**, **gp_resgroup_status_per_host** и др. См. документацию Greenplum по workload management и gp_toolkit.

## 7.2.6. Функции Greenplum

Ряд функций дополняют стандартный набор PostgreSQL:

- **gp_segment_id** — при вызове в контексте строки возвращает идентификатор сегмента для этой строки (см. выше).
- **get_ao_distribution(имя_таблицы)** — распределение строк AO-таблицы по сегментам (dbid, tuplecount). См. [§5.2](chapter-05-02.md).
- **get_ao_compression_ratio(имя_таблицы)** — оценка степени сжатия AO-таблицы.

Функция **gp_dist_random('имя_таблицы')** возвращает множество строк из таблицы, читая **напрямую с одного из сегментов** (без сбора на координаторе по обычному распределённому плану); используется для отладки и служебных скриптов. Синтаксис и ограничения см. в справочнике функций Greenplum.

Прочие функции (административные, для работы с партициями, с распределением) перечислены в разделе «Summary of Built-in Functions» или «Greenplum Database Function Reference» документации вашей версии.

## 7.2.7. Параметры конфигурации с префиксом gp_

Многие параметры сервера в Greenplum имеют префикс **gp_** и управляют поведением MPP: **gp_interconnect_type**, **gp_interconnect_address_type** ([§2.3](chapter-02-03.md)), **gp_default_storage_options** ([§5.1](chapter-05-01.md)), **gp_resource_manager**, настройки ресурсных групп и очередей и т.д. Текущие значения можно посмотреть в **gp_settings** (агрегат pg_settings по сегментам) или в **pg_settings** на координаторе. См. справочник по параметрам конфигурации Greenplum.

---

## 7.2.8. Типичные ошибки

- **Использовать gp_segment_id на реплицированной таблице:** в Greenplum это запрещено; запрос завершится ошибкой.
- **Путать pg_stat_* и gp_stat_*:** pg_stat_activity показывает только координатор; для картины по кластеру используйте gp_stat_activity и смотрите gp_segment_id.
- **Опираться на устаревшие представления:** состав gp_toolkit и системных представлений может меняться между мажорными версиями; сверяйтесь с документацией своей версии.

---

## Ключевое

- **gp_*** — префикс системных представлений и таблиц Greenplum для топологии и статистики по кластеру: **gp_segment_configuration** (топология, status), **gp_stat_activity**, **gp_stat_*_tables** и др. (агрегат по сегментам, часто с столбцом **gp_segment_id**).
- **gp_segment_id** — сегмент для текущей строки; полезен для проверки распределения и перекоса; на реплицированных таблицах использовать нельзя.
- **gp_toolkit** — схема с представлениями для перекоса (gp_skew_*), очередей (gp_resqueue_status), ресурсных групп и др.; функции **get_ao_distribution**, **get_ao_compression_ratio** — для AO-таблиц.

В [§7.3](chapter-07-03.md) мы разберём **массовую загрузку**: COPY для быстрой загрузки из файла и gpload для ETL-сценариев.
