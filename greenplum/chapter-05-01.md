# §5.1 Heap-таблицы

В [§4.4](chapter-04-04.md) мы разобрали мониторинг и логи. Далее в главе 5 речь о **типах хранения таблиц** в Greenplum: от выбора модели хранения зависят производительность загрузки и запросов, поддержка UPDATE/DELETE и сжатие. В этом разделе — **heap-таблицы**: тип по умолчанию, **row-oriented** (построчное) хранение, сценарии использования (OLTP-подобные нагрузки, частые UPDATE/DELETE) и когда предпочесть другие модели (append-optimized, колоночные). По [Tanzu Greenplum 7 — Choosing the Table Storage Model](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-ddl-ddl-storage.html).

---

## 5.1.1. Heap-таблицы по умолчанию

В Greenplum, как и в PostgreSQL, **heap** — модель хранения таблицы по умолчанию. Если при создании таблицы не указать опции хранения (секция **WITH** или **ACCESS METHOD**), создаётся обычная **row-oriented heap-таблица**. См. [Глоссарий](glossary.md).

Пример:

```sql
CREATE TABLE dim_product (
    product_id   int PRIMARY KEY,
    name         text,
    category_id  int,
    updated_at   timestamptz DEFAULT now()
) DISTRIBUTED BY (product_id);
```

Здесь не заданы appendoptimized, orientation и т.д. — таблица будет heap, строки хранятся по строкам (row-oriented). Ключ распределения (**DISTRIBUTED BY**) задаётся отдельно от модели хранения; для heap он указывается так же, как для других типов таблиц ([§6.1](chapter-06-01.md)).

Параметр **gp_default_storage_options** позволяет задать значения по умолчанию для опций хранения (например, для тестовых окружений); в production обычно явно указывают тип таблицы в **CREATE TABLE**.

---

## 5.1.2. Row-oriented хранение

**Row-oriented** (построчное) хранение означает, что данные таблицы организованы по строкам: все столбцы одной строки лежат рядом. При чтении одной строки или небольшого числа строк с несколькими столбцами такой порядок эффективен — за одно обращение к странице получают целую строку. См. [Глоссарий](glossary.md).

Для heap-таблиц в Greenplum доступно только row-oriented хранение. Колоночное хранение (column-oriented) доступно только для **append-optimized** таблиц ([§5.3](chapter-05-03.md)).

Сравнение с колоночным (кратко): при запросах, которые читают **много строк и мало столбцов** (например, агрегации по одному столбцу), колоночное хранение часто выгоднее по I/O и сжатию. При запросах, где нужна **целиком строка** или много столбцов одной строки, row-oriented обычно эффективнее. Для смешанной нагрузки и частых изменений данных row-oriented heap даёт хороший баланс гибкости и производительности.

---

## 5.1.3. UPDATE и DELETE: версионирование строк

Heap-таблицы хранят **информацию о версиях строк** (visibility information), необходимую для корректной обработки транзакций: какая версия строки видна какому транзакции, учёт изоляции (READ COMMITTED, REPEATABLE READ и т.д.). Это та же модель, что и в PostgreSQL (MVCC — multiversion concurrency control).

**UPDATE** и **DELETE** в heap выполняются как обычно: старая версия строки помечается как устаревшая, при UPDATE создаётся новая версия (или запись в heap + индексы). Такое поведение нужно для OLTP-подобных сценариев, где данные часто меняются после загрузки. Напротив, в **append-optimized** таблицах нет per-row информации видимости; UPDATE/DELETE там либо не поддерживаются в части режимов изоляции, либо реализованы иначе (например, через маркировку и последующую очистку), и для массовых изменений после загрузки heap подходит лучше. По документации Greenplum, на append-optimized таблицах UPDATE и DELETE в транзакции REPEATABLE READ или SERIALIZABLE приводят к преждевременному завершению транзакции; DECLARE...FOR UPDATE и триггеры для append-optimized не поддерживаются. См. [§5.2](chapter-05-02.md).

Итог: если таблица часто обновляется и удаляется по строкам, предпочтительна **heap**.

---

## 5.1.4. Сценарии использования heap

По документации Greenplum heap лучше всего подходит для:

- **OLTP-подобных нагрузок**: данные часто изменяются после первоначальной загрузки; много коротких транзакций с INSERT/UPDATE/DELETE. См. [Глоссарий](glossary.md) (OLTP).
- **Небольших таблиц**, в частности **таблиц измерений (dimension tables)**: справочники, категории, контрагенты, которые обновляются по отдельным строкам (исправление атрибутов, смена статуса).
- **Таблиц с одновременными INSERT, UPDATE и DELETE**: heap поддерживает все эти операции без ограничений, присущих append-optimized.

Для **больших фактовых таблиц**, которые загружаются пачками и в основном читаются (аналитические запросы, редкие обновления), обычно выбирают append-optimized (AO) или AO columnar: там нет накладных расходов на версионирование строк (экономия порядка 20 байт на строку), возможны сжатие и оптимизация под массовую вставку. Выбор типа таблицы для разных слоёв DWH разбирается в [§5.4](chapter-05-04.md).

## 5.1.5. Явное указание heap и переход к другим типам

Чтобы явно задать heap (например, после изменения gp_default_storage_options), можно не указывать опции хранения или использовать **ACCESS METHOD heap** (в версиях, где поддерживается):

```sql
CREATE TABLE t1 (id int, val text) DISTRIBUTED BY (id);
-- или с явным указанием (синтаксис зависит от версии):
-- CREATE TABLE t1 (id int, val text) USING heap DISTRIBUTED BY (id);
```

Существующую таблицу можно перевести в другую модель хранения с помощью **ALTER TABLE ... SET ACCESS METHOD** (heap, ao_row, ao_column); при этом данные перезаписываются, операция может быть тяжёлой. См. документацию по ALTER TABLE.

---

## 5.1.6. Типичные ошибки

- **Использовать heap для огромных фактовых таблиц с только добавлением данных:** теряются выгоды AO (меньше места, быстрее массовая вставка); предпочтите append-optimized или AO columnar.
- **Ожидать сжатия на heap:** встроенное сжатие на уровне таблицы в Greenplum доступно только для append-optimized таблиц; для heap сжатия на уровне СУБД нет.
- **Путать тип хранения и распределение:** DISTRIBUTED BY задаёт, как строки распределяются по сегментам; heap/AO/columnar задаёт, как строки хранятся на страницах (по строкам или по столбцам, с версионированием или без).

---

## Ключевое

- **Heap** — тип таблицы по умолчанию в Greenplum; **row-oriented** хранение; подходит для OLTP-подобных нагрузок и частых UPDATE/DELETE.
- Heap хранит **информацию о версиях строк** (как PostgreSQL); UPDATE/DELETE работают без ограничений, присущих append-optimized таблицам.
- Рекомендуется для **небольших и средних таблиц**, в том числе **измерений**, которые часто обновляются; для больших только добавляемых фактов — обычно AO или AO columnar ([§5.2](chapter-05-02.md), [§5.3](chapter-05-03.md)).

В [§5.2](chapter-05-02.md) мы разберём append-optimized (AO) таблицы: оптимизация под массовую вставку, сжатие, AO row и подготовка к колоночному хранению.
