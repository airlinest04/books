# §9.1 Protocol eXtension Framework (PXF)

В [§8.4](chapter-08-04.md) мы завершили главу об оптимизации запросов. Часть V книги посвящена **интеграции и аналитике**: доступ к данным вне кластера и вычисления внутри БД. Данные часто лежат в **Hadoop (HDFS)**, в **облачных хранилищах** (S3, Azure Blob, GCS), в других СУБД или в файловых системах. Полная загрузка всего объёма в Greenplum не всегда нужна или возможна. **Protocol eXtension Framework (PXF)** — расширение Greenplum, которое даёт **параллельный** доступ к внешним источникам **без предзагрузки** в кластер: вы описываете внешние данные в виде **внешней таблицы**, и запросы читают их «на лету». В этом разделе — зачем нужен PXF, его **архитектура** (PXF Service на хостах, параллельное обращение с сегментов) и основные понятия: коннекторы, серверы, профили. Создание внешних таблиц и настройка источников — в [§9.2](chapter-09-02.md)–[§9.4](chapter-09-04.md). По [Tanzu Greenplum PXF — Overview](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum-platform-extension-framework/6-10/gp-pxf/overview_pxf.html), [Introduction to PXF](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum-platform-extension-framework/6-10/gp-pxf/intro_pxf.html).

## 9.1.1. Зачем PXF: доступ без загрузки и федеративные запросы

Данные в организации часто разнесены по системам: операционные данные в MySQL или Oracle, аналитика в Greenplum, архивы в S3 или HDFS. Полная выгрузка из внешней системы и загрузка в Greenplum требуют времени, места и поддержки ETL-пайплайнов. Во многих сценариях эффективнее **запросить внешние данные напрямую** и объединить результат с таблицами Greenplum в одном SQL (**federated query**): только нужное подмножество читается в момент запроса, без копирования всего объёма.

PXF предоставляет **коннекторы** к разным типам источников и **форматам** данных. Пользователь создаёт в Greenplum **внешнюю таблицу**, указывающую на путь или объект во внешней системе (файл в HDFS, префикс в S3, таблица Hive, JDBC-источник и т.д.) и **профиль** (формат: Parquet, ORC, Avro, текст, JSON и др.). Запрос к такой таблице выполняется так: сегменты Greenplum обращаются к **PXF Service** на своих хостах, PXF читает данные из внешнего источника и отдаёт строки планировщику; данные могут объединяться с локальными таблицами, фильтроваться и агрегироваться. Таким образом можно:

- **Запрашивать внешние данные на месте** (без загрузки в Greenplum).
- **Загружать выбранное подмножество** (INSERT INTO internal_table SELECT ... FROM external_table WHERE ...).
- **Писать во внешний источник** (writable external table), если коннектор это поддерживает.
- **Выполнять сложные запросы** над смесью локальных и внешних данных в одном SQL.

См. [§1.4](chapter-01-04.md), [Глоссарий](glossary.md) (PXF, Внешняя таблица).

## 9.1.2. Архитектура PXF

В развёртывании Greenplum есть **координатор** (и при необходимости Standby) и **хосты сегментов**. На **каждом хосте** (координатор и каждый хост сегментов) работает один **PXF Service** (процесс PXF). См. документацию PXF.

**На хостах сегментов** PXF Service участвует в выполнении запросов к внешним таблицам: для каждого сегмента на хосте, который участвует в скане внешней таблицы, выделяется **рабочий поток** (worker). Несколько хостов сегментов обращаются к внешнему хранилищу **параллельно** — каждый со своего хоста, за свою «долю» данных (например, свои фрагменты файлов или диапазоны). Так сохраняется параллелизм MPP: внешние данные читаются не одним процессом, а многими, что даёт высокую пропускную способность. Координатор и Standby тоже имеют процесс PXF, но в текущей реализации **передача данных** при скане внешней таблицы идёт между сегментами и внешним источником; координатор в обмене данными с внешней системой при таком скане не участвует. См. [§2.4](chapter-02-04.md).

Внутренняя реализация PXF включает компонент на стороне сегмента (расширение, интегрированное с Greenplum) и серверный процесс PXF на хосте (Java-приложение), которые обмениваются запросами и данными. Администратор устанавливает и настраивает PXF на всех узлах кластера, запускает и при необходимости обновляет PXF Service. Управление сервисом (запуск, остановка, перезагрузка конфигурации) выполняется утилитами командной строки PXF. Детали установки и конфигурации — в руководстве по PXF. См. документацию Greenplum и PXF.

## 9.1.3. Коннекторы, серверы и профили

**Коннектор** — реализация доступа к определённому типу внешнего хранилища. PXF поставляется с коннекторами для:

- **Hadoop**: HDFS, Hive, HBase;
- **Объектные хранилища**: AWS S3, Azure Blob Storage, Azure Data Lake, Google Cloud Storage, MinIO, Dell ECS;
- **SQL-базы** (через JDBC): Apache Ignite, Hive, MySQL, Oracle, Microsoft SQL Server, DB2, PostgreSQL;
- **Сетевые файловые системы** (NFS и др.).

**Сервер PXF** (server) — именованная **конфигурация** для коннектора: параметры доступа к конкретному экземпляру источника (адрес, учётные данные, дополнительные настройки). Администратор создаёт один или несколько серверов для каждого внешнего источника, к которому разрешён доступ (например, сервер `s3_prod` для бакета S3, сервер `hdfs_warehouse` для каталога в HDFS). Имя сервера указывается при создании внешней таблицы. Зарезервированное имя **default** — сервер по умолчанию; если в LOCATION не указан SERVER=, используется default. См. [§9.2](chapter-09-02.md).

**Профиль** (profile) — именованное соответствие **формату данных** и (при необходимости) **протоколу** для данного типа источника. Профиль определяет, как читать или писать байты (текст с разделителем, Parquet, ORC, Avro, JSON, SequenceFile, RCFile и т.д.). В LOCATION внешней таблицы указывают **PROFILE=** имя_профиля. Разные коннекторы поддерживают разные профили; например, для объектного хранилища используются профили вроде `s3:parquet`, `s3:text`, для HDFS — `hdfs:parquet`, `hdfs:text` и др. (синтаксис имён зависит от версии PXF). В [§9.3](chapter-09-03.md) разобраны форматы Parquet, ORC, Avro. См. документацию PXF по коннекторам и профилям.

## 9.1.4. Использование: внешняя таблица и протокол pxf

PXF реализует протокол Greenplum с именем **pxf**. Внешняя таблица, обращающаяся к данным через PXF, в предложении **LOCATION** задаёт URI с схемой **pxf://**. Общий вид (по документации PXF):

```text
LOCATION('pxf://путь_или_объект?PROFILE=профиль[&SERVER=сервер][&опция=значение ...]')
```

**Путь или объект** зависит от источника: для HDFS — абсолютный путь к файлу или каталогу; для S3 — префикс или путь к объекту; для Hive — имя таблицы в формате схема.таблица; для JDBC — параметры подключения. В **query-части** URI (после `?`) задаются **PROFILE**, при необходимости **SERVER** и прочие опции профиля или сервера. Формат строк (TEXT, CSV или CUSTOM с форматтером) указывается в предложении **FORMAT**. Полный синтаксис CREATE EXTERNAL TABLE для PXF и примеры — в [§9.4](chapter-09-04.md). См. справочник Greenplum по CREATE EXTERNAL TABLE и руководство PXF.

Ряд коннекторов и профилей поддерживают **filter pushdown** (передачу условий WHERE в источник, чтобы отфильтровать данные на стороне HDFS/S3 и т.д.) и **column projection** (чтение только указанных столбцов в колоночных форматах). Это снижает объём передаваемых данных и ускоряет запросы. См. документацию PXF.

## Ключевое

- **PXF** (Platform Extension Framework) — расширение Greenplum для **параллельного** доступа к внешним данным без загрузки в кластер; федеративные запросы (JOIN локальных и внешних таблиц), выборочная загрузка или запрос на месте.
- **Архитектура:** один **PXF Service** на каждом хосте; на хостах сегментов при скане внешней таблицы выделяются воркеры по сегментам, обращение к внешнему источнику идёт **параллельно** с нескольких хостов.
- **Коннектор** — тип источника (HDFS, S3, JDBC и др.); **сервер** — именованная конфигурация доступа; **профиль** — формат данных (Parquet, ORC, текст и т.д.). Внешняя таблица задаёт LOCATION с протоколом **pxf://** и параметрами PROFILE, SERVER.

В [§9.2](chapter-09-02.md) мы разберём **доступ к HDFS и облачным хранилищам**: настройка коннекторов и серверов для S3, Azure Blob, HDFS.
