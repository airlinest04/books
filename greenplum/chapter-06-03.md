# §6.3 Партиционирование (PARTITION BY)

В [§6.2](chapter-06-02.md) мы разобрали DISTRIBUTED RANDOMLY и REPLICATED. **Партиционирование** — это **логическое** разбиение большой таблицы на части (партиции) по значениям ключевого столбца или выражений; физическое распределение по сегментам (DISTRIBUTED BY) при этом сохраняется. В этом разделе — зачем нужно партиционирование, как оптимизатор отсекает ненужные партиции (**partition pruning**), типы партиций **RANGE** и **LIST** и как они задаются при создании таблицы. Детальный синтаксис RANGE, LIST и подпартиции — в [§6.4](chapter-06-04.md). По [Tanzu Greenplum 7 — Partitioning Large Tables](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-ddl-ddl-partition.html).

---

## 6.3.1. Партиционирование и распределение

**Распределение** (DISTRIBUTED BY или RANDOMLY) определяет, **на каком сегменте** хранится каждая строка — это физическое разбиение данных по узлам кластера. **Партиционирование** — логическое разбиение: таблица объявляется разделённой на партиции по диапазону значений (RANGE), по списку значений (LIST) или по хешу (HASH в Greenplum 7); каждая партиция хранит подмножество строк в соответствии со своими границами. Внутри партиции данные по-прежнему распределены по сегментам. См. [Глоссарий](glossary.md).

Итог: у таблицы есть и **политика распределения** (по сегментам), и при необходимости **стратегия партиционирования** (по ключу партиции). Партиционирование не заменяет распределение и не отменяет его.

---

## 6.3.2. Зачем партиционировать большие таблицы

Партиционирование больших таблиц (фактов) даёт:

- **Ускорение запросов:** если условие запроса ограничивает данные по ключу партиции (например, по дате), оптимизатор может **не сканировать** партиции, в которых заведомо нет подходящих строк (**partition pruning**, отсечение партиций). Вместо полного скана таблицы выполняется скан только нужных партиций.
- **Упрощение обслуживания:** удаление старых данных — **DROP** партиции или **ALTER TABLE ... DETACH PARTITION** вместо тяжёлого массового DELETE; загрузка новых данных — добавление новой партиции и загрузка в неё. Меньше нагрузка на VACUUM по сравнению с массовым удалением строк.
- **Управление хранением:** старые партиции можно переносить на более дешёвые носители или отдельные tablespace’ы.

Партиционирование имеет смысл, когда таблица **достаточно велика**, типичные запросы **фильтруют по ключу партиции** (дата, регион, период), и данные можно **равномерно** разбить по этому ключу. Для маленьких таблиц накладные расходы на множество партиций (планирование, обслуживание, количество файлов) могут перевесить выгоду. Не создавайте избыточное число партиций; при многоуровневом партиционировании число листовых партиций растёт очень быстро. См. документацию Greenplum.

---

## 6.3.3. Partition pruning (отсечение партиций)

**Partition pruning** (partition elimination) — использование оптимизатором ограничений партиций для того, чтобы **не сканировать** партиции, не содержащие строк, удовлетворяющих условию запроса. Например, при партиционировании по месяцу и запросе `WHERE logdate >= '2024-01-01' AND logdate < '2024-02-01'` сканируются только партиции за январь 2024 года. См. [Глоссарий](glossary.md).

Отсечение работает, когда в запросе есть **прямое и простое** ограничение по ключу партиции с **неизменяемыми** операторами (=, <, <=, >, >=, <>). Поддерживаются **STABLE** и **IMMUTABLE** функции (например, `date > CURRENT_DATE`); **VOLATILE** функции в предикате могут помешать отсечению. Важное ограничение: отсечение **не выполняется**, когда значения ключа партиции задаются **подзапросом** (например, `WHERE region IN (SELECT region FROM ...)`); список партиций должен быть определён на этапе компиляции запроса. Проверять, что партиции отсекаются, можно по плану запроса (**EXPLAIN**): в плане должны фигурировать только нужные партиции, а не вся иерархия.

Если запрос не ограничивает данные по ключу партиции и сканирует все партиции, партиционированная таблица может выполняться **медленнее**, чем непартиционированная из-за накладных расходов на обход иерархии. Партиционируйте только тогда, когда значимая часть запросов позволяет отсекать партиции.

---

## 6.3.4. Типы партиций: RANGE и LIST

**RANGE** — партиции задаются **диапазонами** значений ключа (например, по дате: январь, февраль, …; по числу: 0–1000, 1000–2000). Границы обычно задаются как включительно нижняя и **исключительно** верхняя: партиция `FROM ('2024-01-01') TO ('2024-02-01')` содержит даты с 2024-01-01 по 2024-01-31 включительно; 2024-02-01 попадает в следующую партицию. См. [§6.4](chapter-06-04.md).

**LIST** — партиции задаются **списком** значений ключа (например, регион: 'usa', 'europe', 'asia'; статус: 'new', 'done'). Каждая партиция хранит строки с указанными значениями. Часто добавляют **DEFAULT**-партицию для значений, не входящих ни в один явный список. См. [§6.4](chapter-06-04.md).

В Greenplum 7 также поддерживается **HASH**-партиционирование (по модулю и остатку от хеша ключа); детали см. в документации. В этом разделе основное внимание — RANGE и LIST как наиболее распространённые в DWH.

## 6.3.5. Корневая таблица и партиции

**Партиционированная таблица** (root, корень) — виртуальная таблица без собственного хранения; данные лежат в **партициях** (дочерних таблицах). Каждая партиция — обычная таблица Greenplum с ограничением (partition bound), задающим допустимые значения ключа. При **INSERT** в корневую таблицу Greenplum направляет строки в нужную партицию по значению ключа партиции. Партиция может быть объявлена партиционированной снова — получается **подпартиционирование** (многоуровневая иерархия). Листовые партиции (leaf) — партиции без дочерних; только они хранят данные. См. документацию Greenplum.

Партицию можно **отсоединить** (DETACH) от родителя — она станет самостоятельной таблицей с сохранёнными данными; партицию можно **добавить** (ATTACH), в том числе превратив в партицию существующую таблицу. Обычную таблицу нельзя «сделать» партиционированной одной командой — нужно создать новую партиционированную таблицу, перенести данные, удалить старую и переименовать новую. См. [§6.4](chapter-06-04.md) и справочник ALTER TABLE.

## 6.3.6. Простой пример партиционированной таблицы

Пример таблицы, партиционированной по **RANGE** по дате (современный синтаксис Greenplum 7):

```sql
CREATE TABLE fact_events (
    event_id   bigint,
    event_date date,
    region     text,
    amount     numeric(12,2)
) DISTRIBUTED BY (event_id)
  PARTITION BY RANGE (event_date);

CREATE TABLE fact_events_2024_01 PARTITION OF fact_events
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE fact_events_2024_02 PARTITION OF fact_events
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
-- и т.д.
```

Запрос `SELECT ... FROM fact_events WHERE event_date >= '2024-02-01' AND event_date < '2024-03-01'` при корректном отсечении сканирует только партицию `fact_events_2024_02`. Пример **LIST** — в [§6.4](chapter-06-04.md).

## 6.3.7. Типичные ошибки

- **Партиционировать маленькие таблицы:** накладные расходы на множество партиций и планирование могут быть больше выигрыша от pruning.
- **Выбирать ключ, по которому запросы не фильтруют:** отсечение не срабатывает, все партиции сканируются; производительность может ухудшиться.
- **Полагаться на partition pruning при условии с подзапросом:** значения из подзапроса не используются для отсечения; проверяйте план (EXPLAIN).
- **Создавать слишком много партиций (многоуровневая глубокая иерархия):** число листовых партиций и файлов растёт быстро; усложняется обслуживание (vacuum, backup, расширение кластера). Оценивайте количество партиций заранее.

---

## Ключевое

- **Партиционирование** — логическое разбиение таблицы по ключу (RANGE, LIST, HASH); распределение по сегментам задаётся отдельно (DISTRIBUTED BY).
- **Partition pruning** — отсечение партиций по условию запроса; работает при прямых ограничениях по ключу партиции; не работает при значениях из подзапроса; проверяйте по EXPLAIN.
- **RANGE** — по диапазонам (даты, числа); **LIST** — по списку значений (регион, статус). Партиции — дочерние таблицы; данные вставляются в корень и маршрутизируются в нужную партицию.

В [§6.4](chapter-06-04.md) мы разберём синтаксис партиционирования по диапазону и списку подробнее: RANGE (даты, числа), LIST (регион, статус), подпартиции и default-партиция.
