# §3.4 Правила перехода между слоями

В [§3.2](chapter-03-02.md) мы описали классические слои (Raw, Staging, Core, Mart), в [§3.3](chapter-03-03.md) — варианты их наименований. Чтобы слои работали как задумано (переиспользование, аудит, перезапуск), нужны **правила**: что можно и нельзя на каждом слое, в каком порядке выполнять загрузки и как обеспечивать **идемпотентность** и **повторяемость** загрузок. В этом разделе мы сформулируем эти правила. Глава 3 на этом завершается; в [§4.1](chapter-04-01.md) мы перейдём к схемам «звезда» и «снежинка» — структурам данных в витринах и в ядре. См. [Глоссарий](glossary.md).

---

## 3.4.1. Общие принципы правил

Правила перехода между слоями преследуют несколько целей:

- **Целостность данных:** данные не должны теряться и не должны дублироваться при повторном прогоне; следующий слой не должен обновляться до готовности предыдущего.
- **Воспроизводимость:** повторный запуск пайплайна (за тот же период или с теми же ключами) даёт предсказуемый результат — идемпотентность.
- **Прослеживаемость:** можно понять, откуда взялись данные в слое (источник, загрузка, дата).
- **Разделение ответственности:** каждый слой имеет чёткие границы: кто пишет, кто читает, какие преобразования допустимы.

Ниже правила сформулированы по слоям (Raw → Staging → Core → Mart) и дополнены требованиями к идемпотентности и порядку загрузки.

---

## 3.4.2. Сырой слой (Raw / Landing): что можно и нельзя

**Кто пишет:** только процесс извлечения данных из источников (ingestion). Никакие другие пайплайны не должны записывать в Raw от имени «преобразований» — иначе сырой слой перестаёт быть воспроизводимым снимком источника.

**Что можно:**
- Добавлять новые данные (новая партиция за дату загрузки, новый файл, append).
- При необходимости перезаписывать данные **в рамках одной и той же загрузки** за тот же период (идемпотентность по ключу загрузки: повторный прогон за тот же run_id или дату загрузки не создаёт дубликатов — либо вставка с заменой партиции, либо проверка «уже загружено»).
- Минимальные технические преобразования: распаковка, разбор формата, запись в единый формат хранения (например, Parquet). Без бизнес-логики и без объединения с другими источниками.

**Что нельзя:**
- Удалять или изменять данные из прошлых загрузок «по бизнес-причине» (например, «исправить ошибку»). Исправления делаются на следующих слоях или через новую загрузку с меткой. Исключение — явная политика перезаписи партиции за период при идемпотентном повторном прогоне за тот же период.
- Писать в Raw результатам преобразований из Staging или Core — Raw только от источников.
- Смешивать данные из разных источников в одну таблицу без явного ключа источника и загрузки (иначе теряется прослеживаемость).

**Метаданные:** каждая загрузка должна помечаться (дата/время, идентификатор пайплайна, при необходимости источник и версия). Это нужно для отладки и перезапуска следующих этапов.

---

## 3.4.3. Промежуточный слой (Staging / ODS): что можно и нельзя

**Кто пишет:** пайплайны, читающие из Raw (и только из Raw для этого слоя) и выполняющие очистку и подготовку. Данные из источников в Staging не пишутся напрямую — только через Raw.

**Что можно:**
- Читать из Raw за выбранный период или по ключу загрузки.
- Валидировать, приводить типы, дедуплицировать в рамках одного источника; записывать результат в Staging. Перезапись партиции или таблицы за период при повторном прогоне допустима (идемпотентность: повторный прогон за тот же период даёт тот же результат — полная перезапись за период или merge по ключу).
- Хранить несколько «версий» по дате загрузки, если это зафиксировано в политике слоя (например, одна партиция на дату загрузки).

**Что нельзя:**
- Писать в Staging данные, минуя Raw (напрямую из источника). Иначе теряется воспроизводимость: при перезапуске Raw → Staging нельзя будет пересчитать Staging из Raw.
- Интегрировать данные из разных источников в единые сущности, если слой определён как «очистка по источнику». Интеграция — в Core; в Staging допустима только подготовка к ней (единые форматы полей, ключи).
- Удалять данные из Raw из Staging (Staging не управляет Raw).

**Зависимости:** загрузка в Staging выполняется после успешной загрузки в Raw за соответствующий период. Порядок: сначала Raw, затем Staging.

---

## 3.4.4. Ядро (Core / DWH): что можно и нельзя

**Кто пишет:** пайплайны, читающие из Staging (и при необходимости из Raw для дополнительных источников) и выполняющие интеграцию: сопоставление сущностей, загрузка справочников, применение бизнес-правил, временная привязка, версионирование измерений (SCD). Витрины в Core не пишут — Core питает витрины, а не наоборот.

**Что можно:**
- Читать из Staging (и при необходимости из Raw) по всем релевантным источникам.
- Интегрировать: единые ключи сущностей, единые справочники, объединение атрибутов из нескольких источников. Записывать в Core в нормализованной форме, Data Vault или иной принятой модели.
- Добавлять новые записи (факты, версии измерений) или обновлять по правилам SCD и бизнес-логике. Идемпотентность: повторный прогон за тот же период не должен создавать дубликатов фактов и некорректных версий измерений (например, вставка только новых фактов по бизнес-ключу и дате, закрытие версий измерений по правилам).
- Хранить историю (неизменяемость или версионирование) согласно принципам [§1.3](chapter-01-03.md).

**Что нельзя:**
- Писать в Core данные из витрин (Mart) или из отчётов. Core — верх по потоку от источников; обратный поток «из отчёта в ядро» не допускается.
- Удалять или перезаписывать историю без явной регламентированной процедуры (корректировки — через отдельные записи или версии, с аудитом).
- Пропускать Staging и писать в Core напрямую из Raw, если политика проекта требует прохождения Staging (иначе нарушается единая точка очистки). Исключение — явно принятая архитектура «Raw → Core» без отдельного Staging.

**Зависимости:** загрузка в Core выполняется после готовности Staging (и при необходимости Raw) за соответствующий период. Измерения, от которых зависят факты, загружаются или обновляются перед фактами.

---

## 3.4.5. Витрины (Mart / Presentation): что можно и нельзя

**Кто пишет:** пайплайны, читающие из Core (и только из Core или из утверждённого набора слоёв) и формирующие витрины: денормализация, агрегаты, срезы по доменам. Пользователи и отчёты в Mart не пишут — только читают.

**Что можно:**
- Читать из Core (таблицы фактов, измерений, интеграционные представления).
- Строить звёздные схемы, агрегатные таблицы, материализованные представления. Записывать в Mart. Полная перезапись витрины за период или инкрементальное обновление по правилам — при повторном прогоне результат идемпотентный (та же витрина за период).
- Хранить только то, что нужно для отчётов данного домена; не обязательно хранить всю детализацию Core.

**Что нельзя:**
- Читать для построения витрины из Raw или из неочищенных зон, если политика проекта требует питание из Core. Иначе витрина перестаёт быть согласованной с остальными (единый источник правды — Core).
- Писать в Core или в Staging из пайплайна витрин. Поток односторонний: источники → Raw → … → Core → Mart.
- Менять историю в Core из витрины (витрина — потребитель, не источник правды для ядра).

**Зависимости:** загрузка витрин выполняется после обновления Core за соответствующий период. Если витрина зависит от нескольких областей Core, порядок обновления Core (измерения → факты) должен быть соблюдён до запуска загрузки витрины.

## 3.4.6. Идемпотентность и повторяемость загрузок

**Идемпотентность** загрузки означает: повторное выполнение пайплайна с теми же входными данными и за тот же период (или с тем же ключом запуска) не меняет итоговое состояние слоя или меняет его предсказуемо так, что результат эквивалентен одному успешному прогону. Нет дубликатов, нет «поломанных» данных после повторного запуска. См. [Глоссарий](glossary.md).

Как достигается:

- **Raw:** загрузка за период привязана к ключу (дата загрузки, run_id). Повторный прогон: либо перезапись партиции за этот период (результат тот же), либо проверка «уже есть» и пропуск.
- **Staging:** перезапись партиции/таблицы за период при каждом прогоне; или merge по бизнес-ключу и дате с обновлением только изменившихся полей. Вход — Raw за период; результат однозначен.
- **Core:** факты — вставка только «новых» по (бизнес-ключ, дата) или перезапись партиции за период; измерения — по правилам SCD (новая версия вместо перезаписи текущей). Повторный прогон не создаёт дублей фактов и не ломает версии измерений.
- **Mart:** полная перезапись витрины за период из Core или инкремент по правилам (например, удаление + вставка за период). Повторный прогон даёт тот же набор данных за период.

**Повторяемость** означает: при наличии одних и тех же данных в предыдущем слое повторный запуск следующего этапа воспроизводит тот же результат. Это обеспечивается идемпотентностью и фиксированным порядком загрузки (сначала зависимости). Перезапуск с нужной точки (например, только Core → Mart при сбое на Mart) при сохранении данных в Core даёт корректное состояние Mart без повторного чтения источников.

---

## 3.4.7. Порядок загрузки и зависимости

Рекомендуемый порядок выполнения загрузок в рамках одного цикла (например, ночная загрузка):

1. **Извлечение и запись в Raw** по всем источникам за целевой период.
2. **Очистка и запись в Staging** по каждому источнику (читаем Raw за период).
3. **Интеграция и запись в Core:** сначала обновление измерений (справочники, SCD), затем загрузка фактов. При наличии зависимостей между областями Core — порядок по зависимостям.
4. **Построение витрин (Mart):** после готовности Core каждая витрина пересчитывается за период (или инкрементально по своим правилам).

Параллельное выполнение допустимо там, где нет зависимостей: несколько источников в Raw параллельно; несколько витрин после готовности Core — параллельно. Нельзя обновлять Mart до готовности Core за тот же период; нельзя обновлять Core до готовности Staging за тот же период. Явная фиксация зависимостей (граф пайплайнов, расписание) снижает риск «гонок» и неполных данных.

## 3.4.8. Типичные ошибки

- **Писать в Raw из пайплайна преобразований:** Raw только от источников; иначе сырой слой теряет смысл воспроизводимого снимка.
- **Пропускать слой при перезапуске:** перезапуск «только Mart» при изменённом Core корректен; перезапуск «только Mart» без пересчёта Core за новый период даёт устаревшую витрину. Нужно явно определять, какие срезы данных актуальны после перезапуска.
- **Не обеспечивать идемпотентность:** повторный прогон создаёт дубликаты или портит историю измерений. Необходимы уникальные ключи, партиции и правила вставки/обновления.
- **Обновлять слои в неправильном порядке:** например, обновить Mart до обновления Core за тот же день — витрина будет содержать смесь старых и новых данных или неполные данные.
- **Не фиксировать метаданные загрузки:** без run_id или даты загрузки сложно связать данные в слое с конкретным прогоном и воспроизвести цепочку при расследовании.

---

## Ключевое

- **Правила по слоям:** Raw — пишет только ingestion; только добавление или идемпотентная перезапись за период; без бизнес-преобразований. Staging — пишет только из Raw; очистка и подготовка; идемпотентность за период. Core — пишет только из Staging/Raw; интеграция; без записи из Mart. Mart — пишет только из Core; потребление только чтением.
- **Идемпотентность:** повторный прогон за тот же период/ключ не создаёт дубликатов и не портит данные; достигается перезаписью партиций, merge по ключам, вставкой только новых записей по правилам.
- **Порядок загрузки:** Raw → Staging → Core (сначала измерения, затем факты) → Mart. Витрины после готовности Core за период; параллельное выполнение только при отсутствии зависимостей.
- Метаданные загрузки (дата, run_id, источник) на каждом слое обеспечивают прослеживаемость и воспроизводимость. Нарушение правил (запись не из того слоя, неверный порядок, неидемпотентность) ведёт к рискам целостности и аудита.

В [§4.1](chapter-04-01.md) мы начнём главу 4 и разберём измерения и факты — основы схем «звезда» и «снежинка», которые используются в витринах и в размерном моделировании.
