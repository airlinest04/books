# §5.4 Срезы по дате и запросы к истории

В [§5.3](chapter-05-03.md) мы разобрали реализацию Type 2: структуру измерения с effective_from/effective_to и логику ETL. При запросах к данным нужно **корректно выбирать версию измерения**: для отчёта «на дату» — версию, актуальную на эту дату; для отчёта по фактам — связь факта с измерением по суррогатному ключу (факт уже привязан к версии на дату события). В этом разделе мы разберём **срезы по дате** и **запросы к истории**: как писать запросы к измерению «на дату», как связывать факты с измерением по периоду действия и какие подводные камни избегать. Глава 5 на этом завершается; в [§6.1](chapter-06-01.md) мы перейдём к главе 6 — витринам данных (Data Marts). См. [Глоссарий](glossary.md).

---

## 5.4.1. Выбор версии измерения «на дату»

**Срез измерения на дату** (dimension as of date) — выбор той версии строки измерения, которая была актуальна на заданную дату. Условие: дата попадает в интервал действия версии. См. [Глоссарий](glossary.md).

Для одной строки измерения (одной версии) интервал действия: **[effective_from, effective_to)** — включительно начало, исключительно конец (или effective_to IS NULL для текущей версии, трактуем как «до сих пор»). Заданная дата **as_of_date** попадает в эту версию, если:

- effective_from <= as_of_date  
- и (effective_to IS NULL OR effective_to > as_of_date)

В SQL для параметра @as_of_date:

```sql
SELECT *
FROM dim_product
WHERE effective_from <= @as_of_date
  AND (effective_to IS NULL OR effective_to > @as_of_date);
```

Так получаем «снимок» измерения на дату: каждая сущность (по бизнес-ключу) представлена не более одной строкой — той версией, которая действовала на @as_of_date. Для отчёта «список продуктов и их категорий на конец прошлого года» подставляем дату 31.12 прошлого года и соединяем при необходимости с другими таблицами.

Если измерение хранит effective_to как дату включительно (closed interval), условие меняется на effective_to >= @as_of_date; важно зафиксировать в проекте, включён ли конец периода в интервал или нет, и везде использовать одну и ту же семантику.

## 5.4.2. Связь фактов с измерением по периоду действия

В фактовой таблице хранится **суррогатный ключ** измерения (product_sk, customer_sk и т.д.), полученный при загрузке фактов по правилу «версия, действующая на дату факта» ([§5.3](chapter-05-03.md)). Поэтому **прямой JOIN факта с измерением по суррогатному ключу** уже даёт правильную версию атрибутов для каждого факта: факт за январь связан с версией продукта на январь, факт за март — с версией на март (если между январем и мартом атрибут менялся).

Пример: «Продажи по категориям за январь 2024».

```sql
SELECT d.category, SUM(f.amount) AS revenue
FROM fact_sales f
JOIN dim_product d ON f.product_sk = d.product_sk
JOIN dim_date dt ON f.date_id = dt.date_id
WHERE dt.year = 2024 AND dt.month = 1
GROUP BY d.category;
```

Дополнительного фильтра по effective_from/effective_to в запросе **не нужно**: факт уже содержит product_sk той версии, которая была актуальна на дату продажи. JOIN по product_sk однозначно подтягивает категорию на момент продажи. Так исторический отчёт «продажи по категориям за январь» даёт корректные категории на январь.

Исключение: если факты загружались **до** внедрения Type 2 и в них подставлен «текущий» суррогатный ключ (все факты ссылаются на текущую версию). Тогда старые факты будут показывать текущую категорию, а не историческую. Исправление — перезагрузка привязки фактов к версиям (пересчёт product_sk по дате факта и бизнес-ключу) при наличии истории в измерении.

## 5.4.3. Запрос «факты + измерение на дату среза»

Иногда нужен отчёт не «как было на дату каждого факта», а «как выглядело измерение на одну общую дату» для всех фактов. Например: «все продажи за год с категорией продукта на конец года». Тогда факты соединяют не просто с измерением по product_sk, а с **версией измерения на фиксированную дату**.

Вариант 1: подзапрос или CTE с измерением на дату (как в 5.4.1), затем JOIN фактов с этим набором по бизнес-ключу (в факте должен быть доступен бизнес-ключ продукта или соединение через текущее измерение по product_sk с последующей заменой на версию «на дату» по business_key). На практике в факте часто хранится только суррогатный ключ; тогда «измерение на дату среза» используют для отчётов типа «список сущностей и атрибутов на дату», а не для перепривязки всех фактов.

Вариант 2: если нужны факты с атрибутами измерения **на дату факта** (типичный случай исторического отчёта) — достаточно обычного JOIN по суррогатному ключу, как в 5.4.2. Срез «на одну общую дату» для атрибутов при анализе фактов — менее частый сценарий; он требует либо хранения в факте бизнес-ключа, либо отдельной логики сопоставления факта с версией на заданную дату по дате факта и бизнес-ключу из измерения.

Итог: в большинстве отчётов «факты за период + атрибуты на момент факта» достаточно JOIN по суррогатному ключу; срез измерения «на дату» как отдельный запрос — по условию effective_from / effective_to из 5.4.1.

## 5.4.4. Текущее состояние измерения

Для запроса **«текущий список»** (все продукты, все клиенты с актуальными атрибутами) используют фильтр по текущей версии:

```sql
SELECT * FROM dim_product WHERE is_current = 1;
-- или
SELECT * FROM dim_product WHERE effective_to IS NULL;
```

Одна строка на сущность (на бизнес-ключ). Используется в справочных отчётах, в выпадающих списках и при проверке данных.

---

## 5.4.5. Измерение «Дата» и роль измерений

Измерение «Дата» (dim_date) обычно **не версионируют** по Type 2: календарная дата не меняется. Но одно и то же измерение даты может участвовать в факте в **нескольких ролях** (дата заказа, дата отгрузки) — см. [§4.3](chapter-04-03.md). Для каждой роли в запросе свой алиас: JOIN dim_date d_order ON f.order_date_id = d_order.date_id, JOIN dim_date d_ship ON f.ship_date_id = d_ship.date_id. Срезы «на дату» для dim_date не требуют effective_from/effective_to — дата статична.

## 5.4.6. Типичные ошибки

- **Фильтровать измерение по is_current = 1 в историческом отчёте по фактам:** тогда все факты получат текущую версию атрибутов, и отчёт «продажи по категориям за прошлый год» будет неверен. Для отчётов по фактам — JOIN по суррогатному ключу без фильтра по is_current.
- **Путать срез измерения на дату и срез фактов за период:** «измерение на 31.12» — версии измерений, актуальные на эту дату; «факты за январь» — факты с датой в январе. Для «продажи за январь с категориями на момент продажи» нужны факты за январь + JOIN с измерением по product_sk (без среза измерения на одну дату).
- **Не учитывать NULL в effective_to:** в части СУБД сравнение с NULL даёт UNKNOWN; условие должно явно включать (effective_to IS NULL OR effective_to > @as_of_date).
- **Разная семантика границ периода:** если в одном месте effective_to «исключительно», в другом «включительно», срезы на граничную дату дадут разный результат. Зафиксировать в модели и в ETL единую семантику.

---

## Ключевое

- **Срез измерения на дату:** версия, для которой effective_from <= @as_of_date AND (effective_to IS NULL OR effective_to > @as_of_date). Один запрос к измерению с этим условием даёт «снимок» измерений на дату.
- **Факты и измерение:** факт хранит суррогатный ключ версии на дату события. **JOIN по суррогатному ключу** даёт корректные атрибуты на момент факта; дополнительный фильтр по effective_from/effective_to в запросе к отчёту по фактам не нужен.
- **Текущее состояние:** WHERE is_current = 1 (или effective_to IS NULL). Запрос «факты + измерение на одну общую дату среза» возможен, но требует отдельной логики; типичный исторический отчёт — факты за период с атрибутами на дату каждого факта (JOIN по суррогатному ключу).
- Единая семантика границ периода (включительно/исключительно) и учёт NULL в effective_to. Глава 5 завершена; витрины данных — в главе 6.

В [§6.1](chapter-06-01.md) мы начнём главу 6 и дадим определение витрины данных (Data Mart): подмножество данных DWH, ориентированное на домен или группу пользователей, с упрощённой моделью для отчётов.
