# §5.3 Реализация Type 2

В [§5.2](chapter-05-02.md) мы описали типы SCD; Type 2 — новая строка при изменении с датами действия и флагом текущей версии. В этом разделе разберём **реализацию Type 2**: структуру таблицы измерения (**суррогатный ключ**, **effective_from**, **effective_to**, **is_current**), **логику ETL** при обновлении измерения (сравнение с текущей версией, закрытие старой, вставка новой) и связь с загрузкой фактов. В [§5.4](chapter-05-04.md) — как писать запросы к измерению «на дату» и связывать факты с версией по периоду действия. См. [Глоссарий](glossary.md).

---

## 5.3.1. Структура таблицы измерения для Type 2

Таблица измерения с поддержкой Type 2 содержит:

- **Суррогатный ключ (PK):** уникальный идентификатор каждой строки (каждой версии). Генерируется при вставке (автоинкремент, sequence, UUID). В фактовой таблице хранится именно этот ключ — так факт привязывается к конкретной версии измерения на дату события. См. [Глоссарий](glossary.md).

- **Бизнес-ключ (natural key):** идентификатор сущности в источнике (product_code, customer_id из ERP/CRM). Один и тот же бизнес-ключ может встречаться в нескольких строках (несколько версий одной сущности); уникальность по (business_key, effective_from) или по (business_key, is_current) при is_current=1.

- **Атрибуты измерения:** название, категория, регион и т.д. — те поля, которые могут меняться и по которым ведётся история (или часть из них по Type 2, часть по Type 1).

- **effective_from:** дата (или дата-время) начала действия данной версии. Для первой версии — дата появления сущности в источнике или дата первой загрузки; для последующих версий — дата изменения (дата из источника или дата загрузки).

- **effective_to:** дата окончания действия версии. Для **текущей** версии — NULL или условная «максимальная» дата (например, 9999-12-31); для исторических версий — дата, с которой начала действовать следующая версия (то есть effective_from следующей строки).

- **is_current:** флаг (0 или 1): 1 — текущая версия (актуальна «сейчас»), 0 — историческая. У одной сущности (по бизнес-ключу) только одна строка с is_current = 1. Удобно для запросов «текущий список» без проверки effective_to IS NULL.

Пример структуры (фрагмент):

| product_sk (PK) | product_code (business key) | product_name | category | effective_from | effective_to | is_current |
|-----------------|-----------------------------|--------------|----------|----------------|--------------|------------|
| 1 | P001 | Молоко 1л | Молочные | 2020-01-01 | 2024-03-15 | 0 |
| 2 | P001 | Молоко 1л | Свежие продукты | 2024-03-15 | NULL | 1 |

Факты за период до 2024-03-15 ссылаются на product_sk = 1; факты с 2024-03-15 — на product_sk = 2. Суррогатный ключ в факте — product_sk (или product_id в именовании проекта).

## 5.3.2. Логика ETL при обновлении измерения

При каждой загрузке измерения (из Staging или из источника) для каждой входящей записи выполняют:

1. **Найти текущую версию** сущности по бизнес-ключу: строка с is_current = 1 (или effective_to IS NULL) для данного business_key.

2. **Сравнить** входящие атрибуты (те, что ведём по Type 2) с атрибутами текущей версии. Сравнивать только значимые поля; служебные (дата загрузки) не трогаем.

3. **Если атрибуты не изменились:** ничего не делать (или обновить только Type 1-атрибуты, если такие есть).

4. **Если атрибуты изменились:**
   - **Закрыть текущую версию:** UPDATE текущей строки SET effective_to = [дата изменения], is_current = 0. Датой изменения обычно считают дату загрузки или дату из источника (если есть).
   - **Вставить новую версию:** INSERT новой строки с новыми значениями атрибутов, effective_from = [та же дата, что effective_to старой], effective_to = NULL (или 9999-12-31), is_current = 1. Суррогатный ключ генерируется автоматически.

В результате у одной сущности (business_key) появляется вторая строка; старая остаётся с заполненным effective_to, новая — текущая. Идемпотентность: при повторной загрузке тех же данных изменение не должно детектироваться (сравнение по атрибутам), либо даты не должны дублироваться; при повторной вставке «новой» версии с теми же данными можно проверять «уже есть текущая версия с такими атрибутами» и не вставлять дубликат.

## 5.3.3. Выбор даты изменения (effective_from / effective_to)

Дата, которую подставляют в effective_from новой версии и в effective_to старой, может быть:

- **Дата загрузки в DWH:** дата/время выполнения ETL. Плюс — всегда есть; минус — не отражает реальную дату изменения в источнике.
- **Дата из источника:** если источник передаёт «дату последнего изменения» или «дату начала действия» записи. Предпочтительно для корректности исторических срезов.
- **Дата из фактов:** в некоторых схемах дату смены версии берут из даты первого факта с «новым» состоянием (например, первая продажа продукта в новой категории). Сложнее в реализации.

Единообразие в рамках одного измерения важно: не смешивать «дату загрузки» и «дату из источника» без правил, иначе срезы «на дату» будут интерпретироваться некорректно.

---

## 5.3.4. Загрузка фактов и привязка к версии измерения

При загрузке **фактов** нужно подставлять в фактовую таблицу **суррогатный ключ той версии измерения, которая действовала на дату факта**. Алгоритм:

- Для каждого факта известны бизнес-ключ измерения (например, product_code) и дата факта (event_date или date_id).
- Найти в измерении строку, где business_key = [код из факта] AND effective_from <= [дата факта] AND (effective_to IS NULL OR effective_to > [дата факта]). Либо через is_current не пользоваться — для исторических фактов нужна именно версия на дату факта.
- Подставить в факт найденный суррогатный ключ (product_sk).

Так факт «привязывается» к правильной версии продукта/клиента/магазина на момент события. Если при загрузке фактов подставлять всегда «текущую» версию (is_current = 1), исторические факты окажутся связаны с новой версией и отчёты «на дату» будут неверны. Подробнее запросы к истории — в [§5.4](chapter-05-04.md).

---

## 5.3.5. Новые сущности (первая версия)

При появлении **новой сущности** в источнике (новый продукт, новый клиент) в измерении выполняется не обновление, а **вставка первой версии**:

- INSERT с новым суррогатным ключом, business_key из источника, атрибуты, effective_from = [дата появления или дата загрузки], effective_to = NULL, is_current = 1.

Отдельная ветка в ETL: «если по business_key нет ни одной строки — INSERT, иначе — сравнить с текущей версией и при изменении закрыть + вставить новую».

---

## 5.3.6. Типичные ошибки

- **В факте хранить бизнес-ключ вместо суррогатного:** тогда при JOIN с измерением нельзя однозначно выбрать версию на дату факта (в измерении несколько строк с одним business_key). В факте должен быть суррогатный ключ версии.
- **Не закрывать предыдущую версию:** после INSERT новой версии забыть UPDATE старой (effective_to, is_current). Получится две «текущих» версии и неоднозначность.
- **Путать дату факта и дату загрузки:** при привязке факта к версии измерения использовать дату загрузки факта, а не дату события. Нужна дата события (event_date / date_id).
- **Разная семантика effective_from в одном измерении:** для одних строк — дата из источника, для других — дата загрузки. Должна быть единая политика.
- **Нет уникальности по (business_key, is_current):** допускать две строки с одним business_key и is_current = 1. Ограничение (unique constraint) по (business_key) где is_current = 1 или эквивалентная проверка в ETL предотвращают ошибку.

---

## Ключевое

- **Структура Type 2:** суррогатный ключ (PK) на каждую версию; бизнес-ключ; атрибуты; **effective_from**, **effective_to** (NULL для текущей), **is_current** (1 — текущая, 0 — историческая).
- **ETL при изменении:** найти текущую версию по business_key; сравнить атрибуты; при изменении — UPDATE текущей (effective_to, is_current = 0), INSERT новой (effective_from, effective_to = NULL, is_current = 1). Новые сущности — только INSERT первой версии.
- **Дата изменения** — единая политика (дата загрузки или дата из источника) для effective_from/effective_to. **Загрузка фактов:** подставлять суррогатный ключ версии, для которой effective_from <= дата факта < effective_to (или effective_to IS NULL).
- Факт хранит суррогатный ключ измерения; при запросе «на дату» выбирается версия по периоду действия. Запросы к истории и срезы — в §5.4.

В [§5.4](chapter-05-04.md) мы разберём срезы по дате и запросы к истории: как писать запросы к измерению «на дату» и связывать факты с версией по периоду действия.
