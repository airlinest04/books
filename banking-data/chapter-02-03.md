# §2.3 Данные для отчётности и аналитики

В [§2.2](chapter-02-02.md) мы разобрали авторизацию, клиринг и данные транзакции (сумма, дата, мерчант, MCC). Теперь — какие **агрегаты и разрезы** нужны для отчётности и аналитики по картам: **обороты** по картам, **средний чек**, **сегментация**, и какие данные требуются для внутренних отчётов, регуляторики и **антифрода**. Материал опирается на сущности и транзакции из [§2.1](chapter-02-01.md) и [§2.2](chapter-02-02.md); связь с планом счетов и загрузка в DWH — в [§2.4](chapter-02-04.md). См. [Глоссарий](glossary.md).

---

## 2.3.1. Обороты по картам

**Обороты по картам** — сумма проведённых транзакций за период в разрезе выбранного объекта: карта, договор, клиент, продукт, филиал, канал (POS/ATM/e-commerce), категория мерчанта (MCC) и т.д. См. [Глоссарий](glossary.md).

Что считать:

- **По дате:** обороты за период считаются по дате валютирования (для сверки с бухучётом и отчётами по движению средств) или по дате авторизации (для анализа активности и антифрода). В отчёте и витрине должно быть явно указано: «обороты по дате зачёта» или «по дате операции».
- **База расчёта:** только успешно проведённые транзакции (статус «проведена»); отмены и возвраты учитываются отдельно (отрицательные суммы или отдельный показатель «возвраты за период»), чтобы не занижать обороты при агрегации.
- **Разрезы:** обороты по договору/карте (для отчёта клиенту), по продукту (дебетовая/кредитная), по сегменту клиентов, по MCC (категории расходов), по каналу, по региону/стране мерчанта. Для этого в данных транзакции должны быть привязка к карте → договору → клиенту и атрибуты мерчанта/MCC. См. [§2.2](chapter-02-02.md).

Типичные поля витрины оборотов: период (день/месяц), идентификатор объекта (договор, карта, клиент, продукт, MCC), количество транзакций, сумма оборотов (в валюте счёта или в единой валюте), при необходимости — сумма возвратов. Источник — таблица транзакций с фильтром по статусу и дате; агрегация по выбранному измерению. См. [§4.2](chapter-04-02.md).

## 2.3.2. Средний чек

**Средний чек** — средняя сумма одной транзакции за период по выбранной совокупности: по карте, договору, клиенту, продукту, MCC, каналу. См. [Глоссарий](glossary.md).

Формула: сумма проведённых транзакций за период / количество транзакций за тот же период. Возвраты могут учитываться как отрицательные транзакции (тогда средний чек считается по нетто-обороту и количеству всех операций) или исключаться из расчёта — в зависимости от бизнес-правила; в отчёте правило должно быть зафиксировано.

Для расчёта в данных нужны: транзакции за период с суммой и привязкой к объекту (договор, продукт, MCC и т.д.), подсчёт количества и суммы. Средний чек по MCC используется для анализа структуры расходов; по каналу — для сравнения POS, ATM, e-commerce; по сегменту клиентов — для маркетинга и тарифов. См. [§2.2](chapter-02-02.md).

---

## 2.3.3. Сегментация

**Сегментация** в контексте карточных данных — разбиение портфеля карт или транзакций по признакам для отчётов и аналитики. См. [Глоссарий](glossary.md).

Типичные разрезы:

| Разрез | Источник данных | Назначение |
|--------|------------------|------------|
| Продукт | Договор / карта: тип продукта (дебетовая/кредитная) | Обороты и показатели по продуктам |
| Сегмент клиента | Справочник клиентов: сегмент (массовый, премиум, корпоративный и т.д.) | Отчёты по сегментам, тарифы |
| MCC | Транзакция: код MCC | Структура расходов, отчёты по категориям |
| Канал | Транзакция: канал (POS, ATM, e-commerce) | Активность по каналам, антифрод |
| Регион / страна | Транзакция или мерчант: страна, регион | География операций, риски |
| Филиал / подразделение | Договор или карта: филиал выдачи | Внутренняя отчётность по подразделениям |

Для сегментации в данных должны быть: в транзакции — карта (и через неё договор, клиент, продукт), мерчант, MCC, канал, при необходимости страна; в справочниках — сегмент клиента, филиал. Витрины могут хранить предрассчитанные обороты и средний чек по сегментам за период или строиться на лету из таблицы транзакций. См. [§2.1](chapter-02-01.md), [§2.2](chapter-02-02.md), [§4.2](chapter-04-02.md).

## 2.3.4. Данные для отчётов

Внутренние и регуляторные отчёты по картам опираются на те же данные: транзакции (проведённые), карты, договоры, счета, клиенты. См. [§2.4](chapter-02-04.md), главы 5–6.

**Для внутренних отчётов** обычно нужны: обороты за период по продукту, сегменту, каналу, MCC; количество активных карт на дату; количество и сумма транзакций; средний чек; при необходимости — сравнение с прошлым периодом, доля возвратов. Источники: витрина оборотов (агрегаты за период), снимки портфеля карт на дату, таблица транзакций для детализации.

**Для регуляторной отчётности** (формы ЦБ и иные) — объёмы операций по картам, суммы оборотов, иногда разбивка по типам операций или по валютам. Требования к составу и формату полей задаются конкретными указаниями ЦБ; данные берутся из операционных систем и DWH, маппинг «поле отчёта — источник» и пайплайн подготовки форм — в [§5.3](chapter-05-03.md), [§6.1](chapter-06-01.md). Критична согласованность дат (валютирование) и исключение дублей транзакций при агрегации.

**Чек-лист данных для отчётов по картам:**

- Транзакции: ID, дата авторизации, дата валютирования, карта, договор, счёт, сумма, валюта, тип операции, мерчант, MCC, канал, статус.
- Связь транзакция — карта — договор — счёт на дату операции/зачёта.
- Справочники: продукт (тип карты), сегмент клиента, филиал; при необходимости справочник MCC.
- Единое правило даты для оборотов (валютирование или операция) и единообразный учёт возвратов.

## 2.3.5. Данные для антифрода

**Антифрод** (противодействие мошенничеству) по карточным операциям использует те же транзакции, но с акцентом на признаки аномалий и скорость обработки. См. [§9.2](chapter-09-02.md), [Глоссарий](glossary.md).

Что нужно из данных транзакции для правил и моделей антифрода:

- **Время и география:** дата и время авторизации (с точностью до секунды), страна и при возможности регион/город мерчанта, страна выдачи карты; время между транзакциями по одной карте (невозможность физически быть в двух точках).
- **Сумма и частота:** сумма операции, количество транзакций за короткий интервал (час, день), нарастающий оборот за период; резкие скачки по сравнению с типичным поведением клиента.
- **Точка приёма:** MCC, идентификатор мерчанта; рискованность категории или мерчанта (история мошенничеств).
- **Канал:** POS, ATM, e-commerce; для онлайн — IP, устройство, при необходимости данные 3DS и т.д.
- **Контекст по карте/клиенту:** история оборотов по договору, средний чек, типичные MCC; при смене паттерна — повышение риска.

Данные для антифрода должны поступать с минимальной задержкой (стриминг или частые выгрузки), чтобы правила и модели срабатывали до или сразу после проведения операции. Исторические транзакции с разметкой (мошенническая/легитимная) используются для обучения моделей. Подробнее признаки мошенничества и архитектура — в [§9.2](chapter-09-02.md) и [§9.4](chapter-09-04.md).

## 2.3.6. Типичные ошибки

- **Считать обороты без учёта возвратов и отмен:** если возвраты не вычитаются или не выделяются, обороты завышены; правило учёта возвратов должно быть единым для всех отчётов.
- **Смешивать дату операции и дату зачёта в одном отчёте без указания:** разные подразделения могут ожидать разную базу; в витрине и в подписи отчёта явно указывать «по дате валютирования» или «по дате авторизации».
- **Сегментация без актуальной привязки карта — договор — клиент:** при перевыпуске карты транзакции привязаны к разным записям карт, но договор один; агрегаты по клиенту/договору должны объединять все карты договора. См. [§2.1](chapter-02-01.md).
- **Для антифрода использовать только агрегаты без детализации:** правила аномалий требуют полей по каждой транзакции (время, география, MCC, канал); агрегированные витрины недостаточны для реал-тайм антифрода.
- **Дубли транзакций при агрегации:** при загрузке из разных источников (авторизации и клиринг) одна операция не должна учитываться дважды; ключ идемпотентности — ID транзакции. См. [§2.2](chapter-02-02.md).

## Ключевое

- **Обороты по картам** — сумма проведённых транзакций за период в выбранном разрезе (договор, продукт, MCC, канал и т.д.); считать по дате валютирования или по дате авторизации — явно фиксировать; возвраты учитывать отдельно или как отрицательные суммы.
- **Средний чек** — сумма оборотов за период / количество транзакций; нужны транзакции с суммой и привязкой к объекту (договор, MCC, канал).
- **Сегментация** — разрезы по продукту, сегменту клиента, MCC, каналу, региону, филиалу; в данных — привязка транзакции к карте/договору/клиенту и атрибуты мерчанта/MCC/канала.
- Для **отчётов** нужны: транзакции с полным набором полей и связью карта — договор — счёт; справочники продукта, сегмента, MCC; единое правило даты и учёта возвратов.
- Для **антифрода** нужны детальные транзакции (время, география, сумма, MCC, канал, мерчант) и контекст по клиенту/карте; данные с минимальной задержкой и история с разметкой для моделей. См. гл. 9.

В [§2.4](chapter-02-04.md) мы разберём связь карточных операций с планом счетов и DWH: проводки по операциям, счета учёта, загрузка в хранилище и витрины.
