# §9.3 Риски в реальном времени: данные и скоринг

В [§9.2](chapter-09-02.md) мы разобрали антифрод: данные, признаки и модели в потоке транзакций. Аналогичная по смыслу задача в реал-тайм — **скоринг заявки** на кредит или карту: на основе заявки и данных о клиенте банк принимает решение об **одобрении или отказе** и о **лимите**. В этом разделе — какие **данные** нужны для скоринга заявки (из DWH и из стрима), как сочетаются лимиты и решение, и как это связано с архитектурой «стрим + DWH». Архитектура стриминга и витрин — в [§9.4](chapter-09-04.md). См. [Глоссарий](glossary.md).

---

## 9.3.1. Скоринг заявки

**Скоринг заявки** — оценка кредитного риска по заявке клиента (кредит, кредитная карта, лимит): расчёт скора (числовой показатель риска) или категории решения (одобрить, отклонить, на ручную проверку) на основе признаков заявки и данных о клиенте. Решение принимается в реальном времени при подаче заявки (онлайн, в офисе, через партнёра). См. [Глоссарий](glossary.md), [§1.1](chapter-01-01.md).

**Вход заявки:** сумма и срок (или тип продукта), канал подачи, при необходимости цель кредита. Идентификатор клиента (или данные для идентификации, если новый клиент) позволяет подтянуть историю и справочные данные. См. [§1.1](chapter-01-01.md), [§4.2](chapter-04-02.md).

**Выход:** решение (одобрено / отказ / на проверку) и при одобрении — лимит (или сумма кредита), ставка, срок. Решение и скор логируются для анализа и обратной связи (как заявки, одобренные или отклонённые, повели себя в портфеле). См. [§9.3.3](#933-лимиты-и-одобрениеотказ), [§9.4](chapter-09-04.md).

---

## 9.3.2. Данные из DWH и из стрима

Для скоринга нужны **данные о клиенте** и **данные о заявке**. Часть из них приходит в потоке (событие заявки), часть хранится в DWH и должна быть доступна в момент принятия решения. См. [§9.1](chapter-09-01.md), [§9.4](chapter-09-04.md).

**Из стрима (событие заявки):**

- Поля заявки: дата/время, клиент (ID или реквизиты для поиска), запрашиваемая сумма, срок, продукт, канал (офис, онлайн, партнёр). См. [§1.1](chapter-01-01.md).

**Из DWH (или из кэша, обновляемого из DWH):**

- **История по клиенту:** текущие и закрытые договоры, остатки, просрочка (DPD, категория качества), количество отказов и одобрений в прошлом. Витрины «портфель кредитов», «просрочка» по клиенту. См. [§1.4](chapter-01-04.md), [§4.2](chapter-04-02.md).
- **Справочные данные клиента:** сегмент, тип (физлицо/юрлицо), длительность отношений с банком, доход (если хранится и разрешён к использованию в скоринге). См. [§4.2](chapter-04-02.md).
- **Внешние скоринговые данные:** при использовании бюро кредитных историй (БКИ) или внешних скорингов — запрос в БКИ в момент заявки или заранее обновлённый срез; результат (скор БКИ, количество просрочек в БКИ) подаётся в модель. См. [§1.1](chapter-01-01.md).

Задержка: данные из DWH обычно обновляются батчами (ежедневно или чаще); для реал-тайм скоринга актуальный срез по клиенту поднимается из кэша или из быстрого хранилища (ключ — client_id), которое синхронизируется с DWH. Если клиент только что получил отказ по другой заявке или только что погасил кредит, эти данные могут попасть в кэш с задержкой; требования к свежести задаются политикой рисков. См. [§9.4](chapter-09-04.md).

## 9.3.3. Лимиты и одобрение/отказ

**Лимит** — максимальная сумма задолженности (по кредиту или по кредитной карте), которую банк готов предоставить клиенту. При одобрении заявки определяется лимит (или сумма разового кредита в пределах лимита); при отказе лимит не выдаётся. См. [§1.1](chapter-01-01.md), [Глоссарий](glossary.md).

**Правила лимитов:** лимит может быть фиксированным по продукту, рассчитанным по доходу клиента, по скору (чем выше скор — тем выше допустимый лимит) или по комбинации правил. В данных должны быть: правила и пороги (конфиг или код), входные данные для расчёта (доход, скор, продукт), результат — одобренный лимит или отказ с причиной (скор ниже порога, превышен лимит по сегменту и т.д.). См. [§9.3.1](#931-скоринг-заявки).

**Одобрение/отказ** — итоговое решение по заявке. Может быть полностью автоматическим (модель + правила лимитов) или с участием человека (заявки с пограничным скором отправляются на ручную проверку). Решение, скор, лимит (при одобрении) и причина отказа фиксируются в данных и связываются с заявкой; при одобрении заявка переходит в этап заключения договора и выдачи. См. [§1.1](chapter-01-01.md), [§4.2](chapter-04-02.md).

## 9.3.4. Связь с архитектурой стрим + DWH

Поток заявок поступает в брокер (Kafka и аналоги); потребитель — сервис скоринга. Для каждой заявки сервис запрашивает данные по клиенту: из кэша/быстрого хранилища (синхронизированного с DWH) или через API витрин. Скор и правила лимитов применяются к вектору признаков (заявка + данные клиента); решение возвращается в операционный контур и записывается; при одобрении далее создаётся договор и счёт. См. [§9.1](chapter-09-01.md), [§9.4](chapter-09-04.md).

Требования к данным: заявка должна содержать client_id (или однозначный ключ поиска); витрины и кэш должны отдавать по client_id актуальный портфель, просрочку и справочные атрибуты в пределах допустимой задержки (секунды). Обратная связь: факт выдачи, последующая просрочка или добросовестное погашение — накапливаются в DWH и используются для переобучения скоринговой модели и калибровки лимитов. См. [§4.4](chapter-04-04.md), [§9.2](chapter-09-02.md) (аналогия с обратной связью в антифроде).

## Ключевое

- **Скоринг заявки** — оценка кредитного риска по заявке в реальном времени; вход — данные заявки и клиента, выход — решение (одобрено/отказ/на проверку) и при одобрении лимит (или сумма, ставка, срок).
- **Данные из стрима** — событие заявки (клиент, сумма, срок, продукт, канал). **Данные из DWH** — история по клиенту (портфель, просрочка), справочные атрибуты, при необходимости данные БКИ; для реал-тайм доставляются через кэш или быстрый слой, синхронизированный с DWH.
- **Лимиты** задаются правилами (по продукту, доходу, скору); при одобрении фиксируются лимит и условия; при отказе — причина. Решение и скор логируются для обратной связи.
- Архитектура: поток заявок → сервис скоринга → запрос данных по клиенту из кэша/DWH → модель и правила лимитов → решение; обратная связь по выдачам и просрочке в DWH для переобучения.

В [§9.4](chapter-09-04.md) мы разберём архитектуру: как стрим и DWH дополняют друг друга, синхронизация и витрины реал-тайм и исторические.
