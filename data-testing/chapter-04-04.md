# §4.4 Запуск тестов вручную и по расписанию

В [§4.3](chapter-04-03.md) мы разобрали примеры unit-тестов для запросов. Чтобы тесты приносили пользу, их нужно **запускать**: вручную при разработке, в CI при коммите, по расписанию или после деплоя. В этом разделе мы разберём, как запускать SQL-тесты скриптами, как интегрировать их с Airflow и как фиксировать результаты и отчёты.

---

## 4.4.1. Запуск вручную: скрипты и оболочка

**Ручной запуск** — выполнение тестов по запросу разработчика: локально или на тестовом сервере. Типичные способы:

**Выполнение SQL-файла через клиент СУБД.** Тест хранится в виде `.sql` файла (один файл на тест или один файл с набором тестов). Запуск:

- **PostgreSQL:** `psql -h host -U user -d test_db -f tests/test_aggregation.sql`. При RAISE EXCEPTION в скрипте psql завершится с ненулевым кодом возврата; успех — код 0.
- **Oracle:** `sqlplus user/pass@db @tests/test_aggregation.sql` или вызов через SQL*Plus с `WHENEVER SQLERROR EXIT FAILURE`. При RAISE_APPLICATION_ERROR скрипт прерывается, код возврата ненулевой.

По коду возврата оболочка (bash, CI) понимает, прошёл тест или упал.

**Обёртка-скрипт (bash).** Скрипт по очереди запускает несколько SQL-файлов и собирает результат: при первом падении выходит с ошибкой или прогоняет все тесты и выводит сводку (сколько прошло, сколько упало).

Пример (bash, PostgreSQL):

```bash
#!/bin/bash
# Запуск SQL unit-тестов для PostgreSQL
set -e
DB_URL="-h localhost -U test_user -d test_db"
FAILED=0
for f in tests/sql/test_*.sql; do
  echo "Running $f ..."
  if psql $DB_URL -f "$f"; then
    echo "  OK"
  else
    echo "  FAILED"
    FAILED=1
  fi
done
exit $FAILED
```

Если нужен режим «прогнать все и вывести отчёт», убирают `set -e` и вместо немедленного выхода накапливают FAILED и выводят список упавших файлов в конце.

**Запуск из языка приложения (Python, Java).** Тесты вызываются из кода: подключение к БД, выполнение SQL из файла или строки, проверка кода возврата или разбор результата; при падении — assert или исключение. Так тесты можно встроить в pytest, JUnit и т.п. и получать отчёт в формате фреймворка (JUnit XML, вывод pytest). Подробнее интеграция с CI рассмотрена в §1.4; здесь важно, что единицей запуска может быть как один SQL-файл, так и один тест-кейс внутри тест-раннера.

## 4.4.2. Запуск по расписанию

Тесты можно запускать **по расписанию**, чтобы регулярно проверять тестовую среду (например, после ночной загрузки данных или после обновления зависимостей):

- **cron:** в crontab задаётся команда запуска скрипта тестов (например, ежедневно в 6:00). Результат пишется в лог; при падении можно отправлять письмо или алерт (через скрипт: проверить код возврата и вызвать mail/curl к системе уведомлений).
- **Планировщик CI:** Jenkins, GitLab CI и др. позволяют настроить периодический job (build periodically), который поднимает тестовую БД (или подключается к существующей), прогоняет тесты и сохраняет артефакты и логи.
- **Airflow:** отдельный даг «тесты» запускается по расписанию (например, раз в день после основного дага загрузки); таски дага выполняют скрипты тестов или вызывают тест-раннер. При падении таска даг помечается failed, срабатывают алерты (см. главу 9).

Запуск по расписанию не заменяет прогон в CI при коммите: в CI проверяем код до слияния; по расписанию — дополнительный рубеж на тестовой среде (актуальность данных, окружение, регрессии из-за внешних изменений).

---

## 4.4.3. Интеграция с Airflow

В Airflow тесты оформляются как **таски** в даге: каждая таска вызывает скрипт тестов (BashOperator) или код, выполняющий тесты (PythonOperator). Типичные варианты:

**Один таск «прогнать все SQL-тесты».** BashOperator выполняет скрипт, который запускает psql/sqlplus по всем тестовым файлам. Успех таска = все тесты прошли (код возврата 0); при падении хотя бы одного теста скрипт возвращает ненулевой код, таск падает, даг помечается failed.

**Отдельные таски на группы тестов.** Несколько тасков (например, «unit-тесты агрегаций», «unit-тесты джойнов»); каждая запускает свой набор файлов. Зависимости между тасками задаются через `>>` (например, `task_a >> task_b`); при падении одной таски последующие не запускаются (или запускаются — в зависимости от настроек). Подробнее условное продолжение при падении теста — в §9.2.

**Тесты после загрузки.** В том же даге, что и загрузка данных: таск загрузки → таск тестов. Схема: `load_task >> test_task`. Тесты проверяют только что загруженные данные (интеграционные проверки или smoke). Если тесты в отдельном даге — зависимость по расписанию: «тесты запускаются после дага загрузки» настраивается через слот времени или триггер.

Подключение к БД в Airflow: переменные/секреты (Connection) с хостом, пользователем, паролем; в скрипте или в PythonOperator параметры подставляются из переменных окружения или из Airflow Connection. Не хранить пароли в коде дага. Детали размещения тестов в даге и уведомлений — в §9.1–9.4.

## 4.4.4. Результаты и отчёты

Чтобы понимать, какие тесты упали и почему, нужны **результаты** и по возможности **отчёт** в удобном формате.

**Код возврата и логи.** Самый минимум: скрипт возвращает 0 при успехе и ненулевой код при провале; вывод (stdout/stderr) пишется в лог (файл, консоль CI, лог таска Airflow). По логу видно сообщение RAISE EXCEPTION / RAISE_APPLICATION_ERROR и место падения.

**Сводка в консоли.** Скрипт в конце выводит: «Tests run: 5, passed: 4, failed: 1» и список упавших тестов. Реализуется обёрткой: для каждого теста фиксировать результат (OK/FAIL), в конце вывести сводку.

**JUnit XML (или аналог).** Многие CI-системы умеют показывать результаты тестов в интерфейсе, если тесты выводят отчёт в формате JUnit XML. Тест-раннер на Python (pytest с плагином), Java (JUnit) или кастомный скрипт генерирует XML с тест-кейсами и статусами; CI загружает артефакт и отображает зелёные/красные тесты. Для «голых» SQL-скриптов можно обернуть запуск в тонкий слой (например, pytest с одним тестом «запустить sql-файл и проверить код возврата»), чтобы получить JUnit XML из pytest.

**Артефакты в CI.** Логи и отчёты сохранять как артефакты сборки (артефакты job в GitLab/Jenkins), чтобы при падении можно было открыть лог без повторного прогона.

**Уведомления при падении.** При запуске по расписанию или в даге Airflow при падении теста отправлять алерт (email, Slack, Telegram) — как настроено в вашей среде. В Airflow это делается через callbacks таска или через опцию email_on_failure и интеграцию с мониторингом (см. §9.4).

В [§5.1](chapter-05-01.md) мы начнём главу об assertions и проверке результатов: что именно проверять (количество строк, значения полей, агрегаты, отсутствие дубликатов) и как формулировать проверки в тестах и в мониторинге.

---

## Ключевое

- **Ручной запуск:** выполнение SQL-файла через psql/sqlplus; код возврата 0 = успех, ненулевой = провал. Обёртка на bash позволяет прогнать несколько файлов и вывести сводку; тесты можно вызывать из Python/Java и встроить в pytest/JUnit.
- **По расписанию:** cron, периодический job в CI или даг в Airflow запускают тесты регулярно; при падении — лог и при необходимости алерт. Не заменяет прогон в CI при коммите.
- **Интеграция с Airflow:** тесты как таски (BashOperator/PythonOperator); один таск на все тесты или несколько на группы; тесты после загрузки (load_task >> test_task). Подключение к БД через Connection/секреты.
- **Результаты и отчёты:** код возврата и логи — минимум; сводка в консоли (passed/failed); JUnit XML для отображения в CI; артефакты и уведомления при падении.

В [§5.1](chapter-05-01.md) мы разберём assertions и проверку результатов: что проверять (количество строк, значения полей, агрегаты, отсутствие дубликатов) и как формулировать проверки.
