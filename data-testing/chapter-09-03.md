# §9.3 Отдельный даг для тестов

В [§9.2](chapter-09-02.md) мы разобрали поведение при падении теста и алерты. Тесты можно встраивать в даг загрузки (load >> test) или выносить в **отдельный даг**, в котором только проверки — без шагов извлечения и загрузки. В этом разделе мы разберём, когда нужен отдельный даг для тестов, как его запускать (по расписанию или вручную) и что такое smoke-даг в этом контексте.

---

## 9.3.1. Даг только с тестами

**Отдельный даг для тестов** — даг, в котором тасками являются только проверки данных: запросы к уже загруженным таблицам (row count, контрольные суммы, референциальная целостность, регрессионное сравнение с эталоном). Загрузка при этом выполняется другими дагами или уже выполнена ранее. См. [§2.4](chapter-02-04.md) и [Глоссарий](glossary.md) по smoke-тестам.

Зачем выносить тесты в отдельный даг:

- **Независимый запуск:** тесты можно гонять по своему расписанию или вручную без повторного запуска загрузки (например, раз в час проверить витрину за вчера после того, как ночной даг загрузки уже отработал).
- **Один даг на несколько источников:** один «тестовый» даг проверяет витрины и таблицы, заполняемые разными дагами загрузки; не нужно дублировать тесты в каждом даге.
- **Smoke после деплоя:** отдельный даг «smoke» запускается вручную или по триггеру после выката (см. §1.4); в нём только быстрые проверки (даг загрузки запустился, row count за последний период в норме).
- **Регрессионные проверки по расписанию:** даг «регрессия» раз в день или раз в неделю пересчитывает ключевые метрики по витрине и сравнивает с эталоном; данные уже загружены основными дагами.

Структура такого дага: несколько тасков-проверок (каждый таск — одна группа проверок или один тип: row count, checksum, integrity). Зависимости между тасками при необходимости (например, сначала лёгкие проверки, потом тяжёлые) или параллельный запуск. Параметры (дата среза) берутся из контекста выполнения дага (execution_date) или из Variables.

---

## 9.3.2. Запуск по расписанию или вручную

Отдельный тестовый даг можно запускать:

- **По расписанию (schedule):** например, `schedule_interval='0 8 * * *'` (каждый день в 08:00) — тесты выполняются после ночной загрузки. Расписание подстраивают под время завершения дагов загрузки, чтобы к моменту запуска тестов данные уже были в приёмнике.
- **Вручную (trigger):** даг без расписания (`schedule_interval=None`) или с расписанием; оператор запускает run вручную из UI Airflow с нужной логической датой. Удобно для smoke после деплоя: деплой завершён → вручную запустить smoke-даг за текущую или вчерашнюю дату.
- **По триггеру извне:** API Airflow или webhook (если настроен) для запуска дага из CI/CD после деплоя; даг_id и параметры передаются скриптом деплоя.

Выбор зависит от цели: регулярный контроль качества — по расписанию; проверка после выката — вручную или по триггеру из пайплайна деплоя.

---

## 9.3.3. Smoke-даг

**Smoke-даг** — даг с минимальным набором быстрых проверок (см. §2.4): пайплайн загрузки отработал, данные за последний период появились (row count не нуль, ключевые суммы в допустимых границах). Его часто оформляют как **отдельный даг** и запускают после деплоя или после критичных дагов загрузки.

Содержимое smoke-дага: таски, которые выполняют запросы к витринам/таблицам за вчера или за последнюю партицию — COUNT(*), одна-две SUM; при выходе за порог или при нуле — таск падает. Без тяжёлых регрессионных сравнений и без полной проверки целостности; цель — за несколько минут убедиться, что «ничего не сломалось» после выката или что ночная загрузка не вернула пустой результат.

Smoke-даг может быть подмножеством тестового дага (те же проверки, но запуск по другому расписанию или только вручную) или отдельным файлом дага с коротким списком тасков. В [§9.4](chapter-09-04.md) мы разберём уведомления и логи: куда пишутся логи теста, как настроить уведомление при падении и интеграцию с мониторингом.

---

## Ключевое

- **Отдельный даг для тестов** — даг без шагов загрузки, только таски-проверки по уже загруженным данным; удобен для независимого расписания, для одного дага на несколько источников, для smoke и регрессионных проверок по расписанию.
- **Запуск:** по расписанию (после дагов загрузки), вручную из UI или по триггеру из CI/CD после деплоя. Параметры среза — из execution_date или Variables.
- **Smoke-даг** — даг с быстрыми проверками (row count, ключевые суммы за последний период); запускается после деплоя или после загрузки; цель — быстро убедиться, что данные не «пустые» и не аномальные.

В [§9.4](chapter-09-04.md) мы разберём уведомления и логи: логи теста, уведомление при падении и интеграция с мониторингом.
