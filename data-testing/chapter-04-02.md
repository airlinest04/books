# §4.2 Структура теста: вход — ожидание — результат

В [§4.1](chapter-04-01.md) мы разобрали, что тестировать в SQL: преобразования, агрегации, фильтрацию, джойны и граничные случаи. Теперь важно **как** оформить тест: чёткая структура упрощает чтение, поддержку и отладку. Классическая схема из разработки программного обеспечения — **Arrange, Act, Assert** (AAA): подготовка данных, выполнение проверяемого действия, проверка результата. Для unit-теста запроса это превращается в: подготовить входные данные (фикстуру), выполнить запрос, сравнить результат с ожиданием. В этом разделе мы разберём эти три шага применительно к SQL и приведём пример целиком.

---

## 4.2.1. Arrange: подготовка данных

**Arrange** (подготовка) — создание окружения и входных данных, при которых будет выполняться запрос. Для теста SQL это означает:

1. **Схема:** нужные таблицы (или представления) существуют и имеют ожидаемую структуру. В тестовой среде схема может создаваться один раз при поднятии окружения или в начале набора тестов; для изоляции — пересоздаваться перед каждым тестом.
2. **Данные:** в таблицы загружаются строки фикстуры — те самые «входные» данные, на которых мы проверяем запрос. Загрузка выполняется через INSERT (из скрипта, из кода теста) или через загрузку файла (COPY, LOAD DATA). Важно, чтобы к моменту выполнения запроса (Act) в таблицах были только данные этого теста — никаких «остатков» от других тестов или от предыдущего прогона.

Пример фрагмента Arrange в виде SQL (среда: PostgreSQL; таблица для теста агрегации продаж по региону):

```sql
-- Arrange: схема и фикстура
CREATE TABLE IF NOT EXISTS test.sales (
    id      INT,
    region_id INT,
    amount  NUMERIC(12,2)
);

TRUNCATE test.sales;

INSERT INTO test.sales (id, region_id, amount) VALUES
(1, 10, 100.00),
(2, 10, 200.00),
(3, 20, 150.00),
(4, 20, 250.00);
```

После этого шага в `test.sales` ровно 4 строки с известными `region_id` и `amount`. Ожидаемый результат агрегации «сумма по региону»: region_id=10 → 300, region_id=20 → 400. Этот ожидаемый результат мы будем проверять в Assert.

---

## 4.2.2. Act: выполнение запроса

**Act** (действие) — выполнение проверяемого запроса (или целого выражения/подзапроса). Тест вызывает ровно ту логику, которую мы тестируем, с теми же параметрами, что и в проде (дата, идентификаторы — если запрос параметризован, подставляем фиксированные значения).

Запрос выполняется в той же сессии/соединении, где подготовлены данные, чтобы он видел таблицы фикстуры. Результат сохраняется: во временную таблицу, в переменную (если тест на языке приложения — Python, Java — то результат запроса кладётся в переменную для последующего Assert) или сразу сравнивается с ожиданием в одном скрипте.

Пример Act для теста агрегации (продолжение; запрос — «сумма продаж по региону»):

```sql
-- Act: выполнение проверяемого запроса
CREATE TEMP TABLE test.result AS
SELECT region_id, SUM(amount) AS total
FROM test.sales
GROUP BY region_id
ORDER BY region_id;
```

Результат сохранён во временную таблицу `test.result`; в Assert мы сравним её с эталоном. Альтернатива — выполнить запрос и в Assert сразу сравнить количество строк и значения через отдельные SELECT (например, ожидаем 2 строки, SUM по region_id=10 равен 300, по 20 — 400).

---

## 4.2.3. Assert: проверка результата

**Assert** (проверка) — сравнение фактического результата с ожидаемым. Варианты проверки:

- **Количество строк:** `SELECT COUNT(*) FROM test.result` должно быть равно ожидаемому (в нашем примере — 2).
- **Конкретные значения:** для каждой строки или для ключевых агрегатов сравнить с эталоном. Например: строка с `region_id=10` имеет `total=300`, с `region_id=20` — `total=400`.
- **Сравнение с эталонной таблицей:** создать таблицу ожидаемого результата и выполнить EXCEPT / INTERSECT или поэстрочное сравнение (в PostgreSQL можно использовать `SELECT * FROM result EXCEPT SELECT * FROM expected` — пустой результат означает совпадение).
- **Утверждения в коде теста:** если тест написан на Python/Java, результат запроса читается в переменную и проверяется через assert (например, `assert row_count == 2`, `assert totals[10] == 300`).

Важно, чтобы проверка была **детерминированной**: при наличии ORDER BY в запросе порядок строк фиксирован; при сравнении без порядка — использовать множество строк или сортировку перед сравнением.

Пример Assert в виде SQL (проверка по значениям; можно выполнять в скрипте и проверять код возврата или выводить сообщение при расхождении):

```sql
-- Assert: проверка
DO $$
DECLARE
    cnt INT;
    r10 NUMERIC;
    r20 NUMERIC;
BEGIN
    SELECT COUNT(*) INTO cnt FROM test.result;
    IF cnt != 2 THEN
        RAISE EXCEPTION 'Assert failed: expected 2 rows, got %', cnt;
    END IF;

    SELECT total INTO r10 FROM test.result WHERE region_id = 10;
    SELECT total INTO r20 FROM test.result WHERE region_id = 20;
    IF r10 != 300 OR r20 != 400 THEN
        RAISE EXCEPTION 'Assert failed: expected 300 and 400, got % and %', r10, r20;
    END IF;
END $$;
```

В средах без процедурного расширения проверку делают отдельными SELECT и проверкой результата в скрипте (shell, Python) или в тест-фреймворке. См. [Глоссарий](glossary.md) по утверждениям в тестах.

## 4.2.4. Полный пример теста на SQL

Ниже — объединённый пример unit-теста для запроса «сумма продаж по региону» в виде одного SQL-скрипта. Среда: PostgreSQL; тест можно запускать в psql или из тест-раннера.

```sql
-- Unit-тест: агрегация SUM(amount) GROUP BY region_id
-- Arrange
CREATE TABLE IF NOT EXISTS test.sales (
    id INT, region_id INT, amount NUMERIC(12,2)
);
TRUNCATE test.sales;
INSERT INTO test.sales (id, region_id, amount) VALUES
(1, 10, 100.00), (2, 10, 200.00), (3, 20, 150.00), (4, 20, 250.00);

-- Act
DROP TABLE IF EXISTS test.result;
CREATE TABLE test.result AS
SELECT region_id, SUM(amount) AS total
FROM test.sales
GROUP BY region_id
ORDER BY region_id;

-- Assert: 2 строки; region_id=10 -> 300, region_id=20 -> 400
DO $$
DECLARE cnt INT; r10 NUMERIC; r20 NUMERIC;
BEGIN
    SELECT COUNT(*) INTO cnt FROM test.result;
    IF cnt != 2 THEN RAISE EXCEPTION 'Expected 2 rows, got %', cnt; END IF;
    SELECT total INTO r10 FROM test.result WHERE region_id = 10;
    SELECT total INTO r20 FROM test.result WHERE region_id = 20;
    IF r10 != 300 OR r20 != 400 THEN
        RAISE EXCEPTION 'Expected 300 and 400, got % and %', r10, r20;
    END IF;
    RAISE NOTICE 'Test passed.';
END $$;
```

При успехе скрипт завершается без исключения; при провале — RAISE EXCEPTION прерывает выполнение, и тест-раннер или скрипт оболочки фиксирует ошибку. В [§4.3](chapter-04-03.md) мы приведём дополнительные примеры unit-тестов: тест джойна и тест фильтра, в том числе для PostgreSQL и Oracle.

---

## Ключевое

- Структура unit-теста для SQL укладывается в **Arrange — Act — Assert**: подготовка данных, выполнение запроса, проверка результата.
- **Arrange:** создание/очистка таблиц, загрузка фикстуры; к моменту Act в таблицах только данные этого теста.
- **Act:** выполнение проверяемого запроса; результат сохраняется во временную таблицу или в переменную для Assert.
- **Assert:** сравнение с ожиданием — количество строк, значения полей или сравнение с эталонной таблицей; при расхождении — явная ошибка (EXCEPTION в SQL или assert в коде теста).
- Полный пример: один скрипт с Arrange (фикстура продаж по регионам), Act (GROUP BY, SUM), Assert (2 строки, суммы 300 и 400); при успехе — тихий выход, при провале — исключение.

В [§4.3](chapter-04-03.md) мы разберём примеры unit-тестов для запросов: тест агрегации, тест джойна, тест фильтра на PostgreSQL и Oracle.
