# §10.2 Unit-тесты для преобразований

В [§10.1](chapter-10-01.md) мы задали пайплайн «источник — ETL — витрина» и требования к тестам. Первый практический блок — **unit-тесты для преобразований**: проверка маппинга (источник → staging) и агрегаций (staging → витрина) на фикстурах без полного прогона ETL. В этом разделе мы разберём тесты маппинга, тесты агрегаций и подготовку фикстур в контексте примера с продажами из §10.1.

---

## 10.2.1. Тесты маппинга

**Маппинг** в нашем примере: поля source.sales (id, sale_date, region_id, product_id, amount, currency) переносятся в staging.sales с приведением типов и при необходимости с подстановкой (например, amount в рублях по курсу при currency='USD'). Unit-тест маппинга проверяет: при заданных строках в источнике (фикстура) запрос преобразования или шаг ETL даёт в staging ожидаемые значения. См. [§6.1](chapter-06-01.md).

Что тестировать:

- **Прямое копирование и приведение типов:** sale_date как DATE без времени; amount как NUMERIC(12,2). Фикстура: одна или несколько строк с известными значениями; assertion — совпадение полей в результате.
- **Условное преобразование:** при currency='USD' amount умножается на курс; при 'RUB' — без изменения. Фикстура: по одной строке на каждую ветку (USD, RUB); проверка итогового amount в staging.
- **Граничные случаи:** null в опциональном поле (например, currency); пустая строка. Ожидание: значение по умолчанию или null в приёмнике по правилу.

Фикстура для маппинга: таблица или набор строк с полями источника (или их эмуляция в тестовой таблице с тем же именем/схемой). Тест загружает фикстуру, выполняет запрос INSERT…SELECT или вызывает код преобразования, читает результат из staging (или из временной таблицы) и сравнивает с эталоном. Структура Arrange–Act–Assert из §4.2 сохраняется; при нескольких тест-кейсах (разные ветки маппинга) удобно параметризовать тест (одна функция теста, разные фикстуры и ожидания).

## 10.2.2. Тесты агрегаций

**Агрегация** в примере: из staging.sales строится витрина mart.sales_daily — группировка по (sale_date, region_id, product_id), SUM(amount), COUNT(*). Unit-тест агрегации проверяет: при заданных строках в staging (фикстура) запрос к витрине (или шаг построения витрины) возвращает ожидаемые группы и суммы. См. [§6.2](chapter-06-02.md) и примеры из §4.3.

Что тестировать:

- **Корректность GROUP BY и SUM:** фикстура — несколько строк staging с разными (date, region_id, product_id); ожидание — одна строка на группу с правильной суммой и счётчиком.
- **Округление:** при использовании ROUND или приведения к NUMERIC проверка с точностью до копеек (допуск или сравнение округлённых значений).
- **Пустой вход:** 0 строк в staging за дату → запрос к витрине за эту дату возвращает 0 строк или одну строку с NULL/0 в агрегатах (по принятому правилу).

Фикстура для агрегации: таблица staging.sales (или тестовая копия) с 5–20 строками с известным распределением по дате, региону и продукту; эталон — посчитанные вручную SUM и COUNT по группам. Тест выполняет запрос к витрине (или шаг построения витрины на тестовой БД), сравнивает результат с эталоном. При необходимости несколько тестов: «нормальный кейс», «одна группа», «пустой staging».

## 10.2.3. Фикстуры для пайплайна

Фикстуры для unit-тестов преобразований в контексте пайплайна из §10.1:

- **Для маппинга (источник → staging):** файл или таблица с строками source.sales: колонки id, sale_date, region_id, product_id, amount, currency. Варианты: CSV в репозитории, SQL с INSERT, генерация через Faker с фиксированным seed (§3.2). Загружаются в тестовую таблицу source.sales (или test.source_sales) перед тестом; после теста при необходимости очищаются.
- **Для агрегации (staging → витрина):** строки staging.sales с теми же полями, что ожидает запрос витрины. Минимальный набор: 2–3 группы (date, region_id, product_id), по 2–3 строки в группе, чтобы суммы и счётчики были однозначно посчитаны. Эталон — таблица или набор пар (группа, expected_sum, expected_count).

Управление фикстурами: хранить в репозитории (каталог tests/fixtures или tests/data), версионировать вместе с тестами; при изменении схемы или правил преобразования обновлять фикстуры и эталоны. Изоляция: тесты не должны зависеть друг от друга; перед каждым тестом загружать свою фикстуру в чистую таблицу или использовать отдельную схему/временные таблицы (§3.4). В [§10.3](chapter-10-03.md) мы разберём интеграционные проверки ETL: row count, контрольные суммы и целостность по полному прогону пайплайна.

---

## Ключевое

- **Тесты маппинга:** проверка преобразования источник → staging на фикстуре; прямое копирование и типы, условная логика (валюта, курс), граничные случаи (null). Фикстура — строки источника; assertion — совпадение полей в результате.
- **Тесты агрегаций:** проверка построения витрины (staging → mart) на фикстуре; GROUP BY, SUM, COUNT; округление и пустой вход. Фикстура — строки staging с известным распределением по группам; эталон — суммы и счётчики по группам.
- **Фикстуры:** для маппинга — строки source; для агрегации — строки staging; хранение в репо, изоляция тестов, обновление при смене схемы или правил.

В [§10.3](chapter-10-03.md) мы разберём интеграционные проверки ETL: row count, контрольные суммы и целостность при полном прогоне пайплайна.
