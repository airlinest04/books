# §5.1 Assertions: что проверять

В [§4.4](chapter-04-04.md) мы разобрали запуск тестов вручную и по расписанию и интеграцию с Airflow. Глава 5 посвящена **assertions** — утверждениям, которые формулируют, «что должно быть верно» в результате запроса или после загрузки данных: количество строк, значения полей, агрегаты, отсутствие дубликатов. В этом разделе мы систематизируем, **что именно** проверять в тестах и в проверках после ETL: какие типы assertions наиболее полезны и как они связаны с уже рассмотренными unit- и интеграционными тестами.

---

## 5.1.1. Assertion в контексте тестирования данных

**Assertion** (утверждение) — явно сформулированное условие, которое должно выполняться над данными: «количество строк в таблице равно N», «в колонке X нет отрицательных значений», «сумма по полю Y совпадает с эталоном». Тест или проверка выполняет запрос (или смотрит на уже загруженные данные) и проверяет выполнение условия; при невыполнении — провал (исключение, ненулевой код возврата, алерт в мониторинге). См. [Глоссарий](glossary.md).

Assertions используются и в unit-тестах (проверка результата одного запроса на фикстуре), и в интеграционных тестах (проверка полноты и целостности после прогона ETL), и в мониторинге качества (проверка данных в проде). Разница — в моменте выполнения и в данных (тестовая фикстура vs результат ETL vs продовые таблицы); набор типов проверок общий: количество строк, значения полей, агрегаты, уникальность, референциальная целостность, бизнес-правила. Ниже разобраны четыре базовых типа; в §5.2–5.4 мы детализируем row count и контрольные суммы, референциальную целостность и бизнес-правила в SQL.

---

## 5.1.2. Количество строк

Проверка **количества строк** (row count) — одна из самых частых assertions: результат запроса или таблица после загрузки должны содержать ровно N строк (или не менее N, не более N — в зависимости от формулировки).

Типичные сценарии:

| Сценарий | Утверждение | Пример |
|----------|-------------|--------|
| Unit-тест запроса | Результат запроса содержит ровно N строк. | После фильтра по status='completed' ожидаем 2 строки. |
| Интеграционный тест ETL | Количество строк в приёмнике равно количеству в источнике (за период/срез). | В staging.orders за дату D — столько же строк, сколько в источнике за дату D. |
| Smoke / санитарная проверка | В таблице за последний период не нуль и не аномально мало. | В витрине продаж за вчера COUNT(*) >= 1 (или >= порога). |
| Отсутствие лишних записей | Запрос с уникальным ключом возвращает не более одной строки на ключ. | По (date, product_id) одна строка — проверка через COUNT(*) = COUNT(DISTINCT date, product_id). |

Реализация: запрос `SELECT COUNT(*) FROM ...` (или подсчёт строк результата в приложении), сравнение с ожидаемым числом. В unit-тесте ожидание задаётся эталоном по фикстуре; в интеграционном — по источнику или по эталонному значению; в smoke — по порогу или историческому минимуму. В §5.2 мы разберём row count подробнее: сравнение источник/приёмник и использование в контрольных суммах.

## 5.1.3. Значения полей

Assertions по **значениям полей** проверяют, что в выбранных колонках значения удовлетворяют условию: не null (где не допускается), в допустимом диапазоне, из справочника, равны ожидаемому значению в тесте.

Типичные проверки:

| Проверка | Утверждение | Пример |
|----------|-------------|--------|
| Не null | В колонке нет null (для всех строк или для строк с заданным условием). | `SELECT COUNT(*) FROM t WHERE key_col IS NULL` = 0. |
| Диапазон | Значения в пределах min/max. | amount >= 0 AND amount <= 1000000. |
| Принадлежность справочнику | Значение из допустимого множества или существует в справочной таблице. | status IN ('NEW', 'DONE') или EXISTS в таблице статусов. |
| Точное совпадение (в unit-тесте) | В результате запроса в строке с заданным ключом поле равно X. | Для order_id=1 поле total = 300. |

В unit-тестах мы часто проверяем точное совпадение с эталоном (одна или несколько строк с известными значениями). В интеграционных тестах и мониторинге — скорее инварианты: «нет null в ключевой колонке», «нет отрицательных сумм». Проверку «все значения из справочника» и сложные бизнес-правила разберём в §5.4.

## 5.1.4. Агрегаты

Проверки **агрегатов** (SUM, COUNT, AVG, MIN, MAX) утверждают, что сводные показатели по таблице или по срезу совпадают с ожиданием или находятся в допустимых границах.

Типичные сценарии:

| Сценарий | Утверждение | Пример |
|----------|-------------|--------|
| Unit-тест | Сумма (среднее, количество) по фикстуре равна эталону. | SUM(amount) по тестовой таблице = 150. |
| Интеграционный тест | Сумма в приёмнике равна сумме в источнике (контрольная сумма). | SUM(revenue) в витрине за месяц = SUM(revenue) в источнике за месяц. |
| Регрессионный тест | Агрегат совпадает с сохранённым эталоном. | SUM(sales) по витрине за эталонную дату = 1234567.89 (эталон). |
| Smoke / санитарная проверка | Агрегат в разумных границах (не нуль, не отрицательный, не превышает порог). | SUM(amount) за день > 0 AND SUM(amount) < 1e9. |

Агрегаты удобны тем, что одной проверкой можно охватить весь объём данных: не нужно сравнивать построчно, достаточно сравнить одну или несколько сумм (или хешей — см. §5.2). Детали: расчёт контрольных сумм, хеш по строкам, сравнение с эталоном — в §5.2.

## 5.1.5. Отсутствие дубликатов

Assertion **«нет дубликатов»** по заданному ключу (первичному или бизнес-ключу) гарантирует уникальность: в таблице или в результате запроса не должно быть двух строк с одинаковым значением ключа.

Формулировка: для набора колонок (key_cols) количество строк равно количеству уникальных комбинаций этих колонок.

Типичная проверка в SQL:

```sql
-- Утверждение: по (date, product_id) не более одной строки
SELECT COUNT(*) - COUNT(DISTINCT date, product_id) AS duplicate_key_count
FROM mart.sales
WHERE load_date = :target_date;
-- Ожидание: duplicate_key_count = 0
```

Или: `COUNT(*)` по таблице должен равняться `COUNT(DISTINCT col1, col2, ...)`. Если не равны — есть дубликаты по ключу, assertion не выполняется.

Сценарии: витрина должна быть по одному ряду на (дата, продукт, регион); таблица заказов — по одному ряду на order_id; после дедупликации в ETL дубликатов быть не должно. В интеграционных тестах эта проверка часто идёт вместе с row count и контрольными суммами; референциальная целостность (нет «сирот» по внешнему ключу) — отдельный тип assertion, его разберём в §5.3.

## Ключевое

- **Assertion** в тестировании данных — явное условие над данными (количество строк, значения полей, агрегаты, уникальность); при невыполнении тест или проверка проваливается.
- **Количество строк:** ровно N / не менее N / не более N; используется в unit-тестах, интеграционных (источник = приёмник), smoke и проверке уникальности по ключу.
- **Значения полей:** не null, диапазон, принадлежность справочнику, точное совпадение с эталоном в unit-тесте.
- **Агрегаты:** SUM, COUNT, AVG и т.д. совпадают с эталоном или в допустимых границах; удобны для контрольных сумм и регрессионных проверок.
- **Отсутствие дубликатов:** COUNT(*) = COUNT(DISTINCT key_columns); проверка уникальности по первичному или бизнес-ключу.

В [§5.2](chapter-05-02.md) мы разберём row count и контрольные суммы подробнее: COUNT(*), SUM по полям, хеш по строкам и сравнение с эталоном.
