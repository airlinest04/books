# §7.4 Нет потерь и искажений

В [§7.3](chapter-07-03.md) мы разобрали референциальную целостность в ETL. Завершаем главу о проверке полноты и целостности формулировкой цели «**нет потерь и искажений**»: полнота (все нужные строки попали в приёмник), точность (значения не искажены) и при необходимости **выборочная сверка** записей источник–приёмник по ключам. В этом разделе мы сведим воедино уже введённые проверки и добавим проверку выборочных записей.

---

## 7.4.1. Полнота

**Полнота** — все строки среза источника присутствуют в приёмнике; ничего не потеряно при извлечении, преобразовании и загрузке. См. [Глоссарий](glossary.md).

Проверки полноты, уже разобранные в этой главе:

- **Row count** (§7.1): количество строк в источнике и приёмнике по одному срезу совпадает (или укладывается в правило при фильтре и дедупликации). Базовая assertion для полноты.
- **Охват по ключу:** все ключи (id, составной ключ) из источника за срез присутствуют в приёмнике. Реализация: запрос «ключи из источника MINUS ключи из приёмника» (EXCEPT в PostgreSQL, MINUS в Oracle) по выбранному срезу; результат должен быть пустым. При больших объёмах сравнение множеств может быть тяжёлым; row count плюс контрольная сумма часто достаточны, а проверка по ключам — опционально или выборочно.

Если row count совпадает и ключи уникальны в обоих местах, полнота по сути обеспечена: одинаковое число строк и отсутствие дубликатов по ключу в приёмнике означают, что каждому ключу источника соответствует ровно одна строка в приёмнике (при условии, что ключи в приёмнике те же). При дедупликации в ETL проверяют COUNT(DISTINCT key) в источнике и в приёмнике.

---

## 7.4.2. Точность

**Точность** — значения в приёмнике соответствуют значениям в источнике; нет искажений при маппинге, приведении типов и расчётах.

Проверки точности, уже введённые:

- **Контрольные суммы по SUM** (§7.2): суммы по числовым полям по срезу в источнике и приёмнике совпадают. Выявляют искажения в числах (но не перестановки или изменения в неподсуммируемых полях).
- **Хеш по строкам** (§7.2): хеш от набора полей в фиксированном порядке в источнике и приёмнике совпадает. Жёсткая проверка «набор данных идентичен»; любое изменение значения или состава меняет хеш.

Дополнительно точность можно проверять **выборочной сверкой** записей (см. ниже): для части ключей сравнить построчно поля источник и приёмник. Это полезно, когда полный хеш считать дорого или нужно локализовать расхождение по полям.

---

## 7.4.3. Проверка выборочных записей

**Выборочная проверка** (spot check, sampling): для подмножества записей (по ключу или случайной выборке) сравнить значения полей в источнике и в приёмнике. Цель — убедиться в точности маппинга без сравнения всего объёма.

Подход:

1. Выбрать набор ключей (например, 100 id за срез или случайная выборка по ключу).
2. Для каждого ключа получить строку из источника и строку из приёмника (по ключу).
3. Сравнить выбранные поля (все или критичные): совпадение по каждому полю или по агрегату по полям.

Реализация в SQL: выборка ключей из приёмника (или источника), затем JOIN источника и приёмника по ключу и сравнение полей. Пример идеи:

```sql
-- Выборочная проверка: совпадают ли amount и status для заказов за дату
SELECT o.order_id, 
       s.amount AS src_amount, t.amount AS tgt_amount,
       s.status AS src_status, t.status AS tgt_status
FROM (SELECT order_id FROM staging.orders WHERE order_date = :date LIMIT 100) o
JOIN source.orders s ON s.order_id = o.order_id AND s.order_date = :date
JOIN staging.orders t ON t.order_id = o.order_id AND t.order_date = :date
WHERE s.amount IS DISTINCT FROM t.amount OR s.status IS DISTINCT FROM t.status;
-- Ожидание: 0 строк (нет расхождений по выбранной выборке)
```

Если источник и приёмник в разных системах, выборку ключей получают из одной стороны, затем запрашивают обе и сравнивают в скрипте или в тесте. При расхождении тест падает и выводит ключи и поля, по которым есть различие.

Объём выборки: фиксированное число (100, 1000) или процент от среза. Чем больше выборка, тем выше вероятность поймать искажение, но тем дороже проверка. Для критичных полей иногда делают полное построчное сравнение (эквивалентно проверке хешем при совпадении набора полей); для менее критичных — выборочную проверку после прогона ETL или в регрессионном тесте.

---

## Ключевое

- **Полнота:** все строки среза в приёмнике; проверки — row count и при необходимости охват по ключу (источник MINUS приёмник = пусто). При дедупликации — сравнение COUNT(DISTINCT key).
- **Точность:** значения не искажены; проверки — контрольные суммы по SUM и хеш по строкам (уже в §7.2). Цель набора проверок — «нет потерь и искажений».
- **Выборочная сверка:** для подмножества ключей сравнить поля источник и приёмник; при расхождении — провал теста и отчёт по ключам/полям. Дополняет SUM и хеш при ограничениях по объёму или для локализации ошибок.

В [§8.1](chapter-08-01.md) мы начнём главу об идемпотентности и регрессии: повторный запуск пайплайна даёт тот же результат, тест — два прогона, одинаковый output.
