# §5.2 Row count, контрольные суммы

В [§5.1](chapter-05-01.md) мы перечислили типы assertions: количество строк, значения полей, агрегаты, отсутствие дубликатов. Здесь подробнее разбираем **row count** и **контрольные суммы** — как их считать, когда сравнивать с эталоном и как использовать хеш по строкам для проверки «ничего не изменилось» в наборе данных.

---

## 5.2.1. Row count: COUNT(*)

**Row count** — количество строк в таблице, в результате запроса или в срезе (по дате, по партиции). Базовая проверка: `SELECT COUNT(*) FROM table [WHERE ...]`.

Типичные применения:

| Контекст | Что считаем | С чем сравниваем |
|----------|-------------|------------------|
| Интеграционный тест ETL | Строки в приёмнике за период (или по ключу загрузки). | Количество строк в источнике за тот же период. Совпадение — полнота загрузки. |
| Unit-тест | Строки в результате проверяемого запроса. | Ожидаемое число по фикстуре (ровно N). |
| Smoke / санитарная проверка | Строки в витрине за последний период. | Порог: не 0, при необходимости не ниже исторического минимума. |
| Проверка уникальности | COUNT(*) и COUNT(DISTINCT col1, col2, ...). | Равенство — нет дубликатов по ключу. |

Важно задать **однозначный срез**: по дате загрузки, по партиции, по batch_id — чтобы и в источнике, и в приёмнике считались одни и те же логические строки. Пример для сравнения источник/приёмник (псевдокод логики):

- Источник: `SELECT COUNT(*) FROM source.orders WHERE order_date = :date`.
- Приёмник: `SELECT COUNT(*) FROM staging.orders WHERE load_date = :date AND order_date = :date` (если в staging храним срез за дату).
- Assertion: оба числа равны (или разница в допустимых пределах, если есть явно исключённые записи по правилам).

В разных СУБД учёт NULL и дубликатов у COUNT(*) одинаков: считаются все строки. Для партиционированных таблиц проверку часто делают по одной партиции за раз (например, за конкретную дату), чтобы не сканировать всю таблицу.

---

## 5.2.2. Контрольная сумма по SUM

**Контрольная сумма** на основе **SUM** — сумма по одной или нескольким числовым колонкам по тому же срезу, что и row count. Если все строки перенесены без искажений и маппинг верный, сумма в приёмнике должна совпадать с суммой в источнике (для тех же полей и того же фильтра).

Пример: проверка загрузки продаж за дату.

- Источник: `SELECT SUM(amount) AS total FROM source.sales WHERE sale_date = :date`.
- Приёмник: `SELECT SUM(amount) AS total FROM staging.sales WHERE sale_date = :date`.
- Assertion: значения total совпадают (с учётом округления при необходимости).

Ограничения:

- **Тип и округление:** в источнике и приёмнике типы и порядок округления должны быть согласованы; иначе разница на копейках может давать ложное падение. Для сравнения иногда округляют до 2 знаков или до целых.
- **NULL:** в SQL SUM игнорирует NULL; если в источнике часть значений была NULL, а в приёмнике заменена на 0, суммы могут совпадать, но это уже вопрос бизнес-правил. Важно явно решить, как считаем: только не-NULL или с подстановкой.
- **Выбор колонок:** суммируют ключевые числовые поля (выручка, количество, вес); одной суммы может быть недостаточно — при компенсирующих ошибках (одна запись +100, другая -100) сумма не изменится. Поэтому часто комбинируют row count и несколько SUM по разным колонкам или хеш по строкам.

Контрольная сумма по SUM подходит для регрессионных тестов: эталонное значение суммы сохраняется; после изменений кода пересчитываем сумму по тому же срезу и сравниваем с эталоном. В §2.3 и §8.3 эталоны и их обновление разобраны подробнее.

## 5.2.3. Хеш по строкам

**Хеш по строкам** — значение хеш-функции (MD5, SHA-256) от конкатенации данных в выборке. Цель: зафиксировать «отпечаток» всего набора; любое изменение в данных (значение, порядок, состав строк) меняет хеш. Используется для сравнения «набор данных не изменился» (регрессия) или «набор в приёмнике совпадает с набором в источнике» при детерминированном порядке.

Важно обеспечить **детерминированный порядок**: строки перед конкатенацией сортируют по ключу (например, ORDER BY id, date). Иначе один и тот же набор данных может дать разный хеш при разном порядке строк.

Пример идеи (PostgreSQL): конкатенация всех полей строки в одну строку, сортировка по id, затем хеш от результата. На практике часто хешируют не все колонки, а ключевые (идентификатор, дата, числовые поля), чтобы не зависеть от изменений незначимых полей. Пример подсчёта хеша по срезу (логика):

```sql
-- Пример: MD5 от конкатенации строк (срез за дату), порядок фиксирован
SELECT MD5(
    string_agg(
        id::TEXT || '|' || amount::TEXT || '|' || COALESCE(status, ''),
        '|' ORDER BY id
    )
) AS row_hash
FROM staging.orders
WHERE order_date = :date;
```

Результат `row_hash` сравнивают с эталоном (из источника или сохранённым ранее). Совпадение — данные за срез идентичны; несовпадение — что-то изменилось, нужно разбирать.

Ограничения: хеш чувствителен к любому изменению (включая пробелы, порядок колонок в конкатенации); схема и порядок полей должны быть зафиксированы. Для больших объёмов конкатенация всех строк в одну может быть тяжёлой операцией; иногда хешируют постранично или только ключевые колонки. См. [Глоссарий](glossary.md) по контрольным суммам.

## 5.2.4. Сравнение с эталоном

**Эталон** — сохранённое значение (row count, SUM, хеш), с которым сравнивается текущий результат. Источник эталона:

- **Фикстура / тестовый прогон:** при первом прогоне интеграционного теста на тестовых данных сохраняем COUNT и SUM (и при необходимости хеш) как эталон; при следующих прогонах сравниваем с ним. Изменение эталона допустимо только при явном изменении тестовых данных или логики.
- **Результат по источнику:** в интеграционном тесте эталон — значение, посчитанное по источнику (те же фильтры и колонки); приёмник сравниваем с ним после загрузки.
- **Золотой срез (регрессия):** эталон снят с продовых (или эталонных) данных за выбранную дату и сохранён в репозитории; при регрессионном прогоне пересчитываем метрики по тем же данным с новым кодом и сравниваем. Расхождение — сигнал регрессии.

Правила сравнения:

- **Числа:** точное совпадение или допуск (например, разница из-за округления до 0.01). Для денег часто сравнивают с точностью до копеек (2 знака).
- **Хеш:** строгое совпадение строки; при несовпадении тест падает, разбор — по диффу данных или по логам загрузки.
- **Обновление эталона:** при легитимном изменении логики (исправление бага, новая формула) эталон пересчитывают и сохраняют новое значение с пояснением в коммите. Не обновлять эталон «чтобы тест прошёл» без понимания причины расхождения.

В [§5.3](chapter-05-03.md) мы разберём референциальную целостность: проверки на отсутствие «сирот» (записей со ссылкой на несуществующий родитель) и соответствие внешним ключам.

---

## Ключевое

- **Row count (COUNT(*))** задаёт срез (таблица, период, партиция) и сравнивает с ожиданием: в интеграционном тесте — с источником, в unit-тесте — с фикстурой, в smoke — с порогом.
- **Контрольная сумма по SUM:** сумма по числовым колонкам по тому же срезу; сравнение источник/приёмник или с эталоном; учитывать тип, округление и обработку NULL.
- **Хеш по строкам:** детерминированный порядок (ORDER BY), конкатенация полей, MD5/SHA; сравнение с эталоном для проверки «набор не изменился»; чувствителен к любым изменениям данных и схемы.
- **Сравнение с эталоном:** эталон из фикстуры, из источника или золотого среза; правила сравнения (точность для чисел, обновление эталона только при обоснованном изменении логики).

В [§5.3](chapter-05-03.md) мы разберём референциальную целостность: нет сирот, выполнение ограничений по внешнему ключу и проверки в SQL.
