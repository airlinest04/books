# §9.2 Условное продолжение при падении теста

В [§9.1](chapter-09-01.md) мы разобрали размещение тестов как тасков в даге и зависимость load >> test. При падении тест-таска (failed) важно понимать, **что происходит с дагом** и с последующими тасками, и как вызвать алерт. В этом разделе мы разберём поведение по умолчанию (fail при падении, остановка последующих тасков), настройку уведомлений и при необходимости условные правила запуска (trigger rules).

---

## 9.2.1. Fail при падении

В Airflow таск считается **успешным**, если он завершился с кодом 0 (BashOperator) или без выброса исключения (PythonOperator). Иначе таск переходит в состояние **failed**. Тест данных при провале проверки должен именно **завершаться с ошибкой**: ненулевой код возврата или `raise Exception(...)` в Python, чтобы таск получил статус failed. См. [Глоссарий](glossary.md) в контексте тестов.

Итог: при падении теста тест-таск в состоянии failed; даг для данного run тоже считается **неуспешным** (dag run state = failed), если хотя бы один таск в состоянии failed. Это желаемое поведение: пайплайн с провалившейся проверкой данных не считается успешно выполненным.

---

## 9.2.2. Остановка последующих тасков

По умолчанию в Airflow **downstream-таски** (зависимые от упавшего) **не запускаются**: если test_task упал, все таски, заданные как `test_task >> next_task`, переходят в состояние **upstream_failed** (или skipped, в зависимости от версии Airflow) и не выполняются. Таким образом, «остановка последующих тасков» при падении теста обеспечивается самой моделью зависимостей: тест — upstream для следующих шагов; при failed тесте следующие шаги не стартуют.

Пример: `load >> test >> notify_success`. Если test падает, notify_success не запускается. Если нужно при падении теста выполнять другой таск (например, уведомление об ошибке), его задают отдельно: например, `test >> notify_success` и отдельно обработка failed (через callback или таск с trigger_rule='all_failed' на другом ветке). Стандартный сценарий: после теста нет бизнес-тасков, которые должны идти «в любом случае»; тест — один из последних тасков в даге загрузки, и при его падении даг просто помечается failed без запуска лишних шагов.

Если по архитектуре после теста идут ещё шаги (например, публикация отчёта), то при падении теста их **не выполнять** — правильное поведение, чтобы не публиковать данные, не прошедшие проверку. Зависимости задают так: `load >> test >> publish`; при failed test таск publish не запустится.

---

## 9.2.3. Алерт при падении

Чтобы ответственные узнали о падении теста, настраивают **уведомление при failed таска**. Варианты:

- **Email:** в таске или в даге задаётся `email_on_failure=True` и список получателей (`email`). При переходе таска в failed Airflow отправляет письмо (при настроенной почте в конфигурации).
- **Callback:** параметр `on_failure_callback` у таска — Python-функция, вызываемая при падении. В ней можно отправить сообщение в Slack, Telegram, создать тикет, записать в систему мониторинга. Передаётся контекст (task instance, execution date и т.д.).
- **Внешний мониторинг:** системы мониторинга (Prometheus, Datadog и др.) могут опрашивать Airflow API или получать webhook при смене состояния дага/таска; при failed — алерт по своим правилам.

Содержание алерта полезно делать информативным: какой даг, какой таск (тест), за какую дату (execution_date), краткое сообщение из лога. Детали настройки email и callback — в §9.4. Главное: тест должен **падать** (failed), чтобы триггер сработал; не помечать тест как success при провале проверки только ради «зелёного» дага.

---

## 9.2.4. Trigger rules (когда нужно иное поведение)

По умолчанию таск запускается, когда **все** upstream-таски успешно завершились (trigger_rule='all_success'). Если нужно изменить поведение (например, запускать таск и при failed upstream — для уведомления об ошибке), используют **trigger_rule**:

- `all_success` — по умолчанию; все upstream успешны.
- `all_failed` — таск запускается, когда все upstream в failed (редко для тестов).
- `one_failed` — запуск при первом failed среди upstream.
- `dummy` — не зависит от upstream, всегда готов к запуску.

Для типового сценария «тест после загрузки, при падении теста — алерт, следующих шагов нет» trigger_rule менять не нужно: тест падает → даг failed → алерт через email_on_failure или callback. Отдельный таск «notify_on_failure» с trigger_rule='one_failed' и зависимостью от тест-таска можно использовать, чтобы при падении теста выполнить только уведомление, не помечая весь даг как успешный (даг всё равно будет failed из-за упавшего теста). Подробнее уведомления и логи — в [§9.3](chapter-09-03.md) и §9.4.

---

## Ключевое

- **Fail при падении:** тест должен завершаться с ошибкой (ненулевой код возврата или исключение), чтобы таск получил статус failed; даг run при этом считается неуспешным.
- **Остановка последующих тасков:** по умолчанию downstream от упавшего таска не запускаются; при цепочке load >> test >> publish падение теста не даёт запустить publish.
- **Алерт:** настраивают email_on_failure или on_failure_callback для тест-таска (или дага); в сообщении указывают даг, таск, дату, при необходимости — выдержку из лога.
- **Trigger rules:** для стандартного сценария не требуются; при необходимости отдельного таска «уведомить при падении» используют trigger_rule='one_failed'.

В [§9.3](chapter-09-03.md) мы разберём отдельный даг для тестов: даг только с тестами, запуск по расписанию или вручную и smoke-даг.
