# §7.1 Row count: источник vs приёмник

В [§6.4](chapter-06-04.md) мы завершили главу о тестировании преобразований. Глава 7 посвящена **проверке полноты и целостности ETL**: убедиться, что при прохождении данных от источника до приёмника ничего не теряется и не искажается. Первая и самая простая проверка — **сравнение количества строк**: в срезе источника и в срезе приёмника после загрузки числа должны совпадать (или укладываться в заданный допуск). В этом разделе мы разберём, как считать row count в источнике и приёмнике, когда вводить допуск на отклонение и каковы типичные причины расхождений.

---

## 7.1.1. Зачем сравнивать количество строк

Если ETL загружает данные «как есть» (без фильтрации по бизнес-правилам и без дедупликации по замыслу), то количество строк, обработанных за выбранный период или срез, в приёмнике должно равняться количеству строк в источнике за тот же срез. Расхождение означает: часть данных не попала в приёмник (сбой загрузки, таймаут, отбрасывание по ошибке) или, наоборот, в приёмнике появились лишние строки (дубли при повторной загрузке, неверная партиция). Проверка row count — базовая assertion интеграционного теста ETL и мониторинга после загрузки. См. [Глоссарий](glossary.md) в контексте полноты.

Важно задать **один и тот же срез** для источника и приёмника: по дате загрузки, по дате транзакции, по batch_id, по партиции. Иначе сравнение теряет смысл (в источнике считаем за один период, в приёмнике — за другой). В приёмнике нередко хранят метаданные загрузки (load_date, source_slice_date), по которым и фильтруют при проверке.

---

## 7.1.2. Как считать: источник и приёмник

**Источник:** запрос к таблице источника (или к выгрузке, если источник — файл) с фильтром по срезу. Пример: «все заказы за дату D» — `SELECT COUNT(*) FROM source.orders WHERE order_date = :date`. Если загрузка инкрементальная по дате, срез — одна дата или диапазон дат; если полная перезапись за период — срез за этот период.

**Приёмник:** запрос к таблице приёмника с тем же логическим срезом. Если в приёмнике есть поле «дата среза из источника» (например, order_date или source_date), фильтр тот же: `WHERE order_date = :date` (и при необходимости `WHERE load_date = :load_date`, чтобы не учитывать старые загрузки). Если приёмник партиционирован по дате загрузки, срез может быть «партиция за load_date = :date» — при условии, что за эту дату загружали ровно срез источника за ту же дату.

Пример пары запросов (логика):

```sql
-- Источник: заказы за 2025-02-15
-- source.orders — таблица в системе-источнике или её копия
SELECT COUNT(*) AS cnt FROM source.orders WHERE order_date = '2025-02-15';

-- Приёмник: загруженные заказы за ту же дату (срез по order_date)
SELECT COUNT(*) AS cnt FROM staging.orders WHERE order_date = '2025-02-15';
```

Assertion: оба числа равны. В интеграционном тесте значения получают (через два запроса или один запрос с объединением), сравнивают и при расхождении тест падает с сообщением «source count = X, target count = Y».

---

## 7.1.3. Допуск на отклонение

В части сценариев **строгое равенство** row count не требуется или недостижимо по замыслу:

- **Фильтр по бизнес-правилам:** ETL намеренно отбрасывает часть строк (невалидные, дубликаты по правилу «оставить последний»). Тогда ожидаемое количество в приёмнике меньше, чем в источнике; эталон задаётся не «источник = приёмник», а «приёмник = количество строк, прошедших фильтр» (посчитанное по правилу или по эталонной выборке).
- **Дедупликация:** в источнике дубликаты по ключу, в приёмнике — одна запись на ключ. Row count приёмника меньше; проверка «источник = приёмник» неверна. Правильная проверка — по уникальным ключам (COUNT(DISTINCT key) в источнике и в приёмнике) или сравнение с заранее известным ожидаемым числом после дедупликации.
- **Несколько источников в одну таблицу:** в приёмник пишутся данные из нескольких систем; общий row count приёмника за период сравнивают с суммой row count по всем источникам за тот же период.
- **Допустимые потери по соглашению:** например, «допускаем до 0,1% потерь из-за таймаутов при большом объёме». Тогда assertion — разница не превышает N% или не более K строк. Допуск должен быть явно обоснован и зафиксирован; по умолчанию для тестов данных лучше требовать полное совпадение, если только бизнес не задал иное.

Если вводится **допуск** (tolerance), его задают в виде процента или абсолютного числа: например, `ABS(source_count - target_count) <= max_diff` или `ABS(source_count - target_count) / source_count <= 0.001`. При превышении допуска тест падает.

---

## 7.1.4. Причины расхождений

Когда row count в приёмнике не совпадает с источником (и это не объясняется запланированным фильтром или дедупликацией), возможные причины:

| Причина | Симптом | Что проверять |
|---------|---------|----------------|
| Сбой загрузки | В приёмнике меньше строк. | Логи ETL, таймауты, откат транзакции; повторный запуск с идемпотентностью. |
| Фильтр в ETL | В приёмнике меньше; разница стабильна. | Спецификация: какие строки должны отбрасываться; сравнение с ожидаемым числом после фильтра. |
| Дубликаты в приёмнике | В приёмнике больше строк. | Повторный запуск без идемпотентности; проверка уникальности по ключу (COUNT vs COUNT DISTINCT). |
| Неверный срез | Считаем «не то». | Совпадение фильтров по дате/партиции в источнике и приёмнике; учёт load_date и source_date. |
| Изменение схемы источника | Ошибка при чтении, часть полей/строк отброшена. | Контракт источника, логи парсера; тесты на схему. |
| Разные часы/часовые пояса | «За дату» в источнике и приёмнике считаются по-разному. | Единый часовой пояс и определение «дня» для среза. |

При падении теста по row count первым шагом разбирают: совпадают ли срезы, есть ли запланированный фильтр или дедупликация, затем смотрят логи загрузки и проверяют уникальность и целостность (см. §7.2–7.4). В [§7.2](chapter-07-02.md) мы разберём контрольные суммы и хеши для сравнения источника и приёмника: SUM, MD5/SHA и детерминированность.

---

## Ключевое

- **Сравнение row count** источник vs приёмник — базовая проверка полноты ETL; срез (дата, партиция, batch) должен быть одним и тем же в обоих запросах.
- **Как считать:** запрос COUNT(*) к источнику и к приёмнику с одинаковым фильтром по срезу; assertion — равенство (или явное правило при фильтре/дедупликации).
- **Допуск на отклонение** уместен при запланированном фильтре, дедупликации или согласованном проценте потерь; задавать явно (процент или абсолютное число). По умолчанию — требовать совпадение.
- **Причины расхождений:** сбой загрузки, фильтр в ETL, дубликаты при повторной загрузке, неверный срез, изменение схемы источника, разница в определении даты/часового пояса. Разбор начинают с проверки среза и правил фильтрации.

В [§7.2](chapter-07-02.md) мы разберём контрольные суммы и хеши: SUM по полям, MD5/SHA по строкам, детерминированность и сравнение источника с приёмником.
