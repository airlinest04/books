# §11.2 Целостность чтения

В [§11.1](chapter-11-01.md) мы рассмотрели BEGIN, COMMIT и ROLLBACK. При параллельных сессиях возникает вопрос: **когда одна транзакция видит изменения другой?** Целостность чтения определяется правилами изоляции — какие данные и в какой момент доступны. В этом разделе разберём изоляцию транзакций и уровень READ COMMITTED по умолчанию в PostgreSQL. Подробнее об уровнях изоляции — в [§11.3](chapter-11-03.md). См. [документацию Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

---

## 11.2.1. Изоляция транзакций

**Изоляция** — свойство, при котором транзакция не «видит» незакоммиченные изменения других транзакций. Если сессия A выполнила UPDATE, но ещё не сделала COMMIT, сессия B не должна видеть эти изменения: иначе B опиралась бы на данные, которые могут быть откатаны.

По [документации](https://www.postgresql.org/docs/current/transaction-iso.html) PostgreSQL использует MVCC (multiversion concurrency control): каждая транзакция работает со своим снимком данных. Изменения других сессий становятся видимыми только после их COMMIT.

---

## 11.2.2. READ COMMITTED — уровень по умолчанию

В PostgreSQL уровень изоляции по умолчанию — **READ COMMITTED**. Сводка правил:

- **SELECT** видит только данные, закоммиченные **до начала этой команды**. Не видит незакоммиченные изменения и не видит коммиты других транзакций, произошедшие во время выполнения запроса.
- Каждая команда (SELECT, UPDATE, DELETE) получает **свой снимок** — на момент начала этой команды.
- Два последовательных SELECT в одной транзакции могут вернуть разные данные, если между ними другая сессия сделала COMMIT.

**Грязное чтение** (dirty read) — чтение незакоммиченных данных — в PostgreSQL **невозможно** при любом уровне изоляции.

---

## 11.2.3. Пример: два SELECT в одной транзакции

Сессия 1:

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- например, 1000
-- пауза: здесь сессия 2 обновляет и коммитит
SELECT balance FROM accounts WHERE id = 1;  -- уже другое значение, например 900
COMMIT;
```

Сессия 2 между двумя SELECT:

```sql
UPDATE accounts SET balance = 900 WHERE id = 1;
COMMIT;
```

При READ COMMITTED второй SELECT в сессии 1 увидит 900 — закоммиченное изменение сессии 2. Это **неповторяемое чтение** (non-repeatable read): один и тот же запрос в рамках транзакции вернул разные значения.

---

## 11.2.4. Собственные изменения видны сразу

В рамках одной транзакции видны **свои** незакоммиченные изменения:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SELECT balance FROM accounts WHERE id = 1;  -- уже обновлённое значение
-- другие сессии ещё не видят это изменение
COMMIT;
```

После COMMIT изменение становится видимым всем.

---

## 11.2.5. Когда READ COMMITTED достаточно

READ COMMITTED подходит для большинства приложений: грязное чтение исключено, производительность хорошая. Если нужна более жёсткая согласованность (повторные SELECT в рамках транзакции должны возвращать одни и те же данные) — используют REPEATABLE READ или SERIALIZABLE; об этом — в [§11.3](chapter-11-03.md).

---

## Ключевое

- **Изоляция** — транзакция не видит незакоммиченные изменения других.
- Уровень по умолчанию в PostgreSQL — **READ COMMITTED**: каждая команда видит данные на момент своего начала.
- Грязное чтение в PostgreSQL невозможно. Возможно неповторяемое чтение — два SELECT в одной транзакции могут вернуть разные данные.
- Собственные незакоммиченные изменения видны в той же транзакции; после COMMIT — всем.

В [§11.3](chapter-11-03.md) рассмотрим READ COMMITTED, REPEATABLE READ и SERIALIZABLE — отличия и аномалии.
