# §7.4 Пример пайплайна Pig: логи, фильтрация, группировка

В [§7.3](chapter-07-03.md) мы разобрали выполнение скриптов Pig и преобразование в MapReduce. Здесь соберём **полный пример** пайплайна: загрузка логов событий из HDFS, фильтрация по типу события, группировка по пользователю и подсчёт количества, запись результата. Затем кратко сравним с эквивалентной реализацией на **Hive** и на **MapReduce**. Следующая глава — [Oozie](chapter-08-01.md): оркестрация рабочих процессов. См. [Глоссарий](glossary.md).

---

## 7.4.1. Постановка задачи

Исходные данные — текстовый лог в HDFS (например, `/data/events/raw/`): каждая строка — одно событие, поля разделены табуляцией: `user_id`, `event_type`, `timestamp`. Нужно: оставить только события типа `click`, сгруппировать по `user_id`, посчитать число кликов на пользователя и записать результат в каталог `/data/events/agg_clicks`. См. [Глоссарий](glossary.md).

---

## 7.4.2. Скрипт Pig Latin

```pig
-- Загрузка: путь и схема (табуляция)
raw = LOAD '/data/events/raw/' USING PigStorage('\t')
  AS (user_id: int, event_type: chararray, ts: long);

-- Оставляем только клики
clicks = FILTER raw BY event_type == 'click';

-- Группировка по user_id; в каждом баге — кортежи одного пользователя
by_user = GROUP clicks BY user_id;

-- Подсчёт кликов на пользователя и проекция
result = FOREACH by_user GENERATE group AS user_id, COUNT(clicks) AS click_count;

-- Запись в HDFS
STORE result INTO '/data/events/agg_clicks';
```

Пояснения:

- **LOAD** читает файлы из каталога; `PigStorage('\t')` задаёт разделитель полей; схема даёт имена и типы полей.
- **FILTER** отбрасывает строки с `event_type != 'click'`.
- **GROUP BY user_id** собирает кортежи в баги по ключу; после GROUP отношение имеет вид `(group, clicks)`, где `clicks` — баг кортежей.
- **FOREACH ... GENERATE group AS user_id, COUNT(clicks)** — для каждой группы выдаём ключ и число элементов в баге; получаем пары (user_id, click_count).
- **STORE** записывает результат в указанный каталог; при выполнении Pig скомпилирует это в MapReduce job (LOAD + FILTER в Map, GROUP + COUNT в Reduce, STORE — вывод Reduce).

Запуск: `pig -x mapreduce script.pig` (или просто `pig script.pig` в распределённом окружении). Для отладки на малой выборке можно добавить перед STORE, например: `sample = LIMIT result 100; DUMP sample;` и запускать в локальном режиме с урезанными данными.

## 7.4.3. Эквивалент на Hive

Ту же логику можно выразить одним запросом Hive (при условии, что сырые данные уже загружены в таблицу или лежат в каталоге, на который указывает внешняя таблица). См. [Глоссарий](glossary.md).

Предположим, есть таблица `events` с полями `user_id`, `event_type`, `ts`. Тогда:

```sql
INSERT OVERWRITE DIRECTORY '/data/events/agg_clicks'
ROW FORMAT DELIMITED FIELDS TERMINATED BY '\t'
SELECT user_id, COUNT(*) AS click_count
FROM events
WHERE event_type = 'click'
GROUP BY user_id;
```

Один SQL-запрос заменяет цепочку Pig: Hive сам построит план (Filter, Group By, агрегация) и выполнит его как job на кластере. Плюс Hive — привычный SQL и единая модель таблиц с метаданными. Плюс Pig — явная последовательность шагов с именованными промежуточными отношениями; при более сложном ETL (несколько группировок, джойны, разветвление потока) скрипт Pig может быть нагляднее, чем несколько связанных Hive-запросов с временными таблицами.

## 7.4.4. Эквивалент на MapReduce

Тот же пайплайн «фильтр → группировка по ключу → подсчёт» в виде MapReduce ([гл. 3](chapter-03-01.md)) потребовал бы: См. [Глоссарий](glossary.md).

- **Mapper:** читать строки (TextInputFormat или аналогичный), парсить поля, при `event_type == "click"` выдавать пару `(user_id, 1)` (или просто user_id как ключ и константу как значение).
- **Reducer:** получать ключ (user_id) и список значений, суммировать (или считать количество) и выдать одну пару `(user_id, count)`.
- **Job:** задать InputFormat, пути входа/выхода, классы Mapper/Reducer, типы ключей и значений; при необходимости Combiner для предварительной суммы на маппере.
- Сборка в jar, запуск через `hadoop jar` или YARN.

Объём кода — десятки строк Java (парсинг, типы Writable, конфигурация Job) против нескольких строк Pig Latin. При добавлении шагов (например, ещё один фильтр или джойн со справочником) в MapReduce пришлось бы добавлять отдельный job и код для промежуточного ввода-вывода; в Pig — добавить операторы в цепочку.

---

## 7.4.5. Сравнение подходов

| Критерий | Pig | Hive | MapReduce |
|----------|-----|------|-----------|
| **Объём кода** | Несколько операторов | Один запрос (для простой агрегации) | Много строк Java, несколько job при усложнении |
| **Модель** | Процедурная цепочка отношений | Декларативный SQL | Императивный код Map/Reduce |
| **Промежуточные данные** | Именованные отношения в скрипте | Временные таблицы или подзапросы | Явные пути HDFS и отдельные job |
| **Типичное использование** | Многошаговый ETL, прототипирование | Запросы к таблицам, витрины | Кастомная логика, низкоуровневый контроль |

Для задачи «фильтр + группировка + агрегация» Hive и Pig оба дают короткое решение; выбор между ними зависит от стиля (SQL vs процедурная цепочка) и от того, станет ли пайплайн сложнее (больше шагов, ветвления) — тогда Pig часто удобнее. MapReduce оправдан, когда нужна специфическая логика или максимальный контроль над планом выполнения.

---

## Ключевое

- **Пример пайплайна Pig:** LOAD логов с схемой → FILTER по типу события → GROUP BY user_id → FOREACH с COUNT → STORE; скрипт компилируется в MapReduce job.
- **Hive:** тот же результат одним SQL (SELECT + WHERE + GROUP BY + INSERT INTO DIRECTORY); удобно при уже существующих таблицах и запросном стиле.
- **MapReduce:** эквивалент требует Mapper, Reducer, настройки Job и больше кода; уместен при нестандартной логике.
- Pig даёт короткую процедурную цепочку; при усложнении ETL промежуточные отношения в Pig часто нагляднее, чем цепочка Hive-запросов или несколько MapReduce job.
