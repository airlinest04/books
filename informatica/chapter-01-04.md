# §1.4 Связь с теорией ETL

В [§1.3](chapter-01-03.md) мы разобрали архитектуру PowerCenter: Repository, Integration Service, Designer, Workflow Manager, Workflow Monitor. Теперь сопоставим три этапа ETL — **Extract** (извлечение), **Transform** (преобразование), **Load** (загрузка) — с объектами и компонентами Informatica. Вы научитесь видеть, как абстрактная модель ETL реализуется в конкретной платформе, и поймёте связь этой книги с другими книгами серии: «ETL: концепции и процессы», «Проектирование и архитектура хранилищ данных (DWH)», «Airflow и оркестрация». См. [Глоссарий](glossary.md).

---

## 1.4.1. Extract (извлечение) в контексте Informatica

**Извлечение (Extract)** — первый этап ETL: чтение данных из систем-источников. В теории ETL источниками могут быть реляционные БД, файлы, API, потоки; результат этапа — данные в среде выполнения, готовые к преобразованию. См. книгу «ETL: концепции и процессы» ([../etl/chapter-01-01.md](../etl/chapter-01-01.md)), [../etl/chapter-02-01.md](../etl/chapter-02-01.md).

В Informatica этап извлечения реализуется так:

| Элемент теории ETL | Реализация в Informatica |
|-------------------|--------------------------|
| **Источник данных** | **Source** (определение в Designer): импорт структуры таблицы или файла из БД/файловой системы; метаданные (имена колонок, типы) хранятся в репозитории. |
| **Подключение к источнику** | **Connection** (в Workflow Manager): параметры подключения к БД (хост, порт, база, учётные данные) или путь к файлу; используется в Session при выполнении. |
| **Чтение данных** | **Source Qualifier** (трансформация в маппинге): по умолчанию генерирует `SELECT * FROM source_table`; поддерживает SQL-override для фильтрации, сортировки, join нескольких таблиц на стороне источника. |
| **Исполнение извлечения** | **Integration Service** при выполнении Session: подключается к источнику по Connection, выполняет запрос (или читает файл), получает строки и передаёт их в цепочку трансформаций. |

Таким образом, **Extract в Informatica** — это комбинация Source (метаданные структуры), Connection (параметры доступа), Source Qualifier (логика чтения, при необходимости SQL-override) и Integration Service (фактическое выполнение). Фильтрация и ограничение на этапе извлечения (pushdown) снижают объём данных, передаваемых в движок трансформаций; подробнее — в [§6.1](chapter-06-01.md), [§11.3](chapter-11-03.md).

## 1.4.2. Transform (преобразование) в контексте Informatica

**Преобразование (Transform)** — этап ETL, на котором данные очищаются, приводятся к целевому виду, обогащаются по бизнес-правилам. В теории: очистка, маппинг полей, джойны, агрегация, валидация. См. [../etl/chapter-02-03.md](../etl/chapter-02-03.md).

В Informatica этап преобразования реализуется через **трансформации** (Transformations) в маппинге:

| Вид преобразования (теория) | Трансформации Informatica |
|-----------------------------|---------------------------|
| **Фильтрация** | Filter (одна ветка по условию), Router (несколько веток по группам условий) |
| **Вычисление полей, условная логика** | Expression (формулы, IIF, DECODE, функции) |
| **Обогащение по справочнику** | Lookup (поиск в таблице/файле по ключу; cached или uncached) |
| **Объединение потоков** | Joiner (join двух источников по условию), Union (объединение потоков с совместимой структурой) |
| **Агрегация** | Aggregator (GROUP BY, SUM, AVG, COUNT, MIN, MAX) |
| **Сортировка, дедупликация** | Sorter, Rank, Distinct |
| **Разворот, нормализация** | Normalizer |
| **Вызов внешней логики** | Stored Procedure, HTTP, Web Service |

Все трансформации задаются в **Mapping** в Designer; Integration Service выполняет их при запуске Session. Преобразования могут выполняться **в памяти** Integration Service или **на стороне источника/приёмника** (pushdown) при поддержке СУБД. Подробнее типы трансформаций — в [главах 5–8](chapter-05-01.md).

## 1.4.3. Load (загрузка) в контексте Informatica

**Загрузка (Load)** — заключительный этап ETL: запись подготовленных данных в целевое хранилище. В теории: полная или инкрементальная загрузка, INSERT/UPDATE/MERGE, идемпотентность. См. [../etl/chapter-02-04.md](../etl/chapter-02-04.md).

В Informatica этап загрузки реализуется так:

| Элемент теории ETL | Реализация в Informatica |
|-------------------|--------------------------|
| **Целевое хранилище** | **Target** (определение в Designer): структура таблицы или файла; метаданные в репозитории. |
| **Подключение к приёмнику** | **Connection** (в Workflow Manager): параметры БД или путь к файлу; указывается в Session. |
| **Режим записи** | Настройки Session: Insert, Update, Delete, Bulk Load; для обновления — определение ключа обновления в Target или через Update Strategy. |
| **Исполнение загрузки** | **Integration Service** при выполнении Session: подключается к приёмнику, записывает строки (INSERT, UPDATE, bulk-операции в зависимости от настроек). |

Target поддерживает реляционные таблицы и плоские файлы; при bulk load данные могут загружаться напрямую в таблицу без построчной обработки, что ускоряет загрузку больших объёмов. Идемпотентность обеспечивается правилами маппинга и настройками Session (например, полная перезапись партиции по дате или upsert по ключу). Подробнее — в [§3.2](chapter-03-02.md), [§12.3](chapter-12-03.md).

## 1.4.4. Сопоставление этапов ETL и компонентов Informatica

Сводная таблица: этап ETL → объекты и компоненты Informatica.

| Этап ETL | Объекты Informatica | Компонент, выполняющий этап |
|----------|---------------------|----------------------------|
| **Extract** | Source, Connection, Source Qualifier | Integration Service (читает из источника по Connection, согласно маппингу) |
| **Transform** | Трансформации в Mapping (Expression, Filter, Lookup, Joiner, Aggregator и др.) | Integration Service (выполняет цепочку трансформаций в памяти или pushdown) |
| **Load** | Target, Connection | Integration Service (записывает в приёмник по Connection) |

Метаданные (Sources, Targets, Mappings, Connections) создаются в **Designer** и **Workflow Manager**, хранятся в **Repository**, используются **Integration Service** при выполнении **Session** в рамках **Workflow**. Расписание и запуск задаются в Workflow Manager; мониторинг — в Workflow Monitor.

**Задание для самопроверки:** возьмите маппинг из [главы 4](chapter-04-01.md) или [главы 12](chapter-12-01.md) и пошагово отметьте, какой элемент отвечает за Extract (источник, Source Qualifier), Transform (какие трансформации и что делают), Load (приёмник, режим записи).

## 1.4.5. Связь с книгой «ETL: концепции и процессы»

Книга «ETL: концепции и процессы» ([../etl/](../etl/)) даёт **теоретическую основу**: определение ETL, этапы Extract/Transform/Load, ETL vs ELT, CDC, качество данных, маппинг, пайплайны и оркестрация. В ней инструменты (Informatica, Talend, SSIS, Datagram) упоминаются как примеры реализации.

Книга «Informatica» — **практическое применение** теории ETL на конкретной платформе. Концепции из книги по ETL находят прямое соответствие:

| Концепция (ETL) | В Informatica |
|-----------------|---------------|
| Извлечение из БД, файлов | Source, Source Qualifier, Connection |
| Инкрементальная выгрузка, CDC | Source Qualifier с фильтром по дате; специализированные коннекторы CDC |
| Преобразование, очистка, маппинг полей | Expression, Filter, Lookup, Joiner, Aggregator и др. |
| Загрузка в DWH, витрину | Target, Session, Bulk Load |
| ETL vs ELT | Pushdown в Source Qualifier и Target; выполнение в СУБД |
| Маппинг (mapping) | Mapping в Designer — визуальное описание потока данных |
| Пайплайн, оркестрация | Workflow, Schedule; связь с внешним оркестратором — см. ниже |

Рекомендуемый порядок изучения: сначала [главы 1–2 книги по ETL](../etl/chapter-01-01.md) (определение, этапы), затем эта книга — для закрепления на практике. См. [../etl/](../etl/).

## 1.4.6. Связь с книгой «Проектирование и архитектура хранилищ данных (DWH)»

Книга по DWH ([../dwh/](../dwh/)) описывает **целевое хранилище**: слои данных (Raw, Staging, Core, витрины), схемы «звезда» и «снежинка», SCD, витрины данных. ETL (и Informatica в частности) **наполняет** это хранилище: извлекает из источников, преобразует и загружает в таблицы слоёв.

Связь Informatica и DWH:

| Концепция DWH | Реализация в Informatica |
|---------------|--------------------------|
| **Слой Staging** | Target — таблицы стейджинга; маппинг с минимальной трансформацией (типы, фильтрация) |
| **Слой Core / витрины** | Target — таблицы фактов и измерений; маппинг с Lookup (обогащение по измерениям), Aggregator (агрегаты), SCD-логика при необходимости |
| **Схема «звезда»** | Отдельные маппинги для фактов и измерений; Lookup для подстановки surrogate key |
| **SCD Type 2** | Expression, Lookup, Router для определения новых/изменённых записей; Update Strategy |
| **Витрины** | Target — таблицы витрин; маппинг с агрегацией и денормализацией |

Informatica не задаёт архитектуру DWH — она выполняет загрузку в таблицы, спроектированные по принципам книги по DWH. Рекомендуется изучать DWH для понимания целевой модели; затем проектировать маппинги под эту модель. См. [../dwh/](../dwh/), [главу 12](chapter-12-01.md) (практика загрузки в DWH).

## 1.4.7. Связь с книгой «Airflow и оркестрация»

Книга «Airflow и оркестрация» ([../airflow/](../airflow/)) описывает **оркестрацию** пайплайнов: планировщик запускает задачи по расписанию и зависимостям; оркестратор не выполняет ETL сам, а **запускает** ETL-задачи. См. [../airflow/chapter-01-03.md](../airflow/chapter-01-03.md) (отличие оркестратора от ETL-инструмента).

Informatica PowerCenter **включает встроенную оркестрацию**: Workflow с расписанием (Schedule) и зависимостями между задачами. Для многих сценариев этого достаточно: Workflow Manager задаёт «когда» и «в каком порядке» выполнять Session.

Однако возможны **гибридные сценарии**:

- **Airflow запускает Informatica:** Airflow DAG содержит задачу (например, через `InformaticaOperator` или `BashOperator` с вызовом `pmcmd`), которая запускает workflow PowerCenter. Airflow управляет зависимостями между разными системами (например, «сначала загрузка из API в файл, затем Informatica загружает файл в DWH»).
- **Informatica как одна из задач пайплайна:** общий пайплайн включает шаги на Python, SQL, Informatica, dbt и др.; Airflow координирует их выполнение.

Разделение ответственности: **Informatica** — ETL (извлечение, преобразование, загрузка); **Airflow** — оркестрация (когда запускать, порядок, мониторинг кросс-системных пайплайнов). См. [../airflow/](../airflow/).

## 1.4.8. Типичные ошибки при сопоставлении ETL и Informatica

- **Считать, что Source Qualifier — единственное место извлечения:** Source Qualifier — точка входа данных в маппинг; но Lookup и Joiner тоже читают данные (Lookup — из справочника, Joiner — из второго источника). С точки зрения этапа Extract ключев именно Source Qualifier для основных источников.
- **Путать Mapping и Session:** Mapping описывает **что** делать (логика ETL); Session — **как** выполнять (Connection, параметры, партиционирование). Оба необходимы для выполнения.
- **Игнорировать pushdown:** часть Transform может выполняться в источнике (SQL-override в Source Qualifier) или в приёмнике; тогда границы E-T-L размыты, но логически этапы сохраняются.
- **Думать, что Informatica заменяет оркестратор:** для изолированных ETL-нагрузок встроенного Workflow достаточно; для сложных кросс-системных пайплайнов Airflow или аналог дополняет Informatica.

## Ключевое

- **Extract в Informatica:** Source (метаданные), Connection (доступ), Source Qualifier (логика чтения, SQL-override), Integration Service (выполнение).
- **Transform в Informatica:** трансформации в Mapping (Expression, Filter, Lookup, Joiner, Aggregator, Sorter, Router и др.); Integration Service выполняет цепочку в памяти или pushdown.
- **Load в Informatica:** Target (метаданные), Connection (доступ), настройки Session (Insert/Update/Bulk), Integration Service (запись).
- **Сопоставление:** этап ETL → объекты Informatica → Integration Service как исполняющий компонент для всех трёх этапов.
- **Связь с книгами серии:** ETL (теория этапов) — основа; DWH (целевая модель) — куда загружаем; Airflow (оркестрация) — координация пайплайнов при необходимости.

В [§2.1](chapter-02-01.md) мы переходим к репозиторию и метаданным: Repository Server, домены, репозитории и сервисы.
