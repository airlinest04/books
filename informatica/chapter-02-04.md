# §2.4 Версионирование и развёртывание

В [§2.3](chapter-02-03.md) мы разобрали Connections и переменные, в том числе parameter file для переопределения значений между окружениями. Теперь рассмотрим **версионирование** и **развёртывание** метаданных: как переносить объекты между репозиториями (DEV → TEST → PROD), экспорт и импорт, инструменты (Repository Manager, pmrep), version control при наличии team-based development и best practices. Вы научитесь планировать миграцию между окружениями и избегать типичных ошибок. См. [Глоссарий](glossary.md).

---

## 2.4.1. Экспорт и импорт: обзор

**Экспорт** — сохранение объектов репозитория в XML-файл. **Импорт** — загрузка объектов из XML-файла в репозиторий (тот же или другой). Экспорт и импорт позволяют переносить метаданные между папками, репозиториями и окружениями без необходимости одновременного подключения к обоим репозиториям. Источник: [Exporting and Importing Objects Overview](https://docs.informatica.com/data-integration/powercenter/10-5/repository-guide/exporting-and-importing-objects/exporting-and-importing-objects-overview.html).

Сценарии использования:

| Сценарий | Описание |
|----------|----------|
| **Развёртывание в production** | После тестирования в DEV экспортировать маппинг, workflow, session в XML и импортировать в PROD. |
| **Архивирование** | Экспорт объектов перед удалением; сохранение истории изменений. |
| **Обмен метаданными** | Передача маппинга третьей стороне без доступа к репозиторию; при необходимости удалить connection-информацию из XML перед передачей. |
| **Поиск и замена в объекте** | Экспорт в XML, редактирование в текстовом редакторе (например, массовая замена имени порта), импорт обратно. |
| **Копирование между репозиториями** | Когда нет одновременного доступа к обоим репозиториям: экспорт на одной машине, перенос файла, импорт на другой. |

**Важно:** экспорт и импорт поддерживаются только между репозиториями **одной версии** PowerCenter. Импорт объектов из более старой или новой версии не поддерживается. См. документацию Informatica.

## 2.4.2. Инструменты экспорта и импорта

| Инструмент | Объекты | Когда использовать |
|------------|---------|---------------------|
| **Repository Manager** | Designer и Workflow Manager | Ручной экспорт/импорт папок, групп объектов; разовый перенос. |
| **Designer** | Только Designer (Sources, Targets, Mappings, Mapplets, Transformations) | Экспорт маппингов и связанных объектов. |
| **Workflow Manager** | Только Workflow Manager (Workflows, Sessions, Connections) | Экспорт workflow и сессий. |
| **pmrep** | Designer и Workflow Manager | Автоматизация: ежедневный/еженедельный экспорт, скрипты развёртывания, CI/CD. |

**pmrep** — командная утилита PowerCenter для работы с метаданными. Команды `pmrep objectexport` и `pmrep objectimport` выполняют экспорт и импорт; можно использовать control files для задания списка объектов и параметров. pmrep устанавливается вместе с PowerCenter Client; для автоматизации развёртывания его вызывают из скриптов (bash, PowerShell) или из пайплайнов CI/CD. См. [§2.1.7](chapter-02-01.md).

---

## 2.4.3. Формат экспорта и зависимости объектов

Объекты экспортируются в **XML-файл**. При экспорте маппинга в файл попадают и зависимые объекты: Sources, Targets, Transformations, используемые в маппинге. При экспорте workflow — Session и связанный Mapping (или ссылка на него). Порядок импорта должен учитывать зависимости: сначала Sources и Targets, затем Mappings, затем Sessions и Workflows.

При импорте можно разрешать **конфликты имён**: если объект с таким именем уже существует, выбрать Replace (заменить), Ignore (пропустить) или Create New (создать с новым именем). Для Connections часто выбирают Ignore при импорте в PROD — connections в PROD настраиваются отдельно и не перезаписываются из DEV.

## 2.4.4. Version control (версионирование)

При включённой опции **team-based development** в репозитории доступно **version control**. В версионированном репозитории:

- хранятся **несколько версий** одного объекта;
- доступны **сравнение версий** (diff), **отслеживание изменений** (change tracking);
- **Labels** (метки) — именованные снимки версий для развёртывания (например, label «Release_2025_02»);
- развёртывание выбранной версии или label в целевой репозиторий.

Version control поддерживает практики change management: кто и когда изменил объект, откат к предыдущей версии, контроль перед выкладкой в production. Опция team-based development — отдельная лицензия; при её отсутствии версионирование недоступно, но экспорт/импорт работают. См. [§2.1.8](chapter-02-01.md).

## 2.4.5. Deployment groups

**Deployment group** — группа объектов, предназначенная для развёртывания. В группу добавляют Mappings, Workflows, Sessions и связанные объекты; группу экспортируют и импортируют как единое целое. Удобно для развёртывания логически связанных компонентов (например, все маппинги и workflow одного проекта).

Deployment groups создаются и управляются в Repository Manager; права на копирование группы требуют Execute permission. См. [§2.2.7](chapter-02-02.md).

## 2.4.6. Миграция между окружениями (DEV → TEST → PROD)

Типичная цепочка окружений:

```
DEV (разработка)  →  TEST (тестирование)  →  PROD (production)
```

**Рекомендуемый процесс:**

1. **Разработка в DEV:** создание и изменение Sources, Targets, Mappings, Workflows, Sessions в репозитории DEV.
2. **Валидация:** проверка маппингов (Valid), выполнение тестовых запусков в DEV.
3. **Экспорт:** экспорт папки, deployment group или отдельных объектов в XML.
4. **Импорт в TEST:** импорт в репозиторий TEST; при необходимости Replace для обновления существующих объектов. Connections в TEST настраиваются отдельно (или переопределяются через parameter file).
5. **Тестирование в TEST:** прогон workflow с тестовыми данными; проверка результатов.
6. **Экспорт из TEST (опционально):** если в TEST вносились исправления, экспорт оттуда для переноса в PROD.
7. **Импорт в PROD:** импорт в production-репозиторий. Connections — как правило, Ignore или отдельная настройка; в PROD используются production-connections.
8. **Parameter file для PROD:** отдельный parameter file с production-значениями (connections, пути, параметры).

Разделение репозиториев по окружениям изолирует production от случайных изменений; доступ к PROD ограничивается. См. [§2.1.6](chapter-02-01.md).

## 2.4.7. Best practices развёртывания

**Использовать parameter file для окружений**

Не хранить production-connections и пути в метаданных Session. Использовать session parameters (`$DBConnectionSource`, `$DBConnectionTarget` и др.) и задавать значения в parameter file при запуске. Один и тот же Session в PROD работает с production-connections через parameter file.

**Проверять версию PowerCenter**

Репозитории DEV, TEST и PROD должны быть одной версии PowerCenter. При обновлении версии — миграция всех репозиториев по плану.

**Экспортировать зависимости**

При экспорте Mapping включать зависимые объекты (Sources, Targets, Transformations). При экспорте Workflow — Session и Mapping. Иначе при импорте появятся ошибки «object not found».

**Не импортировать Connections в PROD без необходимости**

Connections содержат учётные данные и строки подключения. В PROD connections настраиваются отдельно с production-параметрами. При импорте выбирать Ignore для Connection objects или не включать их в экспорт.

**Валидировать после импорта**

После импорта проверить статус объектов (Valid/Invalid). Исправить Invalid объекты до запуска. Зависимости от объектов, отсутствующих в целевом репозитории, приведут к Invalid.

**Использовать deployment groups для связанных объектов**

Группировать объекты одного проекта или релиза в deployment group; развёртывать группой для согласованности.

**Документировать процесс**

Фиксировать порядок развёртывания, список объектов, параметры parameter file для каждого окружения. Это упрощает повторные развёртывания и передачу знаний.

## 2.4.8. pmrep: основные команды для развёртывания

Типичные команды pmrep (синтаксис может отличаться по версиям; см. документацию):

```bash
# Подключение к репозиторию
pmrep connect -r repository_name -d domain_name -n username -x password

# Экспорт папки
pmrep objectexport -o folder_name -f export_file.xml

# Экспорт конкретных объектов
pmrep objectexport -m mapping_name -f export_file.xml

# Импорт из файла
pmrep objectimport -i import_file.xml -c control_file.txt
```

**Deployment Control File** и **Object Import Control File** задают параметры импорта: какие объекты импортировать, как разрешать конфликты (Replace/Ignore), в какую папку помещать. Использование control files упрощает автоматизацию и воспроизводимость развёртывания.

---

## 2.4.9. Интеграция с CI/CD

Экспорт/импорт и pmrep позволяют интегрировать PowerCenter в пайплайны CI/CD:

- **Сборка:** экспорт объектов из DEV (или из системы контроля версий, если XML хранится в Git) через pmrep или скрипт.
- **Тестирование:** импорт в TEST, запуск workflow через infacmd/pmcmd, проверка результатов.
- **Развёртывание:** импорт в PROD по approval, запуск с production parameter file.

Инструменты оркестрации (Apache Airflow, Jenkins и др.) могут вызывать pmrep и pmcmd в задачах пайплайна. Parameter file для каждого окружения хранится в защищённом хранилище (secrets manager) и подставляется при запуске.

## 2.4.10. Типичные ошибки при развёртывании

- **Импорт из репозитория другой версии:** не поддерживается; все репозитории должны быть одной версии PowerCenter.
- **Импорт без учёта зависимостей:** импорт Session без Mapping или Mapping без Source приведёт к ошибкам; экспортировать с зависимостями.
- **Перезапись production-connections:** при импорте с Replace connections в PROD будут перезаписаны значениями из DEV; использовать Ignore для Connection objects.
- **Забыть parameter file для PROD:** Session в PROD будет использовать connection из метаданных (если задан) или упадёт; нужен parameter file с production-значениями.
- **Не проверить Valid после импорта:** Invalid объекты не выполнятся; проверять статус и исправлять перед запуском.
- **Экспорт без зависимых объектов:** маппинг без Source/Target при импорте в пустой репозиторий создаст неполные ссылки; включать зависимости в экспорт.

## Ключевое

- **Экспорт/импорт** — перенос объектов в XML между папками и репозиториями. Инструменты: Repository Manager, Designer, Workflow Manager, pmrep. Только между репозиториями одной версии.
- **Сценарии:** развёртывание в production, архивирование, обмен метаданными, поиск и замена, копирование между репозиториями.
- **Version control** (при team-based development): несколько версий объекта, labels, сравнение, развёртывание выбранной версии.
- **Deployment groups** — группы объектов для развёртывания единым блоком.
- **Миграция DEV → TEST → PROD:** экспорт из DEV, импорт в TEST, тестирование, экспорт из TEST при необходимости, импорт в PROD. Connections в PROD — отдельно; parameter file для production-значений.
- **Best practices:** parameter file для окружений, проверка версии, экспорт с зависимостями, не импортировать connections в PROD, валидация после импорта, deployment groups, документирование.
- **pmrep** — автоматизация экспорта/импорта; CI/CD через pmrep и pmcmd.

В [§3.1](chapter-03-01.md) мы переходим к источникам данных: определение Sources в Designer, Source Analyzer, импорт из БД и плоских файлов.
