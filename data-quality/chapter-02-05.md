# §2.5 Уникальность (Uniqueness)

В [§2.4](chapter-02-04.md) мы разобрали **своевременность**: данные должны быть доступны в срок. Пятое измерение качества — **уникальность** (Uniqueness): в пределах заданной области (таблица, срез, витрина) **нет дубликатов** по выбранному ключу; каждая сущность или факт представлен не более чем одной записью по этому ключу. В разделе мы дадим определение уникальности, разберём выбор ключа для проверки, детекцию дубликатов в SQL и связь с правилами валидации и дедупликацией в ETL.

---

## 2.5.1. Определение уникальности

**Уникальность** (Uniqueness) как измерение качества данных — это степень, в которой **нет повторяющихся записей** по заданному ключу в заданной области: таблице, партиции, витрине. Дубликат — две или более записей с одинаковым значением ключа (или комбинации полей, образующих ключ), где по бизнес-правилам должна быть одна запись. Нарушение уникальности искажает агрегаты (COUNT, SUM), приводит к двойному учёту в отчётах и к неоднозначности при связывании с другими таблицами.

| Аспект | Описание |
|--------|----------|
| Ключ уникальности | Набор полей (бизнес-ключ, суррогатный ключ или их комбинация), по которому в области не должно быть двух одинаковых значений. Например: (order_id), (client_id, contract_id), (date, branch_id, operation_id). |
| Область проверки | Где проверяем: вся таблица, партиция за дату, витрина после загрузки. В инкрементальной загрузке дубликаты могут появляться в рамках одного прогона (повторная вставка) или при наложении срезов. |
| Ожидание | По смыслу данных в каждой области — одна запись на одно значение ключа; дубликаты считаются дефектом качества (если иное не зафиксировано, например историчность по версиям). |

Уникальность не гарантирует правильность значения (точность) или заполненность полей (полнота); она отвечает только на вопрос **«нет ли лишних копий записей по ключу»**. См. [Глоссарий](glossary.md).

---

## 2.5.2. Выбор ключа для проверки уникальности

Проверка уникальности возможна только при **явно заданном ключе**: по каким полям считаем запись дубликатом другой. Ключ определяется бизнес-требованиями:

- **Бизнес-ключ (natural key):** идентификатор из предметной области — номер договора, код заказа, пара (дата, филиал, номер операции). В витрине договоров ожидается одна строка на договор (или одна актуальная версия при SCD).
- **Составной ключ:** несколько полей вместе образуют уникальность — например, (invoice_id, line_num) для строк накладной; (date, source_system, batch_id) для сырого среза.
- **Суррогатный ключ:** технический идентификатор (id), сгенерированный системой; уникальность по нему обычно обеспечивается СУБД, но при загрузке из нескольких источников или при слиянии срезов дубликаты по бизнес-ключу всё равно возможны.

Важно: ключ должен быть **зафиксирован** для таблицы или витрины. Без согласованного ключа «дубликат» неоднозначен: две записи с одинаковым именем клиента, но разными id — это одна сущность или две? Для измерения уникальности ключ задаётся явно (в модели данных, в спецификации витрины). Правила на уровне таблицы и ключи разбираются в главе 4.

## 2.5.3. Детекция дубликатов в SQL

Проверка «есть ли дубликаты по ключу» сводится к поиску значений ключа, встречающихся более одного раза. Базовый приём: группировка по ключу и отбор групп с COUNT(*) > 1.

Пример (PostgreSQL): таблица `staging.orders`, ключ уникальности — `order_id` в рамках партиции `order_date`. Найти ключи, по которым больше одной записи:

```sql
SELECT order_id, order_date, COUNT(*) AS cnt
FROM staging.orders
WHERE order_date = CURRENT_DATE - 1
GROUP BY order_id, order_date
HAVING COUNT(*) > 1;
```

Если запрос возвращает строки — перечислены значения ключа, по которым есть дубликаты. Метрика уникальности: число таких ключей или число «лишних» записей (общее число записей минус число уникальных ключей). Доля уникальных записей: `COUNT(DISTINCT key_fields) * 100.0 / COUNT(*)`; при 100% дубликатов нет, при меньшем значении — есть дубликаты.

Для составного ключа в GROUP BY перечисляются все поля ключа:

```sql
SELECT date, branch_id, operation_id, COUNT(*) AS cnt
FROM staging.transactions
WHERE load_date = CURRENT_DATE - 1
GROUP BY date, branch_id, operation_id
HAVING COUNT(*) > 1;
```

Детекция дубликатов входит в профилирование (глава 3) и в проверки после загрузки (глава 5); при обнаружении дубликатов записи могут отклоняться, отправляться в кварантин или дедуплицироваться по правилу (оставить первую/последнюю по времени). См. [Глоссарий](glossary.md).

## 2.5.4. Источники дубликатов и профилактика

Дубликаты могут появляться по разным причинам:

| Причина | Пример | Профилактика / проверка |
|---------|--------|--------------------------|
| Повторная загрузка одного и того же среза | Два прогона за одну дату без идемпотентности; оба вставили одни и те же строки. | Идемпотентность загрузки (полная перезапись партиции или merge по ключу без дублей); проверка дубликатов после загрузки. |
| Дубликаты в источнике | Источник отдаёт одну операцию дважды (ошибка выгрузки, двойная передача). | Профилирование источника; дедупликация при преобразовании (DISTINCT по ключу, выбор одной записи по правилу). |
| Слияние нескольких источников без дедупликации | Два файла с перекрывающимися ключами загружены в одну таблицу. | Определение единого ключа; дедупликация при merge (например, по максимальной версии или дате обновления). |
| Отсутствие ограничения UNIQUE в целевой таблице | СУБД не запрещает повтор ключа; дубли вставились при сбое логики. | Ограничение UNIQUE (или PRIMARY KEY) на ключевые поля где применимо; проверка перед вставкой или после. |

Проверка уникальности выполняется после преобразования (перед загрузкой в целевой слой) и/или после загрузки в целевой таблице; при нарушении — алерт, отклонение лишних записей или дедупликация по зафиксированному правилу. Идемпотентность пайплайна и дедупликация подробнее — в книге серии по ETL и по тестированию данных.

## 2.5.5. Уникальность и правила валидации

Требование уникальности переводится в правила и проверки:

- **Ограничение в СУБД:** UNIQUE или PRIMARY KEY по полям ключа на целевой таблице; при попытке вставить дубликат СУБД вернёт ошибку. Подходит, когда дубликаты недопустимы на уровне слоя.
- **Проверка в ETL перед загрузкой:** запрос на дубликаты по ключу над набором данных, подготовленных к вставке; при наличии дубликатов — не загружать или дедуплицировать.
- **Проверка после загрузки:** запрос на дубликаты по ключу в целевой таблице (по партиции или по всей таблице); метрика — число дубликатов; алерт при > 0.

Выбор между «жёстко запретить дубликаты» (UNIQUE, отклонение при загрузке) и «разрешить, но мониторить» зависит от слоя и требований: в витрине для отчётов дубликаты обычно недопустимы; в сыром слое могут допускаться с последующей дедупликацией на следующем этапе. Глава 4 — типы правил; глава 7 — обработка ошибочных данных и кварантин.

---

## 2.5.6. Метрики уникальности

| Метрика | Описание | Пример порога |
|---------|----------|---------------|
| Число дубликатов по ключу | Количество значений ключа, для которых COUNT(*) > 1. | 0 |
| Число «лишних» записей | (Общее число записей) − (число уникальных ключей). | 0 |
| Доля уникальных записей | COUNT(DISTINCT key) / COUNT(*) в процентах. | 100% |
| Список ключей с дубликатами | Перечень ключей для ручного разбора или дедупликации. | — |

Метрики собираются по срезу (партиция за дату) или по всей таблице; тренд по дням помогает выявить появление дубликатов после смены источника или логики загрузки.

---

## 2.5.7. Типичные ошибки

- **Проверять уникальность без явного ключа:** без зафиксированного набора полей понятие «дубликат» не определено; возможны ложные срабатывания (разные сущности с совпадающими полями) или пропуск дублей (ключ выбран неполный).
- **Игнорировать область проверки:** в таблице с историей (SCD Type 2) по одному бизнес-ключу может быть несколько записей (разные версии); уникальность проверяется по (business_key, effective_to) или только по активным записям. Область (вся таблица / партиция / только активные) должна быть задана.
- **Считать уникальность достаточной для корректности:** отсутствие дубликатов не гарантирует правильность значений (точность) или полноту; нужны отдельные проверки по другим измерениям.

---

## Ключевое

- **Уникальность (Uniqueness)** — измерение качества: в заданной области нет дубликатов по заданному ключу; каждая сущность или факт представлен не более чем одной записью по этому ключу.
- Ключ уникальности задаётся явно (бизнес-ключ, составной ключ); от его выбора зависит, что считается дубликатом.
- Детекция: группировка по ключу, HAVING COUNT(*) > 1; метрики — число дубликатов по ключу, число лишних записей, доля уникальных записей.
- Профилактика: идемпотентность загрузки, дедупликация в ETL, ограничение UNIQUE в СУБД; проверки до и после загрузки.
- Уникальность проверяется в заданной области (таблица, партиция, только активные записи); в исторических таблицах область задаётся с учётом версионности.

В [§2.6](chapter-02-06.md) мы разберём **валидность** (Validity): значения в допустимом диапазоне, соответствие формату и справочникам.
