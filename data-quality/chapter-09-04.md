# §9.4 Метрики, алерты и отчёт

В [§9.3](chapter-09-03.md) мы реализовали проверки в ETL, кварантин и логирование; метрики записываются в таблицу при каждом прогоне. В этом разделе мы настроим **сбор метрик**, **алерты** при нарушении порогов и **отчёт по качеству**. Это завершает главу 9 и полный цикл практики: от постановки задачи (§9.1) через профилирование (§9.2) и проверки в ETL (§9.3) до мониторинга и отчётности. Теоретическая база — глава 6; здесь применяем её к нашему пайплайну. Далее — [Глоссарий](glossary.md) и список литературы (sources.md). См. [Глоссарий](glossary.md).

---

## 9.4.1. Сбор метрик

Метрики собираются из пайплайна: задачи при прогоне записывают значения в **таблицу метрик** ([§9.3](chapter-09-03.md), [§6.1](chapter-06-01.md)). Для нашего сценария в таблице хранятся по каждому прогону (или по каждому срезу):

- **Идентификаторы:** pipeline_id, partition_date (срез), run_id, timestamp.
- **Счётчики:** extract_count (число записей после извлечения), valid_count (число валидных после валидации), rejected_count (число отклонённых), load_count (число загруженных в Core). Из них выводятся процент валидных (valid_count / extract_count * 100) и тренд по дням.
- **При необходимости:** контрольные суммы (SUM по полям) на этапах extract, после Staging и после load для сверки ([§5.4](chapter-05-04.md)); rejected_by_rule (rule_id, count) для детализации по правилам.
- **Флаги и SLA:** check_load_passed (да/нет), check_mart_passed (да/нет), sla_met (загрузка к дедлайну — да/нет).

Источник данных для таблицы метрик — запись из шагов пайплайна ([§9.3](chapter-09-03.md)): после извлечения пишем extract_count; после валидации — valid_count, rejected_count; после загрузки в Core — load_count и результат сравнения с эталоном. Накопление по дням даёт тренд; сравнение с порогами — основа для алертов. См. [Глоссарий](glossary.md).

---

## 9.4.2. Алерты

**Алерты** настраиваются на основе **порогов** по метрикам ([§6.2](chapter-06-02.md)). Пороги задаются из требований к качеству ([§9.1](chapter-09-01.md)) и согласуются с владельцем данных. Примеры для нашего пайплайна:

| Метрика | Пример порога | Реакция при нарушении |
|---------|---------------|------------------------|
| % валидных записей | Не ниже 99% (или 95% по согласованию) | Алерт; разбор причин; при критичности — блокировка открытия витрины. |
| Число отклонённых | Не более N в день (N задаётся по объёму и допустимой доле) | Алерт; детализация по правилам для приоритизации. |
| Контрольные суммы после загрузки | Совпадение с эталоном (допуск по округлению при необходимости) | Fail задачи загрузки; алерт; разбор. |
| SLA | Загрузка и обновление витрины к заданному времени | Алерт при опоздании; эскалация по регламенту. |

**Реализация алертов:** после записи метрик (или после шага проверки) значение сравнивается с порогом; при нарушении вызывается отправка уведомления — e-mail, мессенджер, тикет ([§6.2](chapter-06-02.md)). В оркестраторе алерт может быть частью callback при падении задачи (on_failure_callback) или отдельной задачей «проверка метрик и уведомление». В уведомлении указывают: пайплайн, срез (дата), метрика, значение, порог, ссылка на дашборд или лог. Получатели задаются по регламенту (дежурный, владелец данных); при отсутствии реакции в срок — эскалация ([§7.4](chapter-07-04.md)). См. [Глоссарий](glossary.md).

## 9.4.3. Отчёт по качеству

**Отчёт по качеству** — сводка метрик за период для заинтересованных сторон ([§6.3](chapter-06-03.md)). Для нашего пайплайна в отчёт включают:

- **Сводка за период:** пайплайн, период (день/неделя/месяц), средний или итоговый % валидных записей, общее число отклонённых, число прогонов с нарушением контрольных сумм, % выполнения SLA.
- **Тренд:** график или таблица % валидных и числа отклонённых по дням; при наличии — разбивка отклонённых по правилам (rule_id).
- **Инциденты:** перечень дней или прогонов с падением проверок, расхождением контрольных сумм или срывом SLA; при необходимости — ссылка на тикеты или на кварантин.

Периодичность отчёта задаётся регламентом: ежедневная сводка для владельца данных и аналитиков, еженедельная или ежемесячная — для руководства и аудита. Формат — дашборд (Grafana, BI-инструмент) с фильтром по периоду или сформированный документ (отчёт по шаблону). Отчётность без связи с действиями (кто разбирает инциденты, кто владелец) теряет смысл ([§6.3](chapter-06-03.md)); получатели и эскалация должны быть зафиксированы. См. [Глоссарий](glossary.md).

## 9.4.4. Полный цикл практики

Глава 9 собрала **полный цикл** пайплайна с проверками качества в один сценарий:

1. **Постановка задачи** (§9.1): загрузка из источника в DWH, требования к качеству, точки проверки.
2. **Профилирование источника** (§9.2): первичный анализ, выявление проблем, определение правил валидации.
3. **Правила и проверки в ETL** (§9.3): реализация проверок в точках пайплайна, кварантин при ошибках, логирование в таблицу метрик.
4. **Метрики, алерты и отчёт** (§9.4): сбор метрик из пайплайна, пороги и алерты, отчёт по качеству.

Задания по главе ([TOC](TOC.md)): определить требования и точки проверки для своего пайплайна; выполнить профилирование источника; сформулировать правила; реализовать пайплайн с проверками, кварантином и метриками по этому сценарию. См. [Глоссарий](glossary.md).

## 9.4.5. Типичные ошибки

- **Не задать пороги:** метрики собираются, но без порогов алерты не настраиваются; нарушения качества остаются без оперативной реакции.
- **Алертить без контекста:** в уведомлении должны быть пайплайн, срез (дата), метрика, значение и порог; иначе получатель не понимает, что проверять.
- **Отчёт без привязки к ответственным:** отчёт «качество за месяц» полезен, если по нему принимают решения и назначены владельцы данных и эскалация; иначе отчётность формальна ([§6.3](chapter-06-03.md)).
- **Не обновлять дашборд или отчёт после изменения пайплайна:** при добавлении новых метрик или пайплайнов дашборд и шаблон отчёта нужно актуализировать.

## Ключевое

- **Сбор метрик:** из пайплайна в таблицу метрик записываются pipeline_id, срез, run_id, extract_count, valid_count, rejected_count, load_count, результат проверок, SLA; при успехе и при ошибке — для тренда.
- **Алерты:** пороги по метрикам (например, % валидных не ниже 99%, число отклонённых не выше N, совпадение контрольных сумм, выполнение SLA); при нарушении — уведомление с контекстом (пайплайн, срез, метрика, значение, порог); получатели и эскалация по регламенту.
- **Отчёт по качеству:** сводка за период, тренд по дням, инциденты; периодичность и аудитория по регламенту; связь с ответственными и действиями.
- **Полный цикл:** постановка задачи → профилирование → правила и проверки в ETL → метрики, алерты и отчёт; задания — реализовать пайплайн с проверками по сценарию.

На этом заканчивается основное содержание книги по качеству данных. Термины собраны в [Глоссарии](glossary.md); список литературы и источников — в файле **sources.md** (при наличии в проекте) или в приложениях по серии. Дальнейшее углубление: главы 1–8 для теории и методик; книги серии по ETL, DWH, Airflow и по финансовым расчётам и сверке — для контекста реализации и предметных областей.
