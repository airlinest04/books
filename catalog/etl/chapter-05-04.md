# §5.4 Метрики качества в пайплайне

В [§5.3](chapter-05-03.md) мы разобрали проверки при загрузке и политику при нарушении ограничений. Чтобы качество данных было **наблюдаемым** и управляемым, нужны **метрики качества**: счётчики обработанных и отклонённых записей по этапам и по правилам, сравнение с предыдущим прогоном и отчётность. В этом разделе мы систематизируем, какие метрики собирать в пайплайне, как их использовать для алертов и трендов и как строить отчётность по качеству. Это завершает главу 5; в [главе 6](chapter-06-01.md) мы перейдём к миграции данных и маппингу. См. [Глоссарий](glossary.md).

---

## 5.4.1. Зачем нужны метрики качества

Метрики качества дают **количественную картину** того, сколько данных прошло каждый этап пайплайна и сколько было отклонено и по каким причинам. Без счётчиков невозможно: оценить полноту (всё ли извлеклось и загрузилось), заметить аномалии (резкий рост отклонённых, нулевой объём), обосновать доработку правил и источников, отчитаться перед заказчиком или регулятором. Метрики опираются на проверки из §5.1–5.3 и дополняют критерий наблюдаемости ([§1.4.5](chapter-01-04.md)). См. [Глоссарий](glossary.md).

Метрики собираются по ходу выполнения пайплайна (на этапах извлечения, преобразования, загрузки) и сохраняются вместе с идентификатором прогона (run_id), датой и именем пайплайна/задачи для последующего анализа и сравнения.

---

## 5.4.2. Счётчики обработанных и отклонённых записей

**Базовые счётчики** — количество записей на каждом этапе.

**На этапе извлечения:**

- Записей прочитано из источника (по таблице, по источнику, по партиции).
- Записей с дубликатами по ключу (если проверка выполнялась).
- Сравнение с ожиданием или с количеством в источнике (для проверки полноты).

**На этапе преобразования:**

- Записей на входе (передано из извлечения).
- Записей принято (прошли все правила валидации и переданы на загрузку).
- Записей отклонено — в целом и **по каждому правилу валидации** (например: правило «статус из справочника» — 10 отклонённых; правило «дата в границах» — 2 отклонённых). Это позволяет видеть, какое правило даёт основной объём отклонений.
- Записей в карантин (если политика — карантин).

**На этапе загрузки:**

- Записей передано на загрузку.
- Записей успешно записано в целевую таблицу.
- Записей отклонено при загрузке (ошибка ограничения СУБД) — в целом и при возможности по типу ошибки (FK, уникальность, CHECK и т.д.).
- Записей в карантин загрузки (если используется).

Итоговая проверка полноты: число записей, извлечённых из источника, сопоставляется с числом записей, в конечном счёте загруженных в цель (с учётом допустимых отклонений по правилам). Расхождение сверх допустимого — повод для алерта и разбора.

---

## 5.4.3. Сравнение с предыдущим прогоном

**Сравнение с предыдущим прогоном** помогает выявить аномалии без жёстко заданных порогов.

- **Объём извлечённых записей:** резкое падение (например, в два раза или до нуля) или резкий рост (в разы) по сравнению с предыдущим успешным прогоном может указывать на неполноту выгрузки, сбой водяного знака или на изменение в источнике. Порог или кратность изменения (например, отклонение более чем на 20%) задаётся по критичности.
- **Объём отклонённых при преобразовании:** рост доли отклонённых (или абсолютного числа при стабильном объёме входа) указывает на ухудшение качества источника или на ужесточение/ошибку правил. Алерт при превышении порога (например, доля отклонённых выше 5% или выше в 1.5 раза, чем в предыдущем прогоне).
- **Объём загруженных записей:** сравнение с числом переданных на загрузку (должно совпадать при отсутствии отклонений при загрузке); сравнение с предыдущим прогоном для одной и той же таблицы — выявление аномального падения или роста.

Сравнение требует хранения метрик предыдущих прогонов (в таблице метаданных, в логах оркестратора, в системе метрик). Идентификатор прогона и дата позволяют однозначно связать метрики с run.

## 5.4.4. Отчётность по качеству

**Отчётность по качеству** — сводные представления метрик для оперативного контроля и для отчётности перед заказчиком или аудитом.

- **Дашборд по прогону:** для каждого run — статус пайплайна, длительность, счётчики по этапам (извлечено, принято при преобразовании, отклонено по правилам, загружено, отклонено при загрузке). Позволяет быстро оценить результат последнего прогона.
- **Тренды:** графики объёма извлечённых, загруженных и отклонённых записей по дням/прогонам; доля отклонённых при преобразовании по правилам. Выявление деградации качества источников или эффективности правил.
- **Сводка по правилам валидации:** сколько записей отклонено по каждому правилу за период (день, неделя); топ правил по числу отклонений. Основа для приоритизации доработки правил и работы с источниками.
- **Аудит:** по запросу — какие записи попали в карантин за период, по каким причинам; сколько записей не загрузилось при загрузке и по каким ошибкам. Поддержка расследования инцидентов и требований соответствия.

Источник данных для отчётности — накопленные метрики (таблица метаданных ETL, логи, экспорт в систему метрик или в DWH). Частота отчётности (реальное время, ежедневная сводка) задаётся потребностями операционной работы и управления.

---

## 5.4.5. Где хранить метрики

Метрики качества могут храниться:

- **В оркестраторе:** переменные задачи (XCom в Airflow и аналоги), логи с структурированным выводом счётчиков. Оркестратор даёт привязку к run_id и задаче; для долгосрочных трендов и отчётности может потребоваться экспорт в хранилище.
- **В таблице метаданных ETL:** отдельная таблица в DWH или в служебной БД с полями: run_id, дата, пайплайн, задача, этап, метрика (имя), значение. Каждый прогон добавляет строки; запросы и дашборды строятся по этой таблице.
- **В системе метрик (Prometheus, облачные метрики):** счётчики и gauge с тегами (pipeline, task, rule); хранение с временными рядами, удобно для графиков и алертов по порогам.
- **В логах:** структурированные логи (JSON) с полями run_id, task, extracted_count, rejected_count и т.д.; при централизованном сборе логов — запросы и агрегации для отчётности. Может дублировать таблицу метаданных для надёжности.

Выбор зависит от имеющегося стека и от того, кто потребляет отчётность (оркестратор, BI-инструмент, отдельная отчётная система).

## 5.4.6. Типичные ошибки

- **Не собирать счётчики по правилам валидации:** только общее «принято/отклонено» не показывает, какое правило даёт основной объём отклонений. Для управляемого качества нужна разбивка по правилам.
- **Не сохранять метрики между прогонами:** без хранения истории невозможно сравнение с предыдущим прогоном и тренды. Минимум — таблица метаданных или экспорт в систему метрик с привязкой к run_id и дате.
- **Не использовать метрики для алертов:** собранные счётчики не используются для порогов и оповещений — аномалии обнаруживаются с опозданием. Настроить алерты на нулевой объём, на превышение доли отклонённых, на резкое отклонение от предыдущего прогона.
- **Смешивать метрики качества и метрики производительности:** длительность задачи и объём записей — разные оси; и те и другие важны, но для качества критичны счётчики принятых/отклонённых и их тренды. Не подменять отчётность по качеству только метриками «время выполнения».

---

## Ключевое

- **Метрики качества** в пайплайне: счётчики обработанных и отклонённых записей на этапах извлечения, преобразования и загрузки; по правилам валидации — сколько отклонено по каждому правилу.
- **Сравнение с предыдущим прогоном** выявляет аномалии (резкое падение или рост объёма, рост доли отклонённых); требует хранения метрик с привязкой к run_id и дате.
- **Отчётность по качеству:** дашборд по прогону, тренды объёмов и отклонений, сводка по правилам валидации, аудит карантина и ошибок загрузки. Источник — таблица метаданных ETL, система метрик или структурированные логи.
- Метрики используются для алертов (пороги по объёму и доле отклонённых) и для управления качеством источников и правил.
