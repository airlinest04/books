# §4.3 Зависимости между задачами

В [§4.2](chapter-04-02.md) мы разобрали, что оркестратор запускает задачи по расписанию и зависимостям, а исполнители выполняют работу с данными. **Зависимости между задачами** задают порядок выполнения: какая задача после какой должна запускаться, чтобы данные были готовы ко времени следующего шага и не нарушалась целостность (например, загрузка фактов только после загрузки измерений). В этом разделе мы разберём порядок загрузки слоёв и таблиц, перезапуск при сбое и связь с идемпотентностью. Мониторинг и оповещения — в [§4.4](chapter-04-04.md). См. [Глоссарий](glossary.md).

---

## 4.3.1. Граф зависимостей (DAG)

Пайплайн в оркестраторе представляется как **граф задач**: узлы — задачи, рёбра — зависимости «задача B после задачи A». Обычно граф **направленный и ациклический** (DAG — Directed Acyclic Graph): нет циклов, чтобы не было бесконечного ожидания. Задача запускается только когда **все её предшественники** (upstream) успешно завершились (или выполнены с допустимым статусом по настройкам оркестратора). См. [Глоссарий](glossary.md).

Пример простого DAG для ETL:

- Задача «Extract_source_A» → задача «Transform_A» → задача «Load_staging_A».
- Задача «Extract_source_B» → задача «Transform_B» → задача «Load_staging_B».
- Задачи «Load_staging_A» и «Load_staging_B» → задача «Load_Core» (объединённый слой Core после стейджинга).
- Задача «Load_Core» → задача «Build_mart_sales» (витрина продаж).

Параллельно могут выполняться независимые ветки (например, Extract и Transform для источника A и для источника B — если между ними нет зависимости). Задача «Load_Core» ждёт оба стейджинга; «Build_mart_sales» ждёт «Load_Core».

Оркестратор при каждом запуске пайплайна (run) обходит граф и ставит в очередь те задачи, у которых все зависимости удовлетворены; завершённые задачи разблокируют следующие.

## 4.3.2. Порядок загрузки слоёв и таблиц

Зависимости должны отражать **реальные зависимости данных** и целостность:

- **Слои Raw → Staging → Core → Mart:** загрузка в Staging зависит от наличия данных в Raw (или от задач извлечения, пишущих в Raw); построение Core зависит от Staging; построение витрин (Mart) — от Core. В графе: задачи загрузки Raw (или извлечения в Raw) → задачи построения Staging → задачи построения Core → задачи построения витрин.
- **Измерения до фактов:** при загрузке в DWH с ссылочной целостностью (внешние ключи) измерения (справочники, размерности) должны быть загружены раньше фактов. Иначе вставка фактов со ссылками на ещё не загруженные измерения приведёт к ошибке. В графе: задачи загрузки измерений → задачи загрузки фактов.
- **Внутри слоя:** при взаимозависимых таблицах (редко) или при явном порядке (например, справочник регионов до справочника городов) зависимости задаются между задачами загрузки этих таблиц.

Типичный порядок для классического ETL в DWH:

1. Извлечение из всех источников (может быть параллельно по источникам).
2. Преобразование и загрузка в стейджинг (или Raw) — по потокам.
3. Загрузка измерений в DWH (можно параллельно по таблицам, если нет ссылок между ними).
4. Загрузка фактов в DWH (после измерений).
5. Построение витрин и агрегатов (после Core/фактов).

Оркестратор не «знает» семантику (что такое измерение или факт); он только соблюдает объявленные зависимости. Проектировщик пайплайна обязан задать зависимости так, чтобы порядок выполнения соответствовал порядку данных ([§2.4.7](chapter-02-04.md)).

## 4.3.3. Перезапуск при сбое

При падении одной из задач оркестратор может:

- **Retry (повторная попытка):** запустить ту же задачу ещё раз (с ограничением по числу попыток и, при необходимости, с задержкой). Уместно при временных сбоях (сеть, таймаут). Если задача идемпотентна, повторный запуск с теми же входами даёт корректный результат.
- **Перезапуск подграфа (downstream):** перезапустить упавшую задачу и все задачи, зависящие от неё (все последующие по графу). Предшественники не перезапускаются; предполагается, что они уже успешно выполнились и их результат пригоден. Идемпотентность последующих задач критична: они снова прочитают те же данные и перезапишут/обновят целевые таблицы без дубликатов и противоречий.
- **Полный перезапуск пайплайна:** перезапустить все задачи с начала. Требует идемпотентности всех шагов; иначе повторное извлечение и загрузка могут создать дубликаты или конфликты. Часто используется при редких «жёстких» сбоях, когда перезапуск подграфа недостаточен (например, подозрение на повреждённые данные в промежуточном слое).

Политика (retry count, перезапуск подграфа vs полный перезапуск) настраивается в оркестраторе. Без идемпотентности задач перезапуск рискован; с идемпотентностью перезапуск — штатный способ восстановления после сбоя ([§2.5.4](chapter-02-05.md)).

## 4.3.4. Идемпотентность в контексте графа

**Идемпотентность** задачи означает: повторное выполнение с теми же входными данными и контекстом даёт тот же результат и не портит состояние целевых таблиц. В контексте зависимостей это важно по двум причинам. См. [Глоссарий](glossary.md).

1. **Перезапуск при сбое:** оркестратор перезапускает задачу или подграф; задачи выполняются повторно. Если загрузка не идемпотентна (например, простой INSERT без проверки дубликатов), повторный запуск создаст дубликаты. Идемпотентная загрузка (полная перезапись партиции, MERGE/upsert по ключу) при повторном запуске приведёт целевые таблицы к тому же состоянию, что и при первом успешном выполнении.
2. **Один и тот же вход от предшественника:** при перезапуске только downstream предшественники не перезапускаются; следующие задачи снова читают выход предшественников (например, те же таблицы стейджинга). Если предшественник идемпотентен, его выход не изменился; если и следующая задача идемпотентна, повторное выполнение безопасно.

Рекомендация: при проектировании пайплайна закладывать идемпотентность на этапе загрузки ([§2.4.5](chapter-02-04.md)) и, где применимо, на этапе преобразования (детерминированность); тогда оркестратор может свободно использовать retry и перезапуск подграфа без риска порчи данных.

## 4.3.5. Типичные ошибки

- **Задать зависимости в обратном порядке:** например, факты до измерений — загрузка фактов упадёт из-за нарушения внешнего ключа. Зависимости должны соответствовать порядку данных и ограничениям целевых таблиц.
- **Не учитывать параллелизм:** несколько задач пишут в одну таблицу без координации — возможны блокировки, дедлоки или гонки. Либо одна задача на таблицу, либо явное разделение (разные партиции, разные ключевые диапазоны) и идемпотентная загрузка.
- **Перезапускать без идемпотентности:** при неидемпотентных задачах перезапуск подграфа или полный перезапуск приведёт к дубликатам или неконсистентному состоянию. Сначала обеспечить идемпотентность загрузки и преобразований, затем полагаться на перезапуск.
- **Забыть про «скрытые» зависимости:** например, витрина зависит от двух таблиц Core; в графе должна быть зависимость от обеих. Если зависимость от одной таблицы не указана, оркестратор может запустить построение витрины до готовности второй таблицы.

---

## Ключевое

- Зависимости между задачами задают **порядок выполнения**; граф задач — DAG (направленный ациклический граф). Задача запускается только после успешного завершения всех предшественников.
- **Порядок загрузки:** Raw/извлечение → Staging → Core (измерения, затем факты) → витрины. Зависимости в оркестраторе должны соответствовать этому порядку и ссылочной целостности.
- **Перезапуск при сбое:** retry задачи, перезапуск подграфа (упавшая и все следующие) или полный перезапуск пайплайна. Выбор зависит от политики и от того, насколько надёжны предшественники.
- **Идемпотентность** задач делает перезапуск безопасным: повторное выполнение не создаёт дубликатов и не портит данные. Без идемпотентности перезапуск рискован.

В [§4.4](chapter-04-04.md) мы разберём мониторинг и оповещения: успех/неудача, длительность, объём данных, алерты и логи.
