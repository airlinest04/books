# §2.1 Извлечение (Extract)

В [§1.4](chapter-01-04.md) мы сформулировали критерии успешного ETL. Теперь переходим к детальному разбору этапов: в этой главе — извлечение, преобразование, загрузка и их связь в пайплайне. Начнём с **извлечения (Extract)**: как читать данные из разных типов источников, когда применять полную и инкрементальную выгрузку, как идентифицировать изменения (даты, хеши) и какие форматы и сжатие использовать. От корректного извлечения зависят полнота и своевременность данных в целевом хранилище. Механизмы выявления изменений в источнике (CDC) разбираются в [§2.2](chapter-02-02.md). См. [Глоссарий](glossary.md).

---

## 2.1.1. Типы источников и способы доступа

Этап извлечения читает данные из **источников**. Тип источника определяет протокол доступа, формат данных и ограничения (размер выборки, блокировки, доступность по расписанию). Ниже — основные типы и типичные способы извлечения.

**Реляционные базы данных (RDBMS):** PostgreSQL, Oracle, SQL Server, MySQL и др. Данные организованы в таблицах со схемой (столбцы, типы, ключи). Доступ — по протоколам JDBC, ODBC или нативным драйверам; ETL выполняет SQL-запросы (SELECT) или использует утилиты выгрузки (pg_dump, expdp и т.п.). Важно: не блокировать операционную систему надолго; для больших таблиц — выборка батчами (pagination), использование индексов по полям фильтрации и учёт пиков нагрузки на источник. См. [Глоссарий](glossary.md).

**Файлы:** CSV, JSON, XML, Parquet, ORC, фиксированная ширина полей. Файлы могут находиться в локальной или сетевой файловой системе, в объектном хранилище (S3, Azure Blob, MinIO). Извлечение — чтение файла целиком или потоковое чтение; при появлении новых файлов (по расписанию или по событию) ETL обрабатывает только новые или непрочитанные. Нужно задать кодировку (UTF-8, Windows-1251 и др.), разделители, наличие заголовка и правила обработки битых строк.

**Веб-API (REST, SOAP, GraphQL):** данные возвращаются по HTTP-запросу в формате JSON, XML и т.д. Извлечение — вызов эндпоинта с параметрами (даты, пагинация), разбор ответа и при необходимости обход страниц (pagination). Учитываются лимиты запросов (rate limit), таймауты, аутентификация (API key, OAuth) и нестабильность сети (повторные попытки, экспоненциальная задержка).

**Очереди сообщений и потоки событий:** Kafka, RabbitMQ, Amazon SQS, Azure Event Hubs. Данные приходят в виде сообщений; ETL (или потоковый консьюмер) читает из топика/очереди, при необходимости накапливает в буфер и передаёт на этап преобразования или сохраняет в стейджинг/озеро для последующей пакетной обработки. Важны позиция чтения (offset), идемпотентность обработки и обработка дубликатов сообщений.

**Прочие источники:** NoSQL-хранилища (MongoDB, Cassandra) — доступ через специфичные драйверы и запросы; электронная почта (вложения); FTP/SFTP; веб-скрапинг (как крайняя мера, с учётом прав и стабильности структуры страниц). Для каждого типа выбирается подходящий коннектор или скрипт извлечения.

Сводка по типам источников и способам доступа:

| Тип источника | Типичный доступ | Особенности извлечения |
|---------------|-----------------|------------------------|
| Реляционная БД | JDBC, ODBC, SQL SELECT | Батчи, индексы, минимизация блокировок; учёт нагрузки на OLTP |
| Файлы | Файловая система, S3-совместимый API | Кодировка, формат, обработка новых файлов, битые строки |
| REST/SOAP API | HTTP-клиент | Пагинация, rate limit, аутентификация, повторные попытки |
| Очереди/потоки (Kafka и др.) | Consumer, подписка на топик | Offset, батчирование, идемпотентность при повторной обработке |

## 2.1.2. Полная выгрузка

**Полная выгрузка** (full extract) — извлечение **всех** записей из таблицы, файла или API-набора за один прогон, без фильтрации по дате изменения или по признаку «новое/изменённое». Результат — полный снимок источника на момент извлечения. См. [Глоссарий](glossary.md).

Когда уместна полная выгрузка:

- **Первичная загрузка (initial load):** при первом запуске ETL или при подключении нового источника нужно перенести все исторические данные; полная выгрузка даёт полный снимок.
- **Небольшие объёмы:** справочники, небольшие таблицы (тысячи строк), где полное чтение выполняется быстро и не создаёт существенной нагрузки на источник.
- **Источник без поддержки инкремента:** нет полей «дата изменения» или «версия», нет доступа к логу транзакций для CDC; единственный вариант — каждый раз читать всё.
- **Требование «всегда полный срез»:** бизнес-правило предполагает, что целевая таблица каждый раз полностью перезаписывается снимком на дату (например, ежедневный полный снимок справочника).

Недостатки полной выгрузки при больших объёмах: длительное время выполнения, высокая нагрузка на источник и сеть, больший объём данных для передачи и последующего преобразования. Поэтому для больших таблиц часто переходят на инкрементальную выгрузку после первой полной загрузки.

Реализация: SQL без WHERE по полю изменений (или с минимальным фильтром по бизнес-признаку), чтение всего файла, вызов API без фильтра по дате. Результат полной выгрузки обычно передаётся на этап преобразования или сохраняется в стейджинг; на этапе загрузки в цель часто используется режим «полная перезапись» целевой таблицы или раздела (см. [§2.4](chapter-02-04.md)).

## 2.1.3. Инкрементальная выгрузка

**Инкрементальная выгрузка** (incremental extract) — извлечение только **новых или изменённых** записей с момента последнего успешного прогона (или за заданный период). Объём данных и нагрузка на источник меньше, чем при полной выгрузке; пайплайн выполняется быстрее. Для инкрементальной выгрузки нужен механизм определения изменений. См. [Глоссарий](glossary.md).

Условия применимости:

- В источнике есть поле (или комбинация полей), по которому можно однозначно отобрать «всё новое/изменённое с момента X»: дата/время модификации, монотонно растущий идентификатор (ID, последовательность), версия записи.
- Или доступен механизм **CDC (Change Data Capture)** — чтение лога транзакций, триггеры или сравнение снимков ([§2.2](chapter-02-02.md)).
- Значение «водяного знака» (последняя обработанная дата или ID) сохраняется между прогонами и используется в следующем запросе извлечения.

Типичная реализация:

1. Прочитать сохранённое значение водяного знака (например, `last_extract_ts` или `max_id`) из таблицы метаданных ETL или из конфигурации.
2. Выполнить запрос к источнику с фильтром: `WHERE modified_at > :last_extract_ts` (или `id > :last_max_id`).
3. Передать извлечённые записи на преобразование и загрузку.
4. После успешной загрузки обновить водяной знак (например, максимум `modified_at` или `id` среди извлечённых записей, или время окончания прогона).

Риски: пропуск записей при неоднозначном порядке (например, одна и та же дата модификации у нескольких строк — лучше использовать `>=` и исключать дубликаты на стороне загрузки или брать границу «строго до начала текущего прогона»); часы поясов и точность времени; сбой после извлечения, но до обновления водяного знака (при перезапуске возможно повторное извлечение одних и тех же записей — важна идемпотентность загрузки).

## 2.1.4. Идентификация изменений: даты, хеши, водяные знаки

Чтобы выполнять инкрементальную выгрузку, нужно **идентифицировать изменённые записи**. Основные подходы:

**Поле даты/времени модификации (modified_at, updated_at):** в источнике хранится время последнего обновления строки. ETL сохраняет «последнюю обработанную метку» (watermark) и при следующем прогоне запрашивает `WHERE modified_at > :watermark`. Плюсы: простота, не требует изменений в источнике, если поле уже есть. Минусы: точность (одна и та же секунда у нескольких строк), часовые пояса; обновление поля должно быть обязательным при любом изменении строки (триггер или дисциплина в приложении). См. [Глоссарий](glossary.md).

**Монотонно растущий идентификатор (id, sequence):** подходит для таблиц, где новые записи только добавляются (append-only) и имеют возрастающий ID. Водяной знак — последний обработанный `max_id`; запрос `WHERE id > :last_max_id`. Не подходит для обновлений и удалений: изменённые записи не получат новый ID и не попадут в выборку.

**Хеш строки (hash of row):** при каждой выгрузке вычисляется хеш от ключевых полей (или всей строки) и сравнивается с сохранённым значением из предыдущего прогона. Позволяет обнаружить изменения даже без поля `modified_at`, но требует хранения хешей и либо полного чтения (с последующим сравнением), либо поддержки в источнике (например, вычисляемый столбец). Часто используется для проверки целостности после извлечения или для детекции изменений при сравнении двух снимков (см. CDC в [§2.2](chapter-02-02.md)).

**Водяной знак (watermark):** значение границы, до которой данные считаются обработанными. Сохраняется в метаданных ETL после успешного прогона; при следующем запуске извлекаются только данные «после» этой границы. Для даты — момент времени; для ID — последний обработанный идентификатор. Критично хранить водяной знак надёжно и обновлять только после успешной загрузки в цель, иначе возможны потери или дубликаты.

Краткая сводка:

| Способ | Применимость | Плюсы | Минусы |
|--------|--------------|-------|--------|
| Поле даты модификации | Таблицы с updated_at/modified_at | Простота, стандартная практика | Точность, часовые пояса, нужна дисциплина обновления |
| Растущий ID | Append-only таблицы | Простота, нет дубликатов по ID | Не ловит обновления и удаления |
| Хеш строки | Любая таблица | Выявление изменений без special-полей | Нужно хранить хеши или читать полный снимок для сравнения |
| CDC (лог, триггеры) | При поддержке в источнике | Точный список изменений, минимум нагрузки | Сложность настройки, зависимость от СУБД/инструмента |

## 2.1.5. Форматы данных и сжатие

Извлечённые данные имеют **формат** (структура представления) и нередко хранятся или передаются в **сжатом** виде. Выбор формата и сжатия влияет на объём, скорость чтения/записи и совместимость с этапом преобразования и целевым хранилищем.

**Текстовые форматы:**

- **CSV (разделённые запятыми/точкой с запятой):** плоская таблица, одна строка — одна запись; разделитель полей и строк задаётся. Плюсы: простота, читаемость, широкая поддержка. Минусы: нет явных типов, вложенные структуры неудобны, экранирование кавычек и разделителей в данных.
- **JSON:** иерархическая структура (объекты, массивы); подходит для API и полуструктурированных данных. Плюсы: гибкость, распространённость. Минусы: избыточность (повтор имён полей), парсинг тяжелее, чем у плоских форматов.
- **XML:** иерархия с тегами; часто в legacy-системах и SOAP. Плюсы: строгая структура, схемы (XSD). Минусы: объёмный, сложнее парсить.

**Бинарные и колоночные форматы (часто для стейджинга и озера):**

- **Parquet, ORC:** колоночное хранение, эффективное сжатие и быстрые агрегации по столбцам; типичны для больших данных и озёр. При извлечении из БД данные могут конвертироваться в Parquet при записи в стейджинг или озеро.
- **Avro:** строковый бинарный формат с явной схемой; удобен для потоков и совместимости версий схемы.

**Сжатие:** уменьшает объём при хранении и передаче. Типичные алгоритмы: gzip, snappy, LZ4, zstd. Выбор зависит от компромисса «степень сжатия / скорость распаковки» и от поддержки в целевом движке (например, многие системы умеют читать Parquet с Snappy). При извлечении в файлы сжатие часто включают по умолчанию; при потоковой передаче между этапами — по необходимости.

**Кодировка:** для текстовых форматов необходимо задать кодировку (UTF-8 рекомендуется для единообразия). Неверная кодировка приводит к искажению символов при чтении; при наличии legacy-источников в Windows-1251 или другой кодировке нужно явно указывать её при извлечении и при необходимости конвертировать в UTF-8 на этапе преобразования.

## 2.1.6. Согласованность среза при извлечении из нескольких объектов

Если один ETL-процесс извлекает данные из **нескольких таблиц** или **нескольких источников**, важно обеспечить **согласованность среза**: все данные должны относиться к одному и тому же логическому моменту времени. Иначе связи между таблицами (например, факты и измерения) могут быть несогласованными: факт ссылается на версию измерения из другого момента.

Варианты:

- **Транзакционная согласованность:** в источнике, поддерживающем транзакции, извлечение выполняется в одной транзакции с уровнем изоляции, дающим снимок на момент начала (например, repeatable read или snapshot). Все запросы внутри транзакции видят согласованное состояние.
- **Временная метка:** все таблицы выгружаются «по состоянию на» одну и ту же метку (например, 00:00 дня). В источниках с полем «дата/время среза» или при поддержке point-in-time recovery можно запрашивать срез на эту метку.
- **Порядок извлечения:** при отсутствии единого снимка задаётся порядок (сначала справочники, затем факты) и минимальная задержка между выгрузками; полной согласованности это не гарантирует, но снижает расхождения.
- **Один источник — один прогон:** каждый источник выгружается в отдельном прогоне с фиксацией времени среза; последующее объединение в преобразовании использует метки среза и правила сопоставления по времени.

Проверки полноты извлечения (счётчики строк, сверка с источником) рассматриваются в [§5.1](chapter-05-01.md).

## 2.1.7. Обработка ошибок на этапе извлечения

На этапе извлечения возможны сбои: недоступность источника, таймаут, неверные учётные данные, битый файл, изменение формата API. Рекомендуемые практики:

- **Повторные попытки (retry):** при временных сбоях (сеть, кратковременная недоступность) — ограниченное число попыток с увеличивающейся задержкой (exponential backoff), чтобы не перегружать источник.
- **Логирование и алерты:** фиксировать код ошибки, сообщение, источник и шаг; при критичных ошибках — оповещение ответственных. Это обеспечивает наблюдаемость ([§1.4](chapter-01-04.md)).
- **Частичный успех:** при извлечении из нескольких источников или файлов решить, останавливать ли весь прогон при ошибке одного или продолжать с пометкой неполноты. Решение должно быть явным и согласованным с требованиями к полноте.
- **Валидация «на входе»:** проверка формата и минимальной структуры данных сразу после чтения (наличие обязательных полей, тип файла) позволяет рано обнаружить повреждённые или неожиданные данные и не передавать их на преобразование.

## 2.1.8. Типичные ошибки при извлечении

- **Игнорировать нагрузку на источник:** тяжёлые полные выгрузки в часы пик OLTP могут замедлять операционную систему. Следует планировать извлечение в окна с низкой нагрузкой или использовать инкрементальную выгрузку и батчи.
- **Некорректный водяной знак:** обновление водяного знака до успешной загрузки в цель ведёт к потере данных при сбое; использование «строго больше» при неоднозначном порядке может пропускать записи. Нужны однозначные правила и сохранение водяного знака только после успешного завершения загрузки.
- **Не задать кодировку и формат файла:** неверная кодировка или разделитель при чтении CSV/текста даёт искажённые данные. Всегда явно указывать кодировку и параметры формата.
- **Не проверять полноту:** отсутствие сверки количества извлечённых записей с ожиданием или с источником маскирует частичную выгрузку. Минимум — логировать и сравнивать счётчики строк.
- **Смешивать срезы разных моментов:** при нескольких таблицах/источниках без согласованного среза связи между данными могут быть некорректны. Нужна явная стратегия согласованности среза.

## Ключевое

- **Типы источников:** реляционные БД (JDBC/SQL), файлы (CSV, JSON, Parquet и др.), веб-API (REST с пагинацией), очереди и потоки (Kafka и др.); от типа зависят протокол доступа и форматы.
- **Полная выгрузка** — извлечение всех записей за прогон; уместна для первичной загрузки, малых объёмов и источников без поддержки инкремента.
- **Инкрементальная выгрузка** — только новые/изменённые записи; требует механизма идентификации изменений (поле даты, ID, хеш, CDC) и хранения водяного знака.
- **Идентификация изменений:** поле даты модификации, монотонно растущий ID, хеш строки, CDC; водяной знак хранится между прогонами и обновляется после успешной загрузки.
- **Форматы и сжатие:** текстовые (CSV, JSON, XML), колоночные (Parquet, ORC); сжатие (gzip, snappy и др.) и явная кодировка (UTF-8) для текста.
- **Согласованность среза:** при извлечении из нескольких таблиц/источников — транзакционный снимок, общая метка времени или явный порядок и правила.
- Ошибки извлечения обрабатываются повторными попытками, логированием и алертами; полнота проверяется счётчиками и сверками.

В [§2.2](chapter-02-02.md) мы разберём CDC (Change Data Capture): выявление изменений через лог транзакций, триггеры и сравнение снимков для инкрементальной загрузки.
