# §9.4 Архитектура: стриминг, DWH и витрины

В [§9.1](chapter-09-01.md)–[§9.3](chapter-09-03.md) мы разобрали события и стриминг, данные для антифрода и скоринга заявок. В этом разделе — **архитектура**: как **стрим и DWH дополняют друг друга**, **синхронизация** данных между контурами и различие **витрин реал-тайм** и **исторических**. Материал обобщает главу 9 и связывает её с главами 4 (модели и витрины) и 6 (пайплайн отчётности). Приложения книги: [Глоссарий](glossary.md) и список литературы. См. [Глоссарий](glossary.md).

---

## 9.4.1. Как стрим и DWH дополняют друг друга

**Стрим** — поток событий в реальном времени (транзакции, заявки, логины); обработка по мере поступления для антифрода, скоринга, алертов. **DWH** — хранилище с историей событий, снимками на дату и витринами для отчётности, регуляторики и аналитики; загрузка обычно батчами по расписанию. См. [§9.1](chapter-09-01.md), [§4.4](chapter-04-04.md).

**Взаимодополнение:**

- **Стрим даёт скорость реакции:** решение по транзакции или заявке принимается до или сразу после операции; без стрима реал-тайм антифрод и скоринг невозможны. См. [§9.2](chapter-09-02.md), [§9.3](chapter-09-03.md).

- **DWH даёт полноту и контекст:** полная история операций, согласованность с бухучётом, снимки на отчётную дату, витрины для форм ЦБ и для аналитики. Регуляторная отчётность и сверка строятся на DWH, а не на сыром потоке. См. [§5.3](chapter-05-03.md), [§6.1](chapter-06-01.md), [§4.2](chapter-04-02.md).

- **Стрим питает DWH:** события из потока (транзакции, заявки, решения) могут записываться в DWH батчами или через коннекторы (Kafka → DWH): один и тот же факт сначала обрабатывается в стриме для реал-тайм решения, затем попадает в DWH для истории и витрин. См. [§4.4](chapter-04-04.md), [§9.1](chapter-09-01.md).

- **DWH питает стрим:** для обогащения события в стриме нужны данные о клиенте, портфеле, лимитах; они поднимаются из кэша или быстрого слоя, синхронизированного с DWH (или из API витрин). См. [§9.2](chapter-09-02.md), [§9.3](chapter-09-03.md).

Итоговая схема: операционные системы публикуют события в брокер (Kafka и аналоги); потребители стрима — антифрод, скоринг, алерты — обрабатывают события, при необходимости запрашивая данные из кэша/DWH; те же события (или подтверждённые факты из операционок) загружаются в DWH батчами; в DWH строятся витрины и отчёты; обратная связь (исход операций, просрочка, оспаривания) накапливается в DWH и используется для переобучения моделей. См. задание к главе 9 в TOC: «схема стрим + DWH». См. [§9.2](chapter-09-02.md), [§9.3](chapter-09-03.md).

## 9.4.2. Синхронизация

**Синхронизация** между стримом и DWH — обеспечение согласованности: данные, которые стрим-обработчик использует для обогащения (портфель клиента, лимиты), должны быть достаточно актуальны относительно DWH; события, попавшие в стрим, в итоге должны оказаться в DWH без потерь и с корректной привязкой к сущностям. См. [§9.3](chapter-09-03.md).

**Направления синхронизации:**

- **DWH → кэш/реал-тайм слой:** витрины или срезы по клиенту/карте обновляются в кэше (или в быстром хранилище) с заданной частотой (каждый час, каждые 15 минут, по триггеру после загрузки). Задержка определяет, насколько «свежие» данные видит антифрод и скоринг. См. [§9.2](chapter-09-02.md), [§9.3](chapter-09-03.md).

- **Стрим → DWH:** события из Kafka (или из операционок после обработки стримом) загружаются в DWH по расписанию или потоково (Kafka Connect, ETL). Важны идемпотентность (повторная загрузка того же события не дублирует запись), ключи (transaction_id, application_id) и порядок загрузки (сначала справочники и факты, затем витрины). См. [§4.4](chapter-04-04.md), [§6.1](chapter-06-01.md).

- **Обратная связь:** решения антифрода и скоринга, оспаривания, просрочка — фиксируются в операционках и в DWH; модели переобучаются на батчевых срезах из DWH. Цикл замыкается: реал-тайм решения → факты в DWH → витрины и разметка → переобучение → обновлённые модели в стриме. См. [§9.2](chapter-09-02.md), [§9.3](chapter-09-03.md).

## 9.4.3. Витрины реал-тайм и исторические

**Исторические витрины** — витрины в DWH: снимки на дату (портфель кредитов, портфель карт), таблицы событий (транзакции, движения по кредитам), агрегаты за период. Строятся батчами после загрузки данных на отчётную дату; используются для отчётности, регуляторики, аналитики и для обучения моделей. См. [§4.2](chapter-04-02.md), [§5.3](chapter-05-03.md).

**Витрины реал-тайм** — агрегаты и срезы, обновляемые по мере поступления событий (или с малой задержкой): например, «последние N транзакций по карте», «сумма операций за последний час по клиенту», «текущий лимит и использование по договору». Хранятся в быстром хранилище (кэш, ключ-значение, оперативная БД) или вычисляются в стриме (окна, агрегаты в памяти). Не заменяют исторические витрины для отчётности: отчётность требует согласованности с бухучётом и срезов на фиксированную дату, что обеспечивает DWH. См. [§9.1](chapter-09-01.md), [§9.2](chapter-09-02.md).

**Разделение ответственности:** реал-тайм витрины — для решений в потоке (антифрод, скоринг, лимиты); исторические витрины — для отчётов, сверки, ретроспективы и обратной связи. Данные в реал-тайм витрине и в исторической за один и тот же период в момент обновления могут различаться (батч ещё не загружен); после загрузки батча историческая витрина становится эталоном для отчётности. См. [§6.2](chapter-06-02.md), [§4.1](chapter-04-01.md).

## Ключевое

- **Стрим и DWH дополняют друг друга:** стрим — скорость реакции (антифрод, скоринг); DWH — полнота истории, согласованность с бухучётом, витрины для отчётности и аналитики. События из стрима попадают в DWH; данные из DWH обогащают обработку в стриме через кэш или быстрый слой.
- **Синхронизация:** DWH → кэш для обогащения в стриме (с заданной частотой); стрим → DWH при загрузке событий (идемпотентность, ключи); обратная связь в DWH для переобучения моделей.
- **Витрины реал-тайм** — агрегаты и срезы для решений в потоке (последние транзакции, оборот за час, лимиты); **исторические витрины** — в DWH, батч, для отчётности и ретроспективы. Разделение ответственности: реал-тайм — для решений, исторические — для отчётов и эталона.
