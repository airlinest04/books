# §9.1 Тесты как таски в даге

В [§8.4](chapter-08-04.md) мы разобрали обнаружение регрессий и алерты при расхождении. Глава 9 посвящена **интеграции тестов с Apache Airflow** и пайплайном загрузки: как встроить проверки в даг так, чтобы тесты выполнялись после загрузки, падение теста влияло на статус дага и при необходимости вызывало уведомления. В этом разделе мы разберём размещение тестов как тасков в даге: зависимость «загрузка → тест», реализация через PythonOperator и BashOperator.

---

## 9.1.1. Тест после загрузки

Логика интеграции: **тесты данных выполняются после того, как данные загружены**. Проверки полноты (row count, контрольные суммы), целостности (нет сирот) и при необходимости регрессионные сравнения имеют смысл только по уже загруженным таблицам. Поэтому в даге загрузки тест ставится **после** тасков, которые выполняют загрузку (извлечение, преобразование, запись в приёмник).

Типичная цепочка: `extract >> transform >> load >> test`. Или при нескольких источниках: `[load_source_a, load_source_b] >> test` — тест запускается один раз после завершения всех загрузок. Если тест проверяет только один слой (например, staging после load), зависимость: `load_staging >> test_staging`. Если следом идёт загрузка в витрину: `load_staging >> load_mart >> test_mart` — тест витрины после загрузки витрины. См. [§1.4](chapter-01-04.md) и [Глоссарий](glossary.md) в контексте CI/CD и smoke.

Цель: при успешной загрузке тест проверяет данные; при падении теста даг помечается failed, последующие таски (если есть) не запускаются по умолчанию, и можно настроить уведомление (см. §9.2, §9.4).

---

## 9.1.2. Зависимость load >> test

В Airflow зависимости между тасками задаются оператором `>>` (и ему обратным `<<`): `task_a >> task_b` означает «task_b выполняется после успешного завершения task_a». Для теста после загрузки: `load_task >> test_task`.

Пример структуры дага (псевдокод):

```python
# Псевдокод дага: загрузка продаж за дату и тест после загрузки
load_sales = BashOperator(task_id='load_sales', ...)
test_row_count = PythonOperator(task_id='test_row_count', ...)
test_checksum = PythonOperator(task_id='test_checksum', ...)

load_sales >> test_row_count >> test_checksum
# или параллельно: load_sales >> [test_row_count, test_checksum]
```

Если тестов несколько, их можно объединить в цепочку (один за другим) или запускать параллельно (общий родитель — load, дети — тесты). При параллельном запуске падение одного теста помечает даг failed; остальные тесты при этом могут завершиться. Порядок «сначала все загрузки, потом все тесты» задаётся так: `[load_a, load_b] >> [test_1, test_2]` (при необходимости через пустой таск-барьер).

Передача контекста: дата или параметры загрузки (execution_date, логическая дата среза) обычно доступны в шаблоне Airflow (например, `{{ ds }}`). Тест-таск получает ту же дату из контекста дага и выполняет проверки за этот срез, чтобы не проверять «чужие» данные.

## 9.1.3. PythonOperator и BashOperator

**BashOperator** — выполнение одной команды или скрипта в shell. Удобен, когда тесты уже оформлены как скрипт (bash вызывает psql/sqlplus или pytest). Успех таска = код возврата 0; ненулевой код возврата (например, от pytest при падении теста) помечает таск failed.

Пример:

```python
test_task = BashOperator(
    task_id='test_staging_checks',
    bash_command='python /path/to/run_tests.py --date {{ ds }}',
    dag=dag,
)
```

Параметры (дата, подключение к БД) передаются через переменные окружения (в Airflow задаются через Connection или Variables) или аргументами скрипта. Скрипт `run_tests.py` подключается к БД, выполняет запросы проверки (row count, контрольная сумма) и завершается с кодом 0 при успехе и ненулевым при провале.

**PythonOperator** — выполнение Python-функции. Удобен, когда логика проверки пишется прямо в коде дага или в отдельном модуле. Функция получает контекст (например, `**kwargs` с execution_date); внутри — подключение к БД (из Connection), выполнение запросов, сравнение с эталоном или с ожиданием; при расхождении — выброс исключения (`raise ValueError(...)`), чтобы таск помечался failed.

Пример идеи:

```python
def run_data_checks(**context):
    ds = context['ds']  # логическая дата
    # подключение к БД, запросы row count и checksum
    # сравнение с ожиданием; при расхождении raise ValueError(...)

test_task = PythonOperator(
    task_id='test_staging_checks',
    python_callable=run_data_checks,
    provide_context=True,
    dag=dag,
)
```

Выбор между BashOperator и PythonOperator: если тесты живут в отдельном репозитории или запускаются через pytest/shell — BashOperator; если проверки встроены в код проекта и удобнее вызывать функцию — PythonOperator. В обоих случаях падение теста (ненулевой код возврата или исключение) переводит таск в состояние failed. В [§9.2](chapter-09-02.md) мы разберём условное продолжение при падении теста: поведение дага при failed тесте, алерт и остановка последующих тасков.

---

## Ключевое

- **Тест после загрузки:** тесты данных выполняются тасками, которые идут **после** тасков загрузки; зависимость задаётся через `load_task >> test_task` (и при нескольких загрузках — после всех нужных load).
- **Зависимость load >> test:** в Airflow задаётся оператором `>>`; дата/параметры среза берутся из контекста дага (например, `{{ ds }}`) и передаются в тест.
- **PythonOperator и BashOperator:** BashOperator запускает скрипт (pytest, psql, кастомный скрипт); успех = код 0. PythonOperator вызывает Python-функцию с контекстом; при провале — исключение. В обоих случаях падение теста помечает таск failed.

В [§9.2](chapter-09-02.md) мы разберём условное продолжение при падении теста: fail при падении, алерт и остановка последующих тасков.
