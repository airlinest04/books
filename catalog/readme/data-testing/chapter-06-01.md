# §6.1 Маппинг полей: до и после

В [§5.4](chapter-05-04.md) мы разобрали проверку бизнес-правил в SQL. Глава 6 посвящена **тестированию преобразований**: как убедиться, что данные при переходе из источника в приёмник (или при проходе через запрос/витрину) отображаются и преобразуются верно. Первый аспект — **маппинг полей**: соответствие «источник → приёмник», типы данных и правила преобразования. В этом разделе мы разберём, как описывать маппинг «до и после», как проверять соответствие полей и типов и как строить тесты маппинга.

---

## 6.1.1. Маппинг: источник, приёмник и правила

**Маппинг** (мы вводили его в §1.1) — соответствие полей источника полям приёмника и правила, по которым значение преобразуется: прямое копирование, приведение типа, формула, подстановка из справочника, объединение нескольких полей в одно. В тестировании преобразований важно зафиксировать для каждого поля приёмника: откуда берётся значение (какое поле или выражение источника), какой тип и какое правило преобразования применяется. См. [Глоссарий](glossary.md).

Пример описания маппинга (таблица «до и после»):

| Поле приёмника | Источник (до) | Правило преобразования | Тип приёмника |
|----------------|---------------|-------------------------|----------------|
| order_id | source.orders.id | как есть | INT |
| order_date | source.orders.created_at | дата без времени (DATE) | DATE |
| amount_rub | source.orders.amount, source.orders.currency | если currency='USD' — умножить на rate; иначе как есть | NUMERIC(12,2) |
| status_group | source.orders.status | CASE: 'new','pending'→'OPEN'; 'done','cancel'→'CLOSED' | VARCHAR(20) |

Такое описание служит и документацией, и основой для тестов: тест проверяет, что при заданном входе (фикстура «до») на выходе (результат «после») в приёмнике получаются ожидаемые значения по каждому полю или по ключевым полям.

---

## 6.1.2. Соответствие полей и типов

Проверка **соответствия полей** — что в приёмнике присутствуют все ожидаемые колонки и что каждая колонка заполняется из правильного источника (или выражения). В unit-тесте это проверяется на фикстуре: загружаем в источник (или в промежуточную таблицу) строки с известными значениями, выполняем преобразование (запрос или шаг ETL), сравниваем результат с эталонной таблицей «после» или с ожидаемыми значениями по полям.

Проверка **типов** — что значения в приёмнике имеют нужный тип и не теряются при приведении: число не обрезается, дата интерпретируется верно, строка не обрезается до нечитаемого вида. Типичные ошибки: источник отдаёт строку '2025-02-16', приёмник ожидает DATE — при неверном формате может получиться null или неверная дата; источник — целое больше 2^31, приёмник — INT — переполнение. В тесте маппинга можно включить строки с граничными значениями типов (максимальная длина строки, крайние даты, большие числа) и проверить, что результат совпадает с ожиданием и тип в приёмнике корректный.

На практике соответствие полей часто проверяют вместе с преобразованием: одна фикстура «до», эталон «после» по всем полям (или по ключевым); тест выполняет преобразование и сравнивает результат с эталоном. Если схема приёмника изменилась (добавлено/удалено поле), тест должен быть обновлён; при падении из-за отсутствия колонки или несовпадения типа причина видна по сообщению теста.

---

## 6.1.3. Тесты преобразований (правил маппинга)

**Тест маппинга** проверяет правило преобразования для одного или нескольких полей: при заданных входных значениях выходное значение совпадает с ожидаемым. Структура — та же Arrange–Act–Assert: фикстура «до» (исходная таблица или файл), выполнение преобразования (запрос INSERT…SELECT, ETL-шаг, представление), проверка «после» (сравнение с эталоном или утверждения по полям).

Что покрывать тестами:

- **Прямое копирование:** значение без изменений переносится в приёмник; тест с несколькими значениями (в т.ч. null, если допустимо) проверяет, что они не искажаются.
- **Приведение типа:** строка → число, строка → дата, число → строка с форматом; тест с типичными и граничными значениями (пустая строка, неверный формат — если обрабатываются, то ожидаемый результат или ошибка должны быть заданы).
- **Формула или выражение:** новое поле = f(source_col1, source_col2); тест с известными входными парами и ожидаемым выходом.
- **CASE / условная логика:** маппинг статуса, кода, группы; по одной строке фикстуры на каждую ветку условия и проверка итогового значения в приёмнике.
- **Подстановка из справочника:** значение источника заменяется по таблице соответствий (или джойну со справочником); тест с ключом, который есть в справочнике, и с ключом, которого нет (ожидаем null или значение по умолчанию).

Один тест может проверять весь маппинг одной таблицы (все поля) или разбиваться на несколько тестов по полям/правилам — в зависимости от сложности и желания локализовать падение. В §6.2 мы разберём тестирование агрегаций и расчётов: суммы, средние, группировка, сравнение с ожидаемым и учёт округления.

## 6.1.4. Пример: тест маппинга статуса

Правило: поле `status` источника (значения 'new', 'pending', 'done', 'cancelled') маппится в поле `status_group` приёмника: 'new' и 'pending' → 'OPEN', 'done' и 'cancelled' → 'CLOSED'. Остальные значения (если появятся) → 'UNKNOWN'.

Фикстура «до» (исходная таблица): 4 строки со статусами 'new', 'pending', 'done', 'cancelled'. Эталон «после»: 'OPEN', 'OPEN', 'CLOSED', 'CLOSED'. Тест загружает фикстуру, выполняет запрос преобразования (или шаг ETL), сравнивает `status_group` в результате с эталоном. Дополнительно можно добавить строку с status='unknown_value' и проверить, что status_group='UNKNOWN'.

Запрос преобразования (логика для теста):

```sql
SELECT id, status,
       CASE status
         WHEN 'new' THEN 'OPEN'
         WHEN 'pending' THEN 'OPEN'
         WHEN 'done' THEN 'CLOSED'
         WHEN 'cancelled' THEN 'CLOSED'
         ELSE 'UNKNOWN'
       END AS status_group
FROM source.orders;
```

Assertion: для каждой строки фикстуры значение `status_group` в результате совпадает с ожидаемым. Реализация — сравнение результата с эталонной таблицей (построчно или через EXCEPT/INTERSECT) или проверка выборочных строк по ключу. Такой тест ловит ошибку при изменении CASE (например, 'pending' случайно отнесли к 'CLOSED') и при добавлении нового статуса без обновления маппинга.

---

## Ключевое

- **Маппинг** задаёт для каждого поля приёмника источник, правило преобразования и тип; описание «до и после» (таблица полей и правил) служит основой для тестов.
- **Соответствие полей и типов** проверяется на фикстуре: результат преобразования сравнивается с эталоном «после»; при необходимости включают граничные значения типов (длина, даты, числа).
- **Тест маппинга** покрывает: прямое копирование, приведение типа, формулы, CASE/условия, подстановку из справочника; структура Arrange–Act–Assert, фикстура «до», проверка «после».
- Пример: маппинг статуса в группу (OPEN/CLOSED/UNKNOWN); фикстура по веткам CASE, assertion — совпадение status_group с эталоном; тест выявляет регрессии при изменении правил.

В [§6.2](chapter-06-02.md) мы разберём тестирование агрегаций и расчётов: сумма, среднее, группировка, сравнение с ожидаемым и округление.
