# §10.3 Интеграционные проверки ETL

В [§10.2](chapter-10-02.md) мы разобрали unit-тесты для преобразований. Следующий шаг — **интеграционные проверки ETL**: полный прогон пайплайна на тестовых данных (источник → staging → витрина) с последующей проверкой **row count**, **контрольных сумм** и **целостности**. В этом разделе мы применим схемы из глав 7 и 2 к пайплайну продаж из §10.1 и соберём конкретный набор проверок.

---

## 10.3.1. Сценарий интеграционного теста

**Сценарий:** в тестовой среде подготовлены данные источника (фикстура или снимок за тестовую дату); запускается полный ETL (извлечение, преобразование, загрузка в staging, построение витрины); после успешного завершения выполняются проверки по загруженным таблицам. См. [§2.2](chapter-02-02.md) и [§7.1](chapter-07-01.md).

Последовательность:

1. **Подготовка:** очистка тестовых таблиц staging и витрины за тестовую дату (или пересоздание схемы); загрузка фикстуры в источник (или использование уже подготовленного тестового источника за дату D).
2. **Запуск ETL:** выполнение дага или скриптов ETL с параметром даты D (один и тот же срез, что в фикстуре).
3. **Проверки:** запросы к staging и витрине за дату D — row count, контрольные суммы, при необходимости целостность (сироты, дубликаты). Сравнение с ожиданием (эталон посчитан по фикстуре или по источнику).
4. **Очистка (опционально):** удаление тестовых данных после прогона.

Для пайплайна из §10.1 проверяем: источник (source.sales за дату D) → staging.sales за дату D → mart.sales_daily за дату D. Ожидание — полное совпадение по количеству и суммам при отсутствии фильтрации и дедупликации по замыслу; при их наличии — явное правило (например, «в staging ровно столько строк, сколько в источнике за D»).

---

## 10.3.2. Row count

**Проверка row count** — количество строк в источнике за срез равно количеству строк в staging за тот же срез; при наличии витрины — количество строк в витрине за срез согласовано с ожиданием (число групп при агрегации). См. [§7.1](chapter-07-01.md).

Для примера (дата D):

- Источник: `SELECT COUNT(*) FROM source.sales WHERE sale_date = :D`
- Staging: `SELECT COUNT(*) FROM staging.sales WHERE sale_date = :D`
- Assertion: оба числа равны (или staging = источник при полной загрузке без фильтра).

Витрина mart.sales_daily: одна строка на (sale_date, region_id, product_id). Ожидаемое количество строк витрины за дату D = число уникальных комбинаций (sale_date, region_id, product_id) в staging за дату D. Проверка: `SELECT COUNT(*) FROM mart.sales_daily WHERE sale_date = :D` равно ожидаемому числу групп (посчитанному по фикстуре или по staging).

При расхождении на любом этапе интеграционный тест падает; разбор — по цепочке (источник → staging → витрина) и по логам ETL.

---

## 10.3.3. Контрольные суммы

**Контрольные суммы** — сравнение SUM по ключевым числовым полям между источником и staging и при необходимости между staging и витриной. См. [§7.2](chapter-07-02.md).

Для примера:

- Источник и staging: `SUM(amount)` за дату D (с учётом конвертации валюты, если она в ETL). Ожидание: совпадение (или явное правило, если часть строк отфильтровывается).
- Витрина: `SUM(sum_amount)` по mart.sales_daily за дату D должен равняться `SUM(amount)` по staging.sales за дату D. Assertion: равенство с допуском на округление (например, до 2 знаков).

При нескольких полях (amount, quantity и т.д.) считают несколько сумм; при расхождении любой из них тест падает. Для ускорения можно ограничиться одной-двумя ключевыми суммами, если row count уже проверен и логика агрегации покрыта unit-тестами.

---

## 10.3.4. Целостность

**Целостность** в контексте интеграционного теста — отсутствие сирот по внешним ключам и при необходимости отсутствие дубликатов по ключу в витрине. См. [§7.3](chapter-07-03.md) и [§5.3](chapter-05-03.md).

Для пайплайна продаж:

- **Сироты:** если staging.sales ссылается на справочники (region_id, product_id), проверка: нет строк в staging с region_id или product_id, отсутствующими в соответствующих справочниках. Запрос через LEFT JOIN / NOT EXISTS; ожидание — 0 сирот.
- **Дубликаты в витрине:** по (sale_date, region_id, product_id) должна быть ровно одна строка. Проверка: `COUNT(*) = COUNT(DISTINCT sale_date, region_id, product_id)` в mart.sales_daily за дату D.

Проверки целостности выполняются после шагов 1–3 (подготовка, ETL, row count и контрольные суммы); при ненулевом количестве сирот или при наличии дубликатов тест падает. В [§10.4](chapter-10-04.md) мы разберём регрессионные проверки витрины, smoke-проверки и интеграцию с Airflow.

---

## Ключевое

- **Интеграционный тест ETL:** полный прогон на тестовых данных (подготовка → ETL → проверки); проверки — row count, контрольные суммы, целостность по загруженным таблицам.
- **Row count:** источник и staging за срез совпадают; количество строк витрины за срез = ожидаемое число групп (по staging или по фикстуре).
- **Контрольные суммы:** SUM по ключевым полям в источнике и staging совпадают; SUM по витрине за срез совпадает с суммой по staging за тот же срез (с учётом округления).
- **Целостность:** нет сирот по FK в staging; нет дубликатов по ключу в витрине. Запросы из §5.3 и §7.3; assertion — 0 нарушений.

В [§10.4](chapter-10-04.md) мы разберём регрессионные проверки витрины, smoke-проверки и интеграцию с Airflow.
