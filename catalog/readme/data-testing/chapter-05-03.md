# §5.3 Референциальная целостность

В [§5.2](chapter-05-02.md) мы разобрали row count и контрольные суммы. Следующий тип assertions — **референциальная целостность**: каждая ссылка из дочерней таблицы на родительскую должна указывать на существующую строку родителя. Нарушение (запись-«сирота»: есть ссылка, но родителя нет) ведёт к ошибкам при джойнах и к неконсистентным отчётам. В этом разделе мы разберём, что такое сироты, как проверять выполнение референциальной целостности в SQL и как это связано с ограничениями внешнего ключа в СУБД.

---

## 5.3.1. Референциальная целостность и сироты

**Референциальная целостность** — свойство данных: для каждого значения внешнего ключа (FK) в дочерней таблице существует соответствующая запись в родительской таблице по первичному ключу (PK). Иначе говоря: нет «сирот» — записей в дочерней таблице, у которых ключ ссылается на несуществующую строку родителя. См. [Глоссарий](glossary.md).

Пример: таблица заказов `orders` с полем `customer_id`, таблица клиентов `customers` с первичным ключом `customer_id`. Целостность соблюдена, если у каждого заказа значение `customer_id` присутствует в `customers.customer_id`. Если в `orders` есть строка с `customer_id = 999`, а в `customers` нет строки с `customer_id = 999`, то эта запись заказа — **сирота** (orphan).

Почему сироты появляются:

- В источнике уже были некорректные данные; ETL не отфильтровал и не исправил их.
- Загрузка идёт в разном порядке: сначала заказы, потом клиенты — временно сироты есть; после полной загрузки проверка должна проходить.
- Ошибка в маппинге или в джойне при построении витрины: подставлен неверный идентификатор.
- Удаление или обновление в родителе без каскада: родитель удалён, дочерние записи остались со старым ключом.

Проверка референциальной целостности — assertion вида «количество сирот по связи X равно 0». Если тест или проверка после ETL находит сироты, данные считаются некорректными до исправления.

---

## 5.3.2. Проверка «нет сирот» в SQL

Проверить отсутствие сирот можно запросом: найти в дочерней таблице такие строки, для которых в родительской таблице нет записи с совпадающим ключом. Количество таких строк должно быть 0.

**Вариант 1: LEFT JOIN и фильтр по NULL.** Дочерняя таблица джойнится с родительской по ключу (LEFT JOIN). Там, где родителя нет, поля родителя будут NULL. Отбираем строки, где ключ родителя NULL — это и есть сироты.

Пример (PostgreSQL): заказы `orders` ссылаются на клиентов `customers`.

```sql
-- Количество сирот: заказы с customer_id, которого нет в customers
SELECT COUNT(*) AS orphan_count
FROM staging.orders o
LEFT JOIN staging.customers c ON c.customer_id = o.customer_id
WHERE c.customer_id IS NULL
  AND o.customer_id IS NOT NULL;  -- если NULL в FK допустим, не считаем сиротой
```

Assertion: `orphan_count = 0`. Условие `o.customer_id IS NOT NULL` нужно, если «заказ без клиента» (NULL в customer_id) допустим по бизнесу; тогда сиротой считаем только не-NULL значение, не найденное в родителе.

**Вариант 2: NOT EXISTS.** Для каждой строки дочерней таблицы проверяем, что в родителе есть строка с таким ключом.

```sql
SELECT COUNT(*) AS orphan_count
FROM staging.orders o
WHERE o.customer_id IS NOT NULL
  AND NOT EXISTS (
    SELECT 1 FROM staging.customers c WHERE c.customer_id = o.customer_id
  );
```

Ожидание: `orphan_count = 0`. NOT EXISTS часто эффективнее на больших таблицах при наличии индекса по ключу в родителе.

**Вариант 3: NOT IN.** Возможен, но при наличии NULL в колонке дочерней таблицы NOT IN даёт неожиданный результат (строка с NULL не попадёт в результат из-за семантики NOT IN с null). Лучше использовать LEFT JOIN или NOT EXISTS.

Для нескольких связей (несколько FK в одной таблице или цепочка таблиц) проверку делают отдельным запросом на каждую пару родитель–потомок. В интеграционном тесте после загрузки ETL запускают набор таких проверок; при хотя бы одной с ненулевым количеством сирот тест падает.

## 5.3.3. Внешние ключи в СУБД и проверки в тестах

В реляционной СУБД можно объявить **ограничение внешнего ключа** (FOREIGN KEY): при вставке или обновлении СУБД сама проверяет, что значение FK существует в родителе. Если ограничение включено и данные загружаются в такую таблицу, сироты не появятся — вставка упадёт с ошибкой.

Тем не менее проверки в тестах и в мониторинге всё равно полезны:

- **Ограничения FK не везде включены:** в хранилищах данных и витринах их часто не создают из соображений производительности загрузки и гибкости схемы. Целостность тогда обеспечивается логикой ETL и проверяется тестами.
- **Разные слои:** загрузка может идти в staging без FK; после переноса в витрину или в слой с другими таблицами связь проверяется запросом. Тест фиксирует ожидание «сирот нет» на уровне витрины.
- **Данные из внешних источников:** источник может поставлять некорректные ключи; проверка после загрузки выявляет это до того, как данные уйдут в отчёты.

Итого: если в схеме есть FK и они строго соблюдаются, запрос «найти сирот» должен возвращать 0. Если FK нет — проверка в SQL становится основным способом убедиться в целостности. В обоих случаях assertion «количество сирот по связи X = 0» можно включить в интеграционный тест и в мониторинг качества данных. В главе 7 мы вернёмся к референциальной целостности в контексте ETL: проверки после загрузки и типичные причины нарушений.

---

## Ключевое

- **Референциальная целостность:** у каждого значения FK в дочерней таблице есть соответствующая запись в родительской; **сирота** — дочерняя запись, чей FK не найден в родителе.
- **Проверка в SQL:** подсчёт сирот через LEFT JOIN (WHERE parent.key IS NULL) или NOT EXISTS; assertion — количество сирот = 0. Учитывать допустимость NULL в FK (не считать NULL сиротой).
- **Связь с FK в СУБД:** ограничение FOREIGN KEY гарантирует целостность при вставке; при отсутствии FK или при загрузке в staging без ограничений проверка запросом — основной способ контроля. Тесты и мониторинг полезны в обоих случаях.
