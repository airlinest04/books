# §5.3 Алгоритмы слияния (merge)

В [§5.1](chapter-05-01.md) и [§5.2](chapter-05-02.md) мы разобрали обнаружение и сравнение дубликатов. В этом разделе рассмотрим **алгоритмы слияния** — как из группы записей-дубликатов сформировать одну золотую запись: выбор «победителя» по полям, обработка групп из трёх и более записей, сохранение истории и маппинга. Концепция слияния введена в [§4.3](chapter-04-03.md); здесь — детали реализации в контексте дедупликации. В [§5.4](chapter-05-04.md) разберём инструменты и SQL-паттерны.

---

## 5.3.1. От группы дубликатов к золотой записи

После обнаружения дубликатов имеем **группы** записей; каждая группа — кандидаты на слияние в одну золотую запись. Группа может содержать 2, 3 и более записей (из одного или разных источников). См. [§5.1](chapter-05-01.md).

Алгоритм слияния:

1. Взять группу сопоставленных записей (дубликатов).
2. Для каждого атрибута золотой записи собрать все непустые значения из записей группы.
3. При конфликте (несколько разных значений) — применить правило выбора (приоритет источника, дата, полнота). См. [§4.2](chapter-04-02.md).
4. Сформировать одну запись с выбранными значениями; присвоить golden_id.
5. Сохранить маппинг: каждая source_id из группы → golden_id.
6. При необходимости — записать историю (кто дал какое значение).

Результат — одна золотая запись и обновлённая таблица маппинга. См. [§4.1](chapter-04-01.md), [§4.3](chapter-04-03.md).

---

## 5.3.2. Выбор «победителя» по полям (survivor)

**Survivor** (победитель, выжившая запись) — в контексте merge по записи: одна запись из группы выбирается как база, остальные дополняют пустые поля. В контексте merge по полям — для каждого поля независимо выбирается «победитель» (значение из одной из записей группы). См. [§4.3](chapter-04-03.md).

Правила выбора «победителя» по полю:

- **Приоритет источника:** среди записей с непустым значением — взять из источника с наивысшим приоритетом.
- **При равном приоритете:** по дате обновления (самое свежее) или по полноте.
- **При пустом у приоритетного:** перейти к следующему источнику в цепочке.

Правила задаются матрицей «атрибут → приоритет источников»; при слиянии группы применяются к каждой паре/набору значений. См. [§4.2](chapter-04-02.md).

---

## 5.3.3. Группы из трёх и более записей

При трёх и более записях в группе алгоритм тот же: для каждого атрибута собираем все непустые значения, при нескольких разных — выбираем по правилам. Источников может быть больше двух; приоритеты применяются ко всем.

Пример: группа из CRM, ERP и биллинга. Для `name`: CRM «ООО Ромашка», ERP «Ромашка ООО», биллинг «ООО Ромашка». При приоритете ERP > CRM > биллинг выбираем «Ромашка ООО». Для `phone`: только в CRM и биллинг; при приоритете CRM — из CRM. Итог: золотая запись — комбинация из трёх источников по полям.

**Транзитивное замыкание:** при обнаружении дубликатов могли найтись пары A–B и B–C (дубликаты), но A и C не сравнивались. Группа должна включать A, B, C. Алгоритм: после попарного сопоставления строим граф «дубликат»; компоненты связности — группы для слияния. Каждая компонента сливается в одну золотую запись. См. [§5.1](chapter-05-01.md).

---

## 5.3.4. Слияние с существующей золотой записью

При **инкрементальной** загрузке новая запись из источника может сопоставиться с уже существующей золотой записью (а не с другой сырой записью). Тогда слияние — «золотая + новая запись»: пересчитываем значения по правилам, учитывая текущую золотую и входящие данные; обновляем золотую запись; добавляем маппинг source_id → golden_id, если новая запись из нового источника. См. [§4.3](chapter-04-03.md), [§10.2](chapter-10-02.md).

Особенность: золотая запись уже могла быть сформирована из нескольких источников; при обновлении из одного источника меняются только те поля, где приоритет у этого источника или где значение пустое. Конфликт: новое значение из источника vs текущее в золотой — по правилам (приоритет, дата).

---

## 5.3.5. Сохранение истории

При слиянии полезно фиксировать:

- **Откуда взято значение:** для каждого атрибута — source_system, source_id (если известен).
- **Когда выполнено слияние:** timestamp.
- **Какие записи слиты:** список source_id, вошедших в группу.
- **Что отброшено:** при конфликте — какие значения не выбраны (для отладки и аудита).

Варианты хранения:

- **В самой золотой записи:** поля `merged_from`, `merged_at`, `merge_audit` (JSON или отдельная таблица).
- **Отдельная таблица аудита:** `merge_history(golden_id, attr, source, value, chosen, merged_at)`.
- **ETL-логи:** при пакетной загрузке — логирование в файл или таблицу логов.

История нужна для расследования инцидентов, согласования с бизнесом и настройки правил. См. [§4.4](chapter-04-04.md).

## 5.3.6. Маппинг и обновление ссылок

После слияния несколько source_id маппятся на один golden_id. Таблица маппинга:

```sql
CREATE TABLE md_account_mapping (
    source_system VARCHAR(50),
    source_id     VARCHAR(100),
    golden_id     BIGINT,
    created_at    TIMESTAMP,
    PRIMARY KEY (source_system, source_id)
);
```

При загрузке фактов (транзакций) из источника: в факте — source_id (например, counterparty_code из ERP); джойн с маппингом даёт golden_id; в факт пишем golden_id (или суррогатный ключ измерения). Старые факты, уже ссылающиеся на source_id, при перезагрузке или при обновлении измерений должны использовать новый golden_id. Если факты хранят source_id — маппинг применяется при запросе; если хранят golden_id — маппинг уже учтён при загрузке. См. [§7.2](chapter-07-02.md).

## 5.3.7. Слияние двух золотых записей (редкий случай)

Иногда обнаруживается, что две **золотые** записи — дубликаты (например, при доработке правил сопоставления или при появлении новых данных). Тогда нужно слить две золотые в одну.

Алгоритм:

1. Выбрать «главную» золотую (например, более старую или с большим числом ссылок).
2. Слить атрибуты по правилам (как две обычные записи).
3. Обновить маппинг: все source_id, маппившиеся на «побочную» золотую, переназначить на «главную».
4. Обновить факты: заменить старый golden_id на новый (или оставить суррогатные ключи и добавить маппинг старый_sk → новый_sk).
5. Пометить «побочную» золотую как объединённую или удалить.

Это более сложная операция; требует аккуратности с фактами и измерениями. См. [§4.4](chapter-04-04.md) (версионирование).

## 5.3.8. Псевдокод алгоритма слияния группы

```
function merge_group(records: List[Record], priority_matrix: Map) -> GoldenRecord:
    golden = {}
    for attr in schema.attributes:
        values = [(r.source, r[attr], r.updated_at) for r in records 
                  if r[attr] is not null and trim(r[attr]) != '']
        if values is empty:
            golden[attr] = null
        else:
            sort values by (priority_matrix[attr][source], desc(updated_at))
            golden[attr] = values[0].value
            if len(values) > 1 and values differ:
                log_conflict(attr, values)
    golden.id = assign_golden_id()
    for r in records:
        mapping.upsert(r.source, r.source_id, golden.id)
    audit_log.merge(golden.id, records, golden)
    return golden
```

## 5.3.9. Типичные ошибки

- **Сливать без проверки группы:** убедиться, что все записи в группе действительно дубликаты (транзитивное замыкание применено).
- **Не обновлять маппинг:** после слияния старые source_id должны указывать на новый golden_id.
- **Игнорировать идемпотентность:** повторная загрузка тех же данных не должна создавать дубликаты золотых или двойной маппинг.
- **Не обрабатывать слияние двух золотых:** при выявлении дубликатов среди золотых нужен отдельный процесс; иначе останутся две записи на одну сущность.

---

## Ключевое

- **Алгоритм слияния группы:** для каждого атрибута — собрать значения, при конфликте — выбрать по приоритету/дате/полноте; сформировать золотую запись; сохранить маппинг.
- **Выбор «победителя» по полям** — merge по полям; матрица приоритетов по атрибутам.
- **Группы из 3+ записей** — тот же алгоритм; транзитивное замыкание для формирования групп.
- **Слияние с существующей золотой** — при инкременте; пересчёт по правилам с учётом входящих данных.
- **Сохранение истории** — откуда значение, что отброшено; аудит для расследований.
- **Маппинг** source_id → golden_id обязателен; используется при загрузке фактов.
- **Слияние двух золотых** — редкий случай; обновить маппинг и факты.

В [§5.4](chapter-05-04.md) мы рассмотрим инструменты и SQL-паттерны: дедупликация в SQL, GROUP BY, оконные функции, связь с ETL.
