# §7.1 Идея реестра

Глава 6 завершила тему иерархий. Часть III посвящена **моделям MDM** — способам организации хранения и обновления эталонных данных. Три основные модели: **реестр (Registry)**, **консолидация (Consolidation)** и **сосуществование (Coexistence)**. В этом разделе рассмотрим **идею реестра**: MDM-система хранит только ссылки (идентификаторы) и маппинг между источниками; сами данные остаются в системах-источниках. В [§7.2](chapter-07-02.md) разберём хранение ссылок и разрешение при запросе; в [§7.3](chapter-07-03.md) — плюсы и минусы; в [§7.4](chapter-07-04.md) — когда реестр уместен.

---

## 7.1.1. Реестр vs консолидация

В модели **консолидации** ([§8.1](chapter-08-01.md)) эталонные данные **копируются** в центральное хранилище (MDM/DWH): золотая запись содержит все атрибуты (наименование, адрес, телефон и т.д.); источники загружают данные в центр; центр — источник правды. Запрос к эталону — чтение из центра, без обращения к источникам.

В модели **реестра** (Registry) эталонные данные **не копируются**. MDM хранит лишь:

- **Единый идентификатор** (golden_id) для каждой сущности.
- **Маппинг** «источник → идентификатор источника» на golden_id: `(source_system, source_id) → golden_id`.

Атрибуты (название, адрес, реквизиты) остаются в системах-источниках. Чтобы получить данные сущности, нужно **разрешить** golden_id в один или несколько source_id и запросить соответствующие источники. См. [§7.2](chapter-07-02.md), [§4.1](chapter-04-01.md).

---

## 7.1.2. «Индекс» эталонных сущностей

Реестр можно представить как **индекс** или **каталог**: он отвечает на вопрос «этот client_id из CRM и этот counterparty_code из ERP — одна и та же сущность?» и «какой golden_id им соответствует?». Данных о самой сущности в реестре нет — только связи между идентификаторами. См. [§3.1](chapter-03-01.md) (дубликаты), [§5.1](chapter-05-01.md) (сопоставление).

Пример: в CRM клиент с id=1001, в ERP контрагент с code=C-4421. Реестр хранит: оба маппятся на golden_id=5001. При загрузке факта продажи из CRM (customer_id=1001) — по маппингу получаем 5001; при загрузке факта платежа из ERP (counterparty_code=C-4421) — тот же 5001. Факты связываются через общий golden_id; атрибуты клиента (название, адрес) берутся при необходимости из CRM или ERP по их source_id.

---

## 7.1.3. Зачем не копировать данные

Причины выбрать реестр вместо консолидации:

- **Объём данных:** копирование миллионов записей клиентов или продуктов в центр — нагрузка на хранилище и ETL; реестр хранит только маппинг.
- **Владельцы данных:** источники остаются владельцами; обновления делают в CRM, ERP — не нужно синхронизировать центр с источниками.
- **Свежесть:** при запросе данные читаются из источника; нет задержки репликации (но доступность зависит от источников).
- **Регуляторика:** данные могут не покидать систему-владелец; реестр хранит только идентификаторы и связи.

Минусы: зависимость от доступности источников при запросе; сложнее объединять атрибуты из нескольких источников; нет «золотой записи» с полным набором атрибутов в одном месте. См. [§7.3](chapter-07-03.md).

---

## 7.1.4. Что хранит реестр

Типичное содержимое реестра:

| Элемент | Описание |
|---------|----------|
| golden_id | Единый идентификатор сущности в MDM |
| Маппинг | (source_system, source_id) → golden_id |
| Метаданные (опционально) | Дата сопоставления, статус (активен/архив), тип сущности |

Никаких атрибутов сущности (имя, адрес, телефон) — только идентификаторы и связи. См. [§7.2](chapter-07-02.md).

---

## 7.1.5. Связь с золотой записью

В консолидации **золотая запись** — полная строка с атрибутами. В реестре золотая запись — по сути **только golden_id** и маппинг; «запись» в смысле «одна сущность = один golden_id» есть, а «золотых атрибутов» в MDM нет — они в источниках.

Терминология: иногда говорят «золотая запись в реестре» в смысле «эталонная сущность с единым ID»; при этом подчёркивают, что атрибуты разрешаются по запросу из источников. См. [§4.1](chapter-04-01.md).

---

## 7.1.6. Реестр и единый источник правды

Реестр обеспечивает **логический** единый источник правды: для каждой сущности определён один golden_id; все системы и отчёты могут ссылаться на него. **Физически** данные разбросаны по источникам; «источник правды по атрибутам» — выбранный источник (например, CRM для клиентов) или комбинация при разрешении. См. [§1.3](chapter-01-03.md).

---

## Ключевое

- **Реестр (Registry)** — модель MDM, при которой хранятся только идентификаторы (golden_id) и маппинг (source_system, source_id) → golden_id; атрибуты сущности остаются в источниках.
- **Реестр vs консолидация:** в консолидации данные копируются в центр; в реестре — нет, только связи.
- **Реестр = индекс:** отвечает на вопрос «какие source_id соответствуют одной сущности» и «какой golden_id им присвоен».
- **Зачем реестр:** экономия места, источники — владельцы, свежесть из источника, ограничения на копирование.
- **Что хранит:** golden_id, маппинг, опционально метаданные; без атрибутов сущности.
- **Единый источник правды:** логически — один golden_id на сущность; физически — данные в источниках.

В [§7.2](chapter-07-02.md) разберём хранение ссылок: структура таблицы маппинга, разрешение golden_id в source_id при запросе.
