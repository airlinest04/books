# §12.1 Постановка задачи

В [§11.4](chapter-11-04.md) мы разобрали качество эталонных данных. Глава 12 — **практика**: соберём полный пайплайн эталонных данных от загрузки из источников до витрины. В этом разделе зафиксируем **постановку задачи**: сценарий (эталон «клиент» из двух источников), цель (золотая запись и витрина), входы и выходы, этапы пайплайна. Далее в [§12.2](chapter-12-02.md) — загрузка и слияние из источников; в [§12.3](chapter-12-03.md) — дедупликация и золотая запись; в [§12.4](chapter-12-04.md) — распространение в витрины. См. [Глоссарий](glossary.md).

---

## 12.1.1. Сценарий: эталон «клиент» из двух источников

Исходная задача: **формировать единый эталон сущности «клиент» из двух источников** (например, CRM и ERP), выполнять дедупликацию, строить золотую запись и загружать её в витрину как измерение. См. [§2.1](chapter-02-01.md), [§8.1](chapter-08-01.md).

Два источника — достаточный минимум для практики MDM: множественность, дубликаты, конфликты при слиянии. Реальный сценарий может включать больше источников; логика та же. См. [§3.2](chapter-03-02.md).

**Источник 1 (CRM):** клиенты B2C, физлица; атрибуты: client_id, ФИО, email, телефон, дата регистрации.

**Источник 2 (ERP):** контрагенты-покупатели, юрлица и физлица; атрибуты: counterparty_id, наименование, ИНН, адрес, телефон.

Оба источника содержат «клиентов» в широком смысле; записи могут относиться к одной реальной сущности (один и тот же человек или компания), но с разными ID и атрибутами. Цель — одна золотая запись на сущность. См. [§4.1](chapter-04-01.md), [§5.1](chapter-05-01.md).

---

## 12.1.2. Цепочка пайплайна

Пайплайн следует архитектуре слоёв эталонных данных ([§10.1](chapter-10-01.md)):

```
CRM, ERP → Raw → Staging (очистка, единая структура) → Дедупликация → Слияние → Core (золотая запись + маппинг) → Mart (dim_customer)
```

| Этап | Содержание |
|------|------------|
| Raw | Срезы из CRM и ERP «как есть»; сохранение для трассировки и повторной обработки. |
| Staging | Приведение к единой структуре; source_system, source_id; нормализация полей; объединение записей из обоих источников в одну таблицу staging.customer. |
| Дедупликация | Обнаружение групп записей-дубликатов (по ИНН, email или fuzzy matching); выбор одной записи на группу или merge по полям. |
| Core | Золотая запись в core.customer; маппинг (source_system, source_id) → golden_id в core.customer_mapping. |
| Mart | Измерение dim_customer для витрин; строится из Core. |

См. [§11.3](chapter-11-03.md), [§8.2](chapter-08-02.md).

---

## 12.1.3. Входы и выходы

**Входы:**

- Выгрузка клиентов из CRM (файл или таблица): client_id, name, email, phone, registration_date.
- Выгрузка контрагентов-покупателей из ERP: counterparty_id, name, inn, address, phone.

**Выходы:**

- core.customer — золотая запись: golden_id, name, inn, email, phone, address, source_priority, updated_at.
- core.customer_mapping — маппинг: golden_id, source_system, source_id.
- mart.dim_customer — измерение для витрин (из Core; при необходимости — SCD Type 2 для истории). См. [§10.3](chapter-10-03.md), [§10.4](chapter-10-04.md).

**Частота:** ежедневная загрузка; полная или инкрементальная — по регламенту. См. [§10.2](chapter-10-02.md).

---

## 12.1.4. Единая структура Staging

Для сопоставления и дедупликации нужна **единая модель** в Staging. Объединяем атрибуты обоих источников:

| Поле Staging | CRM | ERP | Примечание |
|--------------|-----|-----|------------|
| source_system | 'CRM' | 'ERP' | идентификатор источника |
| source_id | client_id | counterparty_id | ID в источнике |
| name | ФИО | наименование | нормализация: trim, регистр |
| inn | — | ИНН | только ERP; для юрлиц |
| email | email | — | только CRM |
| phone | phone | phone | нормализация формата |
| address | — | address | только ERP |
| registration_date | дата | — | только CRM |

Дедупликация: по ИНН (если заполнен) или по комбинации name + phone; при отсутствии ключа — fuzzy matching по name. См. [§5.1](chapter-05-01.md), [§5.2](chapter-05-02.md).

---

## 12.1.5. Правила слияния и приоритеты

При конфликте (разные значения одного атрибута из разных источников) выбираем по правилам. Пример приоритетов:

- **name, inn, address:** ERP (операционные реквизиты).
- **email, phone:** CRM (контактные данные).
- **registration_date:** CRM (если есть).

Правила слияния задаются матрицей приоритетов по атрибутам. См. [§4.2](chapter-04-02.md), [§4.3](chapter-04-03.md).

---

## 12.1.6. Требования к качеству

| Требование | Содержание |
|------------|------------|
| Полнота | Обязательные поля (name, хотя бы один идентификатор — source_id или inn) заполнены. |
| Уникальность | В Core — одна запись на golden_id; дубликаты по бизнес-ключу недопустимы. |
| Валидность | ИНН — 10 или 12 цифр; email — формат; телефон — нормализован. |
| Целостность маппинга | Каждый (source_system, source_id) из Staging маппится на ровно один golden_id. |

Проверки — на этапах Staging и Core. См. [§11.4](chapter-11-04.md).

---

## 12.1.7. Итог постановки

Для реализации в следующих разделах зафиксированы: два источника (CRM, ERP); сущность «клиент»; единая структура Staging; цепочка Raw → Staging → дедупликация → слияние → Core → Mart; правила слияния и приоритеты; требования к качеству.

---

## Ключевое

- **Сценарий:** эталон «клиент» из двух источников (CRM, ERP); дедупликация; золотая запись; витрина.
- **Цепочка:** Raw → Staging (единая структура) → дедупликация → слияние → Core (золотая запись + маппинг) → Mart (dim_customer).
- **Единая структура Staging:** source_system, source_id, name, inn, email, phone, address; нормализация полей.
- **Дедупликация:** по ИНН или name+phone; при отсутствии — fuzzy matching.
- **Правила слияния:** матрица приоритетов по атрибутам (ERP для реквизитов, CRM для контактов).
- **Качество:** полнота, уникальность, валидность; проверки на Staging и Core.

В [§12.2](chapter-12-02.md) реализуем **загрузку и слияние из источников**: ETL в Staging, приведение к единой структуре.
