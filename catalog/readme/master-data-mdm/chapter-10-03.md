# §10.3 Витрины и измерения

В [§10.1](chapter-10-01.md) и [§10.2](chapter-10-02.md) мы разобрали слой эталонных данных и загрузку. В этом разделе сосредоточимся на **витринах и измерениях**: как измерения «клиент», «продукт», «контрагент» строятся из эталонов, как они связываются с фактами и как выглядят типичные джойны для отчётов. В [§10.4](chapter-10-04.md) разберём SCD и историю изменений эталонов.

---

## 10.3.1. Витрина: факты + измерения

**Витрина** (data mart) — слой готовых к потреблению данных: фактовая таблица и связанные таблицы измерений в форме звёздной схемы (или снежинки). См. [§1.4](chapter-01-04.md), [§8.4](chapter-08-04.md).

Пример витрины продаж:

```
fact_sales (sale_id, date_id, customer_id, product_id, store_id, quantity, amount, ...)
    ├── dim_date (date_id, cal_date, year, month, ...)
    ├── dim_customer (customer_id, name, inn, region, segment, ...)
    ├── dim_product (product_id, name, category, brand, unit, ...)
    └── dim_store (store_id, name, city, region, ...)
```

Измерения `dim_customer`, `dim_product`, `dim_store` — это **эталонные сущности** в размерной форме; данные в них происходят из Core эталонов (золотая запись). См. [§10.1](chapter-10-01.md).

---

## 10.3.2. Измерения из эталонов

**Измерение «Клиент»** (dim_customer) строится из `core.customer` (золотая запись клиентов):

- Суррогатный ключ `customer_id` (или customer_sk) — golden_id или его производная.
- Атрибуты: name, inn, address, phone, region, segment — из золотой записи.
- При денормализации: иерархия «регион» может быть развёрнута в столбцы (region_name, country). См. [§6.4](chapter-06-04.md).

**Измерение «Продукт»** (dim_product) — из `core.product`:

- product_id — golden_id; name, category_id, brand_id — из золотой записи.
- В звёздной схеме: category_name, subcategory_name, brand_name — денормализованы в строку.
- В снежинке: ссылка на dim_category, dim_brand. См. [§6.4](chapter-06-04.md).

**Измерение «Контрагент»** (dim_counterparty) — из `core.counterparty` для витрин платежей, закупок и т.д.

См. [§1.4](chapter-01-04.md), [§8.4](chapter-08-04.md).

## 10.3.3. Связь с фактами

**Фактовая таблица** хранит **ключи измерений** (внешние ключи) и **меры** (числовые показатели). См. книга по DWH, [§4.1](../dwh/chapter-04-01.md).

Пример fact_sales:

```sql
-- Упрощённая структура
fact_sales (
    sale_id       BIGINT PK,
    date_id       INT,      -- FK → dim_date
    customer_id   INT,      -- FK → dim_customer (суррогатный ключ = golden_id)
    product_id    INT,      -- FK → dim_product
    store_id      INT,      -- FK → dim_store
    quantity      DECIMAL,
    amount        DECIMAL,
    ...
);
```

При загрузке факта из транзакции: транзакция содержит source_id (customer_id из CRM, product_code из каталога); по таблице маппинга находим golden_id; в факт пишется суррогатный ключ измерения, соответствующий этому golden_id. См. [§5.3](chapter-05-03.md), [§7.2](chapter-07-02.md).

## 10.3.4. Джойны для отчётов

Типичный запрос «выручка по клиентам»:

```sql
SELECT 
    c.name AS customer_name,
    c.region,
    SUM(f.amount) AS total_sales
FROM fact_sales f
JOIN dim_customer c ON f.customer_id = c.customer_id
GROUP BY c.name, c.region;
```

«Выручка по категориям продуктов» (звёздная схема, category в dim_product):

```sql
SELECT 
    p.category_name,
    SUM(f.amount) AS total_sales
FROM fact_sales f
JOIN dim_product p ON f.product_id = p.product_id
GROUP BY p.category_name;
```

«Выручка по регионам» (через dim_store):

```sql
SELECT 
    s.region,
    SUM(f.amount) AS total_sales
FROM fact_sales f
JOIN dim_store s ON f.store_id = s.store_id
GROUP BY s.region;
```

Джойн по одному ключу на измерение; атрибуты для группировки и фильтрации берутся из измерения. Качество эталонов (Core) определяет качество измерений и, следовательно, корректность агрегатов. См. [§4.1](chapter-04-01.md).

---

## 10.3.5. Снежинка: дополнительные джойны

В схеме «снежинка» иерархии вынесены в отдельные таблицы. Запрос «продажи по категориям»:

```sql
SELECT 
    cat.name AS category_name,
    SUM(f.amount) AS total_sales
FROM fact_sales f
JOIN dim_product p ON f.product_id = p.product_id
JOIN dim_category cat ON p.category_id = cat.category_id
GROUP BY cat.name;
```

Цепочка JOIN длиннее; BI-инструменты и пользователи должны учитывать структуру. Часто создают view, «разворачивающие» снежинку в плоскую структуру для упрощения запросов. См. [§6.4](chapter-06-04.md), книга по DWH, [§4.3](../dwh/chapter-04-03.md).

## 10.3.6. Ролевые измерения

**Ролевое измерение** — одна таблица измерения используется в факте в нескольких «ролях» (несколько внешних ключей на одну таблицу). См. [§6.2](chapter-06-02.md), книга по DWH, [§4.3](../dwh/chapter-04-03.md).

Пример: fact_order с датой заказа (order_date_id), датой отгрузки (ship_date_id), датой доставки (delivery_date_id) — все три ссылаются на dim_date. Или: fact_sales с customer_id (покупатель) и store_id (магазин); dim_store может использоваться для «магазин продажи» и «магазин доставки» при наличии двух ссылок.

---

## 10.3.7. Сироты и обработка отсутствующих ключей

Если факт ссылается на customer_id, которого нет в dim_customer (сирота), JOIN даст потерю строки: факт не попадёт в отчёт. См. [§1.2](chapter-01-02.md).

Варианты:

- **LEFT JOIN:** факт остаётся, атрибуты измерения — NULL; в отчёте — отдельная группа «Неизвестный клиент» или исключение.
- **Проверка при загрузке:** не допускать сирот; откладывать факты с неизвестным source_id до появления маппинга.
- **Заглушка в измерении:** запись с id=-1 или специальным ключом «Unknown»; факты-сироты маппятся на неё для явного учёта.

---

## 10.3.8. Типичные ошибки

- **Дубликаты в измерении:** одна сущность — несколько строк; агрегаты завышаются при некорректном джойне. Дедупликация в Core обязательна. См. [§5.1](chapter-05-01.md).
- **Факт ссылается на source_id вместо golden_id:** при нескольких источниках один клиент может иметь разные source_id; в факте должен быть единый ключ (golden_id / surrogate key). Маппинг при загрузке факта. См. [§7.2](chapter-07-02.md).
- **Игнорировать сироты:** факты с несуществующим ключом измерения теряются при INNER JOIN; нужна политика.
- **Смешивать бизнес-ключ и суррогатный:** в факте — суррогатный ключ измерения (стабильный); бизнес-ключ (ИНН, артикул) — атрибут измерения для отображения.

---

## Ключевое

- **Витрина** — факты + измерения в звёздной схеме (или снежинке).
- **Измерения из эталонов:** dim_customer, dim_product, dim_counterparty строятся из Core (золотая запись); суррогатный ключ = golden_id или производная.
- **Связь с фактами:** факт хранит FK на измерения; при загрузке source_id маппится на golden_id.
- **Джойны:** факт JOIN измерение по ключу; группировка по атрибутам измерения.
- **Снежинка** — дополнительные JOIN по иерархии; view для упрощения.
- **Сироты** — факты с отсутствующим ключом измерения; политика: LEFT JOIN, заглушка, отложенная загрузка.

В [§10.4](chapter-10-04.md) разберём SCD и историю изменений эталонов: Type 2, effective_from/effective_to, запросы «на дату».
