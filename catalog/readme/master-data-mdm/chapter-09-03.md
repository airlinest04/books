# §9.3 Конфликты и разрешение

В [§9.1](chapter-09-01.md) и [§9.2](chapter-09-02.md) мы разобрали сосуществование и синхронизацию. В этом разделе сосредоточимся на **конфликтах**: одновременное изменение одного атрибута в двух системах; правила разрешения (timestamp, приоритет источника); матрица приоритетов по полям; ручной разбор и эскалация. Концепция конфликтов введена в [§3.3](chapter-03-03.md); здесь — применение в модели сосуществования. В [§9.4](chapter-09-04.md) разберём, когда сосуществование уместно.

---

## 9.3.1. Одновременное изменение в двух системах

При сосуществовании несколько систем могут менять одну и ту же сущность. **Конфликт** возникает, когда:

- Две (или более) системы изменили **один и тот же атрибут** одной сущности.
- Изменения пришли в центр (или обнаружились при синхронизации) в период, когда ещё не определено, какое значение считать текущим.

Пример: менеджер в CRM обновил телефон клиента в 10:00; бухгалтер в ERP — в 10:15. Оба изменения относятся к одной сущности (golden_id=5001), атрибут `phone`. Значения разные. Какое записать в золотую запись и распространить в системы? См. [§3.3](chapter-03-03.md).

---

## 9.3.2. Правила разрешения: обзор

Основные стратегии разрешения конфликтов:

| Стратегия | Суть | Плюсы | Минусы |
|-----------|-----|-------|--------|
| **Приоритет источника** | Для атрибута задаётся порядок источников; при конфликте берётся значение из источника с наивысшим приоритетом | Детерминированно; отражает «владельца» поля | Игнорирует актуальность |
| **Last Write Wins (timestamp)** | Более позднее по дате изменения выигрывает | Учитывает актуальность; просто | Теряется более раннее; timestamp может быть ненадёжен |
| **Ownership по полям** | Каждое поле закреплено за одной системой; только она может его менять «легитимно» | Меньше конфликтов | Нужна дисциплина; не все системы поддерживают |
| **Ручной разбор** | Конфликт уходит steward'у или владельцу | Точное решение в спорных случаях | Медленно; не масштабируется |

На практике комбинируют: приоритет по умолчанию; для части атрибутов — timestamp; критичные конфликты — на ручной разбор. См. [§4.2](chapter-04-02.md), [§4.3](chapter-04-03.md).

---

## 9.3.3. Приоритет источника

**Приоритет источника** — матрица: для каждого атрибута (или группы) задаётся упорядоченный список систем. При конфликте выбирается значение из системы с наивысшим приоритетом среди давших непустое значение. См. [§3.3](chapter-03-03.md), [§4.2](chapter-04-02.md).

Пример для контрагента:

| Атрибут | 1 | 2 | 3 |
|---------|---|---|---|
| name, inn, legal_address | ERP | CRM | — |
| phone, email | CRM | ERP | — |
| bank_details | ERP | Биллинг | — |
| delivery_address | Логистика | CRM | — |

Обоснование: ERP — реквизиты для документов; CRM — контакты; логистика — адреса доставки. Матрица настраивается и пересматривается при смене процессов. При конфликте по `phone` между CRM и ERP выбирается значение из CRM.

---

## 9.3.4. Timestamp (Last Write Wins)

**Last Write Wins (LWW)** — при конфликте выбирается значение с наиболее поздней датой изменения (`updated_at`, `modified_date`).

Требования:

- Все системы должны сохранять и передавать дату изменения при синхронизации.
- Часовые пояса — единый формат (UTC или согласованный).
- Точность: при совпадении до секунды нужен дополнительный критерий (источник, id события).

Плюсы: отражает «последнее известное» состояние; не нужна матрица приоритетов. Минусы: ошибочная недавняя правка перекроет корректную; при рассинхроне часов возможны некорректные решения. См. [§4.2](chapter-04-02.md).

---

## 9.3.5. Комбинация: приоритет + timestamp

Часто используют **комбинированное правило**:

1. **По приоритету:** если одна из систем имеет более высокий приоритет для данного атрибута — берём её значение.
2. **При равном приоритете:** берём по timestamp (самое свежее).
3. **При равной дате:** фиксированное правило (например, алфавитный порядок кода системы для детерминизма) или эскалация.

Так снижают число «спорных» случаев при равном приоритете. См. [§4.2](chapter-04-02.md).

---

## 9.3.6. Ownership по атрибутам

**Ownership по полям** — каждое поле закреплено за одной системой как «владелец». Только эта система считается авторитетным источником для данного поля; изменения из других систем при конфликте отклоняются или принимаются только при пустом значении у владельца.

Пример: `phone` — владелец CRM; `inn`, `bank_details` — ERP. При конфликте по `phone` всегда берётся CRM. Упрощает правила; уменьшает конфликты. Но требует, чтобы системы не меняли «чужие» поля или чтобы центр при распространении не перезаписывал «чужие» поля в системах-владельцах. Организационная дисциплина. См. [§9.1](chapter-09-01.md).

---

## 9.3.7. Ручной разбор и эскалация

Для **критичных** или **редких** конфликтов автоматическое правило может быть неприемлемо. Варианты:

- **Очередь на разбор:** конфликт логируется; steward или владелец данных получает уведомление; выбирает значение вручную; центр обновляется и распространяет выбранное значение.
- **Эскалация по порогу:** если разница между значениями «велика» (по доменному критерию) или атрибут критичен — не применять LWW, а отправить на ручной разбор.
- **Аудит:** все конфликты логировать (атрибут, значения, источники, timestamp); периодический разбор для настройки правил.

---

## 9.3.8. Распространение после разрешения

После разрешения конфликта золотая запись в центре обновлена. При распространении в системы:

- **Система, чьё значение проиграло:** получит обновление из центра с «чужим» значением. Пользователь может обнаружить, что его изменение «откатилось». Нужна политика: уведомление, объяснение, возможность оспорить.
- **Система, чьё значение выиграло:** получит подтверждение (то же значение) или не получит изменения, если уже актуальна.

Перезапись «проигравшей» системы может вызывать недовольство. Важно документировать правила и уведомлять пользователей при значимых конфликтах. См. [§8.3](chapter-08-03.md).

---

## 9.3.9. Типичные ошибки

- **Нет явных правил:** конфликты разрешаются «как получится» (порядок обработки, случайность); результаты непредсказуемы.
- **Игнорировать timestamp:** при равном приоритете нужен второй критерий; иначе результат зависит от порядка поступления.
- **Не логировать конфликты:** без истории невозможно отладить правила и провести аудит.
- **Распространять без предупреждения:** пользователь не понимает, почему его изменение «пропало»; нужна прозрачность.
- **Смешивать семантику:** «адрес» в одной системе — юридический, в другой — доставки; это разные атрибуты, не конфликт одного поля. См. [§3.3](chapter-03-03.md).

---

## Ключевое

- **Конфликт** — одновременное изменение одного атрибута в двух (и более) системах; нужно выбрать одно значение.
- **Приоритет источника** — матрица по атрибутам; при конфликте берётся значение из системы с наивысшим приоритетом.
- **Timestamp (LWW)** — последнее по дате изменения выигрывает; требует корректных дат и часовых поясов.
- **Комбинация** — приоритет + timestamp при равном приоритете.
- **Ownership по полям** — одно поле — один владелец; упрощает правила.
- **Ручной разбор** — для критичных конфликтов; эскалация, очередь, аудит.
- **Распространение** — после разрешения центр распространяет выбранное значение; «проигравшие» системы получают обновление.

В [§9.4](chapter-09-04.md) разберём, когда выбирать сосуществование: децентрализованная организация, несколько владельцев, сложная синхронизация.
