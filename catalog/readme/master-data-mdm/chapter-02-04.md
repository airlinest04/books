# §2.4 Прочие сущности: сотрудники, контракты

В [§2.1](chapter-02-01.md)–[§2.3](chapter-02-03.md) мы разобрали клиентов, контрагентов, продукты и справочники. В этом разделе рассмотрим **прочие эталонные сущности**: сотрудники, договоры (контракты) и организационная структура. Они участвуют в транзакциях и отчётности, используются во многих процессах и требуют согласованного представления. Завершая главу 2, мы зафиксируем их атрибуты, источники и связь с уже рассмотренными сущностями. В [§3.1](chapter-03-01.md) начнём главу 3 — проблемы эталонных данных (дубликаты и расхождения).

---

## 2.4.1. Сотрудники

**Сотрудник** — работник организации: физлицо с привязкой к должности, подразделению и трудовым отношениям. Эталонная сущность для HR, учёта продаж (менеджер), обращений (исполнитель), бюджетирования (ЦФО) и отчётности. См. [Глоссарий](glossary.md).

Типичные атрибуты:

| Атрибут | Описание | Примечания |
|---------|----------|------------|
| Табельный номер | Внутренний идентификатор | Уникален в организации |
| ФИО | Фамилия, имя, отчество | Может меняться (брак и т.д.) |
| Должность | Название должности | Ссылка на справочник или текст |
| Подразделение | Отдел, филиал, ЦФО | Ссылка на организационную структуру |
| Email, телефон | Контакты | Служебные |
| Дата приёма, дата увольнения | Период работы | Для истории и фильтрации |
| Руководитель | Ссылка на сотрудника | Иерархия подчинённости |
| Статус | Работает, уволен, декрет | Для фильтрации актуальных |

Особенности: сотрудник — физлицо; один человек может быть в разных системах под разными ID (HR, CRM, учёт рабочего времени). Дубликаты возникают при миграциях и интеграции; единый эталонный ID и маппинг источников решают задачу. Персональные данные (ФИО, контакты) подпадают под требования по защите; в DWH и витринах часто хранят обезличенные или агрегированные срезы. См. [§2.1](chapter-02-01.md), [§3.1](chapter-03-01.md).

## 2.4.2. Договоры (контракты)

**Договор** (контракт) — соглашение между организацией и контрагентом (или между подразделениями): поставка, услуги, аренда, кредит и т.д. Эталонная сущность, связывающая контрагента, продукты/услуги, условия и сроки. См. [Глоссарий](glossary.md).

Типичные атрибуты:

| Атрибут | Описание | Примечания |
|---------|----------|------------|
| Номер договора | Уникальный идентификатор | Может быть составным (префикс + номер) |
| Дата заключения | Дата подписания | |
| Стороны | Организация и контрагент | Ссылки на эталоны контрагентов |
| Тип договора | Поставка, услуги, аренда | Справочник |
| Срок действия | Начало, окончание | Продление — новая запись или обновление |
| Статус | Активен, завершён, расторгнут | |
| Условия | Валюта, способ оплаты, штрафы | Могут быть в отдельной сущности |
| Ответственный | Менеджер, сотрудник | Ссылка на эталон сотрудника |

Договор связывает несколько эталонов: контрагент (одна или обе стороны), продукт/услуга (предмет), сотрудник (ответственный). В транзакциях (поставки, платежи, акты) ссылаются на договор; отчёты строят по контрактам (объём поставок, просрочка). Один контрагент может иметь множество договоров; один договор — множество транзакций. Дубликаты договоров (один документ в разных системах под разными номерами) — типичная проблема при интеграции. См. [§6.1](chapter-06-01.md).

## 2.4.3. Организационная структура

**Организационная структура** — иерархия подразделений (отделы, филиалы, центры ответственности, ЦФО). Эталонная сущность для бюджетирования, отчётности по подразделениям, привязки сотрудников и сделок. См. [Глоссарий](glossary.md).

Типичные атрибуты подразделения:

| Атрибут | Описание | Примечания |
|---------|----------|------------|
| Код | Уникальный идентификатор | Внутренний код |
| Наименование | Название подразделения | |
| Родительское подразделение | Ссылка на вышестоящее | Иерархия: дерево |
| Уровень | Уровень в иерархии (1, 2, 3) | Для запросов по уровням |
| Руководитель | Ссылка на сотрудника | |
| Тип | Филиал, отдел, ЦФО | Справочник |
| Дата создания, дата закрытия | Жизненный цикл | Реорганизации |

Иерархия: корень (организация в целом) → филиалы/дивизионы → отделы → группы. Рекурсивная связь parent_id; обход — рекурсивными CTE или отдельной таблицей путей. Оргструктура меняется при реорганизациях; нужна версионность или хранение дат действия для исторических отчётов. См. [§6.1](chapter-06-01.md), [§6.3](chapter-06-03.md).

## 2.4.4. Источники данных

| Сущность | Источники | Особенности |
|----------|-----------|-------------|
| **Сотрудники** | HR-система, 1С ЗУП, SAP HR, табельная система | Главный источник — HR; CRM и др. могут иметь свои ID |
| **Договоры** | ERP, CRM, договорной модуль, юридика | Разные системы — разные номера; нужен маппинг |
| **Оргструктура** | HR, ERP, бюджетирование | Реорганизации; расхождения между системами |

Множественность источников ведёт к дубликатам и расхождениям; MDM (или централизованная загрузка в DWH) обеспечивает единое представление. См. [§3.2](chapter-03-02.md).

---

## 2.4.5. Связи между сущностями

Сотрудник, договор и оргструктура связаны друг с другом и с ранее рассмотренными сущностями:

```
Организационная структура (подразделение)
    │
    ├── Сотрудник (принадлежность к подразделению, руководитель)
    │       │
    │       └── Договор (ответственный менеджер)
    │
Контрагент ──┬── Договор (сторона договора)
             │
Продукт ─────┴── Договор (предмет — опционально, через позиции)
```

При проектировании эталонного слоя важно явно задать связи: внешние ключи, правила целостности, обработку «сирот» (договор без контрагента, сотрудник без подразделения). См. [§1.2](chapter-01-02.md), [§10.3](chapter-10-03.md).

## 2.4.6. Пример структуры: подразделение и договор

Упрощённые примеры:

```sql
-- Подразделение (организационная структура)
CREATE TABLE dim_department (
    department_sk   BIGINT PRIMARY KEY,
    department_bk   VARCHAR(50),
    name            VARCHAR(200),
    parent_sk       BIGINT,              -- ссылка на родителя
    level_num       INT,
    manager_sk      BIGINT,              -- сотрудник-руководитель
    type_code       VARCHAR(20),
    valid_from      DATE,
    valid_to        DATE,
    is_current      SMALLINT
);

-- Договор
CREATE TABLE dim_contract (
    contract_sk     BIGINT PRIMARY KEY,
    contract_bk     VARCHAR(100),        -- номер договора
    counterparty_sk BIGINT,              -- контрагент
    type_code       VARCHAR(50),
    start_date      DATE,
    end_date        DATE,
    status          VARCHAR(20),
    responsible_sk  BIGINT,              -- ответственный сотрудник
    source_system   VARCHAR(50),
    source_id       VARCHAR(100)
);
```

Иерархия подразделений: обход по parent_sk рекурсивным запросом; агрегация по уровням. Договор связывает контрагента и сотрудника; факты (поставки, платежи) ссылаются на contract_sk. См. [§6.3](chapter-06-03.md).

## 2.4.7. Типичные ошибки

- **Игнорировать дубликаты сотрудников:** один человек в HR и CRM под разными ID; без маппинга отчёты по менеджерам искажены.
- **Не учитывать историю оргструктуры:** при реорганизации старые сделки должны быть привязаны к подразделению на дату сделки, а не к текущему.
- **Смешивать договор и счёт/накладную:** договор — рамочное соглашение; счёт, накладная — транзакции по договору; разный уровень гранулярности.
- **Забывать о персональных данных:** сотрудники — персональные данные; при выгрузке в витрины и отчёты нужны маскирование и политики доступа.

---

## Ключевое

- **Сотрудник** — работник с привязкой к должности и подразделению; атрибуты: табельный номер, ФИО, должность, подразделение, статус; источники — HR, CRM.
- **Договор** — соглашение между организацией и контрагентом; связывает контрагента, сотрудника (ответственного), продукты; атрибуты: номер, даты, тип, статус.
- **Организационная структура** — иерархия подразделений; parent_id для дерева; версионность при реорганизациях.
- **Источники:** HR (сотрудники, оргструктура), ERP/CRM (договоры); множественность — риск дубликатов.
- **Связи:** сотрудник → подразделение; договор → контрагент, сотрудник; факты → договор, сотрудник, подразделение.

В [§3.1](chapter-03-01.md) мы начнём главу 3 — проблемы эталонных данных: дубликаты, расхождения, отсутствие единого ключа.
