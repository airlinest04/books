# §5.1 Текстовые форматы в экосистеме Hadoop

В [§4.4](chapter-04-04.md) мы завершили главу о YARN. Данные в HDFS и в экосистеме Hadoop хранятся в разных **форматах**; от выбора формата зависят скорость чтения/записи, сжатие, возможность выборочного чтения столбцов и совместимость с инструментами (Hive, Spark, MapReduce). В этой главе разбираем основные форматы. Начнём с **текстовых форматов** — CSV и JSON: они просты и удобны для обмена и отладки, но имеют ограничения по схеме, сжатию и разбиению. SequenceFile и колоночные форматы (Parquet, ORC) — в [§5.2](chapter-05-02.md) и [§5.3](chapter-05-03.md); критерии выбора — в [§5.4](chapter-05-04.md). См. [Глоссарий](glossary.md).

---

## 5.1.1. Роль формата хранения в HDFS

Файлы в HDFS — это последовательности байт, разбитые на блоки. **Формат** определяет, как эти байты интерпретируются: как текст по строкам (CSV, JSON, лог), как бинарные пары ключ–значение (SequenceFile), как колоночные блоки (Parquet, ORC). См. [Глоссарий](glossary.md).

От формата зависят:

- **Как читать и писать:** нужен ли построчный парсинг, десериализация из бинарного вида, чтение только части столбцов.
- **Сжатие:** одни форматы хорошо сжимаются (повторяющиеся структуры, колоночное хранение), другие — хуже (произвольный текст).
- **Разбиение на сплиты:** при MapReduce и Spark важно, чтобы файл можно было разбить на части без потери смысла (например, по границам строк); не все форматы позволяют безопасно резать в произвольном месте.
- **Схема:** есть ли явное описание типов и полей (в файле или в метаданных Hive) или схема задаётся только при чтении.

Текстовые форматы (CSV, JSON) — самые простые: файл можно открыть и прочитать в любом редакторе; при этом они не содержат встроенной схемы и не оптимальны для аналитики больших объёмов.

## 5.1.2. CSV (значения, разделённые запятыми)

**CSV** (Comma-Separated Values) — текстовый формат, в котором каждая строка — одна запись (строка таблицы), поля разделены разделителем (запятая, точка с запятой, табуляция). См. [Глоссарий](glossary.md).

Пример:

```
id,name,amount
1,Alice,100
2,Bob,200
```

Плюсы:

- **Читаемость:** файл открывается в текстовом редакторе, Excel, скриптах; удобно для отладки и обмена.
- **Простота:** нет сложной сериализации; запись и чтение реализуются легко в любом языке.
- **Широкая поддержка:** экспорт/импорт из СУБД, таблиц, скриптов; Hive, Spark, MapReduce умеют читать CSV (напрямую или через настройку TextInputFormat и парсера).

Минусы:

- **Нет встроенной схемы:** имена и типы столбцов не хранятся в файле; при изменении порядка или набора полей нужна отдельная договорённость или метаданные (например, в Hive — в определении таблицы).
- **Слабое сжатие:** текстовое представление чисел и дат занимает больше места, чем бинарное; повторяющиеся значения сжимаются только общим компрессором (Gzip, Snappy), без учёта структуры столбцов.
- **Разбиение:** разбивать файл по байтам можно по границам строк (если разделитель строк фиксирован — LF или CRLF); при сжатии всего файла одним потоком (например, Gzip) границы блоков HDFS не совпадают с границами записей — нельзя начать чтение с середины файла без распаковки с начала. Для параллельного чтения тогда используют несжатый CSV или сжатие по блокам (block compression в других форматах).
- **Экранирование и кодировки:** запятые и переносы внутри полей требуют правил экранирования (кавычки); разные кодировки (UTF-8, Windows-1251) нужно задавать явно.

В Hive таблица поверх CSV создаётся с `STORED AS TEXTFILE` и при необходимости `ROW FORMAT DELIMITED FIELDS TERMINATED BY ','`. Данные лежат в виде текстовых файлов в HDFS; при запросе Hive парсит строки по разделителю.

## 5.1.3. JSON (JavaScript Object Notation)

**JSON** — текстовый формат представления структур данных (объекты, массивы, числа, строки, булевы значения). Одна строка файла может быть одной JSON-записью (JSON Lines, NDJSON) или весь файл — один большой JSON (массив объектов). См. [Глоссарий](glossary.md).

Пример (одна запись на строку — JSON Lines):

```
{"id":1,"name":"Alice","amount":100}
{"id":2,"name":"Bob","amount":200}
```

Плюсы:

- **Читаемость и универсальность:** JSON широко используется в API, логах, конфигурациях; легко генерировать и парсить в разных языках.
- **Иерархия и гибкая структура:** вложенные объекты и массивы; разные записи могут иметь разный набор полей (гибкая схема).
- **Поддержка в инструментах:** Spark, Hive (через SerDe), многие процессоры событий и логов понимают JSON.

Минусы:

- **Нет встроенной схемы:** типы и полная схема не заданы в формате; при чтении в Hive/Spark схему задают вручную или выводят из выборки.
- **Избыточность:** имена полей повторяются в каждой записи — больший объём и хуже сжатие по сравнению с колоночными форматами, где имена столбцов хранятся один раз.
- **Разбиение:** при формате «одна строка — одна запись» (JSON Lines) разбиение по границам строк возможно; при одном большом JSON-массиве в файле резать по байтам нельзя без парсинга с начала.
- **Производительность парсинга:** разбор JSON тяжелее, чем фиксированных полей в CSV; при больших объёмах колоночные или бинарные форматы часто быстрее.

Для аналитики в Hadoop обычно предпочитают **JSON Lines** (одна строка — один JSON-объект): так файл можно разбивать по строкам и читать параллельно. Целый файл как один JSON подходит для небольших конфигов, но не для больших данных в HDFS.

## 5.1.4. Общие ограничения текстовых форматов

Сводка ограничений, общих для CSV и JSON (и для произвольного текста в целом):

| Аспект | Ограничение |
|--------|--------------|
| **Схема** | Не хранится в файле; задаётся при создании таблицы в Hive или при чтении в Spark; при изменении формата данных возможны ошибки и ручная синхронизация. |
| **Сжатие** | Только общие алгоритмы (Gzip, Snappy, Bzip2); при сжатии всего файла потоком теряется возможность параллельного чтения по блокам без полной распаковки. |
| **Выборка столбцов** | Нельзя прочитать «только столбец A»: нужно прочитать и распарсить всю строку; при широких таблицах и запросах по нескольким столбцам лишний I/O и CPU. |
| **Типы данных** | В тексте числа и даты хранятся как строки; преобразование и проверка типов — при чтении; риск неоднородных форматов (разные форматы дат, разделители). |

Поэтому текстовые форматы уместны для **сырых данных**, **обмена**, **отладки** и **небольших объёмов**; для тяжёлой аналитики и больших таблиц в Hive/Spark чаще используют колоночные форматы (Parquet, ORC) или бинарные (SequenceFile) — см. [§5.2](chapter-05-02.md) и [§5.3](chapter-05-03.md).

## 5.1.5. Когда использовать текстовые форматы

Текстовые форматы (CSV, JSON) целесообразно использовать когда:

- Нужна **максимальная простота** и **читаемость** (просмотр в консоли, отладка, обмен с внешними системами).
- Данные **одноразовые** или объём невелик; требования к скорости запросов и к сжатию не критичны.
- **Входной слой** (landing, raw): данные сначала попадают в HDFS «как есть» (выгрузки из БД, логи, API), затем в отдельном шаге конвертируются в Parquet/ORC или обрабатываются напрямую с парсингом.

Для **витрин**, **аналитических таблиц** и **частых тяжёлых запросов** обычно предпочитают колоночные форматы с сжатием и возможностью выбора столбцов.

## 5.1.6. Типичные ошибки при работе с текстовыми форматами

- **Считать CSV/JSON оптимальными для всех сценариев:** для больших объёмов и аналитических запросов они проигрывают колоночным форматам по объёму, скорости и возможностям (pushdown предикатов, выборка столбцов).
- **Сжимать весь CSV одним Gzip-потоком и ожидать параллельного чтения:** при потоковом сжатии границы блоков HDFS не совпадают с границами записей; каждая Map-задача вынуждена читать с начала до своей позиции или используется несжимаемый текст. Лучше использовать сжатие по блокам (например, в Parquet) или несжатый текст.
- **Игнорировать схему:** без явной схемы (в Hive или в коде) ошибки в данных (лишние поля, неверный тип) обнаруживаются только при выполнении; по возможности задавать схему и валидировать при загрузке.

---

## Ключевое

- **Текстовые форматы** (CSV, JSON) — простые, читаемые, удобные для обмена и отладки; в HDFS хранятся как текст, парсинг при чтении.
- **CSV:** строки с разделителями полей; нет схемы в файле; слабое сжатие; разбиение по строкам возможно, если не сжимать весь файл потоком.
- **JSON:** структурированные записи; гибкая схема, избыточность имён полей; для параллельного чтения предпочтителен формат «одна строка — одна запись» (JSON Lines).
- **Общие ограничения:** нет встроенной схемы, неэффективное сжатие и выборка столбцов; уместны для сырых данных и обмена, для аналитики чаще используют Parquet/ORC.

В [§5.2](chapter-05-02.md) мы разберём SequenceFile — бинарный формат для пар ключ–значение с поддержкой сжатия и использованием в MapReduce.
