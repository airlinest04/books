# §6.2 Метаданные Hive: Metastore и типы таблиц

В [§6.1](chapter-06-01.md) мы разобрали назначение Hive и преобразование HiveQL в job на кластере. Чтобы Hive знал, какие таблицы существуют, какие у них столбцы и **где в HDFS лежат данные**, нужны **метаданные**. Их хранит **Hive Metastore**; от типа таблицы (внутренняя или внешняя) зависит, управляет ли Hive самими файлами данных при удалении таблицы. В этом разделе — что хранится в Metastore, как таблица связывается с каталогами HDFS и в чём разница между **внутренними** и **внешними** таблицами. DDL (CREATE TABLE, форматы, партиции) — в [§6.3](chapter-06-03.md); загрузка и запросы — в [§6.4](chapter-06-04.md). См. [Глоссарий](glossary.md).

---

## 6.2.1. Назначение метаданных

Hive не хранит данные таблицы сам — данные лежат в **файлах в HDFS**. Чтобы выполнить запрос, Hive должен знать: имя таблицы, схему (столбцы и типы), **расположение** каталога с файлами, **формат** файлов (текст, Parquet, ORC и т.д.), при партиционировании — имена и типы столбцов партиций. Вся эта информация — **метаданные**; она хранится отдельно от данных. См. [Глоссарий](glossary.md).

Без метаданных пришлось бы при каждом запросе указывать путь в HDFS, формат и схему вручную. Metastore даёт **единый каталог** таблиц: пользователь обращается к таблице по имени, Hive подставляет путь, формат и схему из метаданных и передаёт их в план выполнения (движок читает файлы по указанному пути с нужным SerDe и форматом).

---

## 6.2.2. Hive Metastore

**Hive Metastore** — сервис (и хранилище), в котором хранятся метаданные Hive: базы данных, таблицы, столбцы, типы, расположение данных в HDFS, формат хранения, партиции и их расположение. Реализация Metastore обычно использует **реляционную БД** (MySQL, PostgreSQL, Derby и др.): таблицы метаданных описывают структуру баз, таблиц, столбцов, партиций и соответствие партиций каталогам в HDFS. См. [Глоссарий](glossary.md).

Архитектурно возможны варианты:

- **Встроенный (embedded) Metastore:** хранилище метаданных (например, Derby) запускается в процессе Hive; подходит для тестов, один процесс.
- **Удалённый (remote) Metastore:** отдельный сервер **Metastore Service**; клиенты Hive (CLI, HiveServer2) подключаются к нему по сети (Thrift). Само хранилище — реляционная БД, к которой обращается только Metastore Service. В кластере обычно используют удалённый Metastore и отдельную БД для надёжности и разделения нагрузки.

При создании таблицы (CREATE TABLE) Hive записывает в Metastore: имя таблицы, схему, формат (STORED AS), при необходимости LOCATION и PARTITIONED BY. При запросе (SELECT) Hive обращается к Metastore, получает путь к данным и параметры формата, и передаёт их в план выполнения.

## 6.2.3. Связь таблицы с каталогами в HDFS

Каждая таблица Hive логически соответствует **каталогу в HDFS** (или в другом совместимом хранилище). Файлы в этом каталоге (и при партиционировании — в подкаталогах) считаются данными таблицы. См. [Глоссарий](glossary.md).

- **Расположение по умолчанию:** для **внутренних** таблиц (см. ниже) Hive сам выбирает каталог в служебном хранилище (например, `/user/hive/warehouse/<db>.db/<table_name>/`). При создании таблицы без LOCATION данные будут писаться в этот каталог.
- **Явное расположение (LOCATION):** в CREATE TABLE можно указать `LOCATION '/path/in/hdfs'`. Тогда данные таблицы — файлы в указанном каталоге. Так обычно задают расположение для **внешних** таблиц, когда данные уже лежат в HDFS и управляются вне Hive (например, залиты другим процессом).
- **Партиционированные таблицы:** каталог таблицы содержит подкаталоги по партициям (например, `dt=2024-01-01/`); в Metastore хранится соответствие партиция (имя, значение) — путь к подкаталогу. Детали — в [§6.5](chapter-06-05.md).

При выполнении запроса движок (MapReduce, Tez, Spark) получает список путей к каталогам/файлам из метаданных и читает их через соответствующий InputFormat/SerDe.

## 6.2.4. Внутренние таблицы (managed tables)

**Внутренняя таблица** (managed table) — таблица, жизненным циклом данных которой **управляет Hive**. При создании без LOCATION Hive создаёт каталог в своей «складе» (warehouse); при **DROP TABLE** Hive **удаляет метаданные и удаляет каталог с данными в HDFS**. Данные такой таблицы считаются принадлежащими Hive: загрузка через INSERT или LOAD попадает в каталог таблицы, удаление таблицы — и данные пропадают. См. [Глоссарий](glossary.md).

Использование: таблицы, которые создаются и наполняются самим Hive (результаты ETL, витрины, промежуточные таблицы). Не подходят для данных, которые должны пережить DROP TABLE или которые создаются и обновляются другими системами без участия Hive.

Создание: `CREATE TABLE ...` без ключевого слова EXTERNAL (по умолчанию таблица внутренняя).

---

## 6.2.5. Внешние таблицы (external tables)

**Внешняя таблица** (external table) — таблица, для которой Hive хранит только **метаданные** (схема, расположение, формат); **данные в HDFS не принадлежат Hive**. При **DROP TABLE** Hive удаляет только запись в Metastore; **каталог и файлы в HDFS остаются**. Данные обычно создаются и пополняются другими процессами (Sqoop, Spark, копирование в HDFS); Hive лишь «навешивает» схему и SQL на уже существующий каталог. См. [Глоссарий](glossary.md).

Использование: сырые данные, загруженные в HDFS извне; общие каталоги, используемые несколькими системами; данные, которые не должны удаляться при удалении таблицы в Hive.

Создание: `CREATE EXTERNAL TABLE ... LOCATION '/path/in/hdfs'`. Путь LOCATION должен указывать на существующий (или будущий) каталог с данными; при добавлении файлов в этот каталог они становятся видимы в таблице после обновления метаданных партиций при необходимости (MSCK REPAIR TABLE или ADD PARTITION).

---

## 6.2.6. Сравнение внутренних и внешних таблиц

| Аспект | Внутренняя (managed) | Внешняя (external) |
|--------|----------------------|--------------------|
| **Кто владеет данными** | Hive (каталог в warehouse или указанный LOCATION) | Внешний процесс; Hive только метаданные |
| **DROP TABLE** | Удаляются метаданные и каталог с данными в HDFS | Удаляются только метаданные; данные в HDFS остаются |
| **Типичное использование** | Витрины, результаты ETL, промежуточные таблицы, созданные Hive | Сырые данные, импорт из Sqoop/других систем, общие каталоги |
| **LOCATION** | Опционально; по умолчанию warehouse | Обычно задаётся явно — каталог, уже существующий в HDFS |

Выбор: если данные создаются и должны жить только в контексте Hive — внутренняя таблица; если данные приходят извне или должны сохраняться при DROP TABLE — внешняя.

---

## Ключевое

- **Метаданные Hive** (схема, расположение, формат, партиции) хранятся в **Hive Metastore**; реализация — обычно реляционная БД; в кластере часто удалённый Metastore Service.
- Каждая таблица соответствует **каталогу в HDFS**; путь задаётся по умолчанию (warehouse) или через LOCATION.
- **Внутренняя таблица:** Hive управляет данными; DROP TABLE удаляет и данные в HDFS; для витрин и таблиц, созданных Hive.
- **Внешняя таблица:** данные не принадлежат Hive; DROP TABLE удаляет только метаданные; для сырых данных и каталогов, управляемых извне.

В [§6.3](chapter-06-03.md) разберём DDL: CREATE TABLE с указанием формата (TEXTFILE, PARQUET, ORC), партиций (PARTITIONED BY) и расположения (LOCATION).
