# §4.4 Запуск приложения и мониторинг в YARN

В [§4.3](chapter-04-03.md) мы разобрали контейнеры, запрос ресурсов и планировщики. В этом разделе — **как приложение попадает в YARN** (MapReduce и Spark) и **как смотреть его статус** в веб-интерфейсе ResourceManager. После прочтения вы сможете запустить MapReduce job (как в [§3.4](chapter-03-04.md)), убедиться, что он выполняется через YARN, и найти логи и статус в UI. С [главы 5](chapter-05-01.md) мы переходим к форматам хранения данных в экосистеме Hadoop. См. [Глоссарий](glossary.md).

## 4.4.1. Запуск MapReduce job через YARN

По умолчанию в Hadoop 2.x и 3.x MapReduce job выполняется **через YARN**: клиент (команда `hadoop jar` или программный вызов) обращается к ResourceManager и запрашивает запуск приложения. См. [Глоссарий](glossary.md).

Краткая последовательность:

1. **Клиент** (например, `hadoop jar wordcount.jar WordCount /input /output`) связывается с **ResourceManager** и передаёт заявку на запуск приложения (тип приложения — MapReduce, путь к JAR, главный класс, аргументы).
2. **ResourceManager** выделяет **контейнер** для **ApplicationMaster** MapReduce и сообщает NodeManager запустить в нём процесс AM. Контейнер для AM запрашивается в очереди по умолчанию (или в указанной при настройке).
3. **ApplicationMaster MapReduce** регистрируется в RM, получает описание job (число Map- и Reduce-задач, входы, выходы) и начинает запрашивать контейнеры: сначала для Map-задач (с учётом локальности к сплитам в HDFS), затем для Reduce-задач.
4. **ResourceManager** по мере доступности ресурсов возвращает AM выделенные контейнеры; AM даёт команды **NodeManager** на соответствующих узлах запустить в контейнерах процессы **MapTask** и **ReduceTask**.
5. Задачи выполняются, читают и пишут HDFS, обмениваются данными при shuffle. AM отслеживает завершение; при сбое задачи может запросить новый контейнер и перезапустить её.
6. По завершении всех задач AM сообщает RM о завершении приложения; клиент получает код возврата (успех/ошибка). Выход job лежит в HDFS в указанном каталоге.

Пользователь запускает только команду `hadoop jar` (или эквивалент); вся координация с YARN выполняется кодом MapReduce (клиент и AM). Конфигурация `mapreduce.framework.name=yarn` (по умолчанию в 2.x/3.x) обеспечивает использование YARN.

## 4.4.2. Запуск Spark через YARN

**Spark** может работать в режиме **YARN**: драйвер и executor’ы запускаются в контейнерах YARN. См. [Глоссарий](glossary.md).

Два типичных режима:

- **YARN client mode:** драйвер (SparkContext) работает на машине, с которой запущена команда (`spark-submit`); только executor’ы запрашиваются у YARN и запускаются в контейнерах. Удобно для интерактивных сценариев (spark-shell, отладка): логи драйвера и вывод в консоли видны сразу. При отключении клиентской машины приложение может прерваться.
- **YARN cluster mode:** драйвер тоже запускается в контейнере YARN (как ApplicationMaster или в отдельном контейнере, в зависимости от версии); клиент только отправляет заявку и может отключиться. Подходит для пакетных job’ов, отправленных из скриптов или планировщиков.

Команда запуска (пример):

```bash
spark-submit --master yarn --deploy-mode cluster \
  --class com.example.MainClass myapp.jar /input /output
```

Spark-«ApplicationMaster» (или драйвер в cluster mode) запрашивает у ResourceManager контейнеры для executor’ов; данные по-прежнему могут читаться из HDFS. Просмотр запущенного Spark-приложения — в том же UI ResourceManager, что и для MapReduce.

## 4.4.3. Веб-интерфейс ResourceManager

**ResourceManager** предоставляет **веб-интерфейс** для мониторинга кластера и приложений. По умолчанию он доступен по порту **8088** (настраивается в yarn-site.xml). См. [Глоссарий](glossary.md).

Типичный адрес: **http://&lt;hostname_resourcemanager&gt;:8088**

В UI обычно доступны:

- **Cluster / Overview:** общая информация о кластере — число узлов, объём памяти и vcore, загрузка, версия YARN.
- **Applications:** список приложений — запущенные, завершённые, с ошибкой. Для каждого приложения: id, имя, пользователь, очередь, состояние (RUNNING, FINISHED, FAILED и т.д.), время старта и длительность. Можно отфильтровать по состоянию и по пользователю.
- **Application detail:** по клику на приложение — детали: тип (MapReduce, Spark), контейнер ApplicationMaster, список контейнеров (задач), ссылки на логи (stdout, stderr, syslog контейнеров). Для MapReduce часто есть ссылка на **ApplicationMaster tracking URL** — переход к UI самого AM (прогресс Map/Reduce, счётчики, неудачные задачи).
- **Nodes:** список узлов (NodeManager’ов), состояние (RUNNING, UNHEALTHY, LOST), загрузка по памяти и CPU, список контейнеров на узле.
- **Scheduler:** при использовании Capacity или Fair Scheduler — состояние очередей, использованные и свободные ресурсы по очередям.

Через UI удобно проверять, что job действительно принят YARN, на каких узлах он выполняется и где смотреть логи при ошибках.

## 4.4.4. Логи приложения и контейнеров

Логи помогают отлаживать падения задач и приложений. См. [Глоссарий](glossary.md).

- **Логи ApplicationMaster:** в карточке приложения в UI RM есть ссылка **ApplicationMaster** или **Logs**; открывается страница с логами AM (stdout, stderr). Там видно, какие контейнеры запрашивались и выделялись, перезапуски задач, финальный статус.
- **Логи контейнеров (задач):** для каждой задачи (MapTask, ReduceTask, Spark executor) в деталях приложения перечислены контейнеры; по клику на контейнер — логи этого контейнера (stdout, stderr). В них — вывод пользовательского кода (например, stack trace при исключении в map/reduce).
- **Где физически хранятся логи:** на узлах в каталогах, заданных конфигурацией YARN (yarn.nodemanager.log-dirs); при включённом **Log Aggregation** логи после завершения контейнера копируются в HDFS и доступны по ссылкам в UI даже после освобождения узла.

Для MapReduce дополнительно полезен **Job History Server**: он хранит историю завершённых job’ов (счётчики, длительность этапов, неудачные попытки). Адрес History Server настраивается отдельно; часто на него ведут ссылки из UI RM для завершённых MapReduce-приложений.

## 4.4.5. Типичные проблемы при запуске и где смотреть

| Проблема | Где смотреть |
|----------|----------------|
| Job не стартует, «Application submission failed» | Логи клиента (консоль при hadoop jar); доступность RM, очередь, лимиты пользователя. |
| Job принят, но «зависает» без контейнеров | UI RM — очередь приложений; возможно, нет свободных ресурсов или очередь переполнена; логи AM — запросы контейнеров. |
| Задача падает (Map/Reduce FAILED) | В приложении в UI RM — список контейнеров, контейнер с FAILED; логи этого контейнера (stderr) — исключение в коде. |
| «Container killed» / OOM | Логи контейнера; увеличить память контейнера для этого типа задачи (mapreduce.map.memory.mb, mapreduce.reduce.memory.mb или аналог для Spark). |

## 4.4.6. Типичные ошибки при работе с UI и запуском

- **Ожидать, что UI доступен на localhost:** в распределённом кластере RM работает на выделенном узле; адрес и порт задаются конфигурацией (yarn.resourcemanager.webapp.address); подключаться нужно по имени/IP узла RM.
- **Путать UI ResourceManager и UI ApplicationMaster MapReduce:** RM показывает все приложения и общее состояние кластера; детали одного MapReduce job (прогресс map/reduce, счётчики) — в UI самого AM, ссылка на который есть в карточке приложения в RM.
- **Игнорировать очередь и лимиты:** при «нет ресурсов» проверить, в какую очередь отправлено приложение и нет ли лимита по пользователю или по очереди; при необходимости указать очередь в конфигурации job или в spark-submit.

---

## Ключевое

- **MapReduce через YARN:** клиент отправляет job в RM; RM выделяет контейнер для AM MapReduce; AM запрашивает контейнеры для Map- и Reduce-задач, запускает их через NM; по завершении выход в HDFS.
- **Spark через YARN:** spark-submit с --master yarn; client mode (драйвер на клиенте) или cluster mode (драйвер в контейнере); executor’ы всегда в контейнерах YARN.
- **UI ResourceManager** (по умолчанию порт 8088): список приложений, узлы, планировщик; в карточке приложения — детали, ссылки на логи AM и контейнеров.
- **Логи:** AM и контейнеры — через UI; при Log Aggregation логи в HDFS; для MapReduce — Job History Server для истории job’ов.

В [§5.1](chapter-05-01.md) мы переходим к форматам хранения данных в экосистеме Hadoop: текстовые форматы (CSV, JSON), их плюсы и ограничения.
