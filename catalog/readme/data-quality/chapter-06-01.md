# §6.1 Метрики качества

В [§5.4](chapter-05-04.md) мы завершили главу о проверках в пайплайне ETL. Проверки порождают **результаты**: сколько записей прошло валидацию, сколько отклонено, совпали ли контрольные суммы. Чтобы управлять качеством непрерывно, эти результаты нужно **измерять и накапливать** — то есть ввести **метрики качества**. Глава 6 посвящена метрикам, порогам, алертам и интеграции с оркестрацией. В этом разделе мы определим, какие метрики качества собирать: процент валидных записей, количество отклонённых, тренд по дням и метрики по измерениям качества (полнота, валидность, уникальность и т.д.). Пороги и алерты — в [§6.2](chapter-06-02.md); дашборды и отчётность — в [§6.3](chapter-06-03.md).

---

## 6.1.1. Что такое метрика качества

**Метрика качества** — измеряемый показатель, отражающий результат проверок качества данных за заданный период или срез: число или доля записей, прошедших или не прошедших правило; агрегат (COUNT, SUM) по отклонённым записям; значение контрольной суммы; факт выполнения или нарушения проверки (да/нет). Метрики собираются по результатам шагов валидации в пайплайне ([§5.2](chapter-05-02.md)), проверок после загрузки ([§5.3](chapter-05-03.md)) и при необходимости по отдельным мониторинговым запросам. Накопление метрик во времени даёт **тренд**: деградация или улучшение качества; сравнение с порогами — основа для алертов ([§6.2](chapter-06-02.md)). См. [Глоссарий](glossary.md).

---

## 6.1.2. Процент валидных записей

**Процент валидных записей** (pass rate, validation rate) — доля записей в срезе, прошедших все применённые правила валидации. Вычисляется как: `(число валидных записей / число записей в срезе) * 100`. Число валидных — записи, переданные на загрузку после этапа преобразования ([§5.2](chapter-05-02.md)); число в срезе — записи, поступившие на валидацию (после извлечения или после маппинга). Альтернатива: по каждому правилу отдельно — доля записей, прошедших это правило (например, «% записей с непустым contract_id»).

Интерпретация: 100% — все записи прошли проверки; при падении ниже порога (например, 99%) — алерт, разбор причин (источник, изменение правил). Метрику считают по срезу (партиция за дату, batch) и при необходимости агрегируют по дню или по неделе для тренда. См. [Глоссарий](glossary.md).

---

## 6.1.3. Количество отклонённых записей

**Количество отклонённых записей** (rejected count) — число записей, не прошедших валидацию и отклонённых или отправленных в кварантин за данный срез или за период. Прямой результат работы шага валидации при преобразовании ([§5.2](chapter-05-02.md)): разница между числом записей до валидации и числом записей, переданных на загрузку. Можно детализировать по **причине** отклонения (какое правило нарушено): тогда метрики — «число отклонённых по правилу X», «число отклонённых по правилу Y» — помогают выявить, какое правило чаще всего нарушается и где править источник или правило.

Интерпретация: рост числа отклонённых при стабильном объёме среза — сигнал деградации качества или ужесточения правил; сравнение с порогом (например, не более N отклонённых в день) задаёт алерт. Метрику логируют по каждому прогону и при необходимости суммируют по дню/неделе. См. [Глоссарий](glossary.md).

---

## 6.1.4. Тренд по дням

**Тренд по дням** — изменение метрик качества во времени: процент валидных, число отклонённых, число дубликатов, расхождение контрольных сумм и т.д. по каждому дню (или по каждому прогону). Тренд позволяет увидеть: стабильно ли качество, было ли резкое ухудшение после определённой даты (смена источника, изменение правил), есть ли сезонность или рост числа отклонённых со временем.

Реализация: метрики по каждому прогону или по каждому дню записываются в таблицу метрик (pipeline_id, partition_date, metric_name, metric_value, recorded_at); по ним строят графики и отчёты. Пороги и алерты ([§6.2](chapter-06-02.md)) могут быть заданы не только на «текущее значение», но и на «изменение относительно вчера/недели» (например, алерт при росте числа отклонённых более чем на X% за день). См. [Глоссарий](glossary.md).

---

## 6.1.5. Метрики по измерениям качества

Метрики можно группировать по **измерениям качества** (глава 2), чтобы видеть, по какому измерению качество деградирует или улучшается:

| Измерение | Примеры метрик |
|-----------|----------------|
| **Полнота** | Доля записей с заполненным полем X (% не null); число записей с null в обязательных полях; число пропущенных партиций/дат за период. |
| **Валидность** | Доля записей, прошедших правила формата и справочника; число записей с невалидным значением по полю X. |
| **Уникальность** | Число дубликатов по ключу за срез; доля уникальных записей (COUNT(DISTINCT key) / COUNT(*)). |
| **Согласованность** | Число записей-сирот (нарушение референциальной целостности); число записей с нарушением бизнес-правила (сумма частей <> целому). |
| **Своевременность** | Факт выполнения загрузки к дедлайну (да/нет); задержка в минутах/часах; % дней с выполненным SLA. |
| **Точность** | Число расхождений при сверке с эталоном; разница контрольных сумм источник vs приёмник. |

Такая группировка помогает при разборе инцидентов и при приоритизации доработок: если растёт число отклонённых по валидности — смотреть форматы и справочники; если по полноте — смотреть источник и обязательные поля. Связь метрик с правилами валидации — глава 4; с проверками в ETL — глава 5. См. [Глоссарий](glossary.md).

## 6.1.6. Где хранить и как собирать метрики

Метрики нужно **сохранять** для тренда и отчётности. Варианты:

- **Таблица метрик в DWH или в отдельной БД:** каждая строка — прогон (или день), метрика, значение, дата записи. Заполняется скриптами пайплайна или отдельной задачей после проверок.
- **Логи пайплайна:** структурированный лог (JSON, поля в таблице логов), из которого потом извлекают метрики для дашбордов и алертов.
- **Специализированные системы мониторинга:** экспорт метрик в Prometheus, Grafana, облачный мониторинг и т.д.; алерты настраиваются там.

Сбор: в конце шага валидации ([§5.2](chapter-05-02.md)) и после загрузки ([§5.3](chapter-05-03.md)) пайплайн записывает в таблицу метрик или в лог: pipeline_id, partition_date, extract_count, transform_valid_count, transform_rejected_count, load_count, checksum_match (да/нет) и при необходимости детали по правилам. Периодические отчёты и дашборды ([§6.3](chapter-06-03.md)) читают из этой таблицы. См. [Глоссарий](glossary.md).

## 6.1.7. Сводка метрик качества

| Метрика | Описание | Использование |
|---------|----------|---------------|
| % валидных записей | Доля записей, прошедших валидацию, в срезе | Тренд, порог для алерта (например, < 99%) |
| Количество отклонённых | Число записей, отклонённых или в кварантине за срез/период | Тренд, порог; детализация по правилу — для разбора |
| Тренд по дням | Значения метрик по датам | Графики, выявление деградации и аномалий |
| Метрики по измерениям | Группировка по полноте, валидности, уникальности и т.д. | Приоритизация и расследование по типу проблемы |
| Row count / контрольные суммы | По этапам ETL (см. главу 5) | Проверка целостности; расхождение — метрика для алерта |

Метрики без порогов и алертов дают только наблюдаемость; чтобы качество управлялось реактивно, нужны пороги и реакция при их превышении ([§6.2](chapter-06-02.md)). См. [Глоссарий](glossary.md).

## 6.1.8. Типичные ошибки

- **Собирать метрики без привязки к срезу и дате:** без partition_date или даты прогона невозможно строить тренд и сопоставлять с конкретной загрузкой; каждая запись метрики должна содержать идентификатор среза и момент записи.
- **Учитывать только общий % валидных без детализации по правилам:** при падении процента непонятно, какое правило нарушается чаще; полезно хранить число отклонённых по правилу или по причине.
- **Не накапливать историю:** разовые проверки без записи в таблицу метрик не дают тренда; для мониторинга нужна персистентная история.
- **Путать метрики пайплайна и метрики качества данных:** время выполнения задачи, использование CPU — метрики пайплайна/инфраструктуры; процент валидных записей, число отклонённых — метрики качества данных. Оба типа полезны, но решают разные задачи.

---

## Ключевое

- **Метрика качества** — измеряемый показатель по результатам проверок: доля валидных записей, число отклонённых, контрольные суммы, факт нарушения правила; накопление даёт тренд и основу для порогов и алертов.
- **Процент валидных записей** — доля записей, прошедших валидацию; падение ниже порога — сигнал к разбору. **Количество отклонённых** — число записей, не прошедших проверки за срез/период; детализация по правилу помогает при расследовании.
- **Тренд по дням** — изменение метрик во времени; выявляет деградацию и аномалии; метрики записываются по каждому прогону/дню с привязкой к срезу и дате.
- **Метрики по измерениям** (полнота, валидность, уникальность, согласованность, своевременность, точность) позволяют группировать проблемы и приоритизировать действия.
- Метрики хранятся в таблице метрик или в логах; собираются по результатам шагов валидации и загрузки; без порогов и алертов — только наблюдаемость, управление — в §6.2.

В [§6.2](chapter-06-02.md) мы разберём **пороги и алерты**: когда считать качество неприемлемым, как настраивать алерты при превышении порога и эскалацию.
