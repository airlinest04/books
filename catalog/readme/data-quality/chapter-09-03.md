# §9.3 Правила и проверки в ETL

В [§9.2](chapter-09-02.md) мы выполнили профилирование источника и определили правила валидации. Следующий шаг — **реализовать проверки в пайплайне ETL**: встроить их в точки проверки ([§9.1](chapter-09-01.md)), организовать **кварантин при ошибках** и **логирование**. В этом разделе мы разберём реализацию проверок, структуру кварантина и что логировать. Метрики, алерты и отчёт по качеству — в [§9.4](chapter-09-04.md). Детали проверок по этапам ETL — глава 5; обработка ошибочных данных — глава 7. См. [Глоссарий](glossary.md).

---

## 9.3.1. Реализация проверок в пайплайне

Правила, сформулированные в §9.2, реализуются **в точках проверки** пайплайна. Каждая точка — отдельная задача (таск) в оркестраторе или явный шаг в ETL-скрипте ([§6.4](chapter-06-04.md)).

**После извлечения (Raw):** проверка полноты среза ([§5.1](chapter-05-01.md)): все ли ожидаемые артефакты за дату/партицию присутствуют; читаемость файла или доступность источника; при возможности — row count и контрольные суммы по источнику. Реализация: скрипт или оператор, который проверяет наличие файлов/партиций по регламенту и при нарушении завершается с ошибкой (fail задачи) или записывает метрику и алертит. Эталон (ожидаемый список дат или row count) берётся из конфигурации или из регламента выгрузки.

**После преобразования (Staging):** применение правил валидации ([§5.2](chapter-05-02.md)) к преобразованным данным. Для каждой записи проверяются условия (NOT NULL, диапазон, формат, справочник, уникальность ключа, бизнес-правила); записи, не прошедшие проверку, не передаются на загрузку в Core, а направляются в кварантин или журнал ошибок с причиной (rule_id, описание). Реализация: в коде ETL (цикл по записям, проверка правил), в SQL (вставка во временную таблицу, выбор невалидных по условиям) или средствами ETL-инструмента. Обязательно фиксировать **число валидных** и **число отклонённых** (и при необходимости по каждому правилу) для метрик и для эталона при проверке загрузки.

**После загрузки в Core:** сравнение row count и контрольных сумм в Core с эталоном (число и суммы по валидным записям после Staging) ([§5.3](chapter-05-03.md), [§5.4](chapter-05-04.md)); проверка отсутствия дубликатов по ключу в целевой таблице. Реализация: запрос к Core по срезу, сравнение с сохранённым эталоном; при расхождении — fail задачи или алерт. Эталон передаётся из шага Staging (XCom, таблица метрик или конфиг).

**Перед открытием витрины (Mart):** контрольные итоги витрины vs эталон, SLA ([§8.4](chapter-08-04.md)). Реализация: запрос к витрине, сравнение с ожиданием; при нарушении — блокировка шага «открыть доступ» и алерт.

Все проверки при нарушении должны либо завершать задачу с ошибкой (жёсткий fail), либо записывать предупреждение и отправлять алерт (мягкое предупреждение) по политике ([§6.4](chapter-06-04.md)). См. [Глоссарий](glossary.md).

## 9.3.2. Кварантин при ошибках

Невалидные записи (не прошедшие валидацию на Staging) не загружаются в Core; по политике организации ([§7.1](chapter-07-01.md)) они либо **отклоняются с записью в журнал ошибок**, либо **загружаются в таблицу кварантина** ([§7.2](chapter-07-02.md)).

**Таблица кварантина** для нашего сценария должна содержать:

- Копию данных записи (все поля преобразованной записи или payload в одном поле).
- Метаданные: `run_id`, `partition_date` (срез), `rejected_at` (время отклонения).
- Причину отклонения: `rule_id` (идентификатор правила из §9.2), `rejection_reason` (текстовое описание). Без причины разбор и метрики по правилам невозможны ([§7.2](chapter-07-02.md)).
- При необходимости — статус для повторной обработки (`pending`, `loaded`, `ignored`).

Запись попадает в кварантин в том же прогоне, в котором не прошла валидацию: в шаге преобразования после применения правил невалидные записи пишутся в таблицу кварантина (INSERT), валидные — передаются на загрузку в Core. Одна и та же задача может выполнять и валидацию, и запись в кварантин, либо запись в кварантин выносится в отдельную задачу, следующую за валидацией. См. [Глоссарий](glossary.md).

## 9.3.3. Логирование

**Логирование** обеспечивает прослеживаемость и вход для метрик ([§9.4](chapter-09-04.md)). Что логировать:

- **В лог задачи оркестратора:** краткий итог прогона: срез (дата/партиция), row count после извлечения, row count валидных после валидации, row count отклонённых (и при возможности по rule_id), row count загруженных в Core, результат проверок (passed/failed). Это позволяет при падении задачи быстро понять, на каком этапе и с какими числами произошла ошибка.
- **В таблицу метрик качества** ([§6.1](chapter-06-01.md)): pipeline_id, partition_date, run_id, extract_count, valid_count, rejected_count, load_count, timestamp; при детализации — rejected_by_rule (rule_id, count). Таблица метрик — источник для дашбордов, порогов и алертов в §9.4.
- **В таблицу кварантина или журнал ошибок:** каждая отклонённая запись с причиной (см. п. 9.3.2).

Запись в таблицу метрик выполняется после каждого значимого шага (после извлечения — extract_count; после валидации — valid_count, rejected_count; после загрузки в Core — load_count) или одной записью в конце прогона с итоговыми значениями. Важно не только логировать при ошибках, но и при успешном прохождении — иначе тренд и доля валидных записей по дням недоступны. См. [Глоссарий](glossary.md).

## 9.3.4. Типичные ошибки

- **Реализовать проверки без привязки к rule_id:** при отклонении записи причина должна содержать идентификатор правила; иначе в метриках и в кварантине нельзя агрегировать по правилам и приоритизировать исправления.
- **Не записывать метрики при успешном прогоне:** метрики нужны и при success (valid_count, rejected_count, load_count за каждый день); иначе дашборд и тренд пустые.
- **Сравнивать загрузку в Core с row count извлечения при наличии отклонений на Staging:** эталон для проверки загрузки — число валидных записей (после Staging), а не число извлечённых ([§5.3](chapter-05-03.md), [§5.4](chapter-05-04.md)); иначе «расхождение» будет ложным.
- **Писать в кварантин без rejection_reason:** разбор и повторная обработка затруднены; в каждую запись кварантина должна попадать причина (rule_id и описание).

## Ключевое

- **Реализация проверок:** правила из §9.2 встраиваются в точки проверки (после извлечения, после преобразования, после загрузки в Core, перед открытием витрины); каждая проверка — отдельная задача или шаг; при нарушении — fail или warning с алертом.
- **Кварантин:** таблица с копией записи, run_id, срезом, rejected_at, rule_id и rejection_reason; невалидные записи пишутся в кварантин в шаге валидации; без причины разбор и метрики по правилам невозможны.
- **Логирование:** в лог задачи — итог прогона (срез, счётчики, результат проверок); в таблицу метрик — pipeline_id, срез, run_id, extract_count, valid_count, rejected_count, load_count (и при успехе тоже); в кварантин/журнал — каждая отклонённая запись с причиной.

В [§9.4](chapter-09-04.md) мы настроим **метрики, алерты и отчёт**: сбор метрик из пайплайна, пороги и уведомления, отчёт по качеству.
