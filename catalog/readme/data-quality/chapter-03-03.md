# §3.3 Null, дубликаты, выбросы

В [§3.2](chapter-03-02.md) мы разобрали статистики и распределения — базовые показатели профиля. Три типа аномалий заслуживают отдельного внимания при профилировании: **null** (пропуски), **дубликаты** по ключу и **выбросы** (значения, резко выделяющиеся на фоне остальных). Их выявление даёт первичную оценку полноты (§2.1), уникальности (§2.5) и валидности/точности; на основе профиля формулируют правила валидации и решают, где нужна очистка или дедупликация. В этом разделе мы разберём, как считать долю null по полям, как детектировать дубликаты по ключу и как выявлять выбросы (статистическими методами и по доменным правилам), с примерами запросов в PostgreSQL.

---

## 3.3.1. Доля null по полям

**Null** (пропуск, отсутствующее значение) в поле означает, что значение не задано. Для профиля по каждому полю считают: сколько строк имеют null в этом поле; какая доля от общего числа строк. Высокая доля null в поле, которое по смыслу должно быть заполнено, указывает на проблему полноты (см. [§2.1](chapter-02-01.md)); нулевая доля — поле заполнено во всех записях (при необходимости можно зафиксировать как обязательное).

Формула: число null = `COUNT(*) - COUNT(column)` (в SQL COUNT(column) не считает null). Доля null в процентах: `100.0 * (COUNT(*) - COUNT(column)) / NULLIF(COUNT(*), 0)`.

Пример: доля null по нескольким полям одной таблицы (PostgreSQL):

```sql
SELECT COUNT(*) AS total_rows,
       COUNT(*) - COUNT(contract_id)   AS null_contract_id,
       COUNT(*) - COUNT(sign_date)      AS null_sign_date,
       COUNT(*) - COUNT(client_id)      AS null_client_id,
       ROUND(100.0 * (COUNT(*) - COUNT(contract_id)) / NULLIF(COUNT(*), 0), 2)   AS pct_null_contract_id,
       ROUND(100.0 * (COUNT(*) - COUNT(sign_date))   / NULLIF(COUNT(*), 0), 2)   AS pct_null_sign_date,
       ROUND(100.0 * (COUNT(*) - COUNT(client_id))   / NULLIF(COUNT(*), 0), 2)   AS pct_null_client_id
FROM staging.contracts
WHERE load_date = CURRENT_DATE - 1;
```

По результату видно, какие поля чаще всего пустые; поля с высоким процентом null — кандидаты на правило полноты (обязательное/желательное с порогом) или на разбор причин пропусков в источнике. Пустая строка (`''`) в части СУБД не совпадает с null; при необходимости считают и «пустые» строки: `column IS NULL OR TRIM(column) = ''`. См. [Глоссарий](glossary.md).

## 3.3.2. Детекция дубликатов по ключу

**Дубликаты** — две или более записей с одинаковым значением ключа (или составного ключа), где по бизнес-правилам должна быть одна запись. В профилировании выявляют: есть ли такие ключи; сколько их; сколько «лишних» записей (общее число записей минус число уникальных ключей). Методика совпадает с [§2.5](chapter-02-05.md): группировка по ключу, отбор групп с COUNT(*) > 1.

Пример: ключи с дубликатами и число дубликатов по ключу (PostgreSQL):

```sql
SELECT order_id, order_date, COUNT(*) AS cnt
FROM staging.orders
WHERE order_date = CURRENT_DATE - 1
GROUP BY order_id, order_date
HAVING COUNT(*) > 1
ORDER BY cnt DESC;
```

Сводная метрика — общее число «лишних» записей:

```sql
SELECT COUNT(*) AS total_rows,
       COUNT(DISTINCT (order_id, order_date)) AS unique_keys,
       COUNT(*) - COUNT(DISTINCT (order_id, order_date)) AS duplicate_rows
FROM staging.orders
WHERE order_date = CURRENT_DATE - 1;
```

Если `duplicate_rows` > 0, в срезе есть дубликаты; список ключей из первого запроса даёт материал для разбора (повторная загрузка, дубли в источнике) и для решения о дедупликации или проверке уникальности в ETL. Выбор ключа уникальности должен быть зафиксирован до интерпретации (см. §2.5). См. [Глоссарий](glossary.md).

## 3.3.3. Выбросы: статистические методы

**Выброс** (outlier) — значение, резко отличающееся от основной массы данных: аномально большое или малое число, дата далеко от типичного диапазона. Выбросы искажают среднее и агрегаты, могут указывать на ошибки ввода или на редкие, но легитимные случаи. В профилировании выбросы выявляют двумя подходами: **статистический** (по разбросу данных) и **доменный** (по правилам предметной области).

**Статистические методы** опираются на распределение значений в поле:

- **По стандартному отклонению:** значения за пределами k стандартных отклонений от среднего (например, |x - AVG| > 2 * STDDEV или 3 * STDDEV) считают выбросами. Чувствительно к уже имеющимся выбросам (среднее и STDDEV смещаются).
- **По межквартильному размаху (IQR):** границы — Q1 − 1.5*IQR и Q3 + 1.5*IQR, где IQR = Q3 − Q1 (квартили). Значения вне этих границ — кандидаты в выбросы. Менее чувствительно к экстремумам, чем метод по STDDEV.
- **По перцентилям:** значения ниже 1% или выше 99% (или другие пороги) помечать для проверки. Простая реализация через PERCENTILE_CONT в окне или подзапросе.

Пример: записи с `amount` вне интервала [Q1 − 1.5*IQR, Q3 + 1.5*IQR] (PostgreSQL, через подзапрос с перцентилями):

```sql
WITH bounds AS (
  SELECT PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY amount) - 1.5 *
         (PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY amount) -
          PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY amount)) AS lower_bound,
         PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY amount) + 1.5 *
         (PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY amount) -
          PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY amount)) AS upper_bound
  FROM staging.orders
  WHERE load_date = CURRENT_DATE - 1 AND amount IS NOT NULL
)
SELECT o.order_id, o.amount
FROM staging.orders o
CROSS JOIN bounds b
WHERE o.load_date = CURRENT_DATE - 1
  AND o.amount IS NOT NULL
  AND (o.amount < b.lower_bound OR o.amount > b.upper_bound);
```

Результат — список записей с аномальными суммами по критерию IQR; их можно выгрузить для ручной проверки или заложить пороги в правила валидации. См. [Глоссарий](glossary.md).

## 3.3.4. Выбросы: доменные правила

**Доменные выбросы** — значения, допустимые с точки зрения типа и формата, но недопустимые или подозрительные по правилам предметной области. Примеры: сумма операции выше лимита по регламенту; отрицательное количество при отсутствии возвратов; дата рождения в будущем; возраст 200 лет. Такие правила задаются не распределением в данных, а бизнес-требованиями; в профилировании их применяют для подсчёта числа «подозрительных» записей и для формулирования правил валидации (диапазон, справочник).

Пример: записи с `amount` вне доменного диапазона (например, отрицательные или выше 10 млн):

```sql
SELECT order_id, amount
FROM staging.orders
WHERE load_date = CURRENT_DATE - 1
  AND (amount < 0 OR amount > 10000000);
```

Доменные правила часто совпадают с правилами валидности (глава 4, §2.6); профилирование выявляет, сколько записей уже нарушают эти правила в источнике, и помогает задать пороги и реакцию (отклонение, кварантин, алерт). Статистические выбросы могут не нарушать доменные правила; доменные — не обязательно выглядят как статистические выбросы. Оба подхода дополняют друг друга. См. [Глоссарий](glossary.md).

## 3.3.5. Сводка: null, дубликаты, выбросы в профиле

| Аномалия | Что считаем | Связь с измерением качества | Типичное действие по результату |
|----------|-------------|-----------------------------|----------------------------------|
| Null | Доля null по каждому полю | Полнота (§2.1) | Зафиксировать обязательные поля, пороги полноты; разобрать причины пропусков. |
| Дубликаты | Число ключей с COUNT > 1; число лишних записей | Уникальность (§2.5) | Ввести дедупликацию или проверку уникальности в ETL; проверить источник. |
| Выбросы (статистические) | Записи вне границ (IQR, STDDEV, перцентили) | Ориентир для валидности/точности | Выгрузить для проверки; при необходимости ограничить диапазон или пометить. |
| Выбросы (доменные) | Записи, нарушающие бизнес-правила (диапазон, формат) | Валидность (§2.6) | Задать правила валидации; отклонять или отправлять в кварантин. |

Включение этих показателей в профиль даёт целостную картину аномалий и основу для правил в главе 4 и проверок в ETL (главы 5–7).

## 3.3.6. Типичные ошибки

- **Считать только null, игнорируя пустую строку:** в части источников пропуск приходит как `''`, а не null; для полноты при необходимости учитывать оба варианта.
- **Искать дубликаты без зафиксированного ключа:** без ключа «дубликат» не определён; возможны ложные выводы (разные сущности с совпадающими атрибутами) или пропуск дублей (неполный ключ).
- **Считать все статистические выбросы ошибками:** экстремальные значения могут быть корректными (крупная сделка, редкое событие); статистика лишь выделяет кандидатов на проверку, решение — по домену или по эталону.
- **Игнорировать доменные правила при профилировании:** без доменных границ (лимиты сумм, допустимые коды) профиль не покажет, сколько записей уже невалидны по бизнес-правилам; доменные правила нужно явно задать или согласовать с владельцем данных.

---

## Ключевое

- **Доля null по полям:** COUNT(*) − COUNT(column), доля в %; высокий процент null — сигнал к правилам полноты и разбору причин пропусков; при необходимости учитывать пустую строку.
- **Дубликаты по ключу:** GROUP BY key HAVING COUNT(*) > 1; число лишних записей = COUNT(*) − COUNT(DISTINCT key); ключ должен быть зафиксирован; результат — вход для дедупликации и проверок уникальности в ETL.
- **Выбросы статистические:** значения вне границ (IQR, k*STDDEV, перцентили); выявляют кандидатов на проверку, не обязательно ошибки.
- **Выбросы доменные:** значения, нарушающие бизнес-правила (диапазон, лимиты, формат); связь с валидностью; задают правила валидации и реакцию на невалидные записи.
- Null, дубликаты и выбросы — обязательные элементы профиля; по ним формулируют правила (глава 4) и проектируют проверки в ETL (главы 5–7).
