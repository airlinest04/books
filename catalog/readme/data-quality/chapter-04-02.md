# §4.2 Правила на уровне поля

В [§4.1](chapter-04-01.md) мы ввели типы правил валидации: бизнес, технические и соответствия. Правила **на уровне поля** проверяют **одно значение** в одной колонке: заполнено ли поле, входит ли значение в диапазон, соответствует ли формату или справочнику. В этом разделе мы разберём пять видов полевых правил: NOT NULL (обязательность), диапазон, формат, справочник и регулярное выражение — и их реализацию в SQL и в ETL. Эти правила соответствуют измерениям полноты и валидности (глава 2) и часто реализуются первыми при проектировании проверок.

---

## 4.2.1. NOT NULL (обязательность)

Правило **NOT NULL** — поле не должно содержать null (и при необходимости пустую строку). Относится к полноте ([§2.1](chapter-02-01.md)): обязательные поля должны быть заполнены в каждой записи.

**Формулировка:** «Поле X обязательно к заполнению» или «В поле X не допускается null».

**Реализация:**

- **В СУБД:** ограничение `NOT NULL` на колонке при создании или изменении таблицы; при попытке вставить null СУБД вернёт ошибку.
- **В ETL:** перед загрузкой запрос или проверка в коде: отбор записей, где поле null (или `TRIM(field) = ''`); такие записи не загружаются в целевой слой или отправляются в кварантин.
- **Проверка «есть ли нарушения»:** `SELECT COUNT(*) FROM table WHERE field IS NULL [AND filter];` — если результат > 0, правило нарушено.

Пример (PostgreSQL): найти записи с пустым обязательным полем `contract_id`:

```sql
SELECT * FROM staging.contracts
WHERE load_date = CURRENT_DATE - 1 AND contract_id IS NULL;
```

Если нужно учитывать и пустую строку: `AND (contract_id IS NULL OR TRIM(contract_id) = '')`. В целевой таблице ограничение NOT NULL гарантирует, что нарушение не попадёт в БД при прямой вставке; при массовой загрузке проверку часто выполняют до вставки. См. [Глоссарий](glossary.md).

---

## 4.2.2. Диапазон

Правило **диапазон** — значение должно находиться в заданных границах: для числа — min и max (включительно или исключительно), для даты — не раньше и не позже заданных границ. Относится к валидности ([§2.6](chapter-02-06.md)).

**Формулировка:** «Поле X в диапазоне [min, max]» или «Дата X не раньше 1900-01-01 и не позже текущей даты».

**Реализация:**

- **В СУБД:** ограничение CHECK: `CHECK (amount >= 0 AND amount <= 1000000)`, `CHECK (sign_date >= '1900-01-01' AND sign_date <= CURRENT_DATE)`.
- **В ETL:** фильтр или отбор невалидных: записи, где значение вне диапазона, отклоняются или пишутся в кварантин.
- **Проверка:** `SELECT * FROM table WHERE field < min OR field > max [AND filter];`

Пример: записи с `amount` вне допустимого диапазона [0, 999999999.99]:

```sql
SELECT order_id, amount
FROM staging.orders
WHERE load_date = CURRENT_DATE - 1
  AND (amount IS NOT NULL AND (amount < 0 OR amount > 999999999.99));
```

Для дат типично: дата не в будущем, дата окончания не раньше даты начала (последнее уже правило на уровне записи — два поля). См. [Глоссарий](glossary.md).

---

## 4.2.3. Формат

Правило **формат** — значение должно соответствовать заданной структуре: дата в определённом виде (YYYY-MM-DD), строка фиксированной или ограниченной длины, число без лишних символов. Относится к валидности ([§2.6](chapter-02-06.md)).

**Формулировка:** «Поле X в формате Y» (например, «дата в формате ISO 8601», «код из ровно 3 заглавных букв»).

**Реализация:**

- **Приведение типа:** попытка преобразовать строку в date/numeric; при ошибке значение невалидно. В SQL проверка через безопасное приведение (например, в PostgreSQL — функция, возвращающая null при невалидной дате) или в коде ETL при разборе.
- **Длина:** `LENGTH(column) BETWEEN min_len AND max_len`; для фиксированной длины — `LENGTH(column) = N`.
- **Регулярное выражение** (см. ниже) — частный случай формата для строк.

Пример: поле `contract_no` — только цифры, длина от 1 до 20 символов (PostgreSQL):

```sql
SELECT contract_id, contract_no
FROM staging.contracts
WHERE load_date = CURRENT_DATE - 1
  AND contract_no IS NOT NULL
  AND (contract_no !~ '^[0-9]+$' OR LENGTH(contract_no) < 1 OR LENGTH(contract_no) > 20);
```

Оператор `~` в PostgreSQL — совпадение с regex; `!~` — не совпадает. Для даты в формате ISO проверка: приведение к `::date` в блоке исключений или regex `^\\d{4}-\\d{2}-\\d{2}$`. См. [Глоссарий](glossary.md).

---

## 4.2.4. Справочник (домен)

Правило **справочник** — значение должно входить в перечень допустимых: таблица-справочник, список кодов, enum. Относится к валидности ([§2.6](chapter-02-06.md)); для внешнего ключа совпадает с референциальной целостностью ([§2.3](chapter-02-03.md), [§4.4](chapter-04-04.md)).

**Формулировка:** «Поле X принимает только значения из справочника R» или «Код валюты из ref.currencies».

**Реализация:**

- **В СУБД:** внешний ключ (FOREIGN KEY) на колонку, ссылающийся на справочник; при вставке значения, отсутствующего в справочнике, СУБД вернёт ошибку.
- **В ETL:** перед загрузкой джойн с справочником или подзапрос NOT IN / NOT EXISTS; записи с кодами, отсутствующими в справочнике, не загружаются или идут в кварантин.
- **Проверка:** записи, у которых значение не найдено в справочнике (LEFT JOIN с справочником, WHERE ref.key IS NULL при не-null в проверяемом поле).

Пример: записи с `currency_code`, которого нет в `ref.currencies` (PostgreSQL):

```sql
SELECT t.deal_id, t.currency_code
FROM staging.deals t
LEFT JOIN ref.currencies c ON t.currency_code = c.currency_code
WHERE t.load_date = CURRENT_DATE - 1
  AND t.currency_code IS NOT NULL
  AND c.currency_code IS NULL;
```

Использование NOT IN: `WHERE currency_code NOT IN (SELECT currency_code FROM ref.currencies WHERE currency_code IS NOT NULL)` — при null в справочнике NOT IN даёт неожиданный результат, поэтому LEFT JOIN надёжнее. См. [Глоссарий](glossary.md).

## 4.2.5. Регулярное выражение

Правило **регулярное выражение** (regex) — строка должна совпадать с заданным шаблоном. Частный случай формата; удобен для кодов, телефонов, e-mail, масок. Относится к валидности ([§2.6](chapter-02-06.md)).

**Формулировка:** «Поле X соответствует шаблону R» (например, «код из 3 заглавных букв латиницы», «телефон в формате +7...»).

**Реализация:**

- **В СУБД:** в PostgreSQL — CHECK с оператором `~` (например, `CHECK (code ~ '^[A-Z]{3}$')`); в Oracle — REGEXP_LIKE в CHECK (где поддерживается). Не все СУБД допускают regex в CHECK.
- **В ETL:** в коде (Python, Java и т.д.) — проверка через библиотеку regex; в SQL — WHERE column ~ 'pattern' (PostgreSQL) или REGEXP_LIKE(column, 'pattern') (Oracle). Записи, не совпадающие с шаблоном, отклоняются или помечаются.
- **Проверка:** `SELECT * FROM table WHERE column IS NOT NULL AND column !~ 'pattern' [AND filter];`

Примеры шаблонов (PostgreSQL, оператор `~`):

| Назначение | Пример шаблона |
|------------|----------------|
| Ровно 3 заглавные буквы | `'^[A-Z]{3}$'` |
| Только цифры | `'^[0-9]+$'` |
| Дата YYYY-MM-DD | `'^\d{4}-\d{2}-\d{2}$'` |
| Не пустая строка без пробелов по краям | проверка LENGTH(TRIM(column)) > 0 |

В Oracle: `REGEXP_LIKE(column, '^[A-Z]{3}$')` для совпадения; для «не совпадает» — `NOT REGEXP_LIKE(column, '^[A-Z]{3}$')`. См. [Глоссарий](glossary.md).

---

## 4.2.6. Сводка правил на уровне поля

| Правило | Что проверяем | Измерение | Реализация в СУБД | Проверка (нарушение) |
|---------|---------------|-----------|-------------------|----------------------|
| NOT NULL | Поле не null (и не пустая строка) | Полнота | NOT NULL | WHERE field IS NULL |
| Диапазон | Значение между min и max | Валидность | CHECK (field BETWEEN ...) | WHERE field < min OR field > max |
| Формат | Длина, структура, приведение типа | Валидность | CHECK (LENGTH...) или в ETL | WHERE не проходит формат |
| Справочник | Значение в списке допустимых | Валидность, референциальная целостность | FOREIGN KEY или в ETL | LEFT JOIN ref WHERE ref.key IS NULL |
| Регулярное выражение | Строка совпадает с шаблоном | Валидность | CHECK (~ pattern) где поддерживается | WHERE column !~ pattern |

Комбинация правил: поле может быть одновременно обязательным (NOT NULL), в диапазоне и из справочника; проверки выполняются по очереди или одним составным условием. Реакция при нарушении (отклонить запись, кварантин, алерт) задаётся отдельно от формулировки правила (глава 7). См. [Глоссарий](glossary.md).

---

## 4.2.7. Типичные ошибки

- **Не учитывать null при проверке диапазона и формата:** условие `amount < 0 OR amount > max` не отбирает строки с null (сравнение с null даёт unknown); при необходимости явно включать или исключать null: `AND amount IS NOT NULL` в условии невалидности.
- **Задавать regex без якорей ^ и $:** шаблон `[0-9]+` совпадает с подстрокой; для «целиком только цифры» нужно `^[0-9]+$`, иначе «abc123def» пройдёт проверку.
- **Справочник с null:** при NOT IN (SELECT code FROM ref) если в ref есть null, условие «не в списке» может дать пустой результат; использовать LEFT JOIN или подзапрос с условием ref.code IS NOT NULL.
- **CHECK в СУБД только при вставке:** при массовой загрузке через COPY или внешние инструменты CHECK может не выполняться в части режимов; дублировать проверку в ETL.

---

## Ключевое

- **Правила на уровне поля** проверяют одно значение в одной колонке: NOT NULL (обязательность), диапазон, формат, справочник, регулярное выражение.
- **NOT NULL** — полнота; реализация: ограничение в СУБД, проверка в ETL; учёт пустой строки при необходимости.
- **Диапазон** — валидность; CHECK в СУБД или фильтр в ETL; для дат — границы и порядок дат.
- **Формат** — длина, приведение типа, структура; **regex** — частный случай формата для строк; в PostgreSQL — оператор `~`, в Oracle — REGEXP_LIKE.
- **Справочник** — значение из списка допустимых; реализация — FK или джойн/подзапрос в ETL; при проверке через NOT IN учитывать null в справочнике, предпочтительнее LEFT JOIN.
- Комбинация правил допустима; реакция при нарушении задаётся отдельно; при проверке явно учитывать null.

В [§4.3](chapter-04-03.md) мы разберём **правила на уровне записи и таблицы**: уникальность ключа, сумма частей равна целому, баланс дебет/кредит — то есть правила, затрагивающие несколько полей или строк.
