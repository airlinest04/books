# §2.2 Arenadata DB Control

В [§2.1](chapter-02-01.md) мы разобрали Arenadata Cluster Manager (ADCM) — оркестратор развёртывания и управления кластерами. В этом разделе рассматривается **Arenadata DB Control (ADB Control)** — система **мониторинга запросов** Arenadata DB в режиме реального времени. Вы узнаете назначение и доступность ADB Control (ADB Enterprise, offline-установка), архитектуру компонентов, как просматривать выполняемые запросы и их планы выполнения, метрики производительности по запросам и сегментам, управление сессиями (включая прерывание «зависших» сессий), а также настройку мониторинга нескольких кластеров. Детальное использование ADB Control в эксплуатации (мониторинг запросов, метрики, алерты, управление сессиями) разобрано в [главе 4](chapter-04-01.md). См. [Глоссарий](glossary.md).

---

## 2.2.1. Назначение и доступность ADB Control

**Arenadata DB Control (ADB Control)** — система мониторинга запросов Arenadata DB в режиме реального времени. По [документации ADB Control](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/overview.html), это «командный центр» для отслеживания выполнения SQL-запросов и транзакций, оценки загруженности кластера, анализа планов выполнения и метрик потребления ресурсов (CPU, RAM, I/O, spill-файлы), аудита обращений к таблицам и административных действий. Администратор может просматривать активные и завершённые запросы, отменять выполняющиеся транзакции, прерывать клиентские сессии и выгружать метрики во внешнюю аналитическую БД. См. [Глоссарий](glossary.md).

**Доступность:** ADB Control входит в состав **ADB Enterprise**; в Community-редакции Arenadata DB его нет. Установка возможна только в режиме **offline** (в составе офлайн-установки кластера ADB через ADCM). Для корректной работы планировщика задач и точных метрик рекомендуется синхронизация времени на хостах кластера (например, сервис Chrony). Веб-интерфейс ADB Control доступен после развёртывания сервиса ADB Control в кластере; из одного экземпляра ADB Control можно мониторить **несколько кластеров ADB** одновременно (в том числе кластеры из разных контуров ADCM).

---

## 2.2.2. Архитектура ADB Control

По [обзору ADB Control](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/overview.html), в состав системы входят следующие компоненты:

| Компонент | Назначение |
|-----------|------------|
| **Agent** | Устанавливается по одному на каждый хост кластера ADB; принимает и фильтрует метрики с координатора и всех сегментов этого хоста; передаёт данные в Backend. |
| **Service Registry** | Каталог зарегистрированных сервисов ADB Control; обнаружение (service discovery) агентов и сервисов; при добавлении нового кластера в мониторинг регистрируются новые агенты. |
| **UI Backend Server** | Обработка запросов веб-интерфейса, взаимодействие с Backend. |
| **Backend Server** | Горизонтально масштабируемый сервис: приём и агрегация метрик от агентов, запись в Query DB и Metrics DB, отправка обновлений в UI Backend. |
| **Scheduler** | Планировщик задач по расписанию: автоматическая очистка старых метрик, выгрузка (offload) метрик и данных аудита во внешнюю БД, актуализация статусов запросов и транзакций, агрегация данных о потреблении ресурсов. |
| **Migration** | Сервис миграции схем и данных в БД ADB Control (Query DB, Metrics DB, Offload DB). |
| **Query DB** | База данных PostgreSQL: логирование запросов и транзакций, агрегаты метрик по ним, аудит, статистика по сущностям БД, системные таблицы ADB Control (пользователи, кластеры, настройки). |
| **Metrics DB** | База данных ClickHouse: хранение системных метрик, получаемых от агентов. |
| **Offload DB** | Внешняя аналитическая БД (PostgreSQL или ADB) для выгрузки метрик и данных аудита по расписанию (опционально). |

Query DB и Metrics DB по умолчанию поднимаются в контейнерах; при необходимости их можно подключить как внешние БД (параметры при конфигурировании сервиса ADB Control при установке кластера). Подробнее настройка внешних БД описана в [документации](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/external-db.html).

## 2.2.3. Мониторинг запросов (Commands)

Страница **Monitoring → Commands** в веб-интерфейсе ADB Control выводит SQL-команды, выполняемые в подключённых для мониторинга кластерах ADB. По [документации по мониторингу команд](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/commands.html):

**Условие отображения:** по умолчанию фиксируются запросы с длительностью **более 5 секунд**. Вложенные запросы (inner query — вызываемые в рамках функций, SPI и т.д.) по умолчанию исключены; при необходимости их мониторинг включается через GUC `adcc.monitor_inner_queries` и `adcc.monitor_utility_inner_queries` в настройках кластера в ADB Control.

**Вкладка Queries:**

- **Online** — команды в статусах: `Queued` (ожидание начала выполнения), `Running` (выполняются), `Cancelling` (идёт отмена). Отображаются поля: Command ID, текст команды, SQL ID, пользователь, статус, база данных, ресурсная группа, кластер, планировщик (GPORCA / Fallbacked / Legacy), время отправки, теги, время выполнения (Run time). Доступны фильтры по кластеру и БД, по столбцам таблицы; можно добавлять столбцы с метриками (Customize table).
- **History** — команды в статусах: `Done`, `Cancelled`, `Error`, `Unknown`. Добавляется поле Ended (время завершения); доступны фильтры по Relation и Schema.

**Детали команды:** при клике на Command ID открывается страница с секциями:

- **Overview** — базовая информация, Run time, оценка прогресса (Est. progress), при ошибке — текст ошибки.
- **Performance** — метрики потребления ресурсов: CPU (usage total, avg %, skew), RAM (average, skew), Virtual memory, Read/Write (total, avg per sec, skew), Spill files (объём и количество по сегментам). Значения выводятся в среднем по кластеру и отдельно по каждому сегменту (включая координатор seg-1, Segment ID = -1). Метрики на сегментах запрашиваются агентами только для команд длительностью **более 15 секунд**; для более коротких команд секция Performance может быть пустой.
- **Command text** — полный текст запроса (с возможностью копирования).
- **План выполнения** — вкладки Plan & progress (графическое дерево плана с прогрессом по узлам, статусами узлов и слайсов), Text (текст плана в формате EXPLAIN), Relations (список используемых отношений). При клике на узел плана отображаются Cost, Relation, Est.tuples, Actual tuples, Prediction accuracy, Row skew, Execution time и др.

**Группы запросов (Groups):** на вкладке **Monitoring → Commands → Groups** (доступна с определённой версии ADB Control) отображаются группы запросов, сгруппированных по SQL ID, номеру узла и типу узла в плане. Группы типа `Short` объединяют запросы длительностью **менее 5 секунд**. Группы бывают активными (последний запрос за последние 5 минут) и неактивными. **SQL ID** — идентификатор структуры SQL-команды (совпадает с `queryid` в `pg_stat_statements`); семантически эквивалентные запросы (одинаковая структура, разные константы или форматирование) имеют один SQL ID и могут анализироваться вместе.

## 2.2.4. Метрики производительности по запросам

Метрики, собираемые для команд (по [документации](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/commands.html)), сгруппированы следующим образом:

| Группа | Метрики | Описание |
|--------|---------|----------|
| **CPU** | CPU usage total, CPU avg usage %, CPU skew | Суммарное время CPU по сегментам; средний процент загрузки; перекос по сегментам. |
| **RAM** | RAM average, RAM skew | Средний объём потребляемой памяти (RSS), перекос по сегментам. |
| **Virtual memory** | Virtual memory average, Virtual memory skew | Выделенная виртуальная память (vsize), перекос. |
| **Read** | Read total, Read avg per sec, Read skew | Объём и скорость чтения с диска, перекос. |
| **Write** | Write total, Write avg per sec, Write skew | Объём и скорость записи, перекос. |
| **Spill files** | Spill files host, Spill files abs host/seg, Spill files skew | Объём spill-файлов (временные данные на диске при нехватке RAM), перекос. |

Показатели skew (перекос) показывают неравномерность нагрузки по сегментам: ненулевое значение указывает, что один или несколько сегментов потребляют больше ресурсов, чем остальные, что может указывать на неравномерное распределение данных или «тяжёлые» узлы плана. На вкладке Online метрики отображаются на текущий момент; на вкладке History — на момент завершения команды.

## 2.2.5. Управление сессиями (Sessions)

Вкладка **Monitoring → Sessions** предназначена для мониторинга **клиентских сессий** ADB — активных и неактивных («зависших»). По [документации по сессиям](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/sessions.html) отображаются:

- **Session ID**, Resource group, Username, Database, **State** (Active / Idle / Idle in transaction), Application name, Start time, Idle time, Command text (последняя или текущая команда), Tags.

В верхней части выводятся счётчики: Active, Idle, Idle in transaction. Фильтр Cluster позволяет выбрать кластер (по умолчанию — кластер, назначенный default в настройках). По клику на Session ID можно перейти к деталям последней команды сессии (если она зарегистрирована в ADB Control).

**Прерывание сессии (Terminate):** в столбце Actions для каждой сессии доступна иконка прерывания; после подтверждения в диалоге сессия завершается, соединение освобождается. Это используется для освобождения пула соединений при «зависших» или неактивных сессиях (Idle in transaction и т.п.). Отмена выполняющейся транзакции (без разрыва сессии) выполняется через мониторинг транзакций (см. [документацию по транзакциям](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/transactions.html)).

## 2.2.6. Управление кластерами и настройка мониторинга

ADB Control позволяет подключать **несколько кластеров ADB** к одному веб-интерфейсу. Управление кластерами выполняется на вкладке **Configuration → Clusters**. По [документации по управлению кластерами](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/config/cluster-manage.html):

- **Список кластеров:** Cluster name, Status (Active / Archived), признак Default cluster, JDBC URL, Username. Имя кластера должно быть уникальным в рамках ADB Control.
- **Подключение нового кластера:** через ADCM в целевой кластер добавляется сервис ADB Control; при конфигурировании включается переключатель External ADB Control server parameters и указываются IP и порт существующего ADB Control. После установки сервиса новый кластер появляется в списке Configuration → Clusters автоматически.
- **Редактирование:** можно изменить JDBC URL, пользователя и пароль подключения к кластеру (имя кластера не редактируется).
- **Кластер по умолчанию:** кнопка Set default cluster — выбор кластера, подставляемого по умолчанию в фильтрах на страницах мониторинга.
- **Архивация кластера:** при архивации приостанавливаются сбор аудита, экспорт метрик и статистика по ресурсным группам для данного кластера; статус меняется на Archived. Возобновление — через действие в столбце Actions.

**Настройки кластера** (при переходе по имени кластера): секции **Databases monitoring** (выбор БД, для которых ведётся мониторинг), **GUC management** (параметры ADB Control: мониторинг вложенных запросов, настройки EXPLAIN ANALYZE и т.д.), **Metric offload** (выбор БД для выгрузки метрик во внешнюю аналитическую БД по расписанию). Подробнее политики задач (очистка, offload) — на вкладке Configuration → Job policy в документации ADB Control.

## 2.2.7. Типичные ошибки при работе с ADB Control

- **Ожидать метрики Performance для коротких запросов:** метрики на сегментах собираются только для команд длительностью более 15 секунд; для быстрых запросов секция Performance в деталях команды будет пустой.
- **Путать прерывание сессии (Terminate) и отмену транзакции (Cancel):** Terminate завершает всю сессию и разрывает соединение; Cancel отменяет текущую команду/транзакцию, сессия остаётся. Отмена транзакции выполняется из раздела мониторинга транзакций.
- **Считать, что все запросы видны в Commands:** по умолчанию отображаются запросы длительностью от 5 секунд; короткие запросы попадают в Groups (тип Short) или могут не отображаться в зависимости от настроек GUC.
- **Игнорировать синхронизацию времени:** для корректной работы Scheduler и метрик время на хостах кластера должно быть синхронизировано (Chrony или аналог); иначе расписания и временные метки могут работать некорректно.

## Ключевое

- **ADB Control** — система мониторинга запросов ADB в реальном времени; входит в ADB Enterprise; установка только offline; возможен мониторинг нескольких кластеров из одного интерфейса.
- **Архитектура:** Agent (на каждом хосте), Service Registry, Backend, Query DB (PostgreSQL), Metrics DB (ClickHouse), Scheduler, опционально Offload DB; метрики собираются с координатора и сегментов через агентов.
- **Мониторинг запросов:** Monitoring → Commands (Queries Online/History, Groups); по умолчанию запросы от 5+ секунд; детали команды — план выполнения (Plan & progress), метрики Performance (CPU, RAM, I/O, spill), текст запроса; SQL ID для группировки семантически одинаковых запросов.
- **Метрики:** CPU, RAM, Virtual memory, Read/Write, Spill files — в среднем по кластеру и по сегментам; skew для выявления перекоса; метрики по сегментам — для команд длительностью более 15 секунд.
- **Сессии:** Monitoring → Sessions — список сессий (Active, Idle, Idle in transaction), прерывание (Terminate) для освобождения соединений.
- **Кластеры:** Configuration → Clusters — добавление, редактирование, кластер по умолчанию, архивация; настройки кластера — выбор БД для мониторинга, GUC, Metric offload.

В [§2.3](chapter-02-03.md) мы разберём Arenadata DB Backup Manager (ADBM) — систему управления резервным копированием: полный и инкрементальный бэкап, расписание, восстановление.
