# §2.3 Arenadata DB Backup Manager

В [§2.2](chapter-02-02.md) мы разобрали Arenadata DB Control — мониторинг запросов и сессий. В этом разделе рассматривается **Arenadata DB Backup Manager (ADBM)** — система управления **бинарными резервными копиями** Arenadata DB. Вы узнаете назначение и доступность ADBM, архитектуру компонентов, типы бэкапов (полный, дифференциальный, инкрементный), точки восстановления (restore point) и механизм PITR, конфигурацию бэкапов и расписания, хранилища (Posix, S3), а также основные действия: создание бэкапа и restore point, полное и выборочное восстановление, очистка, верификация, прерывание и возобновление. Детальные сценарии резервного копирования и восстановления для DWH разобраны в [главе 6](chapter-06-01.md). См. [Глоссарий](glossary.md).

---

## 2.3.1. Назначение и доступность ADBM

**Arenadata DB Backup Manager (ADBM)** — отказоустойчивая система для управления **бинарными** резервными копиями ADB. По [документации ADBM](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/overview.html), ADBM построена на основе **pgbackrest** и обеспечивает: гибкую настройку политик формирования бэкапов (в том числе отдельные расписания для полных, дифференциальных и инкрементных копий); формирование бэкапов по расписанию и вручную; ведение списка бэкапов с поиском и просмотром деталей (включая топологию кластера); удаление бэкапов по политикам и вручную; создание **точек восстановления (restore point)** по расписанию и вручную; **восстановление БД на момент выбранной restore point** (PITR — point-in-time recovery); логирование всех операций с возможностью просмотра причин сбоев; поддержку нескольких кластеров ADB (в том числе с standby и зеркалированием); поддержку S3- и Posix-совместимых хранилищ. См. [Глоссарий](glossary.md).

**Доступность:** ADBM входит в состав **ADB Enterprise**; установка возможна только в режиме **offline** (в составе офлайн-установки кластера ADB через ADCM). **Пользовательский интерфейс ADBM встроен в веб-интерфейс ADB Control**: после входа в ADB Control в левом меню выбирается пункт **Backup manager**; страница Backup manager доступна пользователям с ролями Administrator, ADBM Administrator или Owner. Подключение к ADBM выполняется через адрес хоста ADB Control и порт (по умолчанию 81; задаётся при конфигурировании сервиса ADB Control). Подробнее вход и права — в [документации по подключению к ADBM](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/connect.html).

## 2.3.2. Архитектура ADBM

По [обзору ADBM](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/overview.html), основные компоненты:

| Компонент | Назначение |
|-----------|------------|
| **Backup Manager** | Оркестрация кластерных действий и фоновой работы по расписаниям: создание бэкапов и restore points, очистка и т.д. Взаимодействие с кластером ADB — через агентов. |
| **Backup Agent** | Устанавливается по одному на каждый хост кластера ADB; отвечает за работу с данными сегментов: запуск команд pgbackrest, управление конфигурацией pgbackrest; на хосте координатора — операции управления кластером ADB (например, перезапуск). |
| **Service Registry** | Обнаружение сервисов (service discovery) в ADBM; обнаружение агентов и поиск сервисов ADBM со стороны агентов. При добавлении кластера регистрируются новые агенты. |
| **PostgreSQL** | Хранение: блокировки на уровне кластера (эксклюзивность запускаемых действий); состояние текущего активного действия (при падении Backup Manager метаданные берутся из PostgreSQL); история бэкапов и конфигураций. По умолчанию — в контейнере; возможна внешняя БД (параметры при конфигурировании ADBM). |

Типовая последовательность при работе с ADBM через веб-интерфейс: подключение к ADBM (страница Backup manager в ADB Control) → создание конфигурации бэкапа и при необходимости хранилищ и расписаний → запуск бэкапов вручную или ожидание автоматического формирования → создание restore points → при необходимости очистка, верификация, восстановление. Детали действий отображаются на вкладке Actions.

## 2.3.3. Типы бэкапов, restore point, WAL и PITR

По [документации ADBM](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/overview.html):

**Бэкап (backup)** — консистентная копия данных кластера ADB для восстановления при сбоях. ADBM поддерживает три типа:

- **Full (полный):** в копию попадает всё содержимое БД. Первый бэкап в рамках текущего timeline в ADBM всегда имеет тип full (даже если по расписанию или выбору пользователя указаны diff или incr). Восстановление из full возможно напрямую. Полные копии не рекомендуются для частого регулярного снятия (ежечасно/ежедневно), так как требуют много времени и места.
- **Differential (дифференциальный):** копируются только файлы, изменившиеся после последнего полного бэкапа. Формируется быстрее и занимает меньше места, чем full; для восстановления нужны файлы из последнего full и из данного differential.
- **Incremental (инкрементный):** копируются только файлы, изменившиеся после последнего бэкапа любого типа (full, diff или incr). Минимальное время и объём; восстановление требует последовательного применения last full + при необходимости diff + все последующие incr.

**WAL (Write-Ahead Log)** — механизм, гарантирующий сохранность закоммиченных изменений; все изменения данных записываются в WAL, затем переносятся в основные файлы данных. В ADBM архивирование WAL позволяет воспроизводить изменения после последнего загруженного бэкапа и восстанавливать БД на произвольный момент времени в пределах имеющихся WAL (PITR). Восстановление до выбранной точки: загрузка одного или нескольких бэкапов → воспроизведение записей WAL до именованной точки.

**Restore point** — именованная точка восстановления; минимальная гранулярность согласования данных в кластере ADB. После создания restore point (по расписанию или вручную) ADBM хранит информацию о том, какие бэкапы и WAL-сегменты нужны для восстановления БД на этот момент. Восстановление выполняется выбором restore point в действии Common restore (или Partial restore).

**Timeline** — механизм в ADBM для различения серий WAL: после восстановления БД на какой-либо момент создаётся новый номер timeline; последующие записи WAL помещаются в директории с новым номером, чтобы не перезаписывать WAL исходной истории. После каждого восстановления первый бэкап в новой истории будет full (даже если по расписанию заданы diff или incr).

## 2.3.4. Конфигурация бэкапов, расписание и хранилища

Управление конфигурациями выполняется на странице кластера в ADBM: **Configuration → Backup configuration**. В каждый момент активна только одна версия конфигурации (статус `current`). По [документации по конфигурациям](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/basic/manage-configs.html):

**Backup configuration** включает секции:

- **General configuration:** Number of full backups, Number of differential backups, Total number of backups (лимит на общее число бэкапов), File log level, Archive command (команда при передаче WAL в archive; при изменении кластер перезапускается), Archive timeout, Stanza template, Log path, Exclude path (исключаемые из бэкапа пути).
- **Timeout:** Database query timeout, Protocol timeout, I/O timeout, Job wait timeout.
- **Storage:** выбор хранилища (из вкладки Storages), Relative path в хранилище, Bundle size, Bundle limit, Use block incremental backup.
- **Workspace:** Temporary directory и параметры для Partial restore (Port base, Max processes per host).
- **Compression:** Compression type (none, bz2, gz, lz4, zst), Compression level, число процессов сжатия/передачи, Buffer size.

После сохранения конфигурации запускается действие Apply backup configuration; до успешного завершения конфигурация в статусе `draft`. Редактировать применённую конфигурацию нельзя — создаётся новая версия на базе существующей (Create new); после применения новая версия получает статус `current`, предыдущая — `previous`.

**Расписание (Configuration → Schedule):** отдельные cron-расписания для Full backup, Differential backup, Incremental backup, Restore point creation, Cleanup. При неактивном переключателе соответствующая операция выполняется только вручную.

**Хранилища (Configuration → Storages):** хранилище — место хранения бэкапов и архива WAL. Типы: **posix**, **s3**, **cifs**. Указываются Repository path (для Posix/CIFS — директория, доступная с координатора и сегмент-хостов; можно NFS), для S3 — параметры bucket, endpoint, key, region и др. Отдельно настраиваются пороги оповещений (Almost Full, Critical) для мониторинга заполненности. Один и тот же репозиторий может использоваться в разных конфигурациях с разными Relative path; при очистке ADBM учитывает комбинацию типа, пути и конечной точки S3.

**Важно:** при сохранении любой конфигурации к кластеру применяется `archive_command` и запускается процесс формирования WAL. ADBM не поддерживает топологию «один сегмент-хост с зеркалированием». Если топология кластера изменилась (например, после Expand в ADCM), конфигурация не применится, пока есть хотя бы один валидный бэкап — в таком случае сначала удаляют все бэкапы, затем меняют конфигурацию.

## 2.3.5. Действия: Backup, Restore point, Restore, Cleanup, Verify, Terminate, Resume

Действия запускаются из секции **Clusters** на странице Backup manager (иконка в строке кластера) или с страницы выбранного кластера (кнопка Backup и меню действий). Запуск действий **эксклюзивен** — нельзя запустить новое действие, пока не завершено предыдущее (кроме Terminate). По [документации по запуску действий](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/basic/run-actions.html):

| Действие | Описание |
|----------|----------|
| **Backup** | Ручной запуск бэкапа: выбор типа (Full / Incr / Diff), имя restore point, при необходимости флаги Delta (checksum для incr/diff), Fail on low space. Запускается действие Backup и дочерние subaction; результат отображается на вкладке Backups. |
| **Create restore point** | Создание именованной точки восстановления вручную (при наличии хотя бы одного бэкапа в статусе Done). |
| **Common restore** | Восстановление БД на момент выбранной restore point. Для запущенного кластера выполняются проверки топологии и метаданных, затем кластер останавливается и выполняется восстановление; для остановленного кластера проверки можно пропустить. Параметры: выбор restore point, баз для восстановления, Restore mirrors (No / Parallel / Sequential), флаги Delta, Force, Verify. При ошибке доступен Retry (без повторных проверок). |
| **Partial restore** | Восстановление выбранных таблиц на момент restore point: Source database, Target database, Table suffix, маски имён таблиц (schema/table), число процессов. Таблицы можно восстановить в другую БД или с суффиксом имён. |
| **Cleanup** | Удаление по политикам: лишние full/diff по Number of full/differential backups, бэкапы со статусами Failed/Invalid, неактивные версии конфигураций без связанных бэкапов. При ручном запуске можно указать restore point — тогда удаляется набор бэкапов и restore points, связанных с выбранной точкой (по правилам из документации). |
| **Verify** | Сравнение метаданных бэкапов в ADBM с данными pgbackrest; проверка валидности бэкапов и архивов WAL (наличие, размер, контрольные суммы). Невалидные бэкапы переводятся в статус Invalid и удаляются при следующем Cleanup. Выбор restore point, на момент которой выполняется проверка. |
| **Terminate** | Прерывание запущенного действия Backup или Cleanup. Используется отдельный lock (etcd), поэтому Terminate можно запускать параллельно с другими действиями. После прерывания бэкап переходит в статус Stopped. |
| **Resume** | Возобновление последнего прерванного бэкапа (доступно для типа Full; файлы в бандлах при resume не переиспользуются). После успешного завершения бэкап переходит в статус Done. |
| **Create configuration** | Переход к созданию новой версии конфигурации бэкапа на базе существующей (открывает вкладку Configuration → Backup configuration). |

Список бэкапов и их детали (тип, время, статус, прогресс) отображаются на вкладке **Backups**; история действий и детали сбоев — на вкладке **Actions**. Подробнее просмотр бэкапов и действий — в [документации ADBM](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/basic/view-backups.html).

## 2.3.6. Типичные ошибки при работе с ADBM

- **Путать ADBM и gpbackup:** ADBM управляет **бинарными** бэкапами (на базе pgbackrest), обеспечивает PITR и restore points. **Логические** бэкапы (выборочные схемы/таблицы, перенос между кластерами) делаются инструментами gpbackup/gprestore — они не заменяют ADBM и могут использоваться параллельно.
- **Запускать новое действие до завершения текущего:** кроме Terminate все действия эксклюзивны; при одновременном запуске возвращается ошибка. Следить за вкладкой Actions и статусами перед запуском следующего действия.
- **Менять топологию кластера (Expand) без учёта бэкапов:** после изменения топологии старые бэкапы становятся невалидными для этой конфигурации; применение новой конфигурации блокируется при наличии валидных бэкапов. Нужно либо удалить все бэкапы и затем применить конфигурацию, либо следовать инструкциям по верификации/пересозданию конфигурации после обновления кластера.
- **Игнорировать статус хранилища (Almost Full / Critical):** при Critical формирование бэкапа может не запускаться (если включён флаг Fail on low space). Следить за мониторингом хранилищ (Overview на странице конфигурации с хранилищем) и вовремя расширять или очищать место.
- **Считать, что Restore откатывает только «последний» бэкап:** восстановление идёт на выбранную **restore point**; для неё используются цепочка full + при необходимости diff + incr + WAL. Нужно понимать, какие restore points доступны и до какого момента возможно восстановление.

## Ключевое

- **ADBM** — система управления бинарными бэкапами ADB на базе pgbackrest; входит в ADB Enterprise; установка только offline; UI встроен в ADB Control (пункт Backup manager); поддержка нескольких кластеров, S3 и Posix-хранилищ.
- **Архитектура:** Backup Manager (оркестрация, расписания), Backup Agent (на каждом хосте; pgbackrest), Service Registry, PostgreSQL (блокировки, состояние, история).
- **Типы бэкапов:** Full (вся БД), Differential (изменения после last full), Incremental (изменения после last backup); **restore point** — именованная точка для восстановления; **WAL** и **PITR** — восстановление на произвольный момент; **timeline** — различение серий WAL после восстановления.
- **Конфигурация:** Backup configuration (general, timeout, storage, workspace, compression); одна активная версия (current); расписание (cron) для full/diff/incr, restore point, cleanup; Storages (posix/s3/cifs), мониторинг заполненности.
- **Действия:** Backup, Create restore point, Common restore (на момент restore point), Partial restore (таблицы), Cleanup, Verify, Terminate (прерывание Backup/Cleanup), Resume (возобновление прерванного full backup); запуск эксклюзивен (кроме Terminate).
