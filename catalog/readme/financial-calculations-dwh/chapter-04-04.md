# §4.4 Паттерны: оконные функции и GROUP BY

В [§4.1](chapter-04-01.md)–[§4.3](chapter-04-03.md) мы разобрали обороты за период, остатки на дату и нарастающий итог. Итоги и накопления в SQL можно получать двумя способами: **GROUP BY** с агрегацией и **оконными функциями** (SUM, и др. OVER (...)). Здесь мы сравниваем оба подхода: когда уместен GROUP BY, когда оконные функции, как это влияет на **производительность** и приводим краткие примеры на Oracle и PostgreSQL. Детали синтаксиса оконных функций для оборотов и остатков — в [§8.4](chapter-08-04.md).

---

## 4.4.1. GROUP BY: одна строка на группу

**GROUP BY** уменьшает число строк: по одному значению на каждую комбинацию группировочных полей. Агрегаты (SUM, COUNT, AVG и т.д.) считаются **по группе**; в результате одна строка на группу.

Использовать GROUP BY уместно, когда нужен именно **итог по группе**:

- Обороты по счёту за период — одна строка на счёт (и при необходимости на период): SUM(amount_dt), SUM(amount_ct) с GROUP BY account_id [, period].
- Обороты по счёту по месяцам — одна строка на пару (счёт, месяц).
- Сводные отчёты: итоги по контрагентам, по продуктам за период.

Плюсы: привычный паттерн, хорошая оптимизация в СУБД (хэш- или групповые агрегаты), результат компактный (мало строк). Минус: нельзя в одном запросе одновременно получить и детальные строки (каждая проводка), и итог по группе — итог будет в отдельных строках. См. [Глоссарий](glossary.md).

---

## 4.4.2. Оконные функции: строки сохраняются

**Оконные функции** (SUM, AVG, COUNT и т.д. с OVER (...)) **не сводят** строки: количество строк в результате совпадает с входным набором (после JOIN и WHERE). В каждой строке появляется дополнительная колонка — значение агрегата по «окну» (текущая партиция и рамка).

Использовать оконные функции уместно, когда нужны **и детали, и контекст**:

- Каждая проводка остаётся строкой, плюс колонка «остаток на момент этой проводки» (нарастающий итог).
- Таблица оборотов по месяцам — каждая строка месяц, плюс колонка «оборот с начала года».
- Сравнение строки с итогом по группе (доля в проценте, отклонение от среднего) без потери детализации.

Плюсы: один проход по данным, и детали, и агрегаты в одном результате. Минусы: объём результата равен объёму входных строк (или больше при JOIN); для «только итогов» GROUP BY обычно эффективнее по объёму выдачи.

---

## 4.4.3. Когда что выбирать

| Задача | Предпочтительный способ | Причина |
|--------|--------------------------|---------|
| Обороты по счёту за один период | GROUP BY | Одна строка на счёт, компактный результат |
| Обороты по счёту по нескольким периодам (месяцы года) | GROUP BY по account_id, period | Одна строка на (счёт, период) |
| Остаток после каждой проводки (нарастающий итог) | Оконная SUM() OVER (PARTITION BY account ORDER BY date) | Нужны все строки + накопленная сумма |
| Оборот за период + колонка «оборот с начала года» | GROUP BY + оконная функция по сгруппированному набору или обороты в подзапросе, затем SUM() OVER | Итог по периоду и накопление |
| Только итог по группе без деталей | GROUP BY | Меньше строк, проще для отчёта-сводки |

Комбинированный вариант: подзапрос или CTE с GROUP BY считает обороты по периодам; внешний запрос применяет оконную функцию к этому набору — нарастающий итог по месяцам. Так избегают оконной функции по полной таблице проводок, если данные уже агрегированы.

---

## 4.4.4. Производительность

**GROUP BY:** СУБД строит группы (хэш или сортировка) и один раз считает агрегаты по группе. Объём результата — число групп. Для больших таблиц проводок важен индекс или партиционирование по полям группировки и дате (чтобы фильтр по периоду отсекал данные до агрегации).

**Оконные функции:** обычно требуют сортировки по PARTITION BY и ORDER BY (или второго прохода для рамки). Все строки партиции должны быть доступны; при большом объёме данных и сложной рамке стоимость может быть выше, чем у GROUP BY для той же агрегации. С другой стороны, один запрос с оконной функцией может заменить несколько подзапросов (например, «остаток на дату» для каждой даты отдельно) — меньше проходов по данным.

Рекомендации: для «итог по группе» без деталей — GROUP BY; для нарастающего итога и «каждая строка + контекст» — оконные функции; при сомнении проверять план выполнения и объём результата. См. [§8.4](chapter-08-04.md).

## 4.4.5. Пример: обороты и нарастающий итог по месяцам (PostgreSQL)

Обороты по счёту по месяцам + колонка «оборот с начала года». Сначала агрегация по счёту и месяцу, затем нарастающий итог по месяцам.

```sql
WITH monthly_turnover AS (
    SELECT
        account_id,
        DATE_TRUNC('month', post_date)::DATE AS month_start,
        SUM(amount_dt) - SUM(amount_ct) AS turnover
    FROM ledger.postings
    WHERE post_date >= DATE '2025-01-01'
      AND post_date <  DATE '2026-01-01'
    GROUP BY account_id, DATE_TRUNC('month', post_date)
)
SELECT
    account_id,
    month_start,
    turnover,
    SUM(turnover) OVER (
        PARTITION BY account_id
        ORDER BY month_start
    ) AS turnover_ytd
FROM monthly_turnover
ORDER BY account_id, month_start;
```

Среда: PostgreSQL 15. В Oracle аналогично: GROUP BY с TRUNC(post_date, 'MM'), затем SUM(turnover) OVER (PARTITION BY account_id ORDER BY month_start).

---

## 4.4.6. Пример: остаток по проводкам (Oracle)

Нарастающий итог по каждой проводке для одного счёта; остаток = начальное сальдо + нарастающий итог.

```sql
SELECT
    account_id,
    post_date,
    amount_dt - amount_ct AS movement,
    :opening_balance + SUM(amount_dt - amount_ct) OVER (
        ORDER BY post_date, id
    ) AS balance_after
FROM ledger.postings
WHERE account_id = :account_id
  AND post_date BETWEEN :date_from AND :date_to
ORDER BY post_date, id;
```

Среда: Oracle 21c. `:opening_balance` — начальное сальдо на :date_from (bind-параметр). Без PARTITION BY, так как фильтр по одному счёту. Для нескольких счетов добавить PARTITION BY account_id и брать начальное сальдо из подзапроса или таблицы снимков.

---

## 4.4.7. Типичные ошибки

- **Оконная функция вместо GROUP BY для «только итогов»:** результат раздувается до всех строк; если нужна только сводка по группам, GROUP BY уместнее.
- **GROUP BY вместо оконной для нарастающего итога:** нарастающий итог по определению «на каждую строку» — без оконной функции пришлось бы делать подзапрос или самосоединение по «все предыдущие», что сложнее и часто медленнее.
- **Не совпадающий порядок в PARTITION BY и в запросе:** ORDER BY в запросе должен быть согласован с ORDER BY в окне, если важен порядок вывода; на результат оконной функции ORDER BY в SELECT не влияет.

---

## Ключевое

- **GROUP BY** даёт одну строку на группу и подходит для итогов: обороты по счёту за период, по (счёт, месяц), сводки без деталей.
- **Оконные функции** сохраняют все строки и добавляют агрегат по окну: нарастающий итог, остаток после каждой проводки, оборот с накоплением; уместны, когда нужны и детали, и контекст.
- Выбор: «только итог по группе» → GROUP BY; «каждая строка + накопление или контекст» → оконная функция; можно комбинировать (CTE с GROUP BY, затем SUM() OVER по сгруппированному набору).
- **Производительность:** GROUP BY даёт компактный результат; оконные функции требуют сортировки/прохода по партиции, но один запрос может заменить несколько подзапросов; ориентироваться на план выполнения и объём данных.

В [§5.1](chapter-05-01.md) мы перейдём к расчёту процентов: где округлять (на каждом шаге или в итоге), дневные и месячные проценты.
