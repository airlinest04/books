# §3.4 Алгоритмы компенсации погрешности

В [§3.3](chapter-03-03.md) мы разобрали распределение суммы по строкам с округлением и приём «остаток на последнюю строку». Здесь мы обобщаем **алгоритмы компенсации**: как распределить остаток (разницу между общей суммой и суммой округлённых долей) по строкам, если «последняя» строка не подходит или нужно учесть приоритеты. Рассматриваем добавление копеек к «большим» строкам, итеративное распределение остатка по одной копейке и учёт приоритетов. Пример реализации на SQL — в [§8.3](chapter-08-03.md).

---

## 3.4.1. Общая схема компенсации

После того как каждой строке присвоена **округлённая доля** (ROUND(доля, 2)), сумма по строкам может отличаться от целевой суммы \(S\) на величину **остатка** \(R\) (в копейках: целое число). Остаток может быть положительным (округление «отняло» копейки) или отрицательным (округление «добавило»). Задача компенсации — **скорректировать** одну или несколько строк так, чтобы итоговая сумма по строкам в точности равнялась \(S\).

Схема:

1. Вычислить округлённые доли для всех строк; сумма = \(\widetilde{S}\).
2. Остаток: \(R = S - \widetilde{S}\) (в копейках, целое).
3. Распределить \(R\) по строкам по выбранному правилу: кому добавить копейку, кому убавить (или одной строке присвоить ±\(R\) копеек).

Правило распределения должно быть **детерминированным** и зафиксированным в регламенте, иначе при повторном расчёте результат изменится. См. [Глоссарий](glossary.md).

---

## 3.4.2. Остаток на одну строку (последнюю или по приоритету)

Самый простой вариант — **весь остаток** отдать одной строке. В [§3.3](chapter-03-03.md) мы разобрали «остаток на последнюю»: последняя в заданном порядке строка получает значение \(S - \sum_{i=1}^{n-1} \widetilde{d}_i\).

Обобщение: остаток может получать не обязательно последняя, а строка, выбранная по **приоритету** (первая по приоритету, с максимальной долей, с особым признаком). Тогда:

- Сортируем строки по приоритету (и при равенстве — по ключу для детерминированности).
- Первым \(n-1\) строкам присваиваем округлённые доли.
- Строке с наивысшим приоритетом (или, наоборот, «назначенной» на остаток) присваиваем значение, обеспечивающее сумму \(S\).

Так можно, например, отдавать остаток строке с наибольшей долей (чтобы визуально «крупные» суммы были чуть больше) или строке с особым типом (например, «прочее»). Важно зафиксировать правило в регламенте.

---

## 3.4.3. Добавление копеек к «большим» строкам

Если остаток положительный (нужно **добавить** несколько копеек), их можно распределить по строкам с **наибольшей** округлённой долей: по одной копейке таким строкам, пока остаток не обнулится. Так «лишние» копейки попадают туда, где суммы и так больше, и визуально разброс меньше.

Алгоритм (остаток \(R > 0\), в копейках):

1. Отсортировать строки по убыванию округлённой доли (при равенстве — по ключу).
2. Пока \(R > 0\): взять следующую строку из списка, увеличить её значение на 1 копейку, уменьшить \(R\) на 1.
3. Если строк меньше, чем \(R\), правило нужно уточнить (например, несколько копеек одной строке или цикл по строкам).

Аналогично при **отрицательном** остатке (\(R < 0\)): уменьшать по 1 копейке строки с **наименьшей** долей, пока остаток не станет нулём. Так «недостающие» копейки забираются у наименьших сумм.

Плюс подхода — остаток распределён по нескольким строкам, ни одна не выделяется сильнее других. Минус — логика сложнее и порядок (по убыванию/возрастанию доли) должен быть строго зафиксирован.

## 3.4.4. Итеративное распределение остатка

**Итеративное** распределение: на каждом шаге остаток уменьшается на 1 копейку (или на минимальный шаг), и эта копейка добавляется или вычитается у одной строки. Порядок строк, получающих копейку, задаётся правилом: по порядку сортировки, по приоритету, по кругу (round-robin).

Пример (остаток +3 копейки, добавить по одной копейке):

- Сортируем строки по ID (или по приоритету).
- Строка 1: +1 копейка, остаток 2.
- Строка 2: +1 копейка, остаток 1.
- Строка 3: +1 копейка, остаток 0.

Если остаток больше числа строк, цикл повторяется: снова строка 1, строка 2, … — пока остаток не обнулится. Так копейки распределяются равномерно по кругу. Детерминированность обеспечивается фиксированной сортировкой.

Такой способ удобен, когда остаток может быть большим (много строк, неблагоприятное округление) и нежелательно отдавать всё одной строке. В SQL реализация часто требует цикла (курсор, рекурсивный CTE или процедура); упрощённый вариант — «остаток на последнюю» из §3.3. Полный пример — в [§8.3](chapter-08-03.md).

## 3.4.5. Учёт приоритетов

Приоритеты задают **очередность**, в которой строки получают копейки (или отдают при отрицательном остатке). Например:

- По **размеру доли**: сначала самые большие (при добавлении) или самые маленькие (при вычитании).
- По **типу строки**: определённая категория (например, «основной платёж») получает остаток первой.
- По **внешнему ключу**: контрагент, договор, дата — чтобы при повторном расчёте тот же контрагент получал ту же корректировку.
- По **порядку в документе**: первая/последняя строка в печатной форме.

Приоритет закладывают в ORDER BY при сортировке строк перед распределением остатка. В регламенте фиксируют: «остаток распределяется по убыванию суммы, при равенстве — по возрастанию ID». Тогда результат воспроизводим и при аудите понятно, почему та или иная строка получила копейку.

---

## 3.4.6. Выбор алгоритма и фиксация в регламенте

| Алгоритм | Когда уместен | Сложность |
|----------|----------------|-----------|
| Остаток на последнюю (одну) строку | Простое распределение, одна «принимающая» строка | Низкая, §3.3 |
| Остаток на строку по приоритету | Есть явный приоритет (тип, контрагент) | Низкая |
| Копейки к «большим» / «маленьким» | Нужно распределить остаток по нескольким строкам, визуально сгладить | Средняя |
| Итеративно по кругу | Большой остаток, равномерное распределение по строкам | Выше, часто цикл в SQL/процедуре |

В любом случае в бизнес-правиле и в описании витрины/пайплайна нужно указать: какой алгоритм компенсации используется, по какому полю (полям) задаётся порядок/приоритет и что считается «остатком» (разница в копейках между \(S\) и суммой округлённых долей). Тогда разработчики и аналитики смогут воспроизвести расчёт и проверить сверку. См. [§1.4](chapter-01-04.md).

## 3.4.7. Типичные ошибки

- **Не зафиксировать порядок приоритетов:** при разной сортировке разные строки получают копейки — тесты и сверки нестабильны.
- **Смешивать знак остатка:** при положительном остатке добавляем копейки, при отрицательном — вычитаем; не перепутать направление корректировки.
- **Забыть про граничные случаи:** остаток 0 — корректировка не нужна; одна строка — вся сумма ей; при весах ноль у части строк — исключить их из распределения или явно обработать.

---

## Ключевое

- **Компенсация погрешности** — корректировка округлённых по строкам сумм так, чтобы их сумма в точности равнялась целевой сумме \(S\); остаток \(R = S - \widetilde{S}\) распределяется по выбранному правилу.
- **Остаток на одну строку** — простой вариант: вся разница одной строке (последней по порядку или по приоритету); детерминированность задаётся сортировкой.
- **Добавление копеек к «большим» (или вычитание у «маленьких»)** — остаток по копейке строкам с наибольшей или наименьшей долей; визуально сглаживает разброс.
- **Итеративное распределение** — по одной копейке по кругу в заданном порядке; подходит при большом остатке; требует явного порядка и при необходимости цикла в реализации.
- **Приоритеты** (по доле, типу, ключу) задают порядок получения корректировки; их нужно зафиксировать в регламенте для воспроизводимости.

В [§4.1](chapter-04-01.md) мы перейдём к финансовым агрегациям в SQL: обороты за период по дебету и кредиту, GROUP BY по счёту и периоду.
