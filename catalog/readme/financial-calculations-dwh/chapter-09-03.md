# §9.3 Загрузка в витрину и сверка

В [§9.2](chapter-09-02.md) мы разобрали этапы расчёта и контрольные суммы. Здесь — **загрузка результата в витрину (Mart)**: как выполнять INSERT и UPDATE без дублей, **идемпотентность** пайплайна и **сверка с источником** после загрузки. Типовые ошибки пайплайна — в [§9.4](chapter-09-04.md). См. [Глоссарий](glossary.md).

---

## 9.3.1. От Core к витрине

Данные в витрину попадают из Core: обороты по счёту и периоду, остатки на дату, при необходимости денормализованные таблицы под отчёты ([§6.4](chapter-06-04.md)). Пайплайн читает из факта проводок или из таблиц снимков/агрегатов в Core, применяет группировку и округление по регламенту ([§9.2](chapter-09-02.md)) и записывает строки в таблицы Mart. Ключ строки в витрине обычно составной: **счёт (или группа счетов) + период** (месяц, день) или **счёт + дата снимка** для остатков. Один и тот же ключ не должен появляться в витрине дважды с разными значениями — иначе отчёт покажет дубли или неконсистентные итоги. Поэтому загрузка в витрину делается как **вставка новых и обновление существующих** по ключу (UPSERT). См. [§7.2](chapter-07-02.md) (сверка витрины с Core).

---

## 9.3.2. INSERT и UPDATE: UPSERT по ключу

**UPSERT** (insert or update) — одна операция, которая при совпадении ключа обновляет строку, при отсутствии — вставляет новую. Так витрина по периоду перезаписывается актуальными данными из Core без ручного удаления старых строк.

**PostgreSQL:** `INSERT ... ON CONFLICT ... DO UPDATE`. У витрины должен быть уникальный индекс или первичный ключ по полям ключа (например, account_id, period_month).

```sql
-- Пример: витрина оборотов по счёту и месяцу (PostgreSQL)
INSERT INTO mart.turnover_by_account_month (account_id, period_month, amount_dt, amount_ct)
SELECT account_id,
       date_trunc('month', post_date)::date AS period_month,
       ROUND(SUM(amount_dt), 2) AS amount_dt,
       ROUND(SUM(amount_ct), 2) AS amount_ct
FROM core.fact_postings
WHERE post_date >= :period_start AND post_date < :period_end
GROUP BY account_id, date_trunc('month', post_date)
ON CONFLICT (account_id, period_month)
DO UPDATE SET amount_dt = EXCLUDED.amount_dt, amount_ct = EXCLUDED.amount_ct;
```

**Oracle:** `MERGE INTO ... USING ... ON (...) WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT ...`. Условие ON задаёт ключ сопоставления (например, account_id и period_month).

```sql
-- Идея: Oracle MERGE для витрины оборотов
MERGE INTO mart.turnover_by_account_month t
USING (
  SELECT account_id, TRUNC(post_date, 'MM') AS period_month,
         ROUND(SUM(amount_dt), 2) AS amount_dt, ROUND(SUM(amount_ct), 2) AS amount_ct
  FROM core.fact_postings
  WHERE post_date >= :period_start AND post_date < :period_end
  GROUP BY account_id, TRUNC(post_date, 'MM')
) s ON (t.account_id = s.account_id AND t.period_month = s.period_month)
WHEN MATCHED THEN UPDATE SET t.amount_dt = s.amount_dt, t.amount_ct = s.amount_ct
WHEN NOT MATCHED THEN INSERT (account_id, period_month, amount_dt, amount_ct)
  VALUES (s.account_id, s.period_month, s.amount_dt, s.amount_ct);
```

Альтернатива — **удалить строки витрины за период, затем INSERT** (DELETE WHERE period_month = ... ; INSERT ... SELECT). Тогда ключ должен однозначно определять период перезаписи; при параллельных запусках нужна блокировка или выделение периода, чтобы не затереть данные другого процесса. UPSERT по ключу обычно проще для идемпотентности ([§9.3.3](chapter-09-03.md)). См. [§4.1](chapter-04-01.md) (обороты за период).

## 9.3.3. Идемпотентность пайплайна

**Идемпотентность** (в контексте пайплайна загрузки) — свойство: **повторный прогон пайплайна с теми же входными параметрами (период, ключи) даёт тот же результат и не создаёт дублей и не искажает итоги**. То есть повторный запуск эквивалентен одному запуску. Это нужно при сбоях (перезапуск с того же периода), при ручном перезапуске и при тестировании.

Для **загрузки в витрину** идемпотентность обеспечивается тем, что:

1. **Ключ строки витрины** однозначен (счёт + период и т.п.); за период в витрине не больше одной строки на ключ.
2. **Запись выполняется через UPSERT** (ON CONFLICT DO UPDATE / MERGE): повторная вставка тех же данных по тому же периоду только обновляет строки теми же значениями, дублей не появляется.
3. **Границы периода** (period_start, period_end) заданы явно и одинаково при каждом прогоне за этот период; выборка из Core делается по тем же границам.

Для **загрузки проводок в Core** идемпотентность достигается аналогично: уникальный ключ проводки (posting_id или document_id + line_no), при повторной загрузке — INSERT с ON CONFLICT DO NOTHING или DO UPDATE, либо MERGE. Тогда повторная подача того же файла или того же периода не создаёт дубликатов проводок. Контрольные суммы после Staging и после Core ([§9.2](chapter-09-02.md)) при повторном прогоне совпадают с ожидаемыми для этого набора данных. См. [Глоссарий](glossary.md).

## 9.3.4. Сверка с источником после загрузки

После загрузки проводок в Core и (при необходимости) после загрузки агрегатов в витрину выполняют **сверку с источником** ([§7.1](chapter-07-01.md), [§7.2](chapter-07-02.md)):

- **Источник vs DWH (Core):** количество проводок за период, SUM(amount_dt), SUM(amount_ct) по периоду (и при необходимости по счёту, документу); расхождение в пределах допустимой погрешности ([§1.3](chapter-01-03.md)). Ключи сверки и правила сравнения — в регламенте ([§7.2.4](chapter-07-02.md)).
- **Core vs витрина:** по тем же ключам (счёт, период) обороты и остатки в витрине совпадают с расчётом из Core в пределах округления; при материализации ROUND(..., 2) в витрине сравнивают округлённые значения или допускают копеечное расхождение по правилу.

Сверку можно встроить в пайплайн: после шага «загрузка в Core» — запрос контрольных сумм по Core за период и сравнение с эталоном из источника (или из Staging); после шага «загрузка в витрину» — сравнение итогов витрины с итогами из Core за тот же период. При превышении порога — алерт или блокировка ([§7.4](chapter-07-04.md)). Так расхождение локализуется сразу после этапа, на котором оно возникло. См. [§9.2.7](chapter-09-02.md) (сводка этап–контроль–сверка).

## 9.3.5. Порядок шагов и зависимость от сверки

Типичный порядок в пайплайне:

1. Загрузка из источника в Raw → Staging.
2. Контрольные суммы по Staging; при необходимости сверка с выгрузкой источника за период.
3. Загрузка из Staging в Core (проводки); контрольные суммы по Core, сверка с Staging (и с источником).
4. Расчёт оборотов/остатков (если материализуются в Core или отдельной таблице); контрольные суммы после агрегации.
5. Загрузка в витрину (UPSERT по ключу); контрольные суммы по витрине, сверка витрины с Core.
6. При расхождении на любом шаге — алерт, при жёстком регламенте — остановка пайплайна до разбора.

Сверка с источником может быть по шагу 2 или 3 (до или после Core); сверка витрины с Core — после шага 5. Единые период и ключи на всех шагах — обязательны ([§7.2](chapter-07-02.md)).

---

## Ключевое

- **Загрузка в витрину:** данные из Core (обороты, остатки) записываются в Mart по ключу (счёт + период и т.д.); операция — UPSERT (INSERT ... ON CONFLICT DO UPDATE в PostgreSQL, MERGE в Oracle), чтобы не было дублей по ключу.
- **Идемпотентность пайплайна:** повторный прогон с теми же параметрами не создаёт дублей и не меняет итог; для витрины — за счёт UPSERT по однозначному ключу и фиксированных границ периода; для Core — за счёт уникального ключа проводки и INSERT/MERGE без дублирования.
- **Сверка с источником:** после загрузки в Core — сравнение количества и сумм с источником за период; после загрузки в витрину — сравнение итогов витрины с Core; при превышении порога — алерт или остановка по регламенту.
- Порядок шагов: Staging → контроль/сверка → Core → контроль/сверка → агрегация → витрина → сверка витрины с Core; период и ключи едины на всём пути.

В [§9.4](chapter-09-04.md) мы разберём типовые ошибки пайплайна (FLOAT для денег, округление не в том месте, отсутствие сверки) и чек-лист для проверки.
