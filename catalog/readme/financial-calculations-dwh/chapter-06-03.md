# §6.3 Измерения: счета, контрагенты, периоды

В [§6.2](chapter-06-02.md) мы разобрали типы фактов — транзакционные и снимки. Факт связывается с **измерениями** по ключам; от структуры измерений зависят группировка, фильтрация и корректность сверок. Здесь мы разбираем **справочник счетов** (план счетов, иерархия), **контрагенты**, **периоды** (измерение даты) и **SCD** (Slowly Changing Dimension) для хранения истории изменений атрибутов. Слои загрузки и витрины — в [§6.4](chapter-06-04.md). См. [Глоссарий](glossary.md).

---

## 6.3.1. Справочник счетов (dim_account)

**Измерение «счёт»** (dim_account, план счетов) — справочник счетов бухгалтерского или аналитического учёта. Типичные атрибуты:

- **Ключ:** account_id (суррогатный или бизнес-ключ — код счёта).
- **Код счёта**, **наименование**, **тип счёта** (активный/пассивный) — для отчётов и для определения знака сальдо ([§4.2](chapter-04-02.md)).
- **Родитель / группа** — для иерархии (счёт → группа → раздел плана счетов). В звёздной схеме часто хранят в одной таблице: parent_account_id или group_code, level; в снежинке — отдельная таблица групп. См. [§6.1](chapter-06-01.md).

Факт проводок ссылается на account_id; при запросе оборотов или остатков JOIN к dim_account даёт фильтрацию по группе счетов и вывод наименований. Ключ счёта должен быть стабильным: при изменении кода в источнике в DWH решают, вводить ли новую строку (SCD) или обновлять существующую. См. [§6.3.4](chapter-06-03.md).

---

## 6.3.2. Иерархия счетов

**Иерархия** позволяет агрегировать обороты и остатки «вверх» по дереву: счета нижнего уровня → группа → раздел. Реализация:

- **В одной таблице (звезда):** колонки parent_account_id, level, path (материализованный путь) или group_code. Агрегация по группе — JOIN по parent или фильтр по path/level.
- **В отдельных таблицах (снежинка):** dim_account → dim_account_group → dim_section; запросы с несколькими JOIN.
- **Рекурсивный запрос:** в СУБД с поддержкой рекурсивных CTE (PostgreSQL, Oracle) можно обходить дерево от листа к корню и собирать итоги по ветке.

Для финансовых отчётов «оборот по группе счетов» и «остаток по разделу» иерархия в измерении счёта обязательна; выбор «звезда vs снежинка» — по сложности плана счетов и по частоте изменений структуры. См. [Глоссарий](glossary.md).

## 6.3.3. Контрагенты и измерение даты

**Измерение «контрагент»** (dim_counterparty): ключ (counterparty_id), код (ИНН, внешний код), наименование, признаки (тип, регион и т.д.). Факт проводок ссылается на counterparty_id для оборотов и остатков по контрагентам и для сверки с первичными документами. Атрибуты контрагента могут меняться (переименование, смена типа); при необходимости хранят историю через SCD ([§6.3.4](chapter-06-03.md)).

**Измерение «дата»** (dim_date): одна строка на календарную дату. Атрибуты: год, месяц, квартал, номер недели, признак конца месяца, рабочий/выходной — для фильтрации и группировки по периодам без вычислений в запросе. Факт может хранить post_date как DATE и при необходимости связываться с dim_date по дате для доступа к атрибутам периода. Альтернатива — вычислять год/месяц в запросе (EXTRACT, DATE_TRUNC); dim_date удобен при частых отчётах по периодам и при едином календаре (праздники, периоды закрытия). См. [§4.1](chapter-04-01.md) (обороты за период).

## 6.3.4. SCD для истории изменений

**Slowly Changing Dimension (SCD)** — приёмы хранения истории изменений атрибутов измерения. При изменении в источнике (переименование счёта, смена группы контрагента) в DWH нужно решить: перезаписать строку (потеря истории) или сохранить старую версию и добавить новую.

- **SCD Type 1:** обновить строку на месте. История не хранится; все старые факты «увидят» новое значение атрибута после обновления. Просто, подходит для исправления опечаток.
- **SCD Type 2:** при изменении атрибута не обновлять старую строку, а добавить новую с тем же бизнес-ключом; у старой строки дата окончания действия (valid_to), у новой — дата начала (valid_from). Факт связывается с версией измерения по ключу и по дате факта (fact_date между valid_from и valid_to). История сохраняется; запросы усложняются (JOIN по диапазону дат).
- **SCD Type 3:** хранить только предыдущее значение атрибута в отдельной колонке (текущее + «было»); история ограничена одним шагом назад.

Для финансовых измерений (счёт, контрагент) часто используют **Type 2**, если отчёты должны показывать «как было на дату проводки» (наименование счёта на момент операции). Реализация: суррогатный ключ измерения (id), бизнес-ключ (account_code), valid_from, valid_to, текущий флаг (is_current). При загрузке факта выбирают account_id по (account_code, post_date IN (valid_from, valid_to)). См. [Глоссарий](glossary.md).

## 6.3.5. Сводка: ключевые атрибуты измерений

| Измерение   | Ключ           | Важные атрибуты                    | SCD при необходимости |
|-------------|----------------|-------------------------------------|-------------------------|
| Счёт        | account_id     | код, название, тип, parent/группа | Type 2 для истории      |
| Контрагент  | counterparty_id| код, название, тип                 | Type 2 для истории      |
| Дата        | date_key / date| год, месяц, квартал                | Обычно не меняется      |
| Продукт     | product_id     | код, название, тариф              | Type 2 при смене тарифа |

Факт движений хранит только ключи измерений; наименования и атрибуты берутся из измерений при запросе. Согласованность ключей между источником и DWH критична для сверки ([§7.2](chapter-07-02.md)). См. [§6.4](chapter-06-04.md).

## 6.3.6. Типичные ошибки

- **Нет иерархии счетов:** агрегация «оборот по группе» и отчёты по разделам плана счетов невозможны без родителя/группы в измерении.
- **Путать бизнес-ключ и суррогатный ключ в SCD Type 2:** факт должен ссылаться на суррогатный ключ (id версии), а не на код счёта напрямую, иначе при двух версиях счёта с одним кодом связь будет неоднозначной.
- **Не учитывать valid_from/valid_to при JOIN факта к измерению:** при Type 2 нужно ограничивать JOIN по дате факта: fact.post_date BETWEEN dim.valid_from AND dim.valid_to (или is_current для «последней» версии, если факт только по текущим данным).

## Ключевое

- **Справочник счетов** (dim_account): ключ, код, наименование, тип счёта, родитель/группа для иерархии; используется для группировки оборотов и остатков и для вывода в отчётах.
- **Иерархия счетов** — в одной таблице (parent, level, path) или в снежинке; нужна для агрегации по группам и разделам плана счетов.
- **Контрагенты** (dim_counterparty) и **измерение даты** (dim_date): ключи и атрибуты для фильтрации и отчётов по периодам; dim_date упрощает группировку по месяцу/кварталу.
- **SCD Type 2** — хранение истории изменений измерения (valid_from, valid_to); факт связывается с версией по ключу и дате факта; важен для отчётов «как было на дату».

В [§6.4](chapter-06-04.md) мы разберём слои DWH: Raw, Staging, Core, Mart — куда попадают проводки, где считаются обороты и остатки, как устроены витрины для отчётов.
