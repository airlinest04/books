# §6.2 Варианты использования данных

В [§6.1](chapter-06-01.md) мы разобрали BI как слой отчётов, дашбордов и интерактивного анализа поверх хранилищ и витрин. Одни и те же данные могут использоваться по-разному: для операционной отчётности, для аналитики «что произошло и почему», для прогнозов и для питания приложений и API. В этом разделе мы систематически опишем **варианты использования данных**: операционная отчётность, описательная и диагностическая аналитика, прогнозная аналитика и данные для приложений и API. Понимание вариантов использования помогает правильно выбирать источники данных, требования к качеству и свежести и разграничивать доступ. Безопасность и доступ — в [§6.3](chapter-06-03.md); роли пользователей — в [§6.4](chapter-06-04.md). См. [Глоссарий](glossary.md).

---

## 6.2.1. Операционная отчётность

**Операционная отчётность** — использование данных для мониторинга текущего состояния процессов и для регламентных отчётов: что произошло за период (день, неделя, месяц), какие показатели достигнуты, где отклонения от плана. Примеры: отчёт по продажам за день по магазинам, отчёт по заявкам в поддержку, дашборд по загрузке производства, регламентная отчётность для руководства.

Признаки:

- **Регулярность:** отчёты и дашборды обновляются по расписанию (ежедневно, еженедельно) или по запросу с фиксированным периодом.
- **Структурированность:** показатели и форматы отчётов заданы заранее; данные берутся из витрин или DWH с согласованными определениями метрик.
- **Свежесть:** требования к задержке данных умеренные (данные за вчера к утру следующего дня часто достаточно); для части операционных дашбордов может требоваться обновление несколько раз в день.
- **Потребители:** менеджеры, руководители подразделений, операционные сотрудники; потребление через BI (отчёты, дашборды).

Источник данных — DWH или витрины, подгружаемые из операционных систем через ETL; качество и согласованность критичны, так как на основе отчётности принимаются операционные решения. Управление данными обеспечивает владельцев витрин и единые определения метрик ([§5.1](chapter-05-01.md), [§6.1](chapter-06-01.md)).

## 6.2.2. Описательная и диагностическая аналитика

**Описательная аналитика** — анализ того, что произошло: агрегаты, распределения, сравнения периодов и сегментов. **Диагностическая аналитика** — выявление причин: почему показатель изменился, какие факторы связаны с результатом. Примеры: разбор падения конверсии по шагам воронки, сравнение регионов по выручке и маржинальности, анализ причин оттока клиентов.

Признаки:

- **Исследовательский характер:** аналитик формулирует вопросы, выбирает данные и методы, строит выборки и визуализации; не только просмотр готовых отчётов.
- **Глубина данных:** часто нужны детальные данные (транзакции, события), а не только агрегаты; возможны ad hoc-запросы к витринам и к таблицам DWH или к обработанному слою озера.
- **Инструменты:** BI (интерактивный анализ), SQL, скрипты (Python, R), специализированные инструменты аналитики; потребление может выходить за рамки стандартных дашбордов.
- **Потребители:** аналитики, менеджеры с аналитическими компетенциями; результаты оформляются в отчёты, презентации или доводятся до решений через рекомендации.

Источники данных — DWH, витрины, при необходимости обработанный слой озера; требования к качеству высокие для ключевых метрик, при разведочном анализе допустимы ограничения (например, выборка, а не полный объём). Lineage и каталог помогают аналитику понимать происхождение данных и ограничения ([§3.3](chapter-03-03.md)).

## 6.2.3. Прогнозная аналитика

**Прогнозная аналитика** (predictive analytics) — использование данных для построения моделей, предсказывающих будущие значения или вероятности: прогноз спроса, прогноз оттока клиентов, оценка риска, рекомендации. Данные используются как обучающая выборка и как входные признаки для моделей; результаты моделей могут попадать обратно в отчётность (скоринг в дашборде, прогноз в отчёте).

Признаки:

- **Модели и алгоритмы:** машинное обучение, статистические модели; данные должны быть подготовлены (признаки, разметка при обучении с учителем).
- **Объём и разнообразие:** часто требуются большие объёмы исторических данных и разнообразные признаки; источник — DWH, витрины или обработанный слой озера; для части сценариев — сырые или полуобработанные данные в озере.
- **Итеративность:** эксперименты с признаками, моделями и выборками; потребность в воспроизводимости (версии данных, версии моделей).
- **Потребители:** аналитики данных, ML-инженеры, прикладные специалисты; результаты потребляют бизнес через внедрённые скоринги, рекомендации или отчёты с прогнозами.

Требования к качеству данных для обучения моделей высокие: некорректные и смещённые данные ведут к некачественным прогнозам. Управление данными включает описание наборов для ML в каталоге, владельцев и правил использования персональных и чувствительных данных при обучении моделей ([§2.1](chapter-02-01.md), конфиденциальность).

## 6.2.4. Данные для приложений и API

**Данные для приложений и API** — использование хранимых данных не только для отчётности и аналитики, но и для **питания приложений** и **внешних потребителей** через API или выгрузки: персональные рекомендации в приложении, тарифы и остатки в кассе, справочники для внешних партнёров, данные для мобильного приложения.

Признаки:

- **Программный доступ:** данные запрашиваются приложением или внешней системой по API, по запросу к БД или через сообщения; не только человек через BI.
- **Требования к задержке:** часто нужна низкая задержка (ответ в миллисекундах или секундах); данные могут кэшироваться или реплицироваться из DWH/витрин в слой обслуживания приложений.
- **Формат и контракт:** API задаёт контракт (формат ответа, поля); изменения в структуре данных должны согласовываться с потребителями API.
- **Потребители:** внутренние и внешние приложения, партнёры; доступ контролируется ключами API, квотами и политиками ([§6.3](chapter-06-03.md)).

Источник данных — витрины, DWH или отдельные реплики/кэши; данные для API могут быть агрегированными или обезличенными в соответствии с политиками доступа. Управление данными включает описание API и наборов данных в каталоге, владельцев API и правил использования данных при передаче третьим лицам.

|----------------------|------|------------------------|------------------|-----------------------------------|
| Операционная отчётность | Мониторинг и регламентные отчёты | Менеджеры, руководство, операционные сотрудники | DWH, витрины | Согласованные метрики, задержка час–день; качество высокое |

| Прогнозная аналитика | Прогнозы, скоринг, рекомендации | Аналитики данных, ML-инженеры; бизнес — через внедрённые модели | DWH, витрины, озеро (обучение и признаки) | Качество и репрезентативность для моделей; воспроизводимость |

## 6.2.6. Связь вариантов использования с управлением данными

Разные варианты использования предъявляют разные требования к данным и к политикам:

- **Операционная отчётность** требует единых определений метрик и владельцев витрин; BI подключается только к утверждённым источникам.
- **Аналитика** требует каталога и lineage, чтобы аналитики понимали происхождение и ограничения данных; при доступе к детальным и чувствительным данным — соблюдение политик доступа.
- **Прогнозная аналитика** требует описания наборов для ML, правил использования персональных данных при обучении и версионирования данных для воспроизводимости.
- **API** требуют контрактов, владельца API и контроля доступа (ключи, квоты); при передаче данных третьим лицам — согласование с владельцами данных и compliance.

Управление данными (каталог, владельцы, политики доступа, качество) должно учитывать все варианты использования, чтобы данные оставались обнаруживаемыми, понятными и используемыми в рамках правил организации.

---

## Ключевое

- **Варианты использования данных:** операционная отчётность (мониторинг, регламентные отчёты), описательная и диагностическая аналитика (что произошло и почему), прогнозная аналитика (прогнозы, модели, ML), данные для приложений и API (питание систем и партнёров).
- Каждый вариант задаёт своих потребителей, источники данных и требования к свежести и качеству; один набор данных может обслуживать несколько вариантов.
- Операционная отчётность и аналитика опираются на DWH и витрины; прогнозная аналитика может использовать и озеро; API — на витрины и реплики с контрактами и контролем доступа.
- Управление данными учитывает варианты использования: единые метрики и владельцы для отчётности, каталог и lineage для аналитики, правила для ML и API.

В [§6.3](chapter-06-03.md) мы разберём **безопасность и доступ** к данным: разграничение доступа к данным и объектам BI, аудит обращений, анонимизация и обезличивание при необходимости.
