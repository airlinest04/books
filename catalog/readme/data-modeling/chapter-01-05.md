# §1.5 Ограничения целостности

В [§1.4](chapter-01-04.md) мы разобрали, как изображать модель данных на ER-диаграммах. Структура сущностей и связей задаётся не только именами и типами, но и **ограничениями целостности** — правилами, которые СУБД проверяет при вставке, обновлении и удалении данных. Ограничения гарантируют, что в базе не окажется некорректных или противоречивых значений. В этом разделе мы рассмотрим основные виды ограничений на уровне модели: **NOT NULL**, **UNIQUE**, **CHECK** и **внешние ключи** — зачем они нужны, как их задавать в схеме и как отражать на диаграммах. Раздел завершает главу 1; в [§2.1](chapter-02-01.md) мы перейдём к нормализации баз данных и устранению избыточности и аномалий.

---

## 1.5.1. Что такое ограничение целостности

**Ограничение целостности** (integrity constraint) — правило, накладываемое на данные в базе; СУБД проверяет его при каждой модификации затронутых строк и отклоняет операцию, если правило нарушается. Ограничения задаются в схеме (DDL) и хранятся в метаданных СУБД; приложение не может «обойти» их без изменения схемы или отключения проверки (что, как правило, недопустимо в продакшене). См. [Глоссарий](glossary.md).

Зачем задавать ограничения на уровне модели и схемы:

- **Защита от ошибок:** неверные данные (пустое обязательное поле, дубликат уникального ключа, ссылка на несуществующую строку) отсекаются на уровне БД, а не только в коде приложения. Это снижает риск «мусорных» данных при сбоях, параллельных обновлениях и интеграции из разных источников.
- **Документирование правил:** схема с ограничениями явно фиксирует бизнес-правила (например, «сумма заказа неотрицательна», «у каждого заказа есть клиент»). Разработчики и аналитики видят правила в одном месте — в определении таблиц.
- **Единая точка проверки:** без ограничений каждое приложение и каждый скрипт должны сами проверять одни и те же правила; при добавлении нового потребителя данных легко пропустить проверку. Ограничения в БД действуют для всех клиентов.
- **Оптимизация:** СУБД может использовать знание об уникальности и внешних ключах для построения планов запросов и индексов.

Ограничения делят на категории: **внутри одной таблицы** (NOT NULL, UNIQUE, CHECK, первичный ключ) и **между таблицами** (внешний ключ, ссылочная целостность). Ниже разберём каждое из основных ограничений.

---

## 1.5.2. NOT NULL — обязательность значения

Ограничение **NOT NULL** указывает, что столбец не может содержать значение NULL (отсутствие значения). Каждая строка должна иметь в этом столбце конкретное значение заданного типа.

**Зачем на уровне модели:**

- Обязательные с точки зрения бизнеса атрибуты (идентификатор, имя клиента, дата заказа, сумма) не должны быть «пустыми». NULL в таких полях означал бы неполные или бессмысленные данные.
- Первичный ключ по определению не может быть NULL; в реляционной модели это заложено в понятие ключа. Явное указание NOT NULL для столбцов первичного ключа — стандартная практика.
- Внешний ключ может быть NOT NULL (связь обязательна: у каждого заказа есть клиент) или допускать NULL (связь необязательна: заказ может быть «анонимным» до привязки к клиенту). Решение фиксируется в модели в зависимости от доменных правил.

**В DDL (пример):**

```sql
CREATE TABLE orders (
  id         INTEGER PRIMARY KEY,
  order_date DATE    NOT NULL,
  customer_id INTEGER REFERENCES customers(id),  -- может быть NULL, если заказ без клиента
  total      NUMERIC(12,2) NOT NULL
);
```

**На ER-диаграмме:** опциональные атрибуты иногда помечают как «optional» или «nullable»; обязательные можно не помечать или явно указать «required», «NOT NULL». В нотации «воронья лапка» обязательность связи со стороны «одного» часто показывают вертикальной чертой (обязательно) против кружка (необязательно).

## 1.5.3. UNIQUE — уникальность значения

Ограничение **UNIQUE** указывает, что значения в столбце (или в наборе столбцов) не могут повторяться: каждая комбинация значений встречается не более чем в одной строке. NULL обычно не участвует в проверке уникальности (в стандарте SQL несколько NULL считаются разными; в части СУБД только одна строка может иметь NULL в уникальном столбце — зависит от реализации).

**Зачем на уровне модели:**

- **Естественный ключ:** если атрибут должен быть уникальным в рамках таблицы (логин, email, код товара, номер заказа), но не является первичным ключом (например, PK — суррогатный id), на этот атрибут накладывают UNIQUE.
- **Связь 1:1:** при реализации связи один-к-одному через внешний ключ в одной из таблиц столбец FK должен быть UNIQUE, иначе одна строка «целевой» таблицы могла бы соответствовать нескольким строкам «исходной» — связь станет 1:N. См. [§1.2](chapter-01-02.md).
- **Запрет дубликатов по смыслу:** например, один и тот же пользователь не может быть дважды записан на один и тот же курс в одну дату — уникальность по паре (user_id, course_id) или по (user_id, course_id, date) в таблице записей.

**В DDL (примеры):**

```sql
-- Уникальный логин в таблице пользователей
CREATE TABLE users (
  id    SERIAL PRIMARY KEY,
  login VARCHAR(50) NOT NULL UNIQUE,
  email VARCHAR(255) UNIQUE
);

-- Связь 1:1: у одной записи hr_records — один сотрудник
CREATE TABLE hr_records (
  id          SERIAL PRIMARY KEY,
  employee_id INTEGER NOT NULL UNIQUE REFERENCES employees(id),
  hire_date   DATE NOT NULL
);
```

**Составной UNIQUE:** для пары (или набора) столбцов уникальность задаётся ограничением на уровне таблицы: `UNIQUE (col_a, col_b)`. Тогда дубликатом считается повторение одной и той же пары (a, b); разные пары допустимы.

## 1.5.4. CHECK — проверка по условию

Ограничение **CHECK** задаёт логическое условие, которое должно выполняться для каждой строки (или для каждой изменяемой строки). Если условие ложно, операция вставки или обновления отклоняется. Условие записывается как булево выражение над столбцами строки (сравнения, диапазоны, IN, подзапросы — в зависимости от возможностей СУБД).

**Зачем на уровне модели:**

- **Домен значения:** ограничить допустимые значения атрибута (статус из списка, положительная сумма, дата не в будущем для «даты события», возраст в разумных пределах). Это сужает множество значений сверх того, что даёт тип данных.
- **Согласованность между столбцами:** например, дата окончания не раньше даты начала; минимальная сумма заказа не меньше нуля; процент скидки от 0 до 100.
- **Бизнес-правила:** правила, которые можно выразить формулой по атрибутам одной строки (и при необходимости по константам), удобно фиксировать в CHECK. Сложные правила, требующие подзапросов или нескольких таблиц, не везде поддерживаются или усложняют схему — тогда их выносят в приложение или триггеры.

**В DDL (примеры):**

```sql
CREATE TABLE orders (
  id          INTEGER PRIMARY KEY,
  total       NUMERIC(12,2) NOT NULL CHECK (total >= 0),
  status      VARCHAR(20) CHECK (status IN ('new', 'paid', 'shipped', 'delivered', 'cancelled'))
);

CREATE TABLE order_items (
  id        INTEGER PRIMARY KEY,
  order_id  INTEGER NOT NULL REFERENCES orders(id),
  quantity  NUMERIC(10,2) NOT NULL CHECK (quantity > 0),
  unit_price NUMERIC(12,2) NOT NULL CHECK (unit_price >= 0)
);
```

**Ограничения CHECK в разных СУБД:** стандарт SQL допускает CHECK; часть СУБД не поддерживает подзапросы в CHECK или ссылки на другие таблицы. Ограничение должно быть детерминированным и не вызывать побочных эффектов. Для кроссплатформенной модели лучше ограничиваться проверками в рамках одной строки.

**На ER-диаграмме:** CHECK редко изображают явно на концептуальной диаграмме; в логической модели и в DDL они фиксируются в описании столбца или в списке ограничений таблицы.

## 1.5.5. Внешний ключ и ссылочная целостность

**Внешний ключ** (foreign key) как ограничение целостности гарантирует **ссылочную целостность**: каждое значение в столбце(ах) внешнего ключа либо совпадает со значением первичного ключа (или уникального ключа) целевой таблицы, либо равно NULL (если столбец допускает NULL). Нельзя вставить или обновить строку так, чтобы она ссылалась на несуществующую строку в целевой таблице; при удалении или обновлении целевой строки поведение задаётся правилами ON DELETE и ON UPDATE. См. [Глоссарий](glossary.md) и [§1.2](chapter-01-02.md).

**Зачем на уровне модели:**

- **Реализация связей:** внешний ключ — способ выразить связь между сущностями в реляционной модели. Без ограничения FK приложение могло бы записать произвольный id в столбец «клиент», в том числе несуществующий — появятся «висячие» ссылки и несогласованность данных.
- **Запрет «сирот»:** строки в дочерней таблице не могут ссылаться на удалённую родительскую строку (при RESTRICT), либо каскадно удаляются/обновляются (при CASCADE), либо ссылка обнуляется (при SET NULL) — в зависимости от выбранного правила. Модель должна явно задавать желаемое поведение.
- **Документирование связей:** по схеме и диаграмме видно, какие таблицы от каких зависят; оптимизатор и разработчики учитывают связи при построении запросов и индексов.

**Правила ON DELETE и ON UPDATE** (кратко):

| Правило | При удалении/обновлении целевой строки |
|---------|----------------------------------------|
| RESTRICT / NO ACTION | Запретить операцию, если есть ссылающиеся строки |
| CASCADE | Удалить (обновить) и ссылающиеся строки |
| SET NULL | Установить NULL в столбце FK у ссылающихся строк (только если столбец допускает NULL) |
| SET DEFAULT | Установить значение по умолчанию в столбце FK (поддержка в СУБД различается) |

Выбор правила — часть моделирования: он отражает бизнес-правило (например, «при удалении клиента его заказы не удалять, но запретить удаление клиента, пока есть заказы» — RESTRICT).

**На ER-диаграмме:** связь между сущностями изображается линией; в логической модели линия соответствует внешнему ключу в таблице «многих» (или в одной из таблиц при 1:1). На диаграмме можно подписать имя FK-столбца и при необходимости правило ON DELETE/ON UPDATE в документации или в подписи.

## 1.5.6. Первичный ключ как ограничение

**Первичный ключ** (primary key) одновременно задаёт уникальность и обязательность: все столбцы, входящие в PK, объявляются NOT NULL, а комбинация их значений должна быть уникальной. Таким образом, PK — это объединение ограничений UNIQUE и NOT NULL плюс семантика «идентификатор строки». См. [Глоссарий](glossary.md).

В модели первичный ключ выбирается на этапе проектирования сущностей и связей ([§1.2](chapter-01-02.md)); в схеме он объявляется явно (`PRIMARY KEY`), и по нему строятся внешние ключи из других таблиц. Один столбец или набор столбцов таблицы может быть объявлен первичным ключом; обычно на PK автоматически создаётся уникальный индекс.

## 1.5.7. Сводная таблица ограничений и отражение на диаграмме

В таблице ниже сведены рассмотренные ограничения, их назначение и типичное отражение в модели и на диаграмме.

| Ограничение | Назначение | Где задаётся | На ER-диаграмме |
|-------------|------------|--------------|------------------|
| NOT NULL | Обязательность значения в столбце | Определение столбца | Опционально: пометка «required» / «optional» у атрибута или конца связи |
| UNIQUE | Неповторяемость значения (или комбинации) | Столбец или таблица | Уникальные атрибуты можно помечать (UQ); при 1:1 — явно, что FK уникален |
| CHECK | Условие на значение(я) строки | Столбец или таблица | Редко рисуют; фиксируют в описании атрибута или в документации |
| PRIMARY KEY | Уникальный идентификатор строки, NOT NULL | Таблица | Атрибуты PK помечают PK или подчёркивают |
| FOREIGN KEY | Ссылка на строку другой таблицы, ссылочная целостность | Таблица (столбец + REFERENCES) | Линия между сущностями; направление от FK к PK; при необходимости подпись ON DELETE |

Концептуальная диаграмма чаще отражает только сущности, связи и кратность; логическая диаграмма и DDL дополняют их полным набором ограничений. Важно, чтобы в описании модели (текст или глоссарий) было зафиксировано, какие поля обязательны, какие уникальны и какие проверки (CHECK) применяются, чтобы при реализации в конкретной СУБД ничего не упустить.

## 1.5.8. Типичные ошибки при задании ограничений

- **Не задать NOT NULL для обязательных полей:** в результате в базе появляются NULL там, где по смыслу значение должно быть всегда (например, дата заказа, клиент заказа). Явно решать для каждого атрибута: допускает ли домен отсутствие значения.
- **Забыть UNIQUE при связи 1:1 через FK:** без UNIQUE на столбце внешнего ключа две строки могут ссылаться на одну и ту же строку — связь превращается в 1:N. См. [§1.2](chapter-01-02.md).
- **CHECK только в приложении:** если правило домена (сумма >= 0, статус из списка) проверяется только в коде, данные, попавшие в БД через другой канал (миграция, скрипт, интеграция), могут нарушить правило. Критичные доменные правила дублировать в CHECK.
- **Не задать ON DELETE / ON UPDATE для внешних ключей:** поведение по умолчанию (часто RESTRICT или NO ACTION) может не соответствовать бизнес-правилам; при удалении родительской строки возникнут неожиданные ошибки или каскады. Явно выбирать и документировать правило для каждой связи.
- **Слишком жёсткий CHECK:** условие, которое сложно выполнить при легитимных данных (например, жёсткая привязка к текущей дате или к другой таблице без подзапроса), приведёт к частым отказам или к отказу от ограничения. CHECK должен отражать стабильные инварианты домена.
- **Игнорировать ограничения при миграциях и импорте:** массовая загрузка данных может нарушить UNIQUE или FK; порядок вставки (сначала родители, потом дети) и временное отключение ограничений (если СУБД позволяет) должны быть продуманы, а после загрузки целостность нужно проверить заново.

## Ключевое

- **Ограничение целостности** — правило, проверяемое СУБД при изменении данных; защищает от некорректных и противоречивых значений и документирует бизнес-правила в схеме.
- **NOT NULL** — обязательность значения; для первичного ключа и бизнес-критичных атрибутов задавать явно. **UNIQUE** — неповторяемость значения или комбинации столбцов; используется для естественных ключей и для реализации связи 1:1 через FK.
- **CHECK** — условие на строку (диапазон, список значений, связь между столбцами); задаёт домен и инварианты. **Внешний ключ** — ссылочная целостность: ссылка только на существующую строку; поведение при удалении/обновлении целевой строки задаётся ON DELETE / ON UPDATE (RESTRICT, CASCADE, SET NULL).
- Первичный ключ объединяет UNIQUE и NOT NULL и задаёт идентификатор строки. На ER-диаграмме ограничения отражают по необходимости: PK и связи (линии) — обязательно; NOT NULL, UNIQUE, CHECK — в описании атрибутов или в документации к схеме.

В [§2.1](chapter-02-01.md) мы перейдём к нормализации баз данных: зачем устранять избыточность и аномалии (вставки, обновления, удаления) и как согласованность данных связана с нормальными формами.
