# §4.4 Сравнение JOIN и подзапросов

В [§4.3](chapter-04-03.md) мы рассмотрели внешние соединения. Одну и ту же задачу часто можно решить **соединением (JOIN)** или **подзапросом** — SELECT внутри другого SELECT. В этом разделе сравним оба подхода: когда они эквивалентны, когда что читаемее и когда что эффективнее. Подзапросы подробно рассматриваются в гл. 9. См. [документацию по подзапросам](https://www.postgresql.org/docs/current/functions-subquery.html).

---

## 4.4.1. Подзапрос как альтернатива

**Подзапрос** — это запрос, вложенный в другой. Он может стоять в FROM (как источник данных), в WHERE (в IN, EXISTS, в сравнении), в SELECT (как скалярное выражение). Подзапрос в IN мы уже использовали в [§3.3](chapter-03-03.md): `WHERE id IN (SELECT user_id FROM admins)`.

Многие запросы можно написать и через JOIN, и через подзапрос. Результат совпадает, но читаемость и план выполнения могут отличаться.

---

## 4.4.2. Получение связанных данных: JOIN vs подзапрос в SELECT

Задача: заказы с именем клиента.

**JOIN:**

```sql
SELECT o.id, o.total, c.name AS customer_name
FROM orders o
JOIN customers c ON o.customer_id = c.id;
```

**Подзапрос в SELECT** (скалярный — возвращает одно значение на строку):

```sql
SELECT o.id, o.total,
  (SELECT c.name FROM customers c WHERE c.id = o.customer_id) AS customer_name
FROM orders o;
```

Оба варианта дают один столбец с именем клиента. JOIN обычно читается проще и явно показывает связь таблиц. Скалярный подзапрос удобен, когда нужно одно дополнительное поле и не хочется усложнять FROM.

---

## 4.4.3. Фильтрация «есть совпадение»: JOIN vs IN vs EXISTS

Задача: клиенты, у которых есть хотя бы один заказ.

**JOIN + DISTINCT:**

```sql
SELECT DISTINCT c.id, c.name
FROM customers c
JOIN orders o ON o.customer_id = c.id;
```

**IN с подзапросом:**

```sql
SELECT id, name
FROM customers
WHERE id IN (SELECT customer_id FROM orders);
```

**EXISTS с подзапросом:**

```sql
SELECT id, name
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

Результат одинаков. IN и EXISTS часто читаются лучше для задачи «есть ли связь»: не нужно DISTINCT и не возникает дубликатов. EXISTS может быть эффективнее: достаточно найти первое совпадение и прекратить поиск. Подзапросы в SELECT и WHERE подробнее — в [§9.2](chapter-09-02.md).

---

## 4.4.4. Когда предпочтительнее JOIN

JOIN обычно выбирают, когда:

- Нужны столбцы из обеих таблиц в одной строке результата.
- Связь «один к одному» или «многие к одному» — дубликатов не будет.
- Логика запроса — «объединить две таблицы по ключу»; JOIN это прямо выражает.

Пример: отчёт по заказам с именем клиента, датой и суммой — типичный случай для JOIN.

---

## 4.4.5. Когда предпочтительнее подзапрос

Подзапрос уместен, когда:

- Нужна только проверка существования связи — **EXISTS** или **IN** часто короче и понятнее, чем JOIN + DISTINCT.
- Нужно одно скалярное значение на строку (имя, счётчик) — подзапрос в SELECT.
- Условие сложное или зависит от внешнего запроса — коррелированный подзапрос может быть естественнее.
- Один и тот же подзапрос используется в нескольких местах — его выносят в CTE (гл. 13).

---

## 4.4.6. Дубликаты при связи «один ко многим»

При JOIN связи «один ко многим» (заказ → позиции заказа) одна строка «одной» таблицы повторяется. Если нужны уникальные заказы с каким-то признаком из «многих», возможны два подхода:

**JOIN + DISTINCT:**

```sql
SELECT DISTINCT o.id, o.total
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE oi.product_id = 42;
```

**Подзапрос с IN или EXISTS:**

```sql
SELECT id, total
FROM orders
WHERE id IN (SELECT order_id FROM order_items WHERE product_id = 42);
```

Подзапрос с IN/EXISTS даёт уникальные строки без DISTINCT. JOIN требует DISTINCT, если важно избежать дублей.

---

## 4.4.7. Производительность

PostgreSQL переписывает и оптимизирует запросы; JOIN и подзапрос часто приводятся к схожим планам. Раньше подзапросы выполнялись построчно; современный планировщик обычно этого избегает.

Практические рекомендации:

- Сначала писать понятный запрос; при проблемах с производительностью — анализировать EXPLAIN.
- EXISTS часто эффективнее IN при проверке существования, особенно с большими подзапросами.
- NOT IN с подзапросом, возвращающим NULL, ведёт себя неочевидно; NOT EXISTS обычно безопаснее (см. [§3.3](chapter-03-03.md), [§9.2](chapter-09-02.md)).

---

## 4.4.8. Сводная таблица

| Ситуация | Предпочтительно | Причина |
|----------|-----------------|---------|
| Нужны столбцы из двух таблиц в одной строке | JOIN | Прямое выражение связи |
| Проверка «есть совпадение» | EXISTS или IN | Без дубликатов, часто эффективнее |
| Одно дополнительное поле на строку | JOIN или скалярный подзапрос | JOIN — проще, подзапрос — иногда короче |
| Уникальные строки при связи один-ко-многим | IN/EXISTS или JOIN + DISTINCT | IN/EXISTS не создают дубликатов |
| Сложная вложенная логика | Подзапрос или CTE | Разбиение на шаги |

---

## Ключевое

- Одну задачу можно решить через JOIN или подзапрос; результат может совпадать.
- **JOIN** — когда нужны столбцы из обеих таблиц; связь явно видна в запросе.
- **IN, EXISTS** — когда важна только проверка связи; дубликатов нет, запрос часто короче.
- При связи «один ко многим» JOIN дублирует строки; для уникальности — DISTINCT или IN/EXISTS.
- Производительность зависит от плана; оба подхода могут быть эффективны; при сомнениях — EXPLAIN.

В [§4.5](chapter-04-05.md) рассмотрим self-join — соединение таблицы с собой для иерархий и связей внутри одной таблицы.
