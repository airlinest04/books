# §4.1 gpstart и gpstop

В [§3.4](chapter-03-04.md) мы рассмотрели первый запуск кластера (gpstart) и проверку через psql. Глава 4 посвящена **управлению кластером**. В этом разделе — утилиты **gpstart** и **gpstop**: запуск и остановка всех инстансов Greenplum (Master и сегментов), режимы остановки (graceful и immediate), перезапуск и **перезагрузка конфигурации без остановки** (gpstop -u). Отказоустойчивость и восстановление сегментов — в [§4.2](chapter-04-02.md); прочие утилиты администратора — в [§4.3](chapter-04-03.md). По [Tanzu Greenplum 7 — Starting and Stopping Greenplum Database](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-managing-startstop.html).

---

## 4.1.1. Где и как запускать gpstart и gpstop

Утилиты **gpstart** и **gpstop** находятся в **$GPHOME/bin** и выполняются **только на хосте Master** под пользователем **gpadmin**. Перед запуском должны быть заданы переменные **GPHOME** и **MASTER_DATA_DIRECTORY** (через source greenplum_path.sh и export или через ~/.bashrc). Обе утилиты по MASTER_DATA_DIRECTORY определяют топологию кластера и по SSH отдают команды хостам сегментов, координируя запуск или остановку всех постмастеров. См. [§3.4](chapter-03-04.md), [Глоссарий](glossary.md).

**Важно:** не останавливайте процессы Greenplum через **kill** (в том числе kill -9). Это может привести к повреждению данных и затруднить анализ сбоев. Для остановки используйте **gpstop**; для завершения отдельных запросов или сессий — функции **pg_cancel_backend()** и **pg_terminate_backend()** в БД. По документации Tanzu Greenplum.

---

## 4.1.2. gpstart: запуск кластера

**gpstart** запускает все экземпляры PostgreSQL в кластере: сначала сегменты на всех хостах (параллельно), затем Master. После успешного выполнения кластер готов принимать подключения.

Базовый запуск:

```bash
gpstart
```

Утилита проверяет конфигурацию и при обнаружении сегментов в состоянии down может запросить подтверждение. Для неинтерактивного запуска (скрипты, автоматизация) используйте **-a** (auto-accept):

```bash
gpstart -a
```

Дополнительные опции (уточняйте в `gpstart --help` и в документации вашей версии): **-d** (каталог данных Master, если не задан MASTER_DATA_DIRECTORY), **-q** (тихий режим), **-v** (подробный вывод). Логи пишутся в **~/gpAdminLogs**. См. [§3.4](chapter-03-04.md), [§4.4](chapter-04-04.md).

---

## 4.1.3. gpstop: остановка кластера. Режимы (smart, fast, immediate)

**gpstop** останавливает все процессы Postgres в кластере (Master и сегменты), по умолчанию параллельно (до 64 потоков). Режим остановки задаётся опцией **-M**. По [Tanzu Greenplum 7 — Stopping Greenplum Database](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-managing-startstop.html).

| Режим (-M) | Описание |
|------------|----------|
| **smart** (по умолчанию) | Graceful shutdown: ожидание завершения активных транзакций и отключения клиентов. Если через некоторое время (например, 2 минуты) сессии ещё есть, gpstop запрашивает: продолжать ожидание, перейти в fast или immediate. |
| **fast** | Остановка «быстрая»: текущие транзакции откатываются, соединения разрываются, затем инстансы останавливаются. Данные не повреждаются, но незавершённые транзакции теряются. |
| **immediate** | Немедленная остановка без нормального завершения работы: процессы завершаются без сброса буферов и без корректного закрытия. **Не рекомендуется**: возможна порча данных и сложности при разборе сбоев. Используйте только в крайних случаях (например, «зависший» кластер). |

Команды:

```bash
gpstop              # smart (по умолчанию)
gpstop -M fast      # откат транзакций, разрыв соединений, затем остановка
gpstop -M immediate # принудительная остановка (рискованно)
```

При наличии активных подключений в режиме smart gpstop может ждать и затем выводить интерактивный запрос; для скриптов часто используют **-a** (не запрашивать подтверждение) в сочетании с **-M fast**, если допустимо разорвать сессии. См. [Глоссарий](glossary.md).

## 4.1.4. Перезапуск кластера: gpstop -r

Опция **-r** (restart) у **gpstop** останавливает кластер и после завершения остановки **запускает его снова** (фактически выполняет gpstop, затем gpstart). Удобно после изменения параметров, требующих полного перезапуска (например, shared_buffers, порты, часть GUC).

```bash
gpstop -r
```

Режим остановки задаётся так же опцией -M (smart, fast, immediate). После перезапуска все инстансы поднимаются заново; активные сессии будут разорваны (при -M fast или immediate — сразу, при smart — после ожидания или вашего выбора в диалоге). По документации Tanzu Greenplum.

---

## 4.1.5. Перезагрузка конфигурации без остановки: gpstop -u

Часть изменений конфигурации можно применить **без остановки** кластера. Утилита **gpstop** с опцией **-u** (reload) перечитывает конфигурационные файлы на Master и сегментах и применяет изменения **только к тем параметрам**, которые поддерживают перезагрузку «на лету». При этом активные сессии продолжают работать; новые подключения и новые запросы уже видят обновлённые настройки. По [Tanzu Greenplum 7 — Reloading Configuration File Changes Only](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-managing-startstop.html).

```bash
gpstop -u
```

Обычно перезагружаются:

- **pg_hba.conf** — правила доступа клиентов; изменения вступают в силу при следующих подключениях.
- Параметры в **postgresql.conf**, помеченные в документации как изменяемые без перезапуска (например, часть параметров логирования, work_mem и т.д.).

Параметры, для которых в документации указано «requires restart», после изменения **не** подхватываются при gpstop -u; для их применения нужен полный перезапуск (**gpstop -r**). Список параметров и способ их изменения см. в справочнике Greenplum и в утилите gpconfig ([§4.3](chapter-04-03.md)).

## 4.1.6. Режим обслуживания (maintenance mode): gpstart -m, gpstop -m

Для задач обслуживания (например, правка системного каталога по указанию поддержки) можно запустить **только Master** без сегментов — **режим обслуживания** (maintenance mode). Сегменты при этом не трогаются; подключение возможно только к Master, и только для административных операций. По документации Tanzu Greenplum этот режим рекомендуется использовать только по указанию технической поддержки.

Запуск Master в режиме обслуживания:

```bash
gpstart -m
```

Подключение для каталоговых операций (с опцией utility):

```bash
PGOPTIONS='-c gp_role=utility' psql postgres
```

После завершения работ Master останавливают и поднимают кластер в обычном режиме:

```bash
gpstop -m
gpstart
```

Некорректное использование режима обслуживания может привести к рассогласованности системы; не используйте его без необходимости и без понимания последствий. См. документацию вашего дистрибутива.

## 4.1.7. Завершение отдельных сессий и запросов

Если нужно завершить не весь кластер, а конкретный запрос или сессию, используйте функции PostgreSQL в подключённой к Master сессии:

- **pg_cancel_backend(pid)** — отмена текущего запроса у процесса с указанным PID (запрос прерывается, соединение остаётся).
- **pg_terminate_backend(pid)** — принудительное завершение соединения (сессия разрывается).

PID процессов можно посмотреть в представлении **pg_stat_activity** (столбец pid). Пример:

```sql
SELECT usename, pid, state, query FROM pg_stat_activity WHERE datname = 'postgres';
SELECT pg_terminate_backend(12345);  -- подставьте нужный pid
```

Так можно освободить «зависшие» сессии перед graceful остановкой (gpstop -M smart) или не останавливая кластер. См. документацию Greenplum по системным представлениям.

---

## 4.1.8. Типичные ошибки

- **Останавливать процессы через kill:** используйте только **gpstop**; иначе возможна порча данных и нечитаемые логи.
- **Использовать gpstop -M immediate без крайней необходимости:** риск повреждения данных; предпочтительны smart или fast.
- **Ожидать, что все параметры применились после gpstop -u:** только параметры, поддерживающие reload; для остальных нужен **gpstop -r**.
- **Запускать gpstart/gpstop не с Master или не под gpadmin:** утилиты должны выполняться на хосте Master под пользователем gpadmin с заданными GPHOME и MASTER_DATA_DIRECTORY.

---

## Ключевое

- **gpstart** и **gpstop** выполняются на **хосте Master** под **gpadmin** при заданных GPHOME и MASTER_DATA_DIRECTORY; процессы Greenplum не останавливают через kill.
- **gpstart** — запуск всего кластера; **gpstart -a** — без интерактивных запросов; **gpstart -m** — только Master в режиме обслуживания.
- **gpstop** — остановка; режимы **-M smart** (по умолчанию, ожидание завершения), **-M fast** (откат и разрыв соединений), **-M immediate** (принудительно, не рекомендуется). **gpstop -r** — остановка и перезапуск; **gpstop -u** — перезагрузка конфигурации (pg_hba.conf и параметры с reload) без остановки.
- Параметры, требующие перезапуска, не применяются при **gpstop -u**; для них нужен **gpstop -r**.
