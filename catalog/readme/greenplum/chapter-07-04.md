# §7.4 Представления и материализованные представления

В [§7.3](chapter-07-03.md) мы разобрали COPY и gpload. **Представления (VIEW)** и **материализованные представления (MATERIALIZED VIEW)** в Greenplum работают по сути как в PostgreSQL: VIEW хранит запрос и выполняется при обращении; MATERIALIZED VIEW хранит результат запроса в табличном виде и обновляется командой **REFRESH**. В этом разделе — **CREATE VIEW**, **CREATE MATERIALIZED VIEW**, **REFRESH MATERIALIZED VIEW** и использование в DWH (витрины, предрасчитанные агрегаты). По [Tanzu Greenplum 7 — Creating and Managing Views](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-ddl-ddl-view.html), [Creating and Managing Materialized Views](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-ddl-ddl-mat-view.html).

---

## 7.4.1. Обычные представления (VIEW)

**CREATE VIEW** задаёт представление как **сохранённый запрос**. При обращении к представлению (SELECT из него) выполняется этот запрос; данные **не хранятся** отдельно — каждый раз читаются базовые таблицы. Синтаксис совпадает с PostgreSQL. См. [Глоссарий](glossary.md).

Пример:

```sql
CREATE VIEW mart.sales_by_region AS
SELECT region_id, sale_date, SUM(amount) AS total_amount, COUNT(*) AS cnt
FROM fact_sales f
JOIN dim_region r ON f.region_id = r.id
GROUP BY region_id, sale_date;
```

Использование: `SELECT * FROM mart.sales_by_region WHERE sale_date >= '2024-01-01';` — планировщик подставляет определение представления и строит план по базовым таблицам. В представлении **не сохраняют** ORDER BY/SORT — при выборке из представления порядок строк не гарантирован; сортировку задают в запросе. **DROP VIEW имя CASCADE** удаляет представление и все зависимые от него объекты (другие представления и т.д.). См. документацию Greenplum.

---

## 7.4.2. Материализованные представления (MATERIALIZED VIEW)

**CREATE MATERIALIZED VIEW** создаёт объект, который **хранит результат запроса** в виде таблицы. Данные читаются из этой «таблицы», а не пересчитываются при каждом SELECT, поэтому доступ к сложным агрегатам или соединениям может быть существенно быстрее. Данные в материализованном представлении **не обновляются** автоматически при изменении базовых таблиц — их нужно обновлять командой **REFRESH MATERIALIZED VIEW**. См. [Глоссарий](glossary.md).

Пример:

```sql
CREATE MATERIALIZED VIEW mart.sales_summary AS
SELECT seller_no, invoice_date, SUM(invoice_amt)::numeric(13,2) AS sales_amt
FROM invoice
WHERE invoice_date < CURRENT_DATE
GROUP BY seller_no, invoice_date
ORDER BY seller_no, invoice_date;
```

В Greenplum материализованное представление, как и таблица, **распределено по сегментам**; при создании можно задать **DISTRIBUTED BY (столбец)** или **DISTRIBUTED RANDOMLY**, иначе будет использовано распределение по умолчанию. На материализованное представление можно создавать индексы. ORDER BY в определении при создании влияет только на порядок строк при первоначальном заполнении; при последующих REFRESH и при SELECT порядок не гарантируется, если не указать ORDER BY в запросе. См. документацию Greenplum.

---

## 7.4.3. REFRESH MATERIALIZED VIEW

**REFRESH MATERIALIZED VIEW имя** перезаполняет материализованное представление: выполняется запрос из определения, результат подменяет хранимые данные. Обычно REFRESH выполняют по расписанию (cron, планировщик заданий) после загрузки данных в базовые таблицы. См. документацию Greenplum.

```sql
REFRESH MATERIALIZED VIEW mart.sales_summary;
```

**REFRESH MATERIALIZED VIEW имя WITH NO DATA** удаляет данные из материализованного представления и переводит его в состояние «не сканируемое»: SELECT будет возвращать ошибку до следующего REFRESH без WITH NO DATA. Используется, когда нужно освободить место или отложить пересчёт.

По умолчанию REFRESH выполняет **блокировку** материализованного представления (обычно EXCLUSIVE или аналог); параллельные SELECT могут блокироваться или ждать. В PostgreSQL 9.4+ есть вариант **REFRESH MATERIALIZED VIEW CONCURRENTLY** (требует UNIQUE INDEX), позволяющий читать старые данные во время обновления; поддержку в вашей версии Greenplum уточняйте в документации.

Право на REFRESH по умолчанию имеет владелец материализованного представления и суперпользователь; для выдачи возможности обновления другим ролям можно создать функцию с **SECURITY DEFINER**, вызывающую REFRESH. См. документацию Greenplum.

---

## 7.4.4. Автообновление (mv_maintain_mode)

В Greenplum материализованное представление может быть настроено на **автоматическое обновление** при изменении базовых таблиц: при создании задаётся опция **mv_maintain_mode** со значениями **incremental**, **full** или **none** (по умолчанию). При **incremental** или **full** любое изменение базовых отношений запускает процесс поддержки представления (инкрементальный или полный пересчёт). Для этого требуется расширение **gp_toolkit** версии 1.21 или выше. См. документацию Greenplum.

Для **incremental** действуют ограничения: в определении запроса не допускаются внешние и реплицированные таблицы, каталоги, CTE, другие представления и материализованные представления, DISTINCT, агрегаты, подзапросы. Полный список и условия см. в разделе «Creating and Managing Materialized Views» документации Greenplum. При необходимости надёжного и предсказуемого обновления по расписанию часто используют ручной **REFRESH MATERIALIZED VIEW** по cron.

## 7.4.5. Использование в DWH

**Обычные представления** удобны для:

- **Унификации доступа:** скрытие сложных JOIN и фильтров за простым именем (например, витрина по регионам и датам).
- **Слоёв витрин:** представление поверх фактов и измерений без физического хранения; данные всегда актуальны на момент запроса, но каждый запрос пересчитывается.
- **Прав доступа:** выдача доступа к представлению вместо базовых таблиц с ограничением строк (WHERE по роли/подразделению).

**Материализованные представления** уместны для:

- **Предрасчитанных агрегатов:** сводки по дням/месяцам, по регионам, по продуктам; REFRESH после ночной загрузки фактов.
- **Витрин с редким обновлением:** снимок агрегатов на конец дня/недели; отчётность читает материализованное представление, обновление — по расписанию.
- **Ускорения тяжёлых запросов:** если один и тот же сложный запрос выполняется часто, его результат можно хранить в материализованном представлении и обновлять по расписанию. См. [Глоссарий](glossary.md) (Витрина данных).

Выбор между VIEW и MATERIALIZED VIEW: VIEW — всегда актуальные данные, но стоимость при каждом запросе; MATERIALIZED VIEW — быстрый доступ к снимку, но данные устаревают до следующего REFRESH. Для отчётности «на конец дня» часто достаточно материализованного представления с ночным REFRESH.

## 7.4.6. Типичные ошибки

- **Ожидать, что данные материализованного представления обновляются сами:** без mv_maintain_mode или без периодического REFRESH данные устаревают.
- **Делать REFRESH в часы пик без учёта блокировок:** длительный REFRESH может блокировать или замедлять запросы к материализованному представлению; планируйте обновление в окно минимальной нагрузки или используйте CONCURRENTLY, если поддерживается.
- **Путать VIEW и MATERIALIZED VIEW:** VIEW не хранит данные и не даёт выигрыша по скорости скана; для ускорения повторяющихся тяжёлых запросов нужна материализация.

---

## Ключевое

- **VIEW** — сохранённый запрос; при SELECT выполняется запрос по базовым таблицам; данные не хранятся; **DROP VIEW ... CASCADE** удаляет зависимые объекты.
- **MATERIALIZED VIEW** — результат запроса хранится как таблица; обновление — **REFRESH MATERIALIZED VIEW**; в Greenplum можно задать распределение (DISTRIBUTED BY) и опцию **mv_maintain_mode** для автообновления.
- В DWH: VIEW — унификация доступа и витрины «на лету»; MATERIALIZED VIEW — предрасчитанные агрегаты и витрины с обновлением по расписанию.

В [§8.1](chapter-08-01.md) мы перейдём к **оптимизации запросов**: чтение плана (EXPLAIN, EXPLAIN ANALYZE), Seq Scan, Index Scan и операции motion (Gather, Redistribute, Broadcast).
