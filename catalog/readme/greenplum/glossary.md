# Глоссарий

Термины Greenplum, используемые в книге.

---

## A

**ANALYZE** — команда SQL в Greenplum и PostgreSQL: собирает статистику по таблице (число строк и страниц, распределение значений по столбцам) и сохраняет в pg_statistic и pg_class; планировщик использует её для оценки cost и rows. Запускают после загрузки и крупных изменений; для партиционированных таблиц при GPORCA — ANALYZE ROOTPARTITION. См. [§8.2](chapter-08-02.md).

**analyzedb** — утилита командной строки Greenplum: выполняет сбор статистики (ANALYZE) по таблицам БД вне сессии с БД; поддерживает список таблиц, параллельные сессии и пропуск неизменённых объектов; удобна для расписания. См. [§8.2](chapter-08-02.md).

**Apache MADlib** — библиотека аналитики и машинного обучения внутри СУБД; вызывается через SQL, вычисления выполняются в кластере (в Greenplum — с использованием MPP). Регрессия, классификация, кластеризация, описательная статистика. См. [§1.2](chapter-01-02.md), гл. 10.

**Append-optimized (AO)** — в Greenplum: модель хранения таблицы без per-row информации видимости; оптимизирована под массовую вставку и чтение; поддерживает сжатие (ZLIB, ZSTD для AO row; для AO columnar также RLE). UPDATE/DELETE с ограничениями. AO row — построчное, AO columnar — колоночное хранение. См. [§5.2](chapter-05-02.md), [§5.3](chapter-05-03.md).

**Avro** — бинарный формат хранения данных с явной схемой (JSON); поддерживает вложенные структуры; часто используется для обмена и стриминга (Kafka). В PXF профили *:avro; predicate pushdown для Avro не поддерживается. См. [§9.3](chapter-09-03.md).

## C

**Column-oriented** (колоночное хранение) — способ хранения, при котором значения каждого столбца хранятся отдельно; выгоден для аналитических запросов с доступом к немногим столбцам и для сжатия. В Greenplum доступен только для append-optimized таблиц (orientation=column). См. [§5.3](chapter-05-03.md).

**Column projection** (проекция столбцов) — в PXF: возврат из внешнего источника только столбцов, указанных в SELECT; для колоночных форматов (Parquet, ORC) снижает объём передаваемых данных. Включена по умолчанию; поддержка зависит от коннектора и профиля. См. [§9.3](chapter-09-03.md).

**Computational skew** (перекос при выполнении, processing skew) — в MPP: неравномерная загрузка сегментов во время выполнения запроса (Hash Join, Hash Aggregate, Sort); один или несколько сегментов обрабатывают заметно больше строк. Причина — низкая кардинальность или неравномерное распределение ключей JOIN/GROUP BY. В EXPLAIN ANALYZE виден по разнице max rows и avg rows по сегментам. См. [§8.3](chapter-08-03.md).

**Content id** — в Greenplum: идентификатор «слота» данных; каждому content id соответствует пара сегментов (primary и mirror), хранящих одну и ту же часть данных. См. [§2.2](chapter-02-02.md).

---

## D

**Data skew** (перекос данных) — в MPP: неравномерное распределение строк по сегментам; один или несколько сегментов хранят заметно больше данных, что создаёт узкое место. Возникает при неудачном ключе распределения (низкая кардинальность). Проверка: gp_segment_id, gp_toolkit.gp_skew_*. См. [§6.1](chapter-06-01.md).

**default_statistics_target** — параметр сервера Greenplum/PostgreSQL: задаёт размер гистограммы и списка наиболее частых значений по столбцу при сборе статистики (ANALYZE); большее значение — точнее оценки, дольше ANALYZE. Для столбца переопределяется через ALTER TABLE ... SET STATISTICS. См. [§8.2](chapter-08-02.md).

**DISTRIBUTED BY** — в Greenplum: ключ распределения таблицы по сегментам (столбец или список столбцов); строки с одинаковым значением ключа хранятся на одном сегменте. См. [§1.3](chapter-01-03.md), [§6.1](chapter-06-01.md).

**DISTRIBUTED RANDOMLY** — в Greenplum: политика распределения без ключа; строки размещаются по сегментам round-robin или случайно. Локальные JOIN невозможны. Используют при отсутствии подходящего столбца для hash или для небольших таблиц. См. [§6.2](chapter-06-02.md).

**DISTRIBUTED REPLICATED** — в Greenplum: политика распределения, при которой полная копия таблицы хранится на каждом сегменте; подходит только для маленьких справочников. См. [§6.2](chapter-06-02.md).

**DWH** (Data Warehouse, хранилище данных) — централизованное хранилище данных, предназначенное для аналитики и отчётности; данные загружаются из операционных систем (ETL/ELT) и организованы для запросов по витринам и измерениям. См. [§1.1](chapter-01-01.md), [§1.4](chapter-01-04.md).

## F

**Failover** (переключение при отказе) — активация резервного узла (например, Standby Master) при сбое основного; в Greenplum — gpactivatestandby на хосте Standby. См. [§2.1](chapter-02-01.md).

---

## G

**gp_autostats_mode** — параметр Greenplum: режим автоматического сбора статистики (ANALYZE) при INSERT/COPY/CREATE TABLE AS SELECT. Значения: on_no_stats (ANALYZE при отсутствии статистики), on_change (по порогу gp_autostats_on_change_threshold), none. См. [§8.2](chapter-08-02.md).

**gp_segments_for_planner** — параметр Greenplum (GUC): число сегментов, подставляемое в оценку стоимости motion при планировании (0 — использовать фактическое число primary-сегментов). Увеличение значения повышает оценку стоимости broadcast и склоняет оптимизатор к Redistribute; уменьшение — к Broadcast. См. [§8.3](chapter-08-03.md).

**gp_vmem_protect_limit** — параметр Greenplum: максимальный объём памяти, который могут использовать все процессы одного сегмента в сумме; при превышении — ошибки out of memory или принудительное завершение запросов (runaway_detector_activation_percent). См. [§8.4](chapter-08-04.md).

**gpAdminLogs** — каталог логов утилит администратора Greenplum (по умолчанию $GPADMIN_HOME/gpAdminLogs): gpstart, gpstop, gprecoverseg, gpsegstart и др.; один каталог на сервер, имена файлов содержат дату и при необходимости имя хоста. См. [§4.3](chapter-04-03.md), [§4.4](chapter-04-04.md).

**gpcheck** — утилита Greenplum для проверки окружения (ОС, ядро, сеть, пакеты); в ряде версий помечена как устаревшая (deprecated). См. [§4.3](chapter-04-03.md).

**gpconfig** — утилита Greenplum для просмотра и изменения параметров postgresql.conf на всех инстансах: -s (показать), -c -v (установить), -m (значение для координатора), -r (удалить). После изменения — gpstop -u или gpstop -r. См. [§4.3](chapter-04-03.md).

**gpfdist** — демон Greenplum (Parallel File Server): раздаёт файлы с хоста по HTTP сегментам для параллельной загрузки или выгрузки; в LOCATION внешней таблицы указывают gpfdist://хост:порт/путь. Используется gpload и напрямую при создании внешних таблиц. См. [§7.3](chapter-07-03.md), [§9.4](chapter-09-04.md).

**gpinitsystem** — утилита однократной инициализации кластера Greenplum: создаёт каталоги данных координатора и сегментов, инициализирует экземпляры PostgreSQL на всех узлах, настраивает топологию и запускает кластер. Запускается с Master под gpadmin с конфигом (-c) и hostfile (-h). См. [§3.3](chapter-03-03.md).

**gplogfilter** — утилита Greenplum для поиска по лог-файлам СУБД: фильтрация по уровню (-t для ERROR/FATAL/PANIC), по времени (-b, -e, -d), по строке (-f) или regex (-m); без указания файла используется лог координатора из $COORDINATOR_DATA_DIRECTORY/log/. См. [§4.4](chapter-04-04.md).

**gpload** — утилита Greenplum для параллельной загрузки данных: по YAML-конфигу запускает gpfdist, создаёт внешнюю таблицу и выполняет INSERT/UPDATE/MERGE в целевую таблицу; поддерживает форматы TEXT и CSV, обработку ошибок (ERROR_LIMIT, LOG_ERRORS). См. [§7.3](chapter-07-03.md).

**gprecoverseg** — утилита Greenplum для восстановления упавших сегментов при включённом mirroring: инкрементальное (по умолчанию) или полное (-F) восстановление; -i — по файлу конфигурации, -p — на новый хост; -r — балансировка (возврат в предпочтительные роли). См. [§4.2](chapter-04-02.md).

**gpstart** — утилита Greenplum для запуска кластера (Master и все сегменты); выполняется на хосте Master под gpadmin при заданных GPHOME и MASTER_DATA_DIRECTORY. См. [§3.4](chapter-03-04.md), [§4.1](chapter-04-01.md).

**gpstate** — утилита Greenplum для просмотра состояния кластера: -b (кратко), -s (подробно), -Q (быстро по каталогу), -e (проблемы с mirror), -m (mirror'ы), -c (primary–mirror маппинг), -f (Standby Master). См. [§4.3](chapter-04-03.md).

**gp_stats_missing** — представление в gp_toolkit: перечисляет таблицы (и при необходимости партиции), по которым не собрана статистика; помогает выявить объекты для выполнения ANALYZE. См. [§8.2](chapter-08-02.md).

**gpstop** — утилита Greenplum для остановки кластера (Master и все сегменты); режимы -M smart (по умолчанию), fast, immediate; -r — перезапуск, -u — перезагрузка конфигурации без остановки. См. [§4.1](chapter-04-01.md).

**gpadmin** — служебный пользователь ОС на всех узлах кластера Greenplum; под ним запускаются процессы Greenplum; должен иметь одинаковый UID/GID на всех хостах; для управления кластером требуется SSH без пароля от gpadmin между узлами. См. [§3.1](chapter-03-01.md).

**GPHOME** — переменная окружения Greenplum: путь к каталогу установки (например, /usr/local/greenplum-db); задаётся скриптом greenplum_path.sh. См. [§3.2](chapter-03-02.md).

**Greenplum** — MPP-СУБД на базе PostgreSQL (форк Postgres, доработанный под MPP). Данные распределены по сегментам (Segment), запросы координирует Master, обмен данными между узлами — Interconnect. Ориентирована на DWH и аналитику. См. [§1.2](chapter-01-02.md), [§1.3](chapter-01-03.md).

## H

**Heap** (heap-таблица) — в Greenplum и PostgreSQL: таблица с хранением в виде «кучи» (heap), модель по умолчанию; row-oriented; хранит информацию о версиях строк (MVCC); полная поддержка UPDATE/DELETE. Подходит для OLTP-подобных нагрузок и небольших таблиц (измерения). См. [§5.1](chapter-05-01.md).

**Hostfile** — файл со списком имён хостов кластера Greenplum (Master, Standby, сегменты); используется при инициализации (gpinitsystem) и утилитами gpssh, gpscp. См. [§3.1](chapter-03-01.md), [§3.3](chapter-03-03.md).

---

## I

**Interconnect** — сетевой слой в Greenplum, связывающий Master и сегменты; используется для передачи данных между сегментами при выполнении запросов (motion). См. [§1.2](chapter-01-02.md), [§2.3](chapter-02-03.md).

---

## L

**Local join** (локальный JOIN, co-located join) — в Greenplum: соединение двух таблиц, распределённых по одному и тому же столбцу(ам) с совпадающими типами, при условии что все столбцы распределения участвуют в условии JOIN; выполняется на каждом сегменте без пересылки данных (motion). См. [§6.1](chapter-06-01.md).

---

## M

**MASTER_DATA_DIRECTORY** — переменная окружения Greenplum: путь к каталогу данных Master (например, /data/master/gpseg-1); задаётся после gpinitsystem в профиле gpadmin на Master; используется gpstart, gpstop, psql и др. См. [§3.3](chapter-03-03.md), [§3.4](chapter-03-04.md).

**Master** — координационный узел кластера Greenplum: точка входа для клиентов, планировщик запросов, системный каталог; запросы рассылаются на сегменты с Master. См. [§1.2](chapter-01-02.md), [§2.1](chapter-02-01.md).

**Mean imputation** (подстановка среднего) — способ обработки пропусков: NULL заменяются средним по столбцу. В MADlib используется в функциях correlation и covariance; при необходимости другой обработки пропусков рекомендуется предварительный view. См. [§10.3](chapter-10-03.md).

**Mirror segment** (зеркальный сегмент) — в Greenplum: резервная копия primary segment для того же content id; реплицирует данные по WAL; при сбое primary может быть переведён в роль primary. Должен находиться на другом хосте, чем primary. См. [§2.2](chapter-02-02.md).

**Motion** — в плане запроса Greenplum: операция пересылки данных между сегментами (Gather, Redistribute, Broadcast). См. [§1.3](chapter-01-03.md), [§2.4](chapter-02-04.md), [§8.1](chapter-08-01.md).

**MPP** (Massively Parallel Processing, массово-параллельная обработка) — архитектура, в которой множество независимых узлов (с собственной памятью и дисками, shared-nothing) работают параллельно над общей задачей; в MPP-СУБД данные распределены по узлам, запрос разбивается на подзадачи и выполняется на многих узлах. См. [§1.1](chapter-01-01.md).

---

## O

**OLTP** (On-Line Transaction Processing, обработка транзакций в реальном времени) — режим работы СУБД с множеством коротких транзакций (вставка, обновление, выборка по ключу), характерный для операционных систем; противопоставляется аналитической нагрузке (DWH, тяжёлые запросы). См. [§1.1](chapter-01-01.md).

**ORC** (Optimized Row Columnar) — колоночный формат из экосистемы Hadoop/Hive; данные разбиты на stripes с индексами и статистикой; в PXF поддерживаются профили *:orc, hive:orc; column projection и predicate pushdown. См. [§9.3](chapter-09-03.md).

---

## P

**PARTITION BY** — в Greenplum: объявление логического партиционирования таблицы по ключу (RANGE, LIST или HASH); каждая партиция хранит подмножество строк по границам. Не заменяет распределение по сегментам (DISTRIBUTED BY). См. [§6.3](chapter-06-03.md), [§6.4](chapter-06-04.md).

**Parquet** — колоночный бинарный формат хранения; данные по столбцам, встроенная схема, row groups и страницы; сжатие (snappy, gzip). В PXF профили *:parquet; поддерживаются column projection и predicate pushdown. См. [§9.3](chapter-09-03.md).

**Partition pruning** (отсечение партиций) — использование оптимизатором границ партиций для исключения из плана партиций, не содержащих подходящих строк; требует прямого ограничения по ключу партиции в запросе, не работает при значениях из подзапроса. См. [§6.3](chapter-06-03.md).

**pg_statistic** — системный каталог PostgreSQL/Greenplum: хранит статистику по столбцам (гистограмма, наиболее частые значения, доля NULL и др.), собираемую командой ANALYZE; пользовательское представление pg_stats даёт удобный доступ к этим данным. См. [§8.2](chapter-08-02.md).

**Predicate pushdown** (filter pushdown, перенос предиката) — в PXF: передача условий WHERE во внешний источник для фильтрации до передачи данных в Greenplum; снижает объём данных по сети. Включается параметром gp_external_enable_filter_pushdown; поддерживается для профилей *:parquet, *:orc, hive и др., не поддерживается для *:text, *:avro и др. См. [§9.3](chapter-09-03.md).

**Primary segment** (основной сегмент) — в Greenplum: сегмент, который обрабатывает запросы и принимает запись для данного content id; реплицирует изменения на mirror segment. См. [§2.2](chapter-02-02.md).

**PXF** (Platform Extension Framework) — фреймворк в Greenplum для доступа к внешним данным без загрузки в кластер; коннекторы к HDFS, S3, Azure Blob, Kafka и др.; внешние таблицы (CREATE EXTERNAL TABLE). См. [§1.4](chapter-01-04.md), гл. 9.

---

## Q

**QD** (Query Dispatcher) — процесс на Master в Greenplum, координирующий выполнение одного запроса: рассылает план сегментам, собирает результаты. См. [§2.4](chapter-02-04.md).

**QE** (Query Executor) — процесс на сегменте в Greenplum, выполняющий фрагмент (slice) плана запроса над локальными данными. См. [§2.4](chapter-02-04.md).

---

## R

**Resource queue** (очередь ресурсов) — в Greenplum: механизм управления нагрузкой; лимитирует число одновременно выполняемых запросов (ACTIVE_STATEMENTS) и суммарную память (MEMORY_LIMIT) для ролей, привязанных к очереди. Запросы сверх лимита ожидают в очереди. Просмотр — gp_toolkit.gp_resqueue_status. См. [§8.4](chapter-08-04.md).

**ROOTPARTITION** — в Greenplum: вариант команды ANALYZE (ANALYZE ROOTPARTITION имя_таблицы или ROOTPARTITION ALL) для обновления только статистики корневой партиции партиционированной таблицы; используется оптимизатором GPORCA для оценки по всей таблице. См. [§6.3](chapter-06-03.md), [§8.2](chapter-08-02.md).

**Row-oriented** (построчное хранение, хранение по строкам) — способ хранения, при котором все столбцы одной строки располагаются рядом; эффективен при доступе к целой строке или многим столбцам. В Greenplum heap-таблицы всегда row-oriented; AO-таблицы могут быть row или column. См. [§5.1](chapter-05-01.md), [§5.2](chapter-05-02.md).

---

## S

**Scale out** (масштабирование по горизонтали) — увеличение производительности и объёма системы за счёт добавления узлов в кластер; характерно для MPP. См. [§1.1](chapter-01-01.md).

**Scale up** (масштабирование по вертикали) — увеличение производительности за счёт усиления одного сервера (больше CPU, памяти, дисков); характерно для SMP. См. [§1.1](chapter-01-01.md).

**Segment** (сегмент) — рабочий узел кластера Greenplum; экземпляр PostgreSQL, хранящий и обрабатывающий свою часть данных; на каждом сегменте выполняется часть распределённого плана запроса. См. [§1.2](chapter-01-02.md), [§2.2](chapter-02-02.md).

**Shared memory** (общая память) — архитектура, при которой несколько процессоров используют общую память и общие ресурсы (SMP). См. [§1.1](chapter-01-01.md).

**Shared-nothing** («ничего общего») — архитектура, при которой каждый узел кластера имеет собственные процессор(ы), память и диски; узлы не разделяют память и хранилище, обмениваются только по сети. Основа MPP. См. [§1.1](chapter-01-01.md).

**SMP** (Symmetric Multiprocessing, симметричная многопроцессорность) — архитектура с несколькими процессорами в рамках одной машины (одной ОС), с общей памятью и общим доступом к данным; масштабирование по вертикали. См. [§1.1](chapter-01-01.md).

**Standby Master** — резервный узел Master в Greenplum; синхронизируется с основным Master через репликацию WAL; при отказе основного Master активируется утилитой gpactivatestandby и становится новым активным Master. См. [§2.1](chapter-02-01.md).

**statement_mem** — параметр Greenplum: максимальная память на весь запрос (statement) на каждый сегмент; при нехватке — spill. Ограничивается max_statement_mem и лимитом очереди ресурсов. Рекомендуемая формула: (gp_vmem_protect_limit×0,9)/max_concurrent_queries. См. [§8.4](chapter-08-04.md).

**summary** (MADlib) — функция madlib.summary: вычисляет описательную статистику по столбцам таблицы (mean, variance, min, max, квартили, медиана, distinct, пропуски, наиболее частые значения) и записывает результат в указанную таблицу; поддерживает группировку и опции точного/приближённого подсчёта. См. [§10.3](chapter-10-03.md).

---

## V

**VACUUM** — команда SQL в Greenplum/PostgreSQL: помечает место мёртвых строк (после DELETE/UPDATE) как доступное для повторного использования; VACUUM FULL перезаписывает таблицу и возвращает место ОС. Перед ANALYZE раздутой таблицы рекомендуется VACUUM. Autovacuum выполняет очистку по расписанию. См. [§8.2](chapter-08-02.md).

---

## W

**work_mem** — параметр Greenplum/PostgreSQL: объём памяти на одну операцию (Sort, Hash Join, Hash Aggregate) внутри запроса на сегменте; при нехватке — сброс на диск (spill, workfile). В EXPLAIN ANALYZE отображаются Work_mem used и Work_mem wanted. См. [§8.4](chapter-08-04.md).

---

## В

**Внешняя таблица** (external table) — в Greenplum: таблица, данные которой хранятся вне кластера (HDFS, S3 и др.); доступ через PXF, чтение «на лету» при запросе. См. [§1.4](chapter-01-04.md), [§9.4](chapter-09-04.md).

**Витрина данных** (data mart) — тематический слой данных для отчётности и аналитики (продажи, финансы и т.д.), построенный поверх DWH; обновляется пакетно или по расписанию. См. [§1.4](chapter-01-04.md).

---

## Д

**Двухфазная фиксация (2PC)** — в распределённой СУБД: протокол коммита транзакции (фаза prepare на всех узлах, затем commit), обеспечивающий атомарность при записи на нескольких сегментах. См. [§1.3](chapter-01-03.md).

---

## К

**Ковариация** — мера совместной изменчивости двух случайных величин; в MADlib функция madlib.covariance строит матрицу попарных ковариаций по числовым столбцам таблицы. См. [§10.3](chapter-10-03.md).

**Корреляция Пирсона** (Pearson correlation) — мера линейной связи двух переменных; значение от -1 до 1 (1 — полная положительная, -1 — полная отрицательная, 0 — отсутствие линейной связи). В MADlib madlib.correlation строит матрицу попарных коэффициентов Пирсона по числовым столбцам. См. [§10.3](chapter-10-03.md).

---

## П

**Профиль PXF** (PXF profile) — именованное соответствие формату данных (Parquet, ORC, Avro, текст, JSON и т.д.) для коннектора PXF; задаётся в LOCATION внешней таблицы как PROFILE=имя. См. [§9.1](chapter-09-01.md), [§9.3](chapter-09-03.md).

---

## С

**Сервер PXF** (PXF server) — в PXF: именованная конфигурация доступа к внешнему источнику (адрес, учётные данные, параметры коннектора). Указывается в LOCATION внешней таблицы как SERVER=имя; default — сервер по умолчанию. См. [§9.1](chapter-09-01.md), [§9.2](chapter-09-02.md).
