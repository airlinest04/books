# §6.2 Равномерное распределение (DISTRIBUTED RANDOMLY)

В [§6.1](chapter-06-01.md) мы разобрали hash-распределение по ключу (**DISTRIBUTED BY**). Альтернатива — **DISTRIBUTED RANDOMLY**: строки распределяются по сегментам **без привязки к значению столбца** (round-robin или случайное размещение). В этом разделе — когда использовать RANDOMLY, ограничения (нет локальных JOIN, возможный перекос), изменение распределения и перераспределение данных; кратко — **DISTRIBUTED REPLICATED**. Партиционирование — в [§6.3](chapter-06-03.md). По [Greenplum — Table Distribution Policy](https://www.greenplumdba.com/greenplum-dba-faq/what-are-the-table-distribution-policy-in-greenplum), [Distribution and Skew](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-distribution.html).

---

## 6.2.1. Что такое DISTRIBUTED RANDOMLY

При **DISTRIBUTED RANDOMLY** каждая строка при вставке отправляется на один из сегментов по **round-robin** или по случайному правилу, без учёта значения какого-либо столбца. В результате строки с одинаковыми значениями могут оказаться на разных сегментах. Цель — добиться **равномерного** размазывания данных по сегментам, когда нет подходящего столбца для hash-распределения или когда перекос при hash неприемлем.

Синтаксис:

```sql
CREATE TABLE events_log (
    id         bigserial,
    event_time timestamptz,
    payload    jsonb
) DISTRIBUTED RANDOMLY;
```

Таблица не привязана к ключу JOIN; при любом соединении с другой таблицей оптимизатор вынужден использовать **redistribute** или **broadcast** — локального JOIN не будет. См. [§6.1](chapter-06-01.md), [Глоссарий](glossary.md) (Local join).

---

## 6.2.2. Когда использовать RANDOMLY

**DISTRIBUTED RANDOMLY** имеет смысл в следующих случаях:

- **Нет подходящего ключа для hash:** все столбцы имеют низкую кардинальность или не участвуют в типичных JOIN; выбор любого из них даёт сильный перекос. Случайное распределение может дать более ровное размещение, чем hash по плохому ключу.
- **Небольшие таблицы:** для маленьких таблиц пересылка (broadcast) при JOIN обычно не критична; оптимизатор часто выбирает broadcast. RANDOMLY допустим для справочников и промежуточных таблиц, которые редко соединяют с большими фактами по общему ключу.
- **Типы данных, не подходящие для hash:** если в таблице нет столбцов с типами, по которым Greenplum умеет считать хеш для распределения (например, только геометрические или пользовательские типы), по умолчанию может использоваться распределение, по сути близкое к случайному; явно задают **DISTRIBUTED RANDOMLY** при создании таблицы.
- **Временные таблицы для двухфазной агрегации:** при обработке перекоса (processing skew) иногда создают временную таблицу с **DISTRIBUTED RANDOMLY**, чтобы принудить двухфазную агрегацию и выровнять нагрузку по сегментам. См. документацию Greenplum по processing skew.

Для **больших таблиц**, которые часто соединяют с другими большими таблицами, предпочтительно **DISTRIBUTED BY** по столбцу(ам) JOIN — иначе каждая такая операция будет требовать redistribute или broadcast и терять в производительности.

---

## 6.2.3. Ограничения и перекос

- **Локальные JOIN невозможны:** при любом JOIN с другой таблицей нужна пересылка данных; для больших таблиц это дорого.
- **Равномерность не гарантирована:** при одиночных INSERT или малых batch’ах распределение может оказаться неравномерным; при массовой загрузке round-robin обычно даёт приемлемую равномерность. После загрузки стоит проверить перекос (gp_segment_id, gp_toolkit) так же, как для hash-распределения. См. [§6.1](chapter-06-01.md) (Data skew).
- **ALTER TABLE SET DISTRIBUTED RANDOMLY** не перераспределяет данные автоматически: политика меняется, но существующие строки остаются на тех же сегментах. Чтобы **перераспределить** данные по новой политике (в том числе по RANDOMLY), используют **ALTER TABLE ... SET WITH (REORGANIZE=TRUE)** (или эквивалент в вашей версии). См. документацию по ALTER TABLE.

---

## 6.2.4. Сравнение с распределением по столбцам

| Критерий | DISTRIBUTED BY (столбец) | DISTRIBUTED RANDOMLY |
|----------|--------------------------|----------------------|
| Ключ | Значение столбца(ов) | Нет |
| Локальный JOIN | Возможен при совпадении ключа на обеих таблицах | Нет |
| Равномерность | Зависит от кардинальности ключа | Обычно хорошая при массовой загрузке |
| Когда использовать | Есть столбец с высокой кардинальностью и типичные JOIN по нему | Нет подходящего ключа; небольшие таблицы; специальные случаи |

«Распределение по столбцам» здесь — это **DISTRIBUTED BY (столбец [, ...])**: решение, на каком сегменте окажется строка, определяется значением указанных столбцов. **RANDOMLY** — решение без привязки к содержимому строки. См. [§6.1](chapter-06-01.md).

---

## 6.2.5. DISTRIBUTED REPLICATED (кратко)

Политика **DISTRIBUTED REPLICATED** — каждый сегмент хранит **полную копию** таблицы. Подходит для **маленьких** справочников (измерений), которые часто участвуют в JOIN: пересылки при соединении не нужны — на каждом сегменте есть своя копия. Не подходит для больших таблиц: объём данных умножается на число сегментов. Запросы с **gp_segment_id** по реплицированной таблице в Greenplum не допускаются. Детали и ограничения см. в документации Greenplum по созданию таблиц и распределению.

---

## 6.2.6. Типичные ошибки

- **Использовать RANDOMLY для больших фактов, которые часто JOIN’ят:** каждый JOIN приведёт к redistribute или broadcast; лучше подобрать DISTRIBUTED BY под основные соединения.
- **Считать, что ALTER TABLE SET DISTRIBUTED RANDOMLY переразложит данные:** без REORGANIZE данные останутся на старых сегментах; для перераспределения нужна явная реорганизация.
- **Путать RANDOMLY и REPLICATED:** RANDOMLY — одна копия строки на одном сегменте; REPLICATED — копия на каждом сегменте; цели и стоимость хранения разные.

---

## Ключевое

- **DISTRIBUTED RANDOMLY** — распределение без ключа (round-robin/случайное); подходит при отсутствии подходящего столбца для hash или для небольших таблиц; локальные JOIN невозможны.
- После смены политики на RANDOMLY данные не перераспределяются автоматически; для переразложения используйте **REORGANIZE** (ALTER TABLE ... SET WITH (REORGANIZE=TRUE) или аналог).
- **DISTRIBUTED REPLICATED** — полная копия таблицы на каждом сегменте; только для маленьких справочников.

В [§6.3](chapter-06-03.md) мы разберём **партиционирование (PARTITION BY)**: разбиение больших таблиц, partition pruning и типы партиций (RANGE, LIST).
