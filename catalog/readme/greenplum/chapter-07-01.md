# §7.1 Совместимость с PostgreSQL

В [§6.4](chapter-06-04.md) мы закончили разбор партиционирования. Глава 7 посвящена **SQL в Greenplum**: что работает как в PostgreSQL, какие есть ограничения и расширения. В этом разделе — **совместимость запросов и DDL** с PostgreSQL: SELECT, JOIN, CTE, оконные функции и агрегаты работают привычно; отличия связаны с распределением таблиц и выполнением плана на многих узлах. Общая картина связи Greenplum и PostgreSQL — в [§1.3](chapter-01-03.md); особенности диалекта и системные представления — в [§7.2](chapter-07-02.md). По [greenplum.org — Relationship to PostgreSQL](https://greenplum.org/relationship-and-difference-between-greenplum-and-postgresql/), [Tanzu Greenplum — SQL Compliance](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/ref_guide-misc.html).

## 7.1.1. Что работает как в PostgreSQL

Greenplum — форк PostgreSQL; синтаксис SQL и семантика запросов в большинстве случаев **совпадают** с той веткой Postgres, на которой основана ваша версия (например, Greenplum 7 — на базе PostgreSQL 12.x). См. [§1.3](chapter-01-03.md).

**SELECT, фильтрация, сортировка:** WHERE, ORDER BY, LIMIT/OFFSET, DISTINCT работают как в PostgreSQL. Сканы выполняются **параллельно** на сегментах; результат собирается на Master.

**JOIN:** INNER, LEFT/RIGHT/FULL OUTER, CROSS, по нескольким условиям — поддерживаются. Планировщик строит распределённый план: если таблицы распределены по одному ключу JOIN, соединение **локальное** на каждом сегменте ([§6.1](chapter-06-01.md)); иначе добавляется Redistribute или Broadcast Motion ([§8.1](chapter-08-01.md)).

**Подзапросы и CTE:** подзапросы в WHERE, IN, EXISTS, FROM; **WITH ... AS (CTE)** — поддерживаются. План может содержать motion для подзапросов и CTE; семантика та же, что в PostgreSQL.

**Оконные функции:** ROW_NUMBER(), RANK(), DENSE_RANK(), SUM() OVER (PARTITION BY ... ORDER BY ...), LAG/LEAD и др. — работают. Вычисление выполняется на сегментах с учётом распределения; при необходимости планировщик добавляет перераспределение или границы окон.

**Агрегаты:** COUNT, SUM, AVG, MIN, MAX, GROUP BY, HAVING — как в PostgreSQL. Агрегация может быть двухфазной: локальная на сегментах, затем финальная на Master (Gather Motion).

**INSERT, UPDATE, DELETE:** синтаксис тот же. INSERT направляет строки в партиции и сегменты по правилам распределения и партиционирования; UPDATE/DELETE на heap-таблицах работают как в Postgres; на AO-таблицах действуют ограничения ([§5.2](chapter-05-02.md)).

**Типы данных:** integer, bigint, numeric, varchar, text, date, timestamp, timestamptz, jsonb, uuid и другие стандартные типы PostgreSQL — поддерживаются. При переносе схемы проверяйте документацию по версии на предмет редких типов и расширений.

**Клиенты и протокол:** подключение по протоколу, совместимому с PostgreSQL (libpq); можно использовать psql, JDBC, ODBC, Python (psycopg2), и т.д. Порт и аутентификация настраиваются аналогично PostgreSQL.

## 7.1.2. Обязательное указание распределения при CREATE TABLE

В PostgreSQL при **CREATE TABLE** распределение по узлам не задаётся — таблица целиком на одном инстансе. В Greenplum **каждая пользовательская таблица должна иметь политику распределения**: при создании таблицы нужно указать **DISTRIBUTED BY (столбец [, ...])** или **DISTRIBUTED RANDOMLY**. Без этого Greenplum может подставить распределение по умолчанию (например, по первому столбцу), что часто приводит к перекосу и неоптимальным JOIN. См. [§6.1](chapter-06-01.md), [§6.2](chapter-06-02.md).

При переносе DDL с PostgreSQL в Greenplum в каждый **CREATE TABLE** добавляют предложение распределения:

```sql
-- В PostgreSQL достаточно:
-- CREATE TABLE t (id int, val text);

-- В Greenplum нужно, например:
CREATE TABLE t (id int, val text) DISTRIBUTED BY (id);
```

Для партиционированных таблиц **PARTITION BY** задаётся вместе с **DISTRIBUTED BY** ([§6.3](chapter-06-03.md), [§6.4](chapter-06-04.md)).

## 7.1.3. Ограничения и отличия

**Ограничения целостности:** первичные и внешние ключи, UNIQUE, CHECK поддерживаются. В распределённой среде проверка уникальности и ссылочной целостности требует координации между сегментами; при массовых вставках это может быть дорого. Некоторые сценарии (например, FK на больших таблицах с частыми вставками) в документации рекомендуют пересматривать или отключать при загрузке. См. руководство по администрированию Greenplum.

**Триггеры:** поддерживаются; при срабатывании на сегментах учитывайте, что триггер выполняется в контексте сегмента. **Триггеры на append-optimized таблицах не поддерживаются** ([§5.2](chapter-05-02.md)).

**Курсоры:** DECLARE CURSOR, FETCH работают. **DECLARE CURSOR ... FOR UPDATE** на AO-таблицах не поддерживается. См. документацию по курсорам.

**Редкие конструкции и расширения:** не все возможности PostgreSQL или сторонние расширения портированы или ведут себя одинаково. Перед использованием конкретной функции, типа или расширения проверяйте документацию Greenplum и тестируйте на кластере. В разных мажорных версиях Greenplum (5, 6, 7) список поддерживаемых возможностей и удалённых объектов отличается — см. Release Notes и «Features and Objects Removed» для вашей версии.

**План выполнения:** один и тот же SQL в Greenplum даёт **распределённый** план (с motion по сегментам), а не план одной инстанции. Для отладки и настройки производительности смотрите **EXPLAIN** и **EXPLAIN ANALYZE** в Greenplum ([§8.1](chapter-08-01.md)).

## 7.1.4. Транзакции и изоляция

Транзакции и уровни изоляции (READ COMMITTED, REPEATABLE READ, SERIALIZABLE) поддерживаются; семантика с точки зрения приложения совпадает с PostgreSQL. Внутри кластера для атомарности используется **двухфазная фиксация (2PC)** между сегментами, что добавляет сетевой обмен. Greenplum ориентирован на аналитическую нагрузку и пакетную загрузку; для высокой частоты коротких OLTP-транзакций обычно используют одну инстанцию PostgreSQL. См. [§1.3](chapter-01-03.md).

## 7.1.5. Краткая сводка для переноса с PostgreSQL

- **Запросы (SELECT, JOIN, CTE, оконные функции, агрегаты):** переносятся с минимальными правками или без них; проверяйте план (EXPLAIN) и при необходимости настройте распределение таблиц под основные JOIN.
- **CREATE TABLE:** добавить **DISTRIBUTED BY** или **DISTRIBUTED RANDOMLY**; при необходимости выбрать тип хранения (heap, AO, AO columnar) и партиционирование.
- **Ограничения и триггеры:** в целом поддерживаются; на AO-таблицах триггеры и FOR UPDATE не поддерживаются; при массовых загрузках учтите стоимость проверок.
- **Расширения и редкие типы:** проверять совместимость по версии Greenplum.

Подробнее о расширениях диалекта (представления gp_*, функции Greenplum) — в [§7.2](chapter-07-02.md).

## Ключевое

- **Совместимость SQL** с PostgreSQL высокая: SELECT, JOIN, CTE, оконные функции, агрегаты, INSERT/UPDATE/DELETE работают привычно; выполнение — распределённое по сегментам.
- **CREATE TABLE в Greenplum** должен содержать **DISTRIBUTED BY** или **DISTRIBUTED RANDOMLY**; иначе возможны перекос и неоптимальные запросы.
- **Ограничения:** триггеры и FOR UPDATE не поддерживаются на AO-таблицах; часть ограничений и расширений ведут себя иначе или недоступны — проверяйте документацию по версии.

В [§7.2](chapter-07-02.md) мы разберём особенности диалекта Greenplum: расширения для MPP, системные представления с префиксом **gp_*** и функции Greenplum.
