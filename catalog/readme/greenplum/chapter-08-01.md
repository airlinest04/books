# §8.1 EXPLAIN и EXPLAIN ANALYZE

В [§7.4](chapter-07-04.md) мы разобрали представления и материализованные представления. Глава 8 посвящена **оптимизации запросов**. Основа диагностики — **план выполнения**: какие операции выполняются, на каких сегментах, сколько данных пересылается. В этом разделе — как получать и **читать план** с помощью **EXPLAIN** и **EXPLAIN ANALYZE**, что означают **Seq Scan**, **Index Scan**, узлы **motion** (Gather, Redistribute, Broadcast) и оценки **cost**. По [Tanzu Greenplum 7 — EXPLAIN](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/ref_guide-sql_commands-EXPLAIN.html).

---

## 8.1.1. EXPLAIN и EXPLAIN ANALYZE

**EXPLAIN** выводит **план запроса**, который планировщик Greenplum строит для указанной команды (SELECT, INSERT, UPDATE, DELETE и др.), **без выполнения** запроса. В плане — дерево узлов: каждый узел описывает одну операцию (скан таблицы, соединение, агрегация, пересылка данных). По [Глоссарий](glossary.md) (Motion).

**EXPLAIN ANALYZE** не только строит план, но и **выполняет** запрос и дополняет вывод **фактическими** показателями: реальное время выполнения, число строк на сегментах, использование work_mem и при необходимости объём сброса на диск (spill). Результат запроса клиенту не возвращается, но побочные эффекты (изменение данных при INSERT/UPDATE/DELETE) происходят. Для безопасной проверки DML используйте транзакцию с откатом: `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`

Синтаксис:

```sql
EXPLAIN [ ( option [, ...] ) ] запрос;
EXPLAIN ANALYZE [ VERBOSE ] запрос;
```

Опции: **ANALYZE** (выполнить и показать фактические данные), **VERBOSE** (доп. сведения по узлам), **COSTS** (вкл/выкл оценку стоимости; по умолчанию true), **BUFFERS** (использование буферов; для распределённых запросов в Greenplum не поддерживается в полном виде), **TIMING** (время по узлам при ANALYZE), **FORMAT** (TEXT | XML | JSON | YAML). См. справочник EXPLAIN в документации Greenplum.

## 8.1.2. Как читать план: снизу вверх, cost, rows

План — это **дерево**: данные движутся от **нижних** узлов к **верхним**. Нижние узлы — обычно **сканы** (чтение таблиц); выше — соединения, агрегации, сортировки; **самые верхние** узлы в Greenplum часто — **motion** (пересылка данных между сегментами или на координатор). Читать план нужно **снизу вверх**: каждый узел передаёт строки узлу над ним. См. [§2.4](chapter-02-04.md).

Для каждого узла выводятся (если включены COSTS):

- **cost** — оценка стоимости в условных единицах (часто интерпретируют как «страницы с диска»): **startup cost** (до первой строки) и **total cost** (до последней). Стоимость родительского узла **включает** стоимость всех дочерних. Общая оценка времени плана — cost верхнего узла.
- **rows** — оценка числа строк на выходе узла (с учётом фильтров).
- **width** — оценка средней ширины строки в байтах.

Планировщик минимизирует total cost верхнего узла. Сравнивая фактические строки и время в **EXPLAIN ANALYZE** с оценками, можно понять, насколько точна статистика и не выбрал ли планировщик неудачный план. См. [§8.2](chapter-08-02.md) про ANALYZE и статистику.

## 8.1.3. Seq Scan и Index Scan

**Seq Scan** (последовательное сканирование) — чтение таблицы «подряд», страница за страницей; каждая строка проверяется на условие WHERE. Используется когда нет подходящего индекса или планировщик считает полный скан дешевле. Для больших таблиц с сильной фильтрацией Seq Scan может быть дорогим; для таблиц, целиком умещающихся в кэш, или при слабой селективности — часто нормальный выбор.

**Index Scan** — доступ к таблице через индекс: по ключу (или диапазону) находятся строки в индексе, затем по TID читаются строки таблицы. Появляется в плане, когда условие запроса можно использовать как индексное (равенство, диапазон по индексированным столбцам). Index Scan даёт случайный доступ к страницам таблицы; при большом проценте строк выгоднее может оказаться Seq Scan. В Greenplum сканы выполняются **на каждом сегменте** над своей частью таблицы; в плане указывается slice и segments. См. документацию Greenplum.

Дополнительно встречаются **Bitmap Index Scan** и **Bitmap Heap Scan** (построение битовой карты по индексу и затем чтение только нужных страниц таблицы). Детали см. в справочнике по планам PostgreSQL/Greenplum.

## 8.1.4. Motion: Gather, Redistribute, Broadcast

Узлы **motion** в плане Greenplum описывают **пересылку данных** между сегментами и координатором. Они обычно находятся в **верхней** части плана (или между слоями выполнения). См. [§2.4](chapter-02-04.md), [Глоссарий](glossary.md) (Motion).

**Gather Motion** (часто записывается как **Gather Motion N:1** или **senders: N, receivers: 1**) — сегменты отправляют свои строки **на координатор**; координатор объединяет потоки и отдаёт результат клиенту. Почти каждый распределённый SELECT заканчивается Gather Motion. Соотношение N:1 — N отправителей (сегментов), 1 получатель (координатор).

**Redistribute Motion** — строки **перераспределяются** между сегментами по хешу указанного ключа (например, ключа JOIN). После перераспределения строки с одинаковым значением ключа оказываются на одном сегменте, и следующий узел (например, Hash Join) может выполнять соединение локально. Стоимость пропорциональна объёму пересылаемых данных. См. [§6.1](chapter-06-01.md).

**Broadcast Motion** — **полная копия** набора данных (обычно одной из сторон соединения) рассылается **на все сегменты**. Каждый сегмент получает копию; стоимость пропорциональна размеру данных, умноженному на число сегментов. Часто выбирается для **маленькой** таблицы при JOIN с большой. См. [§6.1](chapter-06-01.md), [§8.3](chapter-08-03.md).

В выводе плана указывается **slice** (номер среза) и **segments** (число задействованных сегментов). План разбит на срезы (slices); каждый срез выполняется на одной или нескольких группах сегментов. По motion-узлам можно оценить объём пересылки: большие Redistribute или Broadcast на больших таблицах — потенциальное узкое место. См. [§8.3](chapter-08-03.md).

## 8.1.5. Пример плана

Упрощённый пример (адаптировано из документации Greenplum):

```text
EXPLAIN SELECT * FROM names WHERE name = 'Joelle';
                        QUERY PLAN
-----------------------------------------------------------
 Gather Motion 3:1 (slice1; segments: 3) (cost=0.00..431.27 rows=1 width=58)
   ->  Seq Scan on names (cost=0.00..431.27 rows=1 width=58)
         Filter: (name = 'Joelle'::text)
 Optimizer: GPORCA
```

Чтение снизу вверх: **Seq Scan on names** — последовательное сканирование таблицы `names` на каждом из 3 сегментов с фильтром по `name`. Результаты передаются в **Gather Motion 3:1** — три сегмента отдают строки координатору. Оценка: одна строка (rows=1), общая стоимость 431.27. При **EXPLAIN ANALYZE** появятся фактические rows, time и т.д.

## 8.1.6. EXPLAIN ANALYZE: фактические показатели

При **EXPLAIN ANALYZE** к каждому узлу добавляются:

- **actual time** — фактическое время (мс) на этом узле (часто «time to first row» и «time to end»).
- **rows** — фактическое число строк (в сравнении с планировщиковой оценкой).
- **Work_mem used / wanted** — при нехватке памяти показывается сброс на диск (workfile I/O), число проходов; это признак того, что увеличение work_mem или statement_mem может помочь. См. [§8.4](chapter-08-04.md).

Общее время выполнения запроса выводится в конце. Узлы с наибольшим **actual time** или с большим расхождением **rows** (оценка vs факт) — кандидаты для оптимизации: уточнение статистики (ANALYZE), изменение запроса или распределения таблиц. См. [§8.2](chapter-08-02.md), [§8.3](chapter-08-03.md).

## 8.1.7. Типичные ошибки

- **Оценивать план только по EXPLAIN без ANALYZE:** оценки cost и rows могут сильно отличаться от факта; для диагностики медленных запросов нужен **EXPLAIN ANALYZE**.
- **Игнорировать motion:** большие Redistribute или Broadcast съедают время и сеть; при возможности выравнивайте распределение таблиц под JOIN ([§6.1](chapter-06-01.md)) или переписывайте запрос.
- **Не смотреть на spill (workfile):** если в плане есть «spilled to disk» или «workfile», операция не поместилась в work_mem; рассмотрите увеличение work_mem/statement_mem или упрощение запроса.

---

## Ключевое

- **EXPLAIN** выводит план без выполнения; **EXPLAIN ANALYZE** выполняет запрос и добавляет фактические time, rows, work_mem/spill. План читают **снизу вверх**.
- Узлы плана: **Seq Scan**, **Index Scan** (и варианты) — сканы; **cost**, **rows**, **width** — оценки; верхние узлы — часто **motion** (Gather, Redistribute, Broadcast).
- **Gather Motion** — сбор с сегментов на координатор; **Redistribute Motion** — перераспределение по ключу; **Broadcast Motion** — рассылка копии на все сегменты. По объёму motion оценивают пересылку данных. См. [§8.3](chapter-08-03.md).

В [§8.2](chapter-08-02.md) мы разберём **статистику и ANALYZE**: зачем нужна актуальная статистика для планировщика и как её собирать.
