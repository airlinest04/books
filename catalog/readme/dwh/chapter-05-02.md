# §5.2 Типы SCD

В [§5.1](chapter-05-01.md) мы разобрали, зачем отслеживать историю измерений. Теперь зафиксируем **типы SCD** — способы реагирования на изменение атрибута в измерении: **Type 1** (перезапись), **Type 2** (новая строка с датами действия и флагом текущей версии), **Type 3** (отдельные столбцы для предыдущего значения) и кратко другие варианты. Выбор типа зависит от того, нужна ли полная история, только предыдущее значение или достаточно «текущего» состояния. В [§5.3](chapter-05-03.md) разберём реализацию Type 2 (суррогатный ключ, effective_from/effective_to, логика ETL); в [§5.4](chapter-05-04.md) — запросы к истории и срезы на дату. См. [Глоссарий](glossary.md).

---

## 5.2.1. Type 1: перезапись

**SCD Type 1** — при изменении атрибута в источнике **перезаписываем** значение в строке измерения. История не сохраняется: в таблице измерения всегда только актуальное значение. Одна бизнес-сущность (один продукт, один клиент) по-прежнему представлена одной строкой с одним суррогатным ключом; факты продолжают ссылаться на тот же ключ. См. [Глоссарий](glossary.md).

Плюсы: простота реализации, нет роста числа строк в измерении, запросы к измерению не усложняются (нет фильтра по датам действия или is_current). Минус: исторические отчёты и срезы «на дату» по этому атрибуту неверны — все факты при JOIN получат текущее значение.

Когда использовать Type 1:
- Атрибут не участвует в исторических срезах и отчётах «на дату» (например, исправление опечатки, внутренний код).
- Требования только к текущему состоянию; ретроспектива по этому атрибуту не нужна.

Для атрибутов, по которым нужна история (категория продукта, регион магазина, сегмент клиента), Type 1 не подходит; выбирают Type 2 или Type 3.

---

## 5.2.2. Type 2: новая строка (версионирование)

**SCD Type 2** — при изменении атрибута **добавляем новую строку** в таблицу измерения с новыми значениями; старая строка остаётся и помечается как «не текущая». Одна бизнес-сущность представлена **несколькими строками** с разными суррогатными ключами и разными периодами действия. Факты ссылаются на суррогатный ключ измерения; при загрузке новых фактов используется ключ той версии измерения, которая актуальна на дату факта. См. [Глоссарий](glossary.md).

Типичные поля в измерении для Type 2:
- **effective_from** (effective_date) — дата начала действия версии.
- **effective_to** — дата окончания действия (NULL или максимальная дата для текущей версии).
- **is_current** — флаг: 1 для текущей версии, 0 для исторических.

Либо только даты, либо даты плюс флаг; главное — однозначно определить, какая строка актуальна на любую дату. Суррогатный ключ (id) в измерении уникален для каждой строки (каждой версии); в фактовой таблице хранится именно суррогатный ключ, а не бизнес-ключ (product_code, customer_id из источника), чтобы факт был привязан к конкретной версии.

Плюсы: полная история; запрос «на дату» и исторические отчёты корректны — выбираем версию по effective_from/effective_to или is_current. Минусы: рост числа строк в измерении; при запросе «текущее состояние» нужен фильтр is_current = 1 (или effective_to IS NULL); ETL сложнее (логика закрытия старой версии и вставки новой). Подробнее реализация Type 2 — в [§5.3](chapter-05-03.md).

---

## 5.2.3. Type 3: отдельные столбцы для предыдущего значения

**SCD Type 3** — при изменении атрибута **не добавляем новую строку**, а добавляем в таблицу измерения **дополнительные столбцы** для хранения одного (или нескольких) предыдущих значений. Например: current_category и previous_category; при следующем изменении current_category станет previous_category, а новое значение запишется в current_category. См. [Глоссарий](glossary.md).

Плюсы: одна строка на сущность, запросы просты; можно сравнивать «текущее» и «предыдущее» значение без JOIN. Минусы: хранится только ограниченная история (одно или N предыдущих значений); срезы «на произвольную дату» и полная история по всем изменениям невозможны. Подходит, когда важно «было — стало» или «предыдущее значение», но не полная хронология.

Редко используется для многих атрибутов сразу (таблица раздувается столбцами). Применяют выборочно для одного-двух атрибутов, по которым нужна именно «предыдущая» версия.

---

## 5.2.4. Сравнение типов

| Критерий | Type 1 | Type 2 | Type 3 |
|----------|--------|--------|--------|
| **Реакция на изменение** | Перезапись значения | Новая строка (версия) | Новый столбец или сдвиг в previous_* |
| **История** | Нет | Полная (все версии) | Только текущее + одно (или N) предыдущих |
| **Строк на сущность** | Одна | Несколько (по числу версий) | Одна |
| **Суррогатный ключ в факте** | Один и тот же для сущности | Разный для каждой версии (факт привязан к версии на дату) | Один и тот же |
| **Запрос «на дату»** | Неверно (всегда текущее) | Корректно (выбор версии по дате) | Только текущее и предыдущее |
| **Сложность ETL** | Низкая | Выше (закрытие версии, вставка новой) | Средняя (обновление столбцов) |
| **Когда уместен** | Атрибуты без исторических требований | Атрибуты с полной историей и срезами на дату | Один-два атрибута с нужой «предыдущего» значения |

В практике витрин чаще всего комбинируют: часть атрибутов — Type 1 (коды, исправления), ключевые для отчётов (категория, регион, сегмент) — Type 2. Type 3 — по необходимости для отдельных атрибутов.

---

## 5.2.5. Другие варианты (кратко)

В литературе упоминают и другие типы:

- **Type 4 (или «историческая таблица»):** текущее состояние хранится в основной таблице измерения (как Type 1), а история — в отдельной таблице (history table). Запросы к текущему состоянию — к основной таблице; к истории — к отдельной. Минус — два места хранения и необходимость решать, куда пишет факт (в текущую таблицу при загрузке фактов нужно знать «текущий» ключ сущности; при ретроспективе — ключ из истории). На практике часто предпочитают единую таблицу с Type 2.

- **Type 6 (гибрид):** комбинация Type 1, 2 и 3: текущие атрибуты в «текущей» строке плюс столбцы с предыдущим значением и полная история в виде версий. Используется редко из-за сложности.

- **Снимки измерений на дату:** вместо версий в одной таблице хранят полный снимок измерения на каждую дату загрузки (одна копия таблицы на дату). История есть, но объём и сложность запросов высоки; применяют при особых требованиях к аудиту.

Для большинства проектов достаточно **Type 1 для некритичных атрибутов** и **Type 2 для атрибутов с историей**. Реализация Type 2 — в [§5.3](chapter-05-03.md).

## 5.2.6. Типичные ошибки

- **Везде Type 1:** тогда исторические отчёты по категориям, регионам и т.д. будут неверны. Определить атрибуты, по которым нужна история, и применить к ним Type 2 (или Type 3 выборочно).
- **В факте хранить бизнес-ключ вместо суррогатного при Type 2:** при Type 2 в факте должен храниться суррогатный ключ (id версии измерения), иначе нельзя однозначно привязать факт к версии на дату. Связь «факт → измерение» по суррогатному ключу.
- **Путать Type 2 и Type 3:** Type 2 — много строк на сущность, полная история. Type 3 — одна строка, текущее + предыдущее значение. Разная структура и разная пригодность для срезов на дату.
- **Не закрывать предыдущую версию при Type 2:** при появлении новой версии у старой должен быть установлен effective_to (и is_current = 0). Иначе две «текущих» версии и неоднозначность при запросах.

---

## Ключевое

- **Type 1:** перезапись атрибута; история не сохраняется. Подходит для атрибутов без требований к историческим срезам.
- **Type 2:** новая строка при изменении; даты действия (effective_from, effective_to), флаг is_current; суррогатный ключ уникален для версии. Полная история; срезы «на дату» корректны. Факт хранит суррогатный ключ версии. Реализация — в §5.3.
- **Type 3:** дополнительные столбцы для предыдущего значения (current_*, previous_*). Одна строка на сущность; только текущее и одно (или N) предыдущих значений; полная история невозможна.
- Комбинирование по атрибутам: Type 1 для некритичных, Type 2 для ключевых с историей, Type 3 выборочно. Другие варианты (Type 4, 6, снимки) — при особых требованиях. Запросы к истории и срезы на дату — в §5.4.

В [§5.3](chapter-05-03.md) мы разберём реализацию Type 2: суррогатный ключ, поля effective_from / effective_to / is_current и логику ETL при обновлении измерения.
