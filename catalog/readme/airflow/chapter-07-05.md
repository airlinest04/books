# §7.5 Variables и Connections

В [§7.4](chapter-07-04.md) мы разобрали XCom для передачи данных между задачами. Для **параметров конфигурации** и **учётных данных** внешних систем в Airflow используются **Variables** и **Connections**: они хранятся в метаданных (или во внешнем бэкенде) и доступны в DAG и задачах без хардкода в коде. В этом разделе — что такое Variables и Connections, как их задавать и использовать в операторах и хуках, и кратко о **безопасности**. В конце главы 7 — выводы и задание. Дальше в [главе 8](chapter-08-01.md) — Celery и распределённое выполнение. См. [Глоссарий](glossary.md).

---

## 7.5.1. Variables (переменные)

**Variables** — ключ–значение для хранения параметров конфигурации: пути к каталогам, имена таблиц, URL, флаги (например, окружение: dev/prod). Не предназначены для паролей и токенов — для секретов используйте Connections или внешние хранилища секретов.

**Задание:** в UI — Admin → Variables; добавить ключ и значение. Или через CLI: `airflow variables set my_key "my_value"`. Импорт из JSON-файла: `airflow variables import variables.json`.

**Использование в коде:**

```python
from airflow.models import Variable

path = Variable.get("data_input_path")
table = Variable.get("staging_table", default_var="staging.sales")  # с значением по умолчанию
```

**Variable.get** обращается к БД метаданных; при каждом вызове во время выполнения задачи читается актуальное значение. В шаблонах Jinja переменные доступны через макрос, например `{{ var.value.my_key }}` или `{{ var.json.my_key }}` для JSON (в зависимости от версии). Не храните в Variables большие объёмы данных и секреты в открытом виде.

## 7.5.2. Connections (подключения)

**Connections** — хранилище параметров подключения к внешним системам: БД (host, port, login, password, schema), HTTP API (host, логин/пароль для Basic Auth), облачные сервисы. Хуки и операторы принимают **conn_id** — идентификатор Connection — и берут оттуда хост, порт, логин, пароль и при необходимости поле **extra** (JSON с дополнительными параметрами). Секреты (пароль) хранятся в зашифрованном виде при включённом шифровании в конфигурации Airflow.

**Задание:** в UI — Admin → Connections; Add. Указать Conn Id (например, `source_db`, `my_api`), тип (Postgres, HTTP, Snowflake и т.д.), Host, Schema (база для БД), Login, Password, Port. Поле Extra — для дополнительных параметров (например, JSON с токеном или параметрами драйвера).

**Использование в хуках и операторах:** передать **conn_id** в конструктор Hook или Operator:

```python
hook = PostgresHook(postgres_conn_id="source_db")
# или в HttpHook: http_conn_id="my_api"
```

Подключение с указанным conn_id должно существовать; иначе задача упадёт при попытке подключения. В продакшене не задавайте пароли в коде — только через Connection или через внешний секрет-менеджер (интеграция зависит от версии и настроек).

---

## 7.5.3. Использование в операторах и хуках

- **Операторы** (PostgresOperator, HttpOperator и др.) принимают параметр **conn_id** (или postgres_conn_id, http_conn_id — по имени в конкретном операторе) и сами получают учётные данные из Connection.
- **Хуки** ([§7.3](chapter-07-03.md)) — то же: PostgresHook(postgres_conn_id="..."), HttpHook(http_conn_id="..."). Connection подставляется при создании хука в задаче.
- **Variables** подставляются в коде через Variable.get или в шаблонах; удобны для путей, имён таблиц, URL без секретов.

Таким образом, конфигурация и секреты выносятся из DAG-файлов: смена окружения или пароля не требует правки кода, только обновление Variable или Connection в UI/CLI.

---

## 7.5.4. Безопасность

- **Пароли и токены** — храните в Connections (пароль в зашифрованном виде при включённом fernet key в airflow.cfg) или во внешнем секрет-менеджере. Не кладите секреты в Variables в открытом виде и не коммитьте их в репозиторий.
- **Variables** — не используйте для чувствительных данных; при необходимости маскирование в логах настраивается отдельно. Ограничьте права на изменение Variables и Connections (роли в Airflow).
- **Логи и UI** — пароли из Connections в логах и в UI маскируются (показываются как ***). Убедитесь, что в коде задач вы не логируете пароли и токены в открытом виде.
- **Доступ к метаданным** — БД Airflow содержит зашифрованные пароли и значения Variables; доступ к ней должен быть ограничен. Регулярная ротация паролей и проверка списка Connections — часть эксплуатации.

## Ключевое по главе 7 и задание

**Выводы главы 7:**

1. **Операторы** — BaseOperator, BashOperator (шаблоны в bash_command), PythonOperator (op_args, op_kwargs, контекст); шаблоны Jinja ({{ ds }} и др.) для привязки к логической дате.
2. **Сенсоры** — ожидание условия (файл, БД); BaseSensorOperator; режимы poke и reschedule; FileSensor, SqlSensor.
3. **Хуки** — абстракция подключения по conn_id; PostgresHook, HttpHook; создание хука внутри задачи.
4. **XCom** — push (return, xcom_push) и pull (xcom_pull); передавать путь к файлу или ключ в БД, не большие данные.
5. **Variables** — параметры конфигурации (пути, имена); **Connections** — учётные данные для БД и API; использование в операторах и хуках; секреты только в Connections или внешнем хранилище.

**Задание:**

- **Таск с сенсором.** Добавьте в один из DAG сенсор (например, ожидание файла по пути с {{ ds }}) перед таском извлечения; проверьте в UI, что сенсор переходит в success после появления файла или падает по timeout при его отсутствии.
- **Таск с хуком к БД.** Реализуйте задачу (PythonOperator), которая через PostgresHook или другой Hook подключается к БД по conn_id, выполняет запрос (например, SELECT 1 или чтение строк за дату) и возвращает результат или пишет в XCom. Connection настройте в UI.
