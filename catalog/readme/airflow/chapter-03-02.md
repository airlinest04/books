# §3.2 Компоненты

В [§3.1](chapter-03-01.md) мы ввели Apache Airflow и кратко перечислили его части. Здесь разберём **компоненты** по отдельности: Scheduler (планирование и постановка задач в очередь), Executor (выполнение), Worker при использовании Celery, метаданные в БД и веб-интерфейс. После этого раздела вы будете понимать, кто за что отвечает в архитектуре Airflow и как данные и управление проходят от кода DAG до фактического выполнения задачи.

---

## 3.2.1. Scheduler (планировщик)

**Scheduler** — отдельный процесс Airflow, который непрерывно работает в фоне и выполняет две основные функции.

1. **Загрузка DAG.** Scheduler периодически сканирует каталог DAG (см. [§3.4](chapter-03-04.md)), загружает Python-файлы, извлекает объекты `DAG` и сохраняет метаданные (структура графа, расписание, параметры) в базе метаданных. Ошибки парсинга (синтаксис, дубликат `dag_id`) фиксируются и отображаются в UI, чтобы разработчик мог исправить код.

2. **Планирование запусков.** Scheduler смотрит на расписание каждого DAG (`schedule_interval`, `start_date`, настройки catchup) и в нужные моменты времени создаёт **DAG Run** — экземпляр запуска пайплайна за конкретную логическую дату. Для каждого DAG Run он проверяет граф зависимостей: какие задачи готовы к выполнению (все предшественники успешно завершены). Готовые задачи он передаёт **Executor** для постановки в очередь на выполнение. Сами задачи Scheduler **не выполняет** — только решает, когда и какие задачи запускать, в полном соответствии с моделью из [§1.2](chapter-01-02.md).

Scheduler — ключевой компонент для «когда» и «в каком порядке»; без работающего Scheduler новые DAG Run не создаются и задачи не попадают в очередь. См. [Глоссарий](glossary.md).

---

## 3.2.2. Executor (исполнитель)

**Executor** — компонент, который **принимает задачи от Scheduler** и организует их выполнение: либо сам запускает в том же процессе/на той же машине, либо отдаёт во внешнюю очередь для воркеров. Концепция Executor в Airflow абстрагирует «как выполнять задачу» от «когда её выполнять» (последнее — зона Scheduler).

Типичные варианты:

- **SequentialExecutor** — задачи выполняются по одной в том же процессе, что и Scheduler. Подходит только для отладки и минимальной нагрузки; в продакшене не рекомендуется.

- **LocalExecutor** — задачи выполняются в отдельных процессах на той же машине (пул воркеров в рамках одного узла). Подходит для небольшого числа DAG и задач; не требует отдельного брокера сообщений.

- **CeleryExecutor** — задачи ставятся в очередь (брокер: Redis или RabbitMQ); отдельные процессы **Celery Worker** на одной или нескольких машинах забирают задачи из очереди и выполняют их. Подходит для масштабирования по горизонтали и высокой параллельности. Подробнее — в [главе 8](chapter-08-01.md).

Executor настраивается в `airflow.cfg`; при смене Executor (например, с Local на Celery) обычно требуется перезапуск Scheduler и при Celery — запуск воркеров. Роль Executor в общей схеме: **получить задачу от Scheduler и довести её до фактического запуска** (локально или через очередь).

---

## 3.2.3. Worker (при Celery)

При использовании **CeleryExecutor** фактическое выполнение задач переносится в процессы **Celery Worker**. Scheduler через Executor помещает задачи в очередь (Redis/RabbitMQ); воркеры подписаны на эту очередь, забирают задачу, выполняют её (запуск подпроцесса, выполнение кода оператора), записывают результат и логи в метаданные (через подключение к БД Airflow) и помечают задачу как успешную или failed. Scheduler при следующем цикле видит обновлённый статус и может ставить в очередь следующие по графу задачи.

Таким образом, при Celery **Worker** — это и есть «исполнитель» в смысле [§1.2](chapter-01-02.md): он выполняет код задач. При LocalExecutor роль воркера выполняют дочерние процессы, порождённые тем же узлом; отдельного процесса с именем «Worker» может не быть, но логика «забрать задачу и выполнить» та же. См. [Глоссарий](glossary.md).

## 3.2.4. Метаданные в БД (Metadata database)

Airflow хранит состояние и конфигурацию в **реляционной БД** (Metadata database). Обычно используют PostgreSQL или MySQL; для лёгкой установки допускается SQLite (только с SequentialExecutor и для разработки).

В БД хранятся в том числе:

- **DAG и задачи** — идентификаторы, структура графа, параметры (после парсинга файлов Scheduler записывает/обновляет метаданные).
- **DAG Run и Task Instance** — экземпляры запусков: за какую логическую дату, статус (running, success, failed и т.д.), время начала и окончания.
- **Логи задач** — вывод stdout/stderr задач; может храниться в самой БД или во внешнем хранилище (например, S3), в зависимости от конфигурации.
- **Переменные и подключения** (Variables, Connections) — для секретов и параметров, используемых в DAG и операторах.

Scheduler и Executor (и воркеры при Celery) постоянно обращаются к БД: прочитать DAG, записать новый DAG Run, обновить статус задачи, прочитать логи. Веб-интерфейс тоже читает данные из этой БД. Поэтому доступность и производительность БД критичны для работы Airflow. Подробнее о Variables и Connections — в [§7.5](chapter-07-05.md).

## 3.2.5. Веб-интерфейс (Web server)

**Web server** — HTTP-сервер (на базе Flask), который отдаёт веб-интерфейс Airflow. Пользователь открывает UI в браузере и видит:

- **Список DAG** — включённые/выключенные, последние запуски, ошибки парсинга.
- **Граф и дерево выполнения** (Graph View, Tree View) — зависимости между задачами и статусы по датам запуска.
- **Детали DAG Run и Task Instance** — логи задачи, длительность, повторные попытки, ручной триггер и перезапуск.
- **Управление** — включение/выключение DAG, пауза, ручной запуск (Trigger DAG), очистка состояния.

Web server сам не планирует и не выполняет задачи; он только читает и записывает данные в БД и отображает их пользователю. Для работы UI нужен запущенный Web server; для появления новых запусков и выполнения задач нужен Scheduler и Executor (и при Celery — воркеры). Запуск Web server и Scheduler — в [§3.3](chapter-03-03.md).

## 3.2.6. Сводка: как компоненты связаны

| Компонент | Роль |
|-----------|------|
| **Scheduler** | Сканирует каталог DAG, создаёт DAG Run по расписанию, определяет готовые к выполнению задачи и отдаёт их Executor. |
| **Executor** | Принимает задачи от Scheduler и организует выполнение (локальные процессы или очередь для Celery Worker). |
| **Worker** (при Celery) | Забирает задачи из очереди и выполняет их, пишет статус и логи в БД. |
| **Metadata DB** | Хранит DAG, запуски, статусы задач, логи, переменные и подключения. |
| **Web server** | Показывает UI: DAG, запуски, логи; ручной триггер и управление. |

Поток данных: код DAG в файлах → Scheduler парсит и пишет в БД → Scheduler создаёт DAG Run и ставит задачи в Executor → Executor/Worker выполняют задачи и обновляют БД → пользователь видит результат в UI. В [§3.3](chapter-03-03.md) мы пройдём установку и первый запуск: инициализация БД, запуск webserver и scheduler.

## Ключевое

- **Scheduler** — планирование: загрузка DAG из каталога, создание DAG Run по расписанию, определение готовых к выполнению задач и передача их Executor. Задачи не выполняет.
- **Executor** — организация выполнения: получает задачи от Scheduler и запускает их локально (LocalExecutor) или отдаёт в очередь для Celery Worker (CeleryExecutor).
- **Worker** (при Celery) — процессы, которые забирают задачи из очереди и выполняют их, обновляя статус и логи в БД.
- **Metadata database** — хранилище DAG, запусков, статусов, логов, переменных и подключений; к нему обращаются Scheduler, Executor, воркеры и Web server.
- **Web server** — веб-интерфейс для просмотра DAG, запусков, логов и ручного управления; не планирует и не выполняет задачи.

В [§3.3](chapter-03-03.md) — установка Airflow, инициализация БД и первый запуск webserver и scheduler.
