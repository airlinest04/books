# §2.4 Наблюдаемость

В [§2.3](chapter-02-03.md) мы разобрали обработку сбоев: retry и уведомления. Чтобы понимать, что произошло, почему упала задача и за какие периоды данные уже загружены, оркестратор должен давать **наблюдаемость** (observability): историю запусков, логи задач и при необходимости метрики и интеграцию с системами мониторинга. В этом разделе — что входит в наблюдаемость планировщика задач и зачем это нужно в контексте данных; в конце главы 2 — выводы и задание.

---

## 2.4.1. История запусков

**История запусков** — это ответ на вопросы: какие пайплайны запускались, когда, за какой период (логическая дата), с каким итоговым статусом (успех, сбой, отмена). Для каждого run должны быть видны:

- Идентификатор пайплайна (DAG) и дата/время запуска (логическая дата).
- Статус run в целом (running, success, failed) и статус каждой задачи в run.
- Время начала и окончания (фактическое), длительность.

Без истории нельзя уверенно ответить: «загружены ли данные за 10 февраля?» или «когда в последний раз успешно отработал пайплайн X?». История позволяет проводить аудит, планировать backfill и анализировать стабильность пайплайнов. В Airflow история хранится в метаданных (БД) и отображается в веб-интерфейсе: список DAG runs, граф и дерево выполнения (graph view, tree view).

---

## 2.4.2. Логи задач

Когда задача падает, недостаточно знать, что она «failed». Нужно **содержимое вывода** задачи: что она вывела в stdout/stderr, какое исключение возникло, какие параметры использовала. Оркестратор должен хранить и показывать **логи каждой задачи** (по run и по task_id).

Типичное использование:

- **Диагностика сбоя:** по логам видно «файл не найден», «таймаут подключения к БД», «ошибка парсинга даты».
- **Проверка корректности:** убедиться, что скрипт взял нужную дату, обработал ожидаемое число строк.
- **Аудит:** что именно выполнялось при данном запуске.

Логи должны быть привязаны к конкретному экземпляру задачи (run + task_id), чтобы при нескольких попытках (retry) или при нескольких run за разные даты можно было смотреть вывод именно нужного выполнения. В Airflow логи доступны через UI (кнопка «Log» у задачи) и при необходимости через бэкенд (например, при хранении в удалённом хранилище).

---

## 2.4.3. Метрики и интеграция с мониторингом

Для эксплуатации на уровне «все пайплайны в проде» полезны **метрики**:

- Количество успешных и проваленных запусков за период.
- Длительность выполнения пайплайнов и отдельных задач.
- Очередь задач (сколько ждёт выполнения), использование воркеров.

Оркестратор может отдавать метрики в системы мониторинга (Prometheus, StatsD, облачные мониторинги) или экспортировать их по API. Тогда в едином дашборде видны не только «упал ли последний run», но и тренды: растёт ли время выполнения, появляются ли «подвисшие» задачи. Интеграция с алертами (см. [§2.3](chapter-02-03.md)) дополняет картину: при падении задачи событие уходит в мониторинг, и ответственный получает уведомление по настройным правилам.

---

## 2.4.4. Наблюдаемость как требование

**Наблюдаемость** — возможность по данным системы (логи, метрики, история) понять текущее и прошлое поведение пайплайнов и причину сбоев. Для планировщика задач в данных минимально необходимо:

| Элемент | Назначение |
|--------|------------|
| История запусков | Какие run были, за какие даты, статус; аудит и планирование backfill. |
| Логи задач | Диагностика сбоев, проверка параметров и результата выполнения. |
| Метрики (опционально) | Тренды, загрузка воркеров, интеграция с общим мониторингом. |
| Алерты | Уведомление при сбоях (см. §2.3). |

Без истории и логов эксплуатация превращается в «чёрный ящик»: пайплайн упал — непонятно когда, за какую дату и почему. С наблюдаемостью команда может быстро локализовать проблему и принять решение о повторе или исправлении кода.

---

## Ключевое по главе 2 и задание

**Выводы главы 2:**

1. **Регулярные загрузки** (ежедневно, еженедельно) — типичный сценарий для планировщика; запуск привязан к логическому периоду данных и к успеху предыдущих шагов.
2. **Зависимости между задачами** задают порядок: Raw → Staging → витрина; при нескольких источниках — параллельные ветви и сведение. Граф выполнения обеспечивается планировщиком.
3. **Обработка сбоев:** retry при временных ошибках, уведомления при окончательном падении; задачи должны быть **идемпотентными**, чтобы повторный запуск не портил данные.
4. **Наблюдаемость:** история запусков, логи задач, при необходимости метрики и интеграция с мониторингом — основа диагностики и эксплуатации.

**Задание:**

- **Список задач с зависимостями и расписанием.** Для выбранного сценария (например, загрузка двух источников в DWH с построением витрины) составьте: (1) список задач с краткими названиями; (2) граф зависимостей (кто после кого); (3) расписание каждой задачи или одного общего пайплайна; (4) что считать идемпотентностью для каждой задачи и как настроить retry/алерты.
