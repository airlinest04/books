# §4.1 DAG (Directed Acyclic Graph)

В [§3.4](chapter-03-04.md) мы разобрали каталог DAG: куда класть Python-файлы, чтобы Airflow подхватил пайплайны. Теперь переходим к **определению DAG в коде**. В этом разделе даётся определение DAG как направленного ациклического графа, объясняется связь «один DAG — один файл Python» (или несколько DAG в одном файле), и показывается базовый способ объявления DAG через контекстный менеджер `with DAG(...)`. Задачи (таски) и их зависимости разбираются в [§4.3](chapter-04-03.md) и [§4.4](chapter-04-04.md); параметры DAG (dag_id, расписание и т.д.) — в [§4.2](chapter-04-02.md).

---

## 4.1.1. Определение: направленный ациклический граф

**DAG** (Directed Acyclic Graph) — направленный ациклический граф. В Airflow под DAG понимают описание пайплайна:

- **Вершины графа** — это **задачи (tasks)**: отдельные единицы работы (запуск команды, вызов функции, выполнение оператора).
- **Рёбра** задают порядок выполнения: ребро из задачи A в задачу B означает «B выполняется после A». Направление — от предшественника к преемнику.
- **Ацикличность** — в графе нет циклов. Нельзя задать «A после B и B после A»; такой цикл сделал бы порядок выполнения неопределённым. Airflow при загрузке проверяет, что граф ацикличен, и при обнаружении цикла может не загрузить DAG или пометить его как ошибочный.

Таким образом, DAG в Airflow — это не только «граф» в математическом смысле, но и **объект в коде** (класс `DAG` из `airflow.models`), к которому привязываются задачи и параметры: идентификатор, расписание, теги и т.д. Один такой объект соответствует одному пайплайну в UI и в планировщике. См. [Глоссарий](glossary.md).

---

## 4.1.2. Один файл Python — один или несколько DAG

В одном Python-файле в каталоге DAG можно определить **один или несколько** объектов `DAG`. При сканировании каталога Airflow импортирует файл и ищет в модуле все экземпляры `DAG`; каждый с уникальным `dag_id` будет зарегистрирован как отдельный пайплайн. Типичная практика:

- **Один DAG в одном файле** — проще навигация и код-ревью; имя файла часто совпадает с логикой пайплайна (например, `sales_daily.py` для ежедневной загрузки продаж).
- **Несколько DAG в одном файле** — допустимо, если пайплайны тесно связаны или генерируются в цикле из общей конфигурации; при этом каждый DAG должен иметь свой уникальный `dag_id`.

Связь «один файл — один DAG» — это соглашение по организации кода, а не ограничение Airflow. Ограничение одно: **уникальность `dag_id`** в рамках всей установки.

## 4.1.3. Контекстный менеджер `with DAG(...)`

Создавать DAG принято через **контекстный менеджер** `with DAG(...):` — тогда все задачи, объявленные внутри блока `with`, автоматически привязываются к этому DAG, и не нужно передавать объект DAG в каждый оператор вручную.

Минимальный пример (среда: Airflow 2.x, Python 3.8+):

```python
from airflow import DAG

with DAG(dag_id="example_minimal_dag") as dag:
    pass  # задачи добавляются здесь (см. §4.3, §4.4)
```

Здесь создаётся DAG с идентификатором `example_minimal_dag`. Внутри блока `with` позже мы будем объявлять задачи (экземпляры операторов); каждая задача, созданная внутри этого блока и привязанная к `dag` (явно или через контекст), войдёт в граф этого DAG. Параметры DAG — `dag_id`, расписание, `start_date`, теги и др. — передаются в конструктор `DAG(...)`; их мы разберём в [§4.2](chapter-04-02.md).

Альтернатива без контекстного менеджера — создать DAG и передавать его в каждый оператор явно:

```python
from airflow import DAG

dag = DAG(dag_id="example_minimal_dag")
# task = SomeOperator(task_id="my_task", dag=dag)
```

Работоспособно, но при большом числе задач удобнее `with DAG(...):`, чтобы не повторять `dag=dag`.

## 4.1.4. Что должно быть в файле для загрузки DAG

Чтобы Airflow загрузил DAG из файла:

1. Файл лежит в каталоге DAG (`dags_folder`) и имеет расширение `.py`.
2. При импорте модуля выполняется код, в котором создаётся хотя бы один объект типа `DAG` (через `DAG(...)` или контекстный менеджер).
3. Объект DAG доступен на уровне модуля: либо как переменная (например, `dag` в `with DAG(...) as dag`), либо все DAG автоматически регистрируются при создании внутри `with`. В типичном варианте с `with DAG(...):` объект DAG регистрируется самим Airflow при разборе модуля, так как Airflow перебирает объекты типа `DAG` в глобальной области загруженного модуля.

Импорт не должен падать с исключением (см. [§3.4](chapter-03-04.md) про ошибки парсинга). Все зависимости, которые импортирует файл (например, `from airflow.operators.bash import BashOperator`), должны быть доступны в окружении, где запускается Scheduler.

## 4.1.5. Типичные ошибки

- **Цикл в графе:** задали зависимости так, что A → B → C → A. Airflow не сможет выстроить порядок выполнения; исправьте зависимости так, чтобы граф был ациклическим.
- **Дублирование dag_id:** два DAG с одинаковым `dag_id` в одном файле или в разных файлах — один перезапишет другой; используйте уникальные идентификаторы.
- **DAG не появляется в UI:** проверьте, что файл в `dags_folder`, расширение `.py`, при импорте нет исключений и создаётся объект `DAG`; при необходимости посмотрите ошибки парсинга в UI и логи Scheduler.

---

## Ключевое

- **DAG** в Airflow — направленный ациклический граф: вершины — задачи, рёбра — порядок «B после A»; циклов быть не должно.
- В одном Python-файле можно определить один или несколько DAG; каждый должен иметь уникальный **dag_id**.
- Удобный способ объявления — **контекстный менеджер** `with DAG(...):`; задачи, объявленные внутри блока, привязываются к этому DAG.
- Для загрузки DAG файл должен лежать в каталоге DAG, при импорте создаваться объект `DAG`, импорт не должен падать с ошибкой.

В [§4.2](chapter-04-02.md) разберём параметры DAG: dag_id, schedule_interval, start_date, теги, catchup и backfill (кратко).
