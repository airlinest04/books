# §3.3 Метрики по таблице и связям

В [§3.2](chapter-03-02.md) мы разобрали метрики по отдельным столбцам: пропуски, уникальность, min/max, распределение, типы и форматы. Профилирование не ограничивается столбцами — важно оценить **таблицу в целом** (число строк, ключи, дубликаты) и **связи между таблицами** (целостность ссылок). В этом разделе рассмотрены метрики по таблице и связям: зачем они нужны, как их считать и как интерпретировать результаты для принятия решений о качестве данных и корректности джойнов.

---

## 3.3.1. Число строк в таблице

**Число строк** (row count) — базовая метрика на уровне таблицы. Она задаёт объём данных и служит ориентиром для полноты ([§2.1](chapter-02-01.md)) и для сравнения с ожиданиями.

**Зачем считать:**

- **Ожидаемый объём:** при загрузке за фиксированный период или срез (например, «все заказы за январь») число строк можно сопоставить с ожиданием по источнику или с предыдущими загрузками. Сильное расхождение — повод проверить пайплайн (не обрезались ли данные, не попали ли дубли).
- **База для долей:** доли пропусков и уникальности по столбцам считаются от числа строк; при расчёте метрик по столбцам число строк таблицы уже используется.
- **Мониторинг:** при регулярном профилировании рост или падение числа строк по сравнению с предыдущим прогоном может сигнализировать об изменении источника или сбое загрузки.

В SQL число строк даёт `SELECT COUNT(*) FROM table`. Для очень больших таблиц в некоторых СУБД используют приближённые оценки (например, статистику планировщика), но для профилирования качества обычно нужен точный count или репрезентативная выборка с явной оговоркой.

---

## 3.3.2. Ключи и уникальность на уровне таблицы

**Первичный ключ (PK)** — столбец или комбинация столбцов, которые однозначно идентифицируют строку в таблице: в таблице не должно быть двух строк с одинаковым значением ключа. См. [Глоссарий](glossary.md).

При профилировании проверяют **кандидата в первичный ключ**: выбранный столбец или комбинация столбцов должны быть уникальны и по возможности без пропусков (NULL в ключе усложняет сравнение и джойны).

**Метрики:**

- **Уникальность по ключу:** для предполагаемого ключа (одного столбца или комбинации) считают `COUNT(*)` и `COUNT(DISTINCT key_columns)`. Если они равны — дубликатов по ключу нет, ключ можно считать уникальным. Если `COUNT(*) > COUNT(DISTINCT ...)` — есть дубликаты ключа; разница даёт число «лишних» строк при приведении к уникальному ключу.
- **Пропуски в ключевых столбцах:** в ключе не должно быть NULL (или их доля должна быть явно допустимой и документированной). Проверка — как в [§3.2](chapter-03-02.md) по каждому столбцу ключа.
- **Составной ключ:** для ключа из нескольких столбцов уникальность проверяется по комбинации: `COUNT(*)` vs `COUNT(DISTINCT col1, col2, ...)`.

Если в таблице нет объявленного первичного ключа, профилирование может предложить кандидата (столбец или комбинацию с уникальностью 100% и без пропусков) или зафиксировать, что однозначного ключа нет — это важно для последующих джойнов и дедупликации.

---

## 3.3.3. Дубликаты строк

**Дубликаты** — строки, полностью совпадающие по всем столбцам или по выбранному подмножеству (например, по ключу).

**Типы проверки:**

- **Дубликаты по первичному ключу:** уже покрыты в п. 3.3.2. Число дубликатов = `COUNT(*) - COUNT(DISTINCT key_columns)`; дублирующиеся строки могут различаться по неключевым полям (тогда это конфликт версий одной сущности) или быть полными копиями.
- **Полные дубликаты строк:** строки, совпадающие по всем столбцам. Метрика: `COUNT(*) - COUNT(DISTINCT col1, col2, ..., colN)`. Если схема большая, часто проверяют дубликаты по ключу, а полное совпадение — выборочно или при подозрении на дублирование загрузки.
- **Дубликаты по бизнес-ключу:** иногда уникальность ожидается не по техническому ID, а по бизнес-идентификатору (например, «один заказ — одна строка», ключ — order_id). Проверка аналогична: уникальность по бизнес-ключу и при необходимости разбор расхождений (разные версии заказа, отмены и т.д.).

Обнаружение дубликатов влияет на решение: дедупликация при загрузке, выбор одной версии по правилу (последняя по дате, макс. версия) или явная оговорка в отчёте («агрегаты считаны с учётом дубликатов по ключу»).

## 3.3.4. Целостность связей между таблицами

При наличии **связей** между таблицами (например, «заказы» ссылаются на «клиентов» по `client_id`) профилирование проверяет **целостность ссылок**: каждая ссылка ведёт к существующей записи в родительской таблице, и при необходимости — нет ли «висячих» записей в родительской таблице (никем не ссылаемых). См. [Глоссарий](glossary.md) — целостность.

**Внешний ключ (FK)** — столбец (или комбинация) в дочерней таблице, значения которого должны присутствовать в родительской таблице как значение первичного ключа (или уникального ключа). См. [Глоссарий](glossary.md).

**Типичные проверки:**

- **Сироты (orphans) в дочерней таблице:** значения внешнего ключа в дочерней таблице, для которых нет соответствующей строки в родительской. Пример: в таблице заказов есть `client_id`, но такого `client_id` нет в таблице клиентов. Метрика: число строк дочерней таблицы, для которых не найдено совпадение в родительской (через LEFT JOIN или NOT IN / NOT EXISTS). Такие записи при джойне «заказы + клиенты» выпадут или дадут NULL по полям клиента — возможна потеря данных или искажение агрегатов.
- **Потерянные родители (optional):** родительские записи, на которые никто не ссылается. Для связи «один ко многим» это нормально (есть клиенты без заказов); проверка нужна только если по бизнес-правилам каждая родительская запись должна иметь хотя бы одну дочернюю.
- **Кратность связи:** при ожидании «один к одному» или «ровно один ко многим» проверяют число дочерних записей на один родительский ключ (например, не больше одной записи на ключ в дочерней таблице). Множество дочерних на один родительский ключ — норма для связи «один ко многим».

Результаты проверки целостности используют при проектировании ETL (валидация на границах загрузки), при написании запросов (INNER vs LEFT JOIN, учёт потерь при джойне) и в документации ограничений набора данных.

## 3.3.5. Сводка метрик по таблице и связям

| Область | Метрика | Назначение |
|---------|---------|------------|
| Таблица | Число строк | Объём, сравнение с ожиданием, мониторинг |
| Таблица | Уникальность по ключу (PK-кандидат) | Подтверждение ключа, выявление дубликатов по ключу |
| Таблица | Пропуски в ключевых столбцах | Пригодность ключа для джойнов и уникальности |
| Таблица | Дубликаты (по ключу, полные, по бизнес-ключу) | Решение о дедупликации и оговорках в отчёте |
| Связи | Сироты (FK в дочерней без записи в родительской) | Целостность ссылок, риск потерь при джойне |
| Связи | Кратность (один к одному, один ко многим) | Соответствие ожидаемой модели данных |

В [§3.4](chapter-03-04.md) мы разберём выбросы (outliers): как их выявлять и как поступать с ними при профилировании и анализе.

---

## Ключевое

- **Метрики по таблице:** число строк (объём, полнота, мониторинг); уникальность по первичному ключу или кандидату; пропуски в ключевых столбцах; дубликаты по ключу, полные дубликаты или по бизнес-ключу.
- **Первичный ключ** — столбец или комбинация с уникальными значениями по таблице; при профилировании проверяют кандидата на уникальность и отсутствие (или допустимость) NULL.
- **Дубликаты:** различают по ключу, по всем столбцам и по бизнес-ключу; от результата зависят решение о дедупликации и формулировки в отчёте.
- **Целостность связей:** проверка «сирот» в дочерней таблице (значения FK без соответствующей записи в родительской); при необходимости — кратность связи. Нарушения влияют на выбор типа джойна и на документирование ограничений данных.

В [§3.4](chapter-03-04.md) мы разберём выбросы (outliers): правила выявления, визуализация и варианты действий — удаление, замена, отдельный анализ.
