# §2.6 Отладка и мониторинг

В [§2.5](chapter-02-05.md) мы разобрали кластерные режимы: локальный, standalone, YARN и Kubernetes. После запуска приложения важно понимать, как наблюдать за выполнением и искать причины сбоев или медленной работы. В этом разделе рассмотрим **Spark UI** (веб-интерфейс мониторинга), **логи драйвера и исполнителей** и **типичные причины медленной работы**: перекос данных (skew) и избыточный shuffle. Материал главы 2 завершается этим разделом; в главе 3 перейдём к Spark SQL и DataFrame API. См. [Глоссарий](glossary.md).

---

## 2.6.1. Spark UI: где смотреть и что искать

**Spark UI** — веб-интерфейс, который драйвер поднимает по умолчанию на порту 4040 (локально: http://localhost:4040). В нём отображается состояние текущего приложения: джобы (jobs), стадии (stages), задачи (tasks), использование памяти и диска исполнителями, объёмы shuffle. UI доступен, пока приложение выполняется (или пока включён режим сохранения истории после завершения). В кластере адрес UI драйвера может быть выдан при запуске (YARN, Kubernetes) или через конфигурацию; в локальном режиме достаточно открыть http://localhost:4040 в браузере после старта PySpark или скрипта. См. [Глоссарий](glossary.md).

Основные вкладки:

- **Jobs** — список джоб (каждое действие порождает одну или несколько джоб). По клику на джобу виден граф стадий и прогресс.
- **Stages** — список стадий; для каждой стадии: число задач, выполненные / активные / пропущенные, время, shuffle read / shuffle write (объём данных, прочитанных или записанных при shuffle). Здесь удобно увидеть, какая стадия заняла больше всего времени и сколько данных прошло через shuffle.
- **Storage** — закэшированные RDD/DataFrame: имя, уровень хранения (memory, disk), объём, число партиций.
- **Executors** — список исполнителей, использование памяти и диска, число выполненных задач, объём shuffle read/write по исполнителю.

По этим данным можно понять: сколько стадий породило действие, где произошёл shuffle, равномерно ли загружены задачи (или одна задача сильно дольше остальных — признак перекоса). См. [§2.3](chapter-02-03.md).

## 2.6.2. Стадии и задачи в UI

На вкладке **Stages** каждая стадия показана с метриками:

- **Duration** — время выполнения стадии (или суммарное по всем задачам с учётом параллелизма).
- **Tasks** — общее число задач, сколько успешно завершено (Succeeded), в процессе (Active), с ошибкой (Failed).
- **Shuffle Read / Shuffle Write** — объём данных, записанных этой стадией для shuffle (write) и прочитанных следующей стадией (read). Большие значения указывают на тяжёлый обмен по сети; при оптимизации часто стремятся уменьшить объём shuffle или число стадий с shuffle.
- По клику на стадию открывается список **задач** (Tasks): для каждой задачи — исполнитель, время выполнения, объём прочитанных/записанных данных. Сильный разброс по времени выполнения задач (одна задача 10 минут, остальные 30 секунд) — типичный признак **skew** (перекоса): одна или несколько партиций содержат непропорционально много данных или получают непропорционально много данных при shuffle. См. [Глоссарий](glossary.md).

## 2.6.3. Логи драйвера и исполнителей

Помимо UI, диагностика опирается на **логи**:

- **Драйвер:** вывод вашего кода (print, логирование), стектрейсы исключений, сообщения планировщика. В локальном режиме логи идут в консоль; при spark-submit в cluster mode логи драйвера собираются через интерфейс кластера (YARN Application Master, логи пода в Kubernetes) или пишутся в указанный файл.
- **Исполнители:** каждая задача при сбое пишет стектрейс; логи исполнителей накапливаются на узлах. В YARN логи контейнеров доступны через веб-интерфейс ResourceManager (Application Master → Logs) или через `yarn logs -applicationId <id>`. В Kubernetes — через `kubectl logs <driver-pod>` и логи подов исполнителей.

Типичные ошибки в логах: OutOfMemoryError (увеличить память исполнителя или драйвера, уменьшить размер партиции), FileNotFoundException (неверный путь к данным), сериализация/десериализация при передаче функций на исполнители (PySpark: убедиться, что передаваемые объекты сериализуемы). При отладке сначала смотреть логи драйвера (исключение в пользовательском коде или при планировании), затем логи упавшей задачи на исполнителе. См. [§2.1](chapter-02-01.md).

## 2.6.4. Перекос данных (skew)

**Skew (перекос данных)** — ситуация, когда при группировке, соединении или другой операции с распределением по ключу часть ключей получает **значительно больше** данных, чем остальные. В результате одна или несколько партиций (и соответствующих задач) обрабатывают огромный объём данных, а остальные — мало. Стадия не завершится, пока не выполнятся все задачи; одна «тяжёлая» задача задерживает всю стадию. В UI это видно по сильному разбросу времени выполнения задач или по одному исполнителю с аномально большим shuffle read. См. [Глоссарий](glossary.md).

Возможные меры:

- **Солевание (salting):** добавить к ключу случайный суффикс, чтобы разбить «горячий» ключ на несколько партиций; после агрегации снова агрегировать по исходному ключу (снять соль). Требует изменения логики запроса.
- **Увеличить число партиций** после shuffle (`repartition`, настройка `spark.sql.shuffle.partitions`), чтобы горячие ключи распределились по большему числу партиций; помогает не всегда, если один ключ доминирует по объёму.
- **Фильтрация или отдельная обработка:** если один ключ (например, null или служебное значение) даёт львиную долю данных, обработать его отдельно и объединить результат с остальными.
- **Broadcast join:** если одна из сторон соединения мала, broadcast избегает shuffle большой таблицы и может убрать перекос на стороне малой таблицы. См. [§7.3](chapter-07-03.md).

Полностью универсального рецепта нет; решение зависит от распределения ключей и от типа операции. Важно сначала **обнаружить** перекос по UI (задачи с резко большим временем или shuffle read), затем подбирать стратегию. См. [Глоссарий](glossary.md).

## 2.6.5. Избыточный shuffle

**Избыточный shuffle** — лишние операции, вызывающие перераспределение данных по сети: лишние стадии, дублирование одних и тех же данных при нескольких последовательных groupBy или join с разными ключами, слишком большое число партиций после shuffle (много мелких задач и накладные расходы). Признаки в UI: много стадий, большие объёмы shuffle read/write, долгое время на стадиях с shuffle.

Что можно сделать:

- **Уменьшить число shuffle-операций:** объединить несколько преобразований в одну стадию там, где это возможно; избегать лишних `repartition` без необходимости.
- **Настроить число партиций shuffle:** параметр `spark.sql.shuffle.partitions` (по умолчанию часто 200) задаёт число партиций после shuffle для DataFrame/SQL. При очень большом объёме данных значение можно увеличить; при малом объёме уменьшить, чтобы не создавать тысячи мелких задач.
- **Broadcast join:** для соединения с малой таблицей использовать broadcast, чтобы не перемешивать большую таблицу. См. [§7.3](chapter-07-03.md).
- **Кэширование:** если один и тот же DataFrame используется в нескольких действиях или в нескольких ветках с shuffle, закэшировать его после вычисления, чтобы не пересчитывать и не делать повторный shuffle. См. [§6.6](chapter-06-06.md).

Регулярный просмотр стадий и объёмов shuffle в UI помогает выявить узкие места и обоснованно менять код или конфигурацию. См. [Глоссарий](glossary.md).

## 2.6.6. Краткий чек-лист при проблемах с производительностью

| Вопрос | Где смотреть / что сделать |
|-------|----------------------------|
| Какая стадия самая долгая? | Spark UI → Stages → Duration. |
| Есть ли одна очень долгая задача в стадии? | Stages → клик по стадии → список задач; возможен skew. |
| Большой объём shuffle? | Stages → Shuffle Read / Shuffle Write; рассмотреть broadcast, уменьшение числа shuffle-операций. |
| Мало параллелизма? | Число задач в стадии = число партиций; при необходимости увеличить партиции или ресурсы исполнителей. |
| OutOfMemoryError? | Логи драйвера/исполнителя; увеличить память или уменьшить размер партиции / число данных на драйвере (избегать больших collect). |
| Приложение «зависло»? | UI → активные стадии и задачи; логи — нет ли блокировки или ожидания ресурсов. |

## Ключевое

- **Spark UI** (порт 4040 по умолчанию) показывает джобы, стадии, задачи, shuffle read/write и кэш; по нему видно, где ушло время и где происходит shuffle.
- В **Stages** смотрят длительность стадий, число задач и объёмы shuffle; по списку задач стадии можно обнаружить перекос (одна задача сильно дольше остальных).
- **Логи драйвера** и **логи исполнителей** (через консоль, YARN, Kubernetes) нужны для диагностики исключений и сбоев задач.
- **Skew (перекос)** — неравномерное распределение данных по партициям; одна или несколько задач сильно дольше остальных; меры: солевание, фильтрация горячих ключей, broadcast join, настройка партиций.
- **Избыточный shuffle** увеличивает время и нагрузку на сеть; уменьшают число операций с shuffle, настраивают `spark.sql.shuffle.partitions`, используют broadcast join и кэширование где уместно.
