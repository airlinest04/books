# §2.3 DAG и этапы (stages)

В [§2.2](chapter-02-02.md) мы разобрали RDD: неизменяемую распределённую коллекцию, партиции, lineage и ленивое выполнение. При вызове **действия** драйвер передаёт накопленный граф операций планировщику. В этом разделе разберём, как этот граф — **DAG (Directed Acyclic Graph)** — превращается в **стадии (stages)** и **задачи (tasks)** и почему границей между стадиями служит **shuffle**. Понимание стадий и задач нужно для чтения Spark UI и для оценки того, какие операции вызывают перераспределение данных по сети. В [§2.4](chapter-02-04.md) мы систематически разберём трансформации и действия; в [§2.6](chapter-02-06.md) — как смотреть DAG и стадии в интерфейсе мониторинга. См. [Глоссарий](glossary.md).

---

## 2.3.1. DAG операций

**DAG (Directed Acyclic Graph)** — направленный ациклический граф. В Spark под DAG понимают граф **операций** (трансформаций) над RDD или над логическим планом DataFrame: узлы — RDD (или логические операторы плана), рёбра — зависимости «родитель → потомок». Например, цепочка «источник → filter → map → groupByKey → map» образует линейный DAG. Разветвления (один RDD порождает два разных по разным трансформациям) дают несколько веток; циклов в графе нет — данные не возвращаются к предыдущему шагу.

DAG строится на **драйвере** по мере вызова трансформаций; данные по рёбрам не передаются до момента выполнения действия. При вызове действия (count, collect, write и т.д.) драйвер передаёт DAG **DAGScheduler**'у, который анализирует зависимости между партициями и разбивает граф на стадии. См. [Глоссарий](glossary.md).

---

## 2.3.2. Узкие и широкие зависимости: почему граница — shuffle

Зависимость между родительским RDD и дочерним бывает **узкой** (narrow) или **широкой** (wide).

**Узкая зависимость (narrow dependency):** каждая партиция дочернего RDD зависит только от **одной или нескольких фиксированных** партиций родителя. Примеры: `map`, `filter`, `flatMap` — одна партиция на входе даёт одну партицию на выходе; `union` — партиции просто объединяются. В таком случае задачу для дочерней партиции можно выполнить на том же исполнителе, где лежат данные родительской партиции; **передавать данные по сети между узлами не обязательно**. Несколько таких операций подряд можно выполнить в одном проходе по данным — **пайплайн** (pipeline): одна задача читает партицию, применяет подряд filter, map и т.д. и пишет результат.

**Широкая зависимость (wide dependency):** одна партиция дочернего RDD может зависеть от **многих партиций** родителя (или наоборот — одна партиция родителя нужна многим партициям потомка). Классический случай — операции, требующие **shuffle**: данные перераспределяются по ключу между узлами. Примеры: `reduceByKey`, `groupByKey`, `join` (в общем случае), `distinct` (внутри может быть shuffle). После shuffle каждая партиция «собирает» данные со многих исполнителей; до этого родительские партиции должны быть обработаны и их вывод должен быть передан по сети. Поэтому **широкая зависимость не позволяет выполнить родителя и потомка в одной задаче**: нужно сначала завершить все задачи родительской стадии, материализовать результат (в памяти или на диске), затем выполнить shuffle и только потом запустить задачи дочерней стадии.

Итог: планировщик **разбивает DAG на стадии по границам широких зависимостей (shuffle)**. Внутри одной стадии — только узкие зависимости; все операции стадии выполняются конвейерно в наборе задач, по одной задаче на партицию. Между стадиями — граница shuffle: данные записываются (или буферизуются), перераспределяются по сети, затем следующая стадия читает их и выполняет свои задачи.

## 2.3.3. Стадии (stages)

**Стадия (stage)** — совокупность операций с узкими зависимостями, которые можно выполнить одним набором задач без shuffle между ними. DAGScheduler обходит DAG «с конца» (от действия к источникам) и при встрече широкой зависимости начинает новую стадию. В результате получается последовательность стадий: например, Stage 0 — чтение и все map/filter до первого shuffle; Stage 1 — операции после shuffle до следующего shuffle или до выхода; и т.д.

- **Стадии выполняются по порядку:** пока не завершены все задачи стадии N, стадия N+1 не запускается (ей нужны результаты shuffle стадии N).
- **Внутри стадии задачи независимы:** каждая задача обрабатывает свою партицию; задачи можно рассылать разным исполнителям и выполнять параллельно. Число задач в стадии равно числу партиций на выходе этой стадии (на последнем RDD стадии).

В Spark UI (веб-интерфейс мониторинга джобы) вы видите список стадий, время выполнения каждой, число задач, объём shuffle read/shuffle write. Это позволяет понять, где ушло время и на какой стадии произошёл shuffle. См. [§2.6](chapter-02-06.md).

## 2.3.4. Задачи (tasks)

**Задача (task)** — единица работы, которую исполнитель выполняет над **одной партицией** в рамках одной стадии. Для стадии с, например, 200 партициями планировщик создаёт 200 задач; каждая задача — это «применить цепочку операций этой стадии к партиции с таким-то номером». Задачи рассылаются свободным исполнителям; исполнитель может выполнять несколько задач последовательно или (если выделено несколько ядер) параллельно. Когда все задачи стадии завершены, результаты (если есть shuffle) становятся доступны для следующей стадии; планировщик запускает задачи следующей стадии.

Размер задачи определяется объёмом данных в партиции и сложностью операций. Слишком мелкие партиции — много задач, накладные расходы на планирование и запуск; слишком крупные — недогрузка кластера и риск нехватки памяти на одну задачу. Выбор числа партиций (и тем самым числа задач в стадии) мы обсуждали в [§2.2](chapter-02-02.md) и подробнее рассмотрим в [§6.6](chapter-06-06.md). См. [Глоссарий](glossary.md).

## 2.3.5. Пример: цепочка с одним shuffle

Рассмотрим упрощённый пример (логика та же для RDD и DataFrame):

1. Чтение из файла → 8 партиций.
2. `filter(...)` — узкая зависимость.
3. `map(...)` — узкая зависимость.
4. `groupByKey()` — широкая зависимость (shuffle по ключу).
5. `mapValues(...)` — узкая зависимость.

DAG разбивается на две стадии:

- **Stage 0:** чтение + filter + map. Выход — 8 партиций; каждая партиция обрабатывается одной задачей. После завершения Stage 0 данные по ключам перераспределяются (shuffle) — каждая ключевая группа оказывается на одном исполнителе.
- **Stage 1:** groupByKey (приём данных после shuffle) + mapValues. Задачи Stage 1 читают результаты shuffle и применяют mapValues. Число задач равно числу партиций после shuffle (например, 8 или 200 — зависит от конфигурации).

Если бы после `mapValues` стояла ещё одна операция с shuffle (например, ещё один `groupByKey`), появилась бы Stage 2, и т.д.

## 2.3.6. Какие операции вызывают shuffle

При отладке и оптимизации полезно знать, какие операции создают широкую зависимость и тем самым новую стадию и сетевой обмен:

| Тип операции | Примеры (RDD / DataFrame) | Shuffle? |
|--------------|---------------------------|----------|
| Поэлементные, без ключа | `map`, `filter`, `flatMap`, `mapPartitions` | Нет (узкая). |
| Объединение без перераспределения | `union` | Нет. |
| Группировка по ключу | `groupByKey`, `reduceByKey`, `aggregateByKey` | Да. |
| Соединения | `join`, `cogroup` (в общем случае) | Да (если оба набора не партиционированы по ключу join и не broadcast). |
| Сортировка | `sortByKey`, `sortWithinPartitions` + глобальная сортировка | Да для глобальной сортировки. |
| Уникальность | `distinct` (через хэш-партиционирование) | Да. |
| Перераспределение явное | `repartition`, `coalesce` с shuffle | `repartition` — да; `coalesce(n)` без shuffle — нет. |

В DataFrame API: `groupBy().agg()`, `join()` (кроме broadcast join), `distinct()`, `orderBy()` (глобальный) — типичные источники shuffle. В [§2.6](chapter-02-06.md) мы кратко разберём, как по Spark UI увидеть объём shuffle и стадии. См. [Глоссарий](glossary.md).

## Ключевое

- **DAG** — граф операций (трансформаций) над RDD/DataFrame; строится на драйвере при вызове трансформаций; при вызове действия передаётся DAGScheduler для разбиения на стадии и задачи.
- **Узкая зависимость:** дочерняя партиция зависит только от небольшого фиксированного набора родительских; операции можно выполнять конвейерно в одной задаче. **Широкая зависимость:** нужен обмен данными по ключу (shuffle) между узлами; граница стадии.
- **Стадия (stage)** — блок операций с только узкими зависимостями; стадии разделяются границами shuffle; стадии выполняются по порядку.
- **Задача (task)** — выполнение цепочки операций одной стадии над одной партицией; число задач в стадии равно числу партиций выхода стадии.
- Операции вроде `groupByKey`, `reduceByKey`, `join`, `distinct`, `repartition` вызывают shuffle и новую стадию; `map`, `filter`, `union` — нет.

В [§2.4](chapter-02-04.md) мы систематически разберём трансформации и действия: какие методы возвращают RDD/DataFrame и не выполняются сразу, а какие запускают вычисление.
