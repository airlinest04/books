# §8.3 Распространение в источники

В [§8.1](chapter-08-01.md) и [§8.2](chapter-08-02.md) мы разобрали центр и загрузку эталонов. В этом разделе рассмотрим **распространение** (publish): центр как источник правды; опциональное обновление операционных систем из центра; потребление эталонов в DWH и других потребителях. В [§8.4](chapter-08-04.md) детально разберём связь консолидации с DWH.

---

## 8.3.1. Центр — источник правды

В модели консолидации **центр** — единый источник правды (SSOT) для эталонных данных. Золотая запись в центре — авторитетная версия сущности. Потребители (DWH, витрины, отчёты, интеграции) ориентируются на центр. См. [§1.3](chapter-01-03.md), [§4.1](chapter-04-01.md).

Поток данных в «чистой» консолидации: **источники → центр → потребители**. Источники загружают данные в центр; центр формирует золотую запись; потребители читают из центра. Обратный поток (центр → источники) — отдельная возможность, не обязательная для консолидации. См. [§8.1](chapter-08-01.md).

---

## 8.3.2. Распространение в операционные системы (опционально)

**Распространение в источники** — обновление операционных систем (CRM, ERP, биллинг и т.д.) данными из центра. Центр «пушит» золотую запись обратно в системы-источники. См. [§4.3](chapter-04-03.md) (маппинг для обратного распространения).

Зачем:

- **Синхронизация:** исправления, сделанные в центре (например, steward'ом), должны попасть в CRM и ERP.
- **Устранение расхождений:** центр — эталон; источники приводятся к нему.
- **Согласованность:** одна и та же запись клиента или контрагента во всех системах.

Как это работает: по golden_id из центра находим source_id для каждой целевой системы (маппинг); формируем payload в формате целевой системы; вызываем API или загружаем в БД источника. См. [§7.2](chapter-07-02.md).

---

## 8.3.3. Условия и ограничения распространения

Распространение **не всегда возможно или целесообразно**:

- **Ограничения систем:** CRM или ERP может не поддерживать обновление эталонов извне; только ручной ввод или импорт по строгому протоколу.
- **Владельцы данных:** подразделения могут не согласиться, что центр перезаписывает «их» данные; организационная политика.
- **Конфликты:** пока центр обновлял золотую запись, пользователь мог изменить запись в CRM; перезапись из центра затрёт его изменения. Нужны правила: кто побеждает, нужна ли блокировка, уведомления. См. [§9.3](chapter-09-03.md).
- **Частота:** слишком частое распространение — нагрузка на системы; слишком редкое — рассинхрон.

Варианты: распространение по расписанию; по событию (изменение в центре); только для выборочных полей; только в «приёмные» системы (не во все источники). Распространение — **опциональная** часть консолидации; многие организации ограничиваются потоком «источники → центр» без обратного push. См. [§9.1](chapter-09-01.md).

---

## 8.3.4. Потребление в DWH

**DWH** — основной потребитель эталонных данных из центра. Поток: центр (Core эталонов) → измерения DWH (dim_customer, dim_product и т.д.) → витрины и отчёты. См. [§1.4](chapter-01-04.md), [§8.4](chapter-08-04.md).

Загрузка эталонов в DWH — ETL из центра: чтение золотых записей, преобразование в структуру измерений (денормализация, SCD), загрузка в dim_*. Факты загружаются отдельно из транзакционных источников; при загрузке фактов source_id маппится на golden_id (или surrogate key измерения) по таблице маппинга. См. [§10.2](chapter-10-02.md).

Центр может быть реализован **внутри DWH** (Core-слой эталонов в том же хранилище) или **вне** (отдельная MDM-система). В первом случае «распространение в DWH» — внутренняя загрузка из Core в Mart; во втором — ETL из MDM в DWH. См. [§8.1](chapter-08-01.md).

---

## 8.3.5. Другие потребители

Кроме DWH центр может снабжать эталонами:

- **Интеграционные шины** — публикация изменений в шину; подписчики (другие приложения) получают обновления.
- **Операционные приложения** — система заказов, биллинг берут эталон контрагента из центра (или из своего кеша, обновляемого из центра).
- **Сервисы и API** — REST API «получить контрагента по golden_id» для внутренних и внешних потребителей.

Формат выдачи: таблицы в БД (для ETL), файлы (CSV, Parquet), API, сообщения в очередь. Выбор зависит от потребителя и требований к латентности. См. [§12.4](chapter-12-04.md).

---

## 8.3.6. Публикация vs подписка

**Публикация (push):** центр сам отправляет обновления потребителям по расписанию или при изменении. Распространение в операционные системы — типичный push.

**Подписка (pull):** потребители сами запрашивают данные из центра. DWH загружает эталоны по расписанию — pull. API «получить контрагента» — pull по запросу.

На практике комбинируют: DWH тянет из центра (ETL); операционные системы получают push из центра (если реализовано распространение). См. [§9.2](chapter-09-02.md).

---

## 8.3.7. Типичные ошибки

- **Считать распространение обязательным:** консолидация работает и без обратного push в источники; распространение — опция.
- **Игнорировать конфликты при push:** перезапись источника данными из центра без учёта локальных изменений создаёт потерю данных и недовольство пользователей.
- **Распространять всё подряд:** не все поля и не во все системы; нужна матрица «что куда».
- **Забыть маппинг при push:** для обновления записи в CRM нужен source_id (id в CRM); маппинг golden_id → source_id даёт его.

---

## Ключевое

- **Центр — источник правды:** потребители ориентируются на золотую запись в центре.
- **Распространение в источники** — опционально; обновление CRM, ERP данными из центра по маппингу golden_id → source_id.
- **Условия:** поддержка обновления целевой системой, согласие владельцев, правила при конфликтах.
- **Потребление в DWH:** Core → измерения → витрины; подробнее в [§8.4](chapter-08-04.md).
- **Другие потребители:** интеграционные шины, API, операционные приложения.
- **Push vs pull:** распространение в источники — push; загрузка DWH — pull.

В [§8.4](chapter-08-04.md) детально рассмотрим связь консолидации с DWH: эталонный слой, витрины, измерения из эталонов.
