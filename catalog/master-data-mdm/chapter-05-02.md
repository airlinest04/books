# §5.2 Сравнение и сопоставление записей

В [§5.1](chapter-05-01.md) мы разобрали обнаружение дубликатов и ввели fuzzy matching. В этом разделе детализируем **сравнение и сопоставление записей**: точное совпадение, нечёткие метрики (Levenshtein, Jaro-Winkler) и комбинированные правила. Понимание метрик необходимо для настройки порогов и выбора подходящего алгоритма под тип данных. В [§5.3](chapter-05-03.md) разберём алгоритмы слияния; в [§5.4](chapter-05-04.md) — SQL и инструменты.

---

## 5.2.1. Точное совпадение

**Точное совпадение** — строки считаются одинаковыми только при полном совпадении символов. Перед сравнением применяют **нормализацию**:

- Приведение к одному регистру (LOWER)
- Удаление пробелов в начале и конце (TRIM)
- Замена множественных пробелов на один
- Удаление или нормализация спецсимволов (дефисы, кавычки)
- Для чисел и кодов — убрать ведущие нули, привести к формату

Пример нормализации наименования:

```sql
-- Упрощённая нормализация
LOWER(TRIM(REGEXP_REPLACE(name, '\s+', ' ', 'g')))
```

Пример нормализации телефона: оставить только цифры; для российских номеров — привести к формату 7XXXXXXXXXX или 8XXXXXXXXXX по правилам.

После нормализации сравнение: `normalized_a = normalized_b`. Быстро и детерминированно; но «ООО Ромашка» и «Ромашка ООО» при такой нормализации не совпадут — нужен fuzzy matching. См. [§3.1](chapter-03-01.md).

---

## 5.2.2. Расстояние Левенштейна (Levenshtein)

**Расстояние Левенштейна** (Levenshtein distance) — минимальное число односимвольных операций (вставка, удаление, замена), чтобы преобразовать одну строку в другую. См. [Глоссарий](glossary.md).

Пример: «Ромашка» → «Ромашкаа» (расстояние 1, одна вставка); «Ромашка» → «Ромаска» (расстояние 1, одна замена).

**Коэффициент схожести** (0–1) на основе Левенштейна:

```
similarity = 1 - (levenshtein(s1, s2) / max(len(s1), len(s2)))
```

При полном совпадении — 1; при полном различии — 0. Чем короче строки, тем сильнее влияние одной опечатки: «Иван» и «Иванн» — distance=1, max_len=5, similarity=0.8; для длинных строк одна опечатка почти не влияет.

В PostgreSQL функция `levenshtein(s1, s2)` — модуль `fuzzystrmatch`; в Python — `Levenshtein.distance()`. См. [§5.4](chapter-05-04.md).

## 5.2.3. Jaro и Jaro-Winkler

**Jaro similarity** — метрика для коротких строк (имена, названия); учитывает совпадение символов и их порядок. Значение от 0 до 1. См. [Глоссарий](glossary.md).

**Jaro-Winkler** — модификация Jaro с бонусом за совпадение префикса; лучше для имён, где начало часто совпадает («Иванов» vs «Иванова»). В PostgreSQL — `jarowinkler(s1, s2)` из `fuzzystrmatch`.

Особенности:

- Быстрее Левенштейна на длинных строках (нет полного DP).
- Лучше для имён и коротких названий.
- Менее чувствителен к перестановкам частей («Ромашка ООО» vs «ООО Ромашка») — может дать высокий результат, т.к. символы в основном те же.

## 5.2.4. Сравнение метрик

| Метрика | Плюсы | Минусы | Когда использовать |
|---------|-------|--------|---------------------|
| **Точное (после нормализации)** | Быстро, нет ложноположительных | Пропускает опечатки, перестановки | ИНН, коды, уникальные идентификаторы |
| **Levenshtein** | Учитывает опечатки; интуитивно | Медленнее на длинных строках; чувствителен к длине | Наименования, адреса средней длины |
| **Jaro-Winkler** | Хорош для имён; быстрее | Менее точен для длинных текстов | ФИО, короткие названия |
| **N-граммы / cosine** | Устойчив к перестановкам слов | Сложнее; для длинных текстов | Описания, длинные поля |

Выбор зависит от типа поля и характера различий в данных. Для эталонных сущностей чаще используют Levenshtein или Jaro-Winkler для строк; точное совпадение — для кодов и числовых полей.

---

## 5.2.5. Нормализация перед fuzzy matching

Перед вычислением метрики строки нормализуют:

- **LOWER, TRIM** — обязательно
- **Удаление лишних пробелов** — REGEXP_REPLACE
- **Стандартизация аббревиатур** — «ООО» → «ооо», «ОАО» → «оао» (или убрать для сравнения)
- **Удаление знаков препинания** — точки, запятые, кавычки (по контексту)
- **Транслитерация** — привести «Ivanov» к «Иванов» при необходимости (отдельная задача)

Разная нормализация для разных полей: для наименования — сохранить «ООО»; для сравнения фонетического — Soundex/Metaphone.

## 5.2.6. Комбинированные правила сопоставления

Для решения «дубликат или нет» часто используют **комбинацию** критериев:

**Правило «И» (все должны выполниться):**
- ИНН совпадает (точное) **И** similarity(наименование) >= 0.8

**Правило «ИЛИ» (достаточно одного):**
- ИНН совпадает **ИЛИ** (similarity(наименование) >= 0.95 **И** similarity(адрес) >= 0.9)

**Взвешенная оценка:**
- score = 0.5 * (1 если ИНН совпадает иначе 0) + 0.3 * similarity(name) + 0.2 * similarity(address)
- дубликат, если score >= 0.85

**Каскад:**
1. Если ИНН совпадает — дубликат (с высокой уверенностью).
2. Иначе если similarity(name) >= 0.95 и similarity(inn_or_address) >= 0.9 — кандидат.
3. Иначе — не дубликат.

Комбинированные правила задаются в конфигурации; подбор весов и порогов — по тестовой выборке. См. [§5.1](chapter-05-01.md).

## 5.2.7. Фонетические алгоритмы (Soundex, Metaphone)

Для сопоставления по **звучанию** (транслитерация, разные написания) используют фонетические алгоритмы:

- **Soundex** — код из 4 символов по звучанию; «Иванов» и «Ivanov» дают близкие коды. Ограничен для русского языка; в английском распространён.
- **Metaphone** — улучшенный Soundex; Double Metaphone — два варианта кода для неоднозначностей.
- **Caverphone** — для имён; используется в демографии.

Применение: совпадение фонетических кодов — дополнительный критерий; «Иванов» = «Ivanov» по коду. Для кириллицы Soundex может потребовать адаптации; существуют реализации под русский. См. [§5.1](chapter-05-01.md).

## 5.2.8. Пример: сравнение в SQL (PostgreSQL)

PostgreSQL с модулем `fuzzystrmatch`:

```sql
-- Активация модуля
CREATE EXTENSION IF NOT EXISTS fuzzystrmatch;

-- Levenshtein distance
SELECT levenshtein('ООО Ромашка', 'Ромашка ООО');
-- Результат: 4 (операции для преобразования)

-- Нормализованное similarity (0-1)
SELECT 1.0 - levenshtein('ООО Ромашка', 'Ромашка ООО')::float 
       / GREATEST(length('ООО Ромашка'), length('Ромашка ООО'));

-- Jaro-Winkler (0-1)
SELECT jarowinkler('Иванов Иван', 'Иванов Иван Иванович');

-- Точное после нормализации
SELECT LOWER(TRIM('  ООО Ромашка  ')) = LOWER(TRIM('ООО Ромашка'));
```

В production сравнение обычно выполняется в ETL (Python, Java) или в процедурах; SQL удобен для прототипов и небольших объёмов. См. [§5.4](chapter-05-04.md).

## 5.2.9. Типичные ошибки

- **Сравнивать без нормализации:** «Москва» и «москва» — различаются при точном сравнении.
- **Использовать одну метрику для всех полей:** ИНН — только точное; наименование — fuzzy.
- **Игнорировать длину строки в Levenshtein:** короткие строки — одна опечатка сильно снижает similarity; для «Иван»/«Иванн» порог 0.9 не пройдёт.
- **Смешивать транслитерацию и кириллицу без преобразования:** «Ivanov» vs «Иванов» — нужна транслитерация или фонетический код.

---

## Ключевое

- **Точное совпадение** — после нормализации (LOWER, TRIM и т.д.); для кодов и уникальных идентификаторов.
- **Levenshtein** — число операций редактирования; similarity = 1 - distance/max_len; учитывает опечатки.
- **Jaro-Winkler** — для коротких строк и имён; бонус за совпадение префикса.
- **Нормализация** перед fuzzy — обязательно; по-разному для разных полей.
- **Комбинированные правила** — И/ИЛИ/взвешенная оценка; каскад по уверенности.
- **Фонетические алгоритмы** — Soundex, Metaphone для сопоставления по звучанию; ограниченно для кириллицы.
- **Выбор метрики** — по типу поля: коды — точное; наименования — Levenshtein или Jaro-Winkler; ФИО — Jaro-Winkler.

В [§5.3](chapter-05-03.md) мы разберём алгоритмы слияния: выбор «победителя» по полям, сохранение истории, обработка групп дубликатов.
