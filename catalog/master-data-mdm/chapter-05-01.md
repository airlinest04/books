# §5.1 Обнаружение дубликатов

В главе 4 мы разобрали золотую запись и слияние. Глава 5 посвящена **дедупликации** — процессу выявления и устранения дубликатов. В этом разделе рассмотрим **обнаружение дубликатов**: сопоставление по ключевым полям, нечёткое сравнение (fuzzy matching), пороги схожести и блокировку (blocking) для сокращения объёма сравнений. В [§5.2](chapter-05-02.md) разберём алгоритмы сравнения (Levenshtein, Jaro-Winkler); в [§5.3](chapter-05-03.md) — алгоритмы слияния; в [§5.4](chapter-05-04.md) — инструменты и SQL-паттерны.

---

## 5.1.1. Задача обнаружения дубликатов

**Обнаружение дубликатов** — идентификация записей, относящихся к одной и той же реальной сущности (клиент, контрагент, продукт), но представленных разными строками с разными ID или атрибутами. См. [§3.1](chapter-03-01.md).

Задача: по набору записей из одного или нескольких источников найти **пары или группы** записей, которые следует считать дубликатами и объединить в золотую запись. Сложность: при N записях полное попарное сравнение даёт O(N²) операций; при больших объёмах это неприемлемо. Нужны приёмы сокращения числа сравнений (блокировка) и эффективные критерии схожести (точное совпадение, fuzzy matching). См. [Глоссарий](glossary.md).

---

## 5.1.2. Сопоставление по ключевым полям

Самый надёжный способ — сопоставление по **уникальному идентификатору**, однозначно определяющему сущность:

| Сущность | Ключевое поле | Примечания |
|----------|---------------|------------|
| Контрагент (юрлицо) | ИНН | 10 цифр; уникален; верифицируется через ЕГРЮЛ |
| Контрагент (ИП) | ИНН | 12 цифр |
| Физлицо | СНИЛС, паспорт | При наличии; не всегда заполнены |
| Продукт | Внутренний SKU, штрихкод | При едином коде в источниках |
| Сотрудник | Табельный номер | В рамках организации |

Если ключевое поле заполнено и совпадает (с учётом нормализации) — записи с высокой вероятностью дубликаты. Запрос `GROUP BY key_field HAVING COUNT(*) > 1` выявляет группы кандидатов. См. [§3.1](chapter-03-01.md) (пример по ИНН).

Ограничения: ключ может отсутствовать (в CRM ИНН не ввели), содержать ошибки, быть разным в разных системах (внутренний код vs артикул поставщика). Тогда нужны дополнительные критерии: сопоставление по комбинации полей, fuzzy matching. См. [§5.2](chapter-05-02.md).

---

## 5.1.3. Комбинированные правила сопоставления

Когда единого ключа нет, используют **комбинацию атрибутов**:

- **Контрагент:** ИНН (если есть) ИЛИ (наименование + адрес) ИЛИ (наименование + телефон)
- **Физлицо:** (ФИО + дата рождения) ИЛИ (ФИО + адрес) ИЛИ (паспорт)
- **Продукт:** (код + наименование) ИЛИ (наименование + категория + бренд)

Правила задаются в виде: «считать дубликатами, если совпадает A и B» или «если совпадает A ИЛИ (B и C)». Важно: правила должны минимизировать ложноположительные (разные сущности признаны дубликатами) и ложноотрицательные (дубликаты не найдены). Точное совпадение по строке даёт мало ложноотрицательных при разных написаниях; fuzzy matching снижает ложноотрицательные, но увеличивает ложноположительные. См. [§5.2](chapter-05-02.md).

---

## 5.1.4. Fuzzy matching (нечёткое сравнение)

**Fuzzy matching** — сравнение строк с допуском незначительных различий: опечатки, разные форматы, сокращения. «ООО Ромашка» и «Ромашка ООО» при точном сравнении не совпадают; при нечётком — могут быть признаны схожими. См. [Глоссарий](glossary.md).

Метрики схожести (подробнее в [§5.2](chapter-05-02.md)):

- **Levenshtein distance** — минимальное число вставок, удалений и замен для преобразования одной строки в другую; нормализуется в коэффициент 0–1.
- **Jaro-Winkler** — учитывает совпадение символов и порядок; лучше для коротких строк и имён.
- **Cosine similarity** — для текстов; по N-граммам или токенам.
- **Soundex, Metaphone** — фонетическое сходство; «Иванов» и «Ivanov» дают близкие коды.

Результат — **число от 0 до 1** (или 0–100%): 1 — полное совпадение, 0 — полное различие. Выбор порога: выше порог — меньше ложноположительных, больше ложноотрицательных; ниже — наоборот. Типичные пороги: 0.85–0.95 для «вероятно дубликат»; 0.7–0.85 для «кандидат на ручную проверку». См. [§5.2](chapter-05-02.md).

---

## 5.1.5. Пороги схожести

**Порог схожести** — минимальное значение метрики, при котором пару записей считают дубликатами (или кандидатами). См. [Глоссарий](glossary.md).

Стратегии:

| Подход | Описание |
|--------|----------|
| **Жёсткий порог** | similarity >= 0.9 → дубликат; < 0.9 → нет. Просто, но граничные случаи |
| **Двухуровневый** | >= 0.95 → автоматически дубликат; 0.8–0.95 → на ручную проверку; < 0.8 → не дубликат |
| **По полям** | Для ИНН — только точное совпадение; для наименования — fuzzy с порогом 0.85 |
| **Взвешенная сумма** | Несколько полей; каждому — вес и порог; итоговая оценка — комбинация |

Пороги подбирают эмпирически на тестовой выборке; при изменении качества данных пересматривают.

---

## 5.1.6. Блокировка (blocking)

**Блокировка** (blocking) — приём сокращения числа пар для сравнения: сравнивать только записи, попавшие в один «блок» по некоторому признаку. Вместо N² сравнений — сумма по блокам (каждый блок обычно много меньше N). См. [Глоссарий](glossary.md).

Идея: дубликаты с высокой вероятностью имеют совпадающий или похожий **блокирующий ключ** (например, первые буквы наименования, хеш от нормализованного имени, почтовый индекс). Записи группируются по блокирующему ключу; сравнение выполняется только внутри каждой группы.

Примеры блокирующих ключей:

| Сущность | Блокирующий ключ | Примечания |
|----------|------------------|------------|
| Контрагент | Первые 4 цифры ИНН | Один ИНН — один блок; при отсутствии ИНН — fallback |
| Контрагент | Первые 3 буквы нормализованного названия | «Ромашка» → «ром»; «Ромашка ООО» → «ром» |
| Контрагент | Почтовый индекс + первые буквы названия | Адрес + название |
| Физлицо | Первые буквы фамилии + год рождения | |
| Продукт | Первые символы кода или категория | |

Риск блокировки: если блокирующий ключ у дубликатов различается (опечатка в первых буквах), пара не попадёт в один блок и не будет сравнена — ложноотрицательный результат. Поэтому используют **несколько блокирующих ключей** и объединяют кандидатов из всех блоков (с дедупликацией пар). См. [§5.4](chapter-05-04.md).

---

## 5.1.7. Полное попарное сравнение vs блокировка

| Подход | Сравнений | Точность | Применимость |
|--------|-----------|----------|--------------|
| **Полное попарное** | N*(N-1)/2 | Максимальная (все пары проверены) | Только малые объёмы (N < 10⁴) |
| **Блокировка по одному ключу** | Сумма по размерам блоков | Зависит от ключа; возможны пропуски | Средние объёмы |
| **Множественная блокировка** | Объединение блоков; дубли пар | Меньше пропусков | Рекомендуется при N > 10⁴ |

При N = 100 000 полное сравнение — ~5 млрд пар; при блокировке по первым 4 цифрам ИНН блоки по ~10–100 записей — порядка 10⁶–10⁷ сравнений. См. [§5.4](chapter-05-04.md).

---

## 5.1.8. Общий алгоритм обнаружения

1. **Нормализация:** привести поля к единому формату (trim, lower, убрать лишние пробелы, нормализовать телефон, ИНН).
2. **Точное сопоставление:** найти группы по уникальному ключу (ИНН и т.д.); такие группы — готовые кандидаты на слияние.
3. **Блокировка:** сгруппировать оставшиеся записи по блокирующему ключу.
4. **Попарное сравнение внутри блоков:** для каждой пары в блоке вычислить метрику схожести (по ключевым полям, с fuzzy matching).
5. **Порог:** пары с similarity >= порога — кандидаты на слияние; при двухуровневом пороге — часть на автоматическое слияние, часть на ручную проверку.
6. **Транзитивное замыкание:** если A–B дубликаты и B–C дубликаты, то A–B–C одна группа; объединить группы.

---

## 5.1.9. Типичные ошибки

- **Сравнивать без нормализации:** «ООО Ромашка» и «ооо ромашка» при точном сравнении не совпадут; нормализация (lower, trim) обязательна.
- **Использовать один блокирующий ключ:** при опечатке в нём дубликат пропустится; желательно несколько ключей.
- **Слишком низкий порог:** много ложноположительных; разные контрагенты будут слиты.
- **Слишком высокий порог:** много ложноотрицательных; дубликаты останутся.
- **Игнорировать транзитивное замыкание:** A–B и B–C — дубликаты, но A и C не сравнили; без замыкания получим две группы вместо одной.

---

## Ключевое

- **Обнаружение дубликатов** — поиск пар/групп записей об одной сущности; первый шаг перед слиянием.
- **Сопоставление по ключевым полям:** ИНН, СНИЛС, SKU — надёжно при наличии и корректности; GROUP BY для групп.
- **Fuzzy matching** — нечёткое сравнение строк; метрики Levenshtein, Jaro-Winkler; результат 0–1.
- **Пороги схожести:** выбор баланса ложноположительных/ложноотрицательных; типично 0.85–0.95; двухуровневый порог для ручной проверки.
- **Блокировка** — группировка по ключу для сокращения сравнений; несколько ключей снижают пропуски.
- **Алгоритм:** нормализация → точное сопоставление → блокировка → сравнение в блоках → порог → транзитивное замыкание.

В [§5.2](chapter-05-02.md) мы детально разберём сравнение и сопоставление: точное совпадение, Levenshtein, Jaro-Winkler, комбинированные правила.
