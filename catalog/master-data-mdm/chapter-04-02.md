# §4.2 Выбор «лучшего» значения

В [§4.1](chapter-04-01.md) мы определили золотую запись. При слиянии данных из нескольких источников возникает вопрос: **какое значение выбрать** для каждого атрибута, когда источники дают разные значения? В [§3.3](chapter-03-03.md) мы ввели приоритет источника и альтернативные критерии. В этом разделе детализируем правила выбора «лучшего» значения: приоритет источника, самое свежее, самое полное, обработку пустых значений и комбинированные правила. В [§4.3](chapter-04-03.md) разберём процесс слияния и стратегии merge по полям.

---

## 4.2.1. Задача выбора

При формировании золотой записи для каждого атрибута нужно получить **одно значение**. Если источник один и значение заполнено — берём его (после нормализации). Если источников несколько и значения совпадают (после нормализации) — любое. **Конфликт** — когда значения различаются; тогда требуется правило выбора. См. [§3.3](chapter-03-03.md).

Дополнительный случай: **пропуск** — в приоритетном источнике пусто, в других — заполнено. Правило: при пустом значении у источника с высшим приоритетом переходим к следующему в цепочке приоритетов, пока не найдём непустое значение.

---

## 4.2.2. Приоритет источника

**Приоритет источника** — основное правило: для каждого атрибута задаётся упорядоченный список источников (1-й, 2-й, 3-й приоритет и т.д.). При конфликте выбирается значение из источника с наивысшим приоритетом среди тех, кто дал непустое значение. См. [Глоссарий](glossary.md).

Пример для контрагента:

| Атрибут | 1 | 2 | 3 |
|---------|---|---|---|
| name | ERP | CRM | Биллинг |
| inn | ERP | — | — |
| legal_address | ERP | CRM | — |
| phone | CRM | ERP | — |
| email | CRM | ERP | — |
| bank_details | ERP | Биллинг | — |

Обоснование задаётся бизнесом: ERP — владелец реквизитов для документов; CRM — контактов; логистика — адресов доставки. Матрица приоритетов — часть конфигурации ETL/MDM; при смене источников или процессов матрицу пересматривают.

---

## 4.2.3. Самое свежее (по дате изменения)

**Критерий «самое свежее»:** при конфликте выбирать значение с наиболее поздней датой обновления (`updated_at`, `modified_date`). Источник: тот, в котором запись была изменена позже всего. См. [§3.3](chapter-03-03.md).

Применимо когда:

- Актуальность важнее «авторитетности» источника.
- Несколько систем могут корректно обновлять атрибут; последнее изменение скорее отражает текущее состояние.

Ограничения:

- Не все источники хранят дату изменения; при её отсутствии критерий не применим.
- Ошибочная недавняя правка перекроет корректное старое значение.
- Часовые пояса и разные системы времени — нужна нормализация.

Использование: как основной критерий для части атрибутов (например, контакты) или как дополнение к приоритету при равном приоритете.

---

## 4.2.4. Самое полное

**Критерий «самое полное»:** при конфликте выбирать более детализированное или длинное значение. Например, «Москва, ул. Ленина, д. 5, офис 10» предпочтительнее «Ленина, 5». См. [§3.3](chapter-03-03.md).

Варианты:

- **По длине строки:** `LEN(value)` — больше значит полнее. Риск: мусор, повторы.
- **По наличию подполей:** для адреса — больше заполненных частей (индекс, город, улица, дом, офис). Риск: разная структура в источниках.
- **По списку обязательных элементов:** адрес «полный», если есть город, улица, дом. Сложнее формализовать.

Использование: как дополнение при равном приоритете или для атрибутов, где детализация важна (адрес, описание).

---

## 4.2.5. Обработка пустых значений

Пустое значение (NULL, пустая строка, пробелы) **не участвует** в выборе при конфликте: источник с пустым значением пропускается, переходим к следующему по приоритету.

Правила:

- **Цепочка приоритетов:** если источник 1 дал пустое — берём из источника 2; если и там пусто — из 3 и т.д.
- **Все пусты:** если все источники дали пустое — в золотую запись пишем NULL (или значение по умолчанию, если задано).
- **Нормализация пустоты:** `''`, `' '`, `NULL` — трактуем единообразно как «пусто» при сравнении.

---

## 4.2.6. Комбинированные правила

На практике правила комбинируют:

1. **Приоритет источника** — основной критерий для большинства атрибутов.
2. **При равном приоритете** (несколько записей из одного источника после дедупликации) — по дате изменения или по полноте.
3. **Пустые значения** — переход к следующему в цепочке приоритетов.
4. **По атрибутам** — разные критерии для разных полей: для `inn` — только ERP (регуляторные данные); для `phone` — CRM или самое свежее.

Пример комбинированного правила для `legal_address`:

```
1. Если ERP дал непустое — взять из ERP.
2. Иначе если CRM дал непустое — взять из CRM.
3. Иначе NULL.
4. При нескольких непустых из ERP (редко) — взять с максимальной датой updated_at.
```

---

## 4.2.7. Разделение атрибутов при семантическом конфликте

Когда «один» атрибут в разных источниках имеет **разный смысл** (семантический конфликт), правильнее **разделить** атрибуты, а не выбирать одно значение. См. [§3.3](chapter-03-03.md).

Пример: «адрес» в CRM — контактный/юридический; в логистике — адрес доставки. Решение: в золотой записи — два поля: `address_legal` и `address_delivery`. Для каждого — свой приоритет источников. Конфликта нет: разные атрибуты.

Аналогично: `phone_main` и `phone_secondary`; `contact_person` (для документов) и `contact_person` (для доставки). Модель данных должна отражать семантику.

---

## 4.2.8. Реализация в коде и конфигурации

Правила выбора можно задавать:

- **В коде ETL:** условная логика (CASE, COALESCE с приоритетом по полям).
- **В конфигурации:** таблица или JSON с матрицей «атрибут → список источников по приоритету»; универсальный алгоритм читает конфиг и применяет.
- **В MDM-платформе:** настройки правил слияния в интерфейсе (если используется MDM-инструмент).

Пример псевдокода:

```
for each attribute A in golden_record_schema:
    values = collect from all sources for A (non-empty)
    if values is empty: golden[A] = NULL
    else if len(values) == 1: golden[A] = values[0]
    else:
        sort values by priority[source] (ascending, 1=highest)
        golden[A] = values[0]  # highest priority
        # or: by max(updated_at) if tied
```

Документирование правил обязательно; при изменении — версионирование конфигурации. См. [§3.3](chapter-03-03.md), [§12.1](chapter-12-01.md).

---

## 4.2.9. Типичные ошибки

- **Один приоритет для всех атрибутов:** для реквизитов — ERP, для контактов — CRM; универсальное «ERP всегда первый» даст устаревшие контакты.
- **Не обрабатывать пустые:** при пустом в приоритетном источнике нужно брать из следующего; иначе теряем данные.
- **Смешивать семантику:** «адрес» из CRM и логистики — разные сущности; разделять поля.
- **Не документировать:** через полгода никто не помнит, почему выбран тот или иной приоритет; при инциденте — сложно разобраться.

---

## Ключевое

- **Выбор «лучшего» значения** — по правилам: приоритет источника, самое свежее, самое полное; при пустом — переход к следующему в цепочке.
- **Приоритет источника** — основной критерий; матрица «атрибут → источники по приоритету»; задаётся бизнесом.
- **Самое свежее** — по дате изменения; для атрибутов, где важна актуальность.
- **Самое полное** — более детализированное значение; осторожно с мусором.
- **Пустые значения** — не участвуют в конфликте; переход к следующему приоритету.
- **Семантический конфликт** — разделять атрибуты (address_legal, address_delivery), а не выбирать одно.
- **Комбинированные правила** — приоритет + дата/полнота при равенстве; разные правила по атрибутам.

В [§4.3](chapter-04-03.md) мы разберём слияние данных из нескольких источников: merge по полям, стратегии слияния, сохранение истории.
