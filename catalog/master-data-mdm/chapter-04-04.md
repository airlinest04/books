# §4.4 Версионирование и история

В [§4.1](chapter-04-01.md)–[§4.3](chapter-04-03.md) мы разобрали золотую запись, выбор «лучшего» значения и слияние. Завершая главу 4, рассмотрим **версионирование и историю** эталонных данных: зачем хранить историю изменений, приёмы SCD (Slowly Changing Dimensions), эффективные даты и аудит. Эталонные сущности меняются во времени; без версионирования исторические отчёты искажаются. Подробнее типы SCD и реализация — в книге «Проектирование и архитектура хранилищ данных», глава 5; здесь — контекст MDM и связь с золотой записью. В [§5.1](chapter-05-01.md) начнём главу 5 — дедупликация.

---

## 4.4.1. Зачем версионировать эталонные данные

Эталонные сущности **меняются** во времени: клиент сменил адрес, продукт переименован или переведён в другую категорию, контрагент сменил реквизиты. Если при изменении просто **перезаписывать** текущую запись, теряется история: отчёт «продажи по клиентам за 2023 год» при джойне с измерением покажет текущий адрес клиента, а не тот, что был в 2023-м. См. [§1.4](chapter-01-04.md).

**Версионирование** сохраняет историю: при изменении атрибута старая версия остаётся, добавляется новая; каждая версия имеет период действия (effective_from, effective_to). Факт (продажа) ссылается на версию эталона, актуальную на дату факта. Исторические отчёты становятся корректными. См. [§10.4](chapter-10-04.md).

---

## 4.4.2. SCD: типы и суть

**SCD** (Slowly Changing Dimensions, медленно меняющиеся измерения) — приёмы хранения истории изменений атрибутов измерений. В контексте MDM эталонные данные, загружаемые в DWH как измерения, подчиняются тем же правилам. См. [Глоссарий](glossary.md).

Кратко по типам:

| Тип | Поведение при изменении | Плюсы | Минусы |
|-----|-------------------------|-------|--------|
| **Type 1** | Перезапись; история теряется | Простота | Исторические отчёты неверны |
| **Type 2** | Добавление новой строки с effective_from/to; факт ссылается на суррогатный ключ версии | Корректная история | Рост таблицы; сложнее запросы |
| **Type 3** | Отдельная колонка «старое значение»; хранится только одно предыдущее | Частичная история | Только одно изменение назад |
| **Type 6** | Комбинация 1, 2, 3 для разных атрибутов | Гибкость | Сложность реализации |

Для эталонных данных в аналитике **Type 2** — наиболее распространённый: полная история, факт привязан к версии на дату события. Подробнее типы SCD, структура таблиц и ETL — в книге по DWH, [§5.1](../dwh/chapter-05-01.md)–[§5.4](../dwh/chapter-05-04.md). См. [§10.4](chapter-10-04.md).

---

## 4.4.3. Type 2: effective_from и effective_to

При **SCD Type 2** для каждой версии записи хранятся:

- `effective_from` — дата начала действия версии
- `effective_to` — дата окончания (NULL или максимальная дата для текущей версии)
- `is_current` — флаг текущей версии (1/0)
- Суррогатный ключ версии — уникальный для каждой строки (customer_sk, product_sk)

При изменении атрибута:

1. Закрыть текущую версию: `effective_to = дата_изменения`, `is_current = 0`
2. Добавить новую строку: `effective_from = дата_изменения`, `effective_to = NULL` (или 9999-12-31), `is_current = 1`, новые значения атрибутов
3. Новые факты ссылаются на суррогатный ключ новой версии; старые факты остаются привязаны к старым версиям

Факт хранит суррогатный ключ версии измерения на дату события; при джойне факт автоматически получает атрибуты, актуальные на момент события. См. книга по DWH, [§5.3](../dwh/chapter-05-03.md), [§5.4](../dwh/chapter-05-04.md).

## 4.4.4. Версионирование в MDM-слое

Вопрос: где хранить историю — в MDM-слое (Core эталонов) или только при загрузке в DWH (в измерении)?

**Варианты:**

1. **MDM хранит только текущее состояние:** золотая запись — одна строка на сущность; история строится в DWH при загрузке в измерение (ETL применяет SCD Type 2). MDM проще; логика версий — в ETL.
2. **MDM хранит историю:** в Core эталонов — версионированные записи с effective_from/to; при загрузке в DWH копируем как есть. Полная история в одном месте; но MDM усложняется.
3. **Гибрид:** MDM хранит текущее + дату последнего обновления; ETL при загрузке сравнивает с предыдущим снимком и при изменении создаёт новую версию в измерении.

Выбор зависит от архитектуры: если MDM — отдельная система и DWH — главный потребитель, часто достаточно текущего снимка в MDM и SCD в ETL при загрузке измерений. Если MDM и DWH объединены (один слой Core), версионирование может быть в Core. См. [§8.1](chapter-08-01.md), [§10.1](chapter-10-01.md).

## 4.4.5. Аудит изменений

**Аудит** — фиксация того, кто, когда и что изменил в эталонных данных. Полезен для:

- Расследования инцидентов (кто испортил данные)
- Соответствия регуляторике (кто имел доступ, что менял)
- Отладки процесса слияния (откуда пришло значение, когда обновлено)

Типичные поля аудита:

- `created_at`, `created_by` — создание записи
- `updated_at`, `updated_by` — последнее обновление
- `source_system`, `source_id` — происхождение
- При версионировании — `effective_from`, `effective_to`; дополнительно — причина изменения (change_reason), если фиксируется

Аудит может храниться в тех же таблицах (поля created_at, updated_at) или в отдельной таблице истории изменений (audit log). См. [§4.3](chapter-04-03.md) (история слияния).

## 4.4.6. Запросы «на дату»

При версионировании (Type 2) типичные сценарии:

- **Текущее состояние:** `WHERE is_current = 1` (или `effective_to IS NULL`)
- **Состояние на дату:** `WHERE effective_from <= @as_of_date AND (effective_to IS NULL OR effective_to > @as_of_date)`
- **Исторический отчёт по фактам:** факт уже хранит суррогатный ключ версии на дату события; JOIN по этому ключу даёт корректные атрибуты без дополнительного фильтра

Для отчёта «продажи за 2023 год с категориями продуктов на момент продажи» — факты за 2023 + JOIN с измерением продукта по product_sk; версия product_sk в факте уже привязана к категории на дату продажи. См. книга по DWH, [§5.4](../dwh/chapter-05-04.md).

## 4.4.8. Типичные ошибки

- **Фильтровать по is_current=1 в историческом отчёте по фактам:** тогда все факты получат текущую версию атрибутов; отчёт «продажи за прошлый год по категориям» будет неверен. Для фактов — JOIN по суррогатному ключу без фильтра is_current.
- **Не закрывать предыдущую версию при Type 2:** при добавлении новой версии старая должна получить effective_to; иначе перекрытие периодов и неоднозначность.
- **Путать дату факта и дату среза измерения:** «факты за январь» и «измерение на 31.12» — разные вещи; для исторического отчёта по фактам нужна версия на дату каждого факта.
- **Игнорировать аудит:** при проблемах с качеством данных невозможно выяснить источник изменения без аудита.

## Ключевое

- **Версионирование** нужно для корректности исторических отчётов: атрибуты эталона на дату факта, а не текущие.
- **SCD Type 2** — добавление новой строки при изменении; effective_from, effective_to, is_current; факт ссылается на суррогатный ключ версии.
- **MDM vs DWH:** история может храниться в MDM или строиться в ETL при загрузке измерений; выбор по архитектуре.
- **Аудит:** created_at, updated_at, created_by, updated_by; отдельный audit log при необходимости.
- **Запрос «на дату»:** effective_from <= date AND (effective_to IS NULL OR effective_to > date).
- **Связь с DWH:** детали SCD — в книге по DWH, глава 5; здесь — контекст эталонных данных.

В [§5.1](chapter-05-01.md) мы начнём главу 5 — дедупликация: обнаружение дубликатов, сопоставление по ключевым полям, fuzzy matching.
