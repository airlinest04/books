# §11.4 Качество эталонных данных

В [§11.3](chapter-11-03.md) мы разобрали дедупликацию в пайплайне. Эталонные данные, формирующие золотую запись и измерения, должны удовлетворять требованиям качества — иначе ошибки размножатся во всех витринах и отчётах. В этом разделе рассмотрим **качество эталонных данных**: какие проверки применять (полнота, уникальность, точность, валидность), где в пайплайне их выполнять и как связать с общей практикой качества данных. Подробности измерений, правил и проверок — в книге «Качество данных»; здесь — привязка к MDM и пайплайну эталонов. В [§12.1](chapter-12-01.md) начнём практическую главу: полный пайплайн эталонных данных.

---

## 11.4.1. Зачем проверять качество эталонов

Эталонные данные — основа измерений DWH и обогащения транзакций. Любой дефект в эталоне (дубликат, неполная запись, неверное значение) отражается во всех потребителях: витрины, отчёты, Lookup при загрузке фактов. См. [§1.4](chapter-01-04.md), [§10.3](chapter-10-03.md).

Типичные последствия дефектов эталонов:

| Дефект | Последствие |
|--------|-------------|
| Дубликат в Core | Двойной учёт при агрегации; неоднозначность при джойне с фактами. |
| Пустое обязательное поле (название клиента, ИНН) | Сироты, пустые измерения, искажение аналитики «по клиентам». |
| Невалидное значение (код региона не из справочника) | Ошибки FK, несовпадение с классификаторами. |
| Устаревшие данные | Обогащение фактов устаревшими атрибутами. |

Проверки качества эталонов встраивают в пайплайн: до загрузки в Core (Staging), после загрузки в Core и перед распространением в Mart. См. [§10.1](chapter-10-01.md).

## 11.4.2. Полнота эталонных данных

**Полнота** (Completeness) — степень, в которой обязательные поля заполнены; отсутствуют null или пустые строки там, где они недопустимы. См. книга «Качество данных» [§2.1 Полнота](../data-quality/chapter-02-01.md).

Для эталонов обязательные поля зависят от сущности:

- **Контрагент:** ИНН (для юрлиц), наименование; при обогащении — адрес, регион.
- **Клиент (физлицо):** ФИО или идентификатор; контакт — при необходимости.
- **Продукт:** код (SKU/артикул), наименование; категория — при иерархии.
- **Справочник:** код и наименование; родитель — при иерархии.

Проверка в SQL (пример — контрагенты):

```sql
-- Записи с пустым обязательным полем
SELECT source_system, source_id, inn, name
FROM staging.counterparties
WHERE load_date = CURRENT_DATE
  AND (inn IS NULL OR inn = '' OR name IS NULL OR TRIM(name) = '');
```

Метрика: доля записей с заполненными обязательными полями; при падении ниже порога — алерт. Неполные записи можно отклонять (кварантин) или загружать с пометкой для последующего исправления. См. [§7.1 Отклонение vs исправление](../data-quality/chapter-07-01.md), [§7.2 Кварантин](../data-quality/chapter-07-02.md).

## 11.4.3. Уникальность эталонных данных

**Уникальность** (Uniqueness) — отсутствие дубликатов по ключу в пределах области (таблица, партиция). Для эталонов проверяют:

1. **В Staging (до дедупликации):** дубликаты допустимы — их выявляет дедупликация; проверяют скорее повторный срез (нет ли дублей по (source_system, source_id) в одной загрузке).
2. **В Core (после дедупликации и слияния):** по бизнес-ключу (ИНН, golden_id) — строго одна запись; дубликаты недопустимы.
3. **В Mart (измерения):** одна актуальная запись на сущность (или одна версия по SCD Type 2). См. [§10.4](chapter-10-04.md).

Проверка уникальности в Core:

```sql
-- Дубликаты по ИНН в Core
SELECT inn, COUNT(*) AS cnt
FROM core.counterparty
WHERE is_current = true
GROUP BY inn
HAVING COUNT(*) > 1;
```

При инкрементальной загрузке — проверять уникальность в рамках батча и при слиянии с уже загруженными данными. См. [§5.1](chapter-05-01.md), [§11.3](chapter-11-03.md), книга «Качество данных» [§2.5 Уникальность](../data-quality/chapter-02-05.md).

## 11.4.4. Точность, валидность, согласованность

Помимо полноты и уникальности, для эталонов важны:

- **Точность (Accuracy):** значения соответствуют реальности (корректный ИНН, адрес). Проверяется сопоставлением с внешними источниками, форматами (ИНН 10/12 цифр, ОГРН 13/15). См. [§2.2 Точность](../data-quality/chapter-02-02.md).
- **Валидность (Validity):** значения в допустимом диапазоне и формате; ссылки на справочники (код региона, валюта, единица измерения). NOT IN справочника — дефект. См. [§2.6 Валидность](../data-quality/chapter-02-06.md).
- **Согласованность (Consistency):** одинаковые правила кодирования; ссылочная целостность (клиент есть в Core, регион — в справочнике регионов). См. [§2.3 Согласованность](../data-quality/chapter-02-03.md).

Пример проверки валидности кода региона:

```sql
-- Контрагенты с кодом региона не из справочника
SELECT c.source_id, c.region_code
FROM staging.counterparties c
LEFT JOIN ref.regions r ON r.code = c.region_code
WHERE c.load_date = CURRENT_DATE
  AND c.region_code IS NOT NULL
  AND r.code IS NULL;
```

## 11.4.5. Проверки в пайплайне эталонов

| Этап | Что проверять |
|------|---------------|
| После загрузки в Staging | Полнота обязательных полей; валидность кодов (справочники); повторный срез (source_system, source_id) в батче. |
| После дедупликации и слияния | Уникальность по бизнес-ключу в Core; полнота золотой записи; целостность маппинга (все source_id из группы → один golden_id). |
| Перед/после загрузки в Mart | Уникальность измерения; отсутствие сирот (факты ссылаются только на существующие ключи); контрольные суммы при сверке. |

Проверки можно реализовать в том же ETL (SQL, Informatica, dbt) или выделить в отдельные задания; при провале — отклонение батча, кварантин, алерт. См. книга «Качество данных» [§5.2 Проверки при преобразовании](../data-quality/chapter-05-02.md), [§5.3 Проверки при загрузке](../data-quality/chapter-05-03.md), [§8.2 Raw, Staging, Core, Mart](../data-quality/chapter-08-02.md).

## 11.4.6. Связь с книгой по качеству данных

Полный разбор измерений качества, правил валидации, проверок в ETL и метрик — в книге «Качество данных» серии:

- **Измерения:** полнота, точность, согласованность, своевременность, уникальность, валидность — [глава 2](../data-quality/README.md#глава-2-измерения-качества-data-quality-dimensions).
- **Правила:** на уровне поля, записи, таблицы — [глава 4](../data-quality/README.md#глава-4-правила-валидации).
- **Проверки в ETL:** извлечение, преобразование, загрузка — [глава 5](../data-quality/README.md#глава-5-проверки-в-пайплайне-etl).
- **Качество по слоям DWH:** Raw, Staging, Core, Mart — [глава 8](../data-quality/README.md#глава-8-качество-данных-в-dwh).

Для MDM применяют те же принципы: эталонный слой (Staging, Core, Mart) — частный случай слоёв DWH; проверки эталонов — подмножество общих проверок качества с акцентом на полноту, уникальность и согласованность золотой записи.

---

## Ключевое

- **Зачем:** дефекты эталонов размножаются во всех витринах и при обогащении; проверки обязательны.
- **Полнота:** обязательные поля заполнены (ИНН, наименование, код и т.д.); null/пустые — недопустимы; метрика — доля заполненных.
- **Уникальность:** в Core — строго одна запись на бизнес-ключ; дубликаты проверять после дедупликации.
- **Точность, валидность, согласованность:** корректные форматы; ссылки на справочники; целостность связей.
- **Где проверять:** Staging (полнота, валидность), Core (уникальность, полнота золотой записи), Mart (сироты, контрольные суммы).
- **Книга «Качество данных»:** измерения, правила, проверки в ETL, качество по слоям — полный контекст.

В [§12.1](chapter-12-01.md) начнём практическую главу: постановка задачи полного пайплайна эталонных данных (загрузка, дедупликация, золотая запись, распространение в витрины).
