# §11.3 Дедупликация в пайплайне

В [§11.1](chapter-11-01.md) и [§11.2](chapter-11-02.md) мы разобрали обогащение транзакций. В этом разделе рассмотрим **дедупликацию в пайплайне**: когда выполнять дедупликацию (при загрузке эталона), в каком месте ETL и какие алгоритмы применять. Подробности обнаружения дубликатов, сравнения и слияния — в главе 5; здесь — привязка к пайплайну и ETL. В [§11.4](chapter-11-04.md) разберём качество эталонных данных.

---

## 11.3.1. Когда дедуплицировать

**Дедупликация** выполняется **при загрузке эталонных данных**, до формирования золотой записи в Core. См. [§8.2](chapter-08-02.md), [§5.1](chapter-05-01.md).

Типичный пайплайн:

```
Источники → Raw → Staging (очистка, единая структура) → Дедупликация → Слияние → Core (золотая запись) → Mart (измерения)
```

Дедупликация — между Staging и Core. Данные из всех источников уже в Staging в единой структуре; дедупликация находит группы записей-кандидатов; слияние формирует одну золотую запись на группу. См. [§10.1](chapter-10-01.md).

**Не** дедуплицировать транзакции: транзакции (продажи, платежи) — уникальные события; дубликаты среди них — отдельная задача (повторы загрузки, идемпотентность). Дедупликация эталонов — про сущности (клиенты, продукты, контрагенты). См. [§1.1](chapter-01-01.md).

---

## 11.3.2. Место в пайплайне

| Этап | Действие |
|------|----------|
| Staging | Очистка, нормализация, source_system, source_id |
| После Staging | Дедупликация: обнаружение групп по ключу или fuzzy matching |
| После дедупликации | Слияние: выбор «лучшего» значения по полям, формирование золотой записи |
| Core | Загрузка золотой записи и маппинга |
| Mart | Измерения из Core (без дедупликации — Core уже дедуплицирован) |

Дедупликация и слияние могут быть реализованы в одном ETL-задании (SQL, Python, Informatica) или в цепочке: задание 1 — Staging → дедупликация (группы); задание 2 — слияние групп → Core. См. [§8.2](chapter-08-02.md), [§12.3](chapter-12-03.md).

---

## 11.3.3. Алгоритмы в ETL

**Сопоставление по ключу (GROUP BY):** при наличии надёжного ключа (ИНН, SKU) группировка по ключу даёт кандидатов на слияние. SQL: `GROUP BY key HAVING COUNT(*) > 1`. Подходит для контрагентов по ИНН, продуктов по внутреннему коду. См. [§5.1](chapter-05-01.md), [§5.4](chapter-05-04.md).

**Оконные функции для выбора «победителя»:** в каждой группе ROW_NUMBER по приоритету (источник, дата); оставить строки с rn=1. Merge по записи — одна запись из группы. См. [§5.4](chapter-05-04.md), [§4.3](chapter-04-03.md).

**Merge по полям:** для каждого атрибута — MAX/MIN KEEP (Oracle) или подзапросы с ROW_NUMBER по приоритету. В Python/pandas — группировка и агрегация с custom function; в Informatica — несколько Lookup или Expression. См. [§4.2](chapter-04-02.md), [§5.3](chapter-05-03.md).

**Fuzzy matching:** при отсутствии ключа — сравнение строк (Levenshtein, Jaro-Winkler); в PostgreSQL — fuzzystrmatch; в Python — rapidfuzz, jellyfish; в ETL-инструментах — специализированные функции. Блокировка (blocking) — перед fuzzy matching: сравнивать только записи в одном блоке. См. [§5.1](chapter-05-01.md), [§5.2](chapter-05-02.md).

## 11.3.4. Реализация в SQL

Дедупликация по ИНН — целиком в SQL:

```sql
-- Группы дубликатов
WITH groups AS (
    SELECT inn, array_agg((source_system, source_id, name, phone, ...)) AS recs
    FROM staging_counterparties
    WHERE inn IS NOT NULL
    GROUP BY inn
),
-- Выбор одной записи на группу (упрощённо — по приоритету)
ranked AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY inn ORDER BY 
        CASE source_system WHEN 'ERP' THEN 1 WHEN 'CRM' THEN 2 ELSE 3 END,
        updated_at DESC NULLS LAST) AS rn
    FROM staging_counterparties
)
INSERT INTO core.counterparty (golden_id, inn, name, ...)
SELECT nextval('golden_seq'), inn, name, ...
FROM ranked WHERE rn = 1;
```

Маппинг — отдельный INSERT из всех строк ranked (не только rn=1) с соответствующим golden_id. Merge по полям из разных записей группы — более сложный запрос или несколько шагов. См. [§5.4](chapter-05-04.md), [§5.3](chapter-05-03.md).

## 11.3.5. Реализация в Python

При сложной логике (fuzzy matching, блокировка, merge по полям с разными приоритетами) удобно вынести дедупликацию в скрипт:

1. Загрузить Staging в DataFrame.
2. Блокировка: разбить на блоки по производному ключу.
3. В каждом блоке — попарное сравнение или группировка по хешу нормализованной строки.
4. Fuzzy matching (rapidfuzz) для кандидатов; порог схожести.
5. Формирование групп; для каждой группы — merge по правилам (pandas groupby + agg с custom).
6. Выгрузка золотых записей в Core; маппинг — в отдельную таблицу.

См. [§5.1](chapter-05-01.md), [§5.2](chapter-05-02.md), книга «Python для анализа данных».

## 11.3.6. Интеграция с Informatica, dbt

**Informatica:** Source — Staging; далее — Expression (нормализация), Aggregator для группировки; Router или Filter для отбора «победителей»; Lookup для merge по полям при необходимости. Fuzzy matching — через механизмы PowerCenter (если есть) или вызов внешнего скрипта. См. книга «Informatica», главы 5–8.

**dbt:** SQL-модели; staging → intermediate (группы, ranked) → core (золотая запись). Всё в SQL; fuzzy matching — через макрос с UDF или вызов Python (dbt Python model). См. [§5.4](chapter-05-04.md).

**Datagram, Talend и др.:** аналоги — группировка, сортировка, условная маршрутизация; при сложном merge — Custom/User-defined component или вызов внешнего скрипта.

## 11.3.7. Инкрементальная дедупликация

При инкрементальной загрузке эталонов не пересчитывать все группы, а обрабатывать только **затронутые** сущности: новые записи из источников, изменённые записи. См. [§10.2](chapter-10-02.md).

Логика:

- Новая запись (source_id нет в маппинге): попытаться сопоставить с существующими золотыми (по ключу, fuzzy); при совпадении — добавить в группу, пересчитать слияние; при отсутствии — новая золотая запись.
- Изменённая запись (source_id есть в маппинге): обновить золотую запись по правилам merge с учётом новых данных.

Полная перезагрузка — при смене правил дедупликации или при обнаружении ошибок. См. [§5.3](chapter-05-03.md).

---

## 11.3.8. Типичные ошибки

- **Дедуплицировать после загрузки в Core:** дубликаты уже попали в Core и измерения; дедупликация должна быть до Core.
- **Пропустить маппинг:** после слияния группа даёт одну золотую запись; каждый source_id из группы должен маппиться на golden_id.
- **Fuzzy matching без блокировки:** попарное сравнение всех записей — O(N²); при больших объёмах неприемлемо.
- **Неидемпотентность:** повторная загрузка тех же данных не должна создавать дубликаты золотых или двойной маппинг. См. [§10.2](chapter-10-02.md).

---

## Ключевое

- **Когда:** при загрузке эталона, между Staging и Core; не для транзакций.
- **Место:** после Staging (очистка, единая структура); перед загрузкой в Core.
- **Алгоритмы:** сопоставление по ключу (GROUP BY), оконные функции (ROW_NUMBER), merge по полям; fuzzy matching при отсутствии ключа; блокировка перед fuzzy.
- **Реализация:** SQL (GROUP BY, оконные функции), Python (pandas, rapidfuzz), ETL-инструменты (Informatica, dbt).
- **Инкрементальная дедупликация:** обрабатывать только новые/изменённые записи; полная перезагрузка при смене правил.

В [§11.4](chapter-11-04.md) разберём качество эталонных данных: проверки, полнота, уникальность.
