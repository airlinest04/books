# §1.3 Экосистема Arenadata

В [§1.2](chapter-01-02.md) мы зафиксировали, что Arenadata DB собирается на базе Greengage и поставляется как коммерческий дистрибутив с дополнительными инструментами. В этом разделе мы даём **обзор экосистемы Arenadata**: три ключевых компонента — **Arenadata Cluster Manager (ADCM)**, **Arenadata DB Control** и **Arenadata DB Backup Manager (ADBM)** — их назначение и место в жизненном цикле кластера ADB, а также дополнительные инструменты, интеграции и документация. Детальное описание установки, настройки и работы с каждым компонентом приведено в главах 2–6; здесь читатель получит общую карту «что за что отвечает» и как компоненты связаны между собой. См. [Глоссарий](glossary.md).

---

## 1.3.1. Arenadata Cluster Manager (ADCM)

**Arenadata Cluster Manager (ADCM)** — универсальный оркестратор для развёртывания и управления data-сервисами. По [документации ADCM](https://docs.arenadata.io/ru/ADCM/current/introduction/intro.html), система обеспечивает эффективный способ развёртывания и управления всеми data-сервисами компании **независимо от инфраструктуры** — в облаке, локально или в виде PaaS. Разделение на два уровня (инфраструктура и приложения) делает эксплуатацию предсказуемой, гибкой и воспроизводимой. По [странице продукта](https://arenadata.tech/products/arenadata-cluster-manager/), ADCM — инструмент для **установки, настройки и обновления** всех продуктов платформы Arenadata с удобным графическим интерфейсом; продукт доступен под **Apache License 2.0** (открытый исходный код). См. [Глоссарий](glossary.md).

В контексте Arenadata DB ADCM используется для:

- **Развёртывания кластера ADB:** загрузка бандла (архива с конфигурациями и Ansible-скриптами), создание кластера в веб-интерфейсе, добавление хостов, распределение компонентов (координатор, сегменты), настройка сервисов и запуск установки. Это заменяет ручную установку «ванильного» Greenplum/Greengage по шагам документации.
- **Управления кластером:** обновление (upgrade), расширение кластера (добавление сегментов), мониторинг состояния, настройка уведомлений и пороговых значений. Метрики и логи собираются связкой Graphite + Grafana + Diamond (по материалам Arenadata).
- **Единой точки входа:** из одного интерфейса можно управлять несколькими кластерами и продуктами Arenadata (Arenadata DB, Arenadata Hadoop, Arenadata QuickMarts, Arenadata Postgres, Arenadata Streaming и др.), а при необходимости — подключать сторонние сервисы через открытый формат бандлов и REST API.

ADCM поставляется в виде Docker-контейнера; документация на русском и английском языках доступна на [docs.arenadata.io](https://docs.arenadata.io/ru/ADCM/current/introduction/intro.html). Подробнее развёртывание кластера ADB с помощью ADCM разобрано в [главе 3](chapter-03-01.md).

## 1.3.2. Arenadata DB Control (ADB Control)

**Arenadata DB Control (ADB Control)** — система **мониторинга запросов** Arenadata DB в режиме реального времени. По [документации ADB Control](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/overview.html), это «командный центр» для отслеживания выполнения запросов, оценки загруженности кластера, анализа планов запросов и метрик по ресурсам, аудита доступа к данным и административных задач. ADB Control доступен в редакции **ADB Enterprise**; установка — только **offline** (в составе офлайн-установки кластера ADB).

Основные возможности (по официальному обзору):

| Возможность | Описание |
|-------------|----------|
| Работа с несколькими кластерами | Подключение и мониторинг нескольких кластеров ADB из одного интерфейса. |
| Мониторинг запросов и транзакций | Просмотр SQL-запросов и транзакций в реальном времени, включая внутренние запросы (inner query). |
| Сессии | Мониторинг клиентских сессий (активных и неактивных), прерывание сессий при необходимости. |
| Ресурсы | Сбор информации о потреблении системных ресурсов на уровне запросов и транзакций; сводная статистика и графики за выбранный период. |
| Управление выполнением | Отмена выполняющихся транзакций; построение планов запросов с отслеживанием прогресса. |
| Выгрузка метрик | Offload собираемых метрик во внешнюю аналитическую БД (PostgreSQL/ADB). |
| Аудит | Аудит обращений к таблицам ADB, авторизаций и других действий пользователей в ADB Control. |

Архитектура ADB Control включает: **Agent** (на каждом хосте кластера, приём и фильтрация метрик с координатора и сегментов), **Service Registry** (обнаружение сервисов и агентов), **Backend Server** (обработка и агрегация метрик, запись в Query DB и Metrics DB), **Scheduler** (очистка старых данных, offload, актуализация статусов), **Query DB** (PostgreSQL — логи запросов, транзакций, аудит, настройки), **Metrics DB** (ClickHouse — системные метрики). Для корректной работы планировщика и метрик рекомендуется синхронизация времени на хостах (например, Chrony). Подробнее мониторинг и управление запросами — в [главе 4](chapter-04-01.md).

## 1.3.3. Arenadata DB Backup Manager (ADBM)

**Arenadata DB Backup Manager (ADBM)** — отказоустойчивая система для управления **бинарными резервными копиями** ADB. По [документации ADBM](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/overview.html), ADBM построена на основе **pgbackrest** и обеспечивает гибкую настройку политик бэкапов, формирование полных (full), дифференциальных (differential) и инкрементальных (incremental) копий по расписанию или вручную, ведение списка бэкапов, создание **точек восстановления (restore point)** и восстановление БД на выбранный момент времени (PITR — point-in-time recovery). ADBM доступен в редакции **ADB Enterprise**; установка — только **offline**. Пользовательский интерфейс управления бэкапами встроен в **ADB Control** — из одного веб-интерфейса можно работать и с мониторингом запросов, и с резервным копированием. См. [Глоссарий](glossary.md).

Основные возможности ADBM:

- **Типы бэкапов:** полный (вся БД), дифференциальный (изменения после последнего полного), инкрементный (изменения после последнего бэкапа любого типа). Выбор типа влияет на время создания и объём хранилища; для восстановления могут потребоваться цепочки (full + diff + incr + WAL).
- **Restore point:** именованная точка восстановления; после её создания можно восстановить кластер на этот момент. ADBM хранит информацию о том, какие бэкапы и WAL-сегменты нужны для восстановления до выбранной точки.
- **WAL и PITR:** архивирование WAL (write-ahead log) позволяет воспроизводить изменения после последнего загруженного бэкапа и восстанавливать БД на произвольный момент времени в пределах имеющихся данных.
- **Несколько кластеров:** поддержка работы с несколькими кластерами ADB (в том числе с standby и зеркалированием).
- **Хранилища:** поддержка S3- и Posix-совместимых хранилищ для бэкапов.

Архитектура ADBM: **Backup Manager** (оркестрация действий, расписания), **Backup Agent** (по одному на каждый хост кластера; запуск pgbackrest, управление конфигурацией), **Service Registry**, **PostgreSQL** (блокировки, состояние активных действий, история бэкапов и конфигураций). Подробнее резервное копирование и восстановление — в [главе 6](chapter-06-01.md).

## 1.3.4. Дополнительные инструменты и интеграции

Помимо ADCM, ADB Control и ADBM экосистема Arenadata включает:

- **Коннекторы и интеграции (в контексте ADB):** по [материалам Arenadata](https://arenadata.tech/products/arenadata-db/) — ADB Kafka Connector (запись/чтение из топиков Kafka в формате AVRO и др.), ADB ClickHouse Connector (передача данных между ADB и ClickHouse через foreign data wrapper), ADB to ADB Connector (передача данных между двумя кластерами ADB), ADB Spark Connector (перенос данных между ADB и Arenadata Hyperwave). **Platform Extension Framework (PXF)** — фреймворк для параллельного обмена данными со сторонними системами (в том числе Hadoop, S3), единая точка входа для SQL-запросов к внешним источникам.
- **Логическое резервное копирование:** помимо бинарных бэкапов через ADBM, для выборочного бэкапа и переноса схем/данных используется **gpbackup/gprestore** (инструменты Greenplum/Greengage); ADBM управляет бинарными копиями, логические бэкапы могут настраиваться отдельно (в том числе через CLI).
- **Утилиты и расширения:** стандартные утилиты экосистемы Greenplum/Greengage (gpfdist, gpssh, и др.), расширения (MADlib для аналитики и ML, PostGIS для геоданных — по материалам Arenadata о возможностях ADB).

Документация по всем продуктам Arenadata публикуется на [docs.arenadata.io](https://docs.arenadata.io/ru/ADB/current/introduction/intro.html): разделы по ADB, ADCM, ADB Control, ADBM, коннекторам и туториалам. Документация доступна на **русском и английском** языках и поддерживается в актуальном состоянии. Техническая поддержка и обучение (курсы по Arenadata DB для аналитиков, разработчиков и по эксплуатации) предоставляются вендором; для ADCM действует открытое сообщество и Telegram-канал [t.me/arenadata_cm](https://t.me/arenadata_cm).

## 1.3.5. Как компоненты соотносятся друг с другом

Кратко связь компонентов в типовом сценарии эксплуатации ADB:

1. **Развёртывание:** ADCM — создание кластера, добавление хостов, установка ADB и при необходимости ADB Control и ADBM как сервисов кластера.
2. **Эксплуатация и мониторинг:** ADB Control — наблюдение за запросами, сессиями, метриками; при необходимости отмена «зависших» запросов, аудит, выгрузка метрик во внешнюю БД.
3. **Резервное копирование и восстановление:** ADBM — настройка расписаний и конфигураций бэкапов, создание restore points, восстановление на момент точки при сбое или ошибке.
4. **Обновление и масштабирование:** ADCM — upgrade кластера, расширение (добавление сегментов), управление конфигурациями.

ADB Control и ADBM входят в состав **ADB Enterprise**; в Community-редакции ADB их нет (по сравнительной таблице на сайте Arenadata). ADCM доступен отдельно под Apache 2.0 и может использоваться для развёртывания как Community, так и Enterprise-редакции ADB (при наличии соответствующих бандлов и лицензий).

## 1.3.6. Типичные ошибки при восприятии экосистемы

- **Считать ADCM частью только Arenadata DB:** ADCM — оркестратор всей платформы Arenadata (ADB, Hadoop, QuickMarts, Postgres, Streaming и др.); для ADB он используется для установки и управления кластером, но один экземпляр ADCM может обслуживать несколько продуктов и кластеров.
- **Путать ADB Control и ADBM:** ADB Control — мониторинг запросов и сессий в реальном времени; ADBM — управление бинарными бэкапами и восстановлением. Интерфейс ADBM встроен в ADB Control, но это два разных сервиса с разной архитектурой (агенты, БД, назначение).
- **Ожидать ADB Control/ADBM в Community-редакции:** они входят только в **ADB Enterprise**; при выборе Community-редакции мониторинг запросов и управление бэкапами нужно организовывать иными средствами (например, стандартные средства Greenplum/Greengage, gpbackup, внешний мониторинг).

## Ключевое

- **ADCM** — универсальный оркестратор (Apache 2.0) для развёртывания и управления data-сервисами Arenadata на любой инфраструктуре; для ADB: установка кластера, обновление, расширение, мониторинг состояния; веб-интерфейс, бандлы, REST API.
- **ADB Control** — система мониторинга запросов ADB в реальном времени: запросы, транзакции, сессии, метрики ресурсов, планы выполнения, отмена транзакций, аудит, offload метрик; доступен в ADB Enterprise; интерфейс — веб.
- **ADBM** — система управления бинарными бэкапами ADB (на базе pgbackrest): full/diff/incr бэкапы, restore points, PITR, несколько кластеров, S3/Posix; доступен в ADB Enterprise; UI встроен в ADB Control.
- **Дополнительно:** коннекторы (Kafka, ClickHouse, ADB-to-ADB, Spark), PXF, gpbackup/gprestore для логических бэкапов; документация на [docs.arenadata.io](https://docs.arenadata.io/ru/ADB/current/introduction/intro.html) на русском и английском.
