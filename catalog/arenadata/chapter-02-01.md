# §2.1 Arenadata Cluster Manager (ADCM)

В [§1.4](chapter-01-04.md) мы завершили обзор первой главы и критериев выбора Arenadata DB. С этого раздела начинается **глава 2 «Компоненты Arenadata»**: мы подробно разбираем каждый из трёх ключевых инструментов экосистемы. **Arenadata Cluster Manager (ADCM)** — оркестратор для автоматизированного развёртывания и управления кластерами; в этом разделе вы узнаете его назначение, архитектуру, основные возможности веб-интерфейса (конфигурация хостов и сегментов, мониторинг состояния), типовой процесс создания и управления кластером ADB, а также минимальные требования к установке ADCM. Детальные шаги установки ADCM и развёртывания кластера Arenadata DB по шагам приведены в [главе 3](chapter-03-01.md). См. [Глоссарий](glossary.md).

## 2.1.1. Назначение и роль ADCM

**Arenadata Cluster Manager (ADCM)** — универсальный оркестратор, обеспечивающий **развёртывание и управление** data-сервисами компании независимо от инфраструктуры: on-premises, в частном или публичном облаке, в виде PaaS. По [документации ADCM](https://docs.arenadata.io/ru/ADCM/current/introduction/intro.html), система разделяет управление на два независимых уровня — **инфраструктурный** и **уровень приложений**, что делает платформу гибкой, предсказуемой и масштабируемой. По [обзору ADCM](https://docs.arenadata.io/ru/ADCM/current/concept/adcm-overview.html), ADCM относится к типу решений «платформа данных как услуга» (Data Platform as a Service, DPaaS): установка, настройка и обновление кластеров выполняются по нажатию кнопки в графическом интерфейсе или по запросу к API; настройки ОС, сервисов, сети и монтирование дисков выполняются автоматически. См. [Глоссарий](glossary.md).

В контексте **Arenadata DB** ADCM используется для:

- **Автоматизированного развёртывания кластера ADB:** вместо ручной установки бинарников Greenplum/Greengage по документации оператор загружает бандл ADB в ADCM, создаёт кластер, добавляет хосты, распределяет компоненты (координатор, сегменты) по узлам, настраивает параметры и запускает установку — ADCM выполняет Ansible-сценарии на целевых хостах.
- **Управления кластером:** обновление (upgrade) до новой версии бандла, расширение кластера (добавление сегментов), запуск и остановка сервисов, проверка состояния (actions в зависимости от продукта — см. документацию по [действиям с кластером ADB](https://docs.arenadata.io/ru/ADB/current/how-to/manage-cluster/cluster-actions.html)).
- **Мониторинга состояния:** в веб-интерфейсе отображаются статусы кластеров, сервисов, компонентов и хостов (зелёная/жёлтая индикация, heartbeat); при необходимости настраиваются уведомления и пороговые значения; для сбора метрик используется связка Graphite + Grafana + Diamond (по материалам Arenadata).

ADCM поставляется в виде **Docker-образа**; лицензия — **Apache License 2.0** (открытый исходный код). Продукт зарегистрирован как российская программа для ЭВМ и поддерживает российские ОС (РЕД ОС, Альт, Astra Linux и др.), а также Ubuntu, CentOS, RHEL.

## 2.1.2. Архитектура ADCM

Базовая идея ADCM — предоставить простой пользовательский интерфейс, который передаёт достаточно данных для запуска **Ansible**-скриптов на заданном наборе **хостов**. По [обзору архитектуры](https://docs.arenadata.io/ru/ADCM/current/concept/architecture.html), в состав ADCM входят следующие компоненты:

| Компонент | Назначение |
|-----------|------------|
| **Nginx** | Прокси перед веб-интерфейсом; распределение нагрузки; порт 8000. |
| **Веб-интерфейс (WebUI)** | Приём запросов пользователя, отображение данных о кластерах, хостах, сервисах и действиях. |
| **Статус-сервер (Status Server)** | Приём heartbeat от хостов, сервисов и компонентов; приём событий от WebUI; отправка обновлений в WebUI по веб-сокетам (реализован на Go). |
| **Бэкенд-сервер (Backend Server)** | Взаимодействие со статус-сервером по REST API; чтение и запись в базу данных; создание **исполнителей процессов** (Ad hoc job runner) для запуска Ansible. |
| **База данных (Database)** | Хранение данных ADCM, в том числе зашифрованных с помощью Ansible Vault (Ansible secrets). |
| **Фоновый процесс (Background job)** | Выполнение периодических задач (например, удаление устаревших данных по настройкам ADCM). |
| **Исполнитель процесса (Ad hoc job runner)** | Подготовка окружения для Ansible (формирование inventory-файла), запуск команд Ansible на хостах кластера или хостпровайдера. Работа асинхронная: браузер не блокируется, результат записывается в БД и отображается в интерфейсе. Каждый запуск — отдельный процесс (не поток). |

Таким образом, пользователь через WebUI инициирует действие (например, «Install» кластера); бэкенд создаёт задачу, исполнитель процесса готовит inventory по текущему составу кластера и хостов и запускает Ansible; Ansible выполняет playbook на целевых машинах (установка пакетов, конфигурация, запуск сервисов); статусы хостов и компонентов передаются через Status Server в WebUI. Подробнее концепции хоста, сервиса, компонента и кластера описаны в [документации ADCM](https://docs.arenadata.io/ru/ADCM/current/concept/cluster.html).

## 2.1.3. Возможности ADCM: сервисы и инфраструктура

По [обзору ADCM](https://docs.arenadata.io/ru/ADCM/current/concept/adcm-overview.html), возможности сгруппированы следующим образом.

**Работа с сервисами (уровень приложений):**

- Установка и настройка кластеров.
- Обновление (upgrade) кластеров и сервисов.
- Управление (запуск, остановка, перезапуск и т.д. в зависимости от продукта).
- Мониторинг состояния сервисов и компонентов.
- Настройка прав доступа к сервисам.
- Интеграция с другими сервисами.
- Контейнеризация (где поддерживается продуктом).

**Работа с инфраструктурой:**

- Создание и удаление виртуальных машин (при использовании облачных хостпровайдеров).
- Конфигурирование ОС на хостах.
- Мониторинг хостов.
- Управление пользователями на хостах.
- Настройка прав доступа к инфраструктуре.

**Дополнительно:** настройка прав безопасности в ADCM (ролевая модель), открытый **REST API** для интеграции с внешними системами, **открытый формат бандлов** — возможность создавать собственные бандлы для добавления своих сервисов или типов инфраструктуры. Список продуктов, поддерживаемых ADCM, включает Arenadata DB, Arenadata Hadoop, Arenadata QuickMarts, Arenadata Postgres, Arenadata Streaming и др.; для ADB доступны отдельные руководства по [установке](https://docs.arenadata.io/ru/ADB/current/get-started/start-here.html) и [действиям с кластером](https://docs.arenadata.io/ru/ADB/current/how-to/manage-cluster/cluster-actions.html).

## 2.1.4. Веб-интерфейс и типовой процесс управления кластером

Управление кластерами выполняется на вкладке **Clusters** веб-интерфейса ADCM. После загрузки продуктового бандла (например, бандла Arenadata DB) создание и управление кластером осуществляются через следующие шаги (по [документации по вкладке Clusters](https://docs.arenadata.io/ru/ADCM/current/how-to/clusters.html)):

1. **Создание кластера** — выбор бандла, версии, имя и описание кластера; состояние кластера после создания — `created`.
2. **Добавление сервисов** — выбор сервисов продукта (для ADB — собственно ADB, при необходимости ADB Control, ADBM и др.) и их добавление в кластер.
3. **Добавление хостов** — подключение хостов к кластеру (хосты могут быть заведены заранее через хостпровайдера — SSH, облако и т.д.).
4. **Распределение компонентов по хостам (Mapping)** — назначение ролей: какой хост — координатор (Master), какие — сегменты, где размещаются компоненты ADB Control и ADBM при их использовании.
5. **Настройка сервисов и кластера** — конфигурационные параметры на уровне кластера и каждого сервиса (вкладки Primary configuration, при необходимости Configuration groups, Ansible settings).
6. **Настройка кластера** — общие параметры кластера (вкладка Configuration).
7. **Запуск действий** — для кластера в состоянии `created` становится доступно действие **Install**; после успешной установки состояние меняется на `installed`, появляются действия проверки, управления и обновления.

На вкладке Clusters отображается список кластеров с полями: **Name** (и индикатор статуса — зелёная/жёлтая точка по состоянию компонентов и хостов), **State**, **Product**, **Version**, **Description**, **Concerns** (блокирующие или неблокирующие предупреждения), **Actions** (меню действий, обновление до новой версии бандла, удаление кластера). При переходе по имени кластера открывается страница кластера с вкладками:

- **Overview** — описание, информация о бандле, сервисы (Up/Down), хосты (Up/Down), круговые диаграммы.
- **Services** — список сервисов, их состояние, конфигурация (Primary configuration, Configuration groups, Action host groups), компоненты сервисов.
- **Hosts** — список хостов, состояние, хостпровайдер, компоненты на каждом хосте.
- **Mapping** — размещение компонентов на хостах (перетаскивание или выбор); сохранение и сброс изменений.
- **Configuration** — настройки на уровне кластера (Primary configuration, Configuration groups, Ansible settings, Action host groups).
- **Import** — импорт настроек из других кластеров или сервисов в текущий кластер или в выбранный сервис.

Детальное пошаговое руководство по развёртыванию кластера Arenadata DB через ADCM приведено в [главе 3](chapter-03-01.md) настоящей книги.

## 2.1.5. Требования к установке ADCM

ADCM поставляется в виде **Docker-образа**. Для установки ADCM необходимы (по [требованиям к установке](https://docs.arenadata.io/ru/ADCM/current/get-started/prerequisites.html)):

**Операционные системы (одна из):** Ubuntu 22.04, CentOS 7, RHEL 7, Alt Linux SP 8, Alt Linux SP 10.2, Astra Linux SE 1.7 Орел, Astra Linux 1.7.6 Воронеж, РЕД ОС 7.3 Сертифицированная редакция.

**Пользователь:** с правами `sudo` (или root); для доступа к Docker CLI без root рекомендуется добавить пользователя в группу `docker`.

**Хост для запуска ADCM (минимальные требования):**

- CPU: 4 ядра.
- RAM: 16 ГБ.
- HDD: 50 ГБ.

Документация предупреждает: указанные значения минимальны; целевой размер (сайзинг) следует рассчитывать под нагрузку организации. Дополнительно: менеджер пакетов (YUM/APT), доступ к репозиториям ОС (для CentOS — Base и Extras), установленный **Docker** (рекомендуется ставить из репозиториев дистрибутива, а не с официального сайта Docker). Для CentOS 7 / RHEL 7 может потребоваться отключение SELinux; при использовании firewalld — его остановка (конкретные команды см. в [документации по требованиям](https://docs.arenadata.io/ru/ADCM/current/get-started/prerequisites.html)). Установка самого ADCM (запуск контейнера, первый вход в веб-интерфейс) описана в [§3.2](chapter-03-02.md).

## 2.1.6. Типичные ошибки при работе с ADCM

- **Путать «хост» и «сегмент»:** хост — это сервер (виртуальная или физическая машина), добавленный в ADCM через хостпровайдера; сегмент ADB — компонент сервиса Arenadata DB, размещённый на одном или нескольких хостах. Один хост может содержать несколько сегментов; mapping задаёт, какие компоненты на каком хосте стоят.
- **Запускать Install до завершения Mapping и настройки:** кластер в состоянии `created` должен иметь добавленные сервисы, хосты и размещение компонентов (Mapping), и при необходимости — заполненные конфигурации; только после этого действие Install отработает корректно.
- **Игнорировать Concerns:** блокирующие и неблокирующие предупреждения (иконки в столбце Concerns) указывают на проблемы конфигурации или состояния; перед критичными действиями (upgrade, расширение) их следует устранять или учитывать по документации продукта.
- **Считать ADCM только «установщиком»:** ADCM — оркестратор полного жизненного цикла: установка, обновление, расширение, мониторинг, настройка прав; после установки кластера управление продолжается через те же Clusters и страницы кластера/сервисов/хостов.

## Ключевое

- **ADCM** — универсальный оркестратор (DPaaS) для развёртывания и управления data-сервисами (в том числе Arenadata DB) на любой инфраструктуре; два уровня — инфраструктура и приложения; лицензия Apache 2.0, поставка в виде Docker-образа.
- **Архитектура:** Nginx, WebUI, Status Server (heartbeat, веб-сокеты), Backend, БД, Background job, Ad hoc job runner (Ansible); пользовательские действия приводят к запуску Ansible-сценариев на хостах кластера.
- **Возможности:** установка/настройка/обновление/управление/мониторинг сервисов; создание и конфигурирование ВМ и хостов; REST API, открытый формат бандлов.
- **Типовой процесс:** создание кластера → добавление сервисов → добавление хостов → Mapping (размещение компонентов) → настройка сервисов и кластера → запуск действия Install; далее управление через вкладку Clusters и страницы кластера (Overview, Services, Hosts, Mapping, Configuration).
- **Требования к хосту ADCM:** ОС из списка поддерживаемых, Docker, минимум 4 CPU, 16 ГБ RAM, 50 ГБ HDD; детали — в [документации](https://docs.arenadata.io/ru/ADCM/current/get-started/prerequisites.html).

В [§2.2](chapter-02-02.md) мы разберём Arenadata DB Control — систему мониторинга запросов Arenadata DB в режиме реального времени, просмотр выполняемых запросов, метрики производительности и управление сессиями.
