# §6.2 Полный и инкрементальный бэкап

В [§6.1](chapter-06-01.md) мы рассмотрели назначение Arenadata DB Backup Manager, соотношение с gpbackup и интерфейс управления. В этом разделе — **полный бэкап**, **дифференциальный и инкрементальный** бэкапы (поддержка в ADBM), **расписание** формирования бэкапов и создания restore points, а также **хранение** (хранилища, политики очистки). ## 6.2.1. Полный бэкап (Full)

**Полный бэкап (Full)** — копия всего содержимого данных кластера ADB на момент съёма. По [документации ADBM](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/overview.html) в полный бэкап попадают все файлы данных; восстановление из одного full-бэкапа возможно напрямую, без применения других бэкапов.

**Особенности:** первый бэкап в рамках текущего **timeline** в ADBM всегда имеет тип Full (даже если по расписанию или при ручном запуске выбран Diff или Incr). После восстановления кластера на какую-либо точку создаётся новый timeline; следующий бэкап в этой истории снова будет Full. Полные бэкапы требуют больше времени и места, чем дифференциальные и инкрементные; их не рекомендуется снимать слишком часто (например, ежечасно), обычно Full планируют раз в сутки или реже, а между ними — Diff или Incr.

**Запуск:** полный бэкап можно запустить вручную (Backup manager → кластер → действие Backup → выбор типа Full) или по расписанию (Configuration → Schedule → Full backup, cron-выражение). При ручном запуске при необходимости задают имя restore point и флаги (Delta, Fail on low space). Результат отображается на вкладке Backups; статус Done — успешное завершение.

## 6.2.2. Дифференциальный и инкрементальный бэкап

**Дифференциальный бэкап (Differential, Diff)** копирует только файлы, **изменившиеся после последнего полного** бэкапа. Он формируется быстрее и занимает меньше места, чем Full; для восстановления нужны последний Full и данный Differential (и при необходимости последующие Incr и WAL до выбранной точки).

**Инкрементальный бэкап (Incremental, Incr)** копирует только файлы, **изменившиеся после последнего бэкапа любого типа** (Full, Diff или Incr). Объём и время минимальны; восстановление требует цепочки: последний Full + при необходимости один или несколько Diff + все последующие Incr до нужного момента, затем при необходимости воспроизведение WAL до restore point.

**Поддержка в ADBM:** оба типа (Diff и Incr) поддерживаются. Расписание задаётся отдельно для Differential backup и Incremental backup в Configuration → Schedule (cron для каждого типа). При неактивном переключателе соответствующая операция выполняется только вручную. Рекомендуемая практика: периодический Full (например, раз в неделю), более частые Diff (например, раз в сутки) и ещё более частые Incr (например, каждые несколько часов) — в зависимости от требований к RPO и объёму хранилища.

**Ручной запуск:** в действии Backup выбирают тип Incr или Diff; при необходимости указывают имя restore point и опции Delta (использование checksum для определения изменённых блоков в incr/diff) и Fail on low space.

## 6.2.3. Расписание (Schedule)

Расписание формирования бэкапов и вспомогательных операций настраивается на странице кластера в ADBM: **Configuration → Schedule**. По [документации](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/basic/manage-configs.html) для каждой операции задаётся отдельное **cron-выражение** и переключатель активности:

- **Full backup** — расписание полных бэкапов (например, `0 0 2 * * ?` — раз в неделю в воскресенье в 02:00).
- **Differential backup** — расписание дифференциальных бэкапов (например, раз в сутки).
- **Incremental backup** — расписание инкрементальных бэкапов (например, каждые 4–6 часов).
- **Restore point creation** — создание именованной точки восстановления по расписанию (часто совмещают с моментом перед критичными операциями или с фиксированным интервалом).
- **Cleanup** — удаление лишних бэкапов по политикам (Number of full backups, Number of differential backups, Total number of backups из Backup configuration); выполняется по расписанию или вручную.

Если переключатель для операции выключен, она выполняется только при ручном запуске соответствующего действия. Редактирование расписания возможно только в рамках новой версии конфигурации (Create new → изменить Schedule → Apply backup configuration).

## 6.2.4. Хранение (хранилища и очистка)

**Хранилища (Configuration → Storages):** место хранения бэкапов и архива WAL задаётся в виде **Storage**. Поддерживаемые типы:

- **posix** — директория в файловой системе (локальная или сетевая, например NFS); указывается **Repository path** (путь, доступный с координатора и сегмент-хостов).
- **s3** — объектное хранилище S3-совместимое (bucket, endpoint, ключи доступа, region и др.).
- **cifs** — сетевая шара (CIFS/SMB); указывается путь к репозиторию.

В конфигурации бэкапа (Backup configuration → Storage) выбирается одно из созданных хранилищ и при необходимости **Relative path** внутри него. Один и тот же репозиторий (один тип и путь) может использоваться в разных конфигурациях с разными Relative path; при очистке ADBM учитывает комбинацию типа, пути и конечной точки.

**Мониторинг заполненности:** для хранилища настраиваются пороги **Almost Full** и **Critical**. При достижении Critical формирование бэкапа может не запускаться (если в параметрах действия Backup включён флаг Fail on low space). Состояние хранилища отображается в Overview на странице конфигурации с хранилищем; при приближении к лимитам необходимо расширить место или выполнить Cleanup.

**Политики хранения и Cleanup:** в Backup configuration задаются лимиты: **Number of full backups**, **Number of differential backups**, **Total number of backups**. Действие **Cleanup** (по расписанию или вручную) удаляет лишние бэкапы по этим правилам, а также бэкапы со статусами Failed/Invalid и неактивные версии конфигураций без связанных бэкапов. Без регулярного Cleanup хранилище заполняется; задачу Cleanup рекомендуется включать в расписание. Подробнее действие Cleanup и ручное удаление по restore point — в [документации ADBM](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/basic/run-actions.html).

## Ключевое

- **Full:** копия всех данных; первый бэкап в timeline всегда Full; восстановление из одного Full возможно напрямую; обычно планируют реже (раз в сутки/неделю).
- **Diff и Incr:** Diff — изменения после последнего Full; Incr — изменения после последнего бэкапа любого типа; оба поддерживаются в ADBM; восстановление по цепочке Full + Diff + Incr + WAL; задаются отдельные расписания в Schedule.
- **Расписание:** Configuration → Schedule; cron для Full backup, Differential backup, Incremental backup, Restore point creation, Cleanup; при выключенном переключателе — только ручной запуск.
- **Хранение:** Storages (posix, s3, cifs), Repository path; в конфигурации — выбор хранилища и Relative path; пороги Almost Full / Critical; политики хранения (Number of full/differential, Total number) и действие Cleanup по расписанию.

В [§6.3](chapter-06-03.md) мы разберём восстановление из бэкапа, выборочное восстановление и целевые показатели RTO и RPO.
