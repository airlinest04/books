# §3.2 Этапы выполнения MapReduce job

В [§3.1](chapter-03-01.md) мы ввели идею MapReduce: этапы Map (выдача пар ключ–значение по порциям данных) и Reduce (агрегация по ключу). В этом разделе разбираем **как job выполняется в Hadoop** от входа до выхода: как входные данные разбиваются на **сплиты**, как Map-задачи обрабатывают сплиты, что такое **shuffle and sort** и как Reduce-задачи получают сгруппированные данные и пишут результат в HDFS. Понимание конвейера выполнения помогает настраивать job (число Reduce, размер сплита) и интерпретировать логи и метрики. Написание кода Mapper и Reducer — в [§3.3](chapter-03-03.md); пример WordCount — в [§3.4](chapter-03-04.md). См. [Глоссарий](glossary.md).

---

## 3.2.1. Общая схема: от входа в HDFS до выхода в HDFS

Один **MapReduce job** в Hadoop выполняет полный цикл: чтение входных данных из HDFS → этап Map → shuffle and sort → этап Reduce → запись результата в HDFS. См. [Глоссарий](glossary.md).

Кратко по шагам:

1. **Подготовка входа:** фреймворк определяет **входные данные** (файлы/каталоги в HDFS) и разбивает их на **сплиты** (splits). Каждый сплит — это диапазон байт (обычно совпадает с одним блоком HDFS или объединяет несколько блоков) и передаётся одной Map-задаче.
2. **Map-фаза:** для каждого сплита запускается **Map-задача** (Map task) в контейнере YARN. Задача читает свой сплит (часто с узла, где лежит блок — локальное чтение), применяет функцию map и пишет вывод в локальный буфер (пары ключ–значение).
3. **Shuffle and sort:** вывод Map-задач передаётся на узлы, где будут выполняться Reduce-задачи. Партиционирование по ключу определяет, какая Reduce-задача получит пары с данным ключом; на стороне Reduce пары сортируются по ключу (и при необходимости по значению) и группируются — один ключ и итератор по его значениям передаются в функцию reduce.
4. **Reduce-фаза:** каждая **Reduce-задача** получает свой набор ключей и для каждого ключа — список значений. Применяется функция reduce; результат записывается в выходной файл в HDFS (один файл на Reduce-задачу или одна партиция общего выхода).

Данные между этапами не проходят через одну точку: Map пишет локально, shuffle развозит данные по Reduce-узлам, Reduce пишет в HDFS. Координацию (какие задачи запускать, где, перезапуск при сбоях) выполняет ApplicationMaster MapReduce job в рамках YARN ([гл. 4](chapter-04-01.md)).

## 3.2.2. Входные данные и сплиты

**Вход** job — один или несколько путей в HDFS (файлы или каталоги). По умолчанию используется **InputFormat**, который определяет, как разбить вход на **сплиты** (InputSplit). Каждый сплит обрабатывается одной Map-задачей. См. [Глоссарий](glossary.md).

Типичный случай — **FileInputFormat** и текстовые файлы: сплит совпадает с **блоком HDFS** (или с объединением нескольких блоков в пределах заданного размера). Таким образом, число Map-задач по умолчанию примерно равно числу блоков входных данных. Сплит не обязан совпадать с границей записи (например, строки): при разбиении по границе блока первая запись в сплите может начинаться в середине строки; в этом случае **RecordReader** пропускает «обрезанную» запись до начала следующей полной или обрабатывает границы особым образом (зависит от формата). Цель — чтобы каждая Map-задача получала примерно одинаковый объём данных и по возможности читала данные **локально** (блок на том же узле, где выполняется задача).

**Размер сплита** можно задать в конфигурации (min/max size). Мелкие сплиты — больше Map-задач, больше накладных расходов на запуск и shuffle; крупные сплиты — меньше задач, но меньше параллелизма. Ориентир по умолчанию — размер блока HDFS (128–256 МБ).

---

## 3.2.3. Выполнение Map-задач

**Map-задача** (Map task) — единица выполнения этапа Map. Она получает один сплит, открывает соответствующий фрагмент входных данных через **RecordReader** (который выдаёт записи — строки, ключ–значение и т.д. в зависимости от InputFormat), для каждой записи вызывает пользовательскую функцию **map** и собирает пары (ключ, значение), выданные map. См. [Глоссарий](glossary.md).

Вывод Map не пишется сразу в HDFS. Пары сначала попадают в **буфер в памяти** на узле, где выполняется Map-задача. Буфер периодически сбрасывается на диск (spill) в виде отсортированных по ключу файлов — это уменьшает объём данных в памяти и подготавливает данные к передаче в Reduce. Перед завершением Map-задачи несколько таких файлов (spill) могут быть объединены в один отсортированный вывод. Каждая пара при записи проходит через **Partitioner**: по ключу вычисляется номер партиции (номер Reduce-задачи), и пара попадает в соответствующую часть вывода. Так на этапе shuffle каждая Reduce-задача знает, с каких Map-задач забирать свою партицию.

**Локальность:** планировщик YARN (и запросы ApplicationMaster) стараются запустить Map-задачу на узле, где хранится копия блока этого сплита. Тогда чтение идёт с локального диска, без сетевого трафика. Если такой узел занят, задача может быть запущена на другом узле — тогда данные читаются по сети.

## 3.2.4. Shuffle and sort: передача и группировка по ключу

**Shuffle** — фаза, в которой вывод Map-задач **передаётся** на узлы, где выполняются Reduce-задачи. Каждая Reduce-задача запрашивает свою **партицию** вывода у всех Map-задач (ту часть пар, у которых Partitioner назначил данный номер Reduce). Данные копируются по сети с узлов Map на узлы Reduce. См. [Глоссарий](glossary.md).

**Sort** (сортировка): на стороне Reduce-задачи приходят потоки пар из разных Map; они **сливаются с сортировкой по ключу** (merge sort). В итоге Reduce-задача видит все пары с «своими» ключами в отсортированном по ключу порядке. Затем пары с одинаковым ключом **группируются**: функция reduce вызывается один раз на каждый уникальный ключ, с итератором по всем значениям этого ключа в отсортированном порядке (если задана вторичная сортировка по значению — то и порядок значений задаётся).

Shuffle — часто самое «дорогое» место по сетевому трафику и по времени: все промежуточные данные проходят по сети от Map к Reduce. Оптимизации включают: сжатие вывода Map перед передачей, настройку размера буфера и числа потоков копирования, уменьшение объёма данных (фильтрация и агрегация на стороне Map — combiner, см. документацию).

---

## 3.2.5. Выполнение Reduce-задач и запись в HDFS

**Reduce-задача** (Reduce task) получает сгруппированные по ключу данные (после shuffle and sort), для каждого ключа вызывает пользовательскую функцию **reduce** (ключ, итератор значений) и записывает результат. См. [Глоссарий](glossary.md).

**Выход** job по умолчанию пишется в HDFS: каталог задаётся при запуске job. Обычно создаётся по одному файлу на Reduce-задачу (например, `part-r-00000`, `part-r-00001`, …). Формат вывода задаётся **OutputFormat** (текстовый, SequenceFile и др.); сериализация ключа и значения — **Writable** или заданные типы. Запись идёт через **RecordWriter**; повторный запуск job в тот же выходной каталог по умолчанию приводит к ошибке (каталог уже существует), если не указано перезаписывание.

Число Reduce-задач задаётся при конфигурации job (например, `job.setNumReduceTasks(10)`). От этого числа зависит: сколько выходных файлов будет создано, как ключи распределятся по задачам (через Partitioner по хешу ключа по умолчанию) и насколько равномерной будет нагрузка. Нулевое число Reduce-задач допустимо: тогда этап Reduce не выполняется, вывод Map идёт напрямую в HDFS (без группировки по ключу); такой режим используется для задач, где нужна только трансформация без агрегации.

## 3.2.6. Сводная последовательность этапов

| Шаг | Что происходит |
|-----|-----------------|
| 1. Подготовка | Определение входных путей в HDFS; разбиение на сплиты (InputFormat). |
| 2. Map | Запуск Map-задач по одной на сплит; чтение сплита, map(ключ, значение) → пары; буферизация и spill на диск с сортировкой и партиционированием. |
| 3. Shuffle | Копирование партиций вывода Map на узлы Reduce по сети. |
| 4. Sort/Merge | На узле Reduce: слияние партиций с сортировкой по ключу; группировка пар с одинаковым ключом. |
| 5. Reduce | Для каждого ключа вызов reduce(ключ, значения); запись результата через RecordWriter в HDFS. |

Отказ одной задачи (Map или Reduce) обрабатывается повторным запуском задачи на другом узле; повторный запуск Map перечитывает сплит и заново выдаёт пары; повторный запуск Reduce заново запрашивает свою партицию у всех Map (или у кэшированных копий). Детали отказоустойчивости и повторных попыток задаются конфигурацией YARN и MapReduce.

## 3.2.7. Типичные ошибки при понимании этапов выполнения

- **Считать, что Map пишет напрямую в HDFS:** промежуточный вывод Map пишется на локальный диск узла (spill), затем в shuffle копируется на узлы Reduce; в HDFS идёт только финальный вывод Reduce (и при нуле Reduce — вывод Map).
- **Путать shuffle и sort:** shuffle — это **передача** данных от Map к Reduce; sort — **сортировка и группировка** по ключу на стороне Reduce. Оба вместе обеспечивают «все пары с ключом K приходят в одну Reduce-задачу в отсортированном виде».
- **Игнорировать влияние числа Reduce:** слишком мало Reduce-задач — узкое горлышко и перегрузка; слишком много — много мелких выходных файлов и большие накладные расходы на shuffle. Число обычно подбирают по объёму данных и количеству ключей.
- **Ожидать строгого порядка записей в выходном файле:** порядок ключей в выходе определяется партиционированием и порядком обработки в Reduce; для глобальной сортировки по ключу нужна одна Reduce-задача (или явная полная сортировка отдельным job), иначе ключи в разных файлах не упорядочены между собой.

---

## Ключевое

- **Выполнение job:** вход в HDFS → разбиение на сплиты → Map-задачи (по одной на сплит) → shuffle (передача пар по партициям на узлы Reduce) → sort/merge по ключу → Reduce-задачи → запись вывода в HDFS.
- **Сплит** — порция входных данных для одной Map-задачи; обычно соответствует блоку HDFS или заданному размеру; число сплитов задаёт число Map-задач.
- **Map** пишет пары в буфер и spill на локальный диск с партиционированием и сортировкой по ключу; **shuffle** копирует партиции на узлы Reduce; **sort** на Reduce сливает партиции и группирует по ключу.
- **Reduce** получает (ключ, список значений), вызывает reduce и пишет результат в HDFS; число Reduce-задач задаётся при конфигурации job и определяет число выходных файлов.
