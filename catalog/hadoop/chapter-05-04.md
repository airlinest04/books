# §5.4 Выбор формата хранения

В [§5.1](chapter-05-01.md)–[§5.3](chapter-05-03.md) мы разобрали текстовые форматы (CSV, JSON), SequenceFile и колоночные форматы (Parquet, ORC). Итоговый вопрос: **какой формат выбрать** для данных в HDFS? В этом разделе — критерии по **типу доступа** (полный скан против выборки столбцов и фильтрации) и по **инструментам** (Hive, Spark); сводная таблица и практический совет. Следующая глава — [Hive](chapter-06-01.md): SQL поверх Hadoop. См. [Глоссарий](glossary.md).

---

## 5.4.1. По типу доступа к данным

Выбор формата сильно зависит от того, **как** данные будут читаться. См. [Глоссарий](glossary.md).

**Полный скан, все столбцы, обмен и отладка**

- Запросы читают **все строки и все столбцы** (например, полная выгрузка, копирование, отладочный просмотр). Выигрыш от колоночного хранения и предикат pushdown минимален.
- Нужна **читаемость** или **простой обмен** с внешними системами без специальных библиотек — удобны **текстовые форматы** (CSV, JSON). Минусы: нет схемы в файле, слабое сжатие при потоковом сжатии всего файла.
- Если важен **бинарный поток пар** в рамках Hadoop (вход/выход MapReduce, консолидация мелких файлов) — **SequenceFile** ([§5.2](chapter-05-02.md)).

**Выборка столбцов и фильтрация (аналитика)**

- Запросы читают **часть столбцов** (например, SUM(amount), GROUP BY region) или **фильтруют по условию** (WHERE date = '2024-01-01'). Здесь колоночные форматы дают существенный выигрыш: меньше I/O за счёт column pruning и предикат pushdown.
- Рекомендуются **Parquet** или **ORC** ([§5.3](chapter-05-03.md)). Выбор между ними — по экосистеме и инструментам (см. ниже).

**Смешанный режим**

- Часть задач — полный скан, часть — аналитические запросы. Часто сырые данные принимают в тексте или SequenceFile, а витрины и агрегаты хранят в Parquet/ORC; ETL-пайплайн преобразует формат при загрузке в витрину.

## 5.4.2. По инструментам: Hive и Spark

Поддержка форматов в **Hive** и **Spark** хорошая; выбор формата может упростить настройку и использовать сильные стороны движка. См. [Глоссарий](glossary.md).

**Hive**

- **Parquet** и **ORC** поддерживаются нативно; для ORC интеграция глубже (типы Hive, ACID в Hive 3, индексы). Если кластер ориентирован на Hive и сложные типы (struct, map, array), ORC — естественный вариант.
- **Parquet** удобен, если одни и те же данные будут читаться из Hive, Spark, Presto и др.; один формат для мультидвижкового доступа.
- Текстовые форматы (CSV, JSON) — для приёма сырых данных и таблиц с простой схемой; при необходимости поверх создают внешние таблицы и при загрузке в витрину конвертируют в Parquet/ORC.

**Spark**

- **Parquet** — формат по умолчанию для DataFrame/DataSet; запись и чтение с автоматическим выводом схемы; предикат pushdown и выборка столбцов работают из коробки.
- **ORC** поддерживается; при совместном использовании с Hive часто выбирают один из двух (Parquet или ORC) для единообразия.
- **SequenceFile** — когда вход/выход логически представляют пары ключ–значение (legacy job, консолидация файлов).
- Текстовые форматы — для чтения/записи CSV, JSON при обмене и отладке.

Итог: при **преимущественно Hive** можно склоняться к **ORC**; при **Spark или нескольких движках** — к **Parquet**. Оба подходят для аналитических витрин.

## 5.4.3. Сводная таблица форматов

| Критерий | CSV / JSON | SequenceFile | Parquet | ORC |
|----------|------------|--------------|---------|-----|
| **Читаемость / обмен** | Да (текст) | Нет (бинарный) | Нет | Нет |
| **Схема в файле** | Нет | Типы ключа/значения | Да | Да |
| **Выборка столбцов** | Нет | Нет | Да | Да |
| **Предикат pushdown** | Нет | Нет | Да | Да |
| **Сжатие** | Общее (поток/блок) | Record/block | По страницам | По stripe |
| **Типичное использование** | Сырые данные, отладка, обмен | Пары ключ–значение, вывод MR, мелкие файлы | Аналитические витрины, мультидвижок | Аналитические витрины, Hive |
| **Hive** | Да | Да | Да | Нативная поддержка |
| **Spark** | Да | Да | По умолчанию | Да |

## 5.4.4. Практические рекомендации

- **Сырые данные и логи:** текстовые форматы (CSV, JSON) или сжатый текст — для приёма и первичного хранения; при необходимости партиционирование по дате/типу.
- **Витрины и агрегаты для аналитики:** **Parquet** или **ORC**; партиционирование по полям фильтрации (дата, регион) усиливает эффект предикат pushdown.
- **Единый формат в проекте:** выбрать один колоночный формат (например, Parquet) для всех витрин — проще поддержка и меньше форматов в пайплайнах.
- **Практическое задание:** закрепить материал можно, записав и прочитав данные в Parquet через Hive (CREATE TABLE ... STORED AS PARQUET, INSERT ... SELECT) или через Spark (DataFrame.write.format("parquet").save(...) и spark.read.parquet(...)).

---

## Ключевое

- **По типу доступа:** полный скан и обмен — текстовые форматы; выборка столбцов и фильтрация — Parquet или ORC; пары ключ–значение в MR — SequenceFile.
- **По инструментам:** при ориентации на Hive — ORC или Parquet; при Spark или нескольких движках — чаще Parquet.
- **Витрины данных** в Hadoop обычно хранят в Parquet или ORC с партиционированием по полям фильтрации.
- **Один колоночный формат** в проекте упрощает ETL и поддержку.
