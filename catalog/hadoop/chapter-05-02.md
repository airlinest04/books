# §5.2 SequenceFile

В [§5.1](chapter-05-01.md) мы разобрали текстовые форматы (CSV, JSON) и их ограничения. **SequenceFile** — бинарный формат Hadoop для хранения **последовательностей пар ключ–значение**; он поддерживает сжатие на уровне записей или блоков и естественно сочетается с MapReduce (вход и выход в виде пар). В этом разделе — что такое SequenceFile, какие режимы сжатия бывают и когда его используют. Колоночные форматы (Parquet, ORC) — в [§5.3](chapter-05-03.md); сравнение и выбор формата — в [§5.4](chapter-05-04.md). См. [Глоссарий](glossary.md).

---

## 5.2.1. Назначение SequenceFile

**SequenceFile** — формат файла в экосистеме Hadoop, в котором данные хранятся как **последовательность пар (ключ, значение)**. Ключ и значение — объекты, сериализуемые через Hadoop **Writable** (или WritableComparable для ключа). Файл читается и пишется последовательно, запись за записью; формат поддерживает **сжатие** и **разбиение** по границам записей или блоков для параллельного чтения в MapReduce и Spark. См. [Глоссарий](glossary.md).

Типичные сценарии:

- **Выход MapReduce job:** по умолчанию или при явной настройке вывод MapReduce может записываться в SequenceFile (пары ключ–значение совпадают с типами вывода Reducer).
- **Промежуточное хранение пар:** когда данные логически представляют собой поток пар (ключ, значение) и нужны сжатие и совместимость с Hadoop API (SequenceFileInputFormat, SequenceFileOutputFormat).
- **Объединение мелких файлов:** множество мелких файлов можно упаковать в один или несколько SequenceFile (ключ — имя файла, значение — содержимое), уменьшая нагрузку на NameNode и число мелких объектов в HDFS.

SequenceFile не подходит для выборочного чтения по столбцам и для SQL-запросов «только столбец A»: данные хранятся построчно (запись = пара ключ–значение), без колоночной раскладки. Для аналитики с выборкой столбцов чаще используют Parquet или ORC ([§5.3](chapter-05-03.md)).

---

## 5.2.2. Структура и типы ключа и значения

SequenceFile состоит из **заголовка** (версия, имена классов ключа и значения, метаданные, опция сжатия) и **последовательности записей**. Каждая запись — пара (ключ, значение); ключи и значения сериализуются через интерфейс Writable, поэтому типы должны быть известны при чтении (они записаны в заголовке). См. [Глоссарий](glossary.md).

Типы ключа и значения задаются при создании файла и хранятся в заголовке; при чтении Reader восстанавливает объекты по этим типам. Часто используются стандартные Writable: **IntWritable**, **LongWritable**, **Text**, **BytesWritable** и др. Можно использовать и пользовательские классы, реализующие Writable.

Записи идут **последовательно**; порядок ключей может быть произвольным или отсортированным (если файл сформирован выводом MapReduce с сортировкой). Случайный доступ по ключу в середине файла не предусмотрен без индекса (в части реализаций есть опция индекса для частичного поиска).

## 5.2.3. Сжатие: без сжатия, по записи, по блоку

SequenceFile поддерживает три режима сжатия. См. [Глоссарий](glossary.md).

- **None:** сжатие отключено; каждая запись записывается как есть. Максимальная скорость записи и чтения, больший объём на диске.
- **Record compression:** каждая запись (пара ключ–значение) сжимается отдельно. Уменьшается объём; при чтении можно распаковывать записи по одной. Границы записей сохраняются — разбиение на сплиты по границам записей возможно (каждый сплит читает свои записи и распаковывает их).
- **Block compression:** записи группируются в **блоки** (например, по размеру в байтах или по числу записей); блок сжимается целиком. Обычно даёт лучшее сжатие, чем record compression (больший контекст для компрессора). Границы блоков известны — сплит может начинаться с границы блока, что позволяет параллельное чтение без распаковки всего файла с начала.

Выбор режима задаётся при создании SequenceFile (в коде или в настройках OutputFormat). Для MapReduce вывода часто используют block compression как компромисс между объёмом и возможностью разбиения.

## 5.2.4. Использование в MapReduce

В MapReduce SequenceFile удобен, когда **вход или выход** логически представляют собой пары ключ–значение и нужны бинарный формат и сжатие. См. [Глоссарий](glossary.md).

- **Вход:** **SequenceFileInputFormat** читает файлы SequenceFile и выдаёт пары (ключ, значение) в Mapper. Сплиты создаются по границам записей или блоков (в зависимости от формата и сжатия); каждая Map-задача получает свой диапазон записей.
- **Выход:** **SequenceFileOutputFormat** записывает пары (ключ, значение) из Reducer в SequenceFile. Можно задать тип сжатия (RECORD, BLOCK) и кодек (например, Snappy, Gzip).

Пример установки в конфигурации Job (если выход должен быть SequenceFile):

```java
job.setOutputFormatClass(SequenceFileOutputFormat.class);
SequenceFileOutputFormat.setOutputCompressionType(job, SequenceFile.CompressionType.BLOCK);
```

Типы ключа и значения задаются через setOutputKeyClass и setOutputValueClass, как и для текстового вывода; формат сериализации меняется на SequenceFile.

## 5.2.5. Чтение и запись вне MapReduce

SequenceFile можно читать и писать из приложения (Java или через API, например Spark). См. [Глоссарий](glossary.md).

- **Запись:** создать **SequenceFile.Writer**, указать путь, типы ключа и значения, опцию сжатия; в цикле вызывать `writer.append(key, value)`; закрыть writer.
- **Чтение:** создать **SequenceFile.Reader**, открыть файл; в цикле вызывать `reader.next(key, value)` до возврата false; закрыть reader. Позиционирование (seek) в части реализаций поддерживается к границам блоков (sync points).

В Spark чтение SequenceFile: `sc.sequenceFile(path, keyClass, valueClass)` возвращает RDD пар (ключ, значение). Запись: `rdd.saveAsSequenceFile(path)`.

## 5.2.6. Ограничения и когда предпочесть другие форматы

- **Нет колоночного доступа:** нельзя прочитать «только значение второго поля» без десериализации всей записи; для аналитических запросов с выборкой столбцов Parquet/ORC эффективнее.
- **Формат специфичен для Hadoop:** обмен с внешними системами (не Hadoop) обычно проще в текстовом или стандартном колоночном формате (Parquet распространён шире).
- **Один тип ключа и один тип значения на файл:** схема (типы) фиксирована для всего файла; для сильно разнородных записей текстовые или гибкие форматы могут быть удобнее.

SequenceFile уместен для **потоков пар** в рамках Hadoop/Spark, для вывода MapReduce со сжатием и для консолидации мелких файлов; для витрин и тяжёлой аналитики чаще выбирают Parquet или ORC.

---

## 5.2.7. Типичные ошибки при использовании SequenceFile

- **Ожидать выборки по столбцам:** SequenceFile — построчный (запись = пара); выборка столбцов не поддерживается на уровне формата.
- **Путать сжатие по записи и по блоку:** при record compression каждая запись сжимается отдельно; при block — блок записей. Block обычно даёт лучшее сжатие и сохраняет возможность разбиения по блокам для параллельного чтения.
- **Забыть задать типы при чтении:** при открытии Reader типы ключа и значения берутся из заголовка файла; при программном чтении (например, в Spark) нужно указать совместимые классы ключа и значения.

---

## Ключевое

- **SequenceFile** — бинарный формат Hadoop для последовательности пар (ключ, значение); типы — Writable; поддерживает сжатие (none, record, block).
- **Сжатие:** record — по записи; block — по блоку записей (лучше сжатие, разбиение по блокам для параллельного чтения).
- **В MapReduce:** SequenceFileInputFormat и SequenceFileOutputFormat для входа и вывода в виде пар; удобен для вывода job со сжатием и для промежуточного хранения пар.
- **Ограничения:** нет колоночного доступа; формат ориентирован на Hadoop/Spark; для аналитики с выборкой столбцов предпочтительны Parquet/ORC.

В [§5.3](chapter-05-03.md) мы разберём колоночные форматы Parquet и ORC: хранение по столбцам, сжатие и предикат pushdown для аналитических запросов.
