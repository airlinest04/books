# §9.2 Профилирование источника

В [§9.1](chapter-09-01.md) мы зафиксировали постановку задачи: загрузка из источника в DWH, требования к качеству и точки проверки. Чтобы сформулировать **конкретные правила валидации** и настроить проверки в ETL ([§9.3](chapter-09-03.md)), нужен **первичный анализ данных источника** — профилирование. В этом разделе мы выполним **профилирование источника** в контексте нашего сценария: первичный анализ, выявление проблем и определение правил. Теоретическая база — глава 3; здесь применяем её к источнику из постановки §9.1. См. [Глоссарий](glossary.md).

---

## 9.2.1. Первичный анализ

**Первичный анализ** — первый шаг профилирования ([§3.1](chapter-03-01.md)): понять структуру и объём данных, которые будет потреблять пайплайн. Выполняется над **выгрузкой источника** (файл за один или несколько дней, срез из таблицы источника) до проектирования правил валидации.

**Структура:**

- Список полей (колонок), имена, порядок; типы данных в источнике и целевые типы в DWH. Для файлов — формат (CSV, Parquet), разделители, кодировка, наличие заголовка.
- Какие поля считаются ключевыми (бизнес-ключ, первичный ключ), какие — справочными (код региона, статус), какие — измеримыми (сумма, количество). Это нужно для правил уникальности и ссылочной целостности ([§4.3](chapter-04-03.md), [§4.4](chapter-04-04.md)).

**Содержимое (агрегаты по срезу):**

- **COUNT(*)** — объём среза; сравнение с ожиданием из регламента выгрузки ([§5.1](chapter-05-01.md)).
- По каждому полю: **COUNT(column)** (число не-null), доля null; для числовых — MIN, MAX, AVG; для дат — MIN, MAX ([§3.2](chapter-03-02.md)).
- **COUNT(DISTINCT key_columns)** — кардинальность по бизнес-ключу; сравнение с COUNT(*) выявляет дубликаты ([§3.2](chapter-03-02.md), [§2.5](chapter-02-05.md)).

Результат первичного анализа — сводная таблица или отчёт: объём, заполненность полей, диапазоны значений. На их основе переходим к выявлению проблем. См. [Глоссарий](glossary.md).

---

## 9.2.2. Выявление проблем

По результатам первичного анализа выявляем **проблемы качества**, которые нужно учесть правилами валидации или обработкой в ETL:

| Проблема | Как выявляем при профилировании | Что делаем дальше |
|----------|----------------------------------|-------------------|
| **Пропуски (null, пустые строки)** | COUNT(column) < COUNT(*); доля пустых по полю. | Решить: поле обязательное или нет; задать правило NOT NULL или порог полноты; при необходимости default по политике ([§7.3](chapter-07-03.md)). |
| **Дубликаты по ключу** | COUNT(*) > COUNT(DISTINCT key_columns); группировка по ключу с HAVING COUNT(*) > 1. | Задать правило уникальности; в ETL — дедупликация по правилу (оставить первую/последнюю) или отклонение дублей ([§4.3](chapter-04-03.md), [§5.2](chapter-05-02.md)). |
| **Значения вне диапазона или формата** | MIN/MAX выходят за допустимые границы; значения не соответствуют формату даты или справочнику. | Задать правила валидации (диапазон, формат, справочник); невалидные — отклонение или кварантин ([§4.2](chapter-04-02.md), [§7.1](chapter-07-01.md)). |
| **Выбросы** | Значения далеко от основной массы (статистически или по домену) ([§3.3](chapter-03-03.md)). | Решить: считать невалидными и отклонять, или допускать с алертом при превышении порога; зафиксировать в правилах. |
| **Несоответствие справочнику** | Коды, идентификаторы в источнике, которых нет в целевых справочниках DWH. | Правило референциальной целостности; записи-«сироты» — отклонение или кварантин ([§4.4](chapter-04-04.md)). |

Выявленные проблемы фиксируются в виде списка: поле или комбинация полей, тип проблемы, предполагаемая реакция. Это вход для формулировки правил (п. 9.2.3). См. [Глоссарий](glossary.md).

## 9.2.3. Определение правил

На основе выявленных проблем и требований к качеству ([§9.1](chapter-09-01.md)) формулируем **правила валидации** ([§4.1](chapter-04-01.md)), которые будут реализованы в ETL в [§9.3](chapter-09-03.md):

- **По полноте:** какие поля обязательны (NOT NULL); при необходимости — минимальная доля заполненности по полю (например, не менее 95%).
- **По валидности:** диапазоны для числовых полей; форматы для дат и строк; допустимые значения по справочнику (список или таблица-справочник).
- **По уникальности:** по какому ключу не должно быть дубликатов за срез; при наличии дубликатов — какое правило дедупликации или отклонение.
- **По согласованности:** бизнес-правила (сумма частей = целому, дебет = кредит и т.п.); референциальная целостность (внешние ключи к справочникам).

Каждое правило целесообразно описать в виде: идентификатор правила, условие (когда данные проходят проверку), реакция при нарушении (отклонить запись, кварантин, алерт). Список правил согласуется с владельцем данных и становится спецификацией для реализации проверок в пайплайне. Дополнительно фиксируются **автоматические исправления** ([§7.3](chapter-07-03.md)), если применяются: тримминг, приведение регистра, маппинг синонимов, default по полям. См. [Глоссарий](glossary.md).

## 9.2.4. Типичные ошибки

- **Пропустить профилирование и задать правила «по документации»:** в источнике часто оказываются null там, где документация говорит «обязательное поле», или дубликаты по ключу; профиль даёт фактическую картину и снижает сюрпризы в проде.
- **Профилировать по одному дню:** аномалии и редкие значения могут проявляться не каждый день; по возможности брать срез за несколько дней или за репрезентативный период.
- **Не фиксировать выявленные проблемы и правила:** устные выводы теряются; список проблем и перечень правил должны быть записаны (документ, конфиг, каталог правил) для реализации в §9.3 и для аудита.
- **Задать правила без согласования с владельцем данных:** пороги полноты, допустимые значения и реакция при нарушении должны быть согласованы с владельцем источника или витрины ([§7.4](chapter-07-04.md)).

## Ключевое

- **Первичный анализ** — структура (поля, типы, ключи) и содержимое (COUNT, заполненность, MIN/MAX, кардинальность) по срезу источника; основа для выявления проблем.
- **Выявление проблем:** пропуски, дубликаты по ключу, значения вне диапазона/формата/справочника, выбросы; каждая проблема связывается с предполагаемой реакцией (правило, отклонение/кварантин).
- **Определение правил** — формулировка правил валидации (полнота, валидность, уникальность, согласованность) и при необходимости автоматических исправлений; согласование с владельцем данных; список правил — вход для реализации в ETL.

В [§9.3](chapter-09-03.md) мы реализуем **правила и проверки в ETL**: проверки в пайплайне, кварантин при ошибках и логирование.
