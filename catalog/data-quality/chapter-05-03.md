# §5.3 Проверки при загрузке

В [§5.2](chapter-05-02.md) мы разобрали проверки при преобразовании: только валидные записи передаются на загрузку. Этап **загрузки** (Load) — запись данных в целевые таблицы. Проверки **после загрузки** отвечают на вопрос: **совпадает ли результат записи с ожиданием** — число строк, контрольные суммы, нет ли дубликатов в целевой таблице. В разделе мы разберём сравнение row count до и после загрузки, контрольные суммы целевой таблицы и проверку дубликатов в приёмнике. Детали расчёта контрольных сумм и сверки с источником — в [§5.4](chapter-05-04.md).

---

## 5.3.1. Зачем проверять после загрузки

Ошибки на этапе загрузки: частичная запись (часть строк не вставилась из-за сбоя или ограничения), дубликаты по ключу при повторном запуске, расхождение из-за триггеров или правил в БД. Проверки **после загрузки** подтверждают, что данные **действительно попали** в целевой слой в ожидаемом объёме и без искажений. Без них «успешное» завершение шага загрузки не гарантирует целостность: запись могла вернуть успех, но часть данных не записана или записана с ошибкой. Связь с проверками до и после загрузки — [§1.3](chapter-01-03.md). См. [Глоссарий](glossary.md).

---

## 5.3.2. Row count до и после загрузки

**Row count до загрузки** — число записей, переданных на запись (результат этапа преобразования, см. [§5.2](chapter-05-02.md)). **Row count после загрузки** — число записей в целевой таблице за данный срез (партиция за дату, batch_id или период загрузки). Ожидание: эти два числа **совпадают**; расхождение указывает на потерю при записи (меньше в приёмнике) или на дублирование/повторную вставку (больше в приёмнике).

Проверка:

1. До загрузки зафиксировать: `rows_to_load = N` (из шага преобразования).
2. Выполнить загрузку (INSERT, MERGE, COPY и т.д.).
3. После загрузки выполнить запрос к целевой таблице: `SELECT COUNT(*) FROM target_table WHERE partition_filter` (та же партиция/дата, что загружали).
4. Сравнить: `rows_loaded` должно равняться `rows_to_load`. При неравенстве — алерт, разбор причин (ограничения БД, конфликт по ключу, таймаут, частичный откат).

Для инкрементальной загрузки с перезаписью партиции (DELETE + INSERT или TRUNCATE партиции + INSERT) подсчёт после загрузки — по той же партиции. Для MERGE или UPSERT ожидаемое число может отличаться от числа переданных записей (обновления vs вставки); в этом случае критерий формулируется иначе (например, сумма вставленных и обновлённых = переданным, или проверка контрольной суммы). См. [Глоссарий](glossary.md).

## 5.3.3. Контрольные суммы целевой таблицы

**Контрольные суммы** по целевой таблице — агрегаты, вычисленные **по загруженным данным** за срез: COUNT(*), SUM(числовое_поле), при необходимости хеш по группе полей. Они сравниваются с эталоном: контрольными суммами источника ([§5.1](chapter-05-01.md)) или с числом и суммой записей, переданных на загрузку. Совпадение подтверждает, что при загрузке не произошло потери или искажения по объёму и сумме; расхождение — сигнал к расследованию.

Порядок:

1. Эталон: сохранённые при извлечении (или после преобразования) значения — `source_count`, `source_sum` (и при необходимости `source_hash`).
2. После загрузки: запрос к целевой таблице за тот же срез — `target_count = COUNT(*)`, `target_sum = SUM(amount)` и т.д.
3. Сравнение: `target_count` с `source_count` (или с числом переданных на загрузку, если часть записей была отклонена при преобразовании — тогда эталоном служит count после преобразования); `target_sum` с `source_sum`. При расхождении — алерт, разбор.

Учёт округления: при сравнении сумм с плавающей точкой использовать допуск (ABS(diff) > 0.01) или хранить суммы в целочисленных единицах (копейки). Подробнее виды контрольных сумм и сверка с источником — в [§5.4](chapter-05-04.md). См. [Глоссарий](glossary.md).

## 5.3.4. Дубликаты в целевой таблице

После загрузки в целевой таблице не должно появляться **дубликатов по бизнес-ключу** в рамках загруженного среза (партиции за дату). Дубликаты могут возникнуть из-за повторного запуска загрузки без идемпотентности, из-за дублей в переданном наборе или из-за сбоя логики (двойная вставка). Проверка: запрос на дубликаты по ключу в целевой таблице за срез (как в [§2.5](chapter-02-05.md), [§3.3](chapter-03-03.md)) — GROUP BY key HAVING COUNT(*) > 1.

Пример (PostgreSQL): ключи с дубликатами в целевой таблице за партицию:

```sql
SELECT order_id, order_date, COUNT(*) AS cnt
FROM core.orders
WHERE order_date = '2025-02-14'
GROUP BY order_id, order_date
HAVING COUNT(*) > 1;
```

Если запрос возвращает строки — в целевой таблице есть дубликаты за этот срез; требуется разбор (откат среза, исправление загрузки, дедупликация) и обеспечение идемпотентности последующих прогонов. Проверку дубликатов выполняют после каждой загрузки или как отдельный шаг мониторинга. См. [Глоссарий](glossary.md).

---

## 5.3.5. Цепочка метрик: извлечение → преобразование → загрузка

Связь метрик по этапам:

| Этап | Метрика | Сравнение |
|------|---------|-----------|
| Извлечение | row_count_extract, sum_extract (и при необходимости hash) | Эталон для следующих этапов |
| Преобразование | row_count_after_transform (валидные записи) | row_count_after_transform <= row_count_extract; разница = отклонённые |
| Загрузка | row_count_loaded, sum_loaded по целевой таблице | row_count_loaded = row_count_after_transform; sum_loaded = sum_after_transform (или sum_extract при отсутствии отклонений) |
| Дубликаты в приёмнике | count дубликатов по ключу за срез | Должно быть 0 |

При расхождении на любом шаге срабатывает алерт; логи сохраняют значения метрик для расследования. См. [Глоссарий](glossary.md).

## 5.3.6. Реакция при нарушении

При нарушении проверок после загрузки:

- **Row count не совпадает:** алерт, остановка пайплайна или ветвление; разбор — сбой записи, ограничения, конфликты. Опционально откат загруженного среза (DELETE по партиции) и повтор после исправления.
- **Контрольные суммы не совпадают с эталоном:** алерт, расследование (какие записи потеряны или искажены); при критичности — откат среза и повтор.
- **Обнаружены дубликаты в приёмнике:** алерт, разбор причины; устранение дубликатов по регламенту (оставить одну запись, откат и повтор с дедупликацией); проверка идемпотентности загрузки.

Политика (остановка, откат, только алерт) задаётся по критичности данных и по SLA. См. [Глоссарий](glossary.md).

---

## 5.3.7. Типичные ошибки

- **Сравнивать row count с эталоном извлечения при наличии отклонений при преобразовании:** если часть записей отклонена при преобразовании, эталон для загрузки — row count после преобразования, а не после извлечения; иначе «расхождение» будет ложным (ожидаем загрузить меньше, чем извлекли).
- **Считать контрольные суммы по всей таблице вместо среза:** после загрузки агрегаты нужно считать по той же партиции/дате, что загружали; иначе в подсчёт попадут данные других прогонов.
- **Не проверять дубликаты при идемпотентной загрузке:** даже при полной перезаписи партиции возможна ошибка (двойной запуск до завершения первого); проверка дубликатов после загрузки выявляет такие случаи.
- **Игнорировать округление при сравнении сумм:** как в §4.3 и §5.4, использовать допуск или целочисленное представление при сравнении SUM.

---

## Ключевое

- **Проверки после загрузки** подтверждают, что данные записаны в целевой слой в ожидаемом объёме: row count до и после совпадают, контрольные суммы целевой таблицы совпадают с эталоном, в приёмнике нет дубликатов по ключу за срез.
- **Row count до/после:** число записей, переданных на загрузку, должно равняться числу записей в целевой таблице за этот срез; при расхождении — потеря или дублирование при записи.
- **Контрольные суммы целевой таблицы:** COUNT(*), SUM(поля) по загруженному срезу сравниваются с эталоном (источник или результат преобразования); расхождение — сигнал к расследованию.
- **Дубликаты в целевой таблице:** проверка GROUP BY key HAVING COUNT(*) > 1 за срез; при наличии дубликатов — разбор и устранение, проверка идемпотентности загрузки.
- Цепочка метрик: extract → transform → load; на каждом шаге фиксируются count и при необходимости суммы; при отклонениях при преобразовании эталон для загрузки — метрики после преобразования.

В [§5.4](chapter-05-04.md) мы разберём **контрольные суммы и сверку** подробнее: хеш по строкам, сумма по числовым полям, сверка с источником и связь с книгами серии по финансовым расчётам.
