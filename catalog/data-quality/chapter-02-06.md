# §2.6 Валидность (Validity)

В [§2.5](chapter-02-05.md) мы разобрали **уникальность**: отсутствие дубликатов по ключу. Шестое и последнее измерение качества в нашей модели — **валидность** (Validity): значения **входят в допустимый диапазон**, **соответствуют формату** и при необходимости **присутствуют в справочнике** допустимых значений. Валидность не гарантирует, что значение верно по смыслу (это точность), но проверяет, что оно допустимо по правилам типа, формата и домена. В разделе мы дадим определение валидности, разберём типы правил (диапазон, формат, справочник), примеры проверок в SQL и связь с правилами валидации в главе 4. Завершив обзор шести измерений, мы перейдём к главе 3 — профилированию данных.

---

## 2.6.1. Определение валидности

**Валидность** (Validity) как измерение качества данных — это степень, в которой значения полей **соответствуют заданным правилам допустимости**: тип данных, диапазон (минимум–максимум), формат (шаблон, регулярное выражение), перечень допустимых значений (справочник, enum). Невалидное значение — то, которое не проходит хотя бы одно из этих правил: число вне диапазона, строка в неверном формате, код, отсутствующий в справочнике.

| Аспект | Описание |
|--------|----------|
| Допустимый диапазон | Числовое поле в заданных границах (например, сумма >= 0 и <= 10^9); дата в допустимом периоде; возраст в разумных пределах. |
| Соответствие формату | Строка соответствует шаблону: дата в формате ISO (YYYY-MM-DD), код из N символов, телефон в формате +7..., e-mail по шаблону, регулярное выражение. |
| Справочник (домен) | Значение входит в перечень допустимых: код валюты из справочника валют, код региона из справочника регионов, статус из фиксированного набора. |

Валидность отвечает на вопрос **«допустимо ли значение по правилам»**, а не «верно ли оно в реальности». Валидный код региона (есть в справочнике) может быть неточным для данной записи (должен быть другой регион). Проверки валидности — основа правил на уровне поля (глава 4). См. [Глоссарий](glossary.md).

---

## 2.6.2. Валидность и точность

Как мы отмечали в [§2.2](chapter-02-02.md), валидность и точность различаются:

| Измерение | Вопрос | Проверка |
|-----------|--------|-----------|
| **Валидность** | Входит ли значение в допустимый набор/формат? | Правила: диапазон, формат, справочник. |
| **Точность** | Совпадает ли значение с реальностью или эталоном? | Сравнение с эталоном, контрольные суммы, верификация. |

Валидность можно проверить **без эталона**: достаточно задать правила (диапазон, regex, список кодов). Точность требует эталона или способа верификации. В практике сначала часто проверяют валидность (отсечь заведомо недопустимые значения), затем при необходимости — точность (сверка с источником или эталоном). Оба измерения входят в набор проверок качества; правила валидации в ETL чаще всего реализуют именно валидность (и полноту), а точность — отдельными шагами сверки.

## 2.6.3. Правила по диапазону

Значение должно находиться в заданных границах: минимум и максимум для чисел, допустимый интервал дат, неотрицательность. Примеры:

- Сумма операции: `amount >= 0` (и при необходимости `amount <= 1e12`).
- Процент: `pct >= 0 AND pct <= 100`.
- Дата рождения: не в будущем и не раньше разумной границы (например, 1900-01-01).
- Количество: целое неотрицательное.

В SQL проверка «есть ли значения вне диапазона»:

```sql
-- Записи с amount вне допустимого диапазона [0, 999999999.99]
SELECT order_id, amount
FROM staging.orders
WHERE load_date = CURRENT_DATE - 1
  AND (amount < 0 OR amount > 999999999.99);
```

Метрика валидности по полю: доля записей, у которых значение в диапазоне; порог — например 100% для обязательного соблюдения или заданный процент. Подробнее правила на уровне поля — в [§4.2](chapter-04-02.md).

## 2.6.4. Правила по формату

Строковое значение должно соответствовать шаблону: длина, набор символов, структура (дата, код, телефон). Инструменты:

- **Регулярное выражение (regex):** гибкая проверка формата; поддерживается в части СУБД (например, PostgreSQL — `~`, `~*`) или в коде ETL.
- **Приведение типа:** попытка преобразовать строку в дату/число; при ошибке преобразования значение невалидно.
- **Длина и символы:** длина в заданных границах; только цифры, только буквы и т.д.

Пример проверки формата даты в PostgreSQL (ожидаемый формат YYYY-MM-DD):

```sql
-- Записи, где sign_date не соответствует шаблону даты или не парсится
SELECT contract_id, sign_date
FROM staging.contracts
WHERE load_date = CURRENT_DATE - 1
  AND (sign_date IS NOT NULL AND sign_date::text !~ '^\d{4}-\d{2}-\d{2}$');
```

На практике дату часто проверяют через приведение: `sign_date::date` в рамках допустимого диапазона или через исключение записей, где `sign_date` не приводится к типу date. Проверка по regex удобна для кодов (например, код из 3 заглавных букв: `~ '^[A-Z]{3}$'`). Формат e-mail, телефона и т.п. задаётся регулярным выражением или выносится в код приложения. См. [Глоссарий](glossary.md).

---

## 2.6.5. Правила по справочнику

Значение должно входить в **перечень допустимых** — справочник (таблица-справочник, домен). Типичные случаи: код валюты, код региона, статус заказа, тип документа. Проверка — вхождение значения в набор, полученный из справочника (подзапрос или джойн).

Пример: поле `currency_code` в таблице сделок должно существовать в справочнике `ref.currencies`.

```sql
-- Записи с currency_code, которого нет в справочнике
SELECT t.deal_id, t.currency_code
FROM staging.deals t
LEFT JOIN ref.currencies c ON t.currency_code = c.currency_code
WHERE t.load_date = CURRENT_DATE - 1
  AND t.currency_code IS NOT NULL
  AND c.currency_code IS NULL;
```

Если запрос возвращает строки — перечислены невалидные коды (отсутствуют в справочнике). Альтернатива — `WHERE t.currency_code NOT IN (SELECT currency_code FROM ref.currencies)`; при наличии null в справочнике NOT IN ведёт себя иначе, поэтому LEFT JOIN с проверкой на NULL часто предпочтительнее. Референциальная целостность ([§2.3](chapter-02-03.md)) — частный случай валидности по справочнику для внешних ключей: ссылка должна указывать на существующую запись в родительской таблице. Справочники и домены подробнее — в главе 4.

## 2.6.6. Сводка типов правил валидности

| Тип правила | Что проверяем | Пример |
|-------------|---------------|--------|
| Диапазон | Значение в границах min–max (число, дата). | amount >= 0; sign_date BETWEEN '1900-01-01' AND CURRENT_DATE. |
| Формат | Строка соответствует шаблону (regex, тип). | Дата YYYY-MM-DD; код из 3 букв; число без лишних символов. |
| Справочник | Значение входит в список допустимых (таблица, enum). | currency_code IN (SELECT ... FROM ref.currencies). |
| NOT NULL / пустая строка | Поле заполнено (относится к полноте и валидности). | contract_id IS NOT NULL AND contract_id <> ''. |

Правила комбинируются: поле обязательно (полнота), в формате даты (формат), в допустимом диапазоне дат (диапазон), при необходимости — код из справочника. Нарушение любого из правил даёт невалидную запись; запись может отклоняться, попадать в кварантин или помечаться для исправления (глава 7).

---

## 2.6.7. Метрики валидности

| Метрика | Описание | Пример порога |
|---------|----------|---------------|
| Доля валидных записей по полю | % записей, у которых значение проходит правила (диапазон, формат, справочник). | 100% или заданный порог. |
| Число невалидных записей | Количество записей (или полей), не прошедших валидацию. | 0 |
| Список невалидных значений | Перечень значений для разбора или исправления в источнике. | — |

Метрики считаются по срезу (партиция за дату) или по таблице; тренд по дням выявляет деградацию (появление новых невалидных кодов, сбой формата после смены источника). Связь с порогами и алертами — в главе 6.

---

## 2.6.8. Типичные ошибки

- **Путать валидность с точностью:** валидное значение (в диапазоне, по формату, из справочника) может быть неточным для данной сущности; для точности нужна сверка с эталоном или реальностью.
- **Задавать правила без контекста:** один и тот же формат даты или набор кодов может быть допустим в одном слое и недопустим в другом; правила задаются для конкретной таблицы/поля и цели использования.
- **Игнорировать обновление справочников:** при добавлении новых кодов в справочник старые данные с «новым» кодом могут считаться невалидными до обновления справочника в проверке; порядок обновления (сначала справочник, потом данные) и версионирование справочника нужно учитывать.

---

## Ключевое

- **Валидность (Validity)** — измерение качества: значения входят в допустимый диапазон, соответствуют формату и при необходимости присутствуют в справочнике допустимых значений.
- Валидность не заменяет точность: допустимое по правилам значение может быть неверным по смыслу; точность проверяется сравнением с эталоном.
- Типы правил: **диапазон** (min–max для числа/даты), **формат** (regex, приведение типа), **справочник** (значение входит в домен); плюс полнота (NOT NULL, не пустая строка).
- Проверки валидности реализуются в ETL и в СУБД (CHECK, FK на справочник); невалидные записи отклоняются или попадают в кварантин (главы 4 и 7).
- Метрики: доля валидных записей по полю, число невалидных записей; пороги и алерты — в главе 6.

Мы завершили обзор **шести измерений качества**: полнота, точность, согласованность, своевременность, уникальность, валидность. В [§3.1](chapter-03-01.md) мы переходим к **профилированию данных**: анализу структуры и содержимого для выявления аномалий и первичной оценки качества до загрузки.
