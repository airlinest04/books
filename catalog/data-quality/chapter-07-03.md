# §7.3 Автоматические исправления

В [§7.2](chapter-07-02.md) мы разобрали кварантин и журнал ошибок. Часть невалидностей можно устранить **автоматически** по зафиксированным правилам, без ручного разбора каждой записи: после применения правила запись снова проверяется и при успехе идёт на загрузку. В этом разделе мы разберём **автоматические исправления**: тримминг, приведение регистра, значения по умолчанию (default values) и иные правила, применимые без ручного вмешательства. Все они допустимы только в границах политики организации ([§7.1](chapter-07-01.md)) и с согласия владельцев данных. Эскалация и ответственность — в [§7.4](chapter-07-04.md). См. [Глоссарий](glossary.md).

---

## 7.3.1. Тримминг

**Тримминг** (trim) — удаление ведущих и завершающих пробельных символов (пробел, табуляция) из строки. В источниках часто встречаются значения с лишними пробелами (« RU » вместо «RU»), из‑за чего проверка по справочнику или сравнение ключей даёт несовпадение. Приведение к виду без пробелов по краям — **однозначное** исправление: оно не меняет смысл значения при условии, что в домене пробелы в начале и конце не несут информации.

Рекомендуется применять тримминг к строковым полям **до** валидации (на этапе преобразования), чтобы последующие проверки (справочник, уникальность, формат) работали с нормализованными значениями. В SQL — `TRIM(column)`; в других средах — аналог (например, `str.strip()` в Python). Для полей, где пробелы значимы (например, пароль или фиксированное выравнивание), тримминг не применяют; такое исключение фиксируется в регламенте. См. [Глоссарий](glossary.md).

---

## 7.3.2. Приведение регистра

**Приведение регистра** (case normalization) — приведение строки к единому регистру: верхнему (UPPER) или нижнему (LOWER). Используется для кодов, категорий и идентификаторов, где регистр не несёт смыслового различия (код валюты «usd» и «USD» считаются одним значением). Разные регистры в источнике приводят к «дубликатам» с точки зрения бизнеса и к несовпадению со справочником, если в справочнике значения в верхнем регистре.

Правило должно быть зафиксировано: например, «все коды валют — UPPER», «все коды стран — UPPER». Применяется до валидации по справочнику. Не применяется к полям, где регистр значим (имена собственные, свободный текст). См. [Глоссарий](glossary.md).

## 7.3.3. Значения по умолчанию (default values)

**Значение по умолчанию** (default value) — подстановка заданного значения вместо пустого (NULL) или невалидного в случаях, когда политика организации это допускает. Типичные ситуации:

- **Необязательное поле:** поле допускает NULL по модели; в источнике пришло пустое; по согласованию с владельцем данных подставляется, например, «N/A» или «Unknown» для аналитики. Важно: для **обязательных** и ключевых полей default без явного согласия бизнеса недопустим ([§7.1](chapter-07-01.md)).
- **Известный маппинг невалидного значения:** в источнике встречается код «TBD» или «-»; по регламенту он отображается в целевое значение «N/A» или в NULL. Правило документируется; при появлении нового невалидного значения, не входящего в перечень, запись отклоняется.

Список полей и допустимых default values задаётся политикой; любое добавление — по согласованию с владельцем данных, чтобы не исказить отчётность. См. [Глоссарий](glossary.md).

## 7.3.4. Формат и маппинг синонимов

К автоматическим исправлениям без ручного вмешательства относятся также:

- **Приведение формата:** дата в формате «DD.MM.YYYY» преобразуется в целевой формат (например, ISO или тип DATE); число с запятой в качестве десятичного разделителя — в числовой тип с точкой. Правило однозначно и не меняет смысл значения; при невозможности однозначного разбора (например, 01.02.2025 — 1 февраля или 2 января) применяется соглашение (локаль, порядок полей) и фиксируется в регламенте.
- **Маппинг синонимов:** значение из источника отображается в значение из целевого справочника по зафиксированной таблице соответствий (например, «RUS» → «RU», «Russia» → «RU»). Таблица ведётся и утверждается владельцем данных; значения, отсутствующие в таблице, не подставляются автоматически — запись отклоняется или отправляется в кварантин.

Общий принцип: **правило однозначно, документировано и не искажает смысл**; в противном случае применяется отклонение. См. [Глоссарий](glossary.md).

## 7.3.5. Документирование и повторная проверка

Все автоматические исправления должны быть:

- **Задокументированы:** перечень правил (тримминг по каким полям, регистр по каким, default по каким полям и значениям, таблица маппинга синонимов) хранится в регламенте, в коде (комментарии, конфиг) или в каталоге правил. Это нужно для аудита и для единообразия между пайплайнами.
- **Применяться до валидации:** сначала нормализация и исправления, затем проверка правил валидации; исправленная запись обязана **снова проходить валидацию**. Иначе возможна загрузка записи, всё ещё не соответствующей правилам (например, после подстановки default другое правило может быть нарушено).

Порядок в пайплайне: извлечение → преобразование и маппинг → **автоматические исправления** (trim, регистр, формат, default, маппинг синонимов) → **валидация** ([§5.2](chapter-05-02.md)) → отклонение невалидных / кварантин → загрузка валидных. См. [Глоссарий](glossary.md).

## 7.3.6. Типичные ошибки

- **Применять default к обязательным ключевым полям без согласования:** ключ, дата, сумма не должны подменяться значением по умолчанию «для прохода валидации»; при отсутствии значения — отклонение.
- **Не документировать правила исправления:** при смене разработчика или при аудите невозможно обосновать, почему значение было изменено; каждое правило должно быть в регламенте или в конфиге с комментарием.
- **Не выполнять повторную валидацию после исправления:** после подстановки default или маппинга запись может нарушать другое правило; обязательный шаг — проверка всех правил после блока автоматических исправлений.
- **Расширять маппинг синонимов или default без согласования:** появление нового значения в источнике не должно приводить к «тихой» подстановке без утверждения владельцем данных; новые кейсы — в регламент и в конфиг после согласования.

## Ключевое

- **Тримминг** — удаление ведущих и завершающих пробелов; однозначное исправление для строк; применяется до валидации; не используется для полей, где пробелы значимы.
- **Приведение регистра** (UPPER/LOWER) — для кодов и идентификаторов, где регистр не различается; правило фиксируется; не применяется к полям с семантикой регистра.
- **Default values** — только для необязательных полей или по утверждённому маппингу невалидных значений; не для ключевых полей без согласия бизнеса; перечень документируется.
- **Формат и маппинг синонимов** — по однозначным правилам и таблицам; неизвестные значения не подставляются автоматически.
- Все автоматические исправления документируются и применяются до валидации; после исправлений выполняется повторная проверка по всем правилам.

В [§7.4](chapter-07-04.md) мы разберём **эскалацию и ответственность**: кто исправляет данные, процесс уведомления и SLA.
