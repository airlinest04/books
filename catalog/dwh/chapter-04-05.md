# §4.5 Типы фактов

В [§4.4](chapter-04-04.md) мы разобрали выбор между схемой «звезда» и «снежинка». Структура фактовой таблицы (звезда или снежинка) не исчерпывает проектирование: важно **тип факта** — что означает одна строка и как таблица пополняется. В литературе по размерному моделированию выделяют три основных типа фактовых таблиц: **транзакционная таблица фактов**, **периодический снимок** (periodic snapshot) и **накопительный снимок** (accumulating snapshot). В этом разделе мы опишем каждый тип, гранулярность и **когда какой тип использовать**. В [§4.6](chapter-04-06.md) — агрегатные таблицы и мини-витрины. См. [Глоссарий](glossary.md).

---

## 4.5.1. Транзакционная таблица фактов

**Транзакционная таблица фактов** (transaction fact table) — фактовая таблица, в которой **одна строка соответствует одному событию (транзакции)**: одной продаже, одному платежу, одной отгрузке, одной позиции в чеке. Строки **добавляются** по мере появления событий; существующие строки не обновляются. Гранулярность — одна запись на одно событие. См. [Глоссарий](glossary.md).

Примеры:
- Продажи: одна строка — одна позиция в чеке (или одна транзакция оплаты, в зависимости от выбора гранулярности). Меры: количество, сумма, скидка. Ключи измерений: дата, магазин, продукт, кассир и т.д.
- Платежи: одна строка — один платёж. Меры: сумма, комиссия. Измерения: дата, клиент, способ оплаты, контрагент.
- Заказы (детализация по позициям): одна строка — одна позиция заказа. Меры: количество, цена, сумма. Измерения: дата заказа, клиент, продукт, склад.

Транзакционная таблица — самый частый тип в витринах: она естественно отражает поток событий из OLTP и подходит для отчётов «сколько произошло за период» (сумма продаж, количество заказов, объём платежей). Объём строк растёт с каждым днём; партиционирование по дате обязательно при больших объёмах. Исторические строки не меняются — соответствуют принципу неизменяемости ([§1.3](chapter-01-03.md)).

---

## 4.5.2. Периодический снимок (periodic snapshot)

**Периодический снимок** (periodic snapshot fact table) — фактовая таблица, в которой **одна строка — состояние на конец периода** для некоторой сущности (или агрегат за период). Период задаётся заранее: день, неделя, месяц. Строки добавляются с каждым периодом (например, по одному снимку на счёт на конец каждого месяца); при необходимости пересчитываются при перезагрузке за период. См. [Глоссарий](glossary.md).

Примеры:
- Остатки на счёте: одна строка — один счёт на конец месяца. Меры: баланс, обороты за месяц (при необходимости). Измерения: дата снимка (конец месяца), счёт, клиент, продукт. Каждый месяц добавляется по одной строке на каждый счёт.
- Выручка по клиенту за месяц: одна строка — один клиент за один месяц. Меры: сумма выручки, количество заказов. Измерения: год-месяц, клиент, сегмент. Используется для отчётов «выручка по клиентам по месяцам» без сканирования транзакционной таблицы за весь период.
- KPI по магазину за день/неделю: одна строка — один магазин за один период. Меры: выручка, трафик, средний чек. Измерения: дата периода, магазин, регион.

Периодический снимок удобен, когда нужны **регулярные отчёты по состоянию или по агрегатам за период** (балансы, месячные итоги по сущностям). Объём таблицы предсказуем: число строк ≈ число сущностей × число периодов. Минус — нужно заранее определить период и набор сущностей; произвольные периоды (например, «за последние 13 недель») при чистом снимке не покрываются без дополнительной логики или без обращения к транзакционной таблице.

## 4.5.3. Накопительный снимок (accumulating snapshot)

**Накопительный снимок** (accumulating snapshot fact table) — фактовая таблица, в которой **одна строка соответствует одному процессу или «кейсу»** (один заказ, одна заявка, один проект), а **строка обновляется** по мере прохождения этапов процесса. В одной строке хранятся даты (и при необходимости меры) нескольких этапов: дата создания, дата утверждения, дата отгрузки, дата доставки. По мере наступления события соответствующее поле в строке обновляется. См. [Глоссарий](glossary.md).

Примеры:
- Заказ от оформления до доставки: одна строка — один заказ. Измерения: клиент, продукт, склад, способ доставки. Меры: сумма, количество. Даты (или ключи измерения «Дата»): order_date, approve_date, ship_date, deliver_date. Когда заказ отгружен — обновляются ship_date и при необходимости меры на этапе отгрузки; когда доставлен — deliver_date.
- Заявка на кредит: одна строка — одна заявка. Этапы: подача, проверка, решение, выдача. Даты и статусы обновляются по мере прохождения.
- Проект: одна строка — один проект. Этапы: старт, этап 1, этап 2, завершение. Меры: плановые и фактические сроки, бюджет.

Накопительный снимок отвечает на вопросы «сколько заказов в пути», «среднее время от заказа до доставки», «заявки на этапе проверки». В отличие от транзакционной таблицы здесь **одна строка на сущность процесса**, и она **обновляется**. Поэтому накопительный снимок требует аккуратной работы в ETL: идемпотентное обновление при повторной загрузке, корректная привязка к датам измерений при срезах «на дату» (см. главу 5). Объём таблицы ограничен числом процессов (заказов, заявок), а не числом событий.

## 4.5.4. Сравнение типов и когда какой использовать

| Критерий | Транзакционная | Периодический снимок | Накопительный снимок |
|----------|----------------|----------------------|-----------------------|
| **Гранулярность** | Одна строка = одно событие | Одна строка = сущность за период (снимок на конец периода) | Одна строка = один процесс/кейс |
| **Обновление** | Только добавление | Добавление (иногда перезапись за период при пересчёте) | Обновление строки по мере прохождения этапов |
| **Типичные запросы** | «Сколько продаж/платежей за период», детализация по транзакциям | «Баланс на конец месяца», «выручка по клиентам по месяцам» | «Время от заказа до доставки», «заказы в пути», «заявки на этапе X» |
| **Объём строк** | Растёт с каждым событием | Сущности × периоды | Число процессов (заказов, заявок) |
| **Когда использовать** | Поток событий из OLTP; отчёты по объёмам и детализации | Регулярные срезы по состоянию или агрегаты за фиксированные периоды | Процессы с этапами; аналитика длительности и стадий |

В одной витрине могут сосуществовать несколько фактовых таблиц разного типа: например, транзакционная таблица продаж и периодический снимок «выручка по клиентам по месяцам» (агрегат для ускорения отчётов). Агрегатные таблицы и предрасчёты — тема [§4.6](chapter-04-06.md).

## 4.5.5. Гранулярность и выбор типа

**Гранулярность** — уровень детализации одной строки факта. От неё зависят возможные срезы в отчётах.

- Транзакционная таблица: гранулярность задаётся при проектировании — одна строка на одну продажу (транзакцию) или на одну позицию в чеке. Более детальная гранулярность (позиция) даёт срезы по продуктам внутри чека; менее детальная (транзакция) — только по чеку в целом.
- Периодический снимок: гранулярность = (сущность, период). Нужно явно определить, по каким сущностям и по каким периодам строятся снимки (все счета, все клиенты; месяц, неделя).
- Накопительный снимок: гранулярность = один процесс (один заказ, одна заявка). Одна строка не «одно событие», а «один жизненный цикл» с обновляющимися полями.

Неверный выбор гранулярности приводит к невозможности построить нужный отчёт (слишком крупная гранулярность) или к избыточному объёму и сложности (слишком мелкая без потребности). Требования отчётов должны быть учтены при выборе типа факта и гранулярности.

## 4.5.6. Типичные ошибки

- **Путать транзакционную таблицу с периодическим снимком:** в транзакционной одна строка — одно событие, строки не обновляются; в снимке одна строка — период по сущности или один процесс с обновлением. Смешение (например, обновлять «транзакционную» таблицу при изменении статуса заказа) ломает семантику и усложняет запросы.
- **Использовать накопительный снимок без продуманного обновления:** при повторной загрузке (идемпотентность) нужно корректно определять, какие поля обновлять; иначе дубликаты или потеря этапов. ETL для накопительного снимка сложнее, чем для чистой вставки.
- **Строить периодический снимок «на всё подряд»:** снимок имеет смысл, когда есть чёткий период и набор сущностей; не нужно дублировать транзакционную таблицу снимком с той же гранулярностью без выигрыша для отчётов.
- **Забывать про партиционирование транзакционной таблицы:** при большом потоке событий фактовая таблица быстро растёт; партиционирование по дате (день, месяц) обязательно для управляемости и производительности.

## Ключевое

- **Три типа фактов:** **транзакционная таблица** (одна строка = одно событие, только добавление), **периодический снимок** (одна строка = сущность за период, снимок на конец периода), **накопительный снимок** (одна строка = один процесс, строка обновляется по этапам).
- **Транзакционная** — для потока событий (продажи, платежи); отчёты по объёмам и детализации. **Периодический снимок** — для балансов, месячных/недельных агрегатов по сущностям. **Накопительный снимок** — для процессов с этапами (заказ → отгрузка → доставка), аналитика длительности и стадий.
- Гранулярность задаётся при проектировании и определяет возможные срезы; неверная гранулярность ограничивает отчёты или раздувает объём. В одной витрине возможны несколько фактовых таблиц разного типа. Агрегатные таблицы — в §4.6.

В [§4.6](chapter-04-06.md) мы разберём агрегатные таблицы и мини-витрины: предрасчёт для ускорения отчётов и правила обновления агрегатов.
