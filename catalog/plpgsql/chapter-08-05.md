# §8.5 Ограничения и риски

В [§8.4](chapter-08-04.md) мы разобрали типичные применения триггеров. В этом разделе — **ограничения и риски**: влияние на **производительность**, **каскадные** вызовы и рекурсия, взаимодействие с **внешними ключами** и референциальной целостностью, а также когда предпочтительнее **ограничения БД** или **проверки в приложении**. С этой главы завершается раздел о триггерах; далее — гл. 9 (правила). См. [Глоссарий](glossary.md).

---

## 8.5.1. Производительность

Триггер **FOR EACH ROW** вызывается **один раз на каждую затронутую строку**. Массовый UPDATE или INSERT по тысячам строк приводит к тысячам вызовов функции: дополнительные запросы внутри триггера (например, вставка в таблицу аудита) умножаются на число строк. Это увеличивает время выполнения и нагрузку на БД. См. [Глоссарий](glossary.md).

**Смягчение:** использовать условие **WHEN**, чтобы вызывать триггер только для нужных строк (например, только при изменении определённого столбца). Для аудита при массовых операциях рассмотреть триггер **FOR EACH STATEMENT** с transition tables (REFERENCING OLD TABLE / NEW TABLE): один вызов на оператор и одна групповая вставка в таблицу логов вместо N вставок по строке. По документации PostgreSQL, для AFTER-триггера с WHEN условие вычисляется после изменения строки, и при ложном результате вызов не ставится в очередь — это даёт выигрыш при большом числе строк. **BEFORE**-триггер при прочих равных эффективнее AFTER: не нужно сохранять данные строки до конца оператора (раздел 37.1).

## 8.5.2. Каскадные триггеры и рекурсия

Если триггерная функция выполняет SQL (INSERT, UPDATE, DELETE по другим таблицам или по той же), эти команды могут **снова вызвать триггеры** (по документации PostgreSQL, раздел 37.1). Уровней каскада не ограничено. Возможна **рекурсия**: например, INSERT-триггер на таблице A вставляет строку в A — снова срабатывает INSERT-триггер. См. [Глоссарий](glossary.md).

**Риск** — зацикливание и переполнение стека. Ответственность за отсутствие бесконечной рекурсии лежит на разработчике: в коде триггера нужно исключить операции, которые приведут к повторному срабатыванию того же триггера (проверка контекста, флаг в сессии, отказ от изменения той же таблицы в определённых условиях). При отладке полезны RAISE NOTICE или логирование с указанием TG_TABLE_NAME и TG_OP.

## 8.5.3. Триггеры и внешние ключи

Действия по **внешнему ключу** (ON UPDATE CASCADE, ON DELETE SET NULL и т.п.) выполняются обычными командами UPDATE/DELETE по ссылающейся таблице. При этом **срабатывают триггеры**, повешенные на эту таблицу (по документации PostgreSQL). Если такой триггер **блокирует** или **изменяет** результат каскадной операции (например, BEFORE DELETE возвращает NULL), референциальная целостность может быть нарушена. См. [Глоссарий](glossary.md).

Разработчик должен учитывать наличие FK с каскадными действиями: триггер не должен мешать каскаду (если только это не осознанное ограничение с альтернативной обработкой). При необходимости в триггере можно различать «прямой» вызов и вызов из-за каскада (например, по контексту или по данным), но стандартного способа в PL/pgSQL нет — остаётся аккуратное проектирование.

## 8.5.4. Когда предпочесть ограничения БД или приложение

**Ограничения БД** (CHECK, UNIQUE, NOT NULL, FK) — декларативные, выполняются движком, едины для всех клиентов и не требуют поддержки кода триггеров. Для простых правил (значение в диапазоне, уникальность, обязательность поля, ссылка на другую таблицу) их обычно предпочтительнее. См. [Глоссарий](glossary.md).

**Триггер** уместен, когда нужно: изменить данные до или после записи (updated_at, аудит), реализовать логику, невыразимую ограничениями (сложные проверки, обращение к другим таблицам, ветвление по TG_OP), или обеспечить единое поведение для любых клиентов без дублирования кода в приложениях. Недостатки: скрытая логика (надо знать о триггерах при отладке), тестирование и миграции сложнее, риск каскадов и рекурсии.

**Проверки в приложении** удобны для сложной бизнес-логики, зависящей от контекста (права, сценарий), или когда допустима несогласованность при прямом доступе к БД. Для критичной целостности данных предпочтительнее гарантии на уровне БД (ограничения + при необходимости триггеры).

## Ключевое

- **Производительность**: построчный триггер вызывается для каждой строки; смягчение — WHEN, при массовом аудите — триггер по оператору с transition tables; BEFORE при прочих равных эффективнее AFTER.
- **Каскад и рекурсия**: SQL внутри триггера может вызвать другие триггеры; рекурсия (триггер по той же таблице) — риск зацикливания; избегать — обязанность разработчика.
- **Внешние ключи**: каскадные действия выполняются командами по ссылающейся таблице и вызывают её триггеры; триггер не должен ломать референциальную целостность.
- Простые правила — по возможности **ограничения БД**; триггер — для модификации данных, аудита и сложной логики; приложение — где важна гибкость и контекст.

В [§9.1](chapter-09-01.md) начнём главу о **правилах (Rules)** в PostgreSQL: переписывание запроса на этапе планирования и отличия от триггеров.
