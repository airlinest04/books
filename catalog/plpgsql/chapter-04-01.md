# §4.1 Блок EXCEPTION

В [§3.5](chapter-03-05.md) мы завершили главу об управляющих конструкциях. С этой главы — **обработка исключений** в PL/pgSQL. В этом разделе разберём, **когда** и **как** управление переходит в секцию EXCEPTION при ошибке: прерывание операторов между BEGIN и EXCEPTION, поиск подходящего обработчика, выполнение обработчика и завершение блока; откат изменений в базе внутри блока и сохранение переменных. Конкретные условия (WHEN по коду ошибки, OTHERS) — в [§4.2](chapter-04-02.md), получение информации об ошибке — в [§4.3](chapter-04-03.md), явный вызов исключения (RAISE) — в [§4.4](chapter-04-04.md). См. [Глоссарий](glossary.md).

---

## 4.1.1. Когда управление переходит в EXCEPTION

Блок с секцией **EXCEPTION** имеет вид (напоминание из [§2.1](chapter-02-01.md)):

```
[ DECLARE ... ]
BEGIN
  операторы
EXCEPTION
  WHEN условие [ OR условие ... ] THEN
    операторы_обработчика
  [ WHEN условие ... THEN
    операторы_обработчика
    ... ]
END;
```

Пока выполнение идёт в части **BEGIN ...** (до EXCEPTION), любая **ошибка** — исключение, возбуждённое PostgreSQL или оператором RAISE — прерывает выполнение операторов этого блока. Дальнейшие операторы между BEGIN и EXCEPTION **не выполняются**. Управление сразу передаётся в список **EXCEPTION**: движок ищет **первый** обработчик, чьё условие (WHEN) совпадает с возникшей ошибкой. Если такой обработчик найден, выполняются **только** операторы этого обработчика (до следующего WHEN или до END); затем выполнение блока считается завершённым и управление переходит к **следующему оператору после END** этого блока. См. [Глоссарий](glossary.md).

Если **ни один** обработчик не подходит, ошибка **не перехватывается**: она распространяется дальше (к внешнему блоку с EXCEPTION или к вызывающему, либо прерывает транзакцию). В таком случае операторы обработчиков не выполняются.

---

## 4.1.2. После обработчика блок завершается

Важно: после выполнения выбранного обработчика (одного из WHEN ... THEN ...) **весь блок заканчивается**. Нельзя «вернуться» к месту ошибки и продолжить выполнение операторов между BEGIN и EXCEPTION. Обработчик может, например, залогировать ошибку, присвоить переменным значения по умолчанию и выйти из блока; или вызвать RAISE и пробросить ошибку наружу; или выполнить альтернативную логику. Но следующая строка кода после блока — это уже оператор **после** END, а не следующий оператор после той точки, где произошла ошибка. См. [Глоссарий](glossary.md).

Таким образом, EXCEPTION даёт возможность **реагировать** на ошибку и либо завершить блок «мягко», либо перевыбросить исключение, но не «пропустить» ошибку и продолжить как ни в чём не бывало с того же места.

---

## 4.1.3. Подтранзакция: откат изменений в блоке

Блок с секцией EXCEPTION при входе создаёт неявную **точку сохранения** (savepoint). Когда выполнение попадает в один из обработчиков EXCEPTION, все изменения **базы данных** (INSERT, UPDATE, DELETE и т.п.), сделанные **внутри этого блока** после BEGIN, **откатываются**. Изменения, выполненные **до** входа в этот блок (внешние операторы или предыдущие блоки), **сохраняются**. См. [Глоссарий](glossary.md).

При этом **локальные переменные** PL/pgSQL сохраняют те значения, которые они имели в момент ошибки. Обработчик может их читать и использовать (например, для логирования или для присваивания в OUT-параметры). Откатывается только состояние БД в границах блока с EXCEPTION.

Пример (по документации PostgreSQL, адаптировано): до блока выполнен INSERT; внутри блока — UPDATE и присваивание; затем ошибка (деление на ноль). В обработчик попадаем с откатанным UPDATE, но переменная x уже увеличена; INSERT до блока не откатывается:

```sql
INSERT INTO mytab(firstname, lastname) VALUES ('Tom', 'Jones');
BEGIN
  UPDATE mytab SET firstname = 'Joe' WHERE lastname = 'Jones';
  x := x + 1;
  y := x / 0;   -- division_by_zero
EXCEPTION
  WHEN division_by_zero THEN
    RAISE NOTICE 'Поймано: division_by_zero';
    RETURN x;   -- x уже увеличен, UPDATE откатан
END;
-- в таблице остаётся 'Tom Jones', не 'Joe Jones'
```

---

## 4.1.4. Ошибка в обработчике

Если во время выполнения **операторов самого обработчика** возникает новая ошибка, она **не** перехватывается этим же списком EXCEPTION. Ошибка распространяется наружу (к внешнему блоку с EXCEPTION или к вызывающему). Вложенный блок с собственным EXCEPTION внутри обработчика может перехватить такую ошибку. См. [Глоссарий](glossary.md).

---

## 4.1.5. Затраты на блок с EXCEPTION

Вход в блок, содержащий секцию EXCEPTION, и выход из него дороже, чем у блока без EXCEPTION: создаётся точка сохранения и при необходимости откат. Поэтому не стоит оборачивать в EXCEPTION большие участки кода «на всякий случай». Лучше ограничивать блок EXCEPTION тем участком, где действительно возможна и обрабатываемая ошибка. См. документацию PostgreSQL, раздел 41.6.8 (Trapping Errors).

---

## Ключевое

- При **ошибке** в операторах между BEGIN и EXCEPTION выполнение прерывается, управление переходит в список EXCEPTION; ищется первый подходящий обработчик (WHEN условие THEN ...).
- После выполнения обработчика **блок завершается**; управление переходит к оператору после END; возврата к месту ошибки нет.
- Если подходящего обработчика **нет**, ошибка распространяется наружу.
- **Изменения в БД** внутри блока с EXCEPTION при попадании в обработчик **откатываются**; изменения снаружи блока сохраняются; **переменные** сохраняют значения на момент ошибки.
- Ошибка, возникшая **в коде обработчика**, не перехватывается этим же EXCEPTION; блок с EXCEPTION дороже по ресурсам — использовать точечно.
