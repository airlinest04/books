# §1.3 Где выполняется PL/pgSQL

В [§1.2](chapter-01-02.md) мы разобрали, что даёт PL/pgSQL: процедурная логика на сервере, меньше round-trip, согласованность и безопасность. Теперь важно чётко понять, **где** этот код хранится и **откуда** он запускается. Код на PL/pgSQL всегда выполняется в процессе сервера PostgreSQL; он может находиться в **хранимой функции**, в **хранимой процедуре** или в **триггерной функции**, а также в **анонимном блоке** (DO). В этом разделе мы разберём эти объекты и три основных контекста вызова: из SQL (в том числе из других запросов), из приложения (клиент отправляет запрос с вызовом функции или CALL процедуры) и из триггера (автоматический вызов при событии на таблице). В [§1.4](chapter-01-04.md) начнём с практики: выполним первый анонимный блок. См. [Глоссарий](glossary.md).

---

## 1.3.1. В каких объектах живёт код на PL/pgSQL

Код на PL/pgSQL не выполняется «просто так» в виде свободного скрипта на сервере. Он всегда является **телом одного из объектов базы данных** (или одноразового блока). Основные варианты:

- **Функция (CREATE FUNCTION).** Текст функции хранится в системном каталоге PostgreSQL; при вызове сервер выполняет тело функции на PL/pgSQL (или другом языке) и возвращает значение (или набор строк). Функция может вызываться из SQL-выражений, из приложения, из другой функции или из триггерной функции.
- **Процедура (CREATE PROCEDURE).** Аналогично хранится в каталоге; вызывается оператором `CALL`. Не возвращает значение в выражении; может иметь OUT-параметры и выполнять COMMIT/ROLLBACK внутри себя (подробнее гл. 6).
- **Триггерная функция.** Это обычная функция на PL/pgSQL (без аргументов или с особыми аргументами), которая **привязывается к триггеру** на таблице или представлении. Сама по себе она не выполняется по расписанию или по имени из запроса — её вызывает движок PostgreSQL при наступлении события (INSERT, UPDATE, DELETE и т.д.). См. [Глоссарий](glossary.md).
- **Анонимный блок (DO).** Блок кода без имени, не сохраняемый в каталоге; клиент отправляет оператор `DO $$ ... $$`, сервер выполняет его один раз и не сохраняет. Удобен для разовых скриптов и первого знакомства (см. [§1.4](chapter-01-04.md)).

Во всех случаях **выполнение происходит внутри процесса сервера БД**: тот же процесс, который обрабатывает обычные SQL-запросы, интерпретирует или выполняет скомпилированный код PL/pgSQL. Никакого отдельного «интерпретатора» вне сервера нет; клиент лишь инициирует выполнение (отправляет вызов функции, CALL или DO).

## 1.3.2. Вызов из SQL

Функция на PL/pgSQL вызывается из SQL так же, как встроенная или любая другая пользовательская функция: в выражениях `SELECT`, в `WHERE`, в `INSERT ... VALUES (... func() ...)`, в `DEFAULT` для столбца, в проверках и т.д. Движок выполняет функцию в контексте того запроса, который её использует; результат подставляется в выражение. См. [Глоссарий](glossary.md).

Примеры контекстов:

- **SELECT:** `SELECT my_func(a, b) FROM t;` — для каждой строки (или один раз, в зависимости от оптимизатора) вызывается функция, её возвращаемое значение попадает в результат запроса.
- **В выражении:** `UPDATE t SET x = my_func(id) WHERE ...;` — функция вызывается на сервере для каждой обновляемой строки (или как оптимизатор решит).
- **В подзапросе или CTE:** внутри сложного запроса можно вызвать функцию в любом выражении, где допустима функция.

При этом **процедуру** из SQL вызывают только через `CALL`: `CALL my_proc(arg1, arg2);`. В выражение SELECT или в DEFAULT процедуру подставить нельзя — она не возвращает значение. Подробнее о создании и вызове функций и процедур — гл. 5 и 6.

Итого: код PL/pgSQL в виде функции выполняется **внутри SQL-запроса**, когда этот запрос ссылается на функцию; запрос может быть отправлен с клиента, из другого хранимого объекта или из триггера.

## 1.3.3. Вызов из приложения

С точки зрения сервера «вызов из приложения» ничем не отличается от «вызова из SQL»: приложение — это клиент, который открывает соединение с PostgreSQL и отправляет текст запроса. Если в тексте запроса есть вызов функции или процедуры, сервер выполняет его так же, как если бы запрос был введён в psql или выполнен из другой функции. См. [Глоссарий](glossary.md).

Типичные сценарии:

- **Вызов функции:** приложение формирует запрос вида `SELECT my_func($1, $2)` или `SELECT * FROM my_func($1)` (если функция возвращает набор строк), передаёт параметры через подготовленное выражение или подстановку и получает результат в виде набора строк или полей.
- **Вызов процедуры:** приложение отправляет `CALL my_proc($1, $2, ...)`; процедура выполняется на сервере; при наличии OUT-параметров их значения возвращаются клиенту в том формате, который поддерживает протокол (например, в результате CALL).

Таким образом, **место выполнения не меняется** — по-прежнему сервер БД. Меняется только источник текста запроса: не интерактивная сессия или другой объект БД, а код приложения (драйвер отправляет запрос по сети). Один round-trip: приложение один раз отправляет вызов и получает результат, тогда как эквивалентная логика «в приложении» потребовала бы многих запросов.

## 1.3.4. Вызов из триггера

**Триггер** в PostgreSQL — это объект, привязанный к таблице (или представлению), который указывает: «при наступлении события (INSERT, UPDATE, DELETE и т.д.) вызвать заданную функцию». Эта функция и есть **триггерная функция**; её можно написать на PL/pgSQL. См. [Глоссарий](glossary.md).

Последовательность такая: клиент (или другой код) выполняет, например, `INSERT INTO t ...`; сервер перед или после выполнения оператора (в зависимости от типа триггера) **автоматически** вызывает триггерную функцию. Пользователь не пишет в запросе «вызови триггер» — движок сам вызывает функцию по правилам, заданным в определении триггера. Внутри триггерной функции доступны специальные переменные (например, NEW и OLD для строки), что позволяет реализовать аудит, проверки, подстановку значений и т.д. Подробнее триггеры рассмотрены в гл. 8.

Важно: выполнение кода PL/pgSQL в триггере происходит **в том же процессе и в той же транзакции**, что и вызвавший его оператор. Триггер не «уходит» на другой сервер и не выполняется асинхронно по умолчанию — он часть одной атомарной операции с изменением данных.

## 1.3.5. Анонимный блок DO

Кроме именованных объектов (функция, процедура, триггер) код на PL/pgSQL можно выполнить **один раз** без сохранения в каталоге — с помощью оператора **DO**. Синтаксис: `DO $$ блок кода на PL/pgSQL $$`. Клиент отправляет этот оператор; сервер выполняет блок и завершает; объект в каталоге не создаётся. См. [Глоссарий](glossary.md).

DO удобен для администрирования, миграций, разовых скриптов и для первого знакомства с языком: не нужно создавать функцию, достаточно написать блок и выполнить его в psql или из приложения. В [§1.4](chapter-01-04.md) мы напишем и выполним первый такой блок.

---

## Ключевое

- Код PL/pgSQL хранится и выполняется **в объектах БД**: функция (CREATE FUNCTION), процедура (CREATE PROCEDURE), триггерная функция (привязана к триггеру) или в анонимном блоке (DO).
- **Выполнение всегда на сервере** — в процессе PostgreSQL; клиент только инициирует вызов.
- **Из SQL:** функция вызывается в выражениях (SELECT, WHERE, DEFAULT и т.д.); процедура — только через CALL.
- **Из приложения:** клиент отправляет запрос с вызовом функции или CALL процедуры; с точки зрения сервера это тот же SQL.
- **Из триггера:** триггерная функция вызывается автоматически при событии (INSERT/UPDATE/DELETE) на таблице; выполнение в той же транзакции.
- **DO** — выполнение анонимного блока без сохранения в каталоге; один раз за отправку оператора.

В [§1.4](chapter-01-04.md) мы напишем и выполним первый анонимный блок на PL/pgSQL в psql.
