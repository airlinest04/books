# §9.3 Отличие от триггеров

В [§9.2](chapter-09-02.md) мы разобрали CREATE RULE и примеры. В этом разделе сводим воедино **отличие правил от триггеров** по уровню срабатывания и по решаемым задачам, и кратко — **когда что использовать**. Отладка PL/pgSQL и типичные ошибки — в [§9.4](chapter-09-04.md). См. [Глоссарий](glossary.md).

---

## 9.3.1. Уровень: переписывание запроса и выполнение кода

**Правило** действует на этапе **переписывания запроса** (query rewrite): до передачи дерева запроса планировщику исходная команда заменяется или дополняется другими командами. Выполняется уже переписанный запрос; никакой отдельной «функции правила» во время выполнения не вызывается. См. [Глоссарий](glossary.md).

**Триггер** действует **во время выполнения**: команда (уже запланированная) выполняется, и в определённый момент вызывается **триггерная функция** (PL/pgSQL или другой язык). Функция может обращаться к NEW/OLD, выполнять произвольный код, делать запросы к другим таблицам, вызывать RAISE — то есть это именно исполняемая процедура, а не подстановка текста команды.

Итог: правило — **трансформация команды**; триггер — **вызов кода** в ответ на событие.

---

## 9.3.2. Гранулярность: команда целиком и построчная реакция

Правило переписывает **целиком оператор** (один INSERT, один DELETE и т.д.). В действии правила можно ссылаться на NEW/OLD, но само правило не «выполняется N раз по строкам» — переписанная команда может обрабатывать множество строк одним планом. См. [Глоссарий](glossary.md).

Триггер **FOR EACH ROW** вызывается **один раз на каждую затронутую строку**; в функции доступны NEW и OLD именно для этой строки. Удобно для проверок, модификации данных строки, записи в лог по каждой строке с разной логикой. Триггер **FOR EACH STATEMENT** вызывается один раз на оператор (аналогично правилу по кратности), но через вызов функции, а не через подстановку команды.

Итог: для реакции **по строке** с произвольной логикой (условия, ветвление, несколько запросов в зависимости от данных) — **триггер**; для **подмены или добавления одной (или нескольких) команд** на оператор — **правило**.

---

## 9.3.3. Когда использовать правило, когда — триггер

**Правило** уместно (по документации PostgreSQL и практике):

- Реализация представлений (ON SELECT DO INSTEAD) — обычно через CREATE VIEW, без явного CREATE RULE.
- Простое «к каждому DELETE добавить одну команду» (например, INSERT в архив SELECT OLD.*) — правило DO ALSO; одна переписанная команда, без построчного кода.
- Обновляемое представление с простой подстановкой в одну базовую таблицу — правила ON INSERT/UPDATE/DELETE DO INSTEAD.

**Триггер** уместно:

- Аудит **по строке** (разная запись в лог в зависимости от полей, проверки, вызов других функций).
- Проверка и **модификация** NEW перед записью (BEFORE), заполнение полей (updated_at и т.п.).
- Сложное обновляемое представление (несколько таблиц, условия, RETURNING) — **INSTEAD OF** триггеры проще программировать, чем набор правил.
- Реакция на событие с доступом к контексту (TG_OP, другие таблицы, исключения).

Если одна и та же таблица или представление имеет и правила (ON INSERT/UPDATE/DELETE), и **INSTEAD OF** триггеры, сначала применяются **правила**; переписанная команда может уже не обращаться к представлению, и триггеры тогда не сработают (документация PostgreSQL, раздел 39.2.4). См. [Глоссарий](glossary.md).

## 9.3.4. Краткая сводка

| Критерий            | Правило                         | Триггер                          |
|--------------------|----------------------------------|----------------------------------|
| Момент             | До планирования (переписывание) | Во время выполнения              |
| Что происходит     | Замена/дополнение команды       | Вызов функции                    |
| По строкам         | Нет (одна команда на оператор)  | FOR EACH ROW — да                |
| Сложная логика     | Неудобно (только SQL в правиле) | Удобно (PL/pgSQL, ветвление)      |
| Логирование удалений (простое) | DO ALSO INSERT … OLD.*   | AFTER DELETE, INSERT в лог      |
| Обновляемое представление (сложное) | Много правил            | INSTEAD OF триггеры              |

В сомнительных случаях (аудит с условиями, проверки, несколько таблиц) обычно выбирают **триггер** — проще отлаживать и расширять. Правила оставляют для сценариев, где именно переписывание команды даёт нужный эффект без построчного кода. См. [Глоссарий](glossary.md).

---

## Ключевое

- **Правило** — переписывание команды до планирования; **триггер** — вызов функции во время выполнения.
- Правило действует на **оператор целиком**; триггер FOR EACH ROW — **на каждую строку**.
- Простое дополнение команды (например, лог удалений одной вставкой) — правило DO ALSO; аудит по строке, проверки, сложное представление — триггеры.
- На одном объекте правила применяются раньше триггеров; при переписывании команды триггеры по исходному объекту могут не выполниться.

В [§9.4](chapter-09-04.md) разберём **отладку и диагностику** PL/pgSQL: RAISE NOTICE/DEBUG, проверка синтаксиса через DO-блок и типичные ошибки при написании функций.
