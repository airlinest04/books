# §4.4 Зависимости между тасками

В [§4.3](chapter-04-03.md) мы ввели задачу (Task) как экземпляр оператора. Чтобы задать **порядок выполнения**, нужно объявить **зависимости** между задачами: «задача B выполняется после задачи A». В Airflow зависимости задаются оператором `>>` (bitshift) или методами `set_downstream` / `set_upstream`. В этом разделе разобраны эти способы, линейные цепочки и простые ветвления; более сложные графы (параллельные ветки и сведение) — в [§5.1](chapter-05-01.md). Запуск и просмотр в UI — в [§4.5](chapter-04-05.md).

---

## 4.4.1. Оператор >> (task1 затем task2)

Самый распространённый способ задать зависимость: **A >> B** означает «сначала A, потом B» (A — предшественник, B — преемник). Выражение можно читать как «A затем B» или «B зависит от A». Результат `>>` — объект задачи (преемник), поэтому цепочки можно писать подряд.

Пример линейной цепочки из трёх задач:

```python
from airflow import DAG
from airflow.operators.bash import BashOperator
from datetime import datetime

with DAG(
    dag_id="example_chain",
    schedule_interval=None,
    start_date=datetime(2025, 1, 1),
) as dag:
    task_a = BashOperator(task_id="task_a", bash_command="echo A")
    task_b = BashOperator(task_id="task_b", bash_command="echo B")
    task_c = BashOperator(task_id="task_c", bash_command="echo C")

    task_a >> task_b >> task_c
```

Порядок выполнения: сначала `task_a`, после успешного завершения — `task_b`, после успеха `task_b` — `task_c`. Планировщик не поставит `task_b` в очередь, пока `task_a` не завершится успешно; аналогично для `task_c` и `task_b`. Среда: Airflow 2.x.

---

## 4.4.2. Цепочка через несколько >>

Тот же граф можно записать по шагам:

```python
task_a >> task_b
task_b >> task_c
```

Или одной строкой (результат `task_a >> task_b` — это `task_b`, к нему снова применяется `>> task_c`):

```python
task_a >> task_b >> task_c
```

Оба варианта задают один и тот же граф. Используйте тот, что лучше читается в вашем DAG.

---

## 4.4.3. Ветвление: несколько преемников у одной задачи

Если одна задача должна запускаться перед **несколькими** другими, запишите список преемников справа от `>>`:

```python
task_a >> [task_b, task_c]
```

Это означает: и `task_b`, и `task_c` зависят от `task_a`. После успешного завершения `task_a` планировщик поставит в очередь обе задачи — `task_b` и `task_c`; они могут выполняться параллельно (если есть свободные воркеры). Граф: A → B и A → C. Подробнее о параллельных ветках и сведении (B и C → D) — в [§5.1](chapter-05-01.md).

---

## 4.4.4. Несколько предшественников у одной задачи

Чтобы задача D запускалась **после** обеих задач B и C, задайте зависимость от списка предшественников:

```python
[task_b, task_c] >> task_d
```

Планировщик поставит `task_d` в очередь только после успешного завершения и `task_b`, и `task_c`. Комбинируя списки слева и справа от `>>`, можно строить графы с ветвлением и сведением.

---

## 4.4.5. set_downstream и set_upstream

Альтернатива оператору `>>` — методы у объекта задачи:

- **task_a.set_downstream(task_b)** — то же, что **task_a >> task_b**: task_b выполняется после task_a (task_b — «ниже по потоку»).
- **task_b.set_upstream(task_a)** — то же, что **task_a >> task_b**: task_b выполняется после task_a (task_a — «выше по потоку»).

Для нескольких преемников или предшественников передают список:

```python
task_a.set_downstream([task_b, task_c])
# эквивалентно: task_a >> [task_b, task_c]

task_d.set_upstream([task_b, task_c])
# эквивалентно: [task_b, task_c] >> task_d
```

В современном коде чаще используют `>>` как более короткую и наглядную запись; `set_downstream` / `set_upstream` удобны, когда зависимости задаются в цикле или собираются динамически.

---

## 4.4.6. Полный пример: цепочка и ветвление

Линейная часть и сведение двух веток в одну:

```python
with DAG(
    dag_id="example_branch_join",
    schedule_interval=None,
    start_date=datetime(2025, 1, 1),
) as dag:
    start = BashOperator(task_id="start", bash_command="echo start")
    branch_b = BashOperator(task_id="branch_b", bash_command="echo B")
    branch_c = BashOperator(task_id="branch_c", bash_command="echo C")
    join = BashOperator(task_id="join", bash_command="echo join")

    start >> [branch_b, branch_c]
    [branch_b, branch_c] >> join
```

Граф: start → branch_b и start → branch_c; затем branch_b и branch_c → join. Задача `join` запустится только после успешного завершения обеих веток.

---

## 4.4.7. Типичные ошибки

- **Цикл в графе:** например, A >> B >> C >> A. Airflow при загрузке может пометить DAG как ошибочный; уберите цикл.
- **Забыть задать зависимость:** задача без предшественников и без преемников будет «висеть» отдельно; планировщик запустит её в начале run (если нет предшественников), но логика пайплайна может быть нарушена — проверяйте граф в UI.
- **Путать направление >>:** A >> B значит «сначала A, потом B»; B >> A задаёт обратный порядок.

---

## Ключевое

- **Зависимость «A затем B»** задаётся оператором **A >> B** (или `A.set_downstream(B)`, `B.set_upstream(A)`).
- **Цепочка:** task_a >> task_b >> task_c — линейный порядок выполнения.
- **Ветвление:** task_a >> [task_b, task_c] — у одной задачи несколько преемников; **[task_b, task_c] >> task_d** — у одной задачи несколько предшественников (сведение веток).
- Граф должен быть **ациклическим**; планировщик ставит задачу в очередь только после успешного завершения всех предшественников.
