# §2.3 Обработка сбоев

В [§2.2](chapter-02-02.md) мы разобрали граф зависимостей: планировщик не запускает следующую задачу, пока предыдущие не завершились успешно. Но что делать, когда задача **падает**: временный сбой сети, недоступность API, таймаут? В этом разделе рассмотрена **обработка сбоев**: повторные попытки (retry), уведомления и важное требование к самим задачам — **идемпотентность**, чтобы повторный запуск не портил данные.

---

## 2.3.1. Повтор при сбое (retry)

Многие сбои носят **временный** характер: сеть восстановилась через минуту, внешний API вернул 503 и через несколько попыток отвечает. Оркестратор должен позволять настраивать **повторные попытки (retry)** для задачи:

- **Число попыток:** например, до 3 запусков после первого падения.
- **Интервал между попытками:** сразу, через 1 минуту, через 5 минут — чтобы дать внешней системе восстановиться.
- **Условие:** повторять при любом сбое или только при определённых кодах ошибок (опционально).

Планировщик (или исполнитель) при падении задачи не помечает run как окончательно проваленный, а переводит задачу в состояние «ожидание повтора» и через заданный интервал ставит её в очередь снова. После исчерпания попыток задача переходит в статус «failed», и следующие по графу задачи не запускаются — как и обсуждалось в [§2.2](chapter-02-02.md).

Retry уменьшает необходимость ручного вмешательства при кратковременных сбоях. В Apache Airflow retry настраивается на уровне задачи (оператора): `retries`, `retry_delay`, при необходимости `retry_exponential_backoff`. См. [Глоссарий](glossary.md).

---

## 2.3.2. Уведомления при сбое

Когда задача после всех попыток остаётся в статусе «failed», ответственный должен **узнать об этом**. Оркестратор должен поддерживать или интегрироваться с каналами уведомлений:

- **Email** — письмо при падении пайплайна или задачи.
- **Мессенджеры** — Slack, Telegram и т.п. через webhook или интеграцию.
- **Системы мониторинга** — отправка события в Prometheus, PagerDuty и т.д., чтобы сбой отобразился в дашбордах и при необходимости вызвал эскалацию.

Настройки обычно включают: при каком событии слать (failed, success после retry), кому/куда, по каким пайплайнам (например, только критичные). Так обработка сбоев не ограничивается «повторить», но и предполагает **алерт**, чтобы человек мог вмешаться при постоянной ошибке. Требования к мониторингу и алертам мы обобщим в [§2.4](chapter-02-04.md).

## 2.3.3. Идемпотентность задач

**Идемпотентность** (idempotency) в контексте задачи пайплайна означает: **повторный запуск задачи с теми же параметрами (например, за ту же дату) даёт тот же результат и не портит данные**. Другими словами, выполнить задачу один раз или два раза — с точки зрения состояния данных должно быть одинаково.

Зачем это важно при retry и ручном повторном запуске:

- При **retry** оркестратор может запустить одну и ту же задачу за ту же дату несколько раз. Если задача при первом запуске записала данные, а при втором (после временного сбоя) попыталась «дозаписать» без учёта уже записанного, возможны дубликаты или конфликты.
- При **ручном backfill** или «перезапусти задачу за вчера» оператор ожидает предсказуемый результат: данные за этот день пересчитаны/перезаписаны один раз, без артефактов от предыдущих попыток.

Типичные приёмы идемпотентности:

- **Полная перезапись среза:** загрузка за дату D каждый раз перезаписывает партицию или таблицу за D (DELETE + INSERT или TRUNCATE + INSERT, или запись в партиционированную таблицу с перезаписью партиции).
- **Upsert по ключу:** вставка с конфликтом по ключу (ON CONFLICT, MERGE): повторный запуск обновляет те же строки, дубликатов нет.
- **Проверка перед записью:** «если данные за D уже есть и актуальны — не писать»; осторожно с таймингами и консистентностью.

Задача, которая при каждом запуске **добавляет** строки без ключа или без перезаписи среза, **не идемпотентна**: второй запуск создаст дубли. Такую задачу опасно оставлять с retry или перезапускать без предварительной очистки. См. [Глоссарий](glossary.md).

---

## 2.3.4. Типичные ошибки

- **Включать retry без идемпотентности:** при временном сбое после частичной записи повторный запуск может продублировать данные. Сначала обеспечьте идемпотентность (перезапись среза или upsert), затем настраивайте retry.
- **Слишком много попыток без увеличения задержки:** если внешний сервис «лежит» 10 минут, 3 попытки подряд за секунду не помогут; лучше увеличить `retry_delay` или использовать exponential backoff.
- **Не настраивать алерты:** retry справляется с временными сбоями, но при постоянной ошибке кто-то должен получить уведомление и отреагировать.

---

## Ключевое

- **Retry (повтор при сбое)** — настраиваемое число попыток и интервал между ними; снижает ручное вмешательство при временных сбоях.
- **Уведомления при сбое** — алерт в email, мессенджер или мониторинг после исчерпания retry, чтобы ответственный мог отреагировать.
- **Идемпотентность задач** — повторный запуск с теми же параметрами не должен портить данные (перезапись среза, upsert по ключу). Без идемпотентности retry и ручной повторный запуск рискованны.
