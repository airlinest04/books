# §6.3 Таски: преобразование и загрузка

В [§6.2](chapter-06-02.md) мы реализовали таск извлечения. Следующие шаги пайплайна — **преобразование (transform)** и **загрузка (load)**: очистка и приведение данных к целевой модели и запись в слой Raw или Staging. В этом разделе — как реализовать эти таски: **PythonOperator** с вызовом Pandas или SQL, при необходимости **BashOperator** с вызовом ETL-скрипта, и **загрузка в целевую БД** с учётом идемпотентности из [§6.1](chapter-06-01.md). Связывание всех шагов в один DAG — в [§6.4](chapter-06-04.md).

---

## 6.3.1. Преобразование: PythonOperator с Pandas или SQL

Если данные после извлечения лежат в файле (например, путь пришёл по XCom от extract) или во временной таблице, таск **transform** может:

- **Прочитать** источник (файл через Pandas, таблицу через Hook и SQL).
- **Применить** очистку: приведение типов, заполнение пропусков, дедупликация, фильтрация, переименование колонок.
- **Записать** результат во временный файл или во временную/целевую таблицу; путь или ключ при необходимости передать следующей задаче через return (XCom).

Пример схемы с Pandas (среда: Airflow 2.x, Python 3.x, pandas):

```python
def transform_sales(**context):
    ti = context["ti"]
    path_in = ti.xcom_pull(task_ids="extract")  # путь от extract
    ds = context["ds"]
    df = pd.read_csv(path_in)
    # очистка, типы, дедупликация
    df["date"] = ds
    path_out = f"/data/staging/sales_{ds}.parquet"
    df.to_parquet(path_out, index=False)
    return path_out

transform = PythonOperator(
    task_id="transform",
    python_callable=transform_sales,
    dag=dag,
)
```

Если преобразование делается в БД (SQL поверх временной таблицы), можно использовать **PostgresOperator** или PythonOperator с **PostgresHook**: выполнить `INSERT INTO staging.sales SELECT ... FROM raw.sales WHERE ...`, с учётом идемпотентности (см. ниже). Подробнее операторы и хуки — в [главе 7](chapter-07-01.md).

## 6.3.2. Преобразование: BashOperator и внешний ETL-скрипт

Альтернатива — вынести логику преобразования в отдельный скрипт (Python, SQL-скрипт через psql и т.д.) и вызывать его из **BashOperator**. Дата и пути передаются аргументами; при необходимости путь к входному файлу берётся из переменной окружения, которую предыдущая задача записала в XCom и которую можно подставить через шаблон или через передачу в скрипт. Пример:

```python
transform = BashOperator(
    task_id="transform",
    bash_command="python /path/to/transform_sales.py --date {{ ds }} --input {{ ti.xcom_pull(task_ids='extract') }}",
    dag=dag,
)
```

В реальности подстановка XCom в bash_command может требовать обёртки (например, предварительно записать путь в Variable или передать через PythonOperator). Часто проще передавать только дату (`{{ ds }}`), а скрипт сам определяет путь к файлу по соглашению (например, `/data/raw/sales_{{ ds }}.csv`). Подробнее XCom в шаблонах — в [§7.4](chapter-07-04.md).

## 6.3.3. Загрузка в целевую БД

Таск **load** записывает итоговые данные в целевую таблицу Raw или Staging. Реализация зависит от формата данных (файл Parquet/CSV или уже таблица в БД) и выбранной **идемпотентности** ([§6.1](chapter-06-01.md)).

**Полная перезапись среза за дату:** для логической даты `ds` удалить из целевой таблицы все строки с этой датой (или перезаписать партицию) и вставить новые. В PostgreSQL, например: `DELETE FROM raw.sales WHERE date = :ds;` и затем `INSERT ...` или использование временной таблицы и перезапись партиции. В PythonOperator с PostgresHook — выполнить эти запросы; дату подставить из `context["ds"]`.

**Upsert по ключу:** вставка с обработкой конфликта (ON CONFLICT DO UPDATE в PostgreSQL, MERGE в других СУБД). Подходит, когда один и тот же ключ может приходить повторно и нужно обновлять запись.

Пример схемы загрузки с перезаписью за дату (PythonOperator + PostgresHook):

```python
def load_to_raw(**context):
    ds = context["ds"]
    path = context["ti"].xcom_pull(task_ids="transform")
    hook = PostgresHook(postgres_conn_id="dwh")
    # прочитать path (например, Parquet), удалить за ds, вставить новые строки
    # в реальности: df = pd.read_parquet(path); DELETE; insert в БД
    ...

load = PythonOperator(
    task_id="load",
    python_callable=load_to_raw,
    dag=dag,
)
```

Подключение к DWH задаётся в Connections ([§7.5](chapter-07-05.md)). Для больших объёмов часто используют bulk-загрузку (COPY в PostgreSQL, загрузка из файла в облачное хранилище и т.д.).

## 6.3.4. Объединение transform и load в один таск

Если преобразование лёгкое и загрузка идёт сразу в целевую таблицу, шаги **transform** и **load** можно объединить в одну задачу: прочитать из источника (файл или Raw), преобразовать в памяти и записать в Staging/Raw одной операцией. Тогда в DAG будет, например, extract >> transform_and_load. Разделение на два таска полезно, когда нужна отдельная наблюдаемость (логи и ретраи по шагам) или когда transform и load выполняются в разных системах.

---

## Ключевое

- **Преобразование** реализуют **PythonOperator** (Pandas, SQL через Hook) или **BashOperator** (вызов ETL-скрипта с датой и путями). Вход — путь или таблица от extract (XCom или соглашение по путям).
- **Загрузка** — запись в целевую БД (Raw/Staging) с учётом **идемпотентности**: перезапись среза за дату или upsert по ключу. Подключение к БД — через Hook и Connections.
- Transform и load можно объединить в один таск при простой логике; раздельные таски дают лучшую наблюдаемость и точечные retry.

В [§6.4](chapter-06-04.md) — связывание шагов extract >> transform >> load и настройка обработки сбоев (retries, алерты).
