# §5.3 start_date и расписание запусков

В [§5.2](chapter-05-02.md) мы разобрали **schedule_interval**: cron, timedelta и None. Ряд запусков планировщик строит от **start_date** и интервала. В этом разделе — как Airflow генерирует даты запусков (**логическая дата**, logical date), чем она отличается от времени фактического выполнения и зачем это важно для пайплайнов данных. Catchup и backfill — в [§5.4](chapter-05-04.md).

---

## 5.3.1. Роль start_date

**start_date** — дата (и при необходимости время), с которой планировщик **начинает ряд** DAG Run для данного DAG. Передаётся в конструктор `DAG()` как `datetime`. Планировщик не создаёт run «до» start_date; первый возможный run привязан к моменту, следующему за start_date по правилам schedule_interval. Например, при `start_date=datetime(2025, 1, 1)` и `schedule_interval="0 2 * * *"` первый логический момент запуска — 02:00 1 января 2025 (или следующий слот по cron в зависимости от трактовки «конец интервала» в вашей версии Airflow). Точная семантика «первого run» в Airflow 2.x привязана к **data interval**: run за период [start_date, start_date + interval). Для упрощения: start_date задаёт «не раньше какой даты» создавать run.

Важно: **start_date — это не «момент первого запуска в календаре»** в смысле «когда пользователь впервые нажал Play». Это начало **логического ряда периодов** для пайплайна. Реальное время первого запуска зависит от того, когда DAG был включён и когда сработал планировщик.

---

## 5.3.2. Логическая дата (logical date) и data interval

Каждый DAG Run в Airflow привязан к **логической дате** (в документации и коде часто **logical date**; в старых версиях использовался термин **execution_date**). Это дата (и время), которые интерпретируются как **период данных**, за который работает пайплайн: «загрузка за 2025-02-14» означает run с логической датой, соответствующей этому дню. Задачи в run получают эту дату в контексте (например, `ds` в шаблонах — строка `YYYY-MM-DD`) и могут передавать её в скрипты и запросы: какой файл читать, какую партицию писать, за какой день считать витрину.

В Airflow 2.2+ явно введён **data interval**: интервал времени [start, end), за который «отвечает» данный run. Логическая дата обычно совпадает с началом этого интервала или с концом (в зависимости от версии и типа расписания). Для ежедневного пайплайна «за вчера» типичная трактовка: run с логической датой 2025-02-14 обрабатывает данные за 14 февраля. Таким образом, **логическая дата — это идентификатор периода данных**, а не момент «сейчас» в момент запуска задачи.

---

## 5.3.3. Не путать с временем фактического выполнения

**Время фактического выполнения** (actual execution time) — это реальные часы и минуты, когда планировщик поставил задачу в очередь и когда воркер её выполнил. Оно может отличаться от логической даты и от времени срабатывания cron:

- Пайплайн с расписанием «каждый день в 02:00» и логической датой 2025-02-14 может реально стартовать в 02:05 или 02:30 из‑за задержки планировщика или очереди.
- Логическая дата run остаётся «2025-02-14» (или соответствующий timestamp); в коде задач нужно опираться на **логическую дату** из контекста (`ds`, `data_interval_start` и т.д.), а не на `datetime.now()`.

Если в задаче использовать текущее время вместо логической даты, при переносе запуска, backfill или сдвиге расписания логика «за какой день данные» сломается. Всегда берите дату/время из контекста Airflow (шаблоны Jinja, `**context` в PythonOperator).

---

## 5.3.4. Как планировщик генерирует запуски

Планировщик периодически просматривает все DAG с ненулевым schedule_interval и для каждого:

1. Берёт **start_date** и **schedule_interval** (cron или timedelta).
2. Строит ряд **периодов** (data intervals) от start_date до «сейчас» (или до следующего момента по расписанию).
3. Для каждого периода проверяет, есть ли уже DAG Run с такой логической датой (или data interval). Если нет — создаёт run и ставит готовые к выполнению задачи в очередь.

При **catchup=True** планировщик создаёт run за все пропущенные периоды между start_date и текущим моментом (см. [§5.4](chapter-05-04.md)). При **catchup=False** — только «вперёд» от момента включения DAG, без догона за прошлое.

---

## 5.3.5. Пример для ежедневного пайплайна

```python
with DAG(
    dag_id="daily_load",
    schedule_interval="0 2 * * *",
    start_date=datetime(2025, 1, 1),
) as dag:
    ...
```

Планировщик будет создавать по одному run в сутки, с логической датой, соответствующей каждому дню (например, 2025-01-01, 2025-01-02, …). Задача может использовать в шаблоне `{{ ds }}` — подставится строка даты этого run (например, `2025-02-14`). Так пайплайн «знает», за какой день загружать данные, независимо от того, в какой час реально выполнилась задача.

---

## Ключевое

- **start_date** задаёт начало ряда периодов для DAG Run; планировщик не создаёт run раньше этой даты по правилам schedule_interval.
- **Логическая дата** (logical date) run — идентификатор **периода данных** (за какой день/интервал работает пайплайн). В задачах нужно использовать её из контекста (`ds`, data_interval и т.д.), а не текущее время.
- **Время фактического выполнения** может отличаться от логической даты и от времени cron; не опирайтесь на `datetime.now()` в логике «за какой период данные».
- Планировщик генерирует run по start_date и schedule_interval; при catchup создаёт run за пропущенные периоды.

В [§5.4](chapter-05-04.md) — catchup и backfill: запуск за прошлые периоды и ручной догон.
