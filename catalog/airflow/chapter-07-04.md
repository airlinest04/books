# §7.4 Передача данных между тасками (XCom)

В [§7.3](chapter-07-03.md) мы разобрали хуки для подключения к внешним системам. Задачи в одном DAG Run иногда должны **передавать друг другу данные**: путь к файлу, имя таблицы, ключ, счётчик. В Airflow для этого служит **XCom** (cross-communication). В этом разделе — как записать значение в XCom (**push**) и прочитать его в другой задаче (**pull**), **ограничения по размеру** и когда лучше передавать не сами данные, а **путь к файлу** или **ключ в БД**. Variables и Connections — в [§7.5](chapter-07-05.md). См. [Глоссарий](glossary.md).

---

## 7.4.1. Что такое XCom

**XCom** — механизм обмена небольшими артефактами между задачами в рамках одного DAG Run. Значение, записанное одной задачей (push), может прочитать другая задача (pull), указав task_id отправителя и при необходимости key. Данные хранятся в метаданных Airflow (БД); при использовании внешнего бэкенда (например, кастомного XCom backend) — в указанном хранилище. XCom привязан к **dag_id**, **run_id** (или логической дате run) и **task_id** отправителя, поэтому каждая задача в каждом run имеет свой набор записей XCom.

---

## 7.4.2. Push: запись значения

**Записать** значение в XCom можно явно или неявно.

**Неявно (return):** в **PythonOperator** возвращаемое значение callable автоматически записывается в XCom с ключом по умолчанию (например, `return_value`). Пример уже встречался в [§6.2](chapter-06-02.md):

```python
def extract(**context):
    path = f"/data/raw/sales_{context['ds']}.csv"
    # ... создание файла
    return path  # push в XCom

extract_task = PythonOperator(task_id="extract", python_callable=extract, dag=dag)
```

**Явно:** через объект **TaskInstance** в контексте — метод **xcom_push(key, value)**. Удобно, когда нужно записать несколько значений с разными ключами:

```python
def my_task(**context):
    ti = context["ti"]
    ti.xcom_push(key="path", value="/data/file.csv")
    ti.xcom_push(key="rows", value=1000)
```

В **BashOperator** вывод команды (stdout) в части версий тоже можно записать в XCom (опция или по умолчанию); тогда следующая задача сможет прочитать последнюю строку stdout через pull.

---

## 7.4.3. Pull: чтение значения

**Прочитать** значение в другой задаче можно через контекст: **context["ti"].xcom_pull(task_ids="extract", key="return_value")**. Если key не указан, обычно возвращается значение по ключу `return_value` (то, что вернул callable). Для явного push указывайте тот же key:

```python
def load(**context):
    ti = context["ti"]
    path = ti.xcom_pull(task_ids="extract", key="return_value")
    # или key="path", если делали xcom_push(key="path", ...)
    # далее работа с path
```

**task_ids** может быть списком; тогда xcom_pull вернёт значение от первой задачи из списка (или по правилу, описанному в документации вашей версии). Указывайте task_id той задачи, которая выполнилась в **том же DAG Run** — XCom изолирован по run.

---

## 7.4.4. Ограничения по размеру

Данные XCom хранятся в метаданных (по умолчанию в той же БД, что и остальные данные Airflow). Рекомендуется **не передавать через XCom большие объёмы**: большие строки, сериализованные датафреймы, бинарные данные. Это увеличивает нагрузку на БД и может упираться в лимиты размера поля (в старых версиях — порядка десятков килобайт или меньше в зависимости от бэкенда). Официальная документация Airflow рекомендует использовать XCom для небольших артефактов (идентификаторы, пути, ключи). Для больших данных используйте внешнее хранилище (файл, таблица) и через XCom передавайте только **ссылку** (путь, ключ).

---

## 7.4.5. Когда передавать путь к файлу или ключ в БД

Вместо передачи самих данных между задачами лучше передавать **ссылку**:

- **Путь к файлу** — первая задача пишет результат в файл (локальный или в облаке) и возвращает путь через return (XCom). Вторая задача по пути читает файл. Так не нагружаете метаданные и обходите ограничения размера XCom.
- **Ключ в БД** — первая задача записывает данные во временную таблицу или в таблицу с ключом (run_id, logical_date) и возвращает этот ключ через XCom. Вторая задача по ключу читает из БД. Подходит для больших объёмов и когда обе задачи работают с одной БД.

Итог: **XCom — для метаданных о результате** (путь, ключ, количество строк, статус), а не для самих больших данных. Это соответствует рекомендациям в [§6.2](chapter-06-02.md).

---

## 7.4.6. Типичные ошибки

- **Передача больших данных через return** — сериализация датафрейма или большого списка в XCom может привести к ошибкам или к медленной работе. Передавайте путь или ключ.
- **Pull до выполнения отправителя** — убедитесь, что зависимость между задачами задана (task_extract >> task_load); иначе задача с pull может выполниться раньше или в другом run.
- **Путаница task_ids** — в xcom_pull указывайте task_id задачи, которая действительно пишет нужное значение в этом run (при ветвлении может быть несколько задач; при необходимости укажите нужную).

---

## Ключевое

- **XCom** — обмен небольшими артефактами между задачами одного DAG Run: **push** (return в PythonOperator или ti.xcom_push) и **pull** (ti.xcom_pull(task_ids=..., key=...)).
- Есть **ограничения по размеру**; не передавайте большие данные. Передавайте **путь к файлу** или **ключ в БД**, следующая задача сама прочитает данные по этой ссылке.
- XCom привязан к run и task_id; pull выполняется после успешного завершения задачи-отправителя (задайте зависимости).
