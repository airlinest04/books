# §8.4 Оконные функции для оборотов и остатков

В [§8.3](chapter-08-03.md) мы разобрали пример распределения суммы по строкам. Для расчёта **остатка после каждой проводки** и **оборота с накоплением** по счёту удобны **оконные функции** SUM() OVER (PARTITION BY ... ORDER BY ...). Здесь мы сводим паттерны: нарастающий итог по счёту, рамка окна (ROWS BETWEEN) при необходимости и кратко — производительность. Концепция оборотов и остатков — в [§4.1](chapter-04-01.md)–[§4.4](chapter-04-04.md). См. [Глоссарий](glossary.md).

---

## 8.4.1. Нарастающий итог по счёту (остаток после проводки)

Остаток по счёту после каждой проводки = начальное сальдо + нарастающий итог движений (дебет − кредит) в порядке даты. В SQL это **SUM(amount_dt - amount_ct) OVER (PARTITION BY account_id ORDER BY post_date, id)**. См. [§4.3](chapter-04-03.md).

**PostgreSQL:**

```sql
SELECT
    account_id,
    post_date,
    id,
    amount_dt - amount_ct AS movement,
    SUM(amount_dt - amount_ct) OVER (
        PARTITION BY account_id
        ORDER BY post_date, id
    ) AS balance_running
FROM core.fact_postings
WHERE post_date BETWEEN :date_from AND :date_to
ORDER BY account_id, post_date, id;
```

При ненулевом начальном сальдо его прибавляют к первому значению в партиции или вводят отдельной строкой ([§4.3](chapter-04-03.md)). Среда: PostgreSQL 15; типы amount_dt, amount_ct — numeric. См. [§2.3](chapter-02-03.md).

**Oracle:** синтаксис тот же — SUM(amount_dt - amount_ct) OVER (PARTITION BY account_id ORDER BY post_date, id). Среда: Oracle 21c; колонки NUMBER. См. [§2.4](chapter-02-04.md).

---

## 8.4.2. Рамка окна: по умолчанию и ROWS BETWEEN

Без явной рамки при ORDER BY в оконной функции в стандарте SQL и в обеих СУБД по умолчанию используется рамка **от начала партиции до текущей строки** (RANGE/ROWS UNBOUNDED PRECEDING AND CURRENT ROW). Поэтому **SUM(...) OVER (PARTITION BY account_id ORDER BY post_date, id)** даёт нарастающий итог: для каждой строки сумма по всем строкам партиции с датой/id меньше или равным текущему. См. [§4.3](chapter-04-03.md).

Если нужна **скользящая сумма** только за последние N строк (или за последние N дней), задают рамку явно, например:

- **ROWS BETWEEN N PRECEDING AND CURRENT ROW** — текущая и N предыдущих строк по порядку ORDER BY.
- **RANGE BETWEEN INTERVAL '7' DAY PRECEDING AND CURRENT ROW** (где поддерживается) — по значению даты.

Для «остаток после каждой проводки» и «оборот с начала периода» достаточно порядка PARTITION BY account_id, ORDER BY post_date, id без явной рамки. См. [§4.4](chapter-04-04.md).

---

## 8.4.3. Обороты по месяцам и нарастающий итог за год

Если данные уже агрегированы по месяцам (одна строка на счёт и месяц), нарастающий итог по месяцам в пределах года:

```sql
-- PostgreSQL
SELECT
    account_id,
    month_start,
    turnover,
    SUM(turnover) OVER (
        PARTITION BY account_id
        ORDER BY month_start
    ) AS turnover_ytd
FROM monthly_turnover
ORDER BY account_id, month_start;
```

`monthly_turnover` — представление или CTE с оборотами по счёту и месяцу (см. [§4.1](chapter-04-01.md), [§4.4](chapter-04-04.md)). В Oracle синтаксис тот же. См. [Глоссарий](glossary.md).

---

## 8.4.4. Производительность

Оконные функции с ORDER BY обычно требуют **сортировки** по ключам партиции и порядка; при больших объёмах партиция по счёту и сортировка по дате могут быть затратными. Рекомендации:

- **Индекс** по (account_id, post_date, id) ускоряет и фильтр, и порядок в окне.
- Для «только итог по счёту за период» без построчного остатка чаще выгоднее **GROUP BY** и SUM ([§4.4](chapter-04-04.md)); оконная функция нужна, когда важна каждая строка с накоплением.
- При необходимости материализовать остатки на дату в таблицу снимков ([§6.2](chapter-06-02.md)) расчёт можно выполнять пайплайном раз в период, а не в каждом запросе.

См. [§4.4](chapter-04-04.md) (когда GROUP BY, когда оконные).

---

## 8.4.5. Типичные ошибки

- **Не указать PARTITION BY при нескольких счетах:** тогда нарастающий итог считается по всему набору строк; нужен PARTITION BY account_id.
- **Неоднозначный ORDER BY:** при равных post_date порядок должен быть задан однозначно (добавить id проводки в ORDER BY), иначе результат может меняться между запусками.
- **Путать нарастающий итог и оборот за период:** нарастающий итог — сумма с начала партиции до текущей строки; оборот за период — SUM по группе за выбранный интервал дат (GROUP BY, без окна). См. [§4.1](chapter-04-01.md), [§4.3](chapter-04-03.md).

---

## Ключевое

- **Остаток после каждой проводки** — SUM(amount_dt - amount_ct) OVER (PARTITION BY account_id ORDER BY post_date, id); в PostgreSQL и Oracle синтаксис совпадает; при ненулевом начальном сальдо его прибавляют отдельно.
- По умолчанию рамка окна — от начала партиции до текущей строки; для скользящей суммы за N строк задают ROWS BETWEEN N PRECEDING AND CURRENT ROW.
- **Оборот с накоплением за год** по помесячным данным — SUM(turnover) OVER (PARTITION BY account_id ORDER BY month_start).
- **Производительность:** индекс по (account_id, post_date, id); для только итогов за период предпочитать GROUP BY; при больших объёмах — снимки остатков.
