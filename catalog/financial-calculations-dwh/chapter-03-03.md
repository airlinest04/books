# §3.3 Распределение суммы по строкам с округлением

В [§3.2](chapter-03-02.md) мы разобрали TRUNC, FLOOR и CEIL. Частая практическая задача — **распределить одну общую сумму** (например, 100 руб.) по нескольким строкам **с округлением каждой доли** до копеек так, чтобы сумма округлённых значений **совпадала** с исходной суммой. Здесь мы формулируем задачу, показываем, почему наивное округление каждой доли даёт расхождение (99,99 вместо 100), вводим приём **«остаток на последнюю строку»** и обсуждаем **порядок строк**. Алгоритмы компенсации в общем виде — в [§3.4](chapter-03-04.md); пример на SQL — в [§8.3](chapter-08-03.md).

---

## 3.3.1. Постановка задачи

Дано:

- **Общая сумма** \(S\) (например, 100 руб.), которую нужно распределить по \(n\) строкам.
- **Доли** могут быть равными (поровну) или заданы весами (процент по контракту, доля в счёте). Здесь для простоты — равное распределение: каждая доля \(S/n\).
- Требование: каждая строка должна получить **сумму в копейках** (до двух знаков после запятой), и **сумма по строкам должна в точности равняться** \(S\).

Если просто округлить каждую долю до копеек (ROUND(\(S/n\), 2)), получится «сумма округлённых», которая в общем случае не равна \(S\) — это расхождение из [§1.1](chapter-01-01.md). Чтобы итог по строкам совпал с \(S\), нужно **скомпенсировать** остаток: добавить «лишние» или «недостающие» копейки одной или нескольким строкам. См. [Глоссарий](glossary.md).

---

## 3.3.2. Наивный подход: округлить каждую долю

При равном распределении \(S = 100\), \(n = 3\) точная доля равна \(100/3 = 33{,}\overline{3}\). Округляем каждую до двух знаков: ROUND(33.333…, 2) = 33,33. Присваиваем трём строкам по 33,33.

Сумма по строкам: 33,33 + 33,33 + 33,33 = **99,99**. Расхождение с исходными 100 руб. — **0,01**. Одна копейка «теряется». Для платёжки, акта или витрины это недопустимо, если регламент требует, чтобы сумма по строкам в точности равнялась общей сумме.

Общий случай: при делении \(S\) на \(n\) и округлении каждой доли до \(k\) знаков после запятой расхождение может достигать порядка \(n \cdot 10^{-k}/2\) (в худшем случае — до половины единицы последнего разряда на строку). Чтобы устранить расхождение, нужен явный шаг **компенсации остатка**.

---

## 3.3.3. Остаток на последнюю строку

Простой и часто применяемый приём — **остаток отдать одной строке** (как правило, последней в заданном порядке).

Алгоритм (поровну, до копеек):

1. Вычислить **базовую долю** с избыточной точностью: \(d = S / n\) (например, 33,333…).
2. Округлить базовую долю до копеек: \(d_0 = \mathrm{ROUND}(d, 2)\) (33,33).
3. Первым \(n - 1\) строкам присвоить \(d_0\).
4. **Последней** строке присвоить \(S - (n - 1) \cdot d_0\). Так сумма по строкам в точности равна \(S\).

Для \(S = 100\), \(n = 3\): первые две строки по 33,33; последняя строка \(100 - 33{,}33 - 33{,}33 = 33{,}34\). Итого: 33,33 + 33,33 + 33,34 = 100,00. Расхождение устранено. См. [Глоссарий](glossary.md).

Минус подхода: **последняя строка может отличаться от остальных** на копейку (или несколько), что иногда нежелательно по презентации (все «ровные», одна «с хвостом»). Если порядок строк не зафиксирован, «последняя» зависит от сортировки — результат может быть разным при разном порядке. Поэтому порядок строк должен быть **детерминированным** (по ID, по дате, по контракту и т.д.) и зафиксирован в регламенте.

---

## 3.3.4. Порядок строк и детерминированность

«Последняя» строка определяется **порядком**: сортировкой в запросе или порядком обхода в коде. Если порядок не задан, СУБД может возвращать строки в разном порядке при повторных выполнениях — тогда строка, получившая остаток, будет разной, и результаты перестанут быть воспроизводимыми.

Рекомендации:

- Задать **явную сортировку** при распределении: по первичному ключу, по дате, по приоритету. В SQL при использовании оконных функций или обхода курсором порядок задаётся в ORDER BY.
- Зафиксировать в бизнес-правиле: «остаток присваивается строке с максимальным ID» (или «последней по дате», «первой по приоритету» — в зависимости от того, кому по смыслу «достаётся» копейка).
- В отчётах и при сверке указывать, по какому полю определена «последняя» строка, чтобы при повторном расчёте результат совпадал.

Если по смыслу остаток должен получать не последняя, а, например, строка с наибольшей долей или с особым признаком, используют обобщённые алгоритмы компенсации из [§3.4](chapter-03-04.md).

---

## 3.3.5. Распределение по весам

Когда доли **не равные**, а заданы весами \(w_1, \ldots, w_n\) (например, проценты по договору), доля строки \(i\) равна:

\[
d_i = S \cdot \frac{w_i}{\sum_j w_j}.
\]

Сначала считают округлённые значения \(\widetilde{d}_i = \mathrm{ROUND}(d_i, 2)\). Сумма \(\sum_i \widetilde{d}_i\) может не совпадать с \(S\). Остаток \(S - \sum_i \widetilde{d}_i\) (в копейках) распределяют по правилу компенсации: одной строке (например, с максимальным весом или последней в порядке) или по нескольким строкам по алгоритму из §3.4. Порядок строк и правило «кому достаётся остаток» по-прежнему должны быть детерминированными.

---

## 3.3.6. Типичные ошибки

- **Не фиксировать порядок строк:** при разном ORDER BY «последняя» строка меняется — разный пользователь получает копейку; сверки и тесты нестабильны.
- **Считать, что «остаток на последнюю» всегда одна копейка:** остаток может быть 0 (если \(S/n\) округляется без потерь), 1 копейка или в общем случае до \((n-1)\) копеек при неблагоприятном распределении долей. Последняя строка получает не «+1 копейка», а ровно то значение, которое обеспечивает сумму \(S\).
- **Путать «последнюю по сортировке» и «последнюю вставленную»:** в SQL порядок задаётся явно в запросе (ORDER BY); без него порядок строк не гарантирован.

---

## Ключевое

- Задача **распределения суммы по строкам с округлением**: раздать \(S\) по \(n\) строкам так, чтобы каждая сумма была в копейках и сумма по строкам в точности равнялась \(S\).
- **Наивное** округление каждой доли даёт расхождение (например, 99,99 при 100 на 3); его устраняют **компенсацией остатка**.
- Приём **«остаток на последнюю строку»**: первым \(n-1\) строкам — ROUND(\(S/n\), 2); последней — \(S\) минус сумма первых. Сумма по строкам тогда в точности \(S\).
- **Порядок строк** должен быть **детерминированным** (ORDER BY по ключу/дате/приоритету), иначе «последняя» строка и результат не воспроизводимы.
- При **распределении по весам** доли считают по весам, округляют, затем остаток распределяют по выбранному правилу компенсации.

В [§3.4](chapter-03-04.md) мы разберём общие алгоритмы компенсации: добавление копеек к «большим» строкам, итеративное распределение остатка и учёт приоритетов.
