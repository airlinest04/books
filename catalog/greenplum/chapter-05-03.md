# §5.3 Колоночное хранение (AO Columnar)

В [§5.2](chapter-05-02.md) мы разобрали append-optimized таблицы и AO row. **AO columnar** (колоночное хранение) — это AO с **orientation=column**: значения каждого столбца хранятся отдельно, что даёт выигрыш по I/O и сжатию для аналитических запросов, обращающихся к немногим столбцам. В этом разделе — как устроено колоночное хранение, создание таблицы, **сжатие** (RLE, ZLIB, ZSTD, в том числе на уровне столбца), когда использовать columnar и когда предпочесть row или heap. По [Tanzu Greenplum 7 — Choosing the Table Storage Model](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-ddl-ddl-storage.html).

---

## 5.3.1. Хранение по столбцам

При **column-oriented** (колоночном) хранении данные организованы по столбцам: все значения первого столбца идут подряд, затем второго и т.д. При запросе, который читает один или несколько столбцов (например, SUM(amount), AVG(price) WHERE region_id = 5), с диска поднимаются только нужные столбцы — меньше I/O и лучше использование кэша. Кроме того, в одном столбце тип данных один и тот же, поэтому сжатие (в том числе по повторяющимся или близким значениям) часто эффективнее, чем при построчном хранении. См. [Глоссарий](glossary.md) (Row-oriented; там же противопоставление column).

Недостаток: при записи одной строки нужно писать в несколько «колонок» (блоков по столбцам), поэтому колоночные таблицы **не оптимизированы под частые одиночные INSERT**; предпочтительна массовая загрузка. Для таблиц с частыми построчными изменениями лучше heap ([§5.1](chapter-05-01.md)) или AO row ([§5.2](chapter-05-02.md)).

В Greenplum колоночное хранение доступно **только для append-optimized** таблиц: задаётся **orientation=column** вместе с **appendoptimized=true**.

---

## 5.3.2. Создание AO columnar-таблицы

В секции **WITH** указывают **appendoptimized=true** и **orientation=column**. Ключ распределения (**DISTRIBUTED BY**) задаётся как обычно. Пример:

```sql
CREATE TABLE fact_orders (
    order_id    bigint,
    order_date  date,
    customer_id int,
    product_id  int,
    quantity    int,
    amount      numeric(12,2)
) WITH (appendoptimized=true, orientation=column)
  DISTRIBUTED BY (order_id);
```

Для партиционированных таблиц orientation и другие опции хранения можно задавать на уровне партиций и подпартиций; дочерние партиции наследуют настройки. См. документацию Greenplum по партиционированию и хранению.

---

## 5.3.3. Сжатие колоночных таблиц

Для **AO columnar** доступны сжатие на уровне таблицы и **на уровне столбца** (**ENCODING**). Алгоритмы: **RLE_TYPE** (run-length encoding), **ZLIB**, **ZSTD**. RLE хорошо подходит для столбцов с повторяющимися значениями (коды, категории, даты при загрузке в порядке); для числовых типов (BIGINT, INTEGER, DATE, TIME, TIMESTAMP) Greenplum может комбинировать RLE с delta-сжатием при загрузке в отсортированном порядке. См. документацию Greenplum.

**Уровни сжатия:** ZLIB — compresslevel 1–9; ZSTD — 1–19; RLE_TYPE — несколько уровней (от «только RLE» до «RLE + zlib/zstd»). Чем выше уровень, тем обычно лучше степень сжатия и выше нагрузка на CPU.

**Задание сжатия по столбцам** — через **ENCODING** в определении столбца или **COLUMN ... ENCODING**, при необходимости **DEFAULT COLUMN ENCODING** для таблицы. Столбцы без своей ENCODING наследуют настройки по умолчанию. Пример:

```sql
CREATE TABLE analytics_events (
    event_id   bigint ENCODING (compresstype=zstd),
    event_date date  ENCODING (compresstype=rle_type),
    region_id  int   ENCODING (compresstype=zlib, compresslevel=5),
    value      float
) WITH (appendoptimized=true, orientation=column)
  DISTRIBUTED BY (event_id);
```

Параметр **blocksize** (размер блока в байтах, кратный 8192, в заданном диапазоне) управляет размером единицы хранения по столбцу; больший блок может улучшить сжатие, но увеличивает потребление памяти. Не используйте сжатые AO-таблицы на сжатых файловых системах. См. [§5.2](chapter-05-02.md).

## 5.3.4. Когда использовать колоночное хранение

Колоночное хранение целесообразно, когда:

- **Запросы обращаются к малому числу столбцов**: агрегации (SUM, AVG, COUNT) по одному или нескольким столбцам; фильтрация **WHERE** по одному столбцу с отсечением большого объёма строк; проекция с небольшим набором столбцов. Чем меньше столбцов участвует в запросе, тем больше выигрыш от колоночного формата.
- **Таблица широкая** (много столбцов), но типичные запросы читают лишь часть из них — колоночный формат уменьшает объём читаемых данных.
- **Данные загружаются пачками** и редко обновляются по строкам — те же ограничения, что и у AO row; одиночные INSERT не рекомендуются.

**Row-oriented (heap или AO row)** предпочтительнее, когда:

- Нужны **целиком строки** или много столбцов одной строки (OLTP-подобные запросы, выборка по ключу с возвратом всей строки).
- **Частые INSERT** по одной или немногим строкам — колоночная запись менее эффективна.
- Нужны **частые UPDATE/DELETE** по строкам — heap даёт полную поддержку; для AO ограничения см. [§5.2](chapter-05-02.md).

Сводка по выбору типа таблицы — в [§5.4](chapter-05-04.md).

---

## 5.3.5. Ограничения AO columnar

Те же, что и у AO в целом: не рекомендуются одиночные INSERT; UPDATE/DELETE с ограничениями по уровню изоляции; триггеры и DECLARE ... FOR UPDATE не поддерживаются. Кроме того, колоночная запись дороже построчной при малом размере batch’а — предпочтительна массовая загрузка. CLUSTER на AO columnar только по B-tree индексу. См. [§5.2](chapter-05-02.md).

---

## 5.3.6. Типичные ошибки

- **Выбирать columnar для таблиц с запросами «вся строка»:** выигрыша нет, возможен проигрыш по сравнению с row.
- **Задавать сжатие без учёта данных:** RLE выгоден при повторяющихся значениях; на случайных данных может почти не сжимать или увеличивать объём; тестируйте на своих данных.
- **Игнорировать blocksize:** слишком большой blocksize при многих столбцах и партициях увеличивает потребление памяти; см. документацию по выбору blocksize.

---

## Ключевое

- **AO columnar** — append-optimized с **orientation=column**: данные хранятся по столбцам; меньше I/O при запросах к немногим столбцам, эффективнее сжатие.
- **Создание:** WITH (appendoptimized=true, orientation=column); сжатие — compresstype (zlib, zstd, rle_type), при необходимости **ENCODING** по столбцам, blocksize.
- **Когда использовать:** аналитические запросы с агрегациями и фильтрацией по немногим столбцам; широкие таблицы при узкой проекции. **Когда не использовать:** частые построчные INSERT/UPDATE/DELETE, запросы, возвращающие целые строки или много столбцов.

В [§5.4](chapter-05-04.md) мы сведу воедино выбор типа таблицы: heap, AO row и AO columnar в сценариях загрузки сырых данных, витрин и аналитики.
