# §8.2 Статистика и ANALYZE

В [§8.1](chapter-08-01.md) мы разобрали чтение плана (EXPLAIN, EXPLAIN ANALYZE). Оценки **cost** и **rows** в плане опираются на **статистику** таблиц и столбцов. Если статистика устарела или отсутствует, планировщик строит неоптимальные планы. В этом разделе — зачем нужна актуальная статистика, команда **ANALYZE**, **автоматический сбор статистики** (gp_autostats_*), настройка **выборки** (default_statistics_target, по столбцам) и кратко **autovacuum**. По [Tanzu Greenplum 7 — About Database Statistics](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-intro-about_statistics.html), [ANALYZE](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/ref_guide-sql_commands-ANALYZE.html).

---

## 8.2.1. Зачем нужна статистика планировщику

Планировщик выбирает план, минимизируя **оценку стоимости** выполнения. Стоимость считается на основе оценок: сколько строк вернёт скан, какой объём данных придётся переслать при motion, сколько строк попадёт в JOIN и т.д. Эти оценки берутся из **метаданных**, которые собирает **ANALYZE**: число строк и страниц таблицы (pg_class: reltuples, relpages), распределение значений по столбцам (pg_statistic / представление pg_stats) — доля NULL, число уникальных значений, гистограмма и наиболее частые значения. См. документацию Greenplum.

Если статистика **устарела** (после массовой загрузки или удаления не запускали ANALYZE) или **отсутствует** (новая таблица), оценки rows и cost искажаются: планировщик может выбрать неверный порядок JOIN, broadcast вместо redistribute или наоборот, неоптимальный способ агрегации. Поэтому **актуальная статистика — необходимое условие** для хороших планов. Сравнение оценок и факта в **EXPLAIN ANALYZE** ([§8.1](chapter-08-01.md)) помогает понять, пора ли обновить статистику. Когда **reltuples** в pg_class сильно расходится с реальным COUNT(*), по таблице нужно выполнить ANALYZE.

---

## 8.2.2. Команда ANALYZE

**ANALYZE** собирает статистику по содержимому таблиц и сохраняет её в системном каталоге (pg_statistic, обновляет reltuples/relpages в pg_class). Синтаксис:

```sql
ANALYZE [VERBOSE] [таблица [ (столбец [, ...] ) ]];
```

- Без аргументов — анализируются **все** обычные таблицы в текущей БД (может быть долго; обычно анализируют выборочно).
- **ANALYZE таблица** — только указанная таблица.
- **ANALYZE таблица (столбец1, столбец2, ...)** — только указанные столбцы (удобно для очень широких таблиц: собирать статистику по столбцам, участвующим в JOIN, WHERE, GROUP BY).

ANALYZE берёт блокировку **SHARE UPDATE EXCLUSIVE** и может выполняться параллельно с обычными запросами; длительные эксклюзивные операции его блокируют. Для **внешних таблиц** (external tables) статистика не собирается (или зависит от коннектора). См. справочник ANALYZE в документации Greenplum.

**Когда запускать:** после массовой загрузки (COPY, gpload, INSERT ... SELECT), после больших DELETE/UPDATE, после CREATE INDEX. Рекомендуется включать ANALYZE в пайплайн загрузки или выполнять по расписанию для ключевых таблиц. Проверка таблиц без статистики — представление **gp_toolkit.gp_stats_missing**. См. документацию Greenplum.

---

## 8.2.3. Выборка и настройка точности (statistics target)

Для **больших** таблиц Greenplum не читает каждую строку, а строит статистику по **выборке**, чтобы ANALYZE завершался за приемлемое время. Точность оценок зависит от размера выборки и от числа «слотов» статистики по столбцу (гистограмма, наиболее частые значения). См. документацию Greenplum.

**default_statistics_target** — параметр сервера (по умолчанию 100 в документации Greenplum 7; в части версий 25): задаёт размер гистограммы и списка наиболее частых значений по столбцу. Большее значение — более детальная статистика и дольше ANALYZE. Меняется через **gpconfig** ([§4.3](chapter-04-03.md)).

Для отдельного столбца можно задать свой целевой размер статистики:

```sql
ALTER TABLE fact_sales ALTER COLUMN region_id SET STATISTICS 200;
```

Столбцы, не участвующие в условиях и соединениях, можно исключить из сбора: **SET STATISTICS 0** — тогда ANALYZE этот столбец не обрабатывает. Диапазон значений — обычно 0–1000; -1 — вернуться к системному умолчанию. После изменения статистики по столбцу нужно снова выполнить ANALYZE по этой таблице. См. справочник ALTER TABLE.

## 8.2.4. Партиционированные таблицы и ROOTPARTITION

У **партиционированных** таблиц статистика собирается по **листовым партициям**; при необходимости отдельно обновляют статистику **корневой** партиции (root), которую использует оптимизатор GPORCA для оценки по всей таблице. См. [§6.3](chapter-06-03.md).

**ANALYZE имя_корневой_таблицы** — сбор статистики по всем листовым партициям и при включённом по умолчанию **optimizer_analyze_root_partition** — по корню. **ANALYZE ROOTPARTITION имя_таблицы** — обновить только статистику корневой партиции (на основе уже собранной статистики листьев или выборки по данным). **ANALYZE ROOTPARTITION ALL** — обновить корневую статистику у всех партиционированных таблиц в БД. Если изменились только несколько листовых партиций, можно выполнить ANALYZE только по ним; при наличии статистики у остальных листьев корень при необходимости обновляют отдельно (ANALYZE ROOTPARTITION). См. документацию Greenplum по партиционированию и GPORCA.

## 8.2.5. Автоматический сбор статистики (gp_autostats_*)

Greenplum может **автоматически** запускать ANALYZE при определённых операциях. Режим задаётся параметром **gp_autostats_mode**:

- **on_no_stats** (по умолчанию для операций вне функций) — ANALYZE запускается для таблицы **без статистики** при первом INSERT, COPY или CREATE TABLE AS SELECT в эту таблицу (выполняет владелец таблицы или при включённом gp_autostats_allow_nonowner — пользователь, выполнивший операцию).
- **on_change** — ANALYZE запускается, когда число затронутых строк (INSERT, UPDATE, DELETE, COPY, CREATE TABLE AS SELECT) **превышает порог** **gp_autostats_on_change_threshold**. Порог по умолчанию очень большой (2^31-1), то есть по сути отключён; для реального срабатывания его нужно снизить. Режим on_change может вызывать тяжёлые ANALYZE в неожиданный момент и не рекомендуется глобально; иногда его включают на уровень сессии после загрузки.
- **none** — автоматический сбор отключён.

**gp_autostats_mode_in_functions** управляет тем же для операций внутри процедурного кода (по умолчанию **none**). Параметр **log_autostats** включает логирование срабатываний автоанализа. См. документацию Greenplum. В продакшене часто полагаются на **явный** ANALYZE после загрузки или по расписанию, а автосбор оставляют только on_no_stats, чтобы новые таблицы не оставались без статистики.

## 8.2.6. Утилита analyzedb и VACUUM

Утилита **analyzedb** (командная строка) анализирует таблицы БД **вне сессии** с БД: можно задать список таблиц, параллельные сессии; утилита может **пропускать** неизменённые таблицы или партиции (для AO-таблиц сохраняется состояние в каталоге db_analyze). Удобна для регулярного обновления статистики по расписанию. См. справочник утилит Greenplum.

Перед ANALYZE **сильно раздутой** таблицы (много мёртвых строк после массовых DELETE/UPDATE) рекомендуется выполнить **VACUUM** (или VACUUM FULL по необходимости): если выборка ANALYZE попадёт в пустые страницы, статистика будет неточной. **VACUUM ANALYZE** выполняет оба шага подряд, но в документации Greenplum предпочтение отдаётся раздельному выполнению VACUUM и ANALYZE, так как цели у них разные. **Autovacuum** в Greenplum занимается очисткой мёртвых строк (bloat) и при необходимости может запускать анализы; настройки и политику см. в руководстве по администрированию. См. документацию Greenplum.

## 8.2.7. Типичные ошибки

- **Не запускать ANALYZE после загрузки:** новые или сильно изменившиеся таблицы остаются с устаревшей или пустой статистикой; планы ухудшаются. Включите ANALYZE в скрипты загрузки или в расписание.
- **Запускать ANALYZE по всей БД без необходимости:** ANALYZE без аргументов обрабатывает все таблицы и может занимать много времени; предпочтительнее анализировать изменённые таблицы или использовать analyzedb с фильтрами.
- **Игнорировать расхождение оценок и факта в EXPLAIN ANALYZE:** если rows или cost сильно расходятся с фактическими — обновите статистику (ANALYZE) и при необходимости увеличьте statistics target для ключевых столбцов.

---

## Ключевое

- **Статистика** (pg_statistic, reltuples/relpages) нужна планировщику для оценки cost и rows; устаревшая или отсутствующая статистика ведёт к плохим планам.
- **ANALYZE** собирает статистику по таблице (или по указанным столбцам); запускайте после загрузки и крупных изменений; для партиционированных таблиц при GPORCA нужна статистика корня (ANALYZE по корню или ANALYZE ROOTPARTITION).
- **Настройка выборки:** **default_statistics_target** и **ALTER TABLE ... SET STATISTICS** по столбцам; автоматический сбор — **gp_autostats_mode** (on_no_stats, on_change, none). При сильном bloat перед ANALYZE выполните VACUUM.

В [§8.3](chapter-08-03.md) мы разберём **типичные узкие места**: перекос данных (data skew), выбор broadcast vs redistribute, лишние motion и перераспределение.
