# §8.4 Профилирование и настройка

В [§8.3](chapter-08-03.md) мы разобрали типичные узкие места: перекос, broadcast/redistribute, лишние motion. Чтобы устранять их, нужно находить медленные запросы и управлять ресурсами кластера. В этом разделе — **параметры GUC**, влияющие на память (**work_mem**, **statement_mem**), лимит памяти на сегменте (**gp_vmem_protect_limit**), **очереди ресурсов** (resource queues) и **профилирование медленных запросов** (логирование, pg_stat_activity, поиск тяжёлых запросов и переход к EXPLAIN ANALYZE). По [Tanzu Greenplum 6 — Memory and Resource Management with Resource Queues](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/6/greenplum-database/best_practices-workloads.html), [Tanzu Greenplum 7 — Query Profiling](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-query-topics-query-profiling.html).

---

## 8.4.1. Параметры GUC и уровни настройки

Параметры сервера Greenplum (GUC) задаются в **postgresql.conf** на координаторе и сегментах; для кластера их удобно просматривать и менять через **gpconfig** ([§4.3](chapter-04-03.md)). Часть параметров можно менять **на лету** (SET в сессии, или gpstop -u для применения изменений в конфиге без перезапуска). Другие требуют перезапуска (gpstop -r). Документация по каждому параметру указывает, нужен ли перезапуск.

Уровни: **системный** (postgresql.conf), **уровень базы**, **роли**, **сессии**. SET в сессии переопределяет значение для текущего соединения и полезен для точечной настройки одного запроса (например, SET statement_mem='256MB'; перед тяжёлым запросом). Не меняйте значения по умолчанию глобально, пока не поймёте влияние на память и конкуренцию запросов. См. документацию Greenplum по конфигурации.

---

## 8.4.2. work_mem и statement_mem

**work_mem** — объём памяти (на один сегмент), который может использовать **одна операция** (Sort, Hash Join, Hash Aggregate и т.д.) внутри запроса. Если данных больше, операция сбрасывает промежуточные результаты на диск (spill, workfile); это замедляет выполнение. В выводе **EXPLAIN ANALYZE** для узлов, использующих work_mem, показываются **Work_mem used** и **Work_mem wanted**: «wanted» — оценка памяти, которой не хватило, чтобы избежать сброса на диск. Если виден большой «wanted» или сообщение о workfile I/O, имеет смысл увеличить work_mem для этой сессии или запроса. См. [§8.1](chapter-08-01.md).

**statement_mem** — **максимальная память на весь запрос** (statement) на **каждый сегмент**. Запрос не может использовать больше этого объёма на сегменте; при нехватке также происходит spill. Значение по умолчанию в документации Greenplum 6 — 125 MB (в других версиях может быть 128 MB). Верхняя граница задаётся параметром **max_statement_mem**; кроме того, при использовании очередей ресурсов действует лимит очереди (MEMORY_LIMIT). Рекомендуемая формула для statement_mem при настройке кластера: **(gp_vmem_protect_limit × 0,9) / max_expected_concurrent_queries** — чтобы при ожидаемом числе одновременных запросов суммарное использование не превышало защищённый лимит. Например, при gp_vmem_protect_limit = 8 GB и максимум 40 одновременных запросов: (8 × 0,9) / 40 ≈ 184 MB на запрос. Для запросов с **низкими** требованиями к памяти иногда выгодно **уменьшить** statement_mem (например, 1–3 MB), чтобы не резервировать лишнее и дать место другим запросам. См. документацию Greenplum.

## 8.4.3. gp_vmem_protect_limit и защита от исчерпания памяти

**gp_vmem_protect_limit** задаёт **максимальный объём памяти**, который все процессы сегмента (все сессии на этом сегменте) могут использовать в сумме. При достижении лимита новые запросы на этом сегменте могут завершаться с ошибкой out of memory; в документации рекомендуется рассчитывать безопасное значение по формулам (учёт RAM хоста, числа сегментов на хост, mirror). Никогда не задавайте значение выше доступной физической RAM. См. документацию Greenplum по конфигу памяти.

**runaway_detector_activation_percent** — процент использования gp_vmem_protect_limit, при превышении которого Greenplum начинает **принудительно завершать** запросы (сначала те, что потребляют больше всего памяти), пока использование не снизится. По умолчанию 90%. Это защита от «убегающего» потребления памяти. При частых out of memory: проверьте gp_vmem_protect_limit, уменьшите statement_mem или число одновременных запросов (очереди ресурсов), настройте запрос (уменьшите объём данных, перекос). См. документацию Greenplum.

**gp_workfile_limit_files_per_query** — максимальное число временных файлов (workfile) на один запрос при spill; по умолчанию 0 (неограниченно). Ограничение предотвращает заполнение диска одним запросом. **gp_workfile_compression** включает сжатие workfile при частых spill. См. документацию Greenplum.

## 8.4.4. Очереди ресурсов (resource queues)

**Очереди ресурсов** (resource queues) — механизм управления нагрузкой: лимит числа **одновременно выполняемых** запросов и лимит **памяти** для запросов, идущих через очередь. Каждая **роль** (пользователь) привязана к одной очереди; запрос пользователя попадает в эту очередь. Если лимит активных запросов исчерпан, новый запрос **ожидает** в очереди до освобождения слота. Очередь по умолчанию — **pg_default**. Суперпользователи не подчиняются лимитам очередей. См. [Глоссарий](glossary.md).

Создание и настройка:

```sql
CREATE RESOURCE QUEUE имя
  WITH (ACTIVE_STATEMENTS = n, MEMORY_LIMIT = 'значение');
ALTER ROLE имя_роли RESOURCE QUEUE имя_очереди;
```

- **ACTIVE_STATEMENTS** — максимум одновременно выполняемых запросов от ролей этой очереди.
- **MEMORY_LIMIT** — суммарный лимит памяти для запросов очереди **на один сегмент** (например, '2GB'). На хосте с несколькими сегментами суммарное использование = MEMORY_LIMIT × число сегментов на хосте.

Отдельно для очереди можно задать **STATEMENT_MEM** (максимальный statement_mem для запросов в очереди). Приоритеты очередей (PRIORITY) влияют на порядок получения ресурсов при конкуренции. Просмотр использования — представления **gp_toolkit.gp_resqueue_status** (или **gp_resqueue_status**): активные и ожидающие запросы по очередям. См. [§7.2](chapter-07-02.md), документацию Greenplum по workload management.

В ряде версий Greenplum доступны **resource groups** (ресурсные группы) — альтернативная схема с лимитами памяти, CPU и транзакций; сравнение и настройка описаны в руководстве по администрированию.

## 8.4.5. Профилирование медленных запросов

Цель — найти запросы, которые выполняются долго или потребляют много ресурсов, и затем разобрать их план (EXPLAIN ANALYZE) и контекст ([§8.1](chapter-08-01.md)–[§8.3](chapter-08-03.md)).

**Логирование по длительности:** параметр **log_min_duration_statement** (миллисекунды). Если задать, например, 5000, в лог координатора попадут только запросы, выполнившиеся дольше 5 секунд (вместе с длительностью и текстом). Значение 0 логирует все запросы; -1 отключает логирование по длительности. Для анализа медленных запросов задают порог (например, 10000 для 10 с) и просматривают лог (gplogfilter по времени и строке). Чтобы в лог не попадал текст всех запросов, а только медленных, оставляют **log_statement = 'none'** и используют только log_min_duration_statement. См. документацию Greenplum по логированию.

**Текущие запросы:** представление **pg_stat_activity** (на координаторе) показывает активные сессии и выполняемые запросы (query, state, query_start, и т.д.). Запросы, выполняющиеся дольше заданного интервала, можно отфильтровать, например: `SELECT * FROM pg_stat_activity WHERE state = 'active' AND (now() - query_start) > interval '15 minutes';` — для поиска «зависших» запросов. По необходимости запрос можно завершить (pg_cancel_backend, pg_terminate_backend). См. справочник по системным каталогам Greenplum.

**Историческая статистика:** при установленном расширении **pg_stat_statements** (если доступно в вашей версии) можно анализировать накопленную статистику по запросам (суммарное время, число вызовов, среднее время) и выбирать кандидатов на оптимизацию. Детали установки и представления — в документации Greenplum. Другие средства мониторинга (например, gpperfmon при его использовании) могут хранить историю выполненных запросов по порогу длительности.

**Цепочка действий:** включить log_min_duration_statement с порогом; по логам или pg_stat_statements выявить тяжёлые запросы; для выбранного запроса выполнить EXPLAIN ANALYZE; по плану проверить статистику (ANALYZE), motion, перекос, spill; при необходимости скорректировать statement_mem/work_mem, схему или текст запроса.

## 8.4.6. Типичные ошибки

- **Задавать statement_mem слишком большим глобально:** при высокой конкуренции запросов это ведёт к исчерпанию gp_vmem_protect_limit и out of memory; лучше ограничить очередь и задавать больший statement_mem только для отдельных сессий/запросов.
- **Игнорировать spill в EXPLAIN ANALYZE:** сообщения work_mem used/wanted и workfile I/O указывают на нехватку памяти; стоит увеличить work_mem или statement_mem для таких запросов или упростить запрос.
- **Не привязывать роли к очередям:** если все запросы идут через pg_default без лимитов, пики нагрузки могут исчерпать память; назначайте роли на очереди с ACTIVE_STATEMENTS и MEMORY_LIMIT.
- **Запускать тяжёлые запросы от суперпользователя:** суперпользователь обходит очереди ресурсов; для воспроизводимой нагрузки используйте обычную роль с назначенной очередью.

---

## Ключевое

- **work_mem** — память на одну операцию (Sort, Hash Join и т.д.); при нехватке — spill; в EXPLAIN ANALYZE смотрите Work_mem wanted. **statement_mem** — лимит памяти на запрос на сегмент; формула (gp_vmem_protect_limit×0,9)/concurrent_queries; для малопамятных запросов иногда уменьшают.
- **gp_vmem_protect_limit** — лимит суммарной памяти на сегмент; **runaway_detector_activation_percent** — порог принудительного завершения запросов при нехватке памяти.
- **Очереди ресурсов** (resource queues): ACTIVE_STATEMENTS, MEMORY_LIMIT; привязка ролей; мониторинг — gp_toolkit.gp_resqueue_status.
- **Профилирование:** log_min_duration_statement для логирования медленных запросов; pg_stat_activity для текущих; при наличии pg_stat_statements — для истории; далее — EXPLAIN ANALYZE и оптимизация по плану.

В [§9.1](chapter-09-01.md) мы перейдём к **внешним данным**: Protocol eXtension Framework (PXF), доступ к данным вне кластера без загрузки в Greenplum.
