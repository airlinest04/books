# §7.3 Массовая загрузка (COPY, gpload)

В [§7.2](chapter-07-02.md) мы разобрали представления gp_* и функции Greenplum. Загрузка больших объёмов данных в DWH выполняется **массово**: построчные INSERT неэффективны. В этом разделе — **COPY** для загрузки из файла или STDIN (синтаксис как в PostgreSQL, но данные идут через координатор), форматы **TEXT** и **CSV**, ограничения COPY и **gpload** для **параллельной** загрузки через внешние таблицы и **gpfdist**. Детали внешних таблиц и gpfdist — в гл. 9. По [Tanzu Greenplum 7 — Loading Data with COPY](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/admin_guide-load-topics-g-loading-data-with-copy.html), [gpload](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/utility_guide-ref-gpload.html).

---

## 7.3.1. COPY: загрузка из файла и STDIN

Команда **COPY** в Greenplum совместима с PostgreSQL: **COPY таблица FROM источник** загружает данные в таблицу. Источник — путь к файлу на **хосте координатора** или **STDIN** (стандартный ввод). Данные читаются **одним процессом на координаторе** и затем распределяются по сегментам; загрузка **не параллельная** в смысле одновременного чтения файла несколькими сегментами. Поэтому COPY рекомендуется для **небольших** объёмов (порядка тысяч строк); для больших файлов предпочтительна параллельная загрузка через gpfdist и внешние таблицы или **gpload**. См. документацию Greenplum.

**Файл на координаторе:** путь указывается **абсолютным** или относительно каталога данных координатора; файл должен быть доступен на чтение процессу postgres на хосте координатора.

```sql
COPY fact_sales (sale_id, sale_date, customer_id, amount)
FROM '/data/load/sales.csv'
WITH (FORMAT csv, HEADER true, DELIMITER ',');
```

**STDIN:** данные передаются по соединению от клиента к координатору. В **psql** для загрузки из файла, лежащего на **машине клиента**, используют **\copy** (метакоманда psql): она выполняет COPY FROM STDIN и передаёт содержимое файла с клиента, поэтому файл не нужно копировать на координатор.

```text
\copy fact_sales FROM '/local/path/sales.csv' WITH (FORMAT csv, HEADER true);
```

## 7.3.2. Форматы: TEXT, CSV, BINARY

В **COPY FROM** формат задаётся опцией **FORMAT**:

- **TEXT** (по умолчанию для COPY) — строки с разделителем столбцов; по умолчанию разделитель — табуляция (**DELIMITER E'\t'**); можно задать другой символ (**DELIMITER '|'**). Специальные последовательности (например, \N для NULL) обрабатываются как в PostgreSQL.
- **CSV** — формат CSV: разделитель по умолчанию запятая, кавычки, экранирование. Полезны опции **HEADER true** (первая строка — заголовок, не загружать), **QUOTE**, **ESCAPE**, **NULL** (строка для NULL).
- **BINARY** — бинарный формат PostgreSQL (реже используется при загрузке из внешних систем).

**ENCODING** задаёт кодировку файла (например, 'UTF8', 'LATIN1'), если она отличается от клиентской. См. справочник COPY в документации Greenplum.

Пример TEXT с разделителем-вертикальной чертой:

```sql
COPY dim_product FROM '/data/products.txt'
WITH (FORMAT text, DELIMITER '|', NULL '');
```

## 7.3.3. Ограничения COPY и когда переходить на параллельную загрузку

- **Один поток:** данные проходят через координатор; пропускная способность ограничена одним соединением и одним процессом чтения.
- **Файл на координаторе или по сети от клиента:** при COPY FROM файл файловая система координатора или STDIN; при \copy — файл на машине, где запущен psql.
- **Рекомендуемый объём:** для файлов до порядка 10–100 тыс. строк COPY часто достаточен; для миллионов строк и гигабайт данных предпочтительна **параллельная загрузка**.

**Параллельная загрузка** в Greenplum реализуется через **внешние таблицы** и демон **gpfdist**: gpfdist раздаёт файлы (или каталоги с файлами) сегментам по сети; каждый сегмент читает свою часть данных. Утилита **gpload** автоматизирует этот процесс: по YAML-описанию запускает gpfdist, создаёт внешнюю таблицу и выполняет INSERT (или UPDATE/MERGE) в целевую таблицу. См. подраздел 7.3.4 и гл. 9.

## 7.3.4. gpload: параллельная загрузка по YAML-конфигу

**gpload** — утилита загрузки, которая по **YAML-файлу** (control file) запускает **gpfdist**, создаёт временную **внешнюю таблицу** на основе описанных источников и выполняет **INSERT**, **UPDATE** или **MERGE** в целевую таблицу. Всё выполняется в одной транзакции. Запуск: **gpload -f control.yml** (и при необходимости -h, -p, -U, -d для подключения к координатору). gpload должен запускаться с машины, доступной по сети и координатору, и всем сегментам; на этой же машине (или доступном пути) должны лежать загружаемые файлы. На ней же gpload поднимает gpfdist. См. [Глоссарий](glossary.md).

Структура YAML (упрощённо):

- **VERSION** — версия схемы (например, 1.0.0.1).
- **DATABASE**, **USER**, **HOST**, **PORT** — подключение к Greenplum (можно задать переменными окружения PGDATABASE, PGUSER, PGHOST, PGPORT).
- **GPLOAD:**
  - **INPUT** — источники и формат: **SOURCE** (LOCAL_HOSTNAME, PORT или PORT_RANGE, **FILE** — путь к файлу или каталогу), **FORMAT** (text | csv), **DELIMITER**, **COLUMNS** (имя: тип), **HEADER**, **ENCODING**, **ERROR_LIMIT**, **LOG_ERRORS** и др.
  - **OUTPUT** — **TABLE** (целевая таблица), **MODE** (insert | update | merge), при update/merge — **MATCH_COLUMNS**, **UPDATE_COLUMNS**, **MAPPING** (соответствие столбцов источника и цели).
  - **PRELOAD** — например **TRUNCATE: true** (очистить таблицу перед загрузкой).
  - **SQL** — **BEFORE** и **AFTER** (SQL до и после загрузки).

Отступы в YAML значимы; табы не используют. Пример минимального конфига для INSERT из CSV:

```yaml
---
VERSION: 1.0.0.1
DATABASE: mydb
USER: gpadmin
HOST: mdw
PORT: 5432
GPLOAD:
  INPUT:
    - SOURCE:
        LOCAL_HOSTNAME: etlhost
        PORT: 8081
        FILE:
          - /data/load/sales_*.csv
    - FORMAT: csv
    - DELIMITER: ','
    - HEADER: true
    - COLUMNS:
        - sale_id: integer
        - sale_date: date
        - customer_id: integer
        - amount: numeric
  OUTPUT:
    - TABLE: public.fact_sales
    - MODE: insert
  PRELOAD:
    - TRUNCATE: false
```

Запуск: `gpload -f load_sales.yaml`. Логи по умолчанию пишутся в ~/gpAdminLogs/gpload_YYYYMMDD. См. справочник gpload в документации Greenplum.

## 7.3.5. Режимы gpload: INSERT, UPDATE, MERGE

- **MODE: insert** (по умолчанию) — все строки из источника вставляются в целевую таблицу (INSERT INTO ... SELECT * FROM внешняя_таблица).
- **MODE: update** — обновление существующих строк: **MATCH_COLUMNS** задаёт столбцы для сопоставления строк источника и цели, **UPDATE_COLUMNS** — какие столбцы цели обновлять значениями из источника. Опционально **UPDATE_CONDITION** (условие в стиле WHERE).
- **MODE: merge** — вставка новых строк и обновление существующих по MATCH_COLUMNS; если по ключу совпадения нет, строка вставляется целиком.

Для update и merge целевая таблица должна допускать однозначное сопоставление; при необходимости задают **MAPPING** (соответствие имён столбцов источника и цели). UPDATE и MERGE не поддерживаются, если имя столбца цели — зарезервированное слово, с заглавными буквами или требует кавычек. См. документацию gpload.

## 7.3.6. Обработка ошибок и опции загрузки

**ERROR_LIMIT:** при задании этого параметра включается режим изоляции ошибок по строкам: строки с ошибками формата (лишние/недостающие столбцы, неверный тип, неверная кодировка) пропускаются, пока число таких строк на каждом сегменте не превысит лимит. Успешные строки загружаются; при превышении лимита загрузка прерывается. Ошибки ограничений (например, нарушение первичного ключа) по-прежнему приводят к откату операции.

**LOG_ERRORS: true** (при заданном ERROR_LIMIT) — сведения об отброшенных строках записываются в служебную таблицу; просмотр через функцию **gp_read_error_log('имя_таблицы')**. Для сохранения лога между запусками нужна опция **REUSE_TABLES: true**.

**PRELOAD — TRUNCATE: true** — перед загрузкой таблица очищается. **REUSE_TABLES: true** — внешние и промежуточные объекты не удаляются после загрузки (удобно для повторяющихся загрузок в одну и ту же таблицу). См. справочник gpload.

## 7.3.7. Типичные ошибки

- **Использовать COPY для очень больших файлов:** данные идут через координатор; для гигабайт данных используйте gpload или внешние таблицы с gpfdist.
- **Указывать в COPY путь к файлу с клиента:** COPY читает файл на координаторе; для файла на клиенте используйте **\copy** в psql.
- **Ошибаться в отступах в YAML gpload:** в YAML важны пробелы; табы не допускаются; неверный отступ приводит к ошибке разбора.
- **Забывать, что gpload запускает gpfdist на машине запуска:** хост с файлами должен быть доступен сегментам по сети; LOCAL_HOSTNAME и порт должны быть разрешены файрволом для сегментов.

---

## Ключевое

- **COPY** — загрузка из файла (на координаторе) или STDIN; **не параллельная**; подходит для небольших объёмов; форматы **TEXT**, **CSV**, **BINARY**; в psql **\copy** загружает файл с клиента.
- **gpload** — параллельная загрузка по **YAML-конфигу**: запускает **gpfdist**, создаёт внешнюю таблицу, выполняет INSERT/UPDATE/MERGE; секции INPUT (SOURCE, FILE, FORMAT, DELIMITER, COLUMNS), OUTPUT (TABLE, MODE), PRELOAD (TRUNCATE).
- Для больших объёмов предпочтительны **gpload** или внешние таблицы с gpfdist; COPY — для малых файлов и простых сценариев.
