# §6.1 DISTRIBUTED BY: выбор ключа распределения

В [§5.4](chapter-05-04.md) мы свели воедино выбор типа таблицы. Данные в Greenplum **распределены по сегментам**: каждая строка попадает на один сегмент по правилу, заданному при создании таблицы. От выбора **ключа распределения** зависят равномерность загрузки сегментов и возможность выполнять **JOIN без пересылки данных** (локальные соединения). В этом разделе — как работает **hash-распределение** по столбцу(ам), как оно влияет на JOIN и как выбирать ключ. DISTRIBUTED RANDOMLY и партиционирование — в [§6.2](chapter-06-02.md) и [§6.3](chapter-06-03.md). По [VMware Greenplum 6 — Distribution and Skew](https://docs.vmware.com/en/VMware-Greenplum/6/greenplum-database/admin_guide-distribution.html).

---

## 6.1.1. Как данные распределяются по сегментам

При создании таблицы в Greenplum нужно указать **политику распределения**: как строки разбиваются по сегментам. Основной способ — **DISTRIBUTED BY (столбец [, столбец ...])**: по значению указанного ключа вычисляется **хеш**, по нему определяется номер сегмента (content id), и строка сохраняется на соответствующем primary-сегменте. Строки с **одинаковым значением ключа** всегда попадают на **один и тот же сегмент**. См. [Глоссарий](glossary.md) (DISTRIBUTED BY, Content id).

Пример:

```sql
CREATE TABLE fact_sales (
    sale_id     bigint,
    customer_id int,
    product_id  int,
    amount      numeric(12,2)
) DISTRIBUTED BY (customer_id);
```

Все строки с одним и тем же `customer_id` окажутся на одном сегменте. Ключ может быть составным, например `DISTRIBUTED BY (region_id, date_trunc('month', sale_date))` — порядок и типы столбцов важны для локальных JOIN. Количество сегментов задаётся при инициализации кластера и не зависит от конкретной таблицы; хеш равномерно размазывает значения по сегментам при условии, что сами значения ключа распределены достаточно равномерно.

## 6.1.2. Равномерность распределения и перекос (skew)

Скорость запроса в MPP ограничена **самым медленным сегментом**: пока все сегменты не закончат свою часть работы, результат не соберётся. Если данные **перекошены** (data skew) — один или несколько сегментов хранят заметно больше строк, чем остальные, — они становятся узким местом: больше I/O, больше памяти, дольше выполнение сканов, JOIN и агрегаций.

Перекос часто возникает при неудачном выборе ключа распределения: столбец с **низкой кардинальностью** (мало уникальных значений) даёт «кучки» строк на немногих сегментах. Примеры плохих ключей: пол (M/F), флаг (true/false), статус с 2–3 значениями. **Хороший ключ** — с **высокой кардинальностью** и по возможности равномерным распределением значений (идентификаторы, хеши, даты при большом диапазоне). См. документацию Greenplum.

Проверка распределения по сегментам — запросом к **gp_segment_id** (псевдостолбец, возвращающий номер сегмента для строки) с группировкой по нему и подсчётом строк; для выявления перекоса используют представления **gp_toolkit.gp_skew_idle_fractions** (доля «простаивающих» сегментов при скане) и **gp_toolkit.gp_skew_coefficients** (коэффициент вариации по сегментам). Перекос более 10% по idle fraction — повод пересмотреть политику распределения. После первоначальной загрузки и после инкрементальных загрузок распределение стоит проверять заново.

## 6.1.3. Влияние на JOIN: локальные соединения

При **JOIN** двух таблиц совпадающие строки должны оказаться на одном сегменте, чтобы соединение можно было выполнить локально (на каждом сегменте отдельно, без пересылки данных между сегментами). Такие соединения называются **локальными** (local, co-located). Они существенно быстрее: нет обмена по Interconnect, каждый сегмент обрабатывает только свои данные. См. [§2.4](chapter-02-04.md), [Глоссарий](glossary.md) (Motion).

Чтобы JOIN по некоторому столбцу (или набору столбцов) был локальным, **обе таблицы должны быть распределены по одному и тому же столбцу (или одним и тем же столбцам в одном порядке)**. Кроме того:

- Типы данных столбцов распределения должны **совпадать** на обеих таблицах (включая точность/масштаб для numeric). Иначе одинаковые по смыслу значения могут давать разный хеш и попадать на разные сегменты.
- **Все столбцы из DISTRIBUTED BY** должны участвовать в **условии JOIN**. Если таблица распределена по (a, b), а JOIN только по a, локального соединения не будет.

Пример: факт продаж и измерение клиентов часто соединяют по `customer_id`. Если обе таблицы распределены по `customer_id`, соединение по этому столбцу выполняется локально:

```sql
-- Обе таблицы распределены по customer_id
SELECT *
FROM fact_sales f
JOIN dim_customer c ON f.customer_id = c.customer_id;
```

Если одна из таблиц распределена по другому столбцу или по нескольким столбцам, не все из которых в условии JOIN, оптимизатор вынужден организовать **пересылку данных** (motion): **redistribute** (перераспределение по ключу JOIN) или **broadcast** (рассылка одной из таблиц на все сегменты). Оба варианта дороже локального JOIN; выбор между ними делает оптимизатор по оценке стоимости. См. [§8.1](chapter-08-01.md).

## 6.1.4. Redistribute и Broadcast

Когда таблицы не распределены по одному ключу JOIN:

- **Redistribute Motion:** данные одной или обеих сторон пересчитываются по хешу ключа JOIN и рассылаются на соответствующие сегменты. Стоимость пропорциональна объёму перераспределяемых данных.
- **Broadcast Motion:** одна из таблиц (обычно меньшая) целиком копируется на каждый сегмент. Стоимость пропорциональна размеру таблицы, умноженному на число сегментов.

Оптимизатор выбирает вариант с меньшей оценкой стоимости. Как правило, для **маленькой** таблицы выбирается broadcast, для **большой** — redistribute. Локальный JOIN избегает обоих типов motion и предпочтителен для больших таблиц, часто соединяемых по одному и тому же ключу.

## 6.1.5. Практические рекомендации по выбору ключа

1. **Определите основные JOIN:** таблицы, которые часто соединяют в запросах, по возможности распределите по **одному и тому же столбцу** (или одному набору столбцов в одном порядке), по которому идёт соединение. Типы должны совпадать.
2. **Высокая кардинальность:** предпочтительны столбцы с большим числом уникальных значений (id, ключи сущностей), чтобы минимизировать перекос.
3. **Избегайте низкой кардинальности:** не используйте в качестве единственного ключа распределения столбцы с 2–5 значениями (пол, регион из небольшого списка) — перекос будет большим.
4. **Составной ключ:** если JOIN идёт по нескольким столбцам, можно задать DISTRIBUTED BY (col1, col2, ...) в том же порядке и с теми же типами на обеих таблицах; все эти столбцы должны входить в условие JOIN для локального соединения.
5. **Проверяйте перекос:** после загрузки смотрите распределение по сегментам (gp_segment_id, gp_toolkit); при сильном перекосе смените ключ (ALTER TABLE ... SET DISTRIBUTED BY) и перезагрузите или перераспределите данные.

Изменение политики распределения через **ALTER TABLE ... SET DISTRIBUTED BY** приводит к **перераспределению данных** по сегментам — операция тяжёлая для больших таблиц. Ключ лучше выбирать при проектировании схемы. См. документацию Greenplum по ALTER TABLE и распределению.

---

## 6.1.6. Типичные ошибки

- **Распределять по столбцу с низкой кардинальностью:** сильный перекос, узкое место на нескольких сегментах; выбирайте ключ с множеством уникальных значений.
- **Соединять таблицы по столбцу, по которому они распределены по-разному:** локального JOIN не будет, появится redistribute или broadcast; для тяжёлых запросов выровняйте распределение под основные JOIN.
- **Распределять по разным типам при одинаковом смысле:** например, int на одной таблице и bigint на другой для одного и того же ключа — хеши не совпадут, локального JOIN не получится.
- **Забывать проверять перекос после загрузки:** перекос может накапливаться при инкрементальных загрузках; периодически проверяйте gp_toolkit и при необходимости корректируйте ключ или способ загрузки.

---

## Ключевое

- **DISTRIBUTED BY (столбец [, ...])** задаёт **hash-распределение**: строки с одинаковым значением ключа попадают на один сегмент; равномерность зависит от кардинальности ключа.
- **Локальный (co-located) JOIN:** обе таблицы распределены по одному и тому же столбцу(ам), в одном порядке, с совпадающими типами, и все эти столбцы участвуют в условии JOIN — пересылки данных нет.
- **Выбор ключа:** под основные JOIN; высокая кардинальность; избегать низкой кардинальности; проверять перекос (gp_toolkit, gp_segment_id) после загрузки.

В [§6.2](chapter-06-02.md) мы разберём **DISTRIBUTED RANDOMLY**: когда использовать случайное распределение и как оно соотносится с распределением по столбцам.
