# §4.4 Мониторинг и логи

В [§4.3](chapter-04-03.md) мы разобрали утилиты gpstate, gpconfig и gpcheck. Для диагностики сбоев и наблюдения за кластером важно знать **расположение логов**, уметь **анализировать ошибки** в них и при необходимости подключать **внешний мониторинг**. В этом разделе — где лежат логи координатора и сегментов, как искать в них ошибки (в том числе с помощью **gplogfilter**), ротация логов и варианты интеграции с системами мониторинга (Prometheus, Grafana, скрипты). По [Tanzu Greenplum 7 — Monitoring Log Files](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/best_practices-logfiles.html), [gplogfilter](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/utility_guide-ref-gplogfilter.html).

---

## 4.4.1. Где хранятся логи

Логи Greenplum делятся на две группы: **логи СУБД** (PostgreSQL/Greenplum: запросы, ошибки, старт/стоп экземпляра) и **логи утилит администратора** (gpstart, gpstop, gprecoverseg и т.д.). Расположение зависит от переменных окружения и параметра **log_directory** (если задан — логи СУБД пишутся туда; при абсолютном или внешнем пути Greenplum добавляет подкаталог с DBID). Ниже — пути по умолчанию. См. [Глоссарий](glossary.md).

**Логи координатора (Master):**

- **Логи СУБД:** `$COORDINATOR_DATA_DIRECTORY/log/` (в старых версиях — **MASTER_DATA_DIRECTORY**). Внутри: **startup.log** (старт экземпляра), а также файлы логов в формате CSV (по умолчанию имена вида `gpdb-YYYYMMDD_HHMMSS.csv` или аналогичные). Формат записей: timestamp, username, database, pid, tid, hostname, port, starttime, transactionid, gpdb-contents[], loglevel, errcode, messages.
- **Логи утилит:** каталог **gpAdminLogs** по умолчанию в домашней директории пользователя **gpadmin**: `$GPADMIN_HOME/gpAdminLogs/` (часто это `~/gpAdminLogs`). Туда пишутся, в частности: gpstart_*date*.log, gpstop_*date*.log, gpstatus_*date*.log, gprecoverseg_*date*.log, gpsegstart.py_*host*:*gpadmin*_*date*.log, gpsegstop.py_*host*:*gpadmin*_*date*.log, gpinitsystem_*date*.log и др. См. документацию по полному списку.

**Логи сегментов:**

- **Логи СУБД:** на каждом хосте сегментов в каталоге данных каждого экземпляра: `$GPDATA_DIR/segprefixN/log/` (для primary); для mirror — `$GPDATA_DIR/mirror/segprefixN/log/`. Там же startup.log и CSV-файлы логов. В путях *N* — номер сегмента, *segprefix* — префикс сегмента из конфигурации.
- Логи утилит на сегментных хостах при их запуске (gpsegstart и т.д.) при необходимости можно смотреть в gpAdminLogs на Master (по имени хоста в имени файла).

**Ротация логов СУБД** задаётся параметрами **log_rotation_size** (размер файла, при достижении которого создаётся новый) и **log_rotation_age** (время жизни текущего файла; по умолчанию 1d — новый файл раз в сутки). Настраиваются через gpconfig ([§4.3](chapter-04-03.md)).

## 4.4.2. Анализ ошибок в логах

При диагностике сбоев в первую очередь ищут сообщения уровня **ERROR**, **FATAL** и **PANIC** — они указывают на ошибки выполнения запросов, разрывы соединений или критические сбои экземпляра. Сообщения **WARNING** тоже могут быть полезны (например, нехватка ресурсов, таймауты).

**Утилита gplogfilter** — стандартный способ поиска по логам Greenplum. Она читает лог-файлы (в том числе gzip), фильтрует записи по времени, по строке или по регулярному выражению и выводит результат в stdout или в файл. Если входной файл не указан, используется лог координатора из `$COORDINATOR_DATA_DIRECTORY/log/` (или MASTER_DATA_DIRECTORY). Формат записей в логе определяется по timestamp в виде `YYYY-MM-DD [hh:mm[:ss]]`. По [Tanzu Greenplum 7 — gplogfilter](https://techdocs.broadcom.com/us/en/vmware-tanzu/data-solutions/tanzu-greenplum/7/greenplum-database/utility_guide-ref-gplogfilter.html).

Основные опции gplogfilter:

| Опция | Назначение |
|-------|------------|
| **-t**, **--trouble** | Только записи, в первой строке которых есть ERROR:, FATAL: или PANIC:. Рекомендуется начинать разбор с этой опции. |
| **-f** 'строка', **--find** | Вывести записи, содержащие указанную строку. |
| **-m** regex, **--match** | Вывести записи, совпадающие с регулярным выражением (синтаксис Python re). |
| **-b** datetime, **-e** datetime | Начало и конец временного интервала в формате YYYY-MM-DD [hh:mm[:ss]]. |
| **-d** длительность | Искать за последние hh:mm:ss (относительно текущего времени, если не заданы -b/-e). |
| **-n** N, **--tail** N | Вывести только последние N подходящих записей. |
| **-o** путь, **--out** | Записать результат в файл или каталог. |
| **-C** 'номера столбцов' | Вывести только указанные столбцы CSV (номера через запятую). |

Примеры:

```bash
# Последние три ошибки/паники в логе координатора
gplogfilter -t -n 3

# Все сообщения за последние 10 минут
gplogfilter -d :10

# Записи за указанный интервал с текстом "connection"
gplogfilter -b '2025-02-16 09:00' -e '2025-02-16 10:00' -f 'connection'
```

**Поиск по логам сегментов:** gplogfilter по умолчанию работает с логом координатора. Чтобы искать по логам сегментов, запускают gplogfilter на сегментных хостах через **gpssh** (или копируют логи на Master и обрабатывают локально). Соответствие записей координатора и сегментов можно устанавливать по полю **statement_id** (или sessionid/commandid в gpdb-contents). Пример (hostfile — список хостов сегментов):

```bash
gpssh -f hostfile -e 'source $GPHOME/greenplum_path.sh ; gplogfilter -t -n 5 $GPDATA_DIR/*/log/gpdb*.csv'
```

Рекомендация из документации: сначала **gplogfilter -t** по логу координатора, затем при необходимости сужать поиск по времени (**-b**, **-e**, **-d**) или по тексту (**-f**, **-m**) и при необходимости смотреть соответствующие записи в логах сегментов по statement_id. См. раздел «Checking the Log Files for Failed Segments» в Admin Guide при диагностике упавших сегментов.

## 4.4.3. Интеграция с внешним мониторингом

Встроенного централизованного дашборда мониторинга в базовой поставке Greenplum нет; состояние кластера проверяют утилитами (gpstate, запросы к системным каталогам) и логами. Для непрерывного наблюдения и алертинга используют **внешние системы**.

**Скрипты и периодические проверки:** на Master можно настроить cron-задачи, которые выполняют **gpstate -Q** или **gpstate -e** и при наличии down-сегментов или «Not in Sync» отправляют уведомление (почта, мессенджер, вызов алертинга). Аналогично — проверка ключевых представлений (**gp_segment_configuration**, **pg_stat_activity**) и запись метрик в файл или отправка в систему сбора метрик.

**Prometheus и Grafana:** метрики Greenplum можно отдавать в Prometheus и визуализировать в Grafana. Варианты:

- **Официальный экспортер** (Tanzu Greenplum Command Center / Greenplum Exporter в документации Broadcom): отдаёт метрики в формате Prometheus (uptime, конфигурация, соединения, статус запросов — running, queued, blocked, error, long-running и т.д.), сбор с заданным интервалом (например, 15 с). Настраивается endpoint для scrape.
- **Сторонние экспортеры** (например, greenplum_exporter для v5/v6): открытые проекты на GitHub, дают метрики кластера и часто поставляют готовые дашборды Grafana. Актуальность и совместимость с вашей версией нужно проверять.
- **Собственный экспортер:** скрипт или небольшой сервис, который по расписанию опрашивает Greenplum (gpstate, SQL к pg_stat_activity, gp_segment_configuration и др.) и выводит метрики в формате Prometheus (текст на HTTP). Prometheus scrape'ит этот endpoint, Grafana строит графики по запросам к Prometheus.

**Другие системы:** метрики или события можно отправлять в любую систему мониторинга (Zabbix, Nagios, облачные сервисы), используя скрипты или агенты, которые выполняют gpstate, SQL-запросы и чтение логов и передают результаты по API или в лог-агрегатор. Важно мониторить не только «кластер поднят», но и состояние mirror’ов (gpstate -e), дисковое пространство на Master и сегментах, рост логов и при необходимости — содержимое логов (ERROR/FATAL/PANIC через gplogfilter или парсеры).

Документация по установке и настройке конкретного экспортера (Tanzu Greenplum Command Center, Prometheus) приведена в руководствах вашего дистрибутива и на сайтах проектов.

## 4.4.4. Типичные ошибки

- **Искать только на Master:** при ошибках запроса или сбоях сегмента часть информации есть только в логах сегментов; используйте gpssh + gplogfilter или сбор логов с сегментных хостов.
- **Игнорировать gpAdminLogs:** при сбоях gpstart/gpstop/gprecoverseg причина часто в gpAdminLogs (по дате и имени утилиты); не ограничивайтесь только log/ координатора.
- **Не проверять ротацию:** при большом объёме логов без ротации каталог log/ может заполнить диск; настройте log_rotation_size и log_rotation_age и мониторьте место на всех узлах.

## Ключевое

- **Логи СУБД:** координатор — `$COORDINATOR_DATA_DIRECTORY/log/` (startup.log, CSV); сегменты — `$GPDATA_DIR/segprefixN/log/` (и mirror/...). **Логи утилит** — `$GPADMIN_HOME/gpAdminLogs/` (gpstart, gpstop, gprecoverseg и др.).
- **Анализ ошибок:** сначала **gplogfilter -t** по логу координатора (ERROR/FATAL/PANIC); при необходимости -b/-e/-d, -f/-m, -n; для сегментов — gplogfilter через gpssh по путям логов на хостах; связка по statement_id.
- **Внешний мониторинг:** скрипты (gpstate -Q/-e, SQL) + алерты; Prometheus (официальный или сторонний экспортер) + Grafana; мониторинг mirror’ов, дисков и логов.

В [§5.1](chapter-05-01.md) мы перейдём к типам таблиц: heap-таблицы по умолчанию, row-oriented хранение и сценарии использования (OLTP-подобные нагрузки, UPDATE/DELETE).
