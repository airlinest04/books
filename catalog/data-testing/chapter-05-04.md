# §5.4 Бизнес-правила в SQL

В [§5.3](chapter-05-03.md) мы разобрали референциальную целостность. Помимо структурных проверок (row count, контрольные суммы, отсутствие сирот) важны **бизнес-правила** — инварианты предметной области: «дебет равен кредиту», «остаток на счёте сходится с оборотом», «сумма по строкам равна итогу», «дата не из будущего». В этом разделе мы разберём, как формулировать и проверять такие правила в SQL и приводим типовые примеры: двойная запись (дебет/кредит), баланс, согласованность итогов.

---

## 5.4.1. Что такое бизнес-правило в контексте данных

**Бизнес-правило** (в контексте тестирования данных) — утверждение о данных, вытекающее из логики предметной области: бухгалтерия, финансы, складской учёт, заказы. Правило задаёт инвариант: при корректных данных условие всегда выполняется. Примеры: по каждой проводке дебет и кредит равны; сумма позиций заказа равна итогу заказа; остаток на счёте на конец периода равен остатку на начало плюс приход минус расход. См. [Глоссарий](glossary.md).

Проверка бизнес-правила в тесте или в мониторинге — это assertion в SQL: запрос, который считает «нарушителей» (строки или группы, где правило не выполняется), и ожидание «количество нарушений = 0». Если правило сформулировано верно и данные корректны, запрос возвращает ноль; иначе тест падает или срабатывает алерт.

Отличие от чисто технических проверок (row count, FK): бизнес-правила зависят от домена. Один и тот же приём (подсчёт нарушений через SQL) применяется к разным правилам; сами правила задаёт бизнес или аналитик, разработчик теста переводит их в запрос.

---

## 5.4.2. Дебет равен кредиту (двойная запись)

В бухгалтерском учёте каждая проводка должна быть сбалансирована: сумма по дебету равна сумме по кредиту (принцип двойной записи). В данных это означает: по каждой проводке (или по каждому документу/группе проводок) сумма дебетовых оборотов равна сумме кредитовых.

Пример структуры: таблица проводок с полями `entry_id`, `account_id`, `debit`, `credit`, `document_id`. Правило: по каждому `document_id` (или по каждой проводке, если баланс на уровне одной строки) выполняется `SUM(debit) = SUM(credit)`.

Проверка по документам (PostgreSQL):

```sql
-- Найти документы, где дебет не равен кредиту
SELECT document_id,
       SUM(debit) AS total_debit,
       SUM(credit) AS total_credit,
       SUM(debit) - SUM(credit) AS diff
FROM ledger.entries
WHERE load_date = :target_date
GROUP BY document_id
HAVING SUM(debit) != SUM(credit);
```

Assertion: этот запрос должен возвращать 0 строк. Если возвращает строки — перечислены документы с нарушением правила. Для теста можно обернуть в подсчёт: `SELECT COUNT(*) FROM (...)` и ожидать 0.

Если баланс должен соблюдаться по каждой строке (одна проводка — одна строка с заполненным либо debit, либо credit, и по документу итоги сходятся), правило можно сформулировать по-другому; суть та же — сравнение сумм дебета и кредита в выбранном разрезе.

## 5.4.3. Баланс (остаток и обороты)

**Баланс** — инвариант вида: остаток на конец периода = остаток на начало + приход − расход (или аналогичная формула по оборотам). Проверка: по каждому счёту (или по каждой сущности) вычислить правую и левую части равенства и убедиться, что они совпадают.

Пример: таблица оборотов по счёту с полями `account_id`, `period_start`, `period_end`, `opening_balance`, `debit_turnover`, `credit_turnover`, `closing_balance`. Правило: `closing_balance = opening_balance + debit_turnover - credit_turnover` (для активного счёта; для пассивного знаки могут быть иными в зависимости от принятой модели).

Проверка в SQL:

```sql
-- Строки, где расчётный остаток не совпадает с загруженным
SELECT account_id, period_start, period_end,
       opening_balance + debit_turnover - credit_turnover AS calculated_closing,
       closing_balance AS stored_closing
FROM mart.account_turnovers
WHERE load_date = :target_date
  AND closing_balance != opening_balance + debit_turnover - credit_turnover;
```

Assertion: 0 строк. Учитывать округление: при необходимости сравнивать с допуском (например, разница по модулю < 0.01) или округлять до копеек перед сравнением.

Аналогично проверяют «остаток на конец дня = остаток на начало + поступления − списания» в складском учёте или в кассе; формула зависит от домена, способ проверки тот же — сравнение вычисленного значения с хранимым (или сравнение двух агрегатов).

## 5.4.4. Другие примеры бизнес-правил

| Правило | Формулировка | Идея проверки в SQL |
|---------|--------------|----------------------|
| Сумма по строкам = итог | В документе сумма по строкам (позициям) равна полю «итог» в заголовке. | JOIN заголовка и позиций, GROUP BY document_id, сравнить SUM(line_amount) с header.total. Нарушители: HAVING SUM(line_amount) != MAX(header.total). |
| Нет отрицательных остатков | Остаток товара на складе (или по счёту) не отрицательный. | SELECT COUNT(*) FROM ... WHERE balance < 0. Ожидание: 0. |
| Даты в допустимых границах | Дата операции не в будущем; дата рождения не позже текущей даты. | WHERE operation_date > CURRENT_DATE или birth_date > CURRENT_DATE. Ожидание: 0 строк. |
| Коды из справочника | Поле status (или тип, регион) только из допустимого множества. | LEFT JOIN со справочником, WHERE key_in_ref IS NULL AND t.status IS NOT NULL; или NOT IN (список). Ожидание: 0 строк. |
| Один активный статус | У сущности не более одной записи со статусом «активен». | GROUP BY entity_id HAVING COUNT(*) FILTER (WHERE status = 'active') > 1. Ожидание: 0 строк. |

Каждое правило переводится в запрос «найти нарушения»; assertion — «количество строк результата = 0». При падении теста или срабатывании мониторинга по логу или по результату запроса видно, какие именно строки или группы нарушили правило.

---

## 5.4.5. Где использовать проверки бизнес-правил

Проверки бизнес-правил уместны:

- **В unit-тестах** — если запрос или витрина реализуют расчёт (остаток, итог, баланс); фикстура с известными числами, assertion по правилу.
- **В интеграционных тестах ETL** — после загрузки в витрину или в слой расчётов запустить запросы проверки правил по загруженным данным.
- **В мониторинге качества данных** — регулярно (по расписанию или после каждого прогона загрузки) выполнять те же проверки в проде; при появлении нарушений — алерт и разбор.

Правила лучше хранить в одном месте (скрипты, конфиг, описание в репозитории), чтобы при изменении логики обновлять и код расчёта, и проверку. В [§6.1](chapter-06-01.md) мы начнём главу о тестировании преобразований: маппинг полей «до и после», соответствие типов и тесты маппинга.

---

## Ключевое

- **Бизнес-правило** в контексте данных — инвариант предметной области (дебет = кредит, баланс, сумма строк = итог и т.д.); проверка — SQL-запрос, находящий нарушения, assertion «количество нарушений = 0».
- **Дебет = кредит:** по документу (или по проводке) SUM(debit) = SUM(credit); проверка — GROUP BY document_id, HAVING SUM(debit) != SUM(credit); ожидание — 0 строк.
- **Баланс:** остаток на конец = остаток на начало + обороты; проверка — сравнение вычисленного остатка с хранимым (с учётом округления при необходимости); ожидание — 0 нарушений.
- Другие примеры: сумма по строкам = итог в заголовке, нет отрицательных остатков, даты в границах, коды из справочника. Проверки применяют в unit-тестах, интеграционных тестах ETL и в мониторинге качества данных.

В [§6.1](chapter-06-01.md) мы начнём главу о тестировании преобразований: маппинг полей до и после, соответствие типов и тесты маппинга.
