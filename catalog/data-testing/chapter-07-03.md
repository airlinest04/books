# §7.3 Референциальная целостность в ETL

В [§7.2](chapter-07-02.md) мы разобрали контрольные суммы и хеши для сравнения источника и приёмника. Помимо полноты и неизменности значений важна **референциальная целостность** в загруженных данных: после ETL в приёмнике не должно быть сирот (ссылок на несуществующую родительскую запись), а связи между таблицами должны быть консистентны. В этом разделе мы разберём проверку FK после загрузки, отсутствие сирот и консистентность в контексте ETL. Основные приёмы проверки в SQL уже даны в §5.3; здесь — применение к пайплайну загрузки и типичные причины нарушений.

---

## 7.3.1. Проверка после загрузки

Референциальная целостность проверяется **после** того, как ETL загрузил данные в приёмник (staging, витрина, слой марта). Проверка выполняется по загруженным таблицам: не по источнику, а по целевым таблицам, в которые попали данные. Причина: источник может быть консистентен, но при загрузке в разном порядке (сначала детали, потом заголовки) или при ошибке маппинга в приёмнике появляются сироты. См. [§5.3](chapter-05-03.md) и [Глоссарий](glossary.md).

Момент проверки: после завершения всех шагов загрузки, затрагивающих связанные таблицы. Если загрузка идёт в несколько таблиц (заказы, позиции заказов, клиенты), проверку целостности выполняют после загрузки всех этих таблиц за выбранный срез (дата, batch), иначе временно могут быть сироты из-за порядка загрузки.

Проверки можно встроить в интеграционный тест ETL (после шага загрузки — запросы на сирот; при ненулевом количестве тест падает) или в мониторинг (после каждого прогона загрузки — те же запросы; при нарушении — алерт). В даге Airflow такие проверки оформляют отдельными тасками после тасков загрузки (см. главу 9).

---

## 7.3.2. Нет сирот в приёмнике

**Сирота** — запись в дочерней таблице, у которой значение внешнего ключа не найдено в родительской таблице (в том же приёмнике). Проверка: запрос «найти дочерние строки, для которых нет родителя»; ожидание — 0 строк.

Пример: в staging загружены таблицы `orders` и `customers`. У заказов поле `customer_id`. Сироты — заказы с `customer_id`, которого нет в `staging.customers`.

```sql
-- Количество сирот: заказы с customer_id, отсутствующим в customers
SELECT COUNT(*) AS orphan_count
FROM staging.orders o
LEFT JOIN staging.customers c ON c.customer_id = o.customer_id
WHERE c.customer_id IS NULL AND o.customer_id IS NOT NULL;
-- Ожидание: orphan_count = 0
```

Если в приёмнике загружаются только часть таблиц (например, только заказы за день, а справочник клиентов — полный), родительская таблица должна содержать всех клиентов, на которых ссылаются заказы в этом срезе. Иначе проверку делают с учётом среза: например, «все customer_id из staging.orders за load_date = :date присутствуют в staging.customers» (в staging.customers могут быть только клиенты, встретившиеся в загруженных заказах, или полный справочник — в зависимости от дизайна ETL).

Типичные причины появления сирот после ETL:

- Загрузка дочерней таблицы раньше родительской за тот же срез; родитель ещё не загружен. Решение: порядок загрузки (сначала родители) или отложенная проверка после загрузки всех таблиц.
- В источнике уже были некорректные ссылки; ETL перенёс их без валидации. Решение: проверка в ETL (отбрасывать или помечать) или исправление в источнике.
- Ошибка в маппинге ключа (перепутаны поля, неверный тип). Решение: unit-тесты маппинга, проверка целостности после загрузки.

## 7.3.3. Консистентность между таблицами

**Консистентность** здесь — согласованность связей: не только «нет сирот», но и при необходимости «для каждого родителя в срезе есть ожидаемые дочерние записи» (например, у каждого заказа есть хотя бы одна позиция). Проверки зависят от бизнес-правил:

- **Только «нет сирот»:** достаточно проверок из §7.3.2 по каждой связи дочерняя → родительская.
- **Ожидаемое наличие дочерних записей:** например, «у каждого заказа из staging.orders за дату есть хотя бы одна строка в staging.order_lines». Проверка: родители без дочерних записей (LEFT JOIN, WHERE child.id IS NULL); ожидание — 0 строк, если по правилу у каждого заказа должны быть позиции.
- **Согласованность объёмов:** сумма количества по дочерней таблице (например, сумма quantity по позициям) совпадает с полем в родителе (total_quantity в заголовке заказа). Это уже бизнес-правило (см. §5.4); его можно включить в набор проверок после ETL вместе с референциальной целостностью.

Перечень проверок целостности лучше держать в одном месте (скрипты, конфиг): список пар таблиц (родитель, потомок) и полей ключа; для каждой пары — запрос на подсчёт сирот. При добавлении новой таблицы или новой связи в ETL в перечень добавляют соответствующую проверку. В [§7.4](chapter-07-04.md) мы разберём проверку «нет потерь и искажений»: полнота, точность и выборочная сверка записей.

---

## Ключевое

- **Референциальную целостность** проверяют **после загрузки** по таблицам приёмника; момент проверки — после загрузки всех связанных таблиц за срез, чтобы не ловить временные сироты из-за порядка загрузки.
- **Нет сирот:** для каждой связи дочерняя → родительская запрос на подсчёт строк без родителя (LEFT JOIN / NOT EXISTS); assertion — 0. Учитывать срез (родитель может быть неполным в staging).
- **Типичные причины сирот:** порядок загрузки (сначала дети), некорректные данные в источнике, ошибка маппинга ключа. Консистентность расширяют проверками «родитель имеет дочерние записи» и согласованностью объёмов по правилам бизнеса.
- Перечень проверок целостности (пары таблиц, ключи) хранить централизованно и дополнять при изменении ETL.

В [§7.4](chapter-07-04.md) мы разберём проверку отсутствия потерь и искажений: полнота, точность и выборочная сверка записей.
