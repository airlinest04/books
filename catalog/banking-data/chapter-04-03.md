# §4.3 Связь продукт — счёт — проводка

В [§4.2](chapter-04-02.md) мы систематизировали витрины по продуктам и разрезы. Для сверки с бухучётом и для обогащения витрин данными проводок необходима однозначная **связь продуктовой сущности** (договор, карта) с **бухгалтерским счётом** и с **проводками**. В этом разделе — как выстроить эту связь, какие **ключи** использовать для джойнов и как применять их при сверке. Материал опирается на [§1.4](chapter-01-04.md), [§2.4](chapter-02-04.md) и [§3.4](chapter-03-04.md). См. [Глоссарий](glossary.md).

---

## 4.3.1. Зачем нужна связь продукт — счёт — проводка

**Продуктовая сущность** — объект бизнес-учёта: договор кредита, договор на карту, карта, платёж. **Счёт** — объект бухгалтерского учёта по плану счетов банка; по счёту отражаются проводки (обороты и остатки). **Проводка** — запись о движении средств: дебет, кредит, сумма, дата валютирования, документ/операция. См. [Глоссарий](glossary.md), [§1.4](chapter-01-04.md).

Связь между ними нужна чтобы:

- **Сверять** остатки и обороты из продуктовых данных (витрины, события) с остатками и оборотами по счёту из бухучёта. Без связи «договор — счёт» или «карта — счёт» нельзя автоматически сопоставить «остаток долга по договору» с «остатком по счёту ссудной задолженности».
- **Обогащать** витрины данными из бухучёта: при необходимости подтягивать проводки по счёту за период, проверять даты и суммы.
- **Заполнять регуляторные формы:** часть показателей берётся из бухучёта по счетам; маппинг «поле отчёта — счёт» требует знания, какой продукт (договор, карта) к какому счёту относится.
- **Расследовать расхождения:** при несовпадении остатков или оборотов связь «продукт — счёт» позволяет локализовать проблему (ошибка в продукте, в проводке или в привязке).

Связь должна храниться явно: в справочнике (договор → счёт, карта → счёт) или в самой записи продукта/события (поле account_id, contract_id и т.д.). См. [§1.4](chapter-01-04.md), [§6.2](chapter-06-02.md).

## 4.3.2. Ключи для джойнов

Для джойнов между продуктовыми данными и бухучётом используются следующие ключи. См. [§4.2](chapter-04-02.md).

**Идентификатор продукта (договор, карта).** В таблицах договоров, карт, событий (выдачи, платежи по кредиту, транзакции) хранится contract_id, card_id и т.п. По нему можно найти запись в витрине и в справочнике продукта.

**Идентификатор счёта (account_id, номер счёта).** Счёт в бухучёте идентифицируется номером счёта или внутренним ID в системе бухучёта. В проводках каждая строка содержит дебет-счёт и кредит-счёт (или один из них). Связь «договор — счёт» или «карта — счёт» задаёт, по какому счёту искать проводки для данного договора/карты.

**Дата валютирования.** Обороты и остатки считаются по дате зачёта операции (дата валютирования). При джойне продуктовых событий и проводок за период ключ — пара (счёт, дата валютирования) или (договор/карта, дата валютирования): оборот по витрине за период по договору должен совпадать с оборотом по счёту этого договора за тот же период по дате валютирования.

**Сводка ключей:**

| Цель джойна | Ключи |
|-------------|--------|
| Найти счёт по договору/карте | contract_id → справочник contract_account (contract_id, account_id) или поле account_id в договоре/карте |
| Обороты по договору за период = обороты по счёту | account_id, date_from, date_to (дата валютирования); суммировать проводки по счёту за период и сравнить с суммой событий по договору за период |
| Остаток на дату по договору = остаток по счёту | account_id, snapshot_date; остаток по счёту на дату из бухучёта vs расчётный остаток по договору из событий |
| Проводки по операции | operation_id / payment_id / transaction_id в продукте и ссылка на проводку (или document_id в бухучёте); при наличии — общий идентификатор документа |

См. [§1.4](chapter-01-04.md), [§2.4](chapter-02-04.md), [§6.2](chapter-06-02.md).

## 4.3.3. Кредиты: договор — счёт ссудной задолженности и резерва

По кредиту продуктовая сущность — **договор**; с ним связаны счёт учёта ссудной задолженности и при необходимости счёт резерва. См. [§1.4](chapter-01-04.md).

- **Договор → счёт ссудной задолженности:** один договор — один счёт (или несколько при мультивалютности/раздельном учёте). Выдачи увеличивают дебет счёта, погашения тела — кредит. Джойн: contract_id → account_id (из справочника или из поля договора). Обороты за период: сумма выдач по договору = дебетовый оборот по счёту; сумма платежей в тело = кредитовый оборот по счёту. Остаток на дату: расчётный остаток по договору (сумма выдач − сумма в тело) = остаток по счёту на дату.
- **Договор → счёт резерва:** резерв может вестись в разрезе счёта ссудной задолженности или в разрезе группы договоров; для сверки «сумма резерва по витрине» = «остаток по счёту резерва» нужна связь договор → счёт резерва или агрегация по группе счетов резерва. См. [§1.3](chapter-01-03.md), [§1.4](chapter-01-04.md).

В витринах «портфель» и «движения» должно быть поле счёт (account_id или номер счёта), чтобы при сверке не джойнить каждый раз к справочнику; при загрузке в DWH связь подтягивается из продуктовой системы или из справочника договор — счёт. См. [§4.4](chapter-04-04.md).

## 4.3.4. Карты: карта/договор — счёт

По картам продуктовая сущность — **карта** и **договор**; счёт — расчётный (текущий) для дебетовой карты или счёт ссудной задолженности для кредитной. См. [§2.1](chapter-02-01.md), [§2.4](chapter-02-04.md).

- **Карта → договор → счёт:** связь хранится в справочнике карт (card_id → contract_id → account_id) или в договоре (contract_id → account_id). Транзакции привязаны к карте; через карту — к договору и счёту. Обороты по витрине «транзакции» за период по счёту (сумма проведённых операций) должны совпадать с оборотом по счёту в бухучёте (по дебету для расчётного счёта — списания; по дебету для ссудной задолженности — рост операций по кредитной карте).
- Ключи для джойна: card_id или contract_id, account_id, date (валютирования). При перевыпуске карты договор и счёт не меняются — агрегаты по договору объединяют все карты договора. См. [§2.4](chapter-02-04.md), [§4.2](chapter-04-02.md).

## 4.3.5. Платежи: платёж — счета плательщика и получателя

По платежу продуктовая сущность — **платёж**; с ним связаны два счёта: счёт плательщика (списание) и счёт получателя (зачисление). См. [§3.1](chapter-03-01.md), [§3.4](chapter-03-04.md).

- **Платёж → счёт плательщика, счёт получателя:** в записи платежа хранятся payer_account_id (или номер счёта, банк) и beneficiary_account_id (или номер счёта, банк). В бухучёте по каждому исполненному платежу формируются проводки: списание со счёта плательщика, зачисление на счёт получателя. Для сверки: сумма исполненных платежей за период по счёту плательщика (исходящие) = кредитовый оборот по этому счёту за период (или дебетовый — в зависимости от типа счёта); по счёту получателя — аналогично входящие и дебетовый оборот.
- Ключи: payment_id, payer_account_id, beneficiary_account_id, value_date. При внутренних платежах оба счёта в одном банке; при внешних — счёт плательщика в банке-отправителе, счёт получателя в банке-получателе. Сверка оборотов по витрине платежей с оборотами по счетам выполняется по account_id и дате валютирования. См. [§3.4](chapter-03-04.md), [§6.2](chapter-06-02.md).

## 4.3.6. Справочник связей и хранение в DWH

Чтобы не дублировать логику привязки в каждом витрине, связь «продукт — счёт» целесообразно хранить в **справочнике** (или в атрибутах сущности в Core). См. [§4.4](chapter-04-04.md).

**Варианты хранения:**

- **В сущности (договор, карта):** в таблице contract поле account_id; в таблице card поле contract_id и при загрузке или через джойн к contract — account_id. Просто и достаточно, если у договора один счёт на весь срок.
- **Отдельный справочник contract_account:** (contract_id, account_id, date_from, date_to) — при смене счёта по договору (редко, но возможно) хранится история; для «текущего» счёта date_to = NULL или максимальная дата.
- **В фактах (событиях):** в каждой записи выдачи, платежа, транзакции — account_id. Избыточно по объёму, но упрощает агрегаты без джойна к договору; при загрузке account_id подставляется из договора/карты на дату операции.

В DWH при загрузке из операционных систем связь «договор — счёт» и «карта — счёт» должна загружаться из источника (продуктовая система, бухучёт) и быть доступна в Core; витрины потребляют её при построении или хранят account_id в снимках и фактах для быстрой сверки. См. [§6.2](chapter-06-02.md).

## 4.3.7. Типичные ошибки

- **Отсутствие справочника или поля «счёт» в продукте:** сверка тогда возможна только вручную по реквизитам; автоматическая сверка и маппинг отчётов требуют явной связи.
- **Разные идентификаторы счёта в продукте и в бухучёте:** в одном месте — номер счёта (строка), в другом — внутренний account_id; при джойне нужна единая схема (один ключ) или маппинг номер счёта ↔ account_id в справочнике счетов.
- **Не учитывать дату при связи договор — счёт:** если счёт по договору мог меняться (редкий кейс), при сверке за прошлый период нужно брать счёт, действовавший на ту дату; иначе обороты привязываются к неправильному счёту.
- **Джойнить проводки по сумме и дате без идентификатора продукта:** несколько операций на одну сумму в один день дают неоднозначное соответствие; нужен идентификатор операции/документа в проводке и в продукте для построчного сопоставления при детальной сверке.

---

## Ключевое

- Связь **продукт — счёт — проводка** нужна для сверки остатков и оборотов продуктовых данных с бухучётом, для обогащения витрин и для регуляторной отчётности.
- **Ключи для джойнов:** идентификатор продукта (contract_id, card_id), идентификатор счёта (account_id), дата валютирования; справочник договор/карта → счёт или поле account_id в сущности и в фактах.
- **Кредиты:** договор → счёт ссудной задолженности (и при необходимости счёт резерва); обороты и остаток по договору сверяются с оборотом и остатком по счёту.
- **Карты:** карта → договор → счёт; транзакции агрегируются по счёту за период и сверяются с оборотом по счёту.
- **Платежи:** платёж → счёт плательщика, счёт получателя; обороты по витрине платежей по счёту сверяются с оборотами по счёту в бухучёте.
- Связь хранить в справочнике или в атрибутах сущности в Core; в витринах при необходимости хранить account_id для быстрой сверки.

В [§4.4](chapter-04-04.md) мы разберём источники данных и слои загрузки: операционные системы, бухгалтерия, внешние провайдеры; Raw, Staging, Core, Mart применительно к банку.
