# §7.2 Профилирование данных

В [§7.1](chapter-07-01.md) мы ввели определение качества данных и шесть измерений (полнота, точность, согласованность, актуальность, уникальность, валидность). Чтобы оценить качество на практике, данные нужно **проанализировать**: собрать метрики по полям и наборам, выявить аномалии и сопоставить результаты с целевыми уровнями. Эта деятельность называется **профилированием данных** (data profiling). В этом разделе мы разберём, зачем нужно профилирование, какие **базовые метрики** собирают (количество записей, null, распределения, дубликаты), и кратко охарактеризуем инструменты и подходы. Управление качеством на основе результатов профилирования — в [§7.3](chapter-07-03.md); встраивание проверок в ETL — в [§7.4](chapter-07-04.md). См. [Глоссарий](glossary.md).

---

## 7.2.1. Что такое профилирование данных и зачем оно нужно

**Профилирование данных** (data profiling) — сбор и анализ метрик о наборе данных без изменения самих данных: объём, заполненность полей, распределения значений, дубликаты, соответствие форматам и правилам. Профилирование даёт объективную картину состояния данных и служит основой для оценки качества ([§7.1](chapter-07-01.md)), постановки правил качества и приоритизации исправлений.

Зачем нужно профилирование:

- **Оценка качества:** сопоставление метрик (полнота, уникальность, валидность) с целевыми уровнями; выявление полей и записей с отклонениями.
- **Понимание данных перед использованием:** при подключении нового источника или витрины профилирование показывает, что в данных есть (какие поля, какие значения, какие аномалии); это нужно аналитикам и стюардам для описания в каталоге и для формулирования предупреждений потребителям.
- **Проектирование загрузки и правил:** перед построением ETL профилирование помогает определить, какие проверки и преобразования нужны (обязательные поля, справочники для валидации, ключи для дедупликации).
- **Мониторинг:** регулярное профилирование (по расписанию или после каждой загрузки) выявляет деградацию качества (рост числа null, появление невалидных значений, дубликаты) и запускает реакцию ([§7.3](chapter-07-03.md)).
- **Документирование:** результаты профилирования (статистика по полям, примеры значений) пополняют метаданные в каталоге и помогают потребителям понимать ограничения набора данных.

Профилирование может быть разовым (при первичном анализе набора) или постоянным (мониторинг качества); может выполняться над полным набором или над выборкой при больших объёмах. См. [Глоссарий](glossary.md).

## 7.2.2. Базовые метрики: объём и заполненность

**Объём набора:** число записей (строк) в таблице или числе объектов/файлов в выборке. Сравнение объёма с ожиданием (например, «за день должно быть порядка N транзакций») помогает выявить неполную выгрузку или дублирование загрузки.

**Заполненность (полнота по полю):** по каждому полю (столбцу) считают:
- **Число непустых значений** (не null, не пустая строка — в зависимости от правил);
- **Число пустых (null) значений;**
- **Доля заполненности** — отношение числа непустых к общему числу записей, обычно в процентах.

Эти метрики напрямую связаны с измерением **полнота** из [§7.1](chapter-07-01.md). Порог «приемлемая полнота» задаётся владельцем или правилами качества; падение заполненности ниже порога или резкое изменение по сравнению с предыдущим профилированием сигнализирует о проблеме.

**Дополнительно:** минимальная и максимальная длина строки (для текстовых полей), минимальное и максимальное значение (для числовых и дат) — помогают выявить очевидные аномалии (отрицательные значения там, где их быть не должно, даты в неверном диапазоне).

## 7.2.3. Распределения и уникальность

**Распределение значений (frequency distribution):** для каждого поля — сколько раз встречается каждое значение (или каждая группа значений). Для категориальных полей (статус, код региона) это даёт список значений и их частоты; для числовых полей часто строят гистограммы (распределение по интервалам). Распределения помогают:
- обнаружить опечатки и нестандартные значения (редкое написание, лишний код);
- выявить доминирующие значения и возможную неполноту разнообразия;
- подготовить справочники для валидации (допустимые значения).

**Уникальность по полю:** число уникальных значений в поле и доля уникальных от общего числа записей. Для поля, которое по смыслу должно быть ключом (идентификатор заказа), ожидается 100% уникальности; падение уникальности указывает на дубликаты. Для поля-справочника (например, код региона) число уникальных значений должно соответствовать ожидаемому размеру справочника.

**Дубликаты по ключу:** при заданном ключе (одно поле или комбинация полей) подсчитывают число записей с повторяющимся ключом. Метрики: число дубликатов, число ключей, встречающихся более одного раза; связь с измерением **уникальность** из [§7.1](chapter-07-01.md). Выявление дубликатов критично перед загрузкой в витрины и DWH ([§7.4](chapter-07-04.md)).

## 7.2.4. Валидность и форматы

Профилирование может включать проверку **валидности** ([§7.1](chapter-07-01.md)): соответствие значений заданным правилам. Типичные проверки:

- **Формат:** дата в заданном формате, число без посторонних символов, строка в допустимой кодировке; регулярные выражения для полей с фиксированным шаблоном (телефон, email, код).
- **Диапазон:** числовое значение в заданных границах (возраст от 0 до 120, процент от 0 до 100); дата в допустимом интервале.
- **Справочник:** значение входит в список допустимых (код из справочника, статус из перечня); при профилировании можно выявить значения, не входящие в текущий справочник.
- **Целостность:** значение внешнего ключа существует в связанной таблице; при профилировании нескольких таблиц — проверка «висячих» ссылок.

Метрики: число и доля записей (или полей), проходящих каждую проверку; список невалидных значений (или примеры) для последующего исправления или уточнения правил.

## 7.2.5. Сводная таблица метрик профилирования

| Группа метрик | Что считают | Связь с измерением качества |
|---------------|-------------|-----------------------------|
| Объём | Число записей, число файлов | Полнота (набор), согласованность (сверка объёма с источником) |
| Заполненность | По полю: число null/не null, % заполненности | Полнота |
| Min/max, длина | Минимум, максимум, длина строки | Валидность, выявление аномалий |
| Распределение | Частота значений, гистограмма | Валидность, понимание данных |
| Уникальность по полю | Число уникальных значений, % уникальных | Уникальность |
| Дубликаты по ключу | Число дубликатов, число ключей с повторами | Уникальность |
| Проверки правил | Число/доля записей, проходящих правило (формат, диапазон, справочник) | Валидность |

Результаты профилирования хранят в отчётах, в каталоге данных (метаданные качества) или в системе управления качеством; тренды метрик во времени используют для мониторинга ([§7.3](chapter-07-03.md)).

## 7.2.6. Инструменты и подходы

**Ручные запросы и скрипты:** подсчёт записей, COUNT по полям, GROUP BY для распределений и дубликатов — можно выполнять SQL-запросами к БД или скриптами (Python, Pandas) к выгрузкам. Гибко, но трудоёмко при регулярном профилировании многих наборов.

**Специализированные инструменты профилирования:** средства, которые подключаются к источникам (СУБД, файлы), автоматически собирают метрики по полям (заполненность, распределения, базовые статистики) и строят отчёты. Могут быть частью платформы данных или каталога (например, встроенное профилирование в каталогах данных); могут быть отдельными продуктами (open source и коммерческие). Выбор зависит от экосистемы организации и от объёма данных.

**Профилирование в пайплайнах:** метрики качества собираются в рамках ETL-задачи после загрузки или после преобразования; результаты передаются в систему мониторинга или в каталог. Так профилирование становится частью регулярного контроля качества ([§7.4](chapter-07-04.md)).

**Выборка при больших объёмах:** при очень больших таблицах полное сканирование может быть дорогим; профилирование выполняют по выборке (случайная или по партиции). При этом оценки полноты и распределений остаются репрезентативными при корректной выборке; оценка редких дубликатов может потребовать полного прохода или адаптированных правил.

## 7.2.7. Профилирование в контексте управления данными

- **Стюард и владелец:** стюард или ответственный за качество инициирует профилирование при приёме нового набора в каталог и при мониторинге; владелец задаёт целевые уровни и интерпретирует отклонения.
- **Каталог:** результаты профилирования (статистика по полям, дата последнего профилирования, выявленные проблемы) хранятся в каталоге как метаданные качества; потребители видят ограничения набора до использования.
- **Приоритизация:** не все наборы профилируются с одинаковой частотой и глубиной; приоритет — критичные для отчётности витрины и источники, затем — остальные по мере ресурсов.

## 7.2.8. Типичные ошибки при профилировании

- **Профилировать без целей:** сбор метрик «на всякий случай» без привязки к целевым уровням качества и к действиям (что делать при отклонении) не даёт пользы; нужно заранее определить, какие метрики и пороги важны для набора.
- **Игнорировать результаты:** профилирование выявило проблемы, но никто не исправляет данные и не обновляет правила загрузки; профилирование должно быть связано с процессами улучшения качества ([§7.3](chapter-07-03.md)).
- **Не документировать в каталоге:** результаты профилирования остаются в отчёте у аналитика; каталог не обновляется, новые потребители не видят ограничений качества; метаданные качества должны быть в каталоге.
- **Профилировать только один раз:** данные меняются; разовое профилирование при приёме набора не заменяет мониторинг при регулярных загрузках; нужно планировать повторное профилирование или встроенные проверки в ETL.

---

## Ключевое

- **Профилирование данных** — сбор и анализ метрик о наборе данных без изменения данных; основа для оценки качества, понимания данных, проектирования правил загрузки и мониторинга.
- **Базовые метрики:** объём (число записей), заполненность по полю (null, % заполненности), распределения значений, уникальность по полю, дубликаты по ключу, проверки валидности (формат, диапазон, справочник); связь с измерениями качества — полнота, уникальность, валидность.
- Результаты профилирования сопоставляются с целевыми уровнями, документируются в каталоге и используются для приоритизации исправлений и для настройки правил в ETL.
- Инструменты: ручные запросы и скрипты, специализированные средства профилирования, профилирование внутри пайплайнов; при больших объёмах — выборка. Профилирование должно быть привязано к целям и к действиям по качеству.

В [§7.3](chapter-07-03.md) мы разберём **управление качеством данных**: обнаружение проблем, исправление, предупреждение; правила и проверки в пайплайнах; роли и процессы.
