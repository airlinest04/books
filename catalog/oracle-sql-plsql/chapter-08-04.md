# §8.4 План выполнения запроса

В [§8.3](chapter-08-03.md) мы разобрали SAVEPOINT. Чтобы понять, как Oracle выполняет запрос (по каким таблицам и индексам идёт доступ, в каком порядке выполняются соединения и фильтры), используют **план выполнения**. Oracle строит план на основе статистики объектов и стоимости операций. В этом разделе — получение плана через **EXPLAIN PLAN**, просмотр результата (**DBMS_XPLAN.DISPLAY**), основные операции плана (TABLE ACCESS FULL, INDEX RANGE SCAN и др.) и кратко — зачем это нужно. На этом заканчивается часть I книги (Oracle SQL); далее [часть II](chapter-09-01.md): PL/SQL. См. [Глоссарий](glossary.md).

## 8.4.1. EXPLAIN PLAN: получение плана без выполнения

**EXPLAIN PLAN** — команда, которая заставляет оптимизатор Oracle построить **план выполнения** для указанного запроса и записать его в таблицу (по умолчанию в **PLAN_TABLE** или в таблицу, заданную через INTO). Запрос при этом **не выполняется** — только планирование. См. [Глоссарий](glossary.md).

Синтаксис:

```sql
EXPLAIN PLAN
  [INTO таблица_планов [@dblink]]
  [SET statement_id = 'метка']
  FOR запрос;
```

**запрос** — любой допустимый SELECT, INSERT, UPDATE, DELETE, MERGE. Результат планирования попадает в строки таблицы планов (столбцы: operation, options, object_name, id, parent_id, position, cost, cardinality и др.). В современных версиях Oracle для хранения плана часто используют **временную** таблицу или общую PLAN_TABLE; скрипт создания `utlxplan.sql` входит в поставку (каталог admin или подобный). Среда: Oracle Database.

Пример:

```sql
EXPLAIN PLAN FOR
  SELECT * FROM employees WHERE department_id = 10;
```

План записан в PLAN_TABLE (если она есть в схеме и настроена по умолчанию). Чтобы вывести план в читаемом виде, используют пакет **DBMS_XPLAN**.

## 8.4.2. Просмотр плана: DBMS_XPLAN.DISPLAY

Функция **DBMS_XPLAN.DISPLAY** возвращает план из таблицы планов в виде форматированного текста (дерево операций с отступами). Вызов после EXPLAIN PLAN:

```sql
EXPLAIN PLAN FOR SELECT * FROM employees WHERE department_id = 10;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
```

Можно указать таблицу, statement_id и формат: `DBMS_XPLAN.DISPLAY('PLAN_TABLE', NULL, 'BASIC')` или `'TYPICAL'`, `'ALL'`. Результат выводится в виде набора строк — иерархия операций: корень (результат запроса), ниже — дочерние шаги (доступ к таблицам, индексам, соединения, сортировки и т.д.). См. [Глоссарий](glossary.md).

В SQL Developer и других средах план часто показывают в отдельном окне (кнопка «Explain Plan» или F10); под капотом вызывается тот же механизм. Для **реально выполненного** запроса план и фактические затраты можно получить через **V$SQL_PLAN** или **DBMS_XPLAN.DISPLAY_CURSOR** (план из кэша курсоров) — это даёт план того запроса, который уже выполнялся. См. [Глоссарий](glossary.md).

## 8.4.3. Основные операции в плане

В плане каждая строка — **операция**. Ниже перечислены типичные; по ним можно понять, как Oracle получает данные. См. [Глоссарий](glossary.md).

- **TABLE ACCESS FULL** — полное сканирование таблицы (чтение всех блоков). При больших таблицах часто дорого; оптимизатор может выбрать его, если нет подходящего индекса или если по оценке нужно прочитать большую долю строк.
- **INDEX RANGE SCAN** — сканирование индекса по диапазону значений (например, по условию `WHERE col = :1` или `col BETWEEN ...`). Возвращает rowid, по которым затем читаются строки таблицы (или данные берутся из индекса, если запрос покрывается индексом).
- **INDEX UNIQUE SCAN** — доступ по уникальному ключу (одно значение, одна строка).
- **INDEX FULL SCAN** — полное сканирование индекса (все листовые блоки); иногда выгоднее полного сканирования таблицы, если нужны только столбцы индекса и порядок.
- **NESTED LOOPS** — соединение вложенными циклами: для каждой строки внешнего источника ищутся совпадения во внутреннем (часто по индексу).
- **HASH JOIN** — соединение по хеш-таблице: одна часть строится в память, по ней пробивается вторая.
- **SORT AGGREGATE**, **SORT GROUP BY** — агрегация и группировка с сортировкой.
- **FILTER**, **VIEW** — фильтрация и представление/подзапрос.

Столбцы **Cost** и **Cardinality** в выводе плана (при формате ALL или TYPICAL) — оценочная стоимость и ожидаемое число строк; помогают понять, какой шаг оптимизатор считает тяжёлым. Реальные затраты даёт только выполнение запроса и анализ статистики выполнения (AWR, SQL Monitor и т.д.). Среда: Oracle Database.

## 8.4.4. Зачем смотреть план

План выполнения нужен для **оптимизации**: убедиться, что используются индексы там, где ожидается; выявить полные сканирования больших таблиц; проверить порядок соединений и тип JOIN. Неверная или устаревшая статистика может привести к плохому плану — тогда собирают статистику заново (DBMS_STATS). Изменение запроса (переписать подзапрос, добавить подсказку HINT) после анализа плана — следующий шаг. На этом мы завершаем часть I (Oracle SQL); в [части II](chapter-09-01.md) переходим к PL/SQL: блокам, переменным, процедурам и функциям. См. [Глоссарий](glossary.md).

## Ключевое

- **EXPLAIN PLAN FOR запрос** — построить план выполнения без выполнения запроса; результат записывается в таблицу планов (например, PLAN_TABLE). См. [Глоссарий](glossary.md).
- **DBMS_XPLAN.DISPLAY** — вывести последний план из таблицы планов в виде дерева операций. Для плана реально выполненного запроса — DBMS_XPLAN.DISPLAY_CURSOR.
- В плане важны операции доступа: **TABLE ACCESS FULL** (полное сканирование таблицы), **INDEX RANGE SCAN** / **INDEX UNIQUE SCAN** (доступ по индексу), **NESTED LOOPS**, **HASH JOIN** (типы соединений).
- План используют для анализа производительности и выбора индексов; актуальная статистика (DBMS_STATS) влияет на качество плана.
