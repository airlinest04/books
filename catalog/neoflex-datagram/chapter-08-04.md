# §8.4 Workflow и проверка

В [§8.3](chapter-08-03.md) мы собрали поток «источник Parquet/ORC → трансформации → приёмник Hive». В этом разделе оформляем **Workflow**: **последовательность этапов** (при одном потоке — один этап; при разбиении на несколько потоков — несколько этапов с зависимостями), **запуск** пайплайна через оркестратор и **сверка данных** после выполнения. Раздел завершает главу 8; в [§9.1](chapter-09-01.md) мы перейдём к главе 9 «Миграция с IBM Infosphere и Oracle ODI». См. [Глоссарий](glossary.md).

---

## 8.4.1. Последовательность этапов в Workflow

В дизайнере **Workflow** ([§2.2](chapter-02-02.md), [§6.1](chapter-06-01.md)) задаётся, какие этапы выполняются и в каком порядке. Для сценария главы 8 возможны два варианта:

- **Один этап** — один поток трансформаций «чтение из Parquet/ORC → преобразования → запись в Hive» собирается в один артефакт (JAR). В Workflow добавляется один узел-этап, ссылающийся на этот поток. Запуск Workflow выполняет одну задачу оркестратора, которая вызывает `spark-submit` для данного JAR с параметрами (дата среза, путь). Подходит, когда загрузка за одну дату укладывается в один поток и не требует предварительных шагов (например, отдельной загрузки в Raw уже выполнена вне этого пайплайна).
- **Несколько этапов** — если логично разделить на шаги (например, этап 1: только извлечение из Raw в промежуточный слой; этап 2: чтение из промежуточного слоя, преобразования и запись в Staging). Тогда в Workflow создаются два узла-этапа, между ними — связь «этап 2 после этапа 1»; параметры (дата, путь к промежуточному каталогу) передаются по связи или из конфигурации Workflow ([§6.4](chapter-06-04.md)). Каждый этап — отдельный поток и отдельный JAR (или один JAR с разными точками входа).

В обоих случаях в свойствах этапа задаётся: какой поток (или main class) запускать, при необходимости — аргументы и переменные окружения. Сгенерированный DAG (Airflow) или workflow (Oozie) содержит соответствующие задачи и зависимости. Параметр даты среза подставляется при запуске Workflow (ручной ввод или из расписания) и передаётся в задачу запуска Spark ([§7.3](chapter-07-03.md)).

## 8.4.2. Запуск пайплайна

**Запуск** выполняется после сборки проекта ([§7.1](chapter-07-01.md)) и развёртывания артефактов: JAR и при необходимости конфиги и артефакты Workflow размещаются в среде, откуда оркестратор выполняет задачи.

- **Ручной запуск** — в интерфейсе Airflow (trigger DAG) или Oozie (submit job) задаётся дата среза (и при необходимости другие параметры) и запускается выполнение. Задачи выполняются в порядке графа; логи и статус доступны в UI оркестратора и в Spark UI ([§7.4](chapter-07-04.md)).
- **Запуск по расписанию** — в настройках DAG/workflow задаётся расписание (например, ежедневно в 02:00); оркестратор создаёт экземпляр запуска с датой (часто «вчера» или текущая дата) и выполняет этапы. Параметры даты подставляются из шаблона расписания или из конфигурации.
- **Проверка перед продакшеном** — сначала запуск на тестовом окружении с тестовой датой и проверка результата (сверка данных, см. ниже); после успешной проверки — включение расписания или ручные запуски на prod.

При сбое этапа оркестратор помечает задачу как failed; последующие этапы (при последовательной цепочке) не запускаются. Разбор логов и Spark UI ([§7.4](chapter-07-04.md)) позволяет локализовать ошибку; после исправления — перезапуск с той же датой среза без повторного выполнения уже успешных этапов (если оркестратор поддерживает перезапуск с места сбоя).

## 8.4.3. Сверка данных

**Сверка данных** — проверка того, что загрузка выполнилась корректно: объём, целостность, выборочное сравнение с источником.

- **Объём** — количество записей в целевой Hive-таблице за дату среза (или в партиции). Можно выполнить запрос `SELECT COUNT(*) FROM staging.events WHERE date = '2025-02-16'` и сравнить с ожидаемым числом или с количеством записей в источнике (подсчёт строк в Parquet/ORC за эту дату). Расхождение может указывать на фильтрацию (ожидаемую или на ошибку в условиях), дубликаты или потерю данных.
- **Выборочная сверка** — сравнение нескольких полей по выборке строк между источником и приёмником: те же ключи, те же значения после преобразований. Для этого источник (файлы за дату) и целевая таблица читаются в двух запросах или в двух потоках; результат сравнивается по ключу (например, по id). Можно автоматизировать проверку в отдельном этапе Workflow (скрипт или Spark-задание, выполняющее запросы и сравнивающее агрегаты или сэмплы).
- **Целостность и качество** — отсутствие NULL в ключевых полях (если по бизнес-правилам не допускается), проверка диапазонов (даты, суммы), дубликаты по ключу. Такие проверки могут быть оформлены как отдельный этап «валидация» после загрузки или как регламентный отчёт.

Результат сверки фиксируется в логах или в отчёте; при расхождениях — разбор (конфигурация пути, фильтры, схема) и повторный запуск при необходимости. Регулярная сверка после каждого запуска повышает доверие к пайплайну и позволяет быстро обнаружить регрессии.

## Ключевое

- **Workflow:** один этап (один поток «Raw → Staging») или несколько этапов с зависимостями; в свойствах этапа — поток/JAR, параметры; дата среза передаётся при запуске и подставляется в задачу Spark.
- **Запуск:** ручной (trigger с параметрами) или по расписанию; перед продакшеном — проверка на тестовом окружении; при сбое — логи и Spark UI, исправление и перезапуск.
- **Сверка данных:** объём записей (сравнение с источником), выборочная сверка по полям, проверка целостности и качества; при расхождениях — разбор и повторный запуск.
