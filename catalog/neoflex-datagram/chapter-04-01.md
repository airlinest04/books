# §4.1 Spark SQL в Datagram

В [§3.5](chapter-03-05.md) мы разобрали сложноструктурированные форматы (XML, JSON, Avro). Глава 4 посвящена **трансформациям данных** в Neoflex Datagram. В этом разделе рассматривается **Spark SQL** как один из типов преобразований в потоке: использование SQL-запросов над данными, поступившими из источников или из предыдущих трансформаций, и работа с вложенными структурами (struct, поля JSON). Spark SQL позволяет выражать фильтрацию, проекцию, вычисляемые поля и соединения в привычном виде запросов; сгенерированный код вызывает API Spark SQL (DataFrame, spark.sql). В [§4.2](chapter-04-02.md) мы разберём операции реляционной алгебры: Join, Sort, Aggregation в визуальном представлении. См. [Глоссарий](glossary.md).

---

## 4.1.1. Роль Spark SQL в потоке трансформаций

**Spark SQL** — модуль Apache Spark, предоставляющий доступ к данным через SQL-подобный язык и через API DataFrame/DataSet. Данные представляются как таблицы (виртуальные или зарегистрированные представления); над ними выполняются запросы SELECT с фильтрами (WHERE), выражениями (вычисляемые столбцы), агрегацией (GROUP BY, агрегатные функции) и соединениями (JOIN). В среде исполнения Spark эти запросы преобразуются в граф вычислений (логический и физический план) и выполняются распределённо на кластере.

В Neoflex Datagram **трансформация типа Spark SQL** в потоке означает: входной DataFrame (результат источника или предыдущей трансформации) обрабатывается с помощью SQL-запроса. В дизайнере разработчик задаёт текст запроса или выбирает поля и условия через визуальный интерфейс; платформа генерирует код, в котором входной набор регистрируется как временная таблица или представление (temp view), выполняется запрос `spark.sql("...")` и результат передаётся следующему элементу потока. Таким образом, сложная логика (многоступенчатые условия, вложенные подзапросы, оконные функции) может быть выражена в SQL без перехода к отдельным элементам «фильтр» или «выражение» для каждого шага. Подробнее о визуальных элементах Join, Sort, Aggregation — в [§4.2](chapter-04-02.md); о маппинге и преобразовании полей — в [§4.3](chapter-04-03.md).

## 4.1.2. Запросы в потоке: источники и выражения

Входом для трансформации Spark SQL служит **один или несколько** DataFrame, полученных из источников или из предыдущих трансформаций. В типичном сценарии:

- Входной DataFrame регистрируется как временное представление с заданным именем (например, `input_df.createOrReplaceTempView("source_table")`). В запросе к нему обращаются по этому имени.
- В запросе указываются: список выбираемых столбцов (или `*`), переименование (AS), вычисляемые выражения (функции, арифметика, CASE WHEN), фильтр WHERE, при необходимости GROUP BY и агрегатные функции, ORDER BY. Синтаксис соответствует Spark SQL (диалект HiveQL-подобный).
- Результат запроса — новый DataFrame; он становится выходом трансформации и может быть подключён к следующему элементу (другая трансформация или приёмник).

Пример логики в виде SQL (в сгенерированном коде будет вызов `spark.sql(...)`):

```sql
SELECT
  id,
  UPPER(name) AS name_upper,
  amount * rate AS total,
  CASE WHEN status = 'A' THEN 1 ELSE 0 END AS flag
FROM source_table
WHERE date_col >= '2025-01-01'
```

Ограничения и возможности (подзапросы, CTE, оконные функции) определяются поддержкой Spark SQL и тем, как дизайнер Datagram передаёт запрос в генератор. Актуальный список поддерживаемых конструкций уточняйте в документации Neoflex. Книга серии «Spark (PySpark)» ([../spark-pyspark/](../spark-pyspark/)) даёт полный обзор Spark SQL.

## 4.1.3. Вложенные структуры и работа с полями

Данные из источников JSON, Avro или из Hive с комплексными типами часто приходят во **вложенном виде**: столбец типа **struct** (структура с полями) или **array**. В Spark SQL к полям структуры обращаются через **точечную нотацию**: `struct_col.field_name` или в SQL `struct_col.field_name`. Для массива используются функции `explode`, `explode_outer`, `inline` и подобные, чтобы развернуть элементы в отдельные строки.

Пример: после парсинга JSON из Kafka столбец `value` может быть разобран в структуру `payload` с полями `event_id`, `user_id`, `items` (массив). В трансформации Spark SQL можно написать:

```sql
SELECT
  payload.event_id,
  payload.user_id,
  payload.items
FROM parsed_kafka
WHERE payload.event_id IS NOT NULL
```

Дальнейшая работа с массивом `items`: развернуть через `explode(payload.items) AS item` и при необходимости join обратно или агрегировать. Для сырой строки JSON без предварительного парсинга в структуру Spark SQL предоставляет **get_json_object(string_column, '$.path')** — извлечение значения по JSONPath. В дизайнере Datagram возможность задавать такие запросы и обращаться к вложенным полям зависит от того, как платформа экспонирует схему источника (struct-поля отображаются в метаданных и могут быть доступны в конструкторе запроса). Подробнее разбор JSON и маппинг — в [§3.5](chapter-03-05.md) и [§4.3](chapter-04-03.md).

## 4.1.4. Несколько входов и временные представления

Если трансформация Spark SQL должна объединять **несколько входов** (например, два источника или результат двух предыдущих трансформаций), каждый вход регистрируется под своим именем представления. В одном запросе затем выполняются JOIN по этим представлениям. Альтернатива — использовать отдельный визуальный элемент **Join** ([§4.2](chapter-04-02.md)), который явно задаёт ключи и тип соединения; генератор при этом может порождать тот же Spark SQL под капотом или вызовы DataFrame.join(). Выбор «Spark SQL с JOIN в запросе» vs «элемент Join» зависит от принятой в проекте практики и возможностей дизайнера (удобство ревью, повторное использование, параметризация).

Временные представления (temp views), создаваемые в сгенерированном коде, существуют в рамках одной сессии Spark (одного задания); после завершения задания они не сохраняются. Имена представлений должны быть уникальны в пределах одного потока трансформаций в задании; конфликтов с постоянными таблицами Hive при использовании разных имён не возникает.

## Ключевое

- **Spark SQL в потоке** — трансформация, в которой над входным DataFrame выполняется SQL-запрос; вход регистрируется как временное представление, результат запроса — выход трансформации.
- **Запросы:** SELECT с фильтрами WHERE, вычисляемыми полями, агрегацией и GROUP BY, ORDER BY; синтаксис Spark SQL (HiveQL-подобный). Подзапросы, CTE, оконные функции — по поддержке платформы и Spark.
- **Вложенные структуры:** обращение к полям struct через точечную нотацию (`struct_col.field`); массивы — через explode и др.; для сырого JSON — get_json_object по JSONPath.
- **Несколько входов:** каждому входу — своё имя представления; JOIN в одном запросе или отдельный элемент Join. Временные представления действуют в рамках сессии (задания).
