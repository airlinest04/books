# §5.4 Просмотр сгенерированного Scala-кода

В [§5.3](chapter-05-03.md) мы разобрали проверку промежуточных результатов и валидацию. В этом разделе рассматривается **просмотр сгенерированного Scala-кода**: что именно генерируется из модели потока, как соотнести элементы дизайнера с фрагментами кода, когда уместна ручная доработка и как использовать знание кода для отладки. Раздел завершает главу 5; в [§6.1](chapter-06-01.md) мы перейдём к дизайнеру Workflow — последовательному выполнению этапов. См. [Глоссарий](glossary.md).

---

## 5.4.1. Что генерируется

Из модели потока трансформаций (источники, трансформации, приёмники и связи между ними) платформа **генерирует исходный код** на Scala (при поддержке — на Python). Результат генерации — файлы в каталоге проекта: один или несколько модулей с точкой входа (например, метод `main` или объект, вызываемый Spark), код чтения из источников, цепочка трансформаций (переменные DataFrame и вызовы методов Spark), код записи в приёмники. Структура каталогов и имён файлов определяется шаблонами платформы (например, отдельный файл на поток или один файл с несколькими потоками). После генерации проект собирается (compile) в артефакт (JAR) для запуска на кластере ([§2.3](chapter-02-03.md), [§7.1](chapter-07-01.md)).

Генерируется только **код трансформаций** (логика потока данных). Описания для оркестратора (Airflow DAG, Oozie workflow) создаются из модели Workflow отдельно ([§2.2](chapter-02-02.md)). Просмотр сгенерированного кода возможен в виде исходных файлов в файловой системе проекта или в отдельной панели/окне дизайнера, если платформа предоставляет встроенный просмотр. Актуальное расположение артефактов генерации и способ их открытия уточняйте в документации Neoflex.

## 5.4.2. Соответствие модель — код

Каждый элемент потока в дизайнере отображается в один или несколько фрагментов сгенерированного кода. Типичные соответствия (по [§1.2](chapter-01-02.md) и [§2.3](chapter-02-03.md)):

| Элемент модели | Типичный фрагмент кода (идея) |
|----------------|-------------------------------|
| Источник (файл Parquet) | `val df = spark.read.format("parquet").schema(...).load(path)` |
| Источник (Kafka, streaming) | `spark.readStream.format("kafka").option(...).load()` |
| Источник (Hive) | `spark.table("db.table")` или `spark.sql("SELECT ... FROM ...")` |
| Источник (JDBC) | `spark.read.format("jdbc").option("url", ...).option("dbtable", ...).load()` |
| Фильтр | `df.filter(expr("..."))` или `.where(...)` |
| Маппинг / выражения | `df.withColumn("new_col", expr("..."))` |
| Join | `left.join(right, joinExpr, "inner"\|"left"\|...)` |
| Sort | `df.orderBy(col("a").asc, col("b").desc)` |
| Aggregation | `df.groupBy("k1","k2").agg(sum("v"), count("*"), ...)` |
| Spark SQL | `spark.sql("SELECT ... FROM ...")` с предварительной регистрацией temp view |
| Приёмник (файл) | `df.write.format("parquet").mode("overwrite").save(path)` |
| Приёмник (Hive) | запись через Spark в Hive-таблицу |

Порядок в коде следует топологии графа: сначала чтение из источников, затем цепочка присваиваний (результат каждой трансформации передаётся следующей), в конце запись в приёмник(ы). Имена переменных и комментарии в коде зависят от генератора; при наличии комментариев с идентификаторами элементов дизайнера проще сопоставить участок кода с элементом на графе. Понимание этого соответствия помогает при отладке по логам Spark: сообщение об ошибке со ссылкой на строку кода можно соотнести с конкретной трансформацией в потоке.

## 5.4.3. Когда править вручную и риск перезаписи

Сгенерированный код можно **редактировать вручную** для нестандартной логики, тонкой оптимизации или обхода ограничений дизайнера (например, вызов API Spark, для которого нет визуального элемента). Файлы кода хранятся в репозитории вместе с проектом; после правок проект пересобирается и разворачивается как обычно.

**Важно:** при следующем **запуске генерации из модели** (после изменения потока в дизайнере и запросе «сгенерировать код») сгенерированные файлы обычно **перезаписываются**. Ручные правки в них будут потеряны, если платформа не поддерживает защищённые регионы (например, помеченные комментариями «не изменять») или вынос кастомной логики в отдельные модули, не трогаемые генератором. Поэтому порядок сопровождения нужно согласовать заранее: либо правки только в модели (без ручного кода), либо ручные правки в выделенных файлах/блоках при поддержке платформой, либо отказ от повторной генерации для данного потока и дальнейшее сопровождение кода вручную. Подробнее ограничения и стратегии — в [§1.2](chapter-01-02.md); актуальное поведение генератора — в документации Neoflex.

## 5.4.4. Понимание кода для отладки

При сбое на кластере Spark выдаёт трассировку с номерами строк сгенерированного кода. Умение **прочитать этот код** и соотнести строку с элементом потока позволяет быстро понять, на каком шаге произошла ошибка (источник, конкретная трансформация, приёмник) и какие данные или параметры могли к ней привести. Достаточно базового понимания Spark API: `read`/`readStream`, `filter`, `join`, `groupBy`, `agg`, `write` — без углубления в внутренности Spark. При необходимости оптимизации (медленный Join, out of memory) знание сгенерированного кода подсказывает, где добавить broadcast, изменить партиционирование или разбить поток; такие правки снова упираются в вопрос перезаписи при повторной генерации. Книга «Spark (PySpark)» ([../spark-pyspark/](../spark-pyspark/)) даёт основы Spark для углублённой отладки и оптимизации.

## Ключевое

- **Генерируется:** исходники Scala (или Python) по модели потока — чтение, цепочка трансформаций, запись; структура проекта определяется платформой. Workflow генерируется отдельно (Airflow/Oozie).
- **Соответствие модель–код:** каждый тип элемента (источник, Filter, Join, Aggregation, приёмник и т.д.) отображается в типичный вызов Spark API; порядок в коде следует графу потока. Таблица соответствий помогает при отладке по номерам строк.
- **Ручная доработка** возможна, но повторная генерация из модели обычно перезаписывает файлы; нужна согласованная стратегия (только модель, защищённые блоки или отказ от повторной генерации). См. [§1.2](chapter-01-02.md).
- **Понимание кода** нужно для интерпретации логов Spark и для точечной оптимизации; базового знания Spark API достаточно для типичной отладки.
