# §4.5 Партиции и индексы вместе

В [§4.4](chapter-04-04.md) мы разобрали партиционирование по диапазону, списку и хешу. Партиционированная таблица по-прежнему нуждается в индексах для быстрого поиска и сортировки; при этом встаёт вопрос: индексировать каждую партицию **отдельно** (локальные индексы) или строить **один индекс на всю таблицу** (глобальный индекс). В этом разделе мы разберём различие локальных и глобальных индексов и дадим практические рекомендации по индексированию партиционированных таблиц. Раздел завершает главу 4; в [§5.1](chapter-05-01.md) перейдём к транзакциям: определение, границы (BEGIN, COMMIT, ROLLBACK) и явные/неявные транзакции.

---

## 4.5.1. Локальный индекс (на каждую партицию)

**Локальный индекс** (local index) — индекс, построенный в рамках одной партиции: каждая партиция имеет свой экземпляр индекса по тем же столбцам. Логически это «один» индекс на партиционированную таблицу (пользователь создаёт индекс на родительской таблице), но физически СУБД хранит отдельный индекс по каждой партиции. См. [Глоссарий](glossary.md).

**Свойства:**

- При добавлении или удалении партиции соответствующий индекс добавляется или удаляется вместе с ней; не нужно перестраивать общий индекс.
- При удалении партиции (например, за старый год) удаляется только её индекс — операция быстрая.
- Запрос с условием по ключу партиционирования: СУБД сначала выбирает партицию(и) (partition pruning), затем использует локальный индекс только внутри выбранных партиций. Размер каждого локального индекса меньше, чем один глобальный на всю таблицу.
- Запрос **без** условия по ключу партиционирования: сканируются все партиции; в каждой может использоваться локальный индекс по другим столбцам, но общий индекс по всей таблице для «глобального» поиска отсутствует.

В PostgreSQL при создании индекса на партиционированной таблице по умолчанию создаётся именно локальный индекс (индекс на родителе автоматически создаётся на каждой партиции и на новых партициях при их добавлении). В Oracle и других СУБД терминология и реализация могут отличаться; суть та же: один индекс на партицию.

---

## 4.5.2. Глобальный индекс (на всю таблицу)

**Глобальный индекс** (global index) — один индекс, охватывающий все партиции таблицы; ключ индекса не обязан совпадать с ключом партиционирования. По такому индексу можно искать по значению столбца без предварительного определения партиции. См. [Глоссарий](glossary.md).

**Свойства:**

- Запрос по столбцу, входящему в глобальный индекс (например, поиск по `order_id` при партиционировании по `order_date`), может быть выполнен по индексу без перебора партиций: индекс сразу указывает на партицию и строку.
- При удалении партиции глобальный индекс нужно обновлять (удалить из индекса все записи этой партиции). В СУБД, поддерживающих глобальные индексы, это может делаться автоматически, но операция дороже, чем при локальных индексах.
- Глобальный индекс занимает место как единая структура; при большом объёме данных он может быть очень большим.

Не все СУБД поддерживают глобальные индексы в явном виде. В PostgreSQL, например, нет встроенного глобального индекса на партиционированную таблицу: индексы на партиционированной таблице по сути локальные. Для сценариев «поиск по ID без условия по дате» полагаются на partition pruning по другим признакам или на то, что запрос по первичному ключу часто включает ключ партиционирования (например, (order_id, order_date)), и тогда нужная партиция определяется. В Oracle глобальные индексы существуют и могут быть предпочтительны для поиска по уникальному ключу, не совпадающему с ключом партиционирования.

---

## 4.5.3. Когда что выбирать

| Критерий | Локальный индекс | Глобальный индекс |
|----------|------------------|-------------------|
| Удаление/архивирование партиций | Удобно: индекс удаляется вместе с партицией | Требуется обновление индекса при удалении партиции |
| Запросы с условием по ключу партиционирования | Эффективно: pruning + индекс внутри партиции | Также пригоден |
| Запросы без условия по ключу партиционирования (например, по ID) | Сканирование всех партиций или их локальных индексов | Один проход по глобальному индексу |
| Размер индекса | Несколько меньших индексов | Один большой индекс |
| Поддержка в СУБД | Широко (PostgreSQL, Oracle и др.) | Зависит от СУБД (например, есть в Oracle) |

**Рекомендация в общем случае:** для партиционированных таблиц предпочтительны **локальные индексы**: они проще в сопровождении при добавлении и удалении партиций и хорошо работают при запросах с условием по ключу партиционирования (типичный случай для таблиц, разбитых по дате или категории). Глобальный индекс рассматривать, когда часты запросы по уникальному ключу (например, order_id) без условия по ключу партиционирования и СУБД это поддерживает.

## 4.5.4. Практические рекомендации

**Включить ключ партиционирования в составной индекс.** Для запроса «по клиенту и дате» при партиционировании по дате составной индекс (order_date, customer_id) или (customer_id, order_date) на партиционированной таблице создаётся локально в каждой партиции. Тогда после partition pruning по дате в выбранной партиции используется локальный индекс по customer_id (или по паре). Порядок столбцов — по правилам из [§4.3](chapter-04-03.md).

**Первичный ключ и уникальность.** В партиционированной таблице первичный ключ и уникальные ограничения должны включать ключ партиционирования (в PostgreSQL это требование), иначе уникальность нельзя гарантировать локально внутри партиции. Тогда поиск по первичному ключу всегда содержит ключ партиционирования и партиция определяется однозначно; отдельный глобальный индекс для PK не нужен.

**Избегать избыточных индексов на партициях.** Каждый локальный индекс умножается на число партиций; лишние индексы увеличивают объём и замедляют запись. Создавать только те индексы, которые реально используются в запросах к партиционированной таблице.

**Мониторинг и планирование.** После введения партиционирования проверять планы запросов: срабатывает ли partition pruning, используются ли локальные индексы. При появлении новых партиций (RANGE) убедиться, что индексы создаются на новых партициях автоматически или по скрипту.

---

## 4.5.5. Типичные ошибки

- **Ожидать глобальный индекс в СУБД, где его нет:** в PostgreSQL индексы на партиционированной таблице локальные; запросы без условия по ключу партиционирования будут сканировать все партиции. Проектировать ключ партиционирования и запросы так, чтобы по возможности всегда был фильтр по ключу.
- **Не включать ключ партиционирования в PK/UNIQUE:** в СУБД с требованием «уникальность должна включать ключ партиции» ограничение не создастся; кроме того, без ключа партиционирования в PK поиск по PK не даёт pruning.
- **Дублировать индексы на родителе и на партициях вручную:** при корректной настройке индекса на родительской партиционированной таблице СУБД сама создаёт индексы на партициях; ручное создание на каждой партиции приводит к дублированию и путанице.

---

## Ключевое

- **Локальный индекс** — отдельный индекс на каждую партицию (те же столбцы). Удобен при удалении и добавлении партиций; запросы с условием по ключу партиционирования используют pruning и индекс внутри выбранных партиций.
- **Глобальный индекс** — один индекс на всю таблицу. Удобен для поиска по значению без условия по ключу партиционирования; при удалении партиции индекс нужно обновлять. Поддержка зависит от СУБД (есть в Oracle; в PostgreSQL индексы на партиционированной таблице по сути локальные).
- Рекомендации: предпочитать локальные индексы; включать ключ партиционирования в первичный ключ и в составные индексы под запросы; не создавать лишних индексов; проверять partition pruning и использование индексов в планах.
- Первичный ключ партиционированной таблицы должен включать ключ партиционирования (в PostgreSQL — обязательно); тогда поиск по PK определяет партицию и глобальный индекс не требуется.
