# §4.3 Составные индексы и порядок столбцов

В [§4.2](chapter-04-02.md) мы разобрали типы индексов (B-tree, hash, GiST, GIN). Часто условие в запросе или сортировка затрагивают **несколько столбцов**; тогда создают **составной индекс** (composite index) по этим столбцам. От **порядка столбцов** в индексе зависит, сможет ли оптимизатор использовать индекс для конкретного WHERE и ORDER BY. В этом разделе мы разберём, как составной индекс покрывает условия WHERE и ORDER BY и как учитывать **селективность** при выборе порядка столбцов. В [§4.4](chapter-04-04.md) перейдём к партиционированию таблиц.

---

## 4.3.1. Что такое составной индекс

**Составной индекс** (composite index, compound index) — индекс по двум или более столбцам таблицы. Ключ индекса — упорядоченная последовательность значений: сначала по первому столбцу, при равенстве первого — по второму, и т.д. (для B-tree). См. [Глоссарий](glossary.md).

Пример: индекс `(customer_id, order_date)`. Записи в индексе упорядочены по `customer_id`; внутри одного `customer_id` — по `order_date`. Такой индекс может использоваться для запроса «заказы клиента X за период»: поиск по `customer_id`, затем по диапазону `order_date` внутри найденного блока.

Составной индекс **не** эквивалентен нескольким отдельным индексам по каждому столбцу: один индекс `(a, b)` даёт порядок «сначала a, потом b»; отдельные индексы по `a` и по `b` дают два независимых порядка. Оптимизатор может использовать составной индекс для условий только по первому столбцу (и по префиксу столбцов слева направо), но не для условия только по второму столбцу без первого.

---

## 4.3.2. Правило префикса (левые столбцы)

В B-tree составном индексе `(col1, col2, col3)` данные упорядочены по `col1`, затем по `col2`, затем по `col3`. Поэтому индекс может эффективно использоваться для:

- условия только по `col1`;
- условия по `col1` и `col2`;
- условия по `col1`, `col2` и `col3`.

Условие **только по col2** или только по **col3** (без col1) по такому индексу эффективно искать нельзя: в индексе нет порядка «сначала по col2». Оптимизатор может при определённых условиях использовать index-only scan или сканировать индекс целиком, но как правило для условия только по «правому» столбцу составной индекс не даёт выигрыша по сравнению с полным сканированием таблицы или требует отдельного индекса по этому столбцу.

**Итог:** составной индекс полезен для запросов, в которых условия заданы по **префиксу** столбцов слева направо (и при необходимости по всем столбцам). Порядок столбцов в индексе нужно выбирать под типичные запросы.

---

## 4.3.3. Покрытие условий WHERE

Чтобы составной индекс использовался в условии WHERE, условия должны относиться к столбцам в порядке **слева направо** без пропусков (для диапазона — последний используемый столбец может быть диапазоном).

**Примеры для индекса (customer_id, order_date):**

- `WHERE customer_id = 123` — используется (равенство по первому столбцу).
- `WHERE customer_id = 123 AND order_date BETWEEN '2024-01-01' AND '2024-01-31'` — используется (равенство по первому, диапазон по второму).
- `WHERE order_date = '2024-01-15'` — индекс по (customer_id, order_date) для одного этого условия по сути не помогает (нет условия по customer_id).

**Равенство vs диапазон:** часто выгодно ставить столбцы с условиями **равенства** (=, IN) левее, а столбец с **диапазоном** (BETWEEN, <, >) — последним в используемом префиксе. Тогда индекс сужает выборку по равенствам, а диапазон применяется к уже отфильтрованному множеству. Например, для запроса `WHERE customer_id = 123 AND order_date BETWEEN ... AND ...` порядок (customer_id, order_date) подходит; порядок (order_date, customer_id) подходит для запроса по диапазону дат и затем по клиенту, но для «конкретный клиент + диапазон дат» первый вариант лучше.

---

## 4.3.4. Покрытие ORDER BY

Составной B-tree индекс может избавить от отдельной операции сортировки, если порядок в индексе совпадает с ORDER BY (или с обратным порядком при DESC). Важно: столбцы в ORDER BY должны идти в том же порядке, что и в индексе, и направления сортировки (ASC/DESC) должны быть согласованы.

**Примеры для индекса (customer_id, order_date):**

- `ORDER BY customer_id, order_date` — порядок совпадает с индексом; сортировка не нужна.
- `ORDER BY customer_id, order_date DESC` — в части СУБД индекс может использоваться при поддержке обратного сканирования по второму столбцу.
- `ORDER BY order_date` — порядок по индексу не совпадает (в индексе сначала customer_id); для сортировки только по order_date этот индекс не подходит.

Если запрос содержит и WHERE, и ORDER BY, индекс должен сначала покрывать используемые условия WHERE (по префиксу), а затем столбцы ORDER BY. Например, для `WHERE customer_id = 123 ORDER BY order_date` индекс (customer_id, order_date) даёт и фильтр по customer_id, и нужный порядок по order_date внутри выбранного клиента.

## 4.3.5. Селективность и порядок столбцов

**Селективность** (selectivity) столбца — доля строк, отбираемых типичным условием по этому столбцу: чем меньше доля, тем селективнее условие. Высокоселективный столбец (например, уникальный идентификатор) отсекает почти все строки; низкоселективный (например, пол/статус с двумя-тремя значениями) оставляет большую часть таблицы.

При выборе порядка столбцов в составном индексе часто рекомендуют ставить **более селективный столбец левее**, чтобы индекс быстрее сужал множество строк. Это не универсальное правило: важнее соответствие порядку условий в запросах. Если в типичном запросе всегда есть равенство по `customer_id` и затем диапазон по `order_date`, то индекс (customer_id, order_date) правильный независимо от того, селективнее ли customer_id или order_date. Если запросы разнообразны (иногда только по дате, иногда по клиенту и дате), может понадобиться несколько индексов или компромиссный порядок под самый частый сценарий.

Итог: порядок столбцов в индексе выбирают под **конкретные запросы** (какие условия и какой ORDER BY встречаются чаще всего); селективность учитывают как дополнительный фактор, но не в ущерб правилу префикса.

## 4.3.6. Примеры выбора порядка

**Запрос:** заказы клиента за месяц, сортировка по дате.

- Рекомендуемый индекс: `(customer_id, order_date)`. WHERE по customer_id и order_date; ORDER BY order_date — порядок по второму столбцу внутри первого совпадает с индексом.

**Запрос:** последние заказы по всем клиентам (топ-N по дате).

- Индекс по одному `order_date` или составной с `order_date` первым: например `(order_date DESC, order_id)` для стабильной сортировки и лимита. Индекс (customer_id, order_date) для такого запроса не подходит — нужен порядок глобально по дате.

**Запрос:** проверка существования пары (user_id, product_id) — точечный поиск.

- Индекс `(user_id, product_id)` или `(product_id, user_id)` — оба покрывают условие равенства по обоим столбцам. Выбор по тому, по какому столбцу чаще фильтруют отдельно; при необходимости два индекса с разным порядком (редко, из-за стоимости записи).

## 4.3.7. Типичные ошибки

- **Ставить столбец с диапазоном первым в индексе**, когда типичный запрос — равенство по другому столбцу и диапазон по дате. Тогда префикс индекса не совпадает с условием равенства и индекс используется хуже.
- **Ожидать, что индекс (a, b) обслуживает запрос с условием только по b:** по правилу префикса условие по b без a индекс не покрывает. Нужен отдельный индекс по b или другой порядок, если запросы только по b часты.
- **Игнорировать ORDER BY:** индекс, подходящий по WHERE, может не подходить по ORDER BY; тогда остаётся явная сортировка. Добавить в индекс столбцы из ORDER BY в нужном порядке (после столбцов WHERE).
- **Создавать слишком много составных индексов под каждый вариант запроса:** каждый индекс замедляет запись. Выбрать один-два самых критичных варианта запросов и порядок столбцов под них.

---

## Ключевое

- **Составной индекс** — индекс по нескольким столбцам; в B-tree порядок ключа: первый столбец, при равенстве — второй и т.д. Используется для условий и сортировки по **префиксу** столбцов слева направо.
- **Правило префикса:** индекс (a, b, c) полезен для условий по a; по a и b; по a, b и c. Условие только по b или c без a по такому индексу эффективно не обслуживается.
- **WHERE:** условия должны задаваться по столбцам в порядке индекса; обычно столбцы с равенством левее, с диапазоном — последний в префиксе. **ORDER BY:** порядок и направление сортировки должны совпадать с порядком столбцов в индексе (или с обратным сканом при DESC).
- **Селективность** учитывают при выборе порядка, но приоритет — соответствие типичным запросам (какие условия и какой ORDER BY). Не создавать избыточное число составных индексов.
