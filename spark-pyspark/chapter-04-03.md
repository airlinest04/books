# §4.3 Партиционирование при записи

В [§4.2](chapter-04-02.md) мы разобрали пути к данным: HDFS и объектные хранилища (s3a). При записи DataFrame можно не только указать формат и путь, но и **разбить вывод по значениям столбцов** — партиционирование по данным. В этом разделе рассмотрим **partitionBy**: какая структура каталогов получается, как это влияет на **последующие чтения** и фильтрацию (partition pruning) и как выбирать столбцы партиционирования. Детали записи в PySpark и настройка числа партиций — в [§6.4](chapter-06-04.md) и [§6.6](chapter-06-06.md). В [§4.4](chapter-04-04.md) перейдём к интеграции с DWH по JDBC. См. [Глоссарий](glossary.md).

---

## 4.3.1. partitionBy: разбиение по столбцам

При записи вызов **`df.write.partitionBy("col1", "col2").format(...).save("path")`** разбивает данные так, что для каждой **комбинации значений** партиционных столбцов создаётся отдельный подкаталог. Данные записываются не в один общий каталог, а по подкаталогам; каждая партиция (в смысле «один подкаталог по значениям col1, col2») содержит только строки с соответствующей комбинацией. Партиционные столбцы в записанных файлах по умолчанию **не сохраняются** как отдельные колонки в данных: они закодированы в пути. При чтении Spark (и совместимые движки) восстанавливают эти столбцы из структуры каталогов и добавляют их в схему DataFrame. См. [§4.1](chapter-04-01.md), [Глоссарий](glossary.md).

---

## 4.3.2. Каталоговая структура

Типичная структура после записи с **partitionBy("date", "region")** в путь `path`:

```
path/
  date=2024-01-01/
    region=eu/
      part-00000-....parquet
      part-00001-....parquet
    region=us/
      part-00000-....parquet
  date=2024-01-02/
    region=eu/
      ...
```

Имена подкаталогов имеют вид **`имя_столбца=значение`**. Порядок уровней соответствует порядку столбцов в `partitionBy`. Внутри конечного подкаталога лежат файлы формата (Parquet, ORC и т.д.), по одному или несколько на партицию Spark (на каждую партицию DataFrame при записи). Число файлов в подкаталоге можно контролировать через **coalesce** или **repartition** перед записью (см. [§6.6](chapter-06-06.md)). См. [Глоссарий](glossary.md).

## 4.3.3. Влияние на последующие чтения: partition pruning

Партиционирование по столбцам даёт выигрыш при **чтении с фильтром** по этим столбцам. При запросе вида `spark.read.parquet("path").filter(col("date") == "2024-01-01")` планировщик может применить **partition pruning** (отсечение партиций): он знает, что данные с `date=2024-01-01` лежат только в подкаталоге `date=2024-01-01/`, и читает **только** эти подкаталоги, не сканируя остальные. Объём прочитанных данных и время чтения снижаются. То же для нескольких условий: `filter((col("date") >= "2024-01-01") & (col("region") == "eu"))` позволяет читать только подкаталоги, удовлетворяющие условиям. См. [§2.2](chapter-02-02.md), [Глоссарий](glossary.md).

Чтобы pruning работал, фильтр должен быть выражен в терминах **партиционных столбцов** и по возможности в форме, распознаваемой оптимизатором (сравнения с константой, IN, диапазоны). Фильтр только по непартиционным столбцам не уменьшает число читаемых партиций — будут прочитаны все подкаталоги, а фильтрация по данным произойдёт уже после чтения. См. [§6.1](chapter-06-01.md).

## 4.3.4. Выбор столбцов партиционирования

Столбцы для **partitionBy** стоит выбирать по тому, как данные будут запрашиваться:

- **Частые фильтры:** столбцы, по которым часто фильтруют (дата, регион, тип события), — хорошие кандидаты. Тогда типичные запросы получают выигрыш от partition pruning.
- **Кардинальность:** слишком высокая кардинальность (уникальное значение на строку) даёт огромное число подкаталогов и мелких файлов, что ухудшает производительность планирования и чтения. Обычно партиционируют по столбцам с умеренным числом значений (даты, категории, регионы).
- **Баланс:** один партиционный столбец с двумя значениями даёт только два подкаталога; при очень большом объёме данных в каждом подкаталоге можно добавить второй уровень (например, date и затем region). Слишком много уровней и слишком много партиций увеличивают накладные расходы.

Партиционирование по **дате** (день или месяц) — распространённый вариант для логов и событий: запросы «за последние 7 дней» или «за январь» читают только нужные подкаталоги. См. [§6.4](chapter-06-04.md), [§6.6](chapter-06-06.md).

## 4.3.5. Режимы записи и партиционированные каталоги

При **overwrite** и партиционированной записи поведение может отличаться по версиям: в одних реализациях перезаписывается весь корневой каталог, в других — только затронутые партиции. При **append** новые данные дописываются в соответствующие подкаталоги; если партиция уже существовала, в ней появятся дополнительные файлы. При частом append в одни и те же партиции число файлов в подкаталогах может сильно вырасти; периодическая перезапись (например, объединение мелких файлов в крупные) или настройка числа партиций при записи помогают держать структуру управляемой. См. [§4.1](chapter-04-01.md), [§6.6](chapter-06-06.md).

---

## Ключевое

- **partitionBy("col1", "col2")** при записи создаёт подкаталоги вида **col1=value1/col2=value2/**; данные разбиваются по комбинациям значений; партиционные столбцы восстанавливаются из путей при чтении.
- **Структура каталогов** — иерархия по именам столбцов и значениям; внутри — файлы формата (Parquet и т.д.); число файлов на партицию задаётся числом партиций DataFrame при записи (repartition/coalesce).
- **Partition pruning:** при чтении с фильтром по партиционным столбцам оптимизатор читает только подходящие подкаталоги, что снижает объём I/O и ускоряет запросы.
- **Выбор столбцов:** те, по которым часто фильтруют; умеренная кардинальность; типичный пример — дата (день/месяц) для событий и логов.
- Режимы overwrite/append влияют на то, перезаписывается ли весь каталог или только партиции; при append число файлов в партиции может расти — полезно контролировать через repartition/coalesce или периодическую перезапись.
