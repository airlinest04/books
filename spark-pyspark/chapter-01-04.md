# §1.4 Языки и API

В [§1.3](chapter-01-03.md) мы разобрали, когда выбирать Spark: большие объёмы данных, итеративная или сложная логика, интеграция с HDFS, объектными хранилищами и DWH. В этом разделе рассмотрим **языки программирования и API**, доступные в Spark: Scala, Python (PySpark), Java и R. Вы узнаете, чем они отличаются с точки зрения производительности, удобства и области применения, и почему в этой книге основной фокус — **PySpark**. Следующая глава ([§2.1](chapter-02-01.md)) начнёт разбор архитектуры Spark: драйвер, исполнители и выполнение на кластере.

---

## 1.4.1. Scala — родной язык Spark

**Apache Spark** написан на **Scala** и изначально проектировался для JVM. Scala остаётся **родным** (first-class) языком для Spark: движок и все API реализованы на Scala, новые возможности чаще всего появляются сначала в Scala-API, документация и примеры на Scala, как правило, наиболее полные.

Особенности использования Spark на Scala:

- **Производительность:** код выполняется в той же JVM, что и ядро Spark; нет накладных расходов на межъязыковой вызов или сериализацию данных между процессами. Для тяжёлых джоб с большим числом мелких операций Scala часто даёт меньшую задержку и более предсказуемое потребление памяти.
- **Dataset API с типизацией:** в Scala доступен **Dataset[T]** — типизированная обёртка над DataFrame, позволяющая работать с объектами домена (например, `Dataset[User]`) с проверкой типов на этапе компиляции. Ошибки неверного типа или обращения к несуществующему полю обнаруживаются до запуска на кластере.
- **Экосистема JVM:** прямой доступ к библиотекам Java и Scala (Hadoop, Kafka, Cassandra, коннекторы к БД) без дополнительных мостов. Удобно, когда пайплайн уже живёт в JVM-мире (например, приложения на Java/Scala, YARN, Kerberos).

Недостаток Scala для части команд — более высокий порог входа: синтаксис и система типов сложнее, чем у Python; для аналитиков и специалистов по данным, привыкших к Python и SQL, PySpark часто оказывается практичнее. См. [Глоссарий](glossary.md).

## 1.4.2. Python и PySpark

**PySpark** — официальный API Spark для **Python**. Код на Python вызывает классы и методы, которые под капотом общаются с JVM через **Py4J**: команды сериализуются, передаются в JVM, там выполняются реальные вычисления на кластере, результаты возвращаются обратно в Python. Данные между узлами кластера обрабатываются в JVM; в Python оказываются только те данные, которые вы явно запрашиваете (например, через `.collect()` или `.toPandas()`).

Плюсы PySpark:

- **Доступность:** Python — один из основных языков в аналитике данных и машинном обучении; многие специалисты уже владеют им. Один язык и для локального анализа (Pandas, NumPy), и для распределённой обработки (PySpark) снижает порог входа и упрощает поддержку.
- **Единый API:** DataFrame в PySpark по смыслу и по именам методов близок к Pandas (`.select()`, `.filter()`, `.groupBy()`, `.withColumn()` и т.д.). Опыт работы с таблицами в Python переносится на Spark; разница в основном в том, что вычисления выполняются распределённо и лениво.
- **Интеграция с экосистемой Python:** Jupyter, визуализация (Matplotlib, Seaborn), библиотеки ML (Scikit-learn, при необходимости обмен через `.toPandas()` для малых выборок), скрипты и пайплайны (Airflow, Prefect) — всё на одном языке.
- **Быстрая разработка и отладка:** интерактивная работа в оболочке `pyspark` или в Jupyter; можно по шагам загружать данные, смотреть схему, делать срезы и только потом собирать продакшен-скрипт.

Ограничения:

- **Накладные расходы Py4J:** каждый вызов из Python в JVM имеет стоимость; при очень мелкозернистых операциях в цикле (например, вызов Python-функции для каждой строки через `udf`) производительность может быть заметно ниже, чем у эквивалентного кода на Scala. Для типичных пайплайнов на DataFrame (чтение, фильтр, join, агрегация, запись) разница часто приемлема, так как основная работа выполняется в JVM.
- **Типизация:** в Python нет статической проверки типов DataFrame; опечатки в именах столбцов или неверные типы проявляются в runtime при выполнении на кластере.

В этой книге мы используем **PySpark** как основной API: установка и запуск (§5.1–5.2), работа с DataFrame (§5.3–5.4, главы 6–7), чтение и запись (§6.1, §6.4, глава 4), стриминг (глава 8). Концепции (RDD, DAG, трансформации и действия, партиции) излагаются в общем виде в части I и затем применяются в PySpark в части II. См. [Глоссарий](glossary.md).

## 1.4.3. Java и R

**Spark для Java** предоставляет тот же набор API (RDD, DataFrame, Dataset), что и Scala, но с синтаксисом Java. Использование оправдано, когда вся инфраструктура и команда завязаны на Java: единая кодовая база, общие библиотеки, деплой в те же JVM-контейнеры. Синтаксис Java более многословен, чем Scala (например, анонимные классы вместо лямбд в старых версиях); поддержка в документации и в сообществе слабее, чем для Scala и PySpark. Для новых проектов чаще выбирают Scala (если нужна JVM) или PySpark (если приоритет — доступность и экосистема Python).

**Spark для R (SparkR, sparklyr)** даёт доступ к Spark из среды R. Подходит командам, которые ведут аналитику в R и хотят перенести тяжёлые вычисления на кластер без переписывания логики на другой язык. API и документация по объёму уступают PySpark и Scala; при необходимости сложной кастомной логики (UDF, тонкая настройка) обычно обращаются к PySpark или Scala. В этой книге R не рассматривается.

## 1.4.4. Сравнение языков: когда что выбирать

| Критерий | Scala | PySpark (Python) | Java | R (SparkR/sparklyr) |
|----------|--------|------------------|------|----------------------|
| Производительность «сырого» кода | Выше (нативная JVM). | Ниже из-за Py4J; для DataFrame-пайплайнов часто достаточно. | Сопоставима со Scala. | Обычно ниже, меньше оптимизаций. |
| Порог входа | Выше (типы, синтаксис). | Ниже (знакомый многим Python). | Зависит от команды. | Ниже для R-пользователей. |
| Экосистема данных | JVM, Hadoop, Kafka. | Python: Pandas, Jupyter, ML-библиотеки. | JVM. | R-пакеты, визуализация. |
| Типизация (Dataset/схема) | Статическая (Dataset[T]). | Динамическая; ошибки в runtime. | Статическая. | Динамическая. |
| Документация и примеры | Очень хорошие. | Очень хорошие. | Хорошие. | Уже. |
| Фокус книги | Упоминается. | **Основной.** | Не рассматривается. | Не рассматривается. |

Рекомендация для выбора: если команда пишет на **Python** и основная задача — аналитика, ETL и витрины на Spark, **PySpark** — естественный выбор. Если нужна максимальная производительность и глубокая интеграция с JVM (например, общая кодовая база с другими сервисами на Scala/Java) — **Scala**. Java и R — по необходимости при уже сложившемся стеке.

## 1.4.5. Единообразие API между языками

Независимо от выбранного языка, **концепции и структура API** в Spark совпадают:

- **RDD:** `map`, `filter`, `reduceByKey`, `groupBy` и т.д. — те же операции; различается только синтаксис вызова (лямбды Scala/Java vs функции Python).
- **DataFrame / Spark SQL:** один и тот же набор операций (`.select()`, `.filter()`, `.groupBy()`, `.join()`), те же SQL-функции и типы данных. Запрос, написанный на PySpark, легко переписать на Scala и наоборот.
- **Structured Streaming:** модель «поток как бесконечная таблица», те же API для чтения источников и записи приёмников.

Поэтому изучение Spark на одном языке (в нашем случае PySpark) даёт переносимые знания: понимание RDD, DAG, трансформаций и действий, партиций и shuffle пригодится и при переходе на Scala или при чтении кода на другом языке.

---

## Ключевое

- **Scala** — родной язык Spark, нативная JVM, максимальная производительность и типобезопасный Dataset API; удобен при JVM-экосистеме и требовании к скорости.
- **PySpark (Python)** — основной фокус книги; доступность для аналитиков, сходство API с Pandas, интеграция с Jupyter и Python-библиотеками; накладные расходы Py4J для типичных DataFrame-пайплайнов обычно приемлемы.
- **Java** и **R** — поддерживаются для интеграции с существующим стеком; для новых проектов чаще выбирают Scala или PySpark.
- API (RDD, DataFrame, Spark SQL, Structured Streaming) единообразны по сути во всех языках; знания, полученные на PySpark, переносятся на другие языки.
