# §3.1 DataFrame

С этого раздела начинается глава о **Spark SQL и DataFrame API** — табличном представлении данных со схемой и едином API для выборки, фильтрации, группировки и соединений. ## 3.1.1. Табличная абстракция со схемой

**DataFrame** в Spark — это распределённая коллекция данных, организованная по **столбцам** с именами и типами. По смыслу это таблица: строки — записи, столбцы — атрибуты с фиксированными именами (например, `id`, `name`, `age`, `city`) и типами (integer, string, timestamp и т.д.). В отличие от RDD, где элемент может быть произвольным объектом, DataFrame всегда имеет **схему** (schema): движок знает типы столбцов и может оптимизировать хранение и выполнение (например, колоночное сжатие, отложение вычислений до физического плана). См. [Глоссарий](glossary.md).

Схему можно задать явно при создании DataFrame или вывести из источника (Parquet, JSON с опцией `inferSchema`). Просмотр схемы в PySpark: `df.printSchema()`. Схема позволяет ловить часть ошибок на этапе планирования (обращение к несуществующему столбцу, несовместимость типов при соединении) и даёт единую модель для Spark SQL: запросы SQL работают с теми же DataFrame и схемой. См. [§3.2](chapter-03-02.md), [§3.3](chapter-03-03.md).

## 3.1.2. Унифицированный API поверх RDD

DataFrame API реализован **поверх** того же движка выполнения, что и RDD: данные по-прежнему разбиты на партиции, выполняются стадии и задачи, действуют трансформации и действия. Разница — в уровне абстракции:

- **RDD** — произвольные объекты (строки, кортежи, пользовательские классы); операции задаются функциями (map, filter с лямбдами). Планировщик видит только граф RDD и зависимости между партициями; глубокой оптимизации запроса (перестановка предикатов, выбор стратегии join) нет.
- **DataFrame** — таблица со схемой; операции задаются в терминах столбцов и выражений (`select("name", "age")`, `filter(col("age") > 18)`). Планировщик получает **логический план** запроса (дерево операторов: Project, Filter, Join, Aggregate и т.д.) и может применять правила оптимизации до генерации физического плана (байткод для исполнителей).

При необходимости из DataFrame можно получить RDD через `.rdd` (например, для кастомной поэлементной логики); обратно — создать DataFrame из RDD с заданной схемой. В повседневной работе с данными в Spark предпочтительнее DataFrame (и Spark SQL): меньше кода, автоматическая оптимизация, привычная табличная семантика. См. [§2.2](chapter-02-02.md), [§5.3](chapter-05-03.md).

## 3.1.3. Оптимизация через Catalyst

**Catalyst** — модуль оптимизации запросов в Spark SQL. Он работает с **логическим планом** (логический план — это представление запроса в виде дерева операторов: чтение таблицы, проекция столбцов, фильтр, соединение, агрегация и т.д.). Этапы работы Catalyst:

1. **Анализ** — привязка к схеме и каталогу: разрешение имён столбцов и таблиц, вывод типов выражений.
2. **Логическая оптимизация** — применение правил к логическому плану: постоянное сведение (constant folding), проталкивание предикатов (push down: перенос фильтров ближе к источнику данных), устранение лишних проекций, упрощение выражений. Цель — уменьшить объём данных на следующих шагах и упростить план.
3. **Планирование физического плана** — выбор конкретных физических операторов (какой join: sort-merge, broadcast hash join и т.д.), числа партиций, стратегии чтения. Генерируется набор кандидатов; выбирается план с наименьшей оценкой стоимости (cost-based optimization, где реализовано).
4. **Генерация кода** — для критичных участков возможно создание байткода (whole-stage code generation), чтобы уменьшить накладные расходы интерпретации.

В результате один и тот же запрос, написанный через DataFrame API или через SQL, после оптимизации может выполняться быстрее, чем наивная цепочка RDD-операций, за счёт проталкивания фильтров, выбора стратегии join и уменьшения лишних проходов по данным. Пользователь не обязан знать детали Catalyst; достаточно понимать, что DataFrame/SQL дают движку возможность «видеть» структуру запроса и оптимизировать его. См. [Глоссарий](glossary.md).

## 3.1.4. Неизменяемость и ленивое выполнение

Как и RDD, DataFrame **неизменяем**: операция `select`, `filter`, `withColumn` и т.д. возвращает **новый** DataFrame, не изменяя исходный. Цепочка вызовов строится в виде логического плана на драйвере; данные не обрабатываются до вызова **действия** (count, show, write, collect и т.д.). То есть для DataFrame действует то же **ленивое выполнение**: трансформации лишь расширяют план; при действии Catalyst оптимизирует план, он превращается в физический план и выполняется на кластере. См. [§2.2](chapter-02-02.md), [§2.4](chapter-02-04.md), [Глоссарий](glossary.md).

## 3.1.5. Основные операции API (обзор)

Типичные операции DataFrame (подробно в главах 6–7 для PySpark):

| Категория | Примеры | Описание |
|-----------|---------|----------|
| Выборка столбцов | `select`, `selectExpr` | Проекция: какие столбцы оставить, можно с выражениями. |
| Фильтрация | `filter`, `where` | Оставить строки, удовлетворяющие условию. |
| Добавление/замена столбца | `withColumn`, `withColumnRenamed` | Новый столбец или переименование. |
| Удаление столбца | `drop` | Убрать один или несколько столбцов. |
| Агрегация | `groupBy`, `agg` | Группировка по ключу и агрегатные функции (sum, count, avg и т.д.). |
| Соединение | `join` | Соединение двух DataFrame по условию (inner, left, right, full). |
| Сортировка | `orderBy`, `sort` | Упорядочивание строк. |
| Уникальность | `distinct`, `dropDuplicates` | Удаление дубликатов. |

Все эти методы возвращают новый DataFrame (трансформации); выполнение происходит при вызове действия. В [§3.2](chapter-03-02.md) мы разберём способы **создания** DataFrame; в [§3.3](chapter-03-03.md) — выполнение запросов через **Spark SQL**. См. [Глоссарий](glossary.md).

## 3.1.6. Связь со Spark SQL

DataFrame и **Spark SQL** используют один и тот же движок и одну схему данных. DataFrame можно зарегистрировать как **временную таблицу** (или представление) и обращаться к нему из SQL: `spark.sql("SELECT name, age FROM my_table WHERE age > 18")` возвращает DataFrame. И наоборот: результат SQL-запроса — DataFrame, к которому можно применять методы API. Таким образом, можно комбинировать SQL и API в одном приложении: сложные запросы писать на SQL, а конвейер сборки данных — на DataFrame API, или наоборот. Единая абстракция и единый оптимизатор (Catalyst) для обоих способов. См. [§3.3](chapter-03-03.md).

## Ключевое

- **DataFrame** — табличная абстракция в Spark со **схемой** (имена и типы столбцов); данные распределены по партициям, выполнение — те же стадии и задачи, что и у RDD.
- DataFrame API — **унифицированный** слой поверх движка: операции в терминах столбцов и выражений дают планировщику возможность строить логический план и оптимизировать его.
- **Catalyst** — оптимизатор запросов: анализ и привязка к схеме, логическая оптимизация (проталкивание предикатов, упрощение), выбор физического плана и при необходимости генерация кода.
- DataFrame **неизменяем** и выполняется **лениво**: трансформации возвращают новый DataFrame и расширяют план; выполнение — при вызове действия.
- Основные операции: select, filter, withColumn, groupBy/agg, join, orderBy, distinct; детали — в главах 6–7. DataFrame и Spark SQL используют общий движок и схему.

В [§3.2](chapter-03-02.md) мы разберём создание DataFrame: из RDD с заданной схемой, из источников через `spark.read` и из коллекций через `SparkSession.createDataFrame`.
