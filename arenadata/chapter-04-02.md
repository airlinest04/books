# §4.2 Мониторинг запросов в реальном времени

В [§4.1](chapter-04-01.md) мы рассмотрели обзор ADB Control и основные разделы веб-интерфейса. В этом разделе — **мониторинг запросов в реальном времени**: просмотр активных запросов на вкладке Commands (Online), детали команды (время выполнения, оценка прогресса), **планы выполнения** (дерево плана, прогресс по узлам, текст EXPLAIN), а также связь с транзакциями и **блокировками** (ожидание ресурсов, отмена транзакции для разблокировки). Материал опирается на [документацию по мониторингу команд](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/commands.html) и [мониторингу транзакций](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/transactions.html). Управление сессиями и завершение зависших запросов — в [§4.4](chapter-04-04.md). См. [Глоссарий](glossary.md).

---

## 4.2.1. Просмотр активных запросов (Commands → Queries → Online)

Страница **Monitoring → Commands → Queries → Online** отображает команды, которые выполняются или ожидают выполнения в текущий момент. По [документации по мониторингу команд](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/commands.html):

**Статусы на вкладке Online:**
- **Queued** — по команде ещё не получена информация о фактическом начале выполнения.
- **Running** — команда выполняется.
- **Cancelling** — выполняется отмена команды (в рамках отмены или прерывания транзакции).

В верхней части вкладки выводится **Current count** — общее число команд в этих статусах по всем кластерам, подключённым к ADB Control.

**Колонки таблицы:** Command ID (уникальный идентификатор), Command text (начало текста запроса; полный текст — при наведении или в деталях команды), **SQL ID** (общий для запросов с одинаковой структурой), Username, **Status**, Database, Resource group, Cluster, **Planner** (GPORCA / Fallbacked / Legacy), **Submitted** (дата и время отправки), Tags, **Run time** (время выполнения в формате ч:мин:с). Через **Customize table** можно добавить столбцы с метриками (CPU, RAM и др.). Фильтры: по **Cluster** и базам данных (по умолчанию — кластер, отмеченный как default), а также по столбцам таблицы (иконка в заголовке столбца); для сброса фильтров — **Reset**.

**Условие отображения:** по умолчанию в ADB Control фиксируются запросы с длительностью **более 5 секунд**. Вложенные запросы (в рамках функций, SPI и т.д.) по умолчанию не показываются; при необходимости включаются GUC `adcc.monitor_inner_queries` и `adcc.monitor_utility_inner_queries` в настройках кластера (Configuration → Clusters → настройки кластера → GUC).

## 4.2.2. Время выполнения и детали команды

При клике по **Command ID** открывается страница с деталями команды. В заголовке отображаются: идентификатор команды, статус, порядковый номер в ADB Control, **Transaction ID** (ссылка на детали транзакции), **Run time** — время выполнения на текущий момент (обновляется для выполняющихся команд).

**Секция Overview:** базовая информация о команде; **Run time** — длительность; **Est. progress** — оценка прогресса в процентах от прогнозируемого времени (рассчитывается по стоимости узлов плана и фактически извлечённым кортежам: отношение прогресса по узлам к общей оценке стоимости). Для команды, завершившейся с ошибкой (статус Error), под таблицей в Overview выводится текст ошибки.

**Секция Performance:** метрики потребления ресурсов — в среднем по кластеру (с показателями skew) и по каждому сегменту: CPU (%), RAM, Read/Write (per sec), Virtual memory, Spill size и Spill files number. Метрики на сегментах запрашиваются агентами только для команд с длительностью **более 15 секунд**; для более коротких команд секция Performance может быть пустой. На вкладке Online значения метрик соответствуют текущему моменту; для завершённых команд (History) — моменту завершения.

**Секция Command text:** полный текст запроса с возможностью копирования.

## 4.2.3. Планы выполнения (Plan & progress, Text, Relations)

Под секцией Command text расположены вкладки с **планом выполнения** запроса. По [документации](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/commands.html):

**Plan & progress** — графическое представление плана в виде дерева. Выполнение идёт снизу вверх (от дочерних узлов к корневому). В каждом узле отображается тип операции и:
- для выполняющегося запроса: фактическое число извлечённых кортежей на текущий момент, фактическое время выполнения слайса;
- для завершённого: общее время выполнения узла, число извлечённых кортежей, доля времени узла в общем времени запроса (%).

В правом верхнем углу узла — иконка статуса: выполняется, завершён, ошибка слайса (с версии 4.10.3), недостижимый узел. Узлы одного слайса выделены одним цветом и имеют один статус.

При клике на узел в правой панели отображаются: **Cost**, **Schema**, **Relation**, **Row skew**, **Est.tuples**, **Actual tuples**, **Prediction accuracy** (отношение фактических кортежей к прогнозу; >100% означает, что планировщик недооценил объём), **Operation keys** (Hash Key, Join Filter и т.д.), **Execution time**. Это позволяет находить «узкие» узлы плана и перекосы по сегментам.

**Text** — текстовое представление плана (результат EXPLAIN), с возможностью копирования.

**Relations** — список отношений (таблиц и т.п.), используемых в запросе, с указанием схемы. При наличии прав можно перейти к деталям аудита обращений к отношению.

## 4.2.4. Транзакции и блокировки

Одна команда входит в состав одной транзакции. На странице деталей команды по **Transaction ID** можно перейти к **деталям транзакции**. Вкладка **Monitoring → Transactions → Online** показывает все активные транзакции (статус Active); в деталях транзакции — список **Commands** внутри неё, метрики Performance, а также кнопки **Cancel** и **Terminate** для отмены выполняющейся транзакции. По [документации по транзакциям](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/transactions.html):

- **Cancel** — вызов `pg_cancel_backend`: отмена текущей команды/транзакции в процессе, сессия остаётся.
- **Terminate** — вызов `pg_terminate_backend`: завершение процесса, сессия разрывается.

После успешной отмены транзакция переходит в статус Aborted, входящие в неё команды — в Cancelled. Отмена доступна только для активных транзакций и при наличии у пользователя ADB Control соответствующих прав (Kill self queries / Kill some queries / Kill all queries).

**Блокировки (ожидание ресурсов):** если запрос «висит» из‑за ожидания блокировки (lock), вызванной другой транзакцией, в ADB Control это проявляется как длительно выполняющаяся команда или транзакция (большое Run time, статус Running или Queued). Прямого отдельного экрана «блокировки» в веб-интерфейсе ADB Control в документации не описано; идентификация блокирующей и ожидающей сторон выполняется по списку активных транзакций и команд (кто долго выполняется, какие объекты затронуты в Relations/плане). Для разблокировки можно отменить блокирующую транзакцию (Transactions → детали транзакции → Cancel или Terminate). Детальный анализ блокировок (какой процесс кого ждёт, типы блокировок) выполняется средствами СУБД — системными представлениями `pg_locks`, `pg_stat_activity` (в том числе wait_event_type, wait_event) и др. на координаторе ADB; при необходимости запросы к ним выполняют через psql или иной клиент. Прерывание «зависших» сессий целиком — через Monitoring → Sessions (см. [§4.4](chapter-04-04.md)).

## 4.2.5. История запросов и фильтры (Queries → History)

Вкладка **Monitoring → Commands → Queries → History** показывает завершённые команды со статусами: **Done** (успешно), **Cancelled**, **Error**, **Unknown** (итог не получен, например по таймауту). Поля таблицы те же, что на Online, плюс **Ended** — дата и время завершения. Доступны фильтры **Relation** (имя отношения, используемого в запросе) и **Schema** (схема отношения); искомое значение вводится полностью. Детали команды (Overview, Performance, план, текст) для записей из History открываются так же по клику на Command ID; метрики Performance выводятся на момент завершения команды.

---

## Ключевое

- **Активные запросы:** Monitoring → Commands → Queries → Online; статусы Queued, Running, Cancelling; колонки Command ID, Run time, Status, Planner, фильтры по кластеру и столбцам. По умолчанию отображаются запросы длительностью более 5 секунд.
- **Время выполнения и прогресс:** в деталях команды — Run time в заголовке и в Overview; Est. progress (оценка прогресса в %); при ошибке — текст в Overview. Performance (метрики по сегментам) — для команд длительностью более 15 секунд.
- **Планы выполнения:** Plan & progress — дерево плана, статусы узлов и слайсов, при клике на узел — Cost, Actual tuples, Prediction accuracy, Row skew, Execution time; Text — текст EXPLAIN; Relations — список отношений.
- **Транзакции и блокировки:** из деталей команды переход по Transaction ID к транзакции; Transactions → Online — список активных транзакций; Cancel/Terminate для отмены. Ожидание блокировки видно по длительному Run time; разблокировка — отмена блокирующей транзакции; детальный разбор — через pg_locks, pg_stat_activity в СУБД.

В [§4.3](chapter-04-03.md) мы разберём метрики кластера, алерты при сбоях и превышении порогов и интеграцию с внешним мониторингом.
