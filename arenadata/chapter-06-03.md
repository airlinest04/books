# §6.3 Восстановление

В [§6.2](chapter-06-02.md) мы разобрали полный, дифференциальный и инкрементальный бэкапы, расписание и хранение в ADBM. В этом разделе — **восстановление из бэкапа** (действие Common restore), **выборочное восстановление** таблиц (Partial restore), а также целевые показатели **RTO** и **RPO**, на которые влияет стратегия бэкапов и восстановления. Материал опирается на [документацию по запуску действий ADBM](https://docs.arenadata.io/ru/ADB/current/tutorials/adbm/basic/run-actions.html). См. [Глоссарий](glossary.md).

---

## 6.3.1. Восстановление из бэкапа (Common restore)

**Common restore** — действие ADBM, позволяющее восстановить базы данных кластера ADB **на момент одной из существующих restore points**. Это единственное действие, которое можно применить и к **запущенному**, и к **остановленному** кластеру; логика выполнения зависит от статуса кластера.

**Кластер запущен (Up):** перед восстановлением выполняются проверки: сверка **топологии** (сохранённой в бэкапе и текущей из `gp_segment_configuration`) и проверка **метаданных** бэкапа (аналогично действию Verify). При успешном прохождении проверок кластер автоматически останавливается и выполняется восстановление. При ошибке восстановления доступна кнопка **Retry** — повторный запуск последнего процесса восстановления без повторных проверок; для полного запуска с проверками — **New restore**.

**Кластер остановлен (Down):** валидация пропускается; восстановление можно запустить напрямую. Такой способ рекомендуется только при фатальных сбоях, когда кластер не запускается.

**Параметры действия Common restore:** выбор **restore point** (с фильтром по времени Time period), список **Databases** для восстановления, **Processes** (максимум процессов на один сегмент), **Restore mirrors** — восстанавливать ли зеркала и standby: No / Parallel / Sequential. Флаги: **Delta** (использование checksum при восстановлении из Incr/Diff; не влияет на Full), **Force** (полная перезапись путей к данным и tablespace в PostgreSQL), **Verify** (проверка данных бэкапа перед восстановлением). По документации: при Delta без Force перезаписываются только файлы, изменившиеся после бэкапа (по checksum); при Delta и Force проверка по дате и размеру — быстрее, но с меньшими гарантиями целостности.

После успешного выполнения выбранные базы данных возвращаются в состояние на момент указанной restore point; создаётся новый **timeline** (см. [§2.3](chapter-02-03.md)).

## 6.3.2. Выборочное восстановление (Partial restore)

**Partial restore** (доступно начиная с ADBM 2.2.2) позволяет восстановить **не весь кластер, а выбранные таблицы** на момент одной из restore points. Удобно для исправления ошибочно изменённых или удалённых таблиц без полного отката БД.

**Параметры:** выбор **restore point** (и при необходимости Time period), **Source database** (исходная БД), **Target database** (целевая БД; если не указана — восстановление в исходную БД), **Table suffix** (суффикс к именам восстановленных таблиц, до 32 символов; если не задан — используются исходные имена, и в целевой БД не должно быть таблиц с такими именами), **Table name masks** — маски имён таблиц в формате `schema/table` (допускается wildcard `*`; при отсутствии `/` подразумевается схема `public`), **Processes** (число параллельных процессов на хост, 1–100; рекомендуется не больше числа primary-сегментов на хосте), флаг **Verify**.

**Важно:** если Table suffix не задан и таблица с таким именем уже есть в целевой БД, для этой таблицы фиксируется ошибка `Couldn't create table` и её восстановление не выполняется (остальные продолжаются). Длина имени отношения в ADB ограничена 64 символами; при использовании суффикса суммарная длина не должна превышать лимит. Если ни один шаблон в Table name masks не находит таблиц (например, несуществующая схема), действие завершается с ошибкой `No tables were found by provided filter`; если хотя бы один шаблон валиден — восстанавливаются соответствующие таблицы, неверные маски игнорируются.

Результат отображается на вкладке Restores; при ошибке восстановления одной из таблиц родительское действие Table restore переходит в статус Warning, детали по таблицам — во вкладке Tables выбранного восстановления.

## 6.3.3. RTO и RPO

**RPO** (Recovery Point Objective, целевая точка восстановления) — максимально допустимая **потеря данных** при сбое: до какого момента в прошлом мы согласны «откатить» данные. Измеряется во времени (например, «не более 4 часов потери данных»). В контексте ADBM RPO определяется частотой и типом бэкапов и созданием restore points: чем чаще выполняются инкрементальные бэкапы и создаются restore points, тем меньше интервал между «сохранёнными» моментами и тем меньше потенциальная потеря данных. Архивация WAL и восстановление до именованной restore point обеспечивают восстановление на точный момент, для которого создана точка, а не только на момент съёма бэкапа.

**RTO** (Recovery Time Objective, целевое время восстановления) — максимально допустимое **время простоя** (downtime): за какой период система должна вернуться к работе после сбоя. Зависит от времени выполнения восстановления: загрузка полного бэкапа, при необходимости цепочки diff/incr и воспроизведение WAL до выбранной restore point, запуск кластера. Чем больше объём данных и чем длиннее цепочка бэкапов, тем дольше восстановление; параллелизм (Processes, Restore mirrors) и использование Delta для перезаписи только изменённых файлов могут сократить время.

При планировании стратегии бэкапов (см. [§6.4](chapter-06-04.md)) целевые RPO и RTO задают требования к частоте полных и инкрементальных бэкапов, к расписанию создания restore points и к выделению ресурсов хранилища и узлов для быстрого восстановления.

## Ключевое

- **Common restore:** восстановление БД на момент выбранной restore point; применимо к запущенному и остановленному кластеру; при Up — проверки топологии и метаданных, затем остановка и восстановление; Retry без проверок, New restore — с проверками; параметры: Databases, Restore mirrors, Delta, Force, Verify.
- **Partial restore:** восстановление выбранных таблиц на момент restore point; Source/Target database, Table suffix, маски имён (schema/table); при совпадении имён без суффикса — ошибка для таблицы; ограничение длины имени 64 символа.
- **RPO:** максимально допустимая потеря данных; задаётся частотой бэкапов и restore points и архивацией WAL.
- **RTO:** максимально допустимое время простоя; зависит от времени восстановления (объём данных, цепочка бэкапов, параллелизм, Delta).

В [§6.4](chapter-06-04.md) мы рассмотрим стратегии бэкапа для DWH: частоту съёма, разделение по слоям (Raw, Staging, витрины), хранение и практические рекомендации.
