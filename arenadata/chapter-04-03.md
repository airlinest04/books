# §4.3 Метрики и алерты

В [§4.2](chapter-04-02.md) мы разобрали мониторинг запросов в реальном времени: активные запросы, планы выполнения, время выполнения и связь с транзакциями. В этом разделе — **метрики кластера** в ADB Control (источники метрик, Dashboard, настройки сбора), **хранение и очистка** метрик, **индикация сбоев и превышения порогов** (статусы команд и транзакций, использование выгруженных данных), а также **интеграция с внешним мониторингом**: выгрузка метрик во внешнюю БД (Metrics offload) и при необходимости развёртывание стека Prometheus/Grafana в контуре кластера ADB. Материал опирается на [документацию по Dashboard](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/chart.html), [общие настройки ADB Control](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/config/general.html) и [политики задач](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/config/job-policy.html). Управление сессиями и завершение запросов — в [§4.4](chapter-04-04.md). См. [Глоссарий](glossary.md).

## 4.3.1. Метрики кластера в ADB Control

**Источники метрик:** ADB Control собирает метрики с хостов кластеров ADB через агентов (по одному агенту на хост). Агенты получают данные с координатора и сегментов и передают их в Backend; метрики по командам и транзакциям записываются в Query DB и Metrics DB. На уровне **отдельной команды или транзакции** метрики отображаются в секции **Performance** на странице деталей (CPU, RAM, Virtual memory, Read/Write, Spill files, skew по сегментам); на уровне **кластера за период** — на странице **Dashboard**.

**Dashboard (Monitoring → Dashboard):** по [документации по Dashboard](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/monitoring/chart.html) строятся графики по следующим метрикам:

| Вкладка | Метрика | Единица |
|---------|---------|---------|
| Commands | Число SQL-команд в статусе Running | шт. |
| Transactions | Число транзакций в статусе Active | шт. |
| CPU | Общий объём потребляемого CPU по кластеру | % |
| Memory | Общий объём выделенной виртуальной памяти | байты |
| Read | Общий объём прочитанных данных | байты |
| Write | Общий объём записанных данных | байты |

Параметры построения: **Cluster** (кластер для графиков), **Frequency** (частота обновления), **Time period** (временной диапазон; можно задать границы или выбрать пресет). **View**: Summary — сводный график по кластеру; Hosts — отдельный график по каждому хосту. Под графиками выводятся сводные значения за период: **Current**, **Maximum**, **Minimum**, **Average**; при наведении на график — значение в выбранной временной точке.

**Настройки сбора метрик:** вкладка **Configuration → General → Metrics** (доступна с версии ADB Control 4.12.0) задаёт режим сбора метрик spill-файлов: **Cluster** (только по кластеру в целом) или **Cluster and segment** (по кластеру и по каждому сегменту). При выборе Cluster and segment в секции Performance деталей команды заполняются поля **Spill size** и **Spill files number** по каждому сегменту. Остальные метрики (CPU, RAM, Read/Write и т.д.) собираются по умолчанию; метрики на сегментах запрашиваются для команд и транзакций длительностью более 15 секунд.

## 4.3.2. Хранение метрик и автоматическая очистка

Метрики и данные о запросах, транзакциях, сессиях хранятся во внутренних БД ADB Control (Query DB, Metrics DB). Чтобы не исчерпывать дисковое пространство, включают **автоматическую очистку** старых данных. По [документации по Job policy](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/config/job-policy.html):

**Configuration → Job policy → Data cleanup:** переключатель **Data cleanup** включает задачу автоматического удаления метрик по истечении заданного срока. Параметры:

- **Expire duration** — максимальный срок хранения метрик (формат: число + единица: `ms`, `sec`, `min`, `hr`, `d`, `w`; например `5d`, `1w`). По истечении этого срока данные удаляются.
- **Data cleanup schedule** — расписание запуска задачи в формате cron (по умолчанию — раз в сутки).
- **Batch size** — максимальное количество строк в батче при обработке (по умолчанию 500).

Задача очистки по умолчанию включена; отключение не рекомендуется из‑за риска быстрого заполнения диска. Для долговременного хранения истории метрик настраивают **выгрузку во внешнюю БД** (Metrics offload, см. п. 4.3.4).

## 4.3.3. Индикация сбоев и превышение порогов

В веб-интерфейсе ADB Control **нет отдельной страницы «Алерты»** с настраиваемыми порогами и уведомлениями в том виде, как в некоторых системах мониторинга (например, алерты по правилам в Grafana или Prometheus Alertmanager). Индикация проблем осуществляется следующим образом.

**Статусы команд и транзакций:** на вкладках **Commands → Queries** (Online/History) и **Transactions** (Online/History) отображаются статусы: для команд — **Error**, **Cancelled**, **Unknown**; для транзакций — **Aborted**, **Unknown**. Команды со статусом Error в деталях содержат текст ошибки в секции Overview. Долго выполняющиеся запросы (большое Run time) и транзакции видны в Online; их можно отменить (Cancel/Terminate) или проанализировать по плану и метрикам. Таким образом, «алертинг» по сбоям выполнения и «зависшим» запросам выполняется вручную через просмотр списков и деталей.

**Выгрузка метрик во внешнюю БД:** при включённом **Metrics offload** (см. п. 4.3.4) данные о запросах, транзакциях, ошибках (таблицы `query`, `query_error`, `transaction` и др.) попадают во внешнюю PostgreSQL или ADB. Во внешней БД можно строить отчёты, дашборды и **настраивать алерты** средствами этой БД или внешних инструментов (например, скрипты, периодические запросы, интеграция с системами оповещений). То есть пороговые алерты и уведомления при сбоях реализуются не в ADB Control, а в контуре внешней аналитики и мониторинга.

**Мониторинг при развёртывании стека в контуре ADB:** при установке сервиса мониторинга в кластере ADB (Prometheus, Grafana и др. по документации установки) сбор системных и прикладных метрик с хостов выполняется экспортерами; алерты настраиваются в Prometheus (Alertmanager) и/или в Grafana. Детали зависят от версии и состава бандла мониторинга; общая идея — интеграция с внешним мониторингом для пороговых и событийных алертов.

## 4.3.4. Интеграция с внешним мониторингом

**Выгрузка метрик ADB Control во внешнюю БД (Metrics offload).** По [документации по Job policy](https://docs.arenadata.io/ru/ADB/current/tutorials/adbc/config/job-policy.html) на вкладке **Configuration → Job policy → Metrics offload** настраивается периодическая выгрузка собранных ADB Control данных во **внешнюю базу** (PostgreSQL или Arenadata DB). Целевая БД не должна быть той же, по которой собираются метрики (чтобы не нагружать мониторируемый кластер и не засорять мониторинг запросами выгрузки). Требуется доступность БД с хоста ADB Control (сеть, pg_hba.conf при использовании PostgreSQL).

**Параметры:** переключатель **Metrics offload** в активное состояние; **JDBC URL** — строка подключения к внешней БД (например, `jdbc:postgresql://<хост>:5432/<база>`); **User** и **Password** для подключения. В секции Main parameters: **Export sessions** — выгрузка данных о сессиях (при необходимости включить мониторинг сессий в Configuration → General → Sessions); **Batch size**, **Interval** (глубина поиска выгружаемых данных в днях), **Delay** (таймаут поиска новых метрик); **Offload metrics job schedule** — расписание в формате cron. Для каких кластеров и баз выгружать метрики, задаётся в **Configuration → Clusters** → настройки кластера → секция выгрузки (Metric offload / export databases).

После успешной настройки во внешней БД создаётся схема **adcc** с таблицами: **cluster**, **query**, **query_error**, **transaction**, **cluster_query_metric** (метрики по командам: CPU, RAM, read/write, spill и т.д.), **session** (при включённом Export sessions), **audit_auth**, **audit_auth_adb**, **audit_operation**, **relation_statistic**. Эти таблицы позволяют строить отчёты, дашборды и алерты во внешних инструментах (SQL, BI, Grafana с подключением к PostgreSQL/ADB и т.д.).

**Мониторинг в контуре кластера ADB.** В документации по установке ADB описан вариант развёртывания **мониторинга** в том же контуре: добавление сервиса мониторинга (Monitoring), использование компонентов для сбора метрик с хостов (экспортеры), **Prometheus** для сбора и хранения метрик, **Grafana** для визуализации; при необходимости — Graphite. Метрики с хостов (системные, СУБД) поступают в Prometheus; в Grafana настраиваются дашборды и алерты. Таким образом, интеграция с внешним мониторингом достигается либо выгрузкой данных ADB Control во внешнюю БД (Metrics offload), либо развёртыванием полноценного стека Prometheus/Grafana рядом с кластером ADB с последующей настройкой алертов в этом стеке.

## Ключевое

- **Метрики кластера:** собираются агентами с хостов; Dashboard — графики Commands (Running), Transactions (Active), CPU, Memory, Read, Write за период; View Summary/Hosts; Configuration → General → Metrics — режим сбора spill (Cluster / Cluster and segment).
- **Хранение и очистка:** Job policy → Data cleanup — автоматическое удаление метрик по истечении Expire duration по расписанию; отключать не рекомендуется; для длительного хранения — Metrics offload.
- **Сбои и пороги:** в ADB Control нет отдельной страницы алертов; индикация по статусам команд/транзакций (Error, Cancelled, долгое Run time) и деталям; пороговые алерты — во внешней БД (по выгруженным данным) или в Prometheus/Grafana при развёрнутом мониторинге.
- **Интеграция:** Metrics offload — выгрузка метрик и аудита в PostgreSQL/ADB (схема adcc, таблицы query, transaction, cluster_query_metric и др.); выбор кластеров и БД для выгрузки — в Configuration → Clusters. При развёртывании мониторинга в контуре ADB — Prometheus, Grafana, экспортеры на хостах.

В [§4.4](chapter-04-04.md) мы разберём управление сессиями и запросами: завершение зависших запросов и сессий, управление очередью и ограничение ресурсов (ресурсные группы).
