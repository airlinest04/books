# §7.2 Хранение ссылок без копирования данных

В [§7.1](chapter-07-01.md) мы разобрали идею реестра: MDM хранит только идентификаторы и маппинг, данные остаются в источниках. В этом разделе рассмотрим **структуру хранения** — таблицу маппинга и каталог golden_id — и **разрешение** (resolution): как по golden_id получить source_id для запроса к источнику и как по source_id из транзакции получить golden_id. В [§7.3](chapter-07-03.md) разберём плюсы и минусы реестра; в [§7.4](chapter-07-04.md) — когда его использовать.

---

## 7.2.1. Таблица маппинга

Основная структура реестра — **таблица маппинга** `(source_system, source_id) → golden_id`:

```sql
CREATE TABLE registry_counterparty_mapping (
    source_system   VARCHAR(50)   NOT NULL,
    source_id       VARCHAR(100)  NOT NULL,
    golden_id       BIGINT        NOT NULL,
    entity_type     VARCHAR(50)   DEFAULT 'counterparty',  -- сущность: customer, product, ...
    created_at      TIMESTAMP     DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (source_system, source_id),
    UNIQUE (golden_id, source_system, source_id)  -- или отдельный индекс по golden_id
);
```

Одна строка — связь «идентификатор в источнике» с «единым эталонным идентификатором». Несколько source_id из разных (или одного) источников могут маппиться на один golden_id — это дубликаты, объединённые в одну сущность. См. [§5.3](chapter-05-03.md), [§4.3](chapter-04-03.md).

---

## 7.2.2. Каталог golden_id (опционально)

В реестре нет таблицы с атрибутами; есть только маппинг. Список golden_id можно получить как `SELECT DISTINCT golden_id FROM registry_counterparty_mapping`. Если нужны метаданные (дата создания, статус, тип сущности), их хранят в отдельной таблице:

```sql
CREATE TABLE registry_entity (
    golden_id       BIGINT PRIMARY KEY,
    entity_type     VARCHAR(50),
    status          VARCHAR(20) DEFAULT 'active',
    created_at      TIMESTAMP,
    updated_at      TIMESTAMP
);
```

Таблица `registry_entity` не содержит атрибутов сущности (имя, адрес) — только служебные поля. Атрибуты разрешаются из источников по маппингу. См. [§7.1](chapter-07-01.md).

---

## 7.2.3. Разрешение source_id → golden_id

**Разрешение «вперёд»** (source → golden): по идентификатору из источника получить golden_id.

Запрос: «транзакция из ERP с counterparty_code=C-4421 — какому golden_id она соответствует?»

```sql
SELECT golden_id
FROM registry_counterparty_mapping
WHERE source_system = 'ERP' AND source_id = 'C-4421';
```

Результат — один golden_id (или NULL, если запись ещё не сопоставлена). Использование: при загрузке фактов из ERP джойн транзакций с маппингом даёт golden_id; в факт пишется golden_id. См. [§5.3](chapter-05-03.md), [§10.2](chapter-10-02.md).

---

## 7.2.4. Разрешение golden_id → source_id (для запроса данных)

**Разрешение «назад»** (golden → source): по golden_id получить source_id для запроса атрибутов из источника.

Запрос: «нужны атрибуты клиента с golden_id=5001 — откуда их взять?»

```sql
SELECT source_system, source_id
FROM registry_counterparty_mapping
WHERE golden_id = 5001;
```

Результат — одна или несколько пар (source_system, source_id). Дальнейшие действия:

1. **Один источник:** запросить API или БД источника по source_id и получить наименование, адрес и т.д.
2. **Несколько источников:** выбрать «предпочтительный» источник по правилам (приоритет системы, полнота данных) и запросить его; или запросить несколько и слить по правилам (но это уже ближе к консолидации).
3. **Источник недоступен:** данные получить невозможно; реестр не хранит резервной копии. См. [§7.3](chapter-07-03.md).

---

## 7.2.5. Загрузка фактов при реестре

При загрузке транзакций (продажи, платежи) из источника факт содержит source_id (customer_id, counterparty_code). Чтобы факт ссылался на эталон, нужен golden_id:

```sql
-- Загрузка факта платежей из ERP
INSERT INTO fact_payments (payment_id, counterparty_sk, amount, ...)
SELECT 
    p.payment_id,
    m.golden_id,   -- маппинг source → golden
    p.amount,
    ...
FROM staging_payments_erp p
LEFT JOIN registry_counterparty_mapping m 
    ON m.source_system = 'ERP' AND m.source_id = p.counterparty_code
WHERE m.golden_id IS NOT NULL;  -- или обработать отсутствие маппинга отдельно
```

Факт хранит golden_id (или суррогатный ключ измерения, построенный на golden_id). Атрибуты контрагента для отчёта при необходимости джойнят из источника по golden_id → source_id → запрос к источнику. На практике для витрин часто делают **кеш** или **материализованное представление**: периодически разрешают golden_id в атрибуты из выбранного источника и кладут в dim_counterparty для джойна с фактами. См. [§10.1](chapter-10-01.md).

---

## 7.2.6. Запись без маппинга (сироты)

Если в транзакции source_id отсутствует в маппинге (новая запись, ещё не сопоставленная, или ошибка), возможны варианты:

- **Пропустить** транзакцию при загрузке факта (потеря данных).
- **Записать с NULL** по golden_id или в отдельную «корзину» сирот; потом доразрешить при появлении маппинга. См. [§1.2](chapter-01-02.md) (сироты в DWH).
- **Создать золотую запись «на лету»** и маппинг — тогда реестр переходит в режим, близкий к консолидации для новых записей.

Выбор зависит от политики: допускаются ли факты без эталона, как обрабатывать отставание сопоставления.

---

## 7.2.7. Обновление маппинга

Маппинг обновляется при:

- **Сопоставлении дубликатов:** несколько source_id сливаются в один golden_id; добавляются строки маппинга для каждого source_id.
- **Слиянии двух золотых:** все source_id, маппившиеся на «побочную» золотую, переназначаются на «главную»; строка «побочной» золотой удаляется или помечается. См. [§5.3](chapter-05-03.md).
- **Новых записях из источников:** после сопоставления (или автоматического создания) добавляется маппинг source_id → golden_id.

Маппинг — критичная структура; ошибки в нём ломают связи фактов с эталонами. Изменения желательно версионировать или логировать. См. [§4.4](chapter-04-04.md).

---

## 7.2.8. Типичные ошибки

- **Дубликаты в маппинге:** один и тот же (source_system, source_id) не должен маппиться на разные golden_id; PRIMARY KEY это предотвращает.
- **Потерянные ссылки:** при слиянии золотых не обновить маппинг — часть source_id останется привязанной к несуществующему golden_id.
- **Забыть обработать отсутствие маппинга:** транзакция с неизвестным source_id — решение должно быть явным (пропуск, сирота, создание).
- **Считать реестр «бесплатным»:** разрешение golden_id → атрибуты требует запросов к источникам; при высокой нагрузке нужен кеш или материализация.

---

## Ключевое

- **Таблица маппинга:** (source_system, source_id) → golden_id; PRIMARY KEY (source_system, source_id).
- **Каталог golden_id:** опционально — отдельная таблица с метаданными (без атрибутов сущности).
- **Разрешение source_id → golden_id:** по маппингу; используется при загрузке фактов.
- **Разрешение golden_id → source_id:** по маппингу; для запроса атрибутов из источника.
- **Загрузка фактов:** джойн транзакции с маппингом; в факт пишется golden_id.
- **Сироты:** source_id без маппинга — политика (пропуск, корзина, создание на лету).
- **Обновление маппинга:** при сопоставлении дубликатов, слиянии золотых, новых записях.

В [§7.3](chapter-07-03.md) разберём плюсы и минусы реестра: когда выгодно хранить только ссылки и какие ограничения это накладывает.
