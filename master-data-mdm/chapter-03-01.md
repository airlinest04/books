# §3.1 Дубликаты и расхождения

В главах 1 и 2 мы определили эталонные данные и их сущности. Глава 3 посвящена **проблемам** эталонных данных. В этом разделе разберём **дубликаты и расхождения**: один и тот же объект (клиент, контрагент, продукт) представлен несколькими записями в разных системах; разные написания и форматы; отсутствие единого ключа. Понимание причин и последствий дубликатов — основа для проектирования дедупликации и золотой записи (глава 4–5). В [§3.2](chapter-03-02.md) рассмотрим множественность источников; в [§3.3](chapter-03-03.md) — несогласованность и конфликты.

---

## 3.1.1. Понятие дубликата

**Дубликат** — две или более записей, относящихся к одной и той же реальной сущности (одному клиенту, одной организации, одному продукту), но существующих как отдельные строки с разными идентификаторами или атрибутами. См. [Глоссарий](glossary.md).

Признаки дубликатов:

- **Один объект, несколько записей:** физически один клиент — несколько строк в базе.
- **Разные ID:** в CRM — customer_id=101, в ERP — counterparty_code=А-7742, в биллинге — payer_id=991; без маппинга это три «разных» клиента.
- **Разные или схожие атрибуты:** имя может совпадать частично («ООО Ромашка» и «Ромашка ООО») или отличаться из-за опечаток, разных форматов.

Дубликаты возникают при ручном вводе без проверки, загрузке из нескольких источников без сопоставления, миграциях и слияниях систем. Последствия: искажённые агрегаты (один клиент считается несколько раз), дублирование рассылок, сложность сверки и аналитики. См. [§5.1](chapter-05-01.md).

---

## 3.1.2. Один и тот же клиент в разных системах

Типичная ситуация: клиент «ООО Ромашка» присутствует в CRM (создан при первом обращении), в ERP (заведён при первом заказе), в биллинге (добавлен при выставлении счёта). В каждой системе свой ID и свой набор атрибутов; обновления (смена адреса, телефона) вносятся не везде одновременно. См. [§2.1](chapter-02-01.md).

Пример:

| Система | ID | Наименование | ИНН | Адрес |
|---------|-----|--------------|-----|-------|
| CRM | 1001 | ООО «Ромашка» | 7707123456 | Москва, ул. Ленина, 5 |
| ERP | C-4421 | Ромашка ООО | 7707123456 | Ленина 5, Москва |
| Биллинг | B-8892 | ООО Ромашка | 7707123456 | Москва, Ленина, 5 |

Это **три записи об одном контрагенте**. ИНН совпадает — можно сопоставить; наименование и адрес — в разных форматах. Без сопоставления при загрузке в DWH получим три «разных» контрагента; отчёт «топ-10 клиентов по выручке» может разнести одного и того же клиента на три строки или исказить ранжирование. См. [§1.3](chapter-01-03.md).

## 3.1.3. Разные написания

Даже одна и та же сущность может быть записана по-разному:

**Наименования организаций:**

- «ООО Ромашка» / «Ромашка ООО» / «Общество с ограниченной ответственностью „Ромашка“»
- Кавычки, пробелы, порядок слов, сокращения (ООО, ОАО, ЗАО)
- Опечатки: «Ромашка» / «Ромашкаа» / «Ромашкай»

**ФИО физических лиц:**

- «Иванов Иван Иванович» / «Иванов И. И.» / «Ivanov Ivan»
- Транслитерация: «Иванов» / «Ivanov»
- Смена фамилии (брак); разные документы — разные записи

**Адреса:**

- «ул. Ленина, д. 5» / «Ленина 5» / «Ленина, 5» / «улица Ленина, дом 5»
- Сокращения: ул., д., кв., корп.
- Разный порядок: город, улица, дом vs улица, дом, город

**Продукты:**

- «Масло сливочное 82,5%» / «Масло 82.5» / «Сливочное масло 82,5% 200г»
- Разные единицы, разный порядок атрибутов

Сопоставление по точному совпадению строк часто даёт ложноотрицательный результат (не находит дубликат); нужны нормализация, нечёткое сравнение (fuzzy matching) и правила. См. [§5.2](chapter-05-02.md).

## 3.1.4. Отсутствие единого ключа

Если в источниках нет **устойчивого идентификатора**, однозначно определяющего сущность (ИНН для юрлица, паспорт/СНИЛС для физлица, штрихкод для товара), сопоставление усложняется. См. [§2.1](chapter-02-01.md).

Проблемы:

- **Внутренние ID не согласованы:** каждая система генерирует свой ID; кросс-системного маппинга нет.
- **Бизнес-ключ не везде присутствует:** ИНН есть в ERP, но в CRM его не вводили; сопоставление по ИНН невозможно для части записей.
- **Нет надёжного ключа:** для физлица без паспортных данных в системе — только ФИО и телефон; дубликаты возможны (тёзки).

Решения:

- **Использовать регуляторные идентификаторы** (ИНН, ОГРН) где возможно; требовать их ввод при создании контрагента.
- **Строить маппинг** «source_system + source_id → golden_id» при первой загрузке и дедупликации; поддерживать при последующих загрузках.
- **Комбинировать атрибуты** для сопоставления, когда единого ключа нет: ФИО + дата рождения + адрес; наименование + ИНН; код + наименование продукта. См. [§5.1](chapter-05-01.md), [§7.2](chapter-07-02.md).

## 3.1.5. Последствия дубликатов

| Область | Последствие |
|---------|-------------|
| **Аналитика и отчётность** | Завышение числа клиентов/контрагентов; искажение агрегатов (выручка по «одному» клиенту разнесена на несколько); некорректные срезы и ранжирование |
| **Коммуникации** | Дублирование рассылок, писем, уведомлений одному и тому же лицу |
| **Операционные процессы** | Неверный выбор контрагента при создании сделки; ручная сверка и исправление |
| **Регуляторика** | Ошибки в отчётности (например, 115-ФЗ, KYC) при неполной картине по клиенту |
| **Доверие к данным** | Недоверие к отчётам; время на ручную проверку и согласование |

Устранение дубликатов — одна из главных целей MDM. См. [§1.3](chapter-01-03.md).

## 3.1.6. Расхождения в атрибутах

Даже когда дубликаты выявлены (записи относятся к одному объекту), **атрибуты могут расходиться**:

- В CRM адрес «ул. Ленина, 5», в ERP — «Ленина 5, офис 10». Какой считать верным?
- В одной системе телефон +7 (495) 123-45-67, в другой — 84951234567. Нормализация даёт совпадение, но при слиянии — какое значение сохранить?
- Дата обновления разная; в одной системе запись свежее.

Это уже проблема **несогласованности и конфликтов** — какой источник и какое значение считать приоритетным. Мы разберём это в [§3.3](chapter-03-03.md) и в главе 4 (выбор «лучшего» значения при слиянии). Здесь важно: выявление дубликатов — первый шаг; следующий — слияние с правилами разрешения расхождений. См. [§4.2](chapter-04-02.md), [§4.3](chapter-04-03.md).

---

## 3.1.7. Пример: выявление дубликатов по ИНН

Простейший случай — сопоставление по ИНН для юрлиц. Если ИНН заполнен и корректен, совпадение ИНН с высокой вероятностью означает одного контрагента.

```sql
-- Поиск потенциальных дубликатов по ИНН (один ИНН — несколько записей)
SELECT inn, COUNT(*) AS cnt, 
       STRING_AGG(source_system || ':' || source_id, ', ') AS sources
FROM staging_counterparties
WHERE inn IS NOT NULL AND TRIM(inn) != ''
GROUP BY inn
HAVING COUNT(*) > 1;
```

Такие группы — кандидаты на слияние. Дальше: выбор «лучшей» записи по атрибутам, создание золотой записи, маппинг source_id → golden_id. Для физлиц и случаев без ИНН нужны более сложные правила (fuzzy matching по ФИО, адресу, телефону). См. [§5.1](chapter-05-01.md), [§5.2](chapter-05-02.md).

## 3.1.8. Типичные ошибки

- **Полагаться только на точное совпадение строк:** «ООО Ромашка» ≠ «Ромашка ООО» при сравнении; нужна нормализация и нечёткое сравнение.
- **Игнорировать отсутствие ключа:** если ИНН не заполнен у части контрагентов, алгоритм только по ИНН пропустит дубликаты.
- **Считать дубликаты только проблемой «клиентов»:** дубликаты продуктов, сотрудников, договоров столь же критичны.
- **Не вести маппинг после слияния:** слияние дубликатов без сохранения «старый ID → новый ID» ломает ссылки в транзакциях и истории.

---

## Ключевое

- **Дубликат** — несколько записей об одной реальной сущности с разными ID или атрибутами.
- **Один клиент в разных системах** — типичная причина; каждый источник даёт свою запись; сопоставление — по ИНН, коду или комбинации атрибутов.
- **Разные написания** — наименования, ФИО, адреса в разных форматах; нужны нормализация и fuzzy matching.
- **Отсутствие единого ключа** — усложняет сопоставление; решение: регуляторные ID (ИНН, ОГРН), маппинг, комбинация атрибутов.
- **Последствия:** искажение аналитики, дубли рассылок, сверки, недоверие к данным.
- **Расхождения в атрибутах** — при выявленных дубликатах требуется выбор «лучшего» значения; правила слияния — в главе 4.

В [§3.2](chapter-03-02.md) мы рассмотрим множественность источников: несколько систем содержат эталонные данные, разные форматы и атрибуты.
