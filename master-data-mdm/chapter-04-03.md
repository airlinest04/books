# §4.3 Слияние данных из нескольких источников

В [§4.1](chapter-04-01.md) и [§4.2](chapter-04-02.md) мы определили золотую запись и правила выбора «лучшего» значения. В этом разделе разберём **процесс слияния** (merge) данных из нескольких источников: как объединять записи в одну золотую, какие стратегии применять по полям и как обрабатывать конфликты на практике. В [§4.4](chapter-04-04.md) рассмотрим версионирование и историю изменений.

---

## 4.3.1. Слияние (merge): суть процесса

**Слияние** (merge) — объединение двух и более записей, относящихся к одной сущности, в одну золотую запись путём выбора значения для каждого атрибута по правилам. См. [Глоссарий](glossary.md).

Этапы:

1. **Сопоставление:** определить, какие записи относятся к одной сущности (по ИНН, коду, правилам дедупликации). См. [§5.1](chapter-05-01.md).
2. **Сбор атрибутов:** для каждого поля золотой записи собрать все непустые значения из сопоставленных записей с указанием источника.
3. **Разрешение конфликтов:** при нескольких значениях — применить правила выбора (приоритет, дата, полнота). См. [§4.2](chapter-04-02.md).
4. **Формирование записи:** собрать итоговую строку; присвоить golden_id; сохранить маппинг source_id → golden_id.
5. **Сохранение истории (опционально):** записать, какое значение откуда взято, для аудита.

---

## 4.3.2. Merge по полям (field-level merge)

**Merge по полям** — стратегия, при которой для каждого атрибута независимо выбирается значение по правилам. Итоговая запись — «коллаж»: поле A из источника 1, поле B из источника 2, поле C из источника 1. См. [Глоссарий](glossary.md).

Пример для контрагента:

| Атрибут | Источник 1 (CRM) | Источник 2 (ERP) | Результат (по приоритету) |
|---------|------------------|------------------|---------------------------|
| name | ООО Ромашка | Ромашка ООО | ERP (приоритет 1) → «Ромашка ООО» |
| inn | — | 7707123456 | ERP → 7707123456 |
| phone | +7 495 123-45-67 | — | CRM → +7 495 123-45-67 |
| address | Ленина, 5 | Москва, Ленина, 5, оф. 10 | ERP → Москва, Ленина, 5, оф. 10 |

Итог: золотая запись собрана из обоих источников по полям. Merge по полям — наиболее гибкий подход; приоритеты задаются отдельно для каждого атрибута.

---

## 4.3.3. Merge по записи (record-level merge)

**Merge по записи** — стратегия, при которой выбирается **целиком** одна запись как база (например, из источника с наивысшим общим приоритетом), а остальные используются только для заполнения пустых полей. См. [Глоссарий](glossary.md).

Плюсы: проще; одна запись — «главная». Минусы: при равном приоритете или при «лучших» значениях в разных источниках теряем информацию. Merge по записи уместен, когда один источник явно авторитетнее остальных для данной сущности; в типичном случае множества равноправных источников merge по полям предпочтительнее.

---

## 4.3.4. Стратегии при конфликте

Для атрибута с конфликтом (несколько разных значений) применяют:

| Стратегия | Описание | Когда использовать |
|-----------|----------|---------------------|
| **Приоритет источника** | Взять значение из источника с наивысшим приоритетом | Базовый случай; владелец данных определён |
| **Самое свежее** | Взять с максимальной датой обновления | Актуальность важнее авторитета |
| **Самое полное** | Взять более длинное/детализированное | Адрес, описание |
| **Конкатенация** | Объединить (редко) | Несколько контактов в одно поле — спорно; лучше отдельные атрибуты |
| **Ручной разбор** | Не выбирать автоматически; отправить на согласование | Редкие критичные конфликты |

Стратегия задаётся по атрибутам в конфигурации; для большинства полей — приоритет источника.

---

## 4.3.5. Обработка добавлений и обновлений

Слияние выполняется при:

- **Первичной загрузке:** все сопоставленные записи — кандидаты; формируем золотую запись с нуля.
- **Инкрементальном обновлении:** пришли изменения из источника; нужно обновить золотую запись.

При инкременте:

- **Новая запись из источника:** если не сопоставляется ни с одной существующей золотой — создаём новую золотую запись.
- **Обновление существующей:** запись сопоставлена с золотой; пересчитываем значения по правилам слияния с учётом новых данных; при конфликте — применяем стратегию.
- **Удаление в источнике:** по правилам домена — помечать золотую как неактивную, удалять маппинг или сохранять (soft delete). См. [§10.2](chapter-10-02.md).

## 4.3.6. Маппинг после слияния

После слияния дубликатов несколько source_id маппятся на один golden_id:

```
source_system | source_id | golden_id
--------------|-----------|----------
CRM           | 1001      | 5001
ERP           | C-4421    | 5001
Биллинг       | B-8892    | 5001
```

Таблица маппинга нужна для:

- Загрузки фактов: транзакция из ERP с counterparty_code=C-4421 → при джойне получаем golden_id=5001 и пишем его в факт.
- Обратного распространения: обновление в MDM → по golden_id находим source_id для каждой системы и обновляем операционные системы.
- Аудита: откуда пришла запись, когда сопоставлена. См. [§7.2](chapter-07-02.md).

## 4.3.7. Пример алгоритма слияния (псевдокод)

```
function merge_to_golden(matched_records: List[Record]) -> GoldenRecord:
    golden = {}
    for attr in schema.attributes:
        values = [(r.source, r[attr], r.updated_at) for r in matched_records 
                  if r[attr] is not null and trim(r[attr]) != '']
        if values is empty:
            golden[attr] = null
        else if all same value (after normalize):
            golden[attr] = values[0].value
        else:
            # conflict
            sort values by (priority[source], desc(updated_at))
            golden[attr] = values[0].value
    golden.id = assign_golden_id()
    for r in matched_records:
        mapping.add(r.source, r.source_id, golden.id)
    return golden
```

Упрощённо; в реальности — учёт правил по атрибутам, полноты, логирования.

## 4.3.8. Сохранение истории слияния

Для аудита и отладки полезно хранить:

- **Кто дал значение:** для каждого атрибута — source_system, source_id.
- **Когда слияние выполнено:** timestamp.
- **Какие значения отброшены:** при конфликте — что было в других источниках.

Варианты хранения: отдельная таблица `golden_merge_audit` (golden_id, attr, source, value, chosen); расширенные метаданные в ETL-логах. При высокой нагрузке можно логировать только конфликты. См. [§4.4](chapter-04-04.md).

---

## 4.3.9. Типичные ошибки

- **Слияние без сопоставления:** объединять записи, не проверив, что они об одной сущности — риск слить разных клиентов.
- **Игнорировать нормализацию перед сравнением:** «+7 495 123-45-67» и «84951234567» — одно значение; без нормализации считаем конфликтом.
- **Не обновлять маппинг при слиянии:** после merge двух золотых в одну (редкий случай) старые golden_id должны маппиться на новую.
- **Считать слияние одноразовым:** при каждом обновлении из источников слияние пересчитывается; логика должна быть идемпотентной при повторном применении тех же данных.

---

## Ключевое

- **Слияние (merge)** — объединение записей одной сущности в одну золотую по правилам выбора по полям.
- **Merge по полям** — для каждого атрибута своё значение из своего источника; гибко, типичный выбор.
- **Merge по записи** — одна запись-база, остальные только заполняют пустые поля; проще, но менее гибко.
- **Стратегии при конфликте:** приоритет, самое свежее, самое полное; задаются по атрибутам.
- **Маппинг** source_id → golden_id обязателен после слияния; используется при загрузке фактов и обратном распространении.
- **История слияния** — для аудита; кто дал значение, что отброшено.
- **Инкремент:** новые записи — новые золотые; обновления — пересчёт по правилам.

В [§4.4](chapter-04-04.md) мы рассмотрим версионирование и историю: SCD для эталонов, effective_from/effective_to, аудит изменений.
