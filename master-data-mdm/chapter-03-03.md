# §3.3 Несогласованность и конфликты

В [§3.1](chapter-03-01.md) и [§3.2](chapter-03-02.md) мы разобрали дубликаты и множественность источников. В этом разделе рассмотрим **несогласованность и конфликты**: когда разные источники дают разные значения для одного и того же атрибута одной сущности. Нужны правила — приоритеты источников, критерии выбора «лучшего» значения и механизмы разрешения конфликтов. Эти правила лягут в основу слияния при построении золотой записи (глава 4). В [§3.4](chapter-03-04.md) перейдём к иерархиям и связям между сущностями.

---

## 3.3.1. Понятие конфликта

**Конфликт** — ситуация, когда несколько источников содержат разные значения для одного атрибута одной сущности, и при слиянии в золотую запись необходимо выбрать одно значение. См. [Глоссарий](glossary.md).

Пример: контрагент «ООО Ромашка» (ИНН 7707123456). Адрес в CRM — «Москва, ул. Ленина, 5»; в ERP — «Москва, Ленина, 5, офис 10»; в логистике — «Москва, Ленина 5, кв. 10». Три разных значения для атрибута «адрес»; при создании золотой записи нужно решить, какое использовать (или как комбинировать).

Конфликт возникает при:
- Слиянии дубликатов в одну золотую запись
- Синхронизации между системами (модель сосуществования)
- Обновлении эталона из нескольких источников

Без правил разрешения выбор делается произвольно или вручную; при автоматизации нужны детерминированные правила. См. [§4.2](chapter-04-02.md), [§4.3](chapter-04-03.md).

---

## 3.3.2. Типы конфликтов

| Тип | Описание | Пример |
|-----|----------|--------|
| **Разные значения** | Одно поле, разные строки | Телефон: +7 495 123-45-67 vs 8 495 123 45 67 (после нормализации может совпасть) |
| **Разная детализация** | Одно полнее другого | Адрес: «Ленина, 5» vs «Ленина, 5, офис 10» |
| **Разная актуальность** | Одно устарело | CRM обновил адрес вчера; ERP — месяц назад |
| **Пропуск vs значение** | В одном пусто, в другом заполнено | В CRM телефон пустой, в ERP — +7 495 123-45-67 |
| **Семантический конфликт** | Разные атрибуты под одним полем | «Адрес» в CRM — юридический, в логистике — доставки; по смыслу разные |

Семантический конфликт решается не выбором значения, а разделением атрибутов: `address_legal` и `address_delivery`. Остальные типы — через правила приоритета. См. [§4.2](chapter-04-02.md).

---

## 3.3.3. Приоритет источника

**Приоритет источника** — правило: для данного атрибута (или группы атрибутов) при конфликте выбирать значение из источника с более высоким приоритетом. См. [Глоссарий](glossary.md).

Пример матрицы приоритетов для контрагента:

| Атрибут | 1-й приоритет | 2-й приоритет | 3-й приоритет |
|---------|---------------|---------------|---------------|
| Наименование | ERP | CRM | Биллинг |
| ИНН, ОГРН | ERP | — | — |
| Юридический адрес | ERP | CRM | — |
| Контактный телефон | CRM | ERP | — |
| Email | CRM | ERP | — |
| Адрес доставки | Логистика | CRM | — |
| Банковские реквизиты | ERP | Биллинг | — |

Обоснование: ERP — источник реквизитов для документов; CRM — контактов для общения; логистика — адресов доставки. Приоритеты задаются бизнесом и закрепляются в правилах слияния. См. [§4.2](chapter-04-02.md).

---

## 3.3.4. Самое свежее / самое полное

Альтернативы приоритету источника:

**По дате изменения (самое свежее):** при конфликте выбирать значение с более поздней датой обновления. Подходит, когда актуальность важнее «авторитетности» источника. Риск: недавняя ошибочная правка перекроет корректное старое значение.

**По полноте (самое полное):** при конфликте выбирать более длинное или детализированное значение. Например, «Ленина, 5, офис 10» предпочтительнее «Ленина, 5». Риск: «полное» может быть избыточным или содержать мусор.

**Комбинация:** приоритет источника как основной критерий; при равном приоритете — по дате или полноте. Правила можно задавать по атрибутам. См. [§4.2](chapter-04-02.md).

---

## 3.3.5. Разрешение конфликтов: алгоритм

Типичный алгоритм при слиянии записей в золотую:

1. **Сопоставить записи:** определить, что они относятся к одной сущности (по ИНН, коду или правилам сопоставления).
2. **Собрать значения по атрибутам:** для каждого атрибута — список значений из всех источников.
3. **Выявить конфликты:** атрибуты, где значений больше одного и они различаются (с учётом нормализации).
4. **Применить правила:** для каждого конфликтного атрибута — выбрать значение по приоритету источника, дате, полноте или комбинированному правилу.
5. **Записать результат:** золотая запись с выбранными значениями; при необходимости — сохранить историю (кто дал какое значение, когда).

Если правил недостаточно (например, два источника с равным приоритетом и одинаковой датой), возможен **ручной разбор** или эскалация; такие случаи логировать для доработки правил. См. [§5.3](chapter-05-03.md).

## 3.3.6. Синхронизация и одновременные изменения

В модели **сосуществования** несколько систем могут обновлять эталонные данные. При одновременном изменении одного атрибута в двух системах возникает конфликт: какое изменение считать текущим?

Варианты:

- **Last Write Wins:** последнее по timestamp изменение перезаписывает предыдущее. Просто, но теряется первое изменение.
- **Первый применивший выигрывает:** при синхронизации отклонять конфликтующие обновления с уведомлением.
- **Ручное разрешение:** конфликт уходит на согласование владельцу данных.
- **Слияние по полям:** каждое поле имеет свой приоритет; система A обновила адрес, система B — телефон; принимаем оба изменения (конфликта нет, т.к. разные поля). Конфликт только при изменении одного поля в двух системах.

Выбор зависит от частоты конфликтов, критичности данных и возможностей по ручному разбору. См. [§9.2](chapter-09-02.md), [§9.3](chapter-09-03.md).

## 3.3.7. Документирование правил

Правила разрешения конфликтов должны быть **задокументированы** и по возможности формализованы (в конфигурации ETL, в MDM-системе):

- Матрица приоритетов источников по атрибутам
- Дополнительные критерии (дата, полнота) по атрибутам
- Обработка пропусков: если в приоритетном источнике пусто — брать из следующего
- Исключения: особые кейсы, ручной разбор

Документация нужна для воспроизводимости, аудита и передачи знаний. При изменении процессов или источников правила пересматривают. См. [§12.1](chapter-12-01.md).

---

## 3.3.8. Типичные ошибки

- **Один приоритет для всех атрибутов:** для разных атрибутов уместны разные владельцы; «ERP главнее всегда» может дать устаревшие контакты.
- **Игнорировать пустые значения:** при «приоритет CRM» и пустом значении в CRM — брать из ERP; иначе теряем данные.
- **Не учитывать семантику:** «адрес» в разных системах — разный смысл; смешивать неверно.
- **Не логировать конфликты:** при автоматическом разрешении полезно сохранять, какой источник «победил» и какие значения отброшены — для отладки и анализа качества.

---

## Ключевое

- **Конфликт** — разные значения для одного атрибута одной сущности из нескольких источников; при слиянии нужно выбрать одно.
- **Типы конфликтов:** разные значения, разная детализация, разная актуальность, пропуск vs значение, семантический (разные атрибуты под одним полем).
- **Приоритет источника** — правило выбора по владельцу данных; задаётся матрицей «атрибут → приоритет источников».
- **Альтернативы:** самое свежее (по дате), самое полное; комбинация с приоритетом.
- **Алгоритм:** сопоставить → собрать значения → выявить конфликты → применить правила → записать результат.
- **Синхронизация:** при сосуществовании — Last Write Wins, ручное разрешение или слияние по полям.
- **Документирование** правил обязательно для воспроизводимости и поддержки.

В [§3.4](chapter-03-04.md) мы рассмотрим иерархии и связи между сущностями: клиент — филиал — контракт, продукт — категория, многоуровневые связи.
