# §2.2 Продукты и каталог

В [§2.1](chapter-02-01.md) мы разобрали клиентов и контрагентов. В этом разделе рассмотрим **продукты** — товары и услуги, которые организация предлагает или учёт которых ведёт. Продуктовая сущность: номенклатура, иерархия категорий, атрибуты и версионность. Понимание структуры продуктового каталога необходимо для построения эталонного слоя, измерений в DWH и аналитики по номенклатуре. В [§2.3](chapter-02-03.md) перейдём к справочникам и классификаторам.

---

## 2.2.1. Продукт: определение и номенклатура

**Продукт** — товар или услуга в каталоге организации: номенклатурная позиция с кодом, наименованием, атрибутами и связями. В контексте MDM продукт — эталонная сущность: «что» продаётся, хранится, учитывается. См. [Глоссарий](glossary.md).

**Номенклатура** — совокупность продуктов (позиций каталога) с единой структурой атрибутов и правилами идентификации. Номенклатура может включать: материальные товары (SKU), услуги, комплекты, виртуальные позиции (доставка, упаковка). См. [Глоссарий](glossary.md).

| Тип позиции | Описание | Примеры |
|-------------|----------|---------|
| Товар (SKU) | Единица учёта с уникальным кодом | «Масло сливочное 82,5%, 200 г», «Ноутбук X, 16 ГБ» |
| Услуга | Нематериальный продукт | Доставка, консультация, подписка |
| Комплект | Набор товаров/услуг как одна позиция | Набор «подарочный», пакет услуг |
| Групповая позиция | Агрегат для отчётности (без отдельного учёта) | «Масло сливочное» как категория |

Для эталонного слоя критично: каждая позиция имеет **уникальный идентификатор** и **набор атрибутов**, по которым её можно сопоставить в разных источниках. Дубликаты продуктов (один товар под разными кодами или названиями) — типичная проблема, решаемая MDM. См. [§3.1](chapter-03-01.md).

---

## 2.2.2. Иерархия продукта

Продукты часто организованы в **иерархию**: категория → подкатегория → товар. Иерархия используется для навигации в каталоге, срезов в отчётности («продажи по категориям») и фильтрации. См. [§6.1](chapter-06-01.md).

Пример иерархии:

```
Молочные продукты
├── Молоко
│   ├── Цельное
│   └── Обезжиренное
├── Сыры
│   ├── Твёрдые
│   └── Мягкие
└── Масло
    └── Сливочное
```

Особенности:

- **Множественность иерархий:** продукт может входить в несколько «разрезов» — по категории товара, по бренду, по типу упаковки, по поставщику. Выбор иерархии зависит от задач отчётности.
- **Уровни:** корень (все продукты), категория, подкатегория, группа, SKU. Глубина и названия уровней задаются бизнесом.
- **Связь продукт — категория:** в эталонной модели продукт хранит ссылку на категорию (parent_id или category_id); при загрузке в DWH иерархия может быть денормализована (категория в строке продукта) или нормализована (отдельная таблица категорий, схема «снежинка»). См. [§6.2](chapter-06-02.md), [§6.4](chapter-06-04.md).

## 2.2.3. Атрибуты продукта

Типичные атрибуты продукта:

| Атрибут | Описание | Примечания |
|---------|----------|------------|
| Код (SKU, артикул) | Уникальный идентификатор в каталоге | Внутренний код; может отличаться от кода поставщика |
| Наименование | Название позиции | Разные форматы (короткое, полное, для печати) |
| Категория | Ссылка на категорию иерархии | Может быть несколько (категория, подкатегория) |
| Бренд | Производитель или марка | Для аналитики по брендам |
| Единица измерения | шт, кг, л, упак. | Справочник; влияет на учёт и отчётность |
| Описание | Текстовая характеристика | Для каталога, поиска; реже для эталона в DWH |
| Вес, объём, габариты | Физические параметры | Для логистики, хранения |
| Цена | Базовая цена, валюта | Может храниться в отдельной сущности; зависит от канала, периода |
| Статус | Активен, снят с производства, в разработке | Для фильтрации в отчётах |
| Дата ввода, дата снятия | Жизненный цикл | Версионность, история |

Атрибуты могут быть **общими** для всех продуктов или **специфичными** для типа (например, размер для одежды, объём для напитков). В расширяемых каталогах используют атрибуты-пары (название — значение) или отдельные таблицы атрибутов. Для эталонного слоя обычно фиксируют ключевые атрибуты в плоской структуре; расширенные — по необходимости.

## 2.2.4. Версионность продукта

Продукт меняется во времени: переименование, смена категории, снятие с производства, изменение атрибутов. Для корректности исторических отчётов нужна **версионность** (или SCD для измерения «Продукт»). См. [§10.4](chapter-10-04.md).

Два аспекта:

- **Изменение атрибутов:** название, категория, статус. При изменении — новая версия записи с effective_from / effective_to (SCD Type 2) или перезапись с аудитом (Type 1). Факты продаж ссылаются на версию продукта, актуальную на дату продажи.
- **Жизненный цикл:** ввод в каталог, активная продажа, снятие с производства. Статус и даты позволяют фильтровать «текущие» продукты и строить отчёты «на дату».

Без версионности отчёт «продажи по категориям за прошлый год» может исказиться: продукт сменил категорию, и все прошлые продажи «переехали» в новую категорию. SCD Type 2 сохраняет историю атрибутов. См. книга «Проектирование и архитектура хранилищ данных», глава 5.

## 2.2.5. Источники продуктовых данных

| Источник | Что содержит | Особенности |
|----------|--------------|-------------|
| **ERP (номенклатура)** | Полный каталог: коды, наименования, категории, единицы измерения | Часто главный источник; иерархия может быть своей |
| **Склад (WMS)** | Товары с кодами, местами хранения, остатками | Может содержать свои коды; нужен маппинг на номенклатуру ERP |
| **Каталог (PIM, CMS)** | Данные для интернет-магазина: описания, изображения, SEO | Расширенные атрибуты; может отличаться от ERP |
| **Закупки** | Коды поставщиков, артикулы | Один внутренний продукт — несколько артикулов поставщиков |
| **Маркетинг** | Группировки по кампаниям, сегменты | Дополнительные «срезы» для аналитики |

Разные источники — разные коды, наименования и уровни детализации. Задача MDM (или ETL при отсутствии MDM): сопоставить «продукт из ERP» и «товар со склада», свести к единой золотой записи, разрешить конфликты по атрибутам. См. [§3.2](chapter-03-02.md), [§4.3](chapter-04-03.md).

## 2.2.6. Пример структуры эталонной таблицы «Продукт»

Упрощённый пример структуры измерения «Продукт»:

```sql
-- Пример структуры dim_product (упрощённо)
CREATE TABLE dim_product (
    product_sk       BIGINT PRIMARY KEY,
    product_bk       VARCHAR(50),          -- внутренний код (SKU)
    name             VARCHAR(500),
    name_short       VARCHAR(200),
    category_id      BIGINT,               -- ссылка на категорию
    category_name    VARCHAR(200),         -- денормализация для звезды
    brand            VARCHAR(100),
    unit             VARCHAR(20),          -- шт, кг, л
    status           VARCHAR(20),          -- 'ACTIVE' | 'DISCONTINUED'
    source_system    VARCHAR(50),
    source_id        VARCHAR(100),
    valid_from       DATE,
    valid_to         DATE,
    is_current       SMALLINT
);

-- Таблица категорий (для снежинки или иерархии)
CREATE TABLE dim_category (
    category_sk      BIGINT PRIMARY KEY,
    category_bk      VARCHAR(50),
    name             VARCHAR(200),
    parent_id        BIGINT,               -- для иерархии
    level_num        INT
);
```

Выбор «звезда» (category_name в dim_product) или «снежинка» (отдельная dim_category с джойном) — по критериям из книги по DWH. SCD Type 2 реализуется через valid_from, valid_to, is_current. См. [§1.4](chapter-01-04.md), [§10.3](chapter-10-03.md).

## 2.2.7. Специфика услуг и цифровых продуктов

**Услуги** и **цифровые продукты** (подписки, лицензии, контент) отличаются от материальных товаров:

- Нет складского учёта в традиционном смысле.
- Могут не иметь SKU в физическом виде; идентификация — по коду услуги, типу подписки.
- Атрибуты: срок действия, тариф, единица потребления (час, пользователь, гигабайт).

Эталонная модель должна предусматривать тип продукта (товар / услуга / цифровой) и соответствующие атрибуты; при необходимости — отдельные подмодели или наследование.

---

## 2.2.8. Типичные ошибки

- **Путать код продукта и артикул поставщика:** внутренний SKU и артикул поставщика — разные; нужна таблица маппинга «поставщик + артикул → product_id».
- **Игнорировать иерархию при смене категории:** при переносе продукта в другую категорию история продаж должна сохранять старую категорию на дату факта (SCD).
- **Смешивать цену и продукт:** цена — отдельный контекст (канал, период, валюта); в эталоне продукта хранят базовую цену или не хранят, в зависимости от модели.
- **Не учитывать множественность иерархий:** продукт в категории «Молочные» и в бренде «Простоквашино» — один продукт, два разреза; модель должна поддерживать оба.

---

## Ключевое

- **Продукт** — товар или услуга в каталоге; **номенклатура** — совокупность продуктов с единой структурой.
- **Иерархия:** категория → подкатегория → продукт; возможны несколько иерархий (категория, бренд, тип).
- **Атрибуты:** код, наименование, категория, бренд, единица измерения, статус, даты жизненного цикла.
- **Версионность:** изменение атрибутов (название, категория) требует SCD для корректности исторических отчётов.
- **Источники:** ERP, склад, PIM, закупки; сопоставление и слияние — задача MDM/ETL.
- **Услуги и цифровые продукты:** отличаются атрибутами; модель должна их учитывать.

В [§2.3](chapter-02-03.md) мы рассмотрим справочники и классификаторы: ОКВЭД, валюты, единицы измерения и их роль в эталонном слое.
