# §11.1 Обогащение транзакций эталонными данными

Глава 10 завершила тему эталонных данных в DWH. Глава 11 посвящена **ETL и MDM** — практическим аспектам загрузки и использования эталонов в пайплайнах. В этом разделе рассмотрим **обогащение транзакций** эталонными данными: транзакция содержит ID (customer_id, product_code и т.д.); джойн с эталоном или маппингом даёт ключ и атрибуты; как добавлять атрибуты клиента, продукта, контрагента. В [§11.2](chapter-11-02.md) разберём Lookup и джойн; в [§11.3](chapter-11-03.md) — дедупликацию в пайплайне; в [§11.4](chapter-11-04.md) — качество эталонных данных.

---

## 11.1.1. Транзакция содержит ID

Транзакция (продажа, платёж, отгрузка) содержит **ссылки** на эталонные сущности в виде идентификаторов: customer_id, product_id, contract_id, counterparty_code. Эти ID приходят из системы-источника (CRM, ERP, каталог) и могут быть source_id (внутренний ID источника), а не golden_id. См. [§1.1](chapter-01-01.md), [§1.2](chapter-01-02.md).

Для загрузки в DWH и для отчётов нужны:

1. **Разрешение ID:** source_id → golden_id (или surrogate key измерения) по маппингу.
2. **Атрибуты сущности:** наименование клиента, категория продукта, реквизиты контрагента — для интерпретации и группировки в отчётах.

---

## 11.1.2. Обогащение: суть

**Обогащение** (enrichment) — добавление к транзакции (или к факту) атрибутов из эталонной таблицы по ключу. Транзакция имеет customer_id; эталон «клиент» содержит customer_id, name, inn, region, segment; джойн даёт name, region и т.д. См. [§1.1](chapter-01-01.md).

Два варианта использования:

- **При загрузке в DWH (ETL):** разрешить source_id → surrogate key измерения; записать surrogate key в факт. Атрибуты при отчёте получают через JOIN факта с измерением. Типичная размерная модель. См. [§10.3](chapter-10-03.md).
- **При загрузке в плоскую структуру (файл, таблицу):** добавить столбцы name, region, category из эталона прямо в целевую таблицу (денормализация). Отчёт работает без JOIN; но дублирование и рост объёма. См. [§6.4](chapter-06-04.md).

---

## 11.1.3. Разрешение source_id → golden_id

Когда транзакция приходит из источника с **source_id** (customer_id из CRM, product_code из каталога), а в DWH факт должен ссылаться на **golden_id** (или surrogate key измерения), нужен **маппинг**. См. [§7.2](chapter-07-02.md), [§5.3](chapter-05-03.md).

Шаги при загрузке факта:

1. Взять из транзакции source_id и source_system (или он известен по контексту пайплайна).
2. По таблице маппинга найти golden_id: `SELECT golden_id FROM mapping WHERE source_system = ? AND source_id = ?`.
3. Найти surrogate key измерения для этого golden_id (если измерение использует surrogate key, отличный от golden_id).
4. Записать surrogate key (или golden_id) в факт как customer_id, product_id и т.д.

Без маппинга транзакции из разных источников с разными source_id для одной сущности не свяжутся; агрегаты по клиентам или продуктам будут искажены. См. [§3.1](chapter-03-01.md).

---

## 11.1.4. Добавление атрибутов клиента, продукта

**Клиент:** транзакция имеет customer_id (source_id или уже golden_id). Атрибуты — name, inn, region, segment — хранятся в dim_customer или core.customer. При обогащении: JOIN по customer_id; добавить в поток (или в целевую таблицу) столбцы customer_name, customer_region и т.д. См. [§2.1](chapter-02-01.md).

**Продукт:** транзакция имеет product_id или product_code. Атрибуты — name, category, brand, unit — в dim_product или core.product. Обогащение: JOIN; добавить product_name, product_category и т.д. См. [§2.2](chapter-02-02.md).

**Контрагент:** для платежей, закупок — counterparty_id, counterparty_code; атрибуты — name, inn, bank_details. Аналогично: JOIN с эталоном; добавить атрибуты. См. [§2.1](chapter-02-01.md).

---

## 11.1.5. Обогащение в ETL: Lookup и Join

В ETL-инструментах (Informatica, dbt, Python, SQL) обогащение реализуют через:

- **Lookup:** справочная таблица (эталон или маппинг) загружается в память или кеш; для каждой строки транзакции по ключу ищется соответствующая запись; из неё берутся нужные столбцы. Эффективно при небольших справочниках. См. [§11.2](chapter-11-02.md).
- **Join (SQL):** транзакции и эталон джойнятся по ключу; в выходной поток попадают столбцы из обеих таблиц. При больших объёмах — в СУБД. См. [§11.2](chapter-11-02.md).

Выбор зависит от объёма данных, расположения (одна БД или разные источники) и возможностей инструмента. См. книга «Informatica», книга «ETL и интеграция данных».

---

## 11.1.6. Обогащение при запросе (без денормализации)

В размерной модели факт хранит **только ключи** измерений; атрибуты (name, category, region) остаются в измерениях. «Обогащение» происходит **при запросе** — JOIN факта с dim_customer, dim_product и т.д. См. [§10.3](chapter-10-03.md).

ETL при загрузке факта **не добавляет** атрибуты в факт — только подставляет правильный surrogate key (после маппинга source_id → golden_id). Это уменьшает объём факта и избегает дублирования; при этом каждый запрос к витрине выполняет JOIN. Для аналитики такой подход стандартен. См. [§10.1](chapter-10-01.md).

---

## 11.1.7. Сироты при обогащении

Если source_id из транзакции **отсутствует** в маппинге или в эталоне, обогащение не даст результата — сирота. См. [§1.2](chapter-01-02.md).

Варианты:

- **Отбросить** транзакцию (потеря данных).
- **Записать с NULL** по атрибутам или с surrogate key заглушки («Unknown»).
- **Отложить** в корзину для последующей обработки после появления маппинга.
- **Создать запись в эталоне «на лету»** — редко; усложняет пайплайн.

Выбор — по политике: допускаются ли факты без эталона, как их учитывать в отчётах. См. [§10.3](chapter-10-03.md).

---

## 11.1.8. Типичные ошибки

- **Джойнить по source_id без маппинга:** при нескольких источниках один клиент имеет разные source_id; джойн по source_id не свяжет их; нужен golden_id.
- **Путать source_id и golden_id:** в факте должен быть ключ эталона (golden_id или surrogate key), а не «сырой» ID из источника.
- **Обогащать до маппинга:** сначала разрешить source_id → golden_id; затем обогащать по golden_id (или по surrogate key).
- **Игнорировать сироты:** нужна явная политика обработки неизвестных ID.

---

## Ключевое

- **Транзакция содержит ID** (customer_id, product_code и т.д.); для загрузки в DWH нужны разрешение в golden_id и атрибуты для отчётов.
- **Обогащение** — добавление атрибутов из эталона по ключу (Lookup, Join).
- **Разрешение source_id → golden_id** — по таблице маппинга; без маппинга транзакции из разных источников не свяжутся.
- **Атрибуты клиента, продукта, контрагента** — из dim_* или core_*; JOIN по ключу.
- **В размерной модели** факт хранит только ключи; обогащение при запросе (JOIN).
- **Сироты** — source_id без маппинга; политика: отброс, заглушка, корзина.

В [§11.2](chapter-11-02.md) разберём Lookup и джойн с эталоном в ETL: реализация в Informatica и аналогах, производительность.
