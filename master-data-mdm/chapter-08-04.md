# §8.4 Связь с DWH

В [§8.1](chapter-08-01.md)–[§8.3](chapter-08-03.md) мы разобрали консолидацию: центр, загрузку, распространение. В этом разделе зафиксируем **связь консолидации с DWH**: как эталонный слой в хранилище соотносится с центром MDM, как витрины потребляют эталоны и как измерения строятся из золотых записей. Детали эталонного слоя в DWH — в главе 10; здесь — точка пересечения модели консолидации и хранилища. В [§9.1](chapter-09-01.md) начнём тему сосуществования.

---

## 8.4.1. Центр и DWH: два варианта

При консолидации **центр** может быть реализован по-разному:

**Вариант 1: Центр внутри DWH.** Эталонный слой (Core эталонов) — часть DWH. Raw/Staging эталонов и Core находятся в том же хранилище, что и витрины. Поток: источники → ETL → Staging эталонов → дедупликация и слияние → Core (золотая запись) → Mart/измерения. Центр и DWH — одна система. См. [§10.1](chapter-10-01.md).

**Вариант 2: Центр вне DWH (MDM-система).** Отдельная MDM-платформа хранит золотые записи; DWH потребляет эталоны из MDM как из внешнего источника. Поток: источники → MDM (дедупликация, слияние, золотая запись) → ETL DWH → измерения DWH. DWH не выполняет дедупликацию и слияние — только загрузку и преобразование в структуру витрин. См. [§1.4](chapter-01-04.md), [§8.1](chapter-08-01.md).

---

## 8.4.2. Эталонный слой в DWH

**Эталонный слой** — слой данных в DWH, содержащий согласованные эталонные сущности (золотые записи). Типичная структура:

| Слой | Содержимое |
|------|------------|
| Raw / Staging эталонов | Сырые выгрузки из источников; единая структура; source_system, source_id |
| Core эталонов | Золотая запись; одна запись на сущность; golden_id; маппинг |
| Mart / измерения | Таблицы измерений для витрин (dim_customer, dim_product); денормализация, SCD |

Когда центр — внутри DWH, Core эталонов и есть центр консолидации. Когда центр — MDM-система, DWH получает готовые золотые записи; Core в DWH может быть копией или прямым представлением данных из MDM. См. [§1.4](chapter-01-04.md), [§10.1](chapter-10-01.md).

---

## 8.4.3. Витрины потребляют эталоны

**Витрины** (data marts) — срезы данных для конкретных отчётов и аналитики. Витрина продаж: fact_sales + dim_customer + dim_product + dim_date. Витрина платежей: fact_payments + dim_counterparty + dim_contract. См. книга по DWH.

Измерения витрины **потребляют эталоны** из Core: dim_customer строится из core.customer (золотая запись клиентов); dim_product — из core.product. Преобразования при загрузке в Mart: денормализация иерархий ([§6.4](chapter-06-04.md)), SCD Type 2 для истории ([§10.4](chapter-10-04.md)), обрезка атрибутов под нужды витрины. См. [§10.3](chapter-10-03.md).

Качество эталонов в Core определяет качество измерений и, следовательно, витрин. Дубликаты или расхождения в Core исказят агрегаты в отчётах. Консолидация с дедупликацией и слиянием — основа корректных витрин. См. [§4.1](chapter-04-01.md).

---

## 8.4.4. Измерения из эталонов

**Измерения** (dim_customer, dim_product, dim_counterparty и т.д.) — это эталонные сущности в размерной модели DWH. Суррогатный ключ измерения (customer_sk, product_sk) — это golden_id или его производная. См. [§1.4](chapter-01-04.md).

Связь:

- Золотая запись в Core: customer_id (golden_id), name, inn, address, ...
- Измерение в Mart: customer_sk (суррогатный ключ), customer_id (бизнес-ключ или golden_id), name, inn, address, ... + атрибуты для витрины (сегмент, effective_from, effective_to при SCD).

Факты ссылаются на суррогатный ключ измерения. При загрузке фактов из транзакций source_id (customer_id из CRM) маппится на golden_id по таблице маппинга; затем golden_id (или customer_sk) записывается в факт. См. [§5.3](chapter-05-03.md), [§7.2](chapter-07-02.md).

---

## 8.4.5. Реестр vs консолидация: влияние на DWH

При **реестре** DWH не получает полных золотых записей из центра — только маппинг. Атрибуты для измерений разрешаются из источников (или из кеша/витрины, материализующей атрибуты из выбранного источника). Измерения в DWH — результат разрешения, а не прямой загрузки из центра. См. [§7.1](chapter-07-01.md), [§7.3](chapter-07-03.md).

При **консолидации** DWH получает полные золотые записи. Измерения строятся напрямую из Core эталонов. Запросы к витринам не требуют обращения к источникам — данные уже в DWH. Проще пайплайн, быстрее запросы, меньше зависимость от доступности источников.

---

## 8.4.6. Частота и порядок загрузки

**Эталоны** и **факты** загружаются разными пайплайнами. Типично: эталоны — раз в сутки или при изменении; факты — ежедневно, ежечасно, потоково. Порядок: сначала эталоны (измерения), затем факты. Факт ссылается на ключ измерения; при загрузке факта измерение должно уже содержать соответствующую запись (или политика по сиротам). См. [§10.2](chapter-10-02.md).

## Ключевое

- **Центр и DWH:** центр может быть внутри DWH (Core эталонов) или снаружи (MDM → DWH).
- **Эталонный слой:** Raw/Staging → Core (золотая запись) → Mart/измерения.
- **Витрины потребляют эталоны:** измерения строятся из Core; качество эталонов — качество витрин.
- **Измерения из эталонов:** dim_customer, dim_product и т.д. — золотые записи в размерной форме; суррогатный ключ = golden_id или производная.
- **Консолидация vs реестр:** при консолидации DWH получает полные записи; при реестре — только маппинг, атрибуты разрешаются из источников.
- **Порядок загрузки:** эталоны до фактов.

В [§9.1](chapter-09-01.md) рассмотрим модель сосуществования: множество систем обновляют эталонные данные; нет единого владельца; синхронизация и разрешение конфликтов.
