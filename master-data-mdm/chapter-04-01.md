# §4.1 Определение золотой записи

В главе 3 мы разобрали проблемы эталонных данных. Глава 4 посвящена **золотой записи** (Golden Record) — центральной концепции MDM. В этом разделе дадим определение золотой записи, зафиксируем её признаки («истинная» версия сущности, объединённая из источников, единый идентификатор) и связь с целями MDM. В [§4.2](chapter-04-02.md) разберём выбор «лучшего» значения при конфликтах; в [§4.3](chapter-04-03.md) — слияние данных из нескольких источников; в [§4.4](chapter-04-04.md) — версионирование и историю.

---

## 4.1.1. Понятие золотой записи

**Золотая запись** (Golden Record) — единая «истинная» версия эталонной сущности (клиент, контрагент, продукт и т.д.), формируемая путём объединения и слияния данных из одного или нескольких источников, с устранением дубликатов и разрешением конфликтов по правилам. Золотая запись имеет единый идентификатор (golden_id) и служит эталоном для всех потребителей. См. [Глоссарий](glossary.md).

Ключевые признаки:

- **Единая версия:** одна запись на сущность; дубликаты слиты.
- **Объединённая:** атрибуты собраны из всех релевантных источников; используются «лучшие» значения по правилам.
- **Единый идентификатор:** golden_id (или surrogate key) — ключ, на который ссылаются транзакции, витрины и другие системы.
- **Эталон:** источник правды для данной сущности; все потребители ориентируются на золотую запись.

---

## 4.1.2. «Истинная» версия сущности

Золотая запись — это **авторитетное представление** сущности: то, что считается «правильным» для отчётности, аналитики и процессов. Не «копия из CRM» или «копия из ERP», а результат согласованного процесса слияния. См. [§1.3](chapter-01-03.md).

Понятие «истинная» не означает, что данные абсолютно безошибочны; оно означает, что:

- Выбрана **одна** версия из множества возможных (разные источники, дубликаты).
- Применены **явные правила** выбора; процесс воспроизводим и документирован.
- **Все потребители** используют эту версию как эталон; расхождений «у кого какой клиент» нет.

Если в источнике обнаружена ошибка, её исправляют в источнике или в процессе загрузки; золотая запись обновляется по тем же правилам. См. [§4.4](chapter-04-04.md).

---

## 4.1.3. Объединённая из источников

Золотая запись **не копируется** из одного источника, а **формируется** из нескольких (когда их несколько):

- Сопоставление записей из разных источников (выявление дубликатов).
- Сбор атрибутов: для каждого поля — значение из одного или нескольких источников.
- Разрешение конфликтов: при разных значениях — выбор по правилам (приоритет источника, дата, полнота).
- Слияние в одну запись с полным набором атрибутов.

Когда источник один (редкий случай для сложных сущностей), золотая запись может совпадать с ним после нормализации и очистки; но концептуально это всё равно «результат процесса», а не слепая копия. См. [§4.3](chapter-04-03.md).

---

## 4.1.4. Единый идентификатор

Золотая запись имеет **единый идентификатор** (golden_id, master_id, surrogate key) — уникальный ключ в рамках MDM-слоя или DWH. Этот ключ:

- Присваивается при создании золотой записи (после дедупликации и слияния).
- Используется как **внешний ключ** в фактах и витринах: транзакции ссылаются на golden_id, а не на ID из источников.
- Связывается с ID источников через **таблицу маппинга**: `(source_system, source_id) → golden_id`. См. [§7.2](chapter-07-02.md).

Таблица маппинга позволяет:

- При загрузке транзакций из источника: по source_id найти golden_id и записать его в факт.
- При обратном распространении: по golden_id найти source_id для обновления операционной системы.
- Сохранять историю: «старый» customer_id из CRM маппится на golden_id после слияния дубликатов.

Без единого идентификатора невозможно согласованно связывать данные из разных источников и витрин. См. [§1.2](chapter-01-02.md), [§10.3](chapter-10-03.md).

---

## 4.1.5. Связь с целями MDM

Золотая запись реализует цели MDM:

| Цель MDM | Как реализует золотая запись |
|----------|------------------------------|
| Единый источник правды | Одна запись на сущность; все ссылаются на неё |
| Устранение дубликатов | Дубликаты слиты в одну запись |
| Согласованность | Атрибуты выбраны по правилам; конфликты разрешены |
| Доверие к данным | Прозрачный процесс; воспроизводимые правила |

Золотая запись — не абстракция, а **артефакт**: конкретная строка в таблице `core.customer`, `core.counterparty`, `core.product` и т.д., созданная и поддерживаемая пайплайном MDM/ETL. См. [§1.3](chapter-01-03.md), [§8.1](chapter-08-01.md).

---

## 4.1.6. Границы золотой записи

Золотая запись — это **одна сущность**. Для клиента — одна запись на клиента; для продукта — одна на продукт. Связанные сущности (договоры, категории, адреса) могут быть:

- **Частью золотой записи** (денормализация): основные атрибуты договора в строке клиента — редко, т.к. у клиента много договоров.
- **Отдельными сущностями** со своими золотыми записями: договор — отдельная таблица с golden_id; связь клиент ↔ договор через ключи.
- **Справочниками:** категория продукта — справочник; продукт ссылается на категорию по коду.

Выбор зависит от модели: что считается «атрибутом» сущности, а что — отдельной сущностью. Для сложных связей (один клиент — много адресов, много контактов) часто используют отдельные таблицы «клиент — адрес», «клиент — контакт» с маппингом на golden_id клиента. См. [§2.1](chapter-02-01.md), [§6.1](chapter-06-01.md).

---

## 4.1.7. Золотая запись и измерения в DWH

В DWH золотая запись эталонной сущности воплощается в **измерении** (dimension): `dim_customer`, `dim_product`, `dim_counterparty`. Суррогатный ключ измерения (customer_sk, product_sk) — это golden_id или его производная. Факты ссылаются на суррогатный ключ измерения; при загрузке фактов source_id из транзакции маппится на суррогатный ключ. См. [§1.4](chapter-01-04.md), [§10.3](chapter-10-03.md).

Таким образом, золотая запись в MDM и измерение в DWH — одна и та же логическая сущность; различие — в слое (MDM core vs DWH mart) и в том, что измерение может быть денормализованным срезом для витрин.

---

## 4.1.8. Типичные ошибки

- **Путать золотую запись с «копией из главного источника»:** золотая запись — результат слияния; «главный» источник может дать только часть атрибутов.
- **Не вести маппинг source_id → golden_id:** без маппинга невозможно корректно загружать транзакции и обновлять ссылки при слиянии дубликатов.
- **Считать золотую запись неизменной:** она обновляется при поступлении изменений из источников; нужны правила обновления и версионирование.
- **Игнорировать качество:** золотая запись формируется из «грязных» источников; без очистки и валидации «золотая» запись может содержать ошибки.

---

## Ключевое

- **Золотая запись** (Golden Record) — единая «истинная» версия эталонной сущности; объединённая из источников; с устранением дубликатов и разрешением конфликтов; с единым идентификатором.
- **«Истинная»** — авторитетное представление; одна версия по правилам; все потребители ориентируются на неё.
- **Объединённая** — атрибуты собраны из нескольких источников; при конфликтах — выбор по правилам.
- **Единый идентификатор** (golden_id) — ключ для ссылок; таблица маппинга `(source_system, source_id) → golden_id`.
- **Связь с DWH:** золотая запись — измерение; суррогатный ключ измерения — golden_id.
- Золотая запись реализует цели MDM: SSOT, устранение дубликатов, согласованность.

В [§4.2](chapter-04-02.md) мы разберём выбор «лучшего» значения: приоритет источника, самое свежее, самое полное, правила по атрибутам.
