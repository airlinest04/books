# §8.2 Загрузка и обогащение

В [§8.1](chapter-08-01.md) мы рассмотрели централизованное хранилище эталонных данных. В этом разделе разберём **загрузку и обогащение**: как данные из источников попадают в центр, как выполняются дедупликация и слияние, и как формируется золотая запись в Core-слое. В [§8.3](chapter-08-03.md) рассмотрим распространение в источники; в [§8.4](chapter-08-04.md) — связь с DWH.

---

## 8.2.1. Пайплайн загрузки: общая схема

Типичный пайплайн консолидации эталонных данных:

```
1. Извлечение (Extract) — выгрузка из источников (CRM, ERP, ...)
2. Загрузка в Staging — сырые/очищенные данные в единой структуре
3. Дедупликация — обнаружение групп дубликатов
4. Слияние (Merge) — формирование золотой записи из группы
5. Загрузка в Core — золотая запись + маппинг
```

Подробности каждого этапа — в [§5.1](chapter-05-01.md), [§5.2](chapter-05-02.md), [§5.3](chapter-05-03.md). Ниже — сводка в контексте пайплайна центра.

---

## 8.2.2. ETL из источников

**Извлечение:** каждая система-источник выгружает эталонные данные по расписанию или по событию (CDC, API, файлы). Формат: CSV, JSON, прямой доступ к БД, API. См. книга «ETL и интеграция данных», [§11.1](chapter-11-01.md).

**Трансформация при загрузке в Staging:**

- **Нормализация структуры:** приведение к единой модели (одни и те же столбцы: name, inn, address, phone, ...) независимо от формата источника.
- **Нормализация форматов:** телефоны — единый формат; даты — единый тип; пробелы и регистр — приведение.
- **Добавление метаданных:** source_system, source_id, loaded_at для каждой строки.
- **Очистка:** отсев явно некорректных записей (пустые ключевые поля, дубликаты в рамках одного источника).

Результат — таблица Staging (staging.counterparty, staging.customer и т.д.) с записями из всех источников в единой структуре. См. [§3.2](chapter-03-02.md).

---

## 8.2.3. Дедупликация

**Дедупликация** — обнаружение записей, относящихся к одной сущности, и объединение их в группы. См. [§5.1](chapter-05-01.md).

Основные приёмы:

- **Сопоставление по ключевому полю:** ИНН для контрагентов, SKU для продуктов; GROUP BY key HAVING COUNT(*) > 1.
- **Fuzzy matching:** при отсутствии надёжного ключа — сравнение по наименованию, адресу (Levenshtein, Jaro-Winkler); порог схожести 0.85–0.95. См. [§5.2](chapter-05-02.md).
- **Блокировка (blocking):** сокращение числа сравнений — сравнивать только записи в одном блоке (например, по первым буквам названия, цифрам ИНН).
- **Комбинированные правила:** ИНН ИЛИ (наименование + адрес) для контрагентов.

Выход дедупликации — **группы** записей-кандидатов на слияние. Каждая группа — один или несколько source_id, относящихся к одной сущности. См. [§5.4](chapter-05-04.md).

---

## 8.2.4. Слияние (Merge)

**Слияние** — формирование одной золотой записи из группы дубликатов. Для каждого атрибута выбирается значение по правилам: приоритет источника, дата обновления, полнота. См. [§4.2](chapter-04-02.md), [§4.3](chapter-04-03.md).

Стратегии:

- **Merge по полям:** для каждого атрибута независимо — «лучшее» значение из группы (по приоритету ERP > CRM, по дате, по длине строки).
- **Merge по записи:** одна запись — база (например, из ERP); остальные — для заполнения пустых полей.

Результат слияния — одна строка с полным набором атрибутов; присваивается golden_id; сохраняется маппинг: каждый source_id из группы → golden_id. См. [§5.3](chapter-05-03.md).

---

## 8.2.5. Обогащение

**Обогащение** — дополнение золотой записи данными из внешних источников или расчётами:

- **Справочники:** код региона по ОКТМО, расшифровка ОКВЭД, нормализованное наименование юрлица из ЕГРЮЛ.
- **Валидация:** проверка ИНН по контрольной сумме, проверка адреса через сервисы.
- **Вычисляемые поля:** сегмент клиента по правилам, флаг «крупный контрагент» по объёму сделок.
- **Источники обогащения:** госреестры, платные справочники, внутренние аналитические таблицы.

Обогащение может выполняться после слияния (на готовой золотой записи) или при загрузке в Staging (до дедупликации). Выбор зависит от логики: enrichment по golden_id или по сырым записям. См. [§2.3](chapter-02-03.md).

---

## 8.2.6. Загрузка в Core (золотая запись в центре)

**Core** — слой согласованных эталонных данных. Таблицы: core.counterparty, core.customer, core.product и т.д.

Структура загрузки:

1. **Insert/Update золотых записей:** новая группа → INSERT с новым golden_id; обновлённая группа (изменения в источниках) → UPDATE существующей записи по golden_id.
2. **Маппинг:** INSERT в таблицу маппинга (source_system, source_id, golden_id) для каждой записи из группы.
3. **SCD (при необходимости):** при изменении атрибутов — новая версия записи с effective_from/effective_to вместо UPDATE. См. [§4.4](chapter-04-04.md).

Инкрементальная загрузка: только изменённые записи из источников (по дате модификации, CDC); пересчёт групп и слияние только для затронутых сущностей. Полная перезагрузка — при изменении правил дедупликации или слияния. См. [§10.2](chapter-10-02.md).

---

## 8.2.7. Новые записи и сироты

**Новая запись** (нет дубликатов в группе) — образует группу из одного элемента; слияние тривиально; создаётся новая золотая запись и маппинг.

**Сироты:** транзакции из источника ссылаются на source_id, которого нет в маппинге (запись ещё не загружена или не сопоставлена). Политика: отложенная загрузка, «корзина» сирот, или создание золотой записи «на лету» при первой встрече source_id. См. [§7.2](chapter-07-02.md), [§1.2](chapter-01-02.md).

---

## 8.2.8. Типичные ошибки

- **Загружать без дедупликации:** дубликаты из разных источников останутся разными записями в Core.
- **Забыть маппинг:** после слияния source_id должен маппиться на golden_id; иначе факты не привяжутся к эталону.
- **Неидемпотентность:** повторная загрузка тех же данных не должна создавать дубликаты золотых или двойные строки маппинга.
- **Игнорировать порядок:** при инкрементальной загрузке порядок обработки источников и партий может влиять на результат; нужны детерминированные правила.
- **Смешивать обогащение и слияние:** обогащение — дополнение атрибутов; слияние — выбор между конфликтующими значениями из источников; не путать.

---

## Ключевое

- **Пайплайн:** Extract → Staging → Дедупликация → Слияние → Core + маппинг.
- **ETL:** нормализация структуры и форматов, метаданные source_system, source_id.
- **Дедупликация:** сопоставление по ключу, fuzzy matching, блокировка; выход — группы кандидатов.
- **Слияние:** выбор значения по атрибуту (приоритет, дата, полнота); одна золотая запись на группу.
- **Обогащение:** дополнение из справочников, валидация, вычисляемые поля.
- **Core:** золотая запись + маппинг; Insert/Update; опционально SCD.

В [§8.3](chapter-08-03.md) разберём распространение в источники: центр как источник правды; опциональное обновление операционных систем из центра.
