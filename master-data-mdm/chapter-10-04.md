# §10.4 SCD и история изменений эталонов

В [§10.1](chapter-10-01.md)–[§10.3](chapter-10-03.md) мы разобрали слой эталонных данных, загрузку, витрины и измерения. В этом разделе сосредоточимся на **SCD (Slowly Changing Dimensions)** и истории изменений эталонов: Type 2, эффективные даты (effective_from, effective_to), запросы «на дату» и привязка фактов к версии измерения. Концепция версионирования введена в [§4.4](chapter-04-04.md); здесь — применение при загрузке эталонов в DWH. В [§11.1](chapter-11-01.md) начнём главу 11 — ETL и MDM.

---

## 10.4.1. Зачем SCD для эталонов

Эталонные сущности **меняются** во времени: клиент сменил адрес, продукт переименован или переведён в другую категорию. Без версионирования при изменении перезаписывается текущая запись — история теряется. Отчёт «продажи по категориям за 2023 год» при джойне с измерением покажет **текущие** категории продуктов, а не те, что были в 2023-м. См. [§4.4](chapter-04-04.md).

**SCD Type 2** сохраняет историю: при изменении атрибута добавляется новая строка (новая версия); старая остаётся. Факт ссылается на суррогатный ключ версии, актуальной на дату события. Исторические отчёты становятся корректными. См. книга по DWH, [§5.2](../dwh/chapter-05-02.md), [§5.3](../dwh/chapter-05-03.md).

---

## 10.4.2. Type 2: эффективные даты

При **SCD Type 2** каждая версия записи измерения содержит:

| Поле | Описание |
|------|----------|
| surrogate_key | Уникальный ключ версии (customer_sk, product_sk); PK |
| business_key | Идентификатор сущности (golden_id, ИНН, SKU); несколько версий — один business_key |
| атрибуты | name, category, region, ... |
| effective_from | Дата начала действия версии |
| effective_to | Дата окончания (NULL или 9999-12-31 для текущей) |
| is_current | 1 — текущая версия, 0 — историческая |

При изменении: закрыть текущую версию (`effective_to = дата_изменения`, `is_current = 0`); вставить новую (`effective_from = дата_изменения`, `effective_to = NULL`, `is_current = 1`). См. [§4.4](chapter-04-04.md), книга по DWH, [§5.3](../dwh/chapter-05-03.md).

## 10.4.3. Где применять SCD: Core vs Mart

**Вопрос:** версионировать в Core эталонов или только при загрузке в Mart (измерения)?

- **Core хранит только текущее:** золотая запись — одна строка на сущность; SCD строится в ETL при загрузке из Core в Mart. При изменении в Core ETL сравнивает с предыдущим снимком, детектирует изменения и создаёт новую версию в измерении. Проще Core; логика версий в ETL. См. [§4.4](chapter-04-04.md).

- **Core хранит историю:** в core.customer — версионированные записи с effective_from/to; при загрузке в Mart копируем как есть. Полная история в одном месте; Core сложнее. См. [§10.1](chapter-10-01.md).

Типичный вариант: Core — текущее состояние; Mart (измерения) — с SCD Type 2. ETL при загрузке из Core в Mart применяет логику Type 2: при изменении атрибутов — новая версия в dim_customer, dim_product. См. [§8.2](chapter-08-02.md).

## 10.4.4. Запросы «на дату»

**Текущее состояние** измерения:
```sql
SELECT * FROM dim_customer WHERE is_current = 1;
-- или
SELECT * FROM dim_customer WHERE effective_to IS NULL;
```

**Состояние на дату** (as-of date):
```sql
SELECT * FROM dim_customer
WHERE effective_from <= :as_of_date
  AND (effective_to IS NULL OR effective_to > :as_of_date);
```

Для одной сущности по бизнес-ключу:
```sql
SELECT * FROM dim_customer
WHERE customer_id = :golden_id  -- бизнес-ключ
  AND effective_from <= :as_of_date
  AND (effective_to IS NULL OR effective_to > :as_of_date);
```

См. [§4.4](chapter-04-04.md), книга по DWH, [§5.4](../dwh/chapter-05-04.md).

---

## 10.4.5. Факт и версия измерения

**Ключевой принцип:** факт хранит **суррогатный ключ версии** измерения на дату события. При загрузке факта: по дате факта и бизнес-ключу найти версию измерения, действовавшую на эту дату; подставить её surrogate_key в факт. См. книга по DWH, [§5.3](../dwh/chapter-05-03.md).

При джойне факта с измерением по surrogate_key факт автоматически получает атрибуты, актуальные на момент события. **Не нужно** фильтровать по effective_from/effective_to в запросе отчёта — ключ в факте уже указывает на нужную версию.

**Ошибка:** фильтровать `WHERE is_current = 1` при джойне факта с измерением. Тогда все факты получат текущую версию атрибутов; исторический отчёт «продажи за 2023 по категориям» будет неверен. См. [§4.4](chapter-04-04.md).

## 10.4.6. Выбор даты изменения (effective_from)

Дату для effective_from новой версии задают правилами:

- **Дата загрузки в DWH:** дата/время прогона ETL. Всегда доступна; не отражает реальное время изменения в источнике.
- **Дата из источника:** `updated_at`, `modified_date` из Core или источника. Предпочтительно для точности исторических срезов.
- **Дата из факта:** в специальных схемах — дата первого факта с «новым» состоянием. Сложнее в реализации.

Единообразие в рамках одного измерения обязательно. См. книга по DWH, [§5.3](../dwh/chapter-05-03.md).

---

## 10.4.7. Type 1 vs Type 2 по атрибутам

В одном измерении часть атрибутов может вестись по **Type 1** (перезапись без истории), часть — по **Type 2**. Например: `product_name` и `category` — Type 2 (история нужна); `internal_note` — Type 1 (не влияет на отчёты). Такая схема иногда называется Type 6. См. книга по DWH, [§5.2](../dwh/chapter-05-02.md).

Для эталонных данных в аналитике чаще всего **все** значимые атрибуты ведут по Type 2, чтобы исторические отчёты были корректны.

---

## 10.4.8. Типичные ошибки

- **Фильтровать is_current=1 в историческом отчёте по фактам:** факт должен джойниться по surrogate_key без фильтра; ключ уже указывает на версию на дату факта.
- **Не закрывать предыдущую версию:** при добавлении новой версии у старой должен быть установлен effective_to; иначе перекрытие периодов.
- **При загрузке факта подставлять текущую версию:** для исторических фактов нужна версия на дату факта; иначе отчёты искажаются.
- **Путать дату факта и дату среза:** «факты за январь» — дата события; «измерение на 31.12» — срез на дату; для отчёта по фактам нужна версия на дату каждого факта.

---

## Ключевое

- **SCD Type 2** для эталонов — сохранение истории изменений; при изменении — новая строка с effective_from, effective_to, is_current.
- **Эффективные даты:** effective_from — начало версии; effective_to — конец (NULL для текущей).
- **Где применять:** обычно Core — текущее; SCD в Mart при загрузке из Core.
- **Запрос «на дату»:** effective_from <= date AND (effective_to IS NULL OR effective_to > date).
- **Факт хранит surrogate_key версии** на дату события; при джойне — атрибуты на дату факта; не фильтровать is_current в отчёте по фактам.
- **Дата effective_from:** из источника (updated_at) или дата загрузки; единообразие по измерению.
