# §6.1 Схемы «звезда» и «снежинка» для финансов

В [§5.4](chapter-05-04.md) мы разобрали проверку сходимости итогов. Дальше — **моделирование финансовых данных в DWH**: как организовать хранение проводок, оборотов и остатков так, чтобы расчёты из глав 1–5 и сверка из главы 7 были удобны и однозначны. В этом разделе мы вводим **схему «звезда»** и **схему «снежинка»** в применении к финансам: фактовая таблица движений (проводок) и измерения — счёт, контрагент, дата, продукт. Детали фактов и снимков — в [§6.2](chapter-06-02.md); измерения и слои — в [§6.3](chapter-06-03.md) и [§6.4](chapter-06-04.md). Подробнее о методологии DWH см. специализированную литературу по хранилищам данных. См. [Глоссарий](glossary.md).

---

## 6.1.1. Звёздная схема (star schema)

**Звёздная схема** — модель данных, в которой одна или несколько **фактовых таблиц** связаны с **таблицами измерений** (справочниками). Фактовая таблица содержит события или операции (например, проводки); в каждой строке — ключи измерений (идентификаторы счёта, контрагента, даты и т.д.) и **меры** (суммы дебет/кредит, количество). Измерения хранятся в отдельных таблицах; к факту обращаются по внешним ключам, без дублирования атрибутов измерений в факте.

Визуально: в центре «звезды» — фактовая таблица; вокруг неё — таблицы измерений, соединённые с фактом по ключам. Запросы к оборотам и остаткам обычно идут от факта с JOIN к нужным измерениям для фильтрации и вывода наименований. См. [Глоссарий](glossary.md).

---

## 6.1.2. Схема «снежинка» (snowflake)

**Схема «снежинка»** — вариант звёздной схемы, в котором **измерения нормализованы**: атрибуты измерения разнесены по нескольким таблицам (например, счёт → группа счетов → тип счёта). Факт по-прежнему ссылается на «главную» таблицу измерения (счёт); та в свою очередь ссылается на подчинённое измерение (группа, тип). Цепочка связей образует «снежинку».

Плюсы: меньше дублирования в справочниках, проще поддерживать иерархии. Минусы: больше JOIN при запросах, сложнее навигация для пользователей и для простых отчётов. Для финансов часто используют **звезду** с денормализованными измерениями (в таблице счётов хранят и код группы, и название), чтобы запросы оставались простыми; «снежинка» уместна, когда иерархий много и они глубокие. См. [§6.3](chapter-06-03.md).

## 6.1.3. Фактовая таблица движений (проводок)

В контексте финансов центральная фактовая таблица — **движения (проводки)**. Каждая строка — одна проводка с полями:

- **Ключи измерений:** account_id (счёт), counterparty_id (контрагент), date_id или post_date (дата), product_id (продукт/договор) — по необходимости.
- **Меры:** amount_dt (сумма по дебету), amount_ct (сумма по кредиту) в **NUMERIC(18,2)** ([§2.3](chapter-02-03.md)); при необходимости количество, курс и т.д.

Опционально: doc_id (документ-основание), operation_type и др. Типы мер — только точные (NUMERIC), не FLOAT ([§2.2](chapter-02-02.md)). Из этой таблицы считаются обороты за период ([§4.1](chapter-04-01.md)), остатки на дату ([§4.2](chapter-04-02.md)) и нарастающий итог ([§4.3](chapter-04-03.md)); округление и стратегия — по главам 1 и 3.

Пример логической структуры:

| Поле        | Тип           | Описание              |
|-------------|---------------|------------------------|
| post_id     | BIGINT        | Ключ проводки         |
| account_id  | INT           | Счёт (FK → dim_account) |
| counterparty_id | INT        | Контрагент (FK)       |
| post_date   | DATE          | Дата проводки         |
| product_id  | INT           | Продукт (FK, опционально) |
| amount_dt   | NUMERIC(18,2) | Сумма дебет           |
| amount_ct   | NUMERIC(18,2) | Сумма кредит          |

Связь с книгой по DWH: фактовая таблица транзакционных событий — базовый элемент звёздной схемы; детали типов фактов (транзакции vs снимки) — в [§6.2](chapter-06-02.md).

## 6.1.4. Измерения: счёт, контрагент, дата, продукт

**Измерение «счёт»** (dim_account): справочник счетов. Ключ (account_id), код счёта, название, тип (активный/пассивный), группа/родитель для иерархии. Используется для группировки оборотов и остатков, для фильтрации и вывода в отчётах.

**Измерение «контрагент»** (dim_counterparty): справочник контрагентов. Ключ, ИНН/код, наименование, признаки. Нужно для оборотов и остатков по контрагентам и для сверок.

**Измерение «дата»** (dim_date) или поле даты в факте: дата проводки для фильтрации по периоду, для расчёта оборотов за период и остатков на дату. В dim_date часто хранят год, месяц, квартал, признак конца месяца — для агрегации по периодам без вычислений в запросе.

**Измерение «продукт»** (dim_product): продукт, договор, тариф — по требованию домена. Связь с фактом через product_id для отчётов по продуктам и для расчёта комиссий/процентов по продукту.

Иерархия (счёт → группа → тип) может быть в одной таблице измерений (звезда) или в нескольких (снежинка); см. [§6.3](chapter-06-03.md).

## 6.1.5. Связь с расчётами из предыдущих глав

Звёздная схема с фактом проводок и измерениями счёт/контрагент/дата поддерживает:

- **Обороты за период** ([§4.1](chapter-04-01.md)): GROUP BY account_id (и при необходимости period), SUM(amount_dt), SUM(amount_ct), фильтр по post_date.
- **Остатки на дату** ([§4.2](chapter-04-02.md)): начальное сальдо + оборот за период; оборот — из той же фактовой таблицы.
- **Нарастающий итог** ([§4.3](chapter-04-03.md)): SUM(...) OVER (PARTITION BY account_id ORDER BY post_date) по факту.
- **Проценты, комиссии, налог** (глава 5): факт может содержать поля базы и ставки или расчёт делается в витрине из факта; округление по регламенту.
- **Сверка** (глава 7): сравнение итогов по факту DWH с источником по ключам измерений (счёт, период, контрагент).

Единая фактовая таблица движений и согласованные измерения упрощают повторное использование одних и тех же правил округления и стратегий сверки. Слои загрузки (Raw, Staging, Core, Mart) и место расчёта оборотов/остатков — в [§6.4](chapter-06-04.md).

## 6.1.6. Типичные ошибки

- **Денормализовать меры в факт:** хранить в факте не только суммы, но и «оборот за месяц», «остаток на дату» как отдельные колонки без явного источника — дублирование логики и риск расхождения с расчётом на лету. Обороты и остатки лучше считать из факта проводок или хранить в отдельной витрине/снимке ([§6.2](chapter-06-02.md)).
- **Использовать FLOAT для мер в факте:** все денежные поля — NUMERIC ([§2.3](chapter-02-03.md)).
- **Смешивать уровни детализации в одной фактовой таблице:** проводки (одна строка — одна проводка) и снимки остатков (одна строка — остаток на дату по счёту) лучше хранить в разных таблицах фактов или в разных слоях; см. §6.2.

---

## Ключевое

- **Звёздная схема** — фактовая таблица в центре, таблицы измерений связаны с ней по ключам; запросы — от факта с JOIN к измерениям.
- **Схема «снежинка»** — нормализованные измерения (иерархии в отдельных таблицах); больше JOIN, меньше дублирования в справочниках.
- **Факт движений (проводок)** — центральная таблица для финансов: ключи измерений (счёт, контрагент, дата, продукт) и меры (amount_dt, amount_ct в NUMERIC). Из неё считаются обороты, остатки и нарастающий итог.
- **Измерения** — счёт, контрагент, дата, продукт; используются для группировки, фильтрации и сверки; иерархии можно держать в звезде (денормализованно) или в снежинке.

В [§6.2](chapter-06-02.md) мы разберём типы фактов: транзакционные факты (проводки) и снимки (обороты за период, остатки на дату).
