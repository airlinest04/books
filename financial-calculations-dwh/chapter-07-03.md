# §7.3 Контрольные суммы и проверка баланса

В [§7.2](chapter-07-02.md) мы разобрали сверку источников и витрин. Помимо сравнения двух систем полезны **внутренние** проверки данных в DWH: **контрольные суммы** (итоги по выборке) и **проверка баланса** (сумма дебетов = сумма кредитов). Они выявляют ошибки загрузки и расчёта без обращения к источнику. Здесь мы разберём правило «дебет = кредит», итоги по счетам и кросс-проверки. Обработка выявленных расхождений — в [§7.4](chapter-07-04.md). См. [Глоссарий](glossary.md).

---

## 7.3.1. Сумма дебетов = сумма кредитов

В бухгалтерском учёте каждая проводка затрагивает минимум два счёта: дебет одного и кредит другого на одну и ту же сумму. Поэтому по **любой выборке проводок**, образующих замкнутый набор (все проводки за период, по документу, по счёту в разрезе корреспонденции), должно выполняться:

**SUM(amount_dt) = SUM(amount_ct).**

Если по фактовой таблице движений за период сумма дебетов не равна сумме кредитов — в данных ошибка: пропущена проводка, дублирована одна сторона, искажена сумма при загрузке или тип данных (FLOAT) дал погрешность. Проверку «дебет = кредит» выполняют после загрузки проводок в Core (по периоду, по источнику загрузки). См. [§4.1](chapter-04-01.md), [§6.2](chapter-06-02.md). См. [Глоссарий](glossary.md).

Пример проверки в SQL (PostgreSQL): проводки за январь 2025.

```sql
SELECT
    SUM(amount_dt) AS total_dt,
    SUM(amount_ct) AS total_ct,
    SUM(amount_dt) - SUM(amount_ct) AS diff
FROM core.fact_postings
WHERE post_date >= DATE '2025-01-01'
  AND post_date <= DATE '2025-01-31';
```

Ожидаем diff = 0 (или в пределах погрешности при FLOAT, но для денег используем NUMERIC и тогда 0). При diff != 0 — алерт и разбор. Среда: PostgreSQL 15, Oracle — аналогично.

## 7.3.2. Итоги по счетам и кросс-проверки

**Итоги по счетам** — обороты за период по каждому счёту (SUM(amount_dt), SUM(amount_ct) по account_id). Они используются в отчётах и в сверке с источником ([§7.2](chapter-07-02.md)). Дополнительная проверка: сумма оборотов по дебету по **всем** счетам должна равняться общей сумме дебетов по выборке, и то же для кредита. То есть:

SUM по счетам (оборот_дебет) = SUM(amount_dt) по факту за период;  
SUM по счетам (оборот_кредит) = SUM(amount_ct) по факту за период.

Если обороты по счетам считаются из той же фактовой таблицы, это тождество выполняется автоматически; проверка полезна, когда обороты хранятся в отдельной таблице (снимок, витрина) — тогда сверяют сумму строк этой таблицы с итогом по факту. См. [§6.2](chapter-06-02.md) (периодический снимок).

**Кросс-проверки** — взаимные проверки между разными агрегатами. Примеры: остаток на конец периода по счёту = начальное сальдо + оборот дебет − оборот кредит (для активного счёта); сумма остатков по группе счетов = сумма остатков по входящим в группу счетам (при отсутствии «висячих» проводок). Такие проверки выявляют несогласованность между снимками остатков и оборотов или ошибки в расчёте остатков. См. [§4.2](chapter-04-02.md), [§5.4](chapter-05-04.md).

## 7.3.3. Контрольные суммы (хеш, количество, итог)

**Контрольная сумма** — агрегат по выборке для быстрой проверки «ничего не изменилось» или «выгрузка совпадает с эталоном». Варианты:

- **Количество записей:** COUNT(*) по выборке (за период, по документу); сравнение с ожидаемым значением или с другой системой.
- **Сумма одного поля:** SUM(amount_dt), SUM(amount_ct) — уже используются в проверке баланса; можно сравнивать с контрольным значением из источника.
- **Хеш или контрольная строка:** хеш от конкатенации ключевых полей (или от отсортированной выгрузки) для обнаружения любых изменений данных при передаче или хранении. При несовпадении хеша — данные отличаются, нужен детальный разбор.

Контрольные суммы встраивают в пайплайн: после загрузки считают итоги и сравнивают с эталоном (из источника или из предыдущего успешного прогона); при расхождении — алерт. См. [§7.4](chapter-07-04.md).

---

## 7.3.4. Где выполнять проверки

- **После загрузки в Staging или Core:** проверка «дебет = кредит» по загруженному объёму проводок; при инкременте — по полному набору за период или по накопительному итогу.
- **При расчёте снимков и витрин:** сверка суммы оборотов в снимке с SUM по факту; сверка остатков с формулой начальное сальдо + оборот ([§4.2](chapter-04-02.md)).
- **В тестах:** на эталонных данных проверять, что баланс выполняется и контрольные суммы совпадают с ожидаемыми.

Проверки не подменяют сверку с источником ([§7.2](chapter-07-02.md)), но дополняют её: внутренняя согласованность в DWH (баланс, кросс-проверки) и согласованность с внешней системой (полнота и суммы по ключам). См. [§6.4](chapter-06-04.md).

---

## 7.3.5. Типичные ошибки

- **Проверять баланс по подмножеству проводок:** если фильтр отсекает часть проводок (например, только один счёт), равенство дебет = кредит может не выполняться; для проверки баланса брать замкнутый набор (все проводки за период или полный документ).
- **Игнорировать погрешность при FLOAT:** при хранении сумм в FLOAT сумма дебетов и сумма кредитов могут отличаться на копейки из-за представления; для денег использовать NUMERIC ([§2.2](chapter-02-02.md), [§2.3](chapter-02-03.md)).
- **Не реагировать на расхождение:** если проверка баланса или контрольная сумма выявила расхождение, должен сработать алерт или блокировка; иначе ошибка уйдёт в отчётность.

---

## Ключевое

- **Проверка баланса:** по выборке проводок, образующих замкнутый набор (период, документ), должно выполняться **SUM(amount_dt) = SUM(amount_ct)**; нарушение указывает на ошибку в данных или загрузке.
- **Итоги по счетам** и **кросс-проверки:** сумма оборотов по счетам совпадает с итогом по факту; остатки согласованы с формулой начальное сальдо + оборот; снимки и витрины сверяют с фактом.
- **Контрольные суммы** (количество записей, SUM полей, хеш) используются для быстрой проверки целостности и совпадения с эталоном; встраиваются в пайплайн с алертом при расхождении.
- Проверки выполняют после загрузки в Core и при расчёте снимков/витрин; они дополняют сверку с источником, но не заменяют её.

В [§7.4](chapter-07-04.md) мы разберём обработку расхождений и алерты: что делать при выявлении расхождения, эскалация и логирование.
