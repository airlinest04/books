# §2.4 Oracle и PostgreSQL: NUMBER, NUMERIC, DECIMAL

В [§2.3](chapter-02-03.md) мы свели рекомендации по выбору типа. Здесь — **конкретный синтаксис** в двух распространённых СУБД: Oracle и PostgreSQL. Вы узнаете, как объявлять точные числовые типы (NUMBER в Oracle, NUMERIC и DECIMAL в PostgreSQL), как задавать precision и scale, в чём отличия плавающей точки и как обеспечить **совместимость и миграцию** между СУБД при переносе схем и данных DWH.

---

## 2.4.1. Oracle: NUMBER и плавающая точка

В Oracle для точного десятичного представления используется тип **NUMBER**.

**Синтаксис:**

```text
NUMBER [(precision [, scale])]
```

- **precision** — максимальное число десятичных цифр (значащих). Диапазон: 1–38. Если не указано, допускается до 38 цифр и масштаб по умолчанию 0 (целые) или по контексту.
- **scale** — число цифр **после** десятичной запятой. Если не указано, по умолчанию 0. Может быть отрицательным (тогда округление до десятков, сотен и т.д.).

Примеры объявления колонок (среда: Oracle 21c, SQL):

```sql
-- Суммы в рублях с копейками: до 12 цифр всего, 2 после запятой
amount NUMBER(12, 2);

-- Ставка с четырьмя знаками после запятой (0,0001)
rate NUMBER(8, 4);

-- Целое количество (scale по умолчанию 0)
qty NUMBER(10);
```

Ограничения: при вставке значения с большим числом знаков после запятой Oracle округляет до scale; при превышении precision возникает ошибка. Для денег типично **NUMBER(18, 2)** или **NUMBER(15, 2)** в зависимости от требуемого диапазона.

Плавающая точка в Oracle: **BINARY_FLOAT** (32 бита) и **BINARY_DOUBLE** (64 бита). Для денежных полей не используются; эквивалентны FLOAT/DOUBLE в других СУБД по смыслу и по погрешностям из [§2.2](chapter-02-02.md). См. [Глоссарий](glossary.md).

---

## 2.4.2. PostgreSQL: NUMERIC и DECIMAL

В PostgreSQL для точного десятичного представления используются типы **NUMERIC** и **DECIMAL**.

**Синтаксис:**

```text
NUMERIC [(precision [, scale])]
DECIMAL [(precision [, scale])]
```

В PostgreSQL **NUMERIC** и **DECIMAL** эквивалентны: оба — точная арифметика, одни и те же ограничения. Если precision и scale не указаны, допускаются числа произвольной точности (ограничены только ресурсами); для финансовых полей лучше задавать явно.

- **precision** — общее число значащих десятичных цифр (до и после запятой). Максимум — до 131072 цифр до запятой и до 16383 после (по документации PostgreSQL).
- **scale** — число цифр после запятой; не может быть больше precision.

Примеры (среда: PostgreSQL 15, SQL):

```sql
-- Суммы в рублях с копейками
amount NUMERIC(12, 2);
-- или
amount DECIMAL(18, 2);

-- Ставка с четырьмя знаками
rate NUMERIC(8, 4);

-- Без параметров — произвольная точность (для расчётов, не для хранения денег по умолчанию)
value NUMERIC;
```

Плавающая точка: **REAL** (4 байта) и **DOUBLE PRECISION** (8 байт). Для денег не используются; см. [§2.2](chapter-02-02.md).

## 2.4.3. Precision и scale: общие правила и отличия

В обеих СУБД:

- **precision** задаёт максимальное число значащих цифр.
- **scale** задаёт число цифр после запятой; при scale = 2 минимальный шаг — 0,01 (копейка).
- Результат арифметики может потребовать больше цифр; при присвоении колонке с меньшей точностью СУБД округляет (или выдаёт ошибку при переполнении — зависит от настроек).

Отличия при миграции:

| Аспект              | Oracle                    | PostgreSQL                 |
|----------------------|---------------------------|----------------------------|
| Имя точного типа     | NUMBER                    | NUMERIC или DECIMAL        |
| Без precision/scale  | До 38 цифр, scale 0 по умол. | Произвольная точность   |
| Плавающая точка      | BINARY_FLOAT, BINARY_DOUBLE | REAL, DOUBLE PRECISION   |

При переносе схемы из Oracle в PostgreSQL колонки **NUMBER(p, s)** обычно заменяют на **NUMERIC(p, s)** или **DECIMAL(p, s)** с теми же p и s, чтобы диапазон и шаг совпадали. Колонки **NUMBER** без параметров в Oracle могут хранить дробные значения; в PostgreSQL им лучше задать явный NUMERIC(p, s) под реальные данные, иначе возможны различия в округлении при вставке.

## 2.4.4. Приведение типов и литералы

При записи в колонку типа NUMBER/NUMERIC значение из другого типа или строки нужно явно приводить и при необходимости округлять.

**Oracle:**

```sql
-- Приведение строки к NUMBER с масштабом
CAST('123.456' AS NUMBER(10, 2));   -- 123.46 (округление)

-- Из BINARY_DOUBLE (теряется точность, не рекомендуется для денег)
CAST(float_col AS NUMBER(18, 2));
```

**PostgreSQL:**

```sql
-- Строка в NUMERIC
CAST('123.456' AS NUMERIC(10, 2));
'123.456'::NUMERIC(10, 2);

-- Округление при загрузке из FLOAT (приведение из источника)
ROUND(float_col::NUMERIC, 2);
CAST(float_col AS NUMERIC(18, 2));
```

При загрузке денег из внешних источников (файлы, API), где числа приходят как float или строка, на этапе Staging или Core в DWH выполняют приведение к NUMERIC/NUMBER с фиксированным scale и при необходимости ROUND/TRUNC по бизнес-правилу. Так данные в Core и витринах хранятся в одном точном типе, см. [§2.3](chapter-02-03.md).

## 2.4.5. Совместимость и миграция между СУБД

При переносе DWH или отдельных таблиц между Oracle и PostgreSQL учитывайте следующее.

**Схема:**

- Заменить объявления **NUMBER(p, s)** на **NUMERIC(p, s)** (или DECIMAL(p, s)) с теми же p и s.
- **NUMBER** без параметров — заменить на **NUMERIC(p, s)**, подобрав p и s по реальным данным или по регламенту (например, NUMERIC(18, 2) для сумм).
- **BINARY_FLOAT / BINARY_DOUBLE** — на **REAL / DOUBLE PRECISION**; при этом если в этих колонках хранились деньги, нужно спланировать миграцию данных в NUMERIC и изменить схему.

**Данные:**

- При экспорте/импорте (например, CSV, dump) числа с десятичной точкой должны передаваться без потери знаков; форматы дат и разделителей (запятая/точка) должны быть согласованы.
- Если в Oracle в NUMBER-колонке хранились значения с большим числом знаков после запятой, а в PostgreSQL задан NUMERIC(p, 2), при загрузке нужно явно округлить (ROUND при вставке или в ETL).

**Запросы и функции:**

- Арифметика и встроенные функции (ROUND, TRUNC, CEIL, FLOOR) в обеих СУБД есть, но синтаксис и поведение граничных случаев могут отличаться; округление «половинок» см. в [§3.1](chapter-03-01.md) и [§8.1](chapter-08-01.md). Критичные расчёты после миграции проверяют тестами на эталонных данных.

## 2.4.6. Типичные ошибки

- **Оставить NUMBER/NUMERIC без precision и scale для денег:** в Oracle это допустимо, но затрудняет контроль диапазона и миграцию; в PostgreSQL даёт произвольную точность. Для денег явно задавать, например, NUMERIC(18, 2).
- **При миграции не заменить NUMBER на NUMERIC:** в PostgreSQL типа NUMBER нет; нужна замена на NUMERIC или DECIMAL.
- **Задать scale больше, чем нужно:** например, scale = 4 для сумм в рублях — не ошибка, но увеличивает риск путаницы и расхождений при сверке с системами, где хранят до копеек (scale = 2). Лучше единый масштаб по регламенту.
- **Импортировать деньги как FLOAT/DOUBLE:** при загрузке в PostgreSQL или Oracle из файлов/API убедиться, что денежные поля сразу приводятся к NUMBER/NUMERIC с округлением, а не попадают в колонки с плавающей точкой.

---

## Ключевое

- **Oracle:** точный тип — **NUMBER(precision, scale)**; плавающая точка — BINARY_FLOAT, BINARY_DOUBLE. Для денег типично NUMBER(18, 2) или NUMBER(12, 2).
- **PostgreSQL:** точные типы — **NUMERIC(precision, scale)** и **DECIMAL(precision, scale)** (эквивалентны); плавающая точка — REAL, DOUBLE PRECISION. Для денег — NUMERIC(18, 2) или аналог с явными p, s.
- При **миграции** Oracle → PostgreSQL: NUMBER(p, s) заменять на NUMERIC(p, s); NUMBER без параметров — на NUMERIC(p, s) по регламенту; денежные поля из float-источников приводить к NUMERIC с явным округлением.
- При загрузке данных в DWH **приводить** денежные значения к NUMBER/NUMERIC с заданным scale на этапе Staging/Core, не хранить деньги в типах с плавающей точкой.

В [§3.1](chapter-03-01.md) мы перейдём к видам округления: арифметическое округление (ROUND), половинки и стандарты.
