# §9.2 Расчёт с округлением и проверкой

В [§9.1](chapter-09-01.md) мы задали общую постановку пайплайна. Здесь — **этапы расчёта**, **где округлять** суммы и агрегаты, и **контрольные суммы на каждом этапе**, чтобы расхождения можно было быстро локализовать. Загрузка в витрину и сверка с источником — в [§9.3](chapter-09-03.md); типовые ошибки — в [§9.4](chapter-09-04.md). См. [Глоссарий](glossary.md).

---

## 9.2.1. Этапы расчёта в пайплайне

Расчёт в пайплайне финансовых данных можно разбить на этапы:

1. **Staging** — приведение типов (суммы в NUMERIC), округление до копеек при загрузке из строки или float ([§2.4](chapter-02-04.md)); проверка ключей; дедупликация.
2. **Загрузка в Core** — запись проводок в факт движений; суммы уже в NUMERIC(18,2), без повторного округления при копировании.
3. **Агрегация** — обороты за период (SUM по группам), остатки на дату (нарастающий итог или снимок); при записи в таблицу оборотов/остатков — округление по регламенту ([§1.4](chapter-01-04.md)).
4. **Расчёт производных** — проценты, комиссии, налог по строкам; округление по строкам или один раз по итогу ([§5.1](chapter-05-01.md)–[§5.4](chapter-05-04.md)).
5. **Загрузка в витрину** — запись итогов в Mart; округление при записи или при выборке — единообразно ([§9.3](chapter-09-03.md)).

На каждом этапе полезно считать **контрольные суммы** (или счётчики), чтобы при сверке понять, на каком шаге возникло расхождение. См. [§5.4](chapter-05-04.md), [§7.2](chapter-07-02.md).

---

## 9.2.2. Где округлять

**При загрузке из источника (Staging):** один раз при приведении к NUMERIC — ROUND(value, 2) или CAST с масштабом; дальше по пайплайну суммы не переокругляются при копировании. См. [§2.4](chapter-02-04.md).

**При агрегации оборотов:** если бизнес-правило — «итог = округление суммы», то ROUND(SUM(amount_dt), 2) и ROUND(SUM(amount_ct), 2) при записи в таблицу оборотов или при выдаче в витрину. Если «итог = сумма округлённых» — каждая проводка уже в копейках (из Staging), SUM даёт сумму округлённых; при необходимости явно зафиксировать: ROUND(..., 2) при записи. Выбор стратегии — в регламенте ([§1.4](chapter-01-04.md)).

**При расчёте процентов/комиссий/налога по строкам:** округление по строкам — ROUND(база × ставка, 2) в каждой строке; затем проверка сходимости: сумма по строкам vs ROUND(SUM(база) × ставка, 2); порог и эталон заданы регламентом ([§5.4](chapter-05-04.md)).

**При выводе в отчёт или витрину:** округление в одном месте — при записи в витрину или при SELECT в отчёт; не дублировать ROUND в нескольких слоях, иначе правила разъедутся. См. [§1.2](chapter-01-02.md).

**Типичная ошибка:** округлять в Staging, потом снова при агрегации с другой точностью или при записи в витрину без единого правила — это затрудняет сверку и разбор расхождений ([§9.4](chapter-09-04.md)).

## 9.2.3. Контрольные суммы после Staging

После этапа Staging (до загрузки в Core) считают контрольные величины по загруженному набору проводок за период:

- **Количество строк** — COUNT(*).
- **Сумма дебета** — SUM(amount_dt).
- **Сумма кредита** — SUM(amount_ct).
- **Проверка баланса** — SUM(amount_dt) = SUM(amount_ct) в пределах допустимой погрешности ([§7.3](chapter-07-03.md)); при нарушении — алерт до загрузки в Core.

Эти же величины считают по **источнику** за тот же период (по ключам сверки). Расхождение по количеству или по суммам указывает на потерю/дублирование данных или ошибку преобразования на Staging. См. [§7.2](chapter-07-02.md) (ключи сверки).

---

## 9.2.4. Контрольные суммы после загрузки в Core

После INSERT в факт движений по тому же периоду:

- **COUNT(*)** по факту за период.
- **SUM(amount_dt), SUM(amount_ct)** по факту.

Сравнение с контрольными суммами после Staging: должны совпадать (один и тот же набор строк). Если пайплайн идемпотентный и перезаписывает период — сравнение идёт с «ожидаемым» итогом из Staging, а не с предыдущим состоянием Core. См. [§9.3](chapter-09-03.md).

---

## 9.2.5. Контрольные суммы после агрегации

После расчёта оборотов за период:

- **Сумма оборотов по дебету** по всем счетам за период (или по выбранной группе счетов).
- **Сумма оборотов по кредиту** за тот же период.
- Ожидание: эти суммы совпадают с SUM(amount_dt) и SUM(amount_ct) по факту проводок за тот же период (обороты — просто агрегат факта). Расхождение возможно только если агрегация считалась по подмножеству проводок или с другим фильтром — тогда явно зафиксировать правило и сверять с тем же подмножеством.

Для остатков на дату: сумма остатков по выбранным счетам на одну и ту же дату должна быть согласована с начальным сальдо + обороты за период до этой даты; при использовании снимков — контрольная сумма по снимку vs расчёт из факта. См. [§4.2](chapter-04-02.md), [§4.3](chapter-04-03.md).

---

## 9.2.6. Контрольные суммы для процентов и налогов

Если на этапе расчёта считаются проценты, комиссии или налог по строкам ([§5.1](chapter-05-01.md)–[§5.4](chapter-05-04.md)):

- **Сумма по строкам:** SUM(округлённое_значение_по_строке).
- **Расчётная сумма:** ROUND(SUM(база) × ставка, 2) (или по заданной формуле).
- **Проверка сходимости:** разница по модулю не превышает допустимую погрешность ([§1.3](chapter-01-03.md)); при превышении — алерт и при необходимости блокировка загрузки в витрину ([§5.4](chapter-05-04.md)).

Контрольную величину (например, расчётную сумму по документу или по партии) можно сохранять в логе пайплайна или в служебной таблице для аудита.

---

## 9.2.7. Сводка: на каком этапе что проверять

| Этап              | Контрольные величины                          | С чем сверять                          |
|-------------------|-----------------------------------------------|----------------------------------------|
| После Staging     | COUNT, SUM(dt), SUM(ct), баланс dt=ct         | Источник за период                     |
| После Core        | COUNT, SUM(dt), SUM(ct) по факту за период   | Суммы после Staging                    |
| После агрегации   | Суммы оборотов dt/ct по периоду               | Факт за тот же период                  |
| Проценты/налог    | Сумма по строкам, расчётная сумма            | Друг с другом, порог погрешности      |
| Витрина           | Итоги по витрине за период                    | Core (обороты/остатки)                 |

Единый период и одни и те же ключи (счёт, дата, документ) на всех этапах — иначе сверка теряет смысл. См. [§7.2](chapter-07-02.md).

---

## Ключевое

- Этапы расчёта: Staging (округление при приведении типов) → Core (без повторного округления) → агрегация (обороты, остатки; округление по регламенту) → производные (проценты, налог; сходимость по строкам) → витрина (единое место округления при выдаче).
- **Где округлять:** один раз при загрузке в Staging; при агрегации и при выводе в витрину — по зафиксированной стратегии; не дублировать округление в разных слоях без правила.
- **Контрольные суммы:** после Staging (COUNT, SUM(dt), SUM(ct), баланс) — сверка с источником; после Core — совпадение с Staging; после агрегации — совпадение с фактом; для процентов/налога — сходимость суммы по строкам с расчётной суммой в пределах порога.
- Сводная таблица этап–контроль–сверка помогает локализовать расхождение; период и ключи должны быть едиными.

В [§9.3](chapter-09-03.md) мы разберём загрузку в витрину (INSERT/UPDATE, идемпотентность) и сверку с источником.
